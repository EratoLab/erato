# Microsoft Teams bot

Erato can answer in Microsoft Teams personal chats, group chats and channels. Chats started in Teams are ordinary Erato chats: they appear in the web app and the Teams tab, keep their history, and use the same assistants, models, policies, MCP tools and [SharePoint integration](./sharepoint) as the web app.

## Overview

- **Personal chats** stream the answer while it is generated.
- **Group chats and channels** answer when the bot is @mentioned, reply in the thread and mention the requester. The preceding messages of the conversation are attached as context.
- **Files** uploaded in a personal chat, pasted images, and SharePoint/OneDrive files shared in a conversation become chat files.
- **Tool approvals** appear as an Adaptive Card; only the person who asked can decide.
- **Background tasks** post their result back into the Teams conversation once they finish.
- `/new` starts a fresh Erato chat in the current conversation.

In the chat list of the web app and the add-ins, the **Source** filter shows only the chats started in Teams, or hides them. It covers the bot and the Teams tab.

Users are recognized by their Entra object ID, which Erato records whenever they sign in to the web app or the Teams tab. People who have never opened Erato are asked to do so once.

## Prerequisites

- Erato signs users in with Microsoft Entra ID.
- The [Teams app](../configuration#integrationsms_officeteamsenabled) (`integrations.ms_office.teams`) is enabled, so the bot can be shipped in the same app package as the tab.
- You can manage the customer's existing Entra app registration, create or manage an Azure Bot resource, and grant admin consent.

## Setup

Start at `/office-addin/setup` → **Teams** for deployment-specific values.
Follow the manual steps below, or use the optional Cloud Shell helper at the end.

The Teams tab uses the existing Office add-in MSAL registration. The conversational
bot needs an Azure Bot resource and an OAuth connection to obtain delegated Graph
tokens. Both can use the customer's existing Entra application registration.

Erato stays on its existing infrastructure. Azure routes messages to the public
Erato endpoint and manages the bot's OAuth connection. An Azure subscription and
permission to manage the relevant Entra app and Azure resources are required.
See [Microsoft's Azure setup guide](https://learn.microsoft.com/en-us/microsoftteams/platform/teams-sdk/teams/azure-configuration).

These instructions target public Azure and the global Bot Framework token service.
Regional or sovereign deployments must use their corresponding token service,
OAuth callback, and manifest domains.

### 1. Record the identities and deployment URL

| Name used below | Meaning                                                             |
| --------------- | ------------------------------------------------------------------- |
| `TENANT_ID`     | Customer's Entra tenant                                             |
| `BOT_APP_ID`    | Entra client ID registered as the bot's messaging identity          |
| `AUTH_APP_ID`   | Entra client ID used by the add-in, OAuth connection and bot SSO    |
| `TEAMS_APP_ID`  | Package ID in `integrations.ms_office.teams.app_id`; keep it stable |
| `ERATO_HOST`    | Public Erato hostname, without `https://` or a path                 |
| `SSO_RESOURCE`  | Exact Application ID URI exposed by `AUTH_APP_ID`                   |

For a new deployment, `BOT_APP_ID` and `AUTH_APP_ID` can both be the existing
customer-owned single-tenant add-in registration. A bot authenticates as a server
and needs a client secret even though browser MSAL does not use one.

For an existing deployment with separate bot registrations, retain `BOT_APP_ID`
and its working credentials. The OAuth connection can use `AUTH_APP_ID` separately.
For our combined tab/bot package, keeping `AUTH_APP_ID` equal to the current tab's
client ID avoids changing its NAA identity. The generated manifest has one
`webApplicationInfo.id`; `bots[].botId` identifies the messaging bot.
Microsoft documents [separate bot and authentication registrations](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/authentication/bot-sso-register-aad#to-configure-authorized-client-application).

### 2. Extend the existing Entra authentication registration

Open **Entra admin center → App registrations → the application with `AUTH_APP_ID`**.
Keep its existing redirect URIs, scopes, permissions, and credentials.

1. Under **Manifest**, set `api.requestedAccessTokenVersion` to `2`. This concerns
   access tokens issued for this application's exposed API; review existing API
   consumers if the registration already exposes one.
2. Under **Expose an API**, configure the Application ID URI. For a combined
   bot/tab app, use `api://ERATO_HOST/botid-AUTH_APP_ID`. Record this as
   `SSO_RESOURCE` without `/access_as_user` at the end.
3. Add an enabled delegated scope named **`access_as_user`**. Use clear admin/user
   consent labels such as “Access Erato as the signed-in user”.
4. Under **Authorized client applications**, add both clients below and select
   `access_as_user` for each.

| Client                   | Application ID                         |
| ------------------------ | -------------------------------------- |
| Teams desktop and mobile | `1fec8e78-bce4-4aaf-ab1b-5451cc387264` |
| Teams web                | `5e3ce6c0-2b1f-4285-8d4b-75ee78787346` |

5. Under **Authentication → Add a platform → Web**, add
   `https://token.botframework.com/.auth/web/redirect`. Keep the existing Web
   callbacks and SPA `brk-multihub://ERATO_HOST` redirect.
6. Under **API permissions → Microsoft Graph → Delegated permissions**, include
   the following permissions, together with any additional scopes Erato uses:

   ```text
   openid profile email offline_access User.Read GroupMember.Read.All
   Files.Read.All Sites.Read.All Chat.Read ChannelMessage.Read.All
   ```

7. Have an appropriately privileged tenant administrator **grant admin consent**.
   Configuring permissions alone does not grant consent. Consent on an old bot
   registration does not transfer to the shared authentication registration.
8. Under **Certificates & secrets**, add a dedicated OAuth connection credential.
   Use its **Value**, not its Secret ID, in step 4. Keep existing credentials.

If staging and production share an authentication registration, retain both
environment-specific resource URIs in its `identifierUris` array (the Entra
manifest editor or Graph API can edit this array). Use the same `access_as_user`
scope and Teams client pre-authorizations. Process the environments sequentially.

References: [Entra SSO configuration](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/authentication/bot-sso-register-aad),
[combined bot/tab manifest](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/authentication/bot-sso-manifest),
[Application ID URI policy](https://learn.microsoft.com/en-us/entra/identity-platform/identifier-uri-restrictions).

### 3. Create or inspect the Azure Bot resource

Open **Azure Portal → All resources** and find the existing **Azure Bot**.
If none exists, create an Azure Bot in the customer's subscription/resource group,
select **Single Tenant → Use existing app registration**, and supply `BOT_APP_ID`
and `TENANT_ID`. Record the resource name, subscription and resource group.

Under **Configuration**, set the messaging endpoint to:

```text
https://ERATO_HOST/api/integrations/ms_teams/messages
```

Under **Channels**, enable **Microsoft Teams**. The bot credential corresponding
to `BOT_APP_ID` belongs in the Erato deployment's secret storage. This is separate
from the OAuth credential when `BOT_APP_ID` and `AUTH_APP_ID` differ.

### 4. Configure the OAuth connection

On the Azure Bot resource, open **Configuration → OAuth Connection Settings**.
For a staged rollout, create a new connection named **`graph-sso`** and keep any
existing `graph` connection until validation is complete.

| Field              | Value                                                       |
| ------------------ | ----------------------------------------------------------- |
| Name               | `graph-sso`                                                 |
| Service provider   | Azure Active Directory v2                                   |
| Client ID          | `AUTH_APP_ID`                                               |
| Client secret      | The dedicated credential value from step 2                  |
| Tenant ID          | `TENANT_ID`                                                 |
| Token Exchange URL | `SSO_RESOURCE`, exactly as exposed in Entra                 |
| Scopes             | The space-separated delegated Graph scopes listed in step 2 |

Save and use **Test Connection**. A successful test verifies interactive OAuth;
it does not establish that Teams silent SSO works. That requires the package and
client checks below. See [Microsoft's OAuth connection configuration](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/authentication/bot-sso-register-aad#configure-oauth-connection).

### 5. Configure the Erato deployment

Merge these settings into the existing bot configuration:

```toml
[integrations.ms_office.teams.bot]
enabled = true
app_id = "BOT_APP_ID"
tenant_id = "TENANT_ID"
oauth_connection_name = "graph-sso"
public_base_url = "https://ERATO_HOST"
sso_app_id = "AUTH_APP_ID"
sso_resource = "SSO_RESOURCE"
# Supply app_password through the deployment's secret storage.
```

Keep the add-in's `msal_client_id = "AUTH_APP_ID"`. Keep `TEAMS_APP_ID` and the
existing bot identity stable. Increase the Teams manifest version so the updated
package is distinguishable from the installed version.

The exact path `/api/integrations/ms_teams/messages` must reach the backend without
oauth2-proxy stripping its Bot Connector Authorization header. The Erato Helm chart
supports `msTeamsBot.directRoute`; configure the ingress/network-policy allowance
for the actual controller. For example:

```yaml filename="values.yaml"
msTeamsBot:
  directRoute:
    enabled: true
    ingressFrom:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: ingress-nginx
```

The backend validates this route's authentication.

Apply the deployment using the environment's normal deployment procedure. The
optional helper below does not modify Helm, Kubernetes, or Erato configuration.

### 6. Update the Teams package and verify the user experience

1. Open `https://ERATO_HOST/office-addin/setup`, select **Teams**, and download the
   package. Inspect `manifest.json` inside the ZIP:
   - `bots[0].botId` is `BOT_APP_ID`.
   - `webApplicationInfo.id` is `AUTH_APP_ID`.
   - `webApplicationInfo.resource` is exactly `SSO_RESOURCE`.
   - `nestedAppAuthInfo` retains the tab's NAA redirect.
2. Upload the package as an **update to the existing app** through the customer's
   Teams/Microsoft 365 app-management process. Downloading a new manifest does
   not update the installed app.
3. Open the Erato web app or Teams tab once with the test user to record their
   Entra object ID. Then test a fresh personal bot conversation.
4. Verify that user authentication completes without clicking **Sign in**, subject
   to the tenant's consent and Conditional Access requirements. Also test the
   Teams web client, existing tab login, and the other Office add-ins.
5. Test an @mention and a file operation after the personal-chat check succeeds.

Our current handler sends “Please sign in…” even when the OAuth card can trigger
silent SSO. After a successful exchange it says “You're signed in…” and asks the
user to resend their question. The persistent **Sign in** button is the useful
symptom, not the initial text by itself. Channels use a personal conversation
for authentication; don't expect a channel's shared conversation to perform SSO.

If necessary, roll back the deployment to `oauth_connection_name = "graph"`, remove
the SSO overrides, and distribute a higher-version package with the prior
authentication manifest. Keep the original connection and credentials during
rollout. Additive changes to a shared Entra app also affect the other environments
using it; remove only additions whose consumers you have checked.

## Configuration Options

| Option                  | Type    | Default                            | Description                                                                                          |
| ----------------------- | ------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `enabled`               | boolean | `false`                            | Whether the Teams bot is enabled                                                                     |
| `app_id`                | string  |                                    | Bot app registration ID                                                                              |
| `app_password`          | string  |                                    | Bot client secret                                                                                    |
| `tenant_id`             | string  |                                    | Entra tenant whose activities are accepted                                                           |
| `oauth_connection_name` | string  |                                    | Azure Bot OAuth connection that yields the user's Graph token                                        |
| `token_service_url`     | string  | `"https://token.botframework.com"` | Bot Framework token service                                                                          |
| `sso_app_id`            | string  |                                    | App ID for silent sign-in; set together with `sso_resource`                                          |
| `sso_resource`          | string  |                                    | Token exchange URL for silent sign-in, for a combined tab/bot app, `api://<host>/botid-<sso_app_id>` |
| `public_base_url`       | string  |                                    | HTTPS origin used for links from Teams back to Erato chats                                           |
| `assistant_id`          | string  |                                    | Assistant that new Teams chats are bound to                                                          |
| `context_message_count` | integer | `20`                               | Preceding group chat or channel messages attached as context (`0` disables)                          |
| `streaming`             | boolean | `true`                             | Stream answers in personal chats                                                                     |
| `security_groups_only`  | boolean | `true`                             | Resolve only security groups; match the web login's `groups` claim setup                             |

## Limitations

- MCP servers that forward the user's OIDC ID token receive none on Teams requests; servers using access-token forwarding get the Graph token.
- Client tools that run in the desktop sidecar are not available in Teams. The answer links to the chat in Erato instead.
- In group chats and channels, answers built from the requester's data are visible to everyone in the conversation.

## Optional: use the setup page and Azure Cloud Shell

Open `https://ERATO_HOST/office-addin/setup` and choose **Teams**. The page shows
this deployment's messaging identity, authentication app, SSO URI, and Erato
configuration snippet. These are package settings, not a live Azure status check.

At the end of the bot instructions, expand **Optional: check and configure with
Azure Cloud Shell**. This is the customer entry point; there is no need to clone
an infrastructure repository or install Python, PowerShell or Azure CLI locally.

1. Check **Current OAuth connection name** against the existing Azure Bot
   connection or Erato's `oauth_connection_name`. The package does not contain
   this value; the page starts with `graph`.
2. Choose a separate **New SSO connection name**, initially `graph-sso`.
3. Click **Download Cloud Shell helper** and **Open Azure Cloud Shell**. Choose
   **Bash**, sign in to the bot's tenant, and select its subscription. Cloud Shell
   can run without persistent storage. First-time use may require registration
   of the `Microsoft.CloudShell` resource provider in the subscription.
4. Use **Manage files → Upload** to upload `erato-teams-setup.sh`.
5. Run the read-only audit:

   ```bash
   bash ~/erato-teams-setup.sh
   ```

The helper finds the existing bot by its app ID in the selected subscription.
If necessary, select the subscription with `az account set --subscription ID`.
For multiple matching resources, supply `--resource-group GROUP --bot-name NAME`.
The helper validates the bot identity and tenant before allowing SSO changes.
It requires an existing single-tenant bot with its messaging endpoint and Teams
channel already configured.

To preview the changes without applying them:

```bash
bash ~/erato-teams-setup.sh --plan-sso
```

After reviewing the plan, this explicit mode applies the Azure/Entra additions:

```bash
bash ~/erato-teams-setup.sh --apply-sso
```

Apply preserves existing scopes, redirects, permissions and credentials. It adds
SSO settings and any missing Graph delegated permissions to the selected
single-tenant authentication app, and creates a separate OAuth connection with
a dedicated credential. It never overwrites a differently configured connection;
a matching one is reused. The helper does not create a bot, grant admin consent,
deploy Erato, or install a Teams package. Complete those steps above separately.

The apply operator needs permission to update the selected Entra app/add a
credential and write Bot Service connection resources in the chosen resource
group. Tenant consent may require a different administrator. Reader access alone
is enough for some Azure inspection, not all Graph reads or applying the plan.
Do not run apply concurrently for environments that share an authentication app.

Record the returned credential key ID and expiry for rotation (the helper uses a
365-day lifetime, subject to tenant policy). Secret values are not printed. If a
write fails, inspect the reported partial state before retrying; app additions or
a newly created credential may already exist.

Exit codes are `0` for passed checks, `1` for missing settings, and `2` for an
incomplete audit or failed operation. A plan can exit `1` while successfully
showing changes for missing SSO settings. Apply exits `0` when its cloud writes
complete, not when end-to-end Teams SSO has been verified. Use `--json` to obtain
a support report without tokens or secret values.

The download is a readable Bash launcher containing the helper and a snapshot of
the deployment's manifest. It uses Python and Azure CLI already installed in
Cloud Shell, and needs no network access from Cloud Shell to Erato or to a source
repository. Download it again after deployment changes. It checks the package
snapshot, not the package installed in a user's Teams client. Administrators who
prefer local execution need Bash, Python 3.9+, Azure CLI and curl; browser-based
Cloud Shell is the supported path for a machine without those tools.
