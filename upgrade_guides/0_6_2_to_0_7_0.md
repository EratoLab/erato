## `[assistants.delegation]` → `[delegation]` / `[delegation.assistants]`

Added by [#1107](https://github.com/EratoLab/erato/pull/1107). Honored unchanged, with a startup deprecation warning, until **0.8.0**.

### What changed

Delegation configuration moved out from under `[assistants]` into its own
top-level `[delegation]` table, split into `[delegation.assistants]`
(in-chat `@mention` delegation — the direct replacement for the old table)
and the new `[delegation.tasks]` (model-planned tasks, see
["Adopting model-planned delegated tasks"](#delegation-tasks) below).

On startup, if `[assistants.delegation]` is set, the backend automatically
migrates its 8 fields onto the new `[delegation]` struct and logs a warning
— so **nothing breaks today**. But:

- Setting **both** `[assistants.delegation]` (non-default) and a non-default
  `[delegation]` table at the same time is a hard startup failure. You cannot
  incrementally set some new keys while leaving the old table in place with
  real values.
- The old table is undocumented in new config references and will stop being
  read at 0.8.0.

### Before (0.6.2)

```toml
[assistants.delegation]
enabled = true
max_mentions_per_message = 3
run_timeout_seconds = 600
result_max_chars = 16000
allow_background = false
max_concurrent_background_runs = 5
auto_archive_after_days = 7
preamble = "You are working on a task that another conversation delegated to you. ..."
```

### After (0.7.0+)

```toml
[delegation]
run_timeout_seconds = 600
result_max_chars = 16000
allow_background = false
max_concurrent_background_runs = 5
auto_archive_after_days = 7
preamble = "You are working on a task that another conversation delegated to you. ..."

[delegation.assistants]
enabled = true
max_mentions_per_message = 3
```

Field-for-field mapping (old → new):

| `[assistants.delegation]` | New location |
|---|---|
| `enabled` | `delegation.assistants.enabled` |
| `max_mentions_per_message` | `delegation.assistants.max_mentions_per_message` |
| `run_timeout_seconds` | `delegation.run_timeout_seconds` |
| `result_max_chars` | `delegation.result_max_chars` |
| `allow_background` | `delegation.allow_background` |
| `max_concurrent_background_runs` | `delegation.max_concurrent_background_runs` |
| `auto_archive_after_days` | `delegation.auto_archive_after_days` |
| `preamble` | `delegation.preamble` |

### Action required

Migrate to `[delegation]` / `[delegation.assistants]` before 0.8.0. Do not
set both tables with non-default values at once — startup will reject that
configuration outright, by design, to force an explicit choice rather than
an ambiguous merge.

### Related: reserved tool namespace

The same PR also reserves the `erato` tool/MCP-server namespace. If your
deployment configures an MCP server with id `erato`, or a client tool named
`propose_client_action`, `delegate_to_assistant`, `delegate_task`, or
`collect_tasks`, see
["`erato` tool/MCP-server namespace reserved"](#reserved-tool-namespace) —
that change has **no grace period**.

## `[experimental_facets]` → `[facets]`

Added by [#1158](https://github.com/EratoLab/erato/pull/1158). No removal date set.

### What changed

The facets feature is now stable and the `experimental_` prefix is dropped
from the table name and all nested keys. A Serde alias keeps old
`erato.toml` files parsing and working **unchanged** — this is not a
breaking change today. The catch: there is **no startup warning or log
line** when the old key is used. The deprecation is only visible in the
generated config reference / docs, so an operator who doesn't check the
docs will never notice they're on a deprecated key.

### Before (0.6.2)

```toml
[experimental_facets]
only_single_facet = false
priority_order = ["extended_thinking", "web_search"]
tool_call_allowlist = ["web-search-mcp/*"]

[experimental_facets.facets.web_search]
display_name = "Web search"
icon = "iconoir-globe"
tool_call_allowlist = ["web-search-mcp/*", "web-access-mcp/*"]
```

### After (0.7.0+)

```toml
[facets]
only_single_facet = false
priority_order = ["extended_thinking", "web_search"]
tool_call_allowlist = ["web-search-mcp/*"]

[facets.facets.web_search]
display_name = "Web search"
icon = "iconoir-globe"
tool_call_allowlist = ["web-search-mcp/*", "web-access-mcp/*"]
```

The rename is purely mechanical: every `experimental_facets.` prefix becomes
`facets.` — no field was renamed, added, or removed alongside the table.

### Action required

Rename the table and all nested `experimental_facets.*` keys to `facets.*`
proactively. Since there's no runtime warning to prompt you, grep your
`erato.toml` (and any `*.auto.erato.toml` overlays) for
`experimental_facets` now rather than waiting for a future removal.

## `model_settings.generate_images` removed (breaking, no replacement)

Removed by [#829](https://github.com/EratoLab/erato/pull/829). **No grace
period — the setting is gone, not deprecated.**

### What changed

The special image-generation chat mode (a per-model setting that made a
provider generate an image from the user's last message via, e.g., DALL-E,
instead of a normal text response) has been deleted entirely: the config
field, the request-handling branch, and the integration tests are all
removed.

**This is silent.** The config struct this field lived on does not reject
unknown keys, so a deployment that still sets `generate_images = true`
will not fail at startup — the key is just dropped, and the provider quietly
starts behaving like a normal text model instead of generating images. There
is **no built-in replacement** in this release; if you need equivalent
functionality, you must provide it via an MCP tool or other external
mechanism.

### Before (0.6.2)

```toml
[chat_providers.providers.my-image-provider]
provider_kind = "openai"
model_name = "gpt-image-capable-model"

[chat_providers.providers.my-image-provider.model_settings]
generate_images = true
```

### After (0.7.0+)

```toml
[chat_providers.providers.my-image-provider]
provider_kind = "openai"
model_name = "gpt-image-capable-model"

# generate_images no longer exists — remove it. If users need image
# generation, offer it through an MCP tool instead; there is no equivalent
# built-in replacement.
```

### Action required

Search your configuration for `generate_images` under any
`chat_providers.providers.<id>.model_settings` (or the equivalent
`chat_provider.model_settings` / `experimental_facets.facets.<id>.model_settings`
/ `facets.facets.<id>.model_settings` override blocks) and remove it. If
end users relied on this for image generation, communicate the removal —
there is no automatic fallback, and no startup error will tell you it's
gone.

<a id="reserved-tool-namespace"></a>

## `erato` tool/MCP-server namespace reserved (breaking, no grace period)

Added by [#1107](https://github.com/EratoLab/erato/pull/1107). **Enforced
immediately — startup fails if violated, no warning period.**

### What changed

The `erato` namespace is now reserved for built-in synthetic tools used by
the delegation feature. Startup validation now rejects:

- an MCP server configured with id `erato` (`[mcp_servers.erato]`)
- a client tool with `namespace = "erato"`
- a client tool named exactly `propose_client_action`, `delegate_to_assistant`,
  `delegate_task`, or `collect_tasks`

This only affects a deployment that happened to already use one of these
exact names — it is otherwise inert.

### Before (0.6.2) — now rejected at startup

```toml
[mcp_servers.erato]
transport_type = "sse"
url = "http://127.0.0.1:9000/sse"

[client_tools.tools.my_delegate]
name = "delegate_task"
namespace = "erato"
```

### After (0.7.0+) — pick any non-reserved name

```toml
[mcp_servers.my_custom_erato_integration]
transport_type = "sse"
url = "http://127.0.0.1:9000/sse"

[client_tools.tools.my_delegate]
name = "run_custom_delegate"
namespace = "custom"
```

### Action required

Before upgrading, check your configuration for:

- any `[mcp_servers.<id>]` where `<id>` is literally `erato`
- any `[client_tools.tools.<id>]` with `namespace = "erato"`
- any client tool named `propose_client_action`, `delegate_to_assistant`,
  `delegate_task`, or `collect_tasks`

and rename it. Unlike the other deprecations in this release, this is
enforced the moment you upgrade — the backend will panic at startup, not
log a warning.

## Adopting model-planned delegated tasks (`[delegation.tasks]`)

Added by [#1107](https://github.com/EratoLab/erato/pull/1107) and friends
(see the "Delegated assistants and model planned tasks" entry in
`CHANGELOG.md`). Disabled by default — zero effect until configured.

### What it does

Lets the model itself plan and dispatch bounded sub-tasks (via the reserved
`erato/delegate_task` tool) instead of only supporting user-initiated
`@mention` delegation. Enabling the table alone does nothing: the tool must
also be selected into a facet's `tool_call_allowlist`.

### Before (0.7.0 default — feature inert)

```toml
# No [delegation.tasks] table: the model is never offered erato/delegate_task.
```

### After — minimal opt-in

```toml
[delegation.tasks]
enabled = true
max_tasks_per_turn = 5
max_parallel = 3
max_server_tool_calls_per_task = 5
max_client_tool_calls_per_task = 30
persona = "inherit"          # "inherit" (origin assistant persona) or "bare"
run_modes = ["wait"]          # or ["wait", "async"]
scheduling = "when_idle"

# CAUTION: always pair a reserved erato/* pattern with a real MCP pattern.
# An allowlist naming ONLY erato/* narrows the derived MCP filter to
# nothing, dropping every other MCP tool while this facet is active.
[facets.facets.plan]
display_name = "Plan & delegate"
icon = "iconoir-task-list"
tool_call_allowlist = ["erato/delegate_task", "web-search-mcp/*"]
```

### After — with per-facet overrides and approval policy

```toml
[facets.facets.plan.delegation]
max_tasks_per_turn = 3
max_client_tool_calls_per_task = 40   # generous: runs on the user's device
max_server_tool_calls_per_task = 4    # stingy: shares backend MCP capacity
child_facet_ids = ["web_search"]

[facets.facets.plan.delegation.approval]
mode = "plan"
plan_min_tasks = 3
```

### Notes

- `delegation.tasks.enabled` has no coupling requirement with
  `assistants.enabled` (unlike `delegation.assistants.enabled`, which
  requires it) — tasks can be used without the assistants feature at all.
- Two tool-call budgets per task run are independent and never summed:
  server-executed (MCP) calls share backend capacity; client-executed calls
  run on the user's own device and can be set more generously.
- `multitask_strategy` and `scheduling` both accept reserved-but-unimplemented
  spellings (`"enqueue"`/`"interrupt"`) that are rejected at load — don't set
  them expecting them to work yet.

## Adopting the Desktop Sidecar (`[desktop_sidecar]`)

See the "Desktop Sidecar for local sources" entry in `CHANGELOG.md`.
Disabled by default.

### What it does

Lets the backend distribute and connect to an optional desktop companion
app giving users controlled access to local mailboxes, folders, documents,
and search, surfaced to the model as client tools.

### Before (0.7.0 default — feature inert)

```toml
# No [desktop_sidecar] table: no distribution artifacts served, no
# connection status shown in Preferences.
```

### After — serve the installer and show connection status

```toml
[desktop_sidecar]
show_settings_tab = true
# show_settings_tab_office_addin = true  # optional override for the Outlook add-in; inherits show_settings_tab if omitted

[desktop_sidecar.distribution]
enabled = true
directory = "/app/desktop-sidecar-artifacts"
```

### After — white-labeled / side-by-side deployment

```toml
[desktop_sidecar]
show_settings_tab = true
display_name = "Acme Assistant Sidecar"
icon = "/public/common/custom-theme/acme/sidecar-icon.png"
port = 8765
directory_suffix = "acme"

[desktop_sidecar.distribution]
enabled = true
directory = "/app/desktop-sidecar-artifacts"
```

### Notes

- With `[desktop_sidecar.distribution]` enabled, the backend validates
  `manifest.json` and all declared artifacts at startup — a malformed or
  incomplete artifact set is a startup failure, not a silent skip.
- `local_delegation.*` sub-keys (signing keys, verification keys, backend
  origin) are only needed if you're wiring the sidecar into durable local
  delegation; leave them unset otherwise.
- This feature requires a configured and connected Sidecar on the client
  side; individual tools and capabilities remain separately gated by
  `client_tools` / facet allowlists.

<a id="client-tools"></a>

## Adopting durable client tools (`[client_tools]`)

See the "MCP controls" entry in `CHANGELOG.md`. Disabled by default
(`durable_operations_enabled = false`).

### What it does

Declares client-executed tools (results fed back inline, same turn — unlike
`propose_client_action`, which is terminal and user-confirmed) and
optionally lets long-running/pollable client operations park durably
instead of blocking the turn.

### Before (0.7.0 default)

```toml
# No [client_tools] table: no client-executed tools are offered, and no
# client operation can park durably.
```

### After — declare a tool and select it via a facet

```toml
[client_tools]
durable_operations_enabled = false   # leave off unless you need durable parking

[client_tools.tools.outlook_fetch_availability]
name = "fetch_availability"          # must be dot-free; "." breaks OpenAI/Anthropic tool names
namespace = "outlook"                # used only for allowlist selection, e.g. "outlook/*"
description = "Read the signed-in user's Outlook calendar to find a slot that works for everyone."
parameters = """
{
  "type": "object",
  "properties": {
    "lookahead_days": { "type": "integer", "minimum": 1, "maximum": 62 },
    "attendees": { "type": "array", "items": { "type": "string" }, "maxItems": 15 }
  },
  "additionalProperties": false
}
"""

[action_facets.facets.outlook_schedule]
display_name = "Outlook Appointment Scheduling"
platform = "outlook"
tool_call_allowlist = ["outlook/*"]
```

### After — bound compact replay for earlier turns

```toml
[client_tools.tools.outlook_fetch_availability.replay]
mode = "receipt"                      # default is "full"
keep_input_fields = ["$.lookahead_days"]
keep_output_fields = ["$.status", "$.error"]
```

### Notes

- **Allowlist patterns select client tools as well as MCP tools.** A bare
  `"*"` on the global `facets.tool_call_allowlist` or on a regular facet
  activates *every* client tool on *every* platform, including ones the
  current client can't execute. Prefer namespace-scoped patterns
  (`"outlook/*"`) over a bare wildcard.
- Set `requires_client_registration = true` on a tool definition if it's
  optional/device-specific, so it's only offered when the connected client
  actually has a ready executor. Existing tools default to `false`.
- `durable_operations_enabled` only unlocks durable parking for operation
  kinds that already have a compiled, typed result validator — turning it
  on does not, by itself, make an arbitrary client tool durable.

<a id="hidden-facets"></a>

## Adopting hidden, platform-scoped facets

Added by [#796](https://github.com/EratoLab/erato/pull/796). Both new
fields default to inactive — no behavior change until set.

### What it does

Lets you define a baseline system-prompt facet that is always active and
never user-selectable (it never appears in the `/facets` API response, so
it can't be shown, toggled, or removed in any client UI) — useful for
platform-specific framing such as "you are running inside the Outlook
add-in." It's an ordinary facet under the hood, so `model_settings` and
`tool_call_allowlist` still apply to it like any other facet.

The prompt is injected once at conversation start (not re-injected every
turn), matching how the base system prompt behaves.

### Before (0.7.0 default — no hidden facets)

```toml
[facets.facets.web_search]
display_name = "Web search"
icon = "iconoir-globe"
tool_call_allowlist = ["web-search-mcp/*"]
```

### After — a baseline prompt for one platform only

```toml
[facets.facets.outlook_context]
hidden = true                                    # never shown/selectable; default false
hidden_always_active_for_platform = "outlook"    # omit to apply on every platform
additional_system_prompt = "You are running inside the Outlook add-in task pane. Keep responses concise enough to read in a narrow panel."
```

### Notes

- Omitting `hidden_always_active_for_platform` makes the hidden facet
  active unconditionally, on every platform — scope it explicitly if you
  only want it on one client.
- Injection order across multiple hidden facets is deterministic (sorted by
  config id), if you define more than one.
- This reuses the existing `FacetConfig` struct (there is no separate
  `[hidden_facets]` table) — define it exactly like a regular facet, just
  with `hidden = true`.

## Adopting guardrail pattern exclusions (`exclude_pattern_ids`)

Added by [#789](https://github.com/EratoLab/erato/pull/789). Defaults to an
empty list — no behavior change until set.

### What it does

Lets you apply a broad, tag-based prompt-injection guardrail rule set while
opting individual patterns back out (e.g. a known false positive), instead
of having to enumerate every other pattern ID one by one.

### Before (0.7.0 default — all tag-matched patterns apply)

```toml
[chat_providers.all_providers.guardrails.filter_input_prompt_injection]
enabled = true
filter_pattern_tags = ["input"]
```

### After — exclude one known false positive

```toml
[chat_providers.all_providers.guardrails.filter_input_prompt_injection]
enabled = true
filter_pattern_tags = ["input"]
exclude_pattern_ids = ["customer_specific_false_positive"]
```

Also available per provider:

```toml
[chat_providers.providers.<provider-id>.guardrails.filter_input_prompt_injection]
exclude_pattern_ids = ["customer_specific_false_positive"]
```

### Notes

- Startup validation rejects an `exclude_pattern_ids` entry that doesn't
  reference a known pattern under `guardrails.prompt_patterns` — a typo'd
  pattern id fails fast rather than silently doing nothing.
- Exclusion is applied *after* `filter_pattern_ids`/`filter_pattern_tags`
  selection, so it works the same way regardless of which selection
  mechanism added the pattern.

<a id="validate-availability"></a>

## Adopting live model-availability validation (`validate_availability`)

Added by [#1039](https://github.com/EratoLab/erato/pull/1039). Defaults to
`false` — no behavior change until set.

### What it does

Before exposing a configured model to users, queries the provider's own
model-listing endpoint and only shows the model if it's actually present in
that response. If the model isn't listed, or the check request fails, the
model is silently omitted (logged at `info`/`warn`) instead of being shown
and then failing when a user tries to use it.

### Before (0.7.0 default — no live check)

```toml
[chat_providers.providers.gpt5]
provider_kind = "openai"
model_name = "gpt-5"
base_url = "https://api.openai.com/v1/"
```

### After — validate against the provider's listing endpoint

```toml
[chat_providers.providers.gpt5]
provider_kind = "openai"
model_name = "gpt-5"
base_url = "https://api.openai.com/v1/"
validate_availability = true
```

### ⚠ Performance note before enabling

This check runs **on every call** to the available-models listing (e.g.
every time a client populates the model-selector dropdown) with **no
caching**. Enabling it adds a live, synchronous HTTP request to the
provider's listing endpoint to a path that was previously purely
local/config-derived. Only enable this for providers whose listing endpoint
is fast and reliable, and watch for added latency or new failure modes in
the model selector after turning it on.

<a id="embedded-image-retrieval"></a>

## Adopting the embedded PDF image retrieval tool

Added by [#1255](https://github.com/EratoLab/erato/pull/1255). Defaults to
disabled at both levels — no behavior change until set.

### What it does

Offers an image-capable model a synthetic `retrieve_embedded_image` tool
that can fetch images embedded inside a PDF already attached to the
conversation (PDF text extraction emits `file-embed://<file-id>/0`-style
markers the model can reference). Retrieval is scoped to images actually
offered in the current prompt and re-checks file access permissions at
retrieval time, not just at original attachment time.

### Before (0.7.0 default — tool never offered)

```toml
[chat_providers.providers.vision-model]
provider_kind = "openai"
model_name = "gpt-5-vision"

[chat_providers.providers.vision-model.model_capabilities]
supports_image_understanding = true
```

### After — enable for one image-capable provider

```toml
[chat_providers.providers.vision-model]
provider_kind = "openai"
model_name = "gpt-5-vision"
enable_embedded_image_retrieval_tool = true   # per-provider override

[chat_providers.providers.vision-model.model_capabilities]
supports_image_understanding = true
```

### After — enable globally, opt specific text-only providers out

```toml
[chat_providers.all_providers]
enable_embedded_image_retrieval_tool = true

[chat_providers.providers.text-only-model]
enable_embedded_image_retrieval_tool = false  # override back off for this one
```

### Notes

- Pair this with `model_capabilities.supports_image_understanding = true`
  on the same provider — the tool is pointless on a text-only model.
- The per-provider key overrides the `all_providers` default in either
  direction (on-globally-but-off-here, or off-globally-but-on-here).

<a id="runtime-configuration"></a>

## Adopting runtime configuration mirroring (`[runtime_configuration]`)

Added by [#893](https://github.com/EratoLab/erato/pull/893),
[#897](https://github.com/EratoLab/erato/pull/897),
[#914](https://github.com/EratoLab/erato/pull/914),
[#991](https://github.com/EratoLab/erato/pull/991). Disabled by default.

### What it does

On startup, mirrors every raw config file the backend actually loaded
(`erato.toml` plus any auto-discovered `*.auto.erato.toml` overlays) into a
new encrypted `runtime_configuration` database table — intended for
externally-authored configuration (e.g. via an admin panel) to be served
live without a backend restart.

### Before (0.7.0 default — feature inert)

```toml
# No [runtime_configuration] table: config files are read from disk only,
# never mirrored into the database.
```

### After — enable mirroring

```toml
[server]
encryption_key = "<base64 32-byte key, e.g. from `openssl rand -base64 32`>"

[runtime_configuration]
enabled = true
```

### ⚠ Security note before enabling

Mirrored config is redacted before being written, but **only
`server.encryption_key` itself is redacted** — any other secret you keep in
`erato.toml` (API keys, bot app passwords, OAuth client secrets, signing
keys) is written into the database **in plaintext inside the encrypted
blob**, not individually redacted. Before enabling this in a deployment
with secrets in its config files, confirm who/what has read access to the
`runtime_configuration` table and the `server.encryption_key` used to
decrypt it, and treat that access as equivalent to reading your config
files directly.

### Notes

- Requires `server.encryption_key` to be set — mirroring will not run
  without it.
- Writes are guarded by a Postgres advisory lock, so multiple backend
  replicas starting simultaneously won't interleave a delete-then-insert.
- Only the Erato backend's own sources are mirrored today; the
  `source_service` column exists for future multi-service use but nothing
  else writes to it yet.

## Adopting the MCP synthetic `wait` tool

See the "MCP controls" entry in `CHANGELOG.md`
([#918](https://github.com/EratoLab/erato/pull/918),
[#919](https://github.com/EratoLab/erato/pull/919),
[#1040](https://github.com/EratoLab/erato/pull/1040)). Disabled by default
(`enable_wait = false`).

### What it does

For MCP tools with a deferred/pollable result, offers the model a synthetic
`wait` tool it can call to pause and retry instead of the turn failing or
timing out when a long-running tool call hasn't finished yet.

### Before (0.7.0 default — no wait tool offered)

```toml
[mcp_servers.slow_report_generator]
transport_type = "sse"
url = "http://127.0.0.1:63490/sse"
```

### After — opt specific tools into waiting

```toml
[mcp_servers_global]
enable_wait = true        # default false
max_wait_seconds = 60      # default 60

[mcp_servers.slow_report_generator]
transport_type = "sse"
url = "http://127.0.0.1:63490/sse"
wait_tools = ["dispatch_*", "poll_*"]   # only these tool names get the wait affordance
```

### Notes

- `enable_wait` is a global default; `wait_tools` on a server scopes which
  of that server's tools actually offer the wait affordance — turning on
  `enable_wait` alone does not make every tool poll-able unless the server
  also lists matching patterns in `wait_tools`.
- `max_wait_seconds` bounds how long a single wait call may block before
  returning control to the model.

## File-attachment limit defaults changed (review before upgrading)

Changed by [#1044](https://github.com/EratoLab/erato/pull/1044). Not a new
key — existing explicit overrides are unaffected — but the **defaults**
changed and per-file-type size caps were removed.

### What changed

- `frontend.max_files_per_message` default: `5` → `10`
- `assistants.max_files` default: `5` → `10`
- Per-file-type size caps (previously as low as 2MB for plain text/code
  files, up to 50MB for archives) are gone. Every file type is now subject
  to a single uniform per-file size limit, governed by the backend's
  configured upload-size limit (frontend fallback default also rose, from
  20MB to 50MB, when the backend hasn't supplied a value).

If your deployment relies on the old defaults for capacity or cost
planning, this is a behavior change on upgrade even though no key was
removed or renamed.

### Before (0.6.2 effective defaults)

```toml
# Implicit: 5 files per message, 5 files per assistant.
# Plain text/code attachments capped at ~2MB client-side regardless of the
# backend's own upload-size configuration.

[file_storage_providers.seaweedfs]
provider_kind = "s3"
config = { endpoint = "http://localhost:8333", bucket = "erato-storage", region = "us-east-1", access_key_id = "admin", secret_access_key = "admin" }
```

### After (0.7.0 effective defaults — or pin back explicitly)

```toml
[frontend]
max_files_per_message = 10   # was 5; set explicitly to keep the old limit

[assistants]
max_files = 10                # was 5; set explicitly to keep the old limit

[file_storage_providers.seaweedfs]
provider_kind = "s3"
config = { endpoint = "http://localhost:8333", bucket = "erato-storage", region = "us-east-1", access_key_id = "admin", secret_access_key = "admin" }
max_upload_size_kb = 51200     # explicit 50MB cap; omit to inherit the new default
```

### Action required

If you want to keep the previous, smaller limits (for storage/cost/token
reasons), set `frontend.max_files_per_message`, `assistants.max_files`, and
your file-storage provider's `max_upload_size_kb` explicitly rather than
relying on defaults — all three will otherwise silently increase on
upgrade. There is no longer a smaller built-in cap for plain text/code
files specifically; the uniform limit now applies to every file type.
