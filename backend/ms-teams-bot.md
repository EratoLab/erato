# Teams bot

Erato answers in Microsoft Teams personal chats, group chats and channels. Chats started in Teams are ordinary Erato chats: they appear in the web app and the Teams tab, keep their history, and use the same assistants, models, policies, MCP tools and SharePoint integration as the web app.

The code lives in `erato/src/ms_teams_bot/`. The protocol files (`activity`, `inbound_auth`, `connector`, `user_token`, `graph`, `cards`, `citations`, `render`, `streaming`) do not depend on Erato, apart from the language type the bot's texts (`texts`) share with the reminder cards. `handler` decides what to do with each activity, and `host` is the only file that calls Erato internals, which keeps the folder ready to become its own crate.

## File citations

Final answers convert `erato-file://` Markdown links, reference-style links, bare file URIs and simple file-only footnotes into native Teams numbered citations. Files are resolved from the chat's persisted input-file inventory, including earlier turns, rather than by looking up arbitrary model-supplied IDs. Unknown files remain plain text. Code examples and images are not treated as citations, and ordinary web links are unchanged. The raw Erato message is unchanged.

Citation titles use stored filenames. With `integrations.ms_office.teams.bot.public_base_url` configured, source links point to the existing authenticated `/api/v1beta/files/{id}/preview` route, which checks the opening user's file access and SharePoint token as usual. Without that origin, citations still show their title but have no source-opening URL. No signed download URL or bot/Graph token is published. PDF `#page=N` references retain their page target; transcript `#msg=N` references display the message number in the popup, but the direct Markdown preview does not offer Web's rich transcript jump.

Source metadata is added at finalization. When replacing streamed Markdown links changes the cumulative text, the native stream closes and the same message is edited using the existing fallback. Citations survive editable delivery, failed-edit fallback, proactive responses and long-answer splitting. Activity budgets account for UTF-8, JSON escaping and metadata. At most 20 distinct file/location citations are emitted per answer; additional sources remain ordinary authenticated links. Earlier steps uses ordinary source links in its separate card.

This requires no manifest change. Arbitrary MCP resource provenance and generated follow-ups are separate work: [ERMAIN-843](https://linear.app/erato-labs/issue/ERMAIN-843), [ERMAIN-900](https://linear.app/erato-labs/issue/ERMAIN-900), and [ERMAIN-898](https://linear.app/erato-labs/issue/ERMAIN-898)/[ERMAIN-899](https://linear.app/erato-labs/issue/ERMAIN-899).

## Request flow

1. Teams sends an activity to `POST /api/integrations/ms_teams/messages`. The ingress routes this exact path to the backend directly, bypassing oauth2-proxy (which strips `Authorization` on every route, `skip_auth_regex` included), and the route sits outside the user middleware. It checks the Bot Connector's RS256 token itself before reading the body (Bot Framework key set endorsed for `msteams`, issuer `https://api.botframework.com`, audience = bot app ID, `exp`/`nbf` with five minutes of skew; key refreshes at most once a minute, stale keys kept on refresh failure), then reads at most 256 KB and binds the activity to the token: `serviceurl` claim = activity service URL, channel = `msteams`, tenant = `tenant_id`.
2. Messages are acknowledged immediately and handled in the background. Invokes (`signin/tokenExchange`, `signin/verifyState`) answer authentication synchronously; resumed message processing runs in the background. Interactive sign-in can also complete through a `tokens/response` event.
3. The user is looked up by the Entra object ID on the activity (`users.entra_object_id`). Web and Teams tab logins record it from the `oid` claim. Users who never opened Erato are asked to do so once. The time zone and locale of the sender's Teams client (the `clientInfo` entity, falling back to the activity's `localTimezone` and `locale`) are stored as `user_preferences.time_zone`/`language` when they change; the web app reports its browser zone and UI language the same way through `PUT /me/profile/preferences`. Reminders resolve local times in that zone.
4. The bot fetches the user's delegated Graph token from the Azure Bot OAuth connection. Without one, it sends an OAuth card addressed to the requesting Teams user: in personal chats directly, and for group chats and channels in a private chat. With matching SSO configuration and consent, Teams exchanges the token silently; otherwise the card offers interactive sign-in. Sign-in instructions are kept inside the card, so silent SSO does not leave a separate login prompt in chat. Before sending the card, `ms_teams_pending_sign_ins` stores the original message and routing, bound to the bot, tenant, OAuth connection, user and authentication conversation. Successful authentication atomically consumes that request and resumes it without asking the user to repeat the question. Duplicate callbacks and incoming-message retries cannot consume it again. Pending requests expire after 15 minutes, and expired rows are removed when another sign-in request is stored. Consumed rows retain only metadata until expiry; Graph and SSO tokens are never stored in this table.
5. Graph `/me` and `getMemberGroups` produce the same profile a web login yields (identity, email, group IDs for the policy engine; cached for ten minutes). The Graph token takes the place of oauth2-proxy's forwarded access token, so SharePoint and other Graph features work unchanged.
6. `ms_teams_conversations` maps (Teams conversation, user) to the current Erato chat. Channel conversation IDs include the thread, so each thread gets its own chat per user. `/new` starts a fresh chat.
7. Attachments become chat files:
   - Files uploaded in personal chats are downloaded from their pre-authenticated URL.
   - Pasted images are downloaded with the bot token (only from Teams content hosts).
   - SharePoint/OneDrive links, which is how files arrive in group chats and channels, are linked like the SharePoint picker does. When the SharePoint integration is off, they are downloaded instead.
8. In group chats and channels, the preceding messages (default 20) are fetched through Graph and attached as `teams-conversation-context.md`.
9. The message is submitted through the same code path as `submitstream` (`start_message_submit`), with platform `teams` and the chat's active-thread tip as `previous_message_id`.
10. Personal chats show typing while preparing the request, then a native streaming status and answer. Backend reasoning is represented by a “Thinking…” status; tool preparation, execution, progress messages/counts and completion are forwarded without exposing tool arguments or results in the status. Groups and channels maintain one editable reply in the thread, with an @mention of the requester. If a personal-chat turn calls a tool after streaming text, grows too long, or approaches the two-minute native streaming limit, the native stream is closed and that same message is updated instead. A timer coalesces updates at 1.5-second intervals and flushes the last pending update even when no new model event arrives. Native streams send a heartbeat during quiet work so Teams' Stop response can be detected; cancellation stops delivery and requests cancellation of the matching backend generation. Editable replies show a temporary **Working…** indicator. A tool boundary replaces preceding assistant narration with the current progress; text after the last tool step is presented as the answer. Earlier assistant text remains available through an **Earlier steps** disclosure card, without exposing raw reasoning or tool inputs/results. The answer replaces the progress reply as plain text; the disclosure is sent as a separate card-only activity below it. Teams rejects updates that combine text and a card with `Activity resulted into multiple skype activities`. If the optional card fails, earlier text is delivered separately without resending the answer. Cards carry a summary for clients that use it for previews or fallback text. If the details exceed the card size budget, they are retained under a separate Earlier steps section in ordinary text. Turns without a trailing answer keep their existing explanatory text. Final answers, errors and approval pauses replace the progress text and remove the working indicator.
11. A turn that stops on tool approvals posts one Adaptive Card listing every open decision (several for delegated task plans or batches, shown with the child's actual tool). "Submit decisions", "Approve all" or "Deny all" send the complete set, which resumes the turn through `start_continuation`, the same path as `continuestream`, and replaces the card. The continuation's completion reaches the bot through the task broadcast, so chained approvals get a new card. A decision is authorized exactly like `continuestream`, against the clicking user's access to the chat, so other people in a group chat cannot answer someone else's card.
    Approval titles and descriptions come from the MCP descriptor captured by the backend when the call parks. The same sanitized projection feeds Web approvals and the MCP tool catalog: `title`, then `annotations.title`, then the executable name. Cards retain the server/tool identity and actual arguments; display metadata never selects a tool or grants permission. Delegated approvals carry the child's snapshot, and older saved requests fall back to the tool name. Teams renders descriptor text literally and bounds previews to fit its card budget. The finished card is measured after JSON escaping; if it is still too large, it leaves out descriptions, then arguments, then the server/tool lines, and says that the full details are in Erato. Newly discovered tools follow this path automatically; there is no Teams-specific tool catalog or manifest change. This uses normal backend discovery and does not add live `tools/list_changed` refresh.
12. When a background task result is answered (`task_delivery`), the answer is pushed proactively to every Teams conversation whose current chat it belongs to.

## Language

The bot's own texts are English or German, German in the formal "Sie": the welcome and sign-in cards, statuses, response controls, approval cards, errors, the tip and reminder cards, the cards after their buttons and the replies to them. They live in one table keyed by message id (`ms_teams_bot/texts.rs`); a reminder's buttons and times are worded in `services/scheduled_items/wording.rs`, because its producer serves any channel. A `de` tag (`de`, `de-AT`, …) gives German, anything else English (`services/text_language.rs`).

- **Replies** use the sender's stored `user_preferences.language`, then the language their client reports, then `i18n.language.default_language`. The client's report is stored before the reply is worded, so the bot never switches language from one reply to the next.
- **Messages that answer nothing** (a reminder, a tip, a background task's result) use the stored language, then the default.
- **Dates** on cards read `9:30`, `morgen 9:00` or `Freitag, 13. Nov., 9:00`, with `(Ortszeit New York)` only when the reminder's zone is not the user's stored one.
- **Errors.** Erato's own refusal and error details are English only. Those the bot knows (archived chat, a task still running, too many attachments, the stale question, content filter, rate limit, a repeating answer) it words itself in both languages; any other detail shows only in English replies, and German replies say that the request could not start or the answer could not be generated.
- **Names.** Texts that name the bot or the web app use the Teams app's short name (`manifest.short_name`), not "Erato".
- **Not translated:** the model's answers and the tips as the admin enters them.

The card samples `ms_teams_bot/nudge/snapshots/scheduled_reminder_card.snap.json` and `scheduled_reminder_card_de.snap.json` show the reminder card in both languages, `reminder_confirmation_card.snap.json` and `reminder_confirmation_card_de.snap.json` the confirmation after one was scheduled in chat.

## Inactivity nudge

With `integrations.ms_office.teams.bot.inactivity_nudge.enabled`, a user who has not used Erato for `inactive_after` (default 7 days) gets one "Did you know…?" tip in their personal chat with the bot (Jira PAI-950). The code is `ms_teams_bot/nudge.rs`, the first producer and channel on the scheduled-deliveries foundation (`services/scheduled_deliveries.rs`), whose executor (`[scheduled_deliveries] enabled`) must be on.

- **Rule.** Once an hour per replica, from the executor's minute tick (a failed run is retried on the next tick): last activity = the newest message in any chat the user owns, or the chat's creation when it has none (every surface counts; housekeeping writes such as archiving, which move `chats.updated_at`, do not), or `users.created_at` without any chat. Users whose last activity is older than `inactive_after`, who have a `personal` row in `ms_teams_conversations`, are in `pilot_users` when that list is set, and have not opted out get one `scheduled_deliveries` row of kind `inactivity_nudge`. The dedupe key is the last-activity timestamp plus the number of full intervals elapsed, so a period is nudged once; with `repeat`, each further interval of silence gets another tip; a new period only starts when the user is active again. At least one `inactive_after` lies between two tips for the same user, so enabling `repeat` after a long silence does not catch up in a burst. `due_at` is the next slot inside `send_window` (Mon–Fri 08:00–18:00 Europe/Berlin by default).
- **Settings at runtime.** The section is reloadable like the MCP sections: with `runtime_configuration.enabled`, `ReloadableAppState::load` layers it from the mirrored `erato.toml` files, the admin panel's `erato.toml` override and environment variables, validates it as at startup, and keeps the previous settings when it fails (so a bad override cannot hold up the rest of a reload). The producer is registered whenever the bot is enabled and reads the current section on every use; it schedules nothing while the nudge is switched off. `scheduled_deliveries.enabled` and the bot itself stay startup settings: switching the nudge on while the executor is off is logged and sends nothing until a restart with it on.
- **Send-time guard.** Before sending, the row is dropped (`cancelled`, with the reason) when the nudge has been switched off, or the user has been active since, opted out, lost their personal conversation, or is no longer in the pilot. The guard applies the settings in force at send time. A tip that comes up outside the send window (a retry, a reclaimed claim, a restart that straddled the window's end) waits for the next slot without using an attempt.
- **Content.** Tips rotate per user by the number already delivered. The Adaptive Card has the tip, an "Open <app name>" button when `public_base_url` is set, and "Don't remind me", a single-use token stored on the delivery row and bound to the recipient and the conversation the card was sent to.
- **Opt-out.** `user_preferences.teams_nudges_opted_out_at`, set by the button and by `/reminders off` (`/erinnerungen aus`), cleared by `/reminders on` (`/erinnerungen an`). Both work without a bot sign-in: the sender is matched by Entra object ID (the activity is verified at the route), and the button's command is parsed before its token is claimed, so an unknown command cannot burn it.
- **Reachability.** The welcome event (`conversationUpdate` with the bot in `membersAdded`) now also upserts the personal `ms_teams_conversations` row for users Erato knows by Entra object ID, so people the app was installed for by policy can be reached before they ever write. `installationUpdate` is still ignored.
- **Channel.** `teams_personal` sends through the Connector to the user's personal conversation row, not to the current chat's conversation. 403 (`MessageWritesBlocked`, `ForbiddenOperationException`, roster) fails the row as unreachable; 429/412/5xx and transport errors retry per the executor's rules.

## User reminders

Reminders a user schedules (Scheduled page or chat) are `scheduled_items` rows (`services/scheduled_items.rs`): name, message, optional linked chat, channel (`teams_personal`), trigger and the IANA zone its local times were entered in. Each time an item is due, one `scheduled_deliveries` row of kind `reminder` (dedupe key = item id, so at most one open occurrence per item) goes through the same executor and channel as the nudge.

- **Trigger.** `once` (local date and time) or `repeat`: daily, weekdays (Mon–Fri), weekly on chosen days, or monthly on the start date's day (the last day of shorter months for the 29th–31st); a start date; ends never, on a date, or after a number of times. Times resolve in the item's zone: 09:00 stays 09:00 across daylight-saving changes, a time in the spring gap moves to the first valid minute after it, a time in the repeated autumn hour happens once.
- **Series.** After an occurrence is settled (delivered, failed or refused), the producer creates the next one on its next tick, computed from the item's regular time (`occurrence_at`) or now, whichever is later, so a snooze moves only the current occurrence and an outage does not catch up in a burst. The item's row lock makes replicas create one next occurrence between them. With no next occurrence the item is `ended`.
- **Edit and cancel.** A changed trigger reschedules the open occurrence (dropping a snooze); cancelling marks the item `cancelled` and cancels its open occurrence. An occurrence already claimed is refused by the send-time guard if the item was cancelled meanwhile.
- **API.** `GET|POST /me/scheduled-items`, `GET|PUT /me/scheduled-items/{id}`, `POST …/{id}/cancel` and `POST …/{id}/snooze` (`server/api/v1beta/scheduled_items.rs`), own items only. Request times are local to the user's stored zone (`user_preferences.time_zone`, else the send window's zone); create and edit refuse a channel that cannot reach the user (`channel_not_set_up`, `channel_unavailable`) and more than 10 upcoming items (`limit_reached`). These checks live in the service (`create_checked`, `update_checked`, `cancel_checked`), which the chat tools and the cards call too. The page's status (scheduled, snoozed, done, failed, cancelled) is mapped from the item and its occurrences in `scheduled_items::display_status`. System deliveries such as the nudge are not items and never listed.
- **Card.** The item's name as title, its message, and the linked chat (title, link to `public_base_url`) as a button, then Done, Snooze 30 min and Tomorrow 9:00 (in the item's zone; Erledigt, Später (30 Min.) and Morgen 9:00 in German). The buttons share one single-use token on the delivery row (`outcome.action_token`, 30 days, as the tip's), handled like "Don't remind me" without a bot sign-in; a used or expired one gets a reply pointing to `public_base_url/scheduled`. A button calls the same service functions as the page (`scheduled_items::acknowledge`, `snooze_delivered`) and the card is replaced in place (`Connector::update`, from the activity id and content the channel stored in `outcome.delivered`) with a line saying what happened and no buttons. A refusal settles the card like a success; when the service call fails, the token is given back so the button can be pressed again. Times on the card carry a zone name only when the item's zone is not the user's stored one. An unreachable user fails the occurrence through the channel (`no personal Teams conversation`), so the page can show it as failed.
- **By chat.** The built-in tools `create_reminder`, `list_reminders` (read-only) and `cancel_reminder` (`services/scheduled_items/chat_tools.rs`) are offered in the web chat and in Teams when `scheduled_deliveries.enabled` and the bot are on, never in a delegated run, and only where the facets' allowlist selects `erato/<name>`. They create the same item as the form, through the same checks, linked to the chat it was asked in, with origin `{"via": "chat", "chat_id", "message_id", "platform"}`. The create tool's description names the user's zone and today's date there (the system prompt's date is written once per chat); `in` with minutes covers "later". A refused create returns the code and reason; at the cap it also lists the upcoming reminders. `erato_inject_now_date`/`_datetime` in system prompts render in the user's stored zone.
- **Confirmation.** A created reminder's tool result carries a `confirmation` rendered from the stored item in the user's stored language: heading, name, the exact time (`Friday, 13 Nov, 10:00`; the year only when it is not this year's), the repeat pattern, where it arrives, and the labels of Cancel and Open in Scheduled; no Edit. Teams posts it as a card after the answer (once per reminder, also after an approval continuation, and when the turn fails or is stopped after the reminder was stored); the same data is there for the web chat's card. Cancel names the item, not a token, so it never expires: the press is checked against the Teams user's own items (someone else's press only gets a reply that only the person who scheduled it can cancel it) and runs the shared cancel; the card is replaced in place with what happened and keeps Open in Scheduled. Once the reminder is no longer upcoming, the card says what the Scheduled page shows: cancelled (also for one the same turn cancelled, which is confirmed without Cancel), not delivered after a failed delivery, or else that it already happened (a delivered one-off counts from its delivery, before the producer ends it), with a link to the Scheduled page.
- **Failed delivery.** Nothing is posted into any chat; the occurrence is `failed` and the Scheduled page shows it.
- **Not set up.** A create refused with `channel_not_set_up` names the Teams app's short name in its reason, since the chat tools pass the reason to the model, which tells the user.
- **Done.** Only stores `outcome.acknowledged_at` on that delivery (the API's `acknowledged_at`); the page's Done keeps meaning "happened as planned" and the schedule does not change.
- **Snooze after delivery.** Brings back that one reminder as a row of its own (dedupe key `{item_id}:snooze`, `payload.item_id`), so the regular occurrence keeps its row and time. The card offers only snoozes that come back before the item's next regular occurrence, and the service refuses others (`next_occurrence_first`), as it does for a card whose next occurrence already arrived and for a web snooze that would move the re-delivery past it. The re-delivery counts as the item's open occurrence for the page (Snoozed until …), the web snooze, cancel and delete, and the producer leaves the item alone until it settles; an ended one-off is active again meanwhile. A changed schedule drops the re-delivery, except a one-off's, which moves to the new time.

## Setup

Customer instructions: `site/content/docs/integrations/ms_teams.mdx`. Per environment:

1. **Erato configuration.** `[integrations.ms_office.teams.bot] enabled = true`. `app_id`/`sso_app_id` default to the add-in's `msal_client_id`, `tenant_id` to a tenant-specific `msal_authority`, `oauth_connection_name` to `graph-sso`, and the manifest derives `sso_resource = api://<host>/botid-<app_id>`; `messaging_endpoint` accepts a public HTTPS origin or a full URL ending in `/api/integrations/ms_teams/messages`, including a gateway path prefix. The gateway must rewrite that prefixed path to the backend route. `app_password` is the app's client secret (with the Helm chart, `msTeamsBot.appPassword.existingSecret`, typically the oauth2-proxy secret). Route the exact path to the backend without oauth2-proxy: `msTeamsBot.directRoute` and/or `msTeamsBot.publicIngress`, with the ingress controller in `msTeamsBot.directRoute.ingressFrom`.
2. **Azure and Entra.** `/office-addin/setup` → Teams serves `/office-addin/teams/bot-setup.json` (public identifiers and per-instance status) and a pinned Cloud Shell helper (`site/public/setup/teams/<version>/EratoTeamsSetup.ps1`). It creates or adopts the single-tenant Azure Bot with the messaging endpoint and Teams channel, adds the SSO settings (`access_as_user`, Teams client pre-authorization, v2 tokens, Bot Framework redirect, Graph permissions), creates the OAuth connection with a dedicated credential, and grants consent.
3. **Install the app.** With `integrations.ms_office.teams.enabled`, `/office-addin/teams/app-package.zip` contains the tab and the bot; deploy it in Microsoft 365 admin center's Integrated apps (installed and updated without user prompts) or upload it in Teams admin center with an app setup policy. When the bot joins someone's personal chat (`conversationUpdate` with the bot in `membersAdded`), it sends a welcome card; users unknown to Erato are pointed to the tab or `public_base_url` first.

The setup status reports Teams activity from `ms_teams_conversations`, `ms_teams_pending_sign_ins` and `ms_teams_requests` (so on any replica) and checks the bot credential on demand: a token request to Entra, cached like every app token and at most once a minute per instance. It works before the Azure Bot exists and distinguishes a rejected secret (`rejected`) from an app Entra does not find in the tenant (`app_not_in_tenant`, AADSTS7000229/700016).

## Limits

- Progress, response controls and edited-question handling use the existing Connector REST API and require no new Teams manifest, app installation or Graph scopes. Native streaming is personal-chat only; ordinary message updates provide the fallback elsewhere. While a native stream is open, Teams supplies the **Stop** button. When delivery switches to ordinary message updates, Erato adds a temporary **Stop** card. The typed `/stop` command also cancels the exact generation in either mode. Normal completion removes the control card. Teams' native Stop freezes its streamed answer; Erato then shows **Stopped** and, when eligible, **Retry** in a separate card without trying to edit that frozen content.
- Stopped or failed text-only generations offer **Retry**, which uses the same assistant-sibling regeneration path as Web. Requests involving tools do not offer automatic replay; the user supplies a new instruction. Erato checks both observed tool activity and persisted message content, and waits for the prior generation to release its lease. Buttons are bound to their original user/conversation, claimed once, and expire after one day.
- Editing the latest user's Teams message (`messageUpdate` with `editMessage`) offers **Regenerate edited question**. Nothing executes until clicked. Regeneration uses Web's user-message edit branch, keeps the original attachments, and may run tools again. Newer edits invalidate earlier cards; undelete notifications are ignored. Later conversation turns are not replaced from an old Teams card. This applies to messages sent after the durable request mapping was installed; earlier edits must be handled in Erato. Editing attachment membership is not supported by this text-edit flow.
- Request mappings and unconsumed action tokens survive process restarts, but live Connector delivery and generation supervision are not durable jobs. An interrupted preparation or response may require a new user message; a restart does not automatically replay tools or regenerate a question. When a user sends a new message, their settled mappings in that conversation older than two days are deleted; the newest question stays editable.
- Stop controls become available when the backend announces the assistant generation. Earlier preparation, including attachment downloads, shows typing/progress but cannot yet be cancelled through `/stop`.

- Automatic sign-in continuation requires a user already linked to Erato through a web or tab login. Consent and tenant authentication policies may still require interaction. If sign-in takes longer than 15 minutes, send the question again.
- Continuation is claimed before background processing starts. A process failure after that claim can require the user to resend the question; this is not a durable generation job queue.
- MCP servers that forward the OIDC ID token receive none on Teams requests; access-token forwarding gets the Graph token.
- Client tools (desktop sidecar) cannot run in Teams. The answer links to the chat in Erato instead.
- In group chats and channels, answers built from the requester's data are visible to everyone in the conversation.
