# PR #995: Make MCP call and output processing errors recoverable

- PR: https://github.com/EratoLab/erato/pull/995
- Status: pending
- Category: Stability improvements
- Theme: Streaming/generation stability

## Summary

Fixes a significant reliability gap in `stream_generate_chat_completion`
(`backend/erato/src/server/api/v1beta/message_streaming.rs`): previously,
if an individual MCP tool call itself failed (network/server error,
`"Failed to call tool"`) or the tool's output failed post-processing (e.g.
malformed file content in the response, `"Failed to process MCP tool
output"`), the entire generation turn aborted immediately
(`return Err(error)`) — ending the whole chat response with a hard error,
even though only one tool call among possibly several had failed.

Both error paths are now handled the same, recoverable way: the error is
turned into a normal tool-call-error result
(`MessageSubmitStreamingResponseToolCallUpdate` /
`StreamingEvent::ToolCallUpdate` with `status: Error` and an
`{"status": "error", "error": "<message>"}` output payload), the assistant
message's content gets a `ToolUse` entry recording the failure, and — most
importantly — a `genai::chat::ToolResponse` containing the error text is
pushed into `current_turn_tool_responses` and the loop `continue`s instead
of returning. This means the failed tool call is now fed back to the model
like a normal (failing) tool result, so the model can react to it —
retrying, trying a different tool, or explaining the failure to the user —
rather than the whole turn just dying. OTEL tracing (`persist_otel_tool_call`,
per #816) is still recorded for both paths as before. A new E2E test,
`e2e-tests/tests/mcp-resilience.many-models.spec.ts` (41 new lines),
exercises this recovery behavior, alongside `mock-mcp-server` and
`mock-llm-server` test-fixture additions to simulate these failures.

## Compatibility and configuration

No configuration keys or migrations. Behavior change: a chat that
previously would have ended in a hard generation error whenever a single
MCP tool call or its output processing failed will now continue
generating, with the model informed of the specific tool failure instead.
This is a pure reliability improvement with no opt-out; there is no
scenario where the old hard-abort behavior was more correct than surfacing
the error to the model as a tool result.
