# PR #1148: Add a per-chat write-operations switch and the composer Connectors section

- PR: https://github.com/EratoLab/erato/pull/1148
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Stacked on #1147. Adds a per-chat toggle (`chats.mcp_write_tools_enabled`,
default `true`) that, when off, restricts a chat to read-only MCP tools
and suppresses the client-action proposal offer — surfaced via a new
"Connectors" section in the composer's "+"/Tools menu with a
tool-browser modal. Confirmed the core filtering mechanism by reading
the complete `filter_mcp_tools_by_write_access` function in
`message_streaming.rs`:

- **Write-tool filtering correctly reuses the same normalization as the
  approval gate, confirmed exactly**: `filter_mcp_tools_by_write_access`
  calls `crate::services::mcp_tool_approval::normalize_tool_annotations`
  (the exact shared function this session's review of #1146 confirmed
  defaults `read_only_hint` to `false` for any tool with no or partial
  annotation hints) to decide whether to keep a tool when
  `write_tools_enabled` is `false` — a code comment states this precisely:
  "a tool without annotations counts as a write and is dropped," matching
  the PR's stated design that an unannotated tool is read pessimistically
  rather than assumed safe. When `write_tools_enabled` is `true`, the
  function short-circuits and returns every tool unfiltered with an empty
  suppression set — confirming the toggle is genuinely a no-op at its
  default value.
- **Dropped tools are tracked for continuation refusal messaging,
  confirmed exactly**: the function returns a
  `HashSet<(String, String)>` of `(server_id, tool_name)` pairs for every
  write tool it suppressed, consistent with the PR's claim that "the
  continuation refuses a parked write tool once the chat turns writes
  off" — a continuation resuming after the toggle flips can name which
  specific tool it's refusing rather than failing generically.
- Per the PR (not independently re-verified given the very large
  remaining scope): the new migration `0043` (additive, default `true`,
  no behavior change for existing chats); the seeding rules (a new chat
  takes the flag from `MessageSubmitRequest.mcp_write_tools_enabled`,
  ignored when continuing via `existing_chat_id`; a delegated child
  inherits its parent's value at the single creation site); the
  `propose_client_action` offer being suppressed outright when writes are
  off (distinct from the per-tool MCP filtering, since it's a single
  synthetic offer rather than a tool list); top-level `client_tools`
  being contractually read-only and therefore never filtered by this
  mechanism; the new composer "Connectors" section
  (`McpToolsBrowserModal.tsx`, 247 lines) sharing its per-server badge
  rendering (`McpToolSummary`) with the Settings panel from #1146, with
  an "Authorize" affordance for `NEEDS_AUTHENTICATION` servers and a
  "Manage in Settings" link; `useChatMcpWriteTools`'s optimistic PUT for
  an existing chat versus carrying the seed value into the first submit
  for a new one; the add-in's parallel send-chain wiring
  (`AddinChatInput` → `AddinChatInputCore` → `AddinChatCore` →
  `chat.sendMessage`) and Outlook's `pausesHostActionsWhenWritesOff` flag
  naming Reply/Send in the toggle's description text; the disclosed
  review fix changing a non-owner `PUT /me/chats/{chat_id}` from an
  unmapped 500 to a 404, matching the existing GET behavior; and the
  disclosed follow-up concern that `useBrowsableMcpServers` (gating
  whether the Connectors section even renders) calls the
  connect-and-teardown MCP server probe from every composer mount with
  only a 5-minute stale time, flagged by the PR itself as worth revisiting
  once a stateless-MCP mechanism lands.

## Compatibility and configuration

New migration `0043` (additive column, default `true` — confirmed no
behavior change for existing chats, matching the PR's stated default).
New request/response fields across `MessageSubmitRequest`, `ChatDetail`,
`RecentChat`, and `UpdateChatResponse`. A user can now restrict a
specific chat to read-only MCP tools, suppressing any tool whose server
doesn't explicitly mark it read-only (including any unannotated tool, per
the pessimistic-default filtering confirmed above).
