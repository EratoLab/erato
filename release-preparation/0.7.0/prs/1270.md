# PR #1270: Edit Word table cells with bounded document reads

- PR: https://github.com/EratoLab/erato/pull/1270
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Extends the Word add-in cluster reviewed earlier in this session
(#1232/#1257/#1258/#1259/#1265) with a targeted, bounded alternative to
the complete-document-read workflow: editing a single table cell's text
by discovering it through headers/row labels/nearby text/source
references, reading only a small bounded amount of context, and
submitting an edit scoped to exactly that discovered cell. Confirmed the
core discovery-and-scoping mechanism directly:

- **Discovery is snapshot-only, with no live Office/network access,
  confirmed exactly**: the new `readWordTableCell`'s own doc comment
  states "Snapshot-only discovery and authorization: no Office, network
  or live-document access," and its implementation only ever reads from
  the passed-in `WordAuthoringSnapshot.blocks` — matching the PR's
  "reading bounded target context" framing precisely.
- **Discovery supports headers, row labels, nearby text, and source
  references, confirmed exactly**: the query's accepted text filters are
  exactly `["nearbyText", "header", "rowLabel", "text", "sourceRef"]`,
  each matched case/whitespace-insensitively via a shared `normalize`
  helper (NFKC-normalized, lowercased, whitespace-collapsed) — matching
  "Discover cells by headers, row labels, nearby text or source
  references" exactly.
- **Explicit ambiguity and unsupported-target handling, confirmed
  exactly**: the result's `status` is `"ambiguous"` when more than one
  cell matches the query, `"not-found"` when none do, and
  `"unsupported"` (with `reason`/`fallback: "complete-read"`) both when a
  matched cell's text exceeds the 4096-byte `CELL_BYTES` cap and when the
  eligibility pre-check (described next) rejects it — matching "explicit
  ambiguity and unsupported-target handling" exactly, each case pointing
  the caller back to the existing complete-read workflow rather than
  failing silently.
- **Results are paginated and every returned string is bounded,
  confirmed exactly**: candidates are paged at `PAGE_SIZE = 5` via an
  `offset`/`nextOffset` cursor, and every returned text field (`text`,
  `header`, `rowLabel`, `before`, `after`) is passed through a `snippet()`
  helper that truncates to at most `SNIPPET_BYTES = 256` bytes of UTF-8
  (shrinking further if JSON-escaping would push it over), confirming
  the "bounded" framing is a genuine byte-size guarantee, not just a
  loose description.
- **Read-time eligibility is validated through the exact same function
  used at submission time, confirmed exactly — a drift-proofing design
  choice**: before granting a `readToken`, `readWordTableCell` calls the
  real `expandWordTableCellSubmission` with a synthetic matching edit
  (`text` set equal to the discovered `expectedText`, i.e. a no-op edit)
  against a snapshot carrying only this one candidate scope, and treats
  any `WordTableCellSubmissionError` it throws as the discovery-time
  "unsupported" signal — so discovery and the eventual real submission
  can never disagree about whether a given cell is editable.
- **A submitted edit is bound to the exact cell a prior read
  discovered, confirmed exactly**: `expandWordTableCellSubmission`
  requires the submission's `sourceRef`/`rowIndex`/`cellIndex`/
  `expectedText` to match the stored scope's values exactly, rejecting
  with `"outside-read-scope"` and the message "The scoped read
  authorizes only its exact returned cell and expectedText" otherwise —
  matching "Bind scoped authorization to the document, snapshot and
  exact cell" precisely, and directly preventing a read-granted token
  for one cell from being used to edit a different one.
- **A capability limit bounds how many scoped reads one request can
  accumulate, confirmed exactly, a detail not called out in the PR's
  own bullet list but a reasonable defensive bound**: `MAX_SCOPES = 16`
  caps `snapshot.cellReads`, failing further discovery with
  `"cell-read-limit"` once reached.
- Per the PR (not independently re-verified given remaining scope): the
  "concise-cell submission support and the captured list-continuation
  fix" (`wordTableCellText.ts`, 97 lines, and the `wordDocumentPlan.ts`/
  `wordDocumentXml.ts`/`wordTableContent.ts` diffs touching list
  continuation, not traced); "Preserve surrounding content and
  formatting; broader edits retain the complete-read workflow" beyond
  the scoping confirmed above (the actual OOXML cell-text-replacement
  logic in the remainder of `wordTableCellSubmission.ts`, roughly 70
  lines past what was read); "Start authoring with document metadata"
  (`wordActionFacet.ts`/`wordAuthoringContract.ts` diffs); the new
  `office-addin/ARCHITECTURE.md` documentation addition (51 lines); and
  the two large new test files (`wordConciseEdits.test.ts` at 411 lines
  and `wordScopedCellRead.test.ts` at 438 lines), disclosed as covering
  "stale references, scope enforcement, unsupported-cell fallback,
  preservation and list continuation," plus the disclosed validation
  (add-in tests, TypeScript, ESLint, formatting, and diff checks all
  passing).

## Compatibility and configuration

None breaking. Purely additive capability within the existing Word
add-in's document-plan submission pipeline — the complete-document-read
workflow remains the fallback for anything this narrower path can't
handle, confirmed by every "unsupported" exit path explicitly naming
`fallback: "complete-read"`. The PR notes the matching Word
configuration and add-in must be deployed together, consistent with
this being a frontend-only add-in change with no backend diff in this
PR's changed-files list.

## Release note disposition

Proposed category: Features and enhancements, grouped with the rest of
the Word add-in cluster rather than as a standalone entry. Worth folding
into that combined entry: editing a single table cell in a Word document
can now happen through a lightweight, targeted discovery-and-edit path
(find the cell by its header, row label, nearby text, or source
reference, then edit just that cell) instead of always requiring a
complete document read, with every ambiguous or unsupported case falling
back to the existing complete-read workflow.
