# PR #1000: Delegated chats open on a run header, not a machine-written message (ERMAIN-631)

- PR: https://github.com/EratoLab/erato/pull/1000
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Follow-up to #998, adding a header banner to a delegated run's chat view:
`Delegated run · ⟨delegate⟩ · From ⟨origin chat⟩` plus labelled
`Expected output`/`Constraints` fields (each omitted when absent) — since
#998 already cleaned up the first message to be just the task brief, this
adds the context that message alone doesn't convey. Confirmed by reading
the core hook, `useDelegatedRunHeader.tsx`, in full:

- **Keyed off a new dedicated chat-detail fetch, not the sidebar's
  session model — confirmed and confirmed correct**: the hook calls
  `useChatDetail` against a new `GET /me/chats/{chat_id}` endpoint (added
  in this PR, authorized identically to the existing
  `GET /chats/{chat_id}/messages` via `Action::Read` on the chat) rather
  than reading from `useChatHistory`'s listing-derived session state. This
  matters because #982 deliberately hides delegated runs from
  `/me/recent_chats`, so a delegated chat opened via a direct link has no
  corresponding sidebar listing row — a header sourced from that listing
  would silently render nothing and, per the PR, "look like it had
  worked" rather than clearly failing. The new endpoint was chosen over
  extending the messages response specifically because provenance isn't
  message data and the header needs to render before (and independently
  of) any message page loading.
- **The composer-lock logic, confirmed to precisely distinguish two
  distinct 409 causes**: `delegateIsWriting` returns true only when the
  chat's generation status is `running`/`action_required` **and** the
  chat has *not* been adopted (`!adoptedAt`) — directly matching the
  design rationale that once a human has taken over (adopted) a
  delegated run, a running generation there is the *owner's own* turn,
  which the composer already handles normally like any other chat; only a
  still-writing *delegate* (an unadopted run) represents someone/something
  else holding the chat that a user write would collide with (rejected by
  #992's `accept_user_write_into_delegated_run`). Separately,
  `isArchived` (from `chat.archived_at`, covering both a directly-archived
  run and one swept up by #992's cascade from an archived parent) also
  locks the composer, matching `reject_if_archived`'s independent 409
  cause. `composerLocked = isRunning || isArchived` cleanly OR's the two
  causes together, and the header itself still renders for an archived
  run — confirmed the PR's framing that an archived run is "exactly the
  case where you want to know what it was," not one to hide the header
  for.
- Confirmed the design explicitly does **not** change behavior on
  adoption for the header itself: an adopted run still shows as a
  delegated run with its origin link intact — #998's behavior change (the
  *model* stops being told it's a delegate) only affects what's composed
  into the prompt, not what a human sees in the header.
- Per the PR (not independently re-verified given remaining scope): the
  origin-chat link/label follows the same dangling-tolerant pattern as
  #986's assistant-space rows (a real link while the origin exists, a
  plain unlinked label once it's deleted, with the untitled-chat sentinel
  getting its own distinct wording), consolidated into a shared
  `utils/chat/delegatedRunOrigin.ts` used by both this header and #986's
  `AssistantWelcomeScreen` rows (which is refactored to consume it rather
  than duplicating the logic); the new chat-detail endpoint's response
  bundles identity, titles, archived/pinned state, assistant, flattened
  provenance, and the run parameters (`expected_output`/`constraints`
  from #998) in one payload; and there's deliberately no separate "Task"
  row duplicating the brief, since the brief already *is* the chat's first
  message per #998.

## Compatibility and configuration

None new. Additive `GET /me/chats/{chat_id}` endpoint and additive
OpenAPI schema fields; no configuration changes. Purely additive UI for
delegated runs — no behavior change for any non-delegated chat.
