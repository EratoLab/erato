# PR #1052: Keep the picked file size on staged attachments

- PR: https://github.com/EratoLab/erato/pull/1052
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Stacked on #1051. Closes the remaining ERMAIN-691 item without the
backend migration the issue originally proposed. Confirmed by reading the
complete `useFileDropzone.ts` diff:

- **The root cause, confirmed exactly**: `useFileDropzone`'s upload
  handler previously discarded the browser `File[]`'s `size` the moment it
  swapped them for the server's `FileUploadItem[]` response, which has no
  size field. The new `withLocalSizes(uploaded, localFiles)` helper
  re-attaches it by building a `Map<filename, number | null>` from the
  local files, then mapping each uploaded item to `{ ...item, size }`
  when a numeric size is found for its filename.
- **Duplicate-name ambiguity, confirmed exactly**: the map-building loop
  is `sizeByName.set(file.name, sizeByName.has(file.name) ? null :
  file.size)` — the first occurrence of a filename records its size, any
  subsequent occurrence of the same filename overwrites it with `null`
  (and `has` stays true, so a third+ duplicate also stays `null`) — so a
  name duplicated within one upload batch is deliberately left ambiguous
  rather than guessed at, and that file simply renders with no size
  (falling through to #1050's `typeLabel`-only display).
- **Filename-based, not positional, matching confirmed**: the mapping key
  is `item.filename`/`file.name`, with no reliance on array index or
  response ordering — matching the PR's stated rationale that response
  ordering is not part of the upload contract.
- **Call-site wiring, confirmed**: the upload success path now computes
  `const sized = withLocalSizes(result.files, filesToUpload)` and passes
  `sized` (not the raw `result.files`) to `addFiles`, `onFilesUploaded`,
  and the stored `uploadedItems` — so the size is carried through every
  consumer of the upload result, not just the immediately-rendered
  preview.
- Confirmed no backend change: the entire diff is contained in
  `frontend/src/hooks/files/useFileDropzone.ts` and its tests; the PR's
  stated reasoning for not adding a `file_uploads` size column (a rehydrated
  chat never saw the original browser `File`, and comparable products
  don't show size there either) was not independently re-verified but is
  consistent with the fully-frontend scope of the diff.

## Compatibility and configuration

None. Pure frontend fix; no API or database changes. The web composer now
shows a file size (e.g. "PDF · 80 KB") for newly staged attachments where
it previously showed none, matching what the add-in already displayed for
its locally-staged files (per #1050).
