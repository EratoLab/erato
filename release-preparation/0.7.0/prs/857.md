# PR #857: Define protocol for desktop-sidecar

- PR: https://github.com/EratoLab/erato/pull/857
- Status: pending
- Category: Features and enhancements
- Theme: Desktop Sidecar for local sources

## Summary

Introduces the foundational "Desktop Sidecar" protocol: a new
`desktop-sidecar-protocol/` package that is the language-neutral
specification for communication between an Erato client (web app or
Office add-in) and an optional locally-running desktop companion process
("sidecar") that can expose local data sources (mailboxes, folders,
documents, search — per `README.md`/`SPEC.md`, implemented incrementally
in later PRs this cycle). The protocol uses JSON-RPC 2.0 envelopes with
OpenRPC 1.4 discovery and JSON Schema Draft 7 payload contracts;
compatibility is negotiated via an exact protocol version plus a live
capability catalogue intersected with methods compiled into the client
(`README.md`, `SPEC.md`, `TRANSPORT.md`). This PR adds the schemas,
generated TypeScript client/types/validators
(`desktop-sidecar-protocol/typescript/`), and a deterministic Node.js mock
sidecar (`test-server`) used for conformance testing.

On the frontend, a new `DesktopSidecarProvider`
(`frontend/src/providers/DesktopSidecarProvider.tsx`) wraps a
`DesktopSidecarClient` (HTTP transport) and exposes connection state via
`useDesktopSidecar()`. It only activates when an endpoint is explicitly
configured — via `VITE_DESKTOP_SIDECAR_URL` (build time) or
`window.DESKTOP_SIDECAR_URL` (runtime); with neither set, per the
package's own README, "it remains unavailable and performs no loopback
requests." `frontend/src/components/providers/ClientProviders.tsx` and
`office-addin/src/App.tsx` wire this provider into both the web app and
Office add-in.

## Compatibility and configuration

No new *backend* configuration keys in this PR. The frontend gains a new
optional environment/window variable, `VITE_DESKTOP_SIDECAR_URL` /
`window.DESKTOP_SIDECAR_URL` (frontend-only, not backend-templated in this
PR), which is unset by default — the sidecar integration is entirely
opt-in and inert with no observable behavior change for deployments that
don't configure it. No migration. This PR only lays the protocol/client
groundwork; the actual sidecar application, its distribution, and specific
capabilities (mailbox listing, search, file access) are added in
subsequent PRs this cycle (#860, #864, #867/#869/#871/#872 among others).
