# PR #1324: Report the searched period of local searches to the model and under replies

- PR: https://github.com/EratoLab/erato/pull/1324
- Status: pending
- Category: Features and enhancements
- Theme: Desktop Sidecar

## Summary

Second frontend consumer (after #1322) of the protocol's new search
`coverage`/`limitReached` fields (#1316, reviewed in this batch; sidecar
protocol 0.1.35). The `search_sidecar_index` client-tool executor
previously forwarded the sidecar's raw coverage report straight to the
model; it now compacts it into
`{v, asOf, basis, requested, requestedFromBeforeCoverage, limitReached,
sources, notice}`, where each source gets `sourceId`/`label`(+ a
disambiguating `number` only when labels collide)/inclusive ISO
`from`/`to`/`status`/`partialCache`, and a one-sentence `notice` states
the covered period, flags a requested start earlier than coverage, names
sources still indexing newest items, and notes a reached limit — while
an empty-text listing (`basis: catalog`) is described as a listing and
never flagged against the indexed range, since it reads the full
discovered inventory rather than the index. A sidecar that reports no
coverage at all gets `{v: 1, status: "unknown", notice}` rather than
silently omitting the field. A new `LocalSearchCoverageNotice` component
renders a footer under chat replies that used local search, merging a
message's searches by `sourceId`, stated from the *stored* tool results
so it survives streaming, page reload, and shared chat links — not
derived live each render. The PR explicitly flags one deviation from its
own ticket: shared-label numbering is scoped to a message's own sources,
not to the global Settings ordering, to avoid an extra `sources.list`
call per search.

## Compatibility and configuration

None breaking; purely additive model-context and UI content. No config
keys. **Rollout ordering matters** (stated explicitly by the PR): this
frontend change should deploy *before* the sidecar release that starts
reporting `coverage` (ERDSCAR-29) — until the sidecar sends it, an older
frontend would instead forward the sidecar's raw, unprocessed report
straight to the model, which this PR's whole point is to prevent. No
database migration.
