# PR #1259: Show Word messages immediately while the document is prepared

- PR: https://github.com/EratoLab/erato/pull/1259
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

A third Word add-in follow-up in this same cluster (#1232/#1257/#1258):
with "Include this document" on, several seconds passed between
pressing send and seeing the message appear, because `WordChatInput`
only called the shared `sendMessage` (which inserts the optimistic
message synchronously) *after* a slow sequence of document capture,
image capture, and a budget-check network call — leaving the composer
cleared and disabled with no feedback, and silently dropping the draft
if the chat or document changed mid-preparation. Confirmed the new
shared `prepare`-step contract in `useChatMessaging.ts` directly, since
it's the architecturally significant, reusable piece other callers
depend on:

- **The optimistic message and a labeled pending reply appear before
  `prepare` runs, confirmed exactly**: in `sendMessage`, the user message
  is already inserted and `useMessagingStore.getState().setStreaming({
  ..., pendingLabel: prepare.label ?? null }, streamKey)` is called
  *before* `await prepare.run(controller.signal)` — matching "inserts
  the user message, shows the pending reply with a label ('Preparing
  document…')... and only then awaits `prepare`" exactly. The new
  `pendingLabel` field is also confirmed exposed on the hook's return
  value.
- **Stop is available during preparation, confirmed exactly**:
  `cancelMessage` now checks `preparationAbortByKeyRef.current[streamKey]`
  first and, if present, calls `.abort()` on it and returns immediately
  — with a comment "Nothing has reached the server yet; sendMessage
  rolls the send back" — matching "makes Stop available" and connecting
  directly to the abort-handling described next.
- **Every disclosed abandonment path — Stop, an exception, a refused
  duplicate, or the preparation resolving falsy (a chat/document
  change) — rolls back identically, confirmed exactly**: if
  `prepare.run()` throws, or returns a falsy result, or the controller's
  signal was aborted, `sendMessage` calls `removeUserMessages([userMessage.id],
  streamKey)`, `resetStreaming(streamKey)`, clears the new-chat silent-
  navigation flags, clears the submitting-for-key flag, and calls
  `prepare.onAbandoned?.()` before returning `undefined` — nothing ever
  reaches the server on any of these paths. The duplicate-submission
  guard at the top of the function separately calls `prepare?.onAbandoned?.()`
  before its own early return. This matches "the optimistic message and
  pending reply are removed, submitting state and silent-navigation
  flags are reset, nothing reaches the server, and the caller gets the
  draft back" exactly, across all four named trigger causes.
- **Existing callers (web, Outlook, the neutral add-in page) are
  unaffected when `prepare` is omitted, confirmed exactly, structurally**:
  the entire new preparation block is gated behind `if (prepare) {
  ... }`; when absent, `effectiveActionFacet` simply equals the original
  `actionFacet` parameter and the function proceeds exactly as before —
  matching "Without `prepare` the call is unchanged, so web, Outlook and
  the neutral add-in page behave exactly as before."
- **`SendMessagePreparation`'s contract matches the described shape
  exactly**: the new interface is `{ label?: string; run: (signal:
  AbortSignal) => Promise<{ actionFacet?: ActionFacetRequest } | null>;
  onAbandoned?: () => void }` — a `null` result from `run` is explicitly
  documented as "Resolving null drops the send and removes the
  optimistic message," matching the confirmed rollback behavior above
  precisely.
- Per the PR (not independently re-verified given remaining scope): the
  Word-specific `prepare` implementation in `WordChatInput.tsx` (the
  215-line diff — concurrent document+image capture, the budget check,
  read-session activation, and the claimed "budget refusal still sends"/
  "read failure still sends without the document" kept-behavior
  exceptions); `AddinChatCore.tsx`'s draft/attachment snapshot-and-
  restore-on-rollback mechanism (66-line diff, the fix for "silent draft
  loss on a chat or document switch," with the disclosed caveat that
  "@-mention links come back as text only"); `readWordDocument.ts`'s
  claimed skip of the body `getOoxml` call when full-package capture
  replaces it; the new dev-only performance marks in `wordSendTiming.ts`;
  and the disclosed test results (frontend 2770/2770 with 11 skipped;
  add-in 2077/2077, including the new 342-line
  `WordChatInput.prepare.test.tsx` covering six named scenarios).

## Compatibility and configuration

None breaking. Purely additive to the shared `sendMessage` contract — a
new optional parameter with confirmed no-op behavior when omitted — plus
Word-specific consumption of it. No backend, config, or wire changes.
