# PR #837: Chat input stays usable while a response is generating (ERMAIN-466)

- PR: https://github.com/EratoLab/erato/pull/837
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Previously the entire message composer was disabled while a response was
generating. Now only sending is blocked; the textarea, paste-to-attach,
the file/"+" menu, and tool/facet selection remain usable so the next
message can be prepared while the current one streams. Confirmed by
reading `ChatInput.tsx`: the single `isDisabled` flag is split into
`sendLocked` (`isLoading || isPendingResponse`, gating only the Send
button/Enter-to-send) and `composeLocked` (`disabled || isUploading ||
isFileButtonProcessing || isRecording || isRecordingUpload`, gating the
textarea, file attachment controls, and facet/tool selectors) — every
call site that previously used the combined `isDisabled` for the
composer's editable surfaces (textarea `disabled`, file-attachment
buttons, `FacetSelector`, `FileSourceSelector`, paste handler) now uses
`composeLocked` instead.

Two supporting fixes needed for this to actually work correctly mid-stream,
both confirmed by reading the code:

1. **Facet/tool selection surviving the new-chat id transition.** A new
   `userSelectedFacetsSessionRef`, keyed by `composeSessionId`, marks that
   the *current compose session* had an explicit user facet pick. The
   facet re-initialization effect now checks this ref before re-deriving
   selection from `initialSelectedFacetIds`/`chatId` changes — since a
   brand-new chat's `chatId` transitions from `null` to a real id
   mid-stream (the same compose session continuing), this previously
   reset a facet/tool the user had just picked while the first response
   was still generating; a genuine chat switch (a different
   `composeSessionId`) still re-initializes normally.
2. **File attachment during a brand-new chat's first turn.** A new
   `resolveInFlightNewChatId` helper in `useFileDropzone.ts`: if no
   `chatId` is committed yet, it checks the messaging store for a
   first-turn-in-flight signal (`newlyCreatedChatId` already set, or a
   streaming/awaiting-first-chunk state for the sentinel
   `NEW_CHAT_STREAM_KEY`) and, if so, awaits the real chat id (via a
   store subscription, bounded by a 4-second timeout that falls back to
   `null`) instead of immediately falling through to "no chat id → create
   a silent new chat," which previously produced an orphaned second chat
   when a file was attached during a new chat's still-streaming first
   turn.

Per the PR, the Outlook add-in inherits all three fixes automatically
through the shared `ChatInput`/`useFileDropzone` components (no add-in-
specific code change), taking effect on the add-in's next library re-pack
— not independently verified, since that re-pack is outside this diff.

## Compatibility and configuration

None. Pure frontend UX/bug fix; no configuration or API changes. Behavior
change: users can now type, attach files, and change tool/facet selection
while a response is still generating, where the composer was previously
fully locked.
