# PR #800: fix: write text/html to clipboard when copying HTML email drafts (ERMAIN-417)

- PR: https://github.com/EratoLab/erato/pull/800
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes the "Copy" action on an AI-generated `erato-email-html` draft:
previously `navigator.clipboard.writeText(content)` copied the raw HTML
source, so pasting into a compose window showed literal markup
(`<p>`, `<strong>`, …) instead of formatted rich text. New shared
`frontend/src/utils/emailClipboard.ts` (`copyEmailToClipboard`,
`htmlToPlainText`, `transformEmailFencesForCopy`, exported via
`@erato/frontend/library` for the Outlook add-in to reuse) fixes this and
three adjacent defects found during review:
- HTML drafts now copy via `ClipboardItem` with both a `text/html` flavor
  and a plain-text fallback, so paste targets get formatted rich text
  where supported, degrading gracefully to `writeText(plainText)` alone
  when `ClipboardItem` is unavailable (older Firefox/webviews). Plain-text
  drafts continue to use `writeText` directly, unchanged.
- **The clipboard `text/html` content is passed through the same
  `sanitizeHtmlPreview` function used to render the on-screen preview**
  before being written — confirmed in the code — so what gets pasted is
  "exactly what the user approved" rather than raw, unsanitized model
  output (which could otherwise carry event handlers, forms, or other
  live HTML into a paste target).
- `htmlToPlainText` (replacing bare `textContent`, which fused
  `<p>Hi</p><p>Bye</p>` into "HiBye") walks the DOM and inserts newlines at
  `<br>` tags and block-element (`P`, `DIV`, headings, list items, etc.)
  boundaries, skipping `<script>`/`<style>`/`<template>` content, so the
  plain-text fallback reads correctly.
- A separate, message-level "Copy" action (copying an entire chat message
  rather than just the email card) previously copied the raw
  ` ```erato-email-html ` fence markup verbatim; `transformEmailFencesForCopy`
  now rewrites canonical email fences to their rendered draft text (HTML
  fences converted via the same `htmlToPlainText`) at all four copy call
  sites the PR lists (add-in chat, web chat, and two shared-page
  variants), while explicitly leaving "drifted"/malformed fences untouched
  since classifying them correctly needs facet context the copy handlers
  don't have.
