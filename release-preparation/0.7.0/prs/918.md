# PR #918: MCP tool approval UX follow-ups

- PR: https://github.com/EratoLab/erato/pull/918
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Large follow-up (1369 insertions across 33 files) to the MCP tool-call
approval flow from #915, aligning its UX with the add-in's established
consent patterns and adding durable, cross-device visibility for chats
"parked" awaiting a tool-approval decision. Given the scale, review
focused on the backend state-machine mechanics, since they're the most
correctness-critical and least visually self-evident part of the change.

**One real discrepancy found and worth flagging**: the PR description
states "New `chats.pending_tool_approval_at` (migration 0035)" — implying
a new physical database column added via a schema migration. **No
migration file appears anywhere in this PR's diff.** Reading
`models/chat.rs` and `services/background_tasks.rs` directly shows the
actual implementation reuses the *existing* `generation_state` (text,
no `CHECK` constraint) and `generation_ended_at` columns from #868's
migration `0030`: a new value, `"awaiting_approval"`, is simply written
into `generation_state` (via a new `TaskOutcome::AwaitingApproval` enum
variant), and `pending_tool_approval_at` in the `RecentChat`/
`GeneratingChatRow` API types is a **derived SQL expression**
(`CASE WHEN generation_state = 'awaiting_approval' THEN generation_ended_at
END AS pending_tool_approval_at`), not a stored column at all. No
migration is needed because the column was never constrained to a fixed
enum of values. The description's "migration 0035" framing appears to
describe an earlier design that changed before implementation, or was
copied from the linked ticket rather than the shipped code — the feature
itself is real and correctly implemented, just not via the mechanism
described.

Confirmed by reading the relevant diffs:
- `TaskOutcome::AwaitingApproval` is a new third outcome (alongside
  `Completed`/`Errored`) for a generation, set via a new
  `StreamingTask::mark_awaiting_approval()` flag that `derive_outcome`
  checks — with an error still taking priority over a pending approval if
  both occurred.
- Confirmed the "no retention window" claim precisely: the existing
  60-second-retention cleanup query only targets rows where
  `generation_state IN ('completed', 'errored')`, and the stale-generation
  reaper only targets `generation_state = 'running'` — `'awaiting_approval'`
  rows are excluded from both, so a parked chat's marker persists
  indefinitely until a later generation (the approval's own continuation)
  takes over that chat's lease, matching the PR's "durable" claim.
- A separate, shared `temp_chat_generations` table (tracking the live SSE
  stream lifecycle rather than the chat's own state) deliberately maps
  `AwaitingApproval` to `"completed"` there via a new `as_stream_db_str()`
  — confirmed reasoned as: the stream itself genuinely did finish, so
  mapping it to `"completed"` keeps those rows eligible for their own,
  separate retention cleanup, distinct from the chat-level parked marker.
- `get_generating_chats`'s SQL gains an `OR generation_state =
  'awaiting_approval'` branch (parameterized, gated by a new boolean flag)
  so `/me/generating` surfaces parked chats — the PR states this
  supersedes the previously-misleading `"completed"` status a parked chat
  would otherwise have reported.

Not independently verified in this review, given the scale: the frontend
`generationStatusStore`'s new durable/non-fading `action_required` kind
and its tombstone-on-decide logic (108-line diff), the sidebar/rail badge
deduplication against the live confirmation registry, the redesigned
`McpToolApprovalCard` (artifact-style visible-referent rendering) and
`McpToolApprovalSettings` (RadioCard-based Ask/Always-allow rows
replacing the hidden-until-granted list), the new
`POST /me/mcp-tool-approval-settings` endpoint, or the add-in's
per-device-scope clarification in `BehaviorTabContent`.

## Compatibility and configuration

No new database migration (contrary to the PR's own description — see
above). New endpoint `POST /me/mcp-tool-approval-settings` (reuses
existing `upsert_active` logic per the PR, not independently traced).
Behavior/API change: `RecentChat` and the `/me/generating` response gain
a `pending_tool_approval_at`/`action_required` signal for chats parked
awaiting a tool-call decision. Settings UI reshaping: the deliberate
absence of a "Never" tri-state option is explained as intentional — the
backend has no deny concept, so only the two states that map to existing
backend capabilities (Ask / Always allow) are exposed.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the relevant `chat.rs` diff (the derived
`pending_tool_approval_at` SQL expression) and the relevant
`background_tasks.rs` diff (the new `AwaitingApproval` outcome, its
retention-exclusion behavior, and the stream-vs-chat state mapping) —
this is how the migration-description discrepancy was found, by directly
checking for the claimed migration file and finding none, then tracing
the actual mechanism in the code. Given the PR's large scale, the
extensive frontend UI/store changes (McpToolApprovalCard,
McpToolApprovalSettings, UserPreferencesDialog, GenerationStatusPoller,
generationStatusStore) and the ~350 lines of new/expanded test coverage
were not read in detail.

## Release note disposition

Proposed category: Features and enhancements. Worth a mention: a chat
paused awaiting an MCP tool-call approval decision now shows a durable
"Action required" indicator in the sidebar across navigation, reload, and
devices, and the approval/consent UI now matches the add-in's established
confirmation-card pattern; MCP tool permission settings are reorganized
into simpler Ask/Always-allow rows per tool.
