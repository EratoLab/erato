# PR #899: Authorization retry with throttling for cross-replica staleness

- PR: https://github.com/EratoLab/erato/pull/899
- Status: pending
- Category: Bug fixes
- Theme: Multi-replica / cross-replica generation state

## Summary

Fixes a class of spurious authorization failures in multi-replica
deployments. Erato's policy engine (`backend/erato/src/policy/engine.rs`,
OPA-based) keeps an in-memory snapshot of authorization-relevant data per
backend process; each request previously used a request-scoped clone of
this engine (`clone_for_request`) with no ability to trigger a rebuild
itself — if that snapshot was stale or simply didn't yet contain a
resource created on a *different* replica (e.g. a chat/resource created by
another pod moments earlier, in a multi-replica deployment), authorization
for it would fail outright ("Policy data is stale and needs to be rebuilt
before authorization", or simply "not authorized" for an unknown
resource), even though the action should have been allowed.

Authorization now proceeds in two phases via a new `evaluate_authorization`
helper: it returns both whether the action is `allowed` and whether the
`resource_exists` in the local snapshot. If the resource kind is
`is_snapshot_backed()` and doesn't exist locally, and a new
`PolicyRebuildContext` was attached to the engine
(`clone_for_request_with_context`, used for requests that can afford a
one-time DB rebuild), the engine performs exactly one rebuild attempt and
retries the check — but only if no such rebuild for that specific
`(resource_kind, action)` pair happened within the last 10 seconds
(`UNKNOWN_RESOURCE_REBUILD_INTERVAL`, enforced by
`PolicyRebuildContext::claim_miss_rebuild`), so a flood of misses for the
same resource type doesn't trigger a rebuild storm against the database.
If the resource still isn't found/allowed after the retry, the request is
denied as before.

## Compatibility and configuration

No configuration keys or migrations; the 10-second throttle interval is a
hardcoded constant, not configurable. Behavior change: requests referencing
a resource that exists in the database but is missing from a given
replica's authorization snapshot (typically right after that resource was
created on a different replica) now get a one-shot chance to succeed after
an on-demand rebuild, instead of failing immediately — directly relevant
to the multi-replica generation-state sharing added in #898 this cycle,
where a chat/generation created on one pod may be accessed via another.
Deployments running a single backend replica should see no behavior
change beyond the added retry code path (which would rarely trigger, since
that replica's own writes normally invalidate its own snapshot already).
