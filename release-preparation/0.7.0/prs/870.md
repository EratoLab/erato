# PR #870: Parallelize e2e CI: shard many-models, worker knob, raise e2e backend memory

- PR: https://github.com/EratoLab/erato/pull/870
- Status: pending (diff reviewed)
- Category: Chores
- Theme: None

## Summary

CI/dev-infrastructure-only change with no product code touched. Confirmed
by reading the diff: shards the `many-models` E2E scenario into 2 matrix
jobs with 2 Playwright workers each (via a new `PW_WORKERS` env var
consumed by `playwright.config.ts`), while every other scenario keeps
running sequentially; adds a merged blob-reporter HTML report job
replacing per-scenario artifacts; and raises the e2e/dev-cluster backend
pod's resource limits from the chart default (500m/512Mi) to 2000m/2Gi in
`infrastructure/k3d/erato-local/values.yaml` — confirmed this is scoped
only to the local/CI k3d dev-cluster subchart values, not the product
chart's own defaults (the PR notes `charts/erato` there is a symlink; the
product chart's own default resource limits are untouched by this PR).

The PR's own measurements (not independently reproduced) attribute a
prior OOM-kill collapse at 4+ concurrent workers to the backend's
in-memory file caches (3×100MB by default) plus concurrent PDF-parsing
memory use exceeding the old 512Mi limit under E2E's specific heavy-file
fixture load, and separately flags — as a follow-up, not addressed by
this PR — that the same latent OOM exposure could affect a real customer
deployment configured with the chart's still-unchanged 512Mi default
under genuinely concurrent uploads.

## Compatibility and configuration

None for the shipped product. This changes only the local dev/CI k3d
deployment's resource requests/limits and the CI pipeline's test sharding
— no change to the product Helm chart's own defaults, no application code
changes.
