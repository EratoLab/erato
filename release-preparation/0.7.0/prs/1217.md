# PR #1217: Stream tool argument preparation into the chat trace

- PR: https://github.com/EratoLab/erato/pull/1217
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a UX gap where the trace stayed on "Thinking…" while a provider
generated a large tool call's arguments, because the backend ignored the
provider adapter's already-emitted accumulated `ToolCallChunk` snapshots
and only announced the tool after generation finished. Forwards those
snapshots as a new `preparing` status with a bounded preview. Confirmed
every quantitative and safety-relevant claim with high precision by
reading the complete new `tool_arguments.rs` module and its call sites:

- **~4 KiB preview bound, confirmed exactly**: `PREVIEW_BYTES: usize =
  4096`, with `bounded_preview` UTF-8-safely truncating via
  `is_char_boundary`-adjusted head/tail splits (confirmed never splitting
  inside a multi-byte character by a dedicated test feeding 100,000
  repeated 4-byte emoji) — matching "Previews are limited to
  approximately 4 KiB" exactly.
- **Four updates per second per call, confirmed exactly**: `UPDATE_INTERVAL:
  Duration = Duration::from_millis(250)` throttles `observe()`, confirmed
  by a dedicated test showing an update 20ms after the previous one is
  suppressed while one at exactly `UPDATE_INTERVAL` passes — matching
  "four updates per second per call" exactly (250ms = 4/sec). An update
  carrying identical byte length to the last-sent one is also suppressed
  regardless of timing, avoiding redundant no-op emissions.
- **Display-only; the completed provider response remains the sole
  source of executable arguments, confirmed exactly, by construction**:
  the module's own doc comment states this verbatim ("Display-only
  progress while a provider is still generating tool arguments. The
  completed provider response remains the only source of executable
  calls"), and `ToolArgumentStreams::observe` only ever constructs a
  preview `ToolUse` with `status: ToolCallStatus::Preparing` — it has no
  path that feeds into dispatch, schema validation, or approval, which
  (per the PR, consistent with this module's narrow scope) continue to
  read the provider's final, complete `fn_arguments` elsewhere in the
  existing pipeline. Matches "They are display-only; dispatch, schema
  validation and approval still use the completed provider arguments."
- **Interrupted preparation rows excluded from saved content, confirmed
  exactly, including the call-site wiring**: `without_preparing_tools`
  filters out any `ContentPart::ToolUse` whose `status ==
  ToolCallStatus::Preparing`, with a doc comment stating "Partial
  arguments are transient UI state, never executable or replayable
  history." This is confirmed genuinely wired into the save path, not
  merely defined: `message_streaming.rs` calls it both at an earlier
  content-persistence site and at
  `completion.map(|(content, metadata)| (without_preparing_tools(&content),
  metadata))` — directly substantiating "Interrupted preparation rows are
  excluded from saved message content and subsequent model history."
- **Completion and execution update the same row rather than appending a
  second entry, confirmed exactly**: `upsert_tool_use` looks up the
  existing content index for a `tool_call_id` via
  `tool_call_content_index` and replaces in place (or appends only if
  genuinely new) — confirmed by a dedicated test
  (`interleaved_calls_keep_their_positions_when_execution_settles`)
  showing a settled/executed `ToolUse` at the same index a preparing
  preview previously occupied, and that `observe()` itself refuses to
  overwrite a row whose status has already moved past `Preparing`
  (`if matches!(content.get(index), Some(ContentPart::ToolUse(part)) if
  part.status != ToolCallStatus::Preparing) { return None; }`) — directly
  substantiating "completion and execution update the same row" and that
  a settled call can never be clobbered by a late/race-condition
  preparation chunk.
- **A bounded cap on concurrently tracked preparations, confirmed
  exactly, a defensive detail not called out as its own PR bullet**:
  `MAX_PREPARATIONS: usize = 128` caps how many distinct `call_id`s
  `ToolArgumentStreams` will track as "first" (new) previews, refusing to
  add more once the cap is hit — a reasonable memory-bounding safeguard
  against an adversarial or malfunctioning provider emitting many
  concurrent tool-call previews.
- Per the PR (not independently re-verified given remaining scope): the
  "applies to the common server/client/delegation tool lifecycle, with no
  Word-specific code or prompts" framing (a scope statement, not a
  specific technical claim); "Providers/adapters that do not emit
  argument chunks keep the existing completed-call behavior" (plausible
  given `observe()` is purely additive — a provider that never calls it
  simply never produces a `Preparing` row — but the adapter-level
  chunk-emission itself, described as "the pinned provider adapter
  already emits accumulated `ToolCallChunk` snapshots," was not traced);
  "Reconnection can replay the ordinary progress events" (not traced);
  the frontend consumption of the new `preparing` status across
  `ToolCallItem.tsx`, `ToolUseStep.tsx`, `useThinkingGap.ts`, and
  `toolUsePartHelpers.ts` (small diffs, 6/12/14/11 lines respectively,
  confirming the trace's "no second 'Thinking…' placeholder while a tool
  is preparing or running" claim was not independently traced); and the
  disclosed validation (thinking-gap regression tests failing on
  unchanged `main` and passing with the fix; gated localhost-provider
  tests against real Chat Completions/Responses endpoints confirming
  preparation-before-completion, single dispatch with complete arguments,
  and no execution/save of interrupted fragments; 2,534/2,534 frontend
  tests with 11 skipped; 1,261/1,261 backend tests with 4 skipped; clean
  OpenAPI check).

## Compatibility and configuration

None breaking. Pure backend/frontend UX improvement to the existing tool-
call trace rendering — no config keys, and the new `preparing` status is
additive to the existing tool-call status vocabulary (confirmed via the
2-line `message.rs` diff, not read in full but consistent with the
established `ToolCallStatus` enum pattern this session has seen
elsewhere). A provider/adapter that doesn't emit argument chunks is
unaffected by construction, since `observe()` is simply never invoked for
it.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: a tool call with large or
slow-to-generate arguments (for example, drafting a long document) now
appears in the trace immediately with a live, bounded preview of its
arguments as they're generated, instead of leaving the user staring at
"Thinking…" until the whole call completes.
