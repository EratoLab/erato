# PR #1257: Precise Word plan diagnostics and normalize misplaced built-in styles

- PR: https://github.com/EratoLab/erato/pull/1257
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

A follow-up to the Word add-in (#1232, reviewed above), fixing a
concrete, observed failure: a real two-turn test against GPT-5.2 had its
structural document plan rejected twice for the same reason (every
heading and table carried a redundant `styleRef` the host always
rejected), forcing a full ~35 KB/~9K-token plan resubmission each time,
with vague error codes that didn't point at a specific field. Confirmed
the core normalization mechanism and its two new, precisely-targeted
validation error codes directly:

- **Normalization is pure and deterministic, confirmed exactly**:
  `normalizeWordDocumentPlan` deep-clones its input via
  `JSON.parse(JSON.stringify(plan))` before mutating the clone, never
  touching the caller's original plan object — matching "Pure and
  deterministic, applied after parsing at submission, review and apply.
  The stored tool arguments stay unnormalized, and review restore
  re-derives the same plan" (the stored arguments being unnormalized
  follows directly from the function only being applied at the
  described call sites, never to what's persisted).
- **Heading-style redundancy resolved through the live style inventory,
  with the exact localization-aware fallback described, confirmed
  exactly**: for a heading block, the function looks up the document's
  actual built-in heading style for that level via
  `isBuiltInHeadingStyle(style.id, style.name, level)` against the
  captured snapshot; if found, redundancy is judged by comparing the
  built-in style's *id* against the plan's `styleRef` — not an English
  string — so a localized Word document whose level-2 heading style is
  internally named e.g. `Überschrift2` is correctly matched and dropped
  when the plan supplies that same id, while a plan supplying the
  English literal `"Heading2"` against a localized document (where the
  actual built-in style id differs) fails this id comparison and falls
  through to rejection. This precisely substantiates "Resolved through
  the captured style inventory, so localized Word works... The English
  string `Heading2` in a localized document is not dropped and is
  rejected with `heading-style`" — confirmed by tracing the exact
  comparison logic, not merely trusting the claim.
- **Default table style redundancy and misplaced-real-style relocation,
  confirmed exactly**: a table's `styleRef` is dropped when it resolves
  (by id, or by the `"tablenormal"` string fallback) to the document's
  default table style via `isDefaultTableStyle`; separately,
  `misplacedTableStyle` identifies a `styleRef` that resolves to a
  genuine, non-default table-type style with no `format.styleRef`
  already set, and the main `visit` loop moves it there (`delete
  block.styleRef; block.format = { ...block.format, styleRef: tableStyle
  }`) — matching both "A table `styleRef` that is the default table
  style... is dropped" and "A real table style in a table's top-level
  `styleRef` is moved to `format.styleRef`... when the document defines
  it as a table style and the plan sets no `format.styleRef`" precisely.
- **Both new, precisely-targeted validation rules exist exactly as
  named, confirmed exactly, each a direct backstop for whatever
  normalization didn't resolve**: `validateWordDocumentPlan` now
  rejects any heading carrying a `styleRef` with code `heading-style`
  (message: "Headings take no styleRef; the host applies the built-in
  heading style for the level. Remove styleRef.") and any table carrying
  a `styleRef` with code `table-style-placement` (message: "Tables take
  no styleRef; put a table style ID from the read tool in
  format.styleRef, or omit it for the default table style."), both
  pointing at `${blockPath}/styleRef` as the JSON Pointer — matching the
  PR's claimed codes and field paths exactly, and confirming these rules
  run *after* normalization has already stripped or relocated the
  acceptable cases, so only a genuinely wrong `styleRef` reaches them.
- Per the PR (not independently re-verified given remaining scope): the
  full set of other newly-precise diagnostic codes listed (`heading-level`,
  `heading-list`, `table-key`, `table-id`, `table-text`, `table-source`,
  `style-shape`, `table-columns`, `table-column-width`,
  `table-column-total`, `table-rows`, `list-id`, `list-ordered`,
  `list-level`, `block-key` — the bulk of the 89-line `wordRichPlan.ts`
  and 113-line `wordTableContent.ts` diffs, not traced individually);
  the claim that nothing outside the add-in references the old, coarser
  codes (`heading-fields`, `table-shape`'s broader prior scope) — a
  negative/absence claim about the backend, docs, contract, and content
  package not independently checked; `ensureHeading`'s use of the same
  `wordBuiltInStyles.ts` helper ensuring normalization and compilation
  cannot drift (the compiler-side code itself, in
  `wordApplyDocumentPlan.ts`, not traced); and the companion
  subscription-content-package prompt fix (explicitly out of this
  repository's scope).

## Compatibility and configuration

None breaking. Pure Word add-in behavior refinement within the feature
reviewed in #1232 — no backend, config, or wire changes (confirmed by
the all-`office-addin/` changed-files list). Narrows what a model's
structural plan is rejected for (fewer spurious resubmissions for a
redundant-but-harmless `styleRef`) while adding two new, more specific
rejection codes for the cases that remain genuinely wrong.

## Release note disposition

Proposed category: Bug fixes, grouped with #1232's Word add-in rather
than as a standalone entry (the Word feature is still subject to that
PR's own disclosed native-testing caveats). Worth folding into that
entry: a Word document plan proposing a heading or table with a
redundant built-in style (which the host always applies anyway,
including in localized Word installations) is no longer rejected and
forced to resubmit; a genuinely misplaced or invalid style reference now
produces a precise error naming the exact field, rather than a vague
rejection covering several unrelated causes at once.
