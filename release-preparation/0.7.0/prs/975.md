# PR #975: Focus rings: keyboard-only, inset on sidebar rows, aligned trailing controls

- PR: https://github.com/EratoLab/erato/pull/975
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Three related sidebar/focus polish fixes, all confirmed by reading the
code:

1. **Focus rings no longer show on mouse click.** The shared
   `.focus-ring`/`.focus-ring-tight`/`.focus-ring-inset` utility classes
   previously applied their ring on plain CSS `:focus`, which fires for a
   mouse click too — leaving a lingering gray ring on chat-history rows,
   dropdown triggers, and modal panels after every click. Confirmed via
   `globals.css`: all three utilities now key their ring exclusively to
   `:focus-visible` (removing the redundant plain `:focus` ring rules
   entirely), so a mouse click never shows the ring while keyboard
   navigation still gets the full indicator. Form fields (`Input`,
   `Textarea`, checkboxes) and the intentional keyboard-active dropdown-row
   ring recipe are correctly left untouched, per the PR.
2. **Inset rings on sidebar rows**, to prevent clipping: the previously
   outside-drawn 2px focus ring could get visually clipped by the sidebar
   scrollport whenever the themeable row inset was narrower than the ring
   itself — sidebar row surfaces now use the inset-ring variant so this
   can never happen regardless of a theme's chosen inset width. Not
   independently re-verified beyond the general `.focus-ring-inset`
   utility confirmed above; the specific row-class switch was not traced
   in `ChatHistorySidebar.tsx`'s 13-line diff.
3. **Trailing-control alignment and visible hover state.** Confirmed via
   `globals.css`: a new shared `.sidebar-trailing-col-geometry` class
   gives the section-header filter/sort trigger and each chat row's "⋮"
   menu trigger identical right-edge padding (previously off by 8px
   between the two due to one hardcoded `pr-1.5` the other site lacked,
   plus mismatched button geometries). Confirmed via `Button.tsx`: the
   `sidebar-icon` button variant's hover background changes from the
   generic `--theme-bg-hover` to the sidebar-specific
   `--theme-shell-sidebar-hover` token — the code's own comment confirms
   the bug precisely: in the default theme, `--theme-bg-hover` happens to
   equal the sidebar's own background color, making any hover state using
   it invisible on sidebar surfaces (also fixing the same invisible hover
   on the sidebar toggle and logo buttons, which share this variant).

## Compatibility and configuration

None. Pure frontend visual/accessibility polish; no configuration or API
changes. Behavior change: clicking (rather than tab-navigating to) an
interactive element no longer leaves a visible focus ring; sidebar-row
focus rings can no longer be visually clipped; hover feedback on sidebar
icon buttons is now reliably visible regardless of theme token overlap.
