# PR #1276: Add support for uploading arbitrary file types

- PR: https://github.com/EratoLab/erato/pull/1276
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: File previews and formats

## Summary

Introduces a configurable file upload policy that decouples upload eligibility from the set of file-processing operations the deployment supports. Previously a file could only be uploaded if the server had a registered capability (extract text, analyze image) for its type; files whose type had no known processor—such as raw binary data, CAD files, or proprietary formats—were silently rejected at the upload stage even when a deployment wanted to handle them as opaque blobs. The change makes upload eligibility an independent policy dimension.

**New `FileUploadsConfig` with three modes.** The `[file_uploads]` config block introduces `upload_allowed_if_supports`, an allowlist of selectors that OR together. Three kinds of selector are available:

| Selector | Behaviour |
|---|---|
| `supported_operations` (default) | Permits upload of file types for which the server has *any* known operation (extract text, analyze image, etc.). Matches the legacy behaviour exactly. |
| `extract_text` / `analyze_image` | Permits upload only when the server supports the named operation for that file type. Finer-grained than the blanket `supported_operations` gate. |
| `any` | Permits upload of *every* file type, including those with zero known operations. This is the knob for deployments that want to accept arbitrary attachments (e.g. `.bin`, `.dat`, `.stl`) and ship them as opaque blobs to chat context or MCP servers. |

Configuring `upload_allowed_if_supports = []` (an empty list) disables all new uploads.

**Backend: capability model with `upload_allowed` flag.** The new `FileCapability` struct in `models/file_capability.rs` carries an explicit `upload_allowed: bool` field, defaulting to `false`, that is computed from the policy at startup. The file-resolution and message-streaming paths consult this flag instead of the earlier implicit "has any operation" check. The token-usage estimator is updated to skip files whose upload is not permitted, preventing them from contributing to context-window accounting.

**Frontend: client-side enforcement.** The `validateFiles` function in `fileCapabilities.ts` now checks `capability.upload_allowed ?? hasSupportedOperations(capability)` — i.e., it defers to the explicit policy flag when present, falling back to the legacy operation-based check. `useFileDropzone` and `useStandaloneFileUpload` both call `validateFiles` and therefore reject impermissible files at the drop/pick moment with a user-visible error, before any network round-trip.

**Config documentation.** Adds the new `[file_uploads]` section to `site/content/docs/configuration.mdx` with usage examples.

## Compatibility and configuration

No breaking changes. The default (`supported_operations`) preserves the legacy behaviour exactly — every file type that had a processor continues to be eligible; every type that did not continues to be rejected. Deployments that want to accept any file should add:

```toml
[file_uploads]
upload_allowed_if_supports = ["any"]
```

The new config key is optional and fully backward compatible.

## Evidence and review

Verification by reading the complete diff:

- **FileUploadsConfig and its default**: the struct is `#[serde(default)]` on the parent `Config` struct, and `default_upload_allowed_if_supports()` returns `[SupportedOperations]` — matching "default preserves legacy behaviour".
- **`any` bypasses the operation check**: `FileUploadOperationSelector::Any` is a distinct variant; the policy evaluation in `file_capability.rs`'s constructor branches on it to set `upload_allowed = true` unconditionally.
- **Empty list disables uploads**: when `upload_allowed_if_supports` is `[]`, the evaluation loop adds no permissions, leaving all capabilities with `upload_allowed = false`.
- **Frontend validates before upload**: `validateFiles` in `fileCapabilities.ts` calls `capability.upload_allowed ?? hasSupportedOperations(capability)`, so unknown file types with `upload_allowed = true` (from `any` policy) pass through.
- **Office-addin `validateStagedPart` updated**: the add-in's own upload validation also uses the new capability-based check.

## Release note disposition

Include in release notes as a new configurable feature: upload policy. Mention `upload_allowed_if_supports = ["any"]` as the way to accept arbitrary file types.
