# PR #1202: Index the async delivery lookups and the latest-generation probe (ERMAIN perf follow-up)

- PR: https://github.com/EratoLab/erato/pull/1202
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

A small, focused performance follow-up stacking on #1201 (the top of the
"Async re-entry" stack), adding sqitch migration 0047 with two partial
indexes identified by a performance audit of that stack. Confirmed both
indexes' shapes match their target queries exactly, and confirmed the
PR's own disclosed decision *not* to index a third query:

- **`idx_messages_latest_generation` matches `get_generating_chats`'s
  `LATERAL` predicate and ordering exactly, confirmed exactly**: `CREATE
  INDEX idx_messages_latest_generation ON messages (chat_id, created_at
  DESC) WHERE is_message_in_active_thread AND generation_parameters IS
  NOT NULL`. This session's own prior review of PR #1199 confirmed the
  `LATERAL` subquery this serves filters on exactly
  `m.chat_id = ... AND m.is_message_in_active_thread AND
  m.generation_parameters IS NOT NULL ORDER BY m.created_at DESC LIMIT
  1` — the index's `WHERE` clause and column order
  (`chat_id, created_at DESC`) match that filter and sort direction
  precisely, which is what lets Postgres serve the query as a pure index
  scan with no sort node, substantiating the claimed O(conversation
  length) → O(1) improvement structurally (the specific measured numbers
  — 1500 rows sorted/244 buffers/0.534ms before vs. 3 buffers/0.051ms
  after — are the PR's own `EXPLAIN ANALYZE` output, not independently
  reproduced in this review).
- **`idx_chats_async_delivery_in_flight` matches the delivery-lookup
  predicates confirmed in prior reviews, confirmed exactly**: `CREATE
  INDEX idx_chats_async_delivery_in_flight ON chats (origin_chat_id)
  WHERE provenance.kind = 'delegation' AND provenance.run_mode = 'async'
  AND provenance.result_delivery.state IN ('pending', 'claimed')` —
  this exact state-pair (`pending`/`claimed`, scoped to async delegation
  provenance) is the identical predicate this session confirmed
  underlying both the per-origin delivery drain and the #1196 backstop
  sweep's scan/requeue logic in earlier reviews of this stack, so the
  index is a precise match to its two intended consumers.
- **The deliberate non-indexing decision for `get_recent_chats`'s
  `delegated_runs_in_flight`, confirmed consistent with that query's own
  structure**: the migration's own comment states this index is
  "Deliberately NOT written to serve [that] predicate: that predicate
  reaches the delivery state only through an OR, and a partial index is
  usable only when the query implies its predicate, which `A OR B` does
  not." This session's own review of PR #1199 confirmed that query's
  `EXISTS` subquery does indeed combine the generation-liveness check and
  the delivery-state check via `OR` (not `AND`), which is precisely the
  shape a partial index's predicate cannot imply — the stated reasoning
  is structurally sound given that confirmed query shape, even though the
  specific comparative benchmark numbers (26.3ms rewritten vs. 18.9ms
  current; 24.1ms for a widened-predicate attempt) are the PR's own
  measurements, not reproduced here.
- **Non-concurrent index creation inside a transaction, confirmed
  exactly**: both `CREATE INDEX` statements are inside a plain `BEGIN ...
  COMMIT` block with no `CONCURRENTLY` keyword — matching "Indexes are
  created non-concurrently, matching every existing migration in
  `backend/sqitch/deploy`" (consistent with every other migration this
  session has seen referenced across this release's PRs).
- **Revert script is clean and complete, confirmed exactly**: the paired
  revert drops both new indexes with `DROP INDEX IF EXISTS`, matching
  what was created.
- Per the PR (not independently re-verified): the specific `EXPLAIN
  ANALYZE` benchmark figures throughout (all three scenarios: the
  `idx_messages_latest_generation` before/after comparison, the
  delivery-lookup index's "handful of rows" claim at 50k delegated
  children, and the three-way comparison for the deliberately-not-done
  `get_recent_chats` rewrite); the `current_schema.sql` hand-edit
  rationale (avoiding picking up unrelated pre-existing drift — a
  `notify_policy_facts_changed` function and two `assistant_usage`
  indexes — from a full dump, verified by the PR's author by diffing
  `CREATE INDEX` lines against a fresh dump); and the disclosed
  verification (1225/1225 `cargo nextest run --retries 2`, every
  integration test applying this migration via `sqlx::migrate!`; clean
  clippy; clean `gen-openapi`/`gen-config-reference --check`; config
  coverage unchanged at 98; clean frontend lint/typecheck).

## Compatibility and configuration

Pure database migration (sqitch 0047), additive and reversible. No
config keys, no wire/API changes, no application code changes at all —
confirmed by the changed-files list containing only sqitch
deploy/revert/verify/plan/summary files and the hand-maintained
`current_schema.sql`. No behavior change, only query-plan improvement for
two existing, already-shipped query shapes from earlier PRs in this same
stack (#1196's delivery sweep/drain and #1199's generating-chats poll).
