# PR #1265: Repair rejected Word plans with small patches

- PR: https://github.com/EratoLab/erato/pull/1265
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Builds on #1257's style normalization/diagnostics and the client-
submissions validation infrastructure reviewed in #1215. When a large
Word document plan is rejected for one field-level reason, the model can
now submit a small RFC 6902-style patch set against the rejected draft
instead of regenerating the entire proposal. Confirmed essentially every
claim in the PR description with high precision by reading the complete
new `wordDocumentDrafts.ts` module:

- **Patches are limited to `add`/`replace`/`remove`, revision-checked,
  confirmed exactly**: `applyWordDraftPatches` only accepts
  `patch.op` in `["add", "replace", "remove"]`; `materialize` rejects a
  repair whose `draft_id`/`revision` don't exactly match the stored
  draft's with a `draft-revision` error ("The draft ID or revision is
  unavailable or stale. Use the latest rejected draft receipt or submit
  a complete plan.") — matching "accept revision-checked `add`,
  `replace`, and `remove` patches" precisely.
- **A compact draft handle carries only id and revision, confirmed
  exactly**: `reject()` returns `{ draft: { id, revision }, terminal }`
  — no full plan or diagnostics payload echoed back — matching "Return a
  compact draft handle with rejection diagnostics" (the diagnostics
  themselves are the caller's separate `issues` argument folded into the
  internal fingerprint, not the handle itself, consistent with "compact").
- **A proposal that repeats unchanged with the same errors ends the
  turn, confirmed exactly, via a precise fingerprint mechanism**:
  `reject(value, issues)` computes `fingerprint = canonical([value,
  issues])` (a key-order-independent, array-order-preserving stable
  serialization) and sets `terminal = fingerprint === this.failure` —
  i.e., `terminal: true` only when *both* the rejected plan's value and
  its diagnostic issues are identical to the immediately preceding
  rejection. This directly substantiates "end the submission turn when a
  proposal repeats unchanged with the same errors" — requiring the
  *combination* of value and errors to match, not merely a resubmission.
- **Repeated delivery of the same tool call returns its original
  result, confirmed exactly, with a bounded replay cache**: `replay(callId,
  input)` returns the stored result for a previously-seen `callId` if
  the input matches, and throws a distinct `call-conflict` error if the
  same `callId` is reused with *different* arguments (a genuine protocol
  violation, not a legitimate retry); `remember()` caches up to 16
  entries, evicting the oldest on overflow. Matches "Repeated delivery of
  the same tool call returns its original result" exactly, plus a sound
  bounded-memory detail not spelled out in the PR body.
- **Accepted repairs persist the complete materialized plan, not a diff,
  confirmed exactly**: `materialize()` applies the patches to a deep
  clone of the stored draft value and returns the *whole* resulting plan
  object — matching "accepted repairs persist the complete materialized
  plan for review."
- **Immutable fields cannot be touched via a patch, confirmed exactly,
  by construction**: a repair submission's own top-level shape is
  restricted to exactly `["snapshot", "readToken", "draft_id",
  "revision", "patches"]` (any other key throws `repair-shape`), and
  every patch's first path segment must be one of `["scope", "entries",
  "deleted", "stories", "sections"]` — so `snapshot`, `readToken`, or any
  other plan metadata field is structurally unreachable by a patch.
  Matches "Snapshot, readToken and version are immutable" from the
  function's own doc comment precisely.
- **No prototype-pollution or out-of-bounds array writes, confirmed
  exactly — defensive hardening against untrusted, model-supplied patch
  data**: every patch's path segments are checked against
  `["__proto__", "prototype", "constructor"]` and rejected if any match;
  array indices are validated as safe, in-range integers (with `'-'`
  accepted only for `add`, appending); and the patch list itself is
  bounded to 1–32 entries with each path capped at 512 characters.
  Matches "Atomic RFC 6902 add/replace/remove subset; no prototype or
  identity writes" from the function's own doc comment exactly.
- **The repaired plan's size is re-enforced after every single patch,
  confirmed exactly**: after applying each patch in the loop, the
  function re-serializes the whole result and throws `too-large` the
  instant it exceeds `MAX_PLAN_BYTES` — not merely a check at the end of
  the whole patch set, catching a mid-sequence blowup immediately.
- Per the PR (not independently re-verified given remaining scope): "The
  host validates and compiles the complete repaired plan through the
  existing pipeline before accepting it" (the materialized plan's
  onward journey through `wordDocumentSubmission.ts`'s 272-line diff and
  the existing validation/compilation pipeline this session reviewed in
  #1257, not traced from this file); "identify missing or duplicate
  source references" (a specific diagnostic not visible in this file);
  "Full proposals and repairs share the configured attempt budget" (the
  backend-side budget accounting in `client_tools.rs`'s 104-line diff
  and `client_operations/mod.rs`'s 11-line diff, not traced); "Submission
  remains separate from the existing user-approved Apply flow" (a scope
  boundary, consistent with this session's review of #1232/#1257/#1258's
  separate Apply-button flow, but not re-verified here); the disclosed
  caveat that "Current-turn history still contains the initial full
  proposal" and that live Word testing and token-savings measurement
  remain pending; the companion private schema/workflow-instructions
  dependency on an external subscription-content PR; and the disclosed
  validation results (720+ Word tests, 20 frontend executor/transport
  tests, 21 backend submission tests on the `main`-rebased base; a
  slightly larger pre-rebase count including one delegation-timeout test
  that needed a third attempt — a pre-existing flakiness pattern this
  session has seen disclosed elsewhere, not specific to this PR's own
  logic).

## Compatibility and configuration

None breaking. Pure addition to the Word add-in's existing document-
submission flow (reviewed across #1232/#1257/#1258/#1259), itself
layered on the generic client-submissions validation infrastructure from
#1215. No backend config changes beyond what the client-submissions
mechanism already required. In-memory draft/replay state is explicitly
scoped to "exactly the lifetime of its captured read session" per the
class's own doc comment, so nothing persists across sessions or needs a
migration.
