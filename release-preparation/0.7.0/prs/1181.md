# PR #1181: Run a turn's delegated tasks side by side, bounded (ERMAIN-768)

- PR: https://github.com/EratoLab/erato/pull/1181
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 3 / position 3 of "Dynamic Delegated Tasks (Delegation Level D)",
stacked on #1180 (ERMAIN-764, reviewed above), gated by
`delegation.tasks.enabled`. Replaces the task route's one-after-another
dispatch with bounded fan-out: launches stay sequential and in call
order, but the waiting happens concurrently up to a configurable limit.
Confirmed every central mechanism claim via direct code inspection of
the full diff:

- **`max_parallel` config field, confirmed exactly**: new
  `DelegationTasksConfig::max_parallel` (default `3`, serde default
  function), with a matching `Option<u32>` field on
  `FacetDelegationOverrides` for per-facet override — matching "bounds
  how many run at once... per-facet overridable" precisely.
- **Validation: default capped, explicit value rejected, confirmed
  exactly**: `DelegationConfig::validate` rejects `max_parallel == 0`
  outright, and separately rejects `max_parallel > max_tasks_per_turn`
  *only when* `self.tasks.max_parallel != default_delegation_tasks_max_parallel()`
  — i.e., a deployment that merely lowered `max_tasks_per_turn` below the
  unwritten default of 3 boots fine (the default is clamped at use via
  `scope.effective.max_parallel.max(1)` wherever it's read, confirmed in
  `message_streaming.rs`), while a value an operator *wrote explicitly*
  above the total is rejected at startup as a contradiction. This matches
  "A default that exceeds a lowered total is capped, not rejected... A
  value written explicitly above the total is still rejected" exactly,
  including the stated reasoning that rejecting an unset default would
  stop an existing deployment booting over a key it never set.
- **Reservation happens for every call, in call order, regardless of
  whether it launches immediately, confirmed exactly**: inside the
  `'pop_calls` loop (which pops `unfinished_tool_calls` in the model's
  emission order), every task call immediately pushes a `ToolUse`
  placeholder with `output: queued_placeholder_output()` at its slot —
  *before* checking whether it can launch — then only `match
  delegation.as_ref() { Some(context) if in_flight.len() <
  effective_max_parallel => { launch_prepared_task(...); in_flight.push(task)
  } _ => queued_tasks.push_back(pending) }` decides whether it starts now
  or waits. This directly confirms "A batch reserves every slot at pop
  and marks the ones beyond the bound as queued."
- **Bound is read once per batch, not per call, confirmed exactly**:
  `effective_max_parallel` is computed once, before the pop loop begins,
  from `scope.effective.max_parallel.max(1)` — matching the stated
  reasoning "a value that moved mid-batch would make the bound a lie."
- **A freed slot launches the next queued call, confirmed exactly**: in
  the join/drain loop (after a task settles via `in_flight.next()` in the
  `tokio::select!`), `while !leaving && in_flight.len() < effective_max_parallel
  { ... pop_front from queued_tasks ... launch_prepared_task(...) }` —
  confirming "each launches as a slot frees." Combined with the
  bounded-reservation logic above, this structurally substantiates "Ten
  tasks at `max_parallel = 4` run four, then four, then two, and never
  five," though the specific four-four-two timing sequence itself is not
  independently traced through a live run in this review.
- **A queued slot names no child, settling through its own outcome,
  confirmed exactly**: a queued call's placeholder uses
  `queued_placeholder_output()` (not `task_placeholder_output`, which
  carries `child_run_id`/`delegate_chat_id`), and if the batch leaves
  before it starts, it settles via
  `DelegationDispatchOutcome::NeverStarted { reason:
  DelegationRunReason::ParentAbort }` rather than through a
  `DelegationRunResult` envelope — matching "a never-started call settles
  through its own outcome rather than through the result envelope, whose
  child ids are not optional" precisely.
- **Abort does not abandon in-flight runs, confirmed exactly**: a code
  comment states directly "An abort stops further launches but does NOT
  stop the join: each child answers its own abort with a `cancelled`
  envelope, and dropping the waits would leave those slots reading
  'working' for runs that are over." The drain loop's structure confirms
  this: `aborting`/`leaving` flags stop new launches (both in the
  replenish loop and implicitly via the pop loop's abort check) while
  `while !in_flight.is_empty() || !queued_tasks.is_empty()` keeps running
  until every in-flight task has actually settled and every queued one
  has been resolved as `NeverStarted` — matching "Aborting stops further
  launches, settles the queued slots, and keeps draining" exactly.
- **Answers reordered to call order before returning to the model,
  confirmed exactly, including the pre-existing `wait`-tool ordering
  fix**: `current_turn_tool_responses` is now `Vec<(usize,
  genai::chat::ToolResponse)>`, paired with each call's `batch_position`
  — populated both from task settlement (`current_turn_tool_responses.push((
  settled.meta.batch_position, response))` / the queued-settle path) and
  from the pre-existing client-tool `wait` path (`pending_wait.batch_position`,
  confirmed added as a new field on the `PendingWait` struct). Immediately
  before the vector is sent to the model, `current_turn_tool_responses.sort_by_key(|(position,
  _)| *position)` — confirming "each response carries the position of the
  call it answers and the set is sorted before it goes back," and
  directly substantiating the disclosed side-effect fix for the
  pre-existing case where the `wait` tool's answer could land out of
  order.
- Per the PR (not independently re-verified given remaining scope): the
  "Corrections to the issue as written" claims (that `max_tasks_per_turn`
  is already counted in call order at validation time so no separate
  pre-pass was needed; that the parent-per-message cap intentionally
  keeps its non-pre-pass behavior for ordinary turns to avoid changing
  refusal semantics product-wide; that `futures` was already a dependency
  so no new license question arises; that `DelegationRunResult::Suspended`
  does not exist so there's no cross-stack obligation with approvals
  today; and that the waves test necessarily uses staggered delays plus
  state observation rather than an on-demand release, since the mock
  server has no such primitive) — all plausible given the surrounding
  code's style and this session's familiarity with the stack, but not
  independently re-traced; the five new tests and one merge assertion
  (the mutation-verified overlap test, the waves test reading the durable
  row mid-run for exactly one working/two queued slots, the abort test
  asserting exactly one slot names a child) — not independently
  reproduced, and the 801-line new integration test file was not read in
  full; and the disclosed verification claims (1117 backend tests, `cargo
  fmt --check`, three clippy feature variants with `-D warnings`,
  `gen-openapi --check`/`gen-config-reference --check`/docs-coverage all
  clean, the two new config keys documented).

## Compatibility and configuration

Additive, non-breaking. New config keys `delegation.tasks.max_parallel`
(default `3`) and a matching per-facet override, gated behind the
existing `delegation.tasks.enabled` flag (confirmed default-off from
this session's review of earlier PRs in the stack). Confirmed startup
validation: `max_parallel` must be at least 1 and, when explicitly set,
cannot exceed `max_tasks_per_turn`; an untouched default is clamped
rather than rejected if a lowered total would otherwise make it invalid.
Confirmed documented in `backend/erato.template.toml`,
`site/content/docs/configuration.mdx`, and
`backend/generated/config_reference.json`.

## Release note disposition

Proposed category: Features and enhancements. The PR's own drafted
`CHANGELOG.md` entry is accurate per the above verification: delegated
tasks planned in one turn now run side by side (bounded by
`delegation.tasks.max_parallel`, default 3, per-facet overridable)
instead of one after another, a queued task is visible in the
conversation as waiting before it starts, and the model is still
answered in the order it asked regardless of settlement order. As with
the rest of this stack, not independently release-note-worthy until
`delegation.tasks.enabled` ships enabled — tracked cumulatively with
#1162-1166/#1180.
