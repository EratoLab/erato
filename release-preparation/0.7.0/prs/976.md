# PR #976: On-device search part 1: sidecar search protocol, nested trace rendering, client-tool abort plumbing (ERMAIN-616)

- PR: https://github.com/EratoLab/erato/pull/976
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Large groundwork PR (4282 insertions across 47 files) for an on-device
mailbox search feature, explicitly described as "fully dormant on its
own" — no client tool is registered and nothing contacts a sidecar yet;
the actual Outlook add-in integration is deferred to a separate follow-up
(ERMAIN-615). Given the scale, review focused on the two claims most
consequential if wrong: a backend stability fix, and a client-side trust
boundary preventing a server-side tool from faking device provenance.

- **Backend stability fix, confirmed via `main.rs`**: the Tokio runtime's
  worker thread stack size is explicitly set to 16MiB (up from Tokio's 2MiB
  default), with the code comment stating this was needed because the
  message-streaming handler's very large futures overflow the default
  worker stack in unoptimized builds — observed, per the comment, "once
  the client-tool offering path became active on every turn" (i.e. a
  consequence of the earlier #786/#795 client-tools work). The comment
  also correctly notes this reservation is virtual (Linux stack pages are
  only committed as touched), so the larger nominal size costs nothing in
  practice for threads that never approach it. This is a real, unrelated
  production fix bundled into an otherwise-dormant feature PR.
- **Trust-boundary protection against forged "ran on your device" traces,
  confirmed via full read of `localTraceStore.ts`'s header and allowlist**:
  a persisted tool result (replayed from the backend, e.g. after a reload)
  is not the protocol-validated live-path data, so it could in principle
  be shaped by *any* tool's output to falsely claim it ran on-device. The
  store restricts trace attachment to an explicit allowlist
  (`SIDECAR_TRACE_RESULT_TOOLS`, currently `search_sidecar_mailbox` plus
  the existing delegation tool names) — confirmed the code's own comment
  states this exists specifically so "any tool could [otherwise] dress its
  output up as an authoritative nested trace" without it. Separately,
  every value entering the store passes through bounded-length/count
  sanitization (`MAX_STEPS = 32`, `MAX_COUNT_ENTRIES = 16`,
  `MAX_COUNT_KEY_CHARS = 64`) even though the live path is already schema-
  validated by the protocol client — defense in depth specifically for the
  non-schema-validated persisted-and-replayed path.
- Per the PR (not independently verified given scope): the
  `desktop-sidecar-protocol` package (bumped 0.1.9 → 0.1.15) gains a new
  `outlook.search_emails.v1` method and an optional metadata-only `trace`
  field on search results (explicitly documented as never carrying
  content — only steps/models/durations/counts), observable mid-flight via
  the existing `sidecar.progress.v1` poll (#910) with the same
  apply-by-`sequence` idempotency guarantee. New
  `SidecarLocalTraceSubtree`/`SidecarLocalTraceView` components render
  these on-device steps as nested rows under a tool-call's trace entry.
  Client-tool executors gain an optional `ClientToolCallContext`
  (toolCallId/messageId/chatId/AbortSignal), and the user's Stop action now
  aborts in-flight client-tool executions for that chat — while, per the
  PR, a transport-level SSE disconnect deliberately does *not* abort the
  tool, since a `resumestream` reconnection can still deliver the result.
  `GroupedFileAttachmentsPreview` gains new per-group action row and
  click-to-preview capabilities, stated to be inert without a consumer
  (the planned ERMAIN-615 results tray).

Not independently verified given the exceptional scope: the new protocol
schemas/generated types/OpenRPC entries (the bulk of the
`desktop-sidecar-protocol` diff, ~1500 lines including generated
validators), the actual rendering logic in `SidecarLocalTraceView.tsx`
(183 lines) and `TraceStep.tsx`'s extended diff, the `localAnswers.ts`
store (156 lines, for on-device answers the user declined to share), the
`traceEvents.ts` merge/sequencing logic (121 lines), or the ~700 lines of
new test coverage across 7+ test files.

## Compatibility and configuration

None new for the shipped product's default behavior — the PR states this
feature is inert without a follow-up PR's client-tool registration. The
backend Tokio worker stack size change applies unconditionally to every
deployment on upgrade (a stability fix, not a configuration option); per
the code comment, the larger virtual reservation has no real memory cost
for threads that don't need it.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the complete `main.rs` diff (confirming
the Tokio worker-stack-size fix and its stated rationale) and the header/
allowlist portion of `localTraceStore.ts` (confirming the anti-forgery
trust boundary precisely). Given the PR's very large scope and its own
explicit "fully dormant" framing, the protocol schema additions and the
bulk of the new UI rendering/state-management code were not independently
read — the two pieces verified were chosen specifically because they are
either a real production-behavior change (the stack size fix, unrelated
to the dormant feature) or the one security-relevant property
(provenance forgery prevention) most worth confirming before it becomes
load-bearing in a later PR.
