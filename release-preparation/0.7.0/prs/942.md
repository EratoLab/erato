# PR #942: feat(frontend): restore PDF text selection and copy (ERMAIN-570)

- PR: https://github.com/EratoLab/erato/pull/942
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes PDF text selection and copy being completely non-functional after
#941 replaced the browser's native (but sandboxed-frame-blocked) PDF
viewer with EmbedPDF/PDFium — the browser's viewer supported
select-and-copy for free; the WASM replacement had none. Confirmed by
reading the code, every specific fix the PR describes:

- **Root cause and fix, confirmed via full diff of `PdfPreview.tsx`**:
  the page content renders as an `<img>` via EmbedPDF v2.15's
  `RenderLayer`, which sets neither `draggable={false}` nor
  `pointer-events: none` — so a drag gesture across the page started a
  native HTML5 image drag instead of a text selection, and the resulting
  `pointercancel` event killed the selection gesture mid-stream (frozen on
  the first glyph). Confirmed the fix applies `draggable={false}` +
  `style={{ pointerEvents: "none" }}` to **both** `RenderLayer` and the
  separate `TilingLayer` (the code comment notes patching only one still
  yields a single selected character), plus `select-none` on the
  `Viewport` container (without it, the browser's own native DOM
  selection paints over the page and visibly discolors it). The PR states
  this exact fix (`draggable:false` + `pointerEvents:'none'`) is already
  applied upstream in EmbedPDF v3 (a pre-release not yet chosen — see
  below) and is being back-ported here as props onto the same v2
  components.
- **Copy-to-clipboard shortcut confirmed via full diff**: a new
  `PdfCopyShortcut` component listens for the browser's native `copy`
  event (bound to `document`, not a container element, since the PDF page
  layers aren't focusable and would never receive a keystroke) and, on
  copy, reads the current text selection from the plugin and calls
  `copyTextToClipboard`. Confirmed the underlying selection plugin itself
  tracks selections and ships a `CopyToClipboard` listener but never
  raises the actual copy request on its own — this component is what
  connects Cmd/Ctrl+C to an actual clipboard write.
- **Clipboard-write fallback confirmed via full read of
  `copySelectionText.ts`**: `copyTextToClipboard` tries
  `navigator.clipboard.writeText` first, falling back to an off-screen
  (not merely `display:none`, since `execCommand` ignores a selection
  inside an unrendered element) `<textarea>` + the deprecated
  `document.execCommand("copy")` on failure — restoring the user's
  previous DOM selection afterward. This matters specifically because, per
  the PR, both Teams and Outlook-on-the-web (the exact two hosts this
  viewer exists to support, since they're the sandboxed-frame hosts that
  broke the native PDF viewer in the first place) serve their frames with
  a Permissions-Policy that withholds `clipboard-write`, so the async
  Clipboard API call would otherwise fail silently in precisely the
  places this feature needs to work.
- A translucent highlight color (`rgba(59, 130, 246, 0.35)`) replaces the
  plugin's opaque default, which would otherwise visually hide the
  selected glyphs underneath it.
- The PR explicitly documents residual, unfixed upstream bugs
  (releasing the pointer outside the page leaves `selecting: true` stuck;
  a numeric `defaultZoomLevel` never lifts the zoom plugin's render gate —
  the app avoids the latter by using `ZoomMode.FitWidth`) and states a
  concrete fallback plan (switching to pdf.js) if the `execCommand`
  fallback turns out not to work in real Teams/Outlook hosts, which it
  flags as needing manual verification since `execCommand` is documented
  to fail in some other Office web hosts (Excel-on-web).

## Compatibility and configuration

None. Pure frontend bug fix; no configuration or API changes. Adds no new
dependencies (the selection plugin package was already present in
`package.json` from #941, just not previously registered) — cost stated
as +8.7KB gzip.
