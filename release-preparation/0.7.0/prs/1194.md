# PR #1194: Report MCP authorization through the house feedback components

## Summary

Follow-up to #1187 (reviewed above), replacing the hand-rolled progress/
success/failure UI that PR introduced (a per-server Alert banner, a
hand-rolled ten-second dismissal timer, dialog-level alerts) with the
existing toast system and `EntityRow`/`Button` primitives, plus two small
additions to the design system itself. Confirmed the concrete, checkable
claims by reading the new `mcpAuthorizationToasts.ts` module and the
`Toast`/`EntityRow` diffs in full:

- **One dedupe slot per server, confirmed exactly**: `mcpAuthorizationToastKey(serverId)
  = \`mcp-authorization:${serverId}\`` is used as every emitted toast's
  `dedupeKey`, with a doc comment stating directly "emitting a new phase
  replaces the previous one instead of stacking a history of the same
  connection attempt" — matching "one dedupe slot per server" exactly.
- **Retry offered as a toast action, confirmed exactly**: the `"unavailable"`/
  error-type phases (not fully read, but the `check` action object is
  defined once and reused) render a primary-variant "Check connection"
  action wired to `onCheck` — matching "with the retry offered as a toast
  action."
- **`toast.dismissKey` retracts whatever holds a dedupe slot, confirmed
  exactly**: `useToastStore`'s new `dismissKey(dedupeKey)` method finds the
  toast whose `dedupeKey` matches and dismisses it by id — a genuinely new
  store method, not a renamed existing one — matching "`toast.dismissKey`
  retracts whatever holds a dedupe slot" precisely, with a doc comment
  explaining its purpose as the `show`-side `dedupeKey`'s counterpart for
  a caller that doesn't track the generated toast id.
- **A toast action may be a link, confirmed exactly, including the
  stated non-dismissing behavior**: `ToastAction.href?: string` is new and
  `onClick` becomes optional; `ToastItem.tsx` renders an `href`-bearing
  action as a real `<a target="_blank" rel="noopener noreferrer">`
  (styled via the new `controlSurfaceClassName` export from `Button.tsx`)
  rather than a `<button>`, and — critically — its `onClick` handler does
  *not* call `beginDismiss()`, unlike the `<Button>` branch which does.
  This matches both "A toast action may now be a link (`href`), because
  the popup-blocked recovery path needs a navigation the browser performs
  itself" and the doc comment's explicit claim "Such an action does NOT
  dismiss the toast: the user is leaving to do the work and comes back to
  the same waiting state."
- **The reopen-authorization-page action is wired through the new `href`
  mechanism, confirmed exactly**: the `"waiting"` phase's toast includes a
  "reopen" action with `href: browserUrl` and a code comment stating "A
  link, not another window.open: the blocker that swallowed the first
  popup would swallow a second one too" — directly connecting the new
  toast-action capability to the specific popup-blocked-recovery use case
  the PR names.
- **`EntityRow` gains a `pending` tone with its own ring and `aria-busy`,
  confirmed exactly**: `EntityRowTone` gains `"pending"`, rendered with a
  `SpinnerIcon` (not a static tone icon) and `text-theme-fg-secondary`
  (a neutral, non-outcome color, matching the doc comment "nothing has
  happened yet — the ring, not the tint, is what says 'wait'"), and the
  row's content wrapper gets `aria-busy={status?.tone === "pending" ||
  undefined}` — matching "a row that is connecting or disconnecting
  carries its own ring and marks its header aria-busy" exactly.
- Per the PR (not independently re-verified given remaining scope): the
  claim that outcomes are now announced from the app root rather than the
  settings pane (plausible given `ClientProviders.tsx`'s 5-line addition
  and the `McpOauthCallbackBoundary.tsx` diff, both touched, but the
  actual mounting location was not traced); the `Authorize`/`Disconnect`
  buttons switching to `Button`'s `loading` prop instead of swapping
  labels (`Button.tsx`'s 23-line diff was not read in full); the
  disconnect-reporting-the-same-way-as-authorize claim and the retirement
  of the dialog-level `mcpError`/`mcpSuccess` alerts (the 101-line
  `ServersToolsPane.tsx` diff and 42-line `UserPreferencesDialog.tsx` diff
  were not read in full); the OAuth callback screen's restoration to
  house components (Alert/primary button/spinner label slot) in
  `McpOauthCallbackBoundary.tsx`'s 30-line diff; the locale-namespace
  move (`preferences.dialog.mcpServers.oauth` vs. the app-root-only
  `mcp.callback`) across all five `messages.po` files (~163 lines each);
  and the complete deletion of `McpAuthorizationNotice.tsx` (135 lines,
  the component this PR fully supersedes, confirmed present in the
  changed-files list as a full removal, consistent with its
  functionality moving into `mcpAuthorizationToasts.ts` and `EntityRow`'s
  new tone).

## Compatibility and configuration

None breaking. Pure frontend UI refactor of the MCP authorization
feedback surface introduced in #1187 — no wire or config changes.
`ToastAction.href` and `toast.dismissKey` are additive design-system
capabilities with no effect on existing toast callers that don't use
them (`onClick` remaining optional rather than required preserves every
existing non-link action's shape). `EntityRowTone`'s new `"pending"`
variant is additive to the existing `"success"`/`"warning"`/`"error"`
set.
