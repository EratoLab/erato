# PR #1016: Record MCP servers skipped for missing OAuth authorization in generation metadata (ERMAIN-657)

- PR: https://github.com/EratoLab/erato/pull/1016
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

First layer of a new "OAuth MCP visibility" stack. Fixes a real
observability gap: when MCP tool discovery skipped a server because the
*requesting user* specifically hadn't completed that server's OAuth
authorization, the skip previously vanished into a debug log with no
trace anywhere — not in `mcp_servers_unavailable`, not in any persisted
metadata. For a shared assistant configured with multiple MCP servers,
this meant the assistant silently behaved differently per user (missing
tools for whoever hadn't connected a given server) with no way for anyone
to tell why. Confirmed by reading the core classification change in full:

- `ToolDiscoveryResult` gains a new `needing_auth_server_ids` field,
  confirmed kept structurally separate from the existing
  `unavailable_server_ids` — the code comments state the distinction
  precisely: "unavailable" means the server itself is broken (nothing the
  user can do), while "needing auth" means the server works fine and this
  specific user just hasn't connected it yet (fixable by the user).
  Confirmed the discovery loop's existing `continue` on an
  `AuthorizationRequired` error (previously logged at debug level and
  otherwise fully discarded) now first pushes the server id into this new
  list before continuing — the skip itself remains non-fatal, unchanged.
- Per the PR (not independently re-verified across every listed consumer,
  given scope): `mcp_servers_needing_auth` mirrors
  `mcp_servers_unavailable` at every downstream surface —persisted
  generation metadata (including whatever presence gate decides whether
  metadata gets written at all, so a generation whose only anomaly is an
  unconnected server still records that fact), the `ChatMessage` API type
  (both the chat history GET and the completion SSE event, plus the
  share-links route from #866/#879), and Langfuse trace metadata.
- Deliberately unchanged, per the PR: the strict tool-approval
  continuation path (`continue_message`, from #918/#994) still tolerates
  a needing-auth server silently — an approved tool call the user already
  consented to must never be blocked just because some *other*,
  unrelated server on the same assistant happens to need the same user's
  OAuth connection. The success path for a fully-connected user is stated
  to be byte-identical to before this change.

## Compatibility and configuration

None. Additive API field only (`mcp_servers_needing_auth`, mirroring the
existing `mcp_servers_unavailable` shape) — no configuration or backward-
incompatible API changes. This is purely a visibility/observability fix;
no change to which tools are actually offered or how a tool call itself
behaves.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the relevant `mcp_manager.rs` and
`mcp_session_manager.rs` diffs — confirming the new classification field
and its precise separation from the pre-existing "unavailable" category,
directly at the point where the previously-silent skip occurred. Not read
in full: the `message_streaming.rs` (29 lines), `mod.rs` (9 lines), and
`genai_langfuse.rs` (12 lines) diffs propagating the new field to each
downstream consumer, or the 188-line new integration test coverage in
`integration_tests/api/messages.rs` — though its described end-to-end
assertion (exact-list separation across the SSE message, persisted
metadata, and the messages GET, using a real mock that fails with
`AuthorizationRequired`) is a direct and appropriate test of the
mechanism verified above.
