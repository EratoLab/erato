# PR #1107: Lift delegation config to `[delegation]` and reserve the `erato` tool namespace (ERMAIN-754)

- PR: https://github.com/EratoLab/erato/pull/1107
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 1 of 4 (Foundation) for a larger async task-delegation feature.
Lifts delegation configuration from `[assistants.delegation]` into a
top-level `[delegation]` section (with `[delegation.assistants]` and
`[delegation.tasks]` sub-tables) and reserves the `erato` tool/MCP-server
namespace for built-in synthetic tools. Stated as no behavior change:
every new key defaults to today's behavior, and `delegation.tasks.*` has
no consumer yet. Confirmed by reading the complete migration/validation
logic in `config.rs` in full:

- **Deprecation alias and migration, confirmed exactly matching the
  PR's own 8-row mapping table**: when `[assistants.delegation]` is set,
  `migrate()` copies exactly the 8 fields the PR's table lists
  (`run_timeout_seconds`, `result_max_chars`, `allow_background`,
  `max_concurrent_background_runs`, `auto_archive_after_days`,
  `preamble`, and `enabled`/`max_mentions_per_message` onto
  `delegation.assistants.*`) onto the new `delegation` struct, logs a
  `tracing::warn!` deprecation notice, and clears
  `config.assistants.delegation = None` afterward.
- **"Both tables set" detection, confirmed exactly**: the code compares
  `config.delegation != DelegationConfig::default()` to infer whether an
  operator wrote `[delegation]` at all (since deserialization cannot
  otherwise distinguish "not written" from "written with default
  values") — if both the legacy table is set *and* `delegation` differs
  from its default, startup panics with an actionable message naming
  both keys. A code comment on the check states the exact documented
  degenerate case matching the PR description: an operator who spells
  out `[delegation]` with values identical to the defaults while also
  keeping the legacy alias would silently take the alias rather than
  being rejected — a known, accepted limitation of comparing against
  `Default`, not a bug.
- **Err vs. panic split between the two config-load paths, confirmed
  exactly**: `validate_mcp_server_ids` is called from both
  `McpRuntimeConfig::from_toml_sources` (where it propagates via `?` as
  an `Err`) and `AppConfig::migrate` (where the caller wraps it in a
  `panic!`) — matching the PR's stated reason precisely: a full-process
  boot-time misconfiguration should panic, but an admin-panel hot-reload
  of MCP config must not take the whole process down, so it instead keeps
  serving the previous, still-valid configuration.
- **Reserved namespace enforcement, confirmed exactly**:
  `RESERVED_TOOL_NAMESPACE = "erato"` and `RESERVED_TOOL_NAMES` (the four
  named synthetic tools) are checked in two places — an MCP server may
  not use the id `erato` (`validate_mcp_server_ids`), and a client tool
  may not use one of the four reserved names or the `erato` namespace
  (the client-tool validation loop, confirmed extended from checking only
  two hardcoded names to `RESERVED_TOOL_NAMES.contains(&name)` plus a new
  explicit `namespace == RESERVED_TOOL_NAMESPACE` check).
- **Cross-struct coupling rule, confirmed exactly**: `delegation.assistants
  .enabled && !config.assistants.enabled` panics at startup (the
  @-mention delegation route still requires assistants to be enabled
  generally) — confirmed no equivalent check exists for
  `delegation.tasks.enabled`, matching the PR's stated deliberate
  decoupling so a deployment could plan tasks without using assistants at
  all (a forward-looking allowance, since `delegation.tasks` has no
  consumer yet).
- **`child_facet_ids` referential-integrity validation, confirmed
  exactly**: both the global `delegation.tasks.child_facet_ids` list and
  every per-facet `experimental_facets.facets.*.delegation
  .child_facet_ids` override are validated to reference only facet ids
  that actually exist in `experimental_facets.facets`, panicking with the
  specific unknown id and its containing facet otherwise.
- Per the PR (not independently re-verified given remaining scope): the
  new `DelegationConfig`/`DelegationAssistantsConfig`/
  `DelegationTasksConfig`/`TaskPersona`/`TaskScheduling` type definitions
  themselves (with `TaskScheduling.interrupt` deliberately absent rather
  than accepted-and-silently-ignored, per the PR); the new
  `FacetConfig.delegation` per-facet override struct; the new
  `AppConfig::effective_max_tool_calls_per_task()` accessor (needed
  because a serde default function cannot read a sibling struct, so the
  fallback to `generation.max_tool_calls_per_message` is resolved at
  accessor call time rather than deserialization time); and the
  deliberate choice to keep the deprecated table in
  `infrastructure/k3d/erato-local/config/erato.scenario-assistants.toml`
  for one release specifically to keep the deprecation path under
  end-to-end test coverage (also noted in the CHANGELOG per the PR).

## Compatibility and configuration

**Deprecation, not a breaking change in this release**: `[assistants
.delegation]` continues to work with a startup warning until `0.8.0`,
confirmed via the exact migration logic read above. Setting both
`[assistants.delegation]` and a non-default `[delegation]` table
simultaneously is a hard startup rejection (by design, to force an
explicit migration rather than an ambiguous merge). New reserved
namespace/tool-name constraints: an MCP server configured with id `erato`
or a client tool using the `erato` namespace or one of
`propose_client_action`/`delegate_to_assistant`/`delegate_task`/
`collect_tasks` now fails startup validation — a behavior change only for
a deployment that happened to already use one of those reserved names.

## Release note disposition

Proposed category: Features and enhancements (config restructuring,
foundation for a larger delegation/task feature). Worth a mention in a
"Deprecations" or "Configuration changes" section: `[assistants
.delegation]` is deprecated in favor of a new top-level `[delegation]`
section (with `[delegation.assistants]`), with the old table still
honored (with a warning) until 0.8.0; deployments should migrate before
then. The `erato` tool/MCP-server namespace reservation is also worth a
compatibility note for any deployment that happens to use it today.
