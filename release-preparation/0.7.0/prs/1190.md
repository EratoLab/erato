# PR #1190: Keep a delivered task result on the thread when a stale client replies (ERMAIN-778)

- PR: https://github.com/EratoLab/erato/pull/1190
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 4 "Async re-entry", position 3 of 5, based on #1189 (ERMAIN-777,
reviewed above). Like its predecessor, explicitly disclosed as still
dark: "nothing writes a `result_delivery` until ERMAIN-780, so both
behaviours are unreachable in any deployment." Addresses what happens
when a client that hasn't refreshed submits/edits/regenerates below a
server-appended `task_result` row it never saw — submit re-anchors past
such rows instead of branching them away; edit/regenerate (genuine branch
operations) instead reconcile the now-orphaned delivery record. Confirmed
every central mechanism and its stated placement/safety rationale by
reading the complete `requeue_or_supersede_branched_deliveries` SQL and
the relevant `message_streaming.rs` call sites:

- **Submit re-anchors below server rows instead of branching them away,
  confirmed exactly**: `run_message_submit_task` now computes
  `effective_previous_message_id` via
  `resolve_system_delivered_tip(&app_state.db, &chat.id, &anchor)` when
  `delegation.tasks.enabled`, falling back to the client's own anchor if
  no deeper tip is found — and this computed value, not the raw client-
  supplied `previous_message_id`, is what's passed to
  `bg_stream_save_user_message`. A code comment states the walk is
  deliberately allowed to resolve to "a user row, which is the steady
  state for a `silent` delivery," confirming it's a genuine tree-walk past
  server-authored rows, not merely validation.
- **Placement inside the generation lifecycle is load-bearing, confirmed
  exactly, including the stated failure mode it avoids**: the walk runs
  after the (already-reviewed, #1188) lease acquisition and before
  `bg_stream_save_user_message`, with a code comment stating verbatim the
  PR's own reasoning: "a `?` between the lease call and the spawn would
  return with the lease still held and no task to release it — and under
  the identity-guarded heartbeat that chat then refuses every later
  write... Here it runs inside the generation lifecycle, which already
  owns cleanup. Still after the lease, so no concurrent delivery can
  append a row between this read and the write." This directly confirms
  the ordering claim is deliberate and safety-relevant, not incidental.
- **Edit and regenerate reconcile rather than re-anchor, confirmed
  exactly, in both route handlers**: both `regenerate_message_sse` and
  `edit_message_sse` call `requeue_or_supersede_branched_deliveries(&app_state.db,
  &chat.id)` — gated on `delegation.tasks.enabled` — immediately *after*
  their own `submit_message` call returns, with an identical comment in
  both handlers: "After `submit_message` returns, because it owns its own
  transaction and the active flags are not final until it commits."
  Failures are logged via `tracing::warn!` and not propagated, consistent
  with this being dead code today (no `result_delivery` rows exist to
  reconcile) and with best-effort semantics appropriate to a
  reconciliation side-effect.
- **Re-queue vs. supersede logic matches exactly**: in
  `requeue_or_supersede_branched_deliveries`'s SQL, the `requeue_cond`
  requires both `redeliveries = 0` (i.e., not already re-delivered once)
  *and* the delivery's origin message (`provenance.origin_message_id`)
  still being `is_message_in_active_thread` — matching "a delivery whose
  origin turn is still on the thread goes back to pending for one more
  attempt" and "Re-queued at most once, so a user who keeps branching
  does not accumulate re-appended results" precisely. The `ELSE` branch
  marks `state: superseded, reason: origin_branched` for every other
  case (origin turn itself branched away, or already re-delivered once) —
  matching "the rest close as superseded."
- **Path-scoped `jsonb_set`, not a read-modify-write, confirmed exactly,
  with the exact stated reason**: the `UPDATE` targets only the
  `{provenance,result_delivery}` JSON path via `jsonb_set`, merging
  (`||`) into the value read live from `"c"."assistant_configuration"` in
  the *same* statement (not a value cached earlier in the request), with
  a code comment stating precisely: "`mark_delegated_run_adopted`...
  replaces the entire `assistant_configuration` column from a possibly
  stale in-memory row, with no transaction and no version guard, and it
  fires on every user write into a delegated chat. Scoping the write to
  `{provenance,result_delivery}` keeps the two from erasing each other."
  This matches "One path-scoped `jsonb_set` rather than a read-modify-
  write... the two would otherwise erase each other" exactly, and is a
  genuinely verifiable concurrency-safety property (an unscoped
  read-modify-write racing against `mark_delegated_run_adopted`'s
  whole-column replace would indeed lose whichever write landed first).
- **Compare-and-set via the `state IN (...)` predicate, confirmed
  exactly**: the `WHERE` clause requires
  `result_delivery.state IN ('delivered', 'reacted')`, so a row another
  concurrent path already moved elsewhere (e.g., to `pending` or
  `superseded` by a prior run of this same function) is simply excluded
  from the `UPDATE`'s matched rows — matching the code comment "a row
  another path moved on between our read and this write is simply
  skipped."
- Per the PR (not independently re-verified given remaining scope): the
  `resolve_system_delivered_tip` function's own tree-walk implementation
  (in `message.rs`, part of the 112-line diff there, not read) — the walk
  logic itself (how far down the active thread it descends, and what
  counts as "the server's own rows") was not traced line-by-line, only
  its call-site integration and placement; the disclosed test strategy
  ("Both branches of the reconciler, and the route that triggers it, are
  pinned against hand-seeded rows" since nothing yet produces real
  `result_delivery` rows) — plausible given the 661-line new integration
  test additions in `messages.rs`, but not independently reproduced; and
  the disclosed verification (1152/1152 `cargo nextest run`, clean
  clippy `-D warnings`).

## Compatibility and configuration

No new config keys, no wire changes (confirmed consistent with the
changed-files list containing no `config.rs`/`config_reference.json`/
`openapi.json` diffs). Both new behaviors are gated behind
`delegation.tasks.enabled` and additionally only reachable for
`result_delivery` rows nothing currently produces (per #1189's "ships
entirely dark" disclosure) — so this PR has zero runtime effect in any
current deployment, confirmed structurally by every new code path being
behind both the feature flag and data that doesn't yet exist.
