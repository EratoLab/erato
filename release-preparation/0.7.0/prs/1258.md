# PR #1258: Show Word apply progress on the Apply button and read documents less often

- PR: https://github.com/EratoLab/erato/pull/1258
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Another follow-up to the Word add-in (stacked on #1257, reviewed above).
Fixes an apply flow that "felt broken" for a large plan: the Apply
button didn't react to a click, then disappeared with no spinner,
because `applyWordDocumentPlan` did all its synchronous parse/validate/
compile/verify work before the first `await`, starving the UI of a
paint. Separately reduces redundant document reads. Confirmed the core
timing-yield mechanism and the document-read efficiency changes
directly:

- **A bounded frame-yield before synchronous work, confirmed exactly**:
  the new `yieldToPaint()` races `requestAnimationFrame` (which the
  comment notes "pauses in a hidden pane") against a 50ms `setTimeout`
  fallback, resolving on whichever fires — matching "`applyPlan` yields
  one frame (at most 50 ms when the pane is hidden) after entering
  'checking', before the synchronous work, so the busy state paints
  first" exactly.
- **Per-stage timing tracked and logged at debug level, confirmed
  exactly**: the new `trackWordApply` accumulates elapsed time per
  `WordApplyStage` (`"checking" | "backup" | "writing" | "verifying"` —
  matching the PR's stated stage sequence "Checking document…" →
  "Saving backup…" → "Applying…" → "Verifying…") and its `finish`
  callback logs `console.debug("[erato] Word apply timings (ms)", {
  kind, outcome, total, ...perStageDurations })` — matching "Per-stage
  timings are logged via `console.debug('[erato] Word apply timings
  (ms)', …)`" exactly, confirming this is genuinely new instrumentation
  ("there was no debug flag to hook into").
- **4 MB file-read slices replacing 64 KB, with the slice-count bound
  preserved for smaller-slice hosts, confirmed exactly**: `document.getFileAsync`'s
  `sliceSize` changes from `64 * 1024` to a new `WORD_FILE_SLICE_BYTES =
  4 * 1024 * 1024` constant, documented as "Office's documented maximum
  and default; one slice covers every supported DOCX" — matching
  "requests 4 MB slices (Office's documented default and maximum)
  instead of 64 KB: one host round trip instead of up to 64 per full-
  document read" exactly. The slice-count validity check is left
  computed against the *old* 64 KB denominator
  (`Math.ceil(MAX_WORD_DOCX_BYTES / 65536)`), with a new comment "Bounded
  as for 64 KB slices, so a host that returns smaller slices is still
  accepted" — directly confirming "The slice-count bound still
  tolerates hosts that return smaller slices" as a deliberate choice,
  not an oversight.
- **The package fingerprint is now computed lazily, confirmed exactly**:
  `captureWordDocumentPackage`'s returned object's `fingerprint` field
  becomes a getter (`fingerprint ??= createWordXmlComparison(parseWordXml(ooxml)).fingerprint();
  return fingerprint;`) instead of an eagerly-computed value at
  construction time — so a caller that never reads `.fingerprint`
  (described as the send-path capture) never triggers the parse/
  canonicalization work at all, matching "The package fingerprint is
  computed lazily; the send-path capture never reads it, which saves
  one parse and canonicalization per send" exactly.
- Per the PR (not independently re-verified given remaining scope): the
  Apply button's `busy`/`aria-disabled` focus-preserving rendering and
  its interaction with the existing synchronous double-click guard in
  `WordWriteProvider` (in `WordDocumentPlanCard.tsx`'s 36-line diff and
  `WordHostCardRenderer.tsx`'s 28-line diff, not traced); the removal of
  the separate "Applying and verifying the document rewrite…" alert; the
  new `ActionConfirmationCard.progressLabel` prop and its claimed
  non-effect on existing callers (72-line diff, not read); the claim
  that `captureWordAuthoringSnapshot` now fingerprints a document it
  already parsed rather than re-parsing (not traced); the full-document
  apply/revert path's fingerprint source-fallback logic; and the
  extensive disclosed new/updated test files (roughly 300 lines across
  seven test files covering the progress tracker, the card, the host
  renderer, and the apply/package utilities).

## Compatibility and configuration

None breaking. Pure Word add-in UX/performance follow-up within the
feature reviewed in #1232/#1257 — no backend, config, or wire changes
(confirmed by the all-`office-addin/`-plus-shared-component changed-files
list). The 4 MB slice size is within Office's own documented API limits
per the code's comment, not independently verified against Microsoft's
API documentation in this review.
