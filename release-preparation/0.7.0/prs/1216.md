# PR #1216: Expose sidecar search metadata discovery to chat clients

- PR: https://github.com/EratoLab/erato/pull/1216
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Small, focused follow-up to #1213 (reviewed above), adding a third
optional sidecar client tool — `get_sidecar_search_fields` — so the model
can discover which structured metadata fields the connected device's
index supports, and wiring `metadata_filters` through to the existing
search tool with the same mailbox-ID normalization already established
in PRs #1211/#1213. Confirmed both core changes directly:

- **New `get_sidecar_search_fields` tool added, confirmed exactly**: a
  new `GET_SIDECAR_SEARCH_FIELDS_TOOL = "get_sidecar_search_fields"`
  constant and tool entry invokes `client.invoke("search.metadata_fields.v1",
  ...)` — matching "Add `get_sidecar_search_fields` to the shared optional
  client tools, backed by the existing pinned `search.metadata_fields.v1`
  contract" precisely.
- **`metadata_filters` forwarded alongside existing filters, with
  mailbox-ID normalization applied to equality/inequality/membership
  predicates specifically, confirmed exactly**: the search tool's params
  construction now spreads `args.metadata_filters?.map(normalizeMailboxMetadataFilter)`
  into the outgoing request (previously only the plain `filters.mailboxId`
  shorthand was normalized). The new `normalizeMailboxMetadataFilter`
  function only acts when `filter.field === "mailbox_id"`, and handles
  exactly three operators: `"eq"`/`"ne"` (normalizing the single scalar
  `value` via the existing `indexingMailboxId` helper this session
  confirmed in PR #1211's review) and `"in"` with an array value
  (normalizing every element) — any other field or operator passes
  through unchanged. This matches "normalizes compact mailbox IDs in
  equality, inequality and membership predicates" exactly (eq =
  equality, ne = inequality, in = membership), and correctly reuses the
  same compact-to-hyphenated-UUID normalization this session already
  verified elsewhere.
- **Discovery availability is independent of the other sidecar tools,
  confirmed structurally**: `get_sidecar_search_fields` is added as its
  own separate tool entry in the returned array rather than folded into
  or gating the existing `search_sidecar_index`/`read_sidecar_conversation`
  tools' definitions — consistent with "Discovery availability is
  independent: older sidecars retain their supported search and
  conversation tools" (an older sidecar that doesn't implement
  `search.metadata_fields.v1` would simply have this one tool call fail
  or be unavailable, without affecting the other two).
- Per the PR (not independently re-verified): the backend-side rename/
  consolidation from `desktop_sidecar_tools.rs` to `client_tools.rs` and
  the stated move of "Canonical tool definitions, schemas and facet
  prompts" to the subscription configuration package (consistent with
  the full deletion of `backend/examples/desktop-sidecar.erato.toml`, 62
  lines removed with none added, visible in the changed-files list, and
  the "retain generic configuration coverage" framing); the disclosed
  test results (75 frontend tests covering discovery/pinned-validation/
  metadata-predicates/compatibility, 1,365 add-in tests, 2 backend
  configuration tests, shared-library build verification, and Rust
  formatting/Git diff checks); and the explicit disclosure that live
  Windows/Outlook testing remains a separate manual check.

## Compatibility and configuration

None breaking. Purely additive frontend client-tool capability (one new
optional tool plus an enhancement to an existing one's filter forwarding)
shared between the web frontend and add-ins via the shared library,
confirmed consistent with #1213's established `requires_client_registration`
opt-in gating pattern for sidecar tools (not re-verified as changed in
this diff). No sidecar implementation or protocol-package changes,
confirmed by this PR touching no files under `desktop-sidecar-protocol/`.
