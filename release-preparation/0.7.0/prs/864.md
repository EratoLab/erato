# PR #864: Add sidecar restart command to sidecar protocol spec

- PR: https://github.com/EratoLab/erato/pull/864
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Desktop Sidecar for local sources

## Summary

Adds a new `sidecar.restart.v1` JSON-RPC method to the desktop-sidecar
protocol (`desktop-sidecar-protocol/`), intended for development and
operational workflows to request the sidecar process restart itself. Per
the new "§11. Sidecar restart" section added to `SPEC.md`: the sidecar
MUST let the in-flight `{accepted: true}` response complete before
terminating, MUST spawn its replacement using the exact same executable
and argument vector as the current process (preserving bind-address
overrides and any future arguments verbatim, without reinterpreting them),
MUST stop accepting new work and release its listener before terminating,
and MUST reject the request with a protocol error (rather than returning
`accepted: false`) if a restart can't be scheduled. The client must treat
its current discovery data as stale after a restart and rediscover once
the endpoint is available again, since the replacement process gets a new
instance ID. This PR adds the JSON Schema request/result contracts
(params schema is effectively empty/open; result requires a boolean
`accepted`), generated TypeScript types/validators, a
`"sidecar.restart.v1"` overload on `DesktopSidecarClient.invoke`, and a
mock implementation in `test-server/src/server.ts`.

The `openrpc.json` method registration lists four possible errors for this
method: `CapabilityUnavailable`, `InvalidParams`, `PermissionDenied`, and
`SidecarInternal` — the presence of `PermissionDenied` (a pre-existing
shared error type, not specific to this method) indicates restart is
expected to be a gated operation, not something any caller can trigger
unconditionally, though this PR does not itself define the gating policy
(that's left to whatever sidecar implementation adopts the method). The
method is registered under `x-erato-capability` with id `sidecar.restart`,
major version `1`, and `availability.state: "enabled"` — consistent with
how `diagnostics.echo.v1` (the pre-existing method) is declared. Adding
this capability bumps the protocol's overall catalogue revision from `"1"`
to `"2"` (and its SHA-256 digest changes accordingly), which is how a
client detects that the capability set changed since the last discovery.
The mock server implementation in `test-server/src/server.ts` is
minimal and honest about being a stub: it validates the (empty) params,
increments an internal `#restartRequests` counter (exposed via a
`restartRequests` getter, presumably so conformance tests can assert the
mock received the call), and always returns `{accepted: true}` — it does
not actually restart any process, since it's a deterministic mock for
protocol-conformance testing, not a real sidecar.

## Compatibility and configuration

No backend/frontend application configuration keys — this is
protocol-specification and generated-client work only. No production
runtime behavior change; the actual sidecar application implementing this
restart command is out of scope of this PR (only the mock test server
implements it here). This is additive to the protocol (a new optional
capability), not a breaking schema change.
