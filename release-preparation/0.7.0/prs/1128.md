# PR #1128: Implement more granular policy data rebuild

- PR: https://github.com/EratoLab/erato/pull/1128
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Major rework of the backend's authorization-policy data layer, replacing
a periodic whole-dataset rebuild (time-threshold-triggered, with a
`last_miss_rebuild` tracking map and explicit `invalidate_data()` calls
scattered across write paths) with a granular, per-entity fact cache
invalidated by targeted PostgreSQL `NOTIFY` events. The PR description
itself is a title plus a stress-test benchmark table only (no narrative
of design decisions), so — unlike most other reviews in this set — there
are few authored claims to verify sentence-by-sentence; this review
instead confirms what the code demonstrably implements by reading the
core new mechanism directly.

- **New migration `0041`, confirmed exactly by direct read**: adds one
  `notify_policy_facts_changed()` trigger function and seven `AFTER
  INSERT OR UPDATE OR DELETE` triggers (on `chats`, `assistants`,
  `file_uploads`, `chat_file_uploads`, `assistant_file_uploads`,
  `share_grants`, `share_links`, `assistant_hub_assistant_versions`).
  Each trigger call is parameterized with a fact "kind" tag, the id
  column to extract, and — for `UPDATE` only — the specific columns whose
  change should trigger a notification (e.g. `chats` only notifies on
  changes to `id`/`owner_user_id`/`archived_at`, not every column).
  `pg_notify('policy_facts_changed', ...)` fires with a JSON array of
  `[kind, id]` pairs for the distinct old/new ids involved — correctly
  relying on PostgreSQL's guarantee that `NOTIFY` is delivered only after
  commit and discarded on rollback (stated directly in the migration's
  own header comment), so no fact is invalidated for a change that never
  actually committed. The `share_grants`/`share_links` triggers correctly
  scope themselves to the resource type this policy cares about
  (`assistant` grants, `chat` links) via a `CASE` check against
  `resource_type` before extracting an id.
- **New `policy/facts.rs` (1307 lines), confirmed by direct read of its
  core structure**: a `moka::future::Cache` keyed by `(Kind, Uuid)`
  (`CACHE_CAPACITY = 20_000`) holds per-entity fact records (chat
  owner/archived state, assistant owner, file owner, chat/assistant-file
  associations, share grants, share links, assistant-hub publish state).
  Each cached record carries `expires_at = observed_at + FACT_MAX_AGE`
  (`FACT_MAX_AGE = Duration::from_secs(5)`) as an absolute staleness
  ceiling — confirmed directly in code, and confirmed by the module's own
  doc comment: "Committed change notifications invalidate affected
  generations; absolute expiry bounds missed-notification staleness." A
  long-lived background task (`ListenerTask`) issues `LISTEN
  policy_facts_changed` on a dedicated connection (confirmed via a code
  comment noting this must not consume an ordinary query-pool slot) and
  calls `invalidate(&self, keys: &[Key])` on each received notification,
  with a reconnect-and-re-`LISTEN` loop on disconnection.
- **`state.rs`'s `GlobalPolicyEngine` rewritten to match, confirmed
  exactly**: the previous time-threshold-based refresh logic (a
  write-locked `last_rebuild_time` check, an explicit
  `engine.invalidate_data().await` call, then a full
  `rebuild_data_if_needed`) is removed from the request path entirely.
  `get_engine_with_rebuild_check` now ignores its `time_threshold`
  parameter (renamed to `_time_threshold`, ignored) and simply delegates
  to a new `request_engine`, which calls `self.engine.for_request(db,
  config)` — consistent with per-request fact assembly from the granular
  cache rather than a periodically-rebuilt global snapshot. The doc
  comment on `GlobalPolicyEngine` itself is updated to "Shared prepared
  templates and notification-invalidated authorization fact cache,"
  matching this architectural shift precisely.
- **Reported performance impact, self-reported by the PR author, not
  independently reproduced**: a 20-concurrent-user, 60-second stress test
  is cited showing +28.8% completed chats, -22.3% average chat time,
  -27.6% average p95 latency, and successful-session rate improving from
  90% to 100% (36/40 → 40/40) versus baseline — these figures come from
  the PR's own benchmark table and were not re-run or independently
  verified in this review.

## Compatibility and configuration

New migration `0041` (additive: one function, seven triggers, no schema/
column changes — confirmed via the migration's own revert script
existing as a companion). No new configuration keys observed in the diff
stat. This is an internal performance/correctness rework of how
authorization facts stay fresh across concurrent requests; no API
contract change, though the underlying behavior (how quickly a
permission change — e.g. revoking a share grant — becomes visible to a
concurrent request) changes from "periodic rebuild, bounded by the old
time threshold" to "near-immediate via `NOTIFY`, with a 5-second absolute
ceiling as a fallback."

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the complete migration `0041` SQL
(confirming the exact trigger/notify mechanism, its per-table scoping,
and its commit-only delivery guarantee) and the opening ~150 lines of
the new `policy/facts.rs` (confirming the cache structure, key shape, and
staleness-bound design) plus a targeted search confirming the `LISTEN`
background task, its dedicated-connection design, and the
`invalidate`/expiry mechanics. Given this PR's unusually large scope
(2734 lines across `engine.rs` and `facts.rs` alone) and complete absence
of an accompanying narrative description to check individual claims
against, this review does **not** constitute a full line-by-line audit of
the new policy-engine internals — in particular, the bulk of the 1307-line
`facts.rs` (batch-loading logic, cache-population queries, the 732-line
rewritten `engine.rs` consuming these facts to produce authorization
decisions), the `policy_engine_middleware.rs` diff (24 lines), the
`backend.rego`/`backend_test.rego` diffs (96 and 45 new lines), and the
~15 call-site diffs across the API handlers adapting to the new engine
API shape were not independently re-verified beyond confirming the code
compiles into the described architecture.

## Release note disposition

Proposed category: Bug fixes (performance and correctness improvement to
the authorization layer, no user-facing API change). Worth a mention as
a performance improvement: the backend's permission-checking system was
reworked to invalidate only the specific data affected by a change
(instead of periodically rebuilding its entire dataset), improving
throughput and latency under concurrent load per the PR's own benchmark.
