# PR #964: Add config settings for max_files in normal chat and assistants

- PR: https://github.com/EratoLab/erato/pull/964
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Makes the previously-hardcoded per-message and per-assistant file-count
limits configurable. Confirmed by reading the code:

- New `frontend.max_files` (default `5`, with a backward-compatible
  `alias = "max_files_per_message"` so an existing config using the old
  key name keeps working) and `assistants.max_files` (default `5`)
  config fields, both validated to be greater than zero
  (`FrontendConfig::validate`, wired into the main config-validation
  panic path).
- **Confirmed real server-side enforcement, not merely a frontend UI
  cap**: `validate_file_uploads_for_message_submit` now rejects a message
  submission with more than `frontend.max_files` attached files with
  `422 UNPROCESSABLE_ENTITY`; `create_assistant`/`update_assistant`
  similarly reject a request whose `file_ids` exceeds
  `assistants.max_files`. All three checks were read directly and confirm
  the limit is actually enforced at the API boundary, not just advisory
  in the client.
- Frontend: `max_files` is threaded through the environment/feature-config
  pipeline (`frontend_environment.rs`, `env.ts`,
  `FeatureConfigProvider.tsx`) and consumed by the various file-upload UI
  components (`ChatInput`, `AssistantForm`, `CloudFilePicker`,
  `FileUploadWithTokenCheck`, etc.) — not independently re-verified across
  all ~10 touched frontend files, but consistent with replacing a
  previously-hardcoded UI constant with the configured value.

## Compatibility and configuration

New, optional config fields, both defaulting to `5` (matching the
previous hardcoded limit, per the PR's framing as adding configurability
rather than changing behavior):
```toml
[frontend]
max_files = 5  # default; alias: max_files_per_message

[assistants]
max_files = 5  # default
```
No behavior change for any deployment that doesn't override these — the
default matches the prior hardcoded limit. A deployment that does
override either value gets that limit enforced both in the UI and at the
API boundary.
