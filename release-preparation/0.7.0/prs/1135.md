# PR #1135: Mark archived chats in history and offer unarchive (ERMAIN-794)

- PR: https://github.com/EratoLab/erato/pull/1135
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Third of four in the archived-chat stack (on #1134). Makes archived
chats visible (an "Archived" pill, an accessible-name mention) and
restorable (an Unarchive menu action) across every history-rendering
surface, replacing the previous "Remove" action's one-way framing with
"Archive"/"Unarchive." Confirmed by reading the complete new
`chatArchiveActions.tsx` (the shared menu-item builder both the sidebar
and, per a disclosed review fix, the search page now consume) in full:

- **One shared menu builder, confirmed exactly**: `buildArchiveMenuItems`
  is a single function producing the archive/unarchive menu item pair,
  imported by both surfaces — directly confirming the PR's disclosed
  review finding that the search page had been hand-rolling its own row
  menu with its own (missing) confirmation logic, now consolidated so
  "labels, icons, test ids and the conditional confirm exist in exactly
  one place."
- **Confirmation dialog strictly conditional on live generation state,
  confirmed exactly**: `confirmAction: warning != null`, where `warning`
  is non-null only when `status === "running"` (message: "Archiving will
  not stop the response") or `status === "action_required"` (message:
  "Archiving abandons it, and unarchiving will not resume the
  response") — any other status (idle) gets `confirmAction: false`,
  matching the PR's stated design exactly: archiving is reversible, so
  the destructive-confirmation dialog only fires for the specific work
  unarchiving genuinely cannot restore.
- **Handler-presence gating prevents a dead clickable action, confirmed
  exactly**: both branches (`archived`/not) return an empty array unless
  the corresponding `onArchive`/`onUnarchive` callback was actually
  passed — a code comment states this is deliberate, matching every
  other menu item's convention, so a caller that forgets to wire a
  handler doesn't ship a visible-but-inert menu entry.
- **String-id reuse and retirement, confirmed exactly matching the
  disclosed translation-compatibility claim**: the new "Archive" label
  reuses the existing `chat.history.menu.remove` string id (now
  displaying "Archive" instead of "Remove" under the same id), and the
  confirm dialog's title reuses `chat.history.menu.confirm_remove.title`
  (now "Archive this chat?") — both confirmed as the "kept ids that
  changed meaning" the PR calls out for fork-catalog re-translation. The
  old single confirm-message id is confirmed retired: `confirmMessage`
  now comes from the two new conditional ids
  (`chat.history.menu.confirm_archive.running`/`.action_required`), never
  from the old id.
- Per the PR (not independently re-verified given remaining scope): the
  search-page-specific fixes (the query now following the sidebar's
  status filter so `include_archived` is sent consistently, turning the
  search result into a real row component reading the same
  `useChatRowStatus` hook the sidebar uses); the delegated-run-row
  exclusion (archived run rows offering neither Archive nor Unarchive,
  keyed on provenance rather than on whether a display label resolves —
  not independently located in the files read, since `buildArchiveMenuItems`
  itself has no provenance-awareness, implying this exclusion happens at
  a call site before the builder is even invoked); the disclosed silent-
  failure fix (a failed unarchive on all three web surfaces now raises an
  error toast, matching the add-in's existing behavior); the swapped menu
  icons (`ArchiveIcon`/`UndoIcon`, confirmed present in this file, losing
  the previous trash-and-danger treatment now that the action is
  reversible); and the disclosed component-kit-parity gap (a fork
  rendering its own row markup inherits the archived flag/label/composed
  accessible name from the shared presentation hook and the menu builder
  from the generated kit surface, but must still render the pill itself,
  suppress Pin/Share, and wire the unarchive callback through — stated as
  a known gap with a follow-up planned, not fixed here).

## Compatibility and configuration

None breaking. Real, intentional UX change: the row action renamed from
"Remove" to "Archive" (same underlying operation, same string id — a
translation-compatible rename per the PR's own framing) with a new
reversible framing; the destructive confirmation dialog is now shown only
for a chat that's actively generating or parked on a tool approval,
removed for an idle chat. Component-kit forks with their own row markup
need a follow-up to render the pill/suppress Pin-Share/wire unarchive
themselves (explicitly disclosed as not covered by this PR).
