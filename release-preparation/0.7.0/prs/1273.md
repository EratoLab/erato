# PR #1273: Namespace tool calling ID to prevent overlap in e.g. Gemini

- PR: https://github.com/EratoLab/erato/pull/1273
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

No GitHub description beyond a Linear reference (ERMAIN-883); evaluated
directly from the diff, which is self-contained and precisely tested.
Fixes a real correctness bug: some providers (Gemini named in the
title) can reuse the exact same tool-call ID across different turns of
the same generation (e.g. repeated calls to a Python execution tool).
Since the existing code tracked each tool-use part in the assistant
message's content by that raw provider ID, a repeated ID on a later turn
would silently overwrite the already-recorded tool-use part from an
earlier turn — losing that earlier call's recorded outcome entirely.
Confirmed the fix and its two dedicated tests precisely:

- **A deterministic namespacing scheme makes every call ID globally
  unique within a generation, confirmed exactly**: the new
  `generation_tool_call_id(assistant_message_id, turn, call_id)` returns
  `"{assistant_message_id}:{turn}:{call_id}"` — combining the assistant
  message's identity, the current turn number, and the provider's own
  (possibly-reused) call ID, so two turns reusing the identical raw ID
  always produce distinct namespaced IDs.
- **The rewrite is applied uniformly to both relevant stream event
  shapes, confirmed exactly**: `namespace_stream_tool_call_ids` rewrites
  `ChatStreamEvent::ToolCallChunk`'s `tool_call.call_id` and, separately,
  every `GenAiContentPart::ToolCall`'s `call_id` inside an
  `End` event's `captured_content` — covering both the incremental
  streaming-chunk path and the final captured-content path, leaving
  every other event variant (`other => other`) untouched.
- **Wired at the single point where streamed provider events are
  processed, confirmed exactly**: the existing `match result { Ok(message)
  => match message { ... } }` in the generation loop becomes `Ok(message)
  => match namespace_stream_tool_call_ids(message, assistant_message_id,
  current_turn) { ... }` — applying the rewrite to every event before any
  downstream code (including the content-tracking `upsert_tool_use`
  helper this session has seen elsewhere, e.g. PR #1217's review) ever
  sees the raw, possibly-colliding provider ID.
- **A dedicated unit test directly reproduces the exact described bug
  and proves the fix resolves it, confirmed exactly**:
  `repeated_run_python_calls_keep_each_outcome_in_generation_order`
  simulates 14 turns that all reuse the identical raw provider call ID
  (`"call#run_python_code#0"`), with turn 13 succeeding and every other
  turn erroring, feeding each through `namespace_stream_tool_call_ids`
  and then the real `upsert_tool_use` content-tracking function. The
  test asserts the resulting content array has exactly 14 distinct
  parts (not collapsed into fewer by an ID collision), each bearing the
  correctly turn-numbered namespaced ID, with turn 13's success and its
  specific output (`{"files": ["result.csv", "summary.txt"]}`) correctly
  isolated from the other 13 error outcomes — directly proving the
  overwrite bug named in the PR's title ("overwrites prior python calls")
  is fixed.
- **A second test confirms the namespacing is distinct per turn and
  correctly rewrites both event shapes, confirmed exactly**:
  `repeated_provider_ids_are_unique_across_model_turns_and_match_stream_events`
  passes the identical raw call through a `ToolCallChunk` event at turn 1
  and an `End` event at turn 2, asserting the two resulting namespaced
  IDs are exactly `"{uuid}:1:call#run_python_code#0"` and
  `"{uuid}:2:call#run_python_code#0"` respectively, and explicitly
  asserts the two are not equal.
- **A small, unrelated CI/tooling change bundled in, confirmed exactly**:
  both `.github/workflows/docker-build.yml` and `backend/justfile`'s test
  commands gain `--no-fail-fast` on their `cargo nextest run` invocations
  — letting the full test suite run to completion and report every
  failure instead of stopping at the first, a reasonable quality-of-life
  tweak not mentioned anywhere in the (minimal) PR title/body but visible
  directly in the diff.

## Compatibility and configuration

None breaking. The namespaced call ID is purely an internal tracking key
used while building the assistant message's content during a single
generation; nothing in this diff suggests it's persisted in a different
form than before or exposed on the wire differently (not independently
verified against the full persisted-message shape, but the fix is
scoped to the in-memory streaming/content-tracking path). No config
changes.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: a chat turn where the
model calls the same tool (such as Python code execution) more than once
across several internal steps no longer risks losing an earlier call's
recorded result when the provider (observed with Gemini) reuses the same
internal call identifier across those steps.
