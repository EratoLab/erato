# PR #931: feat(office-addin): add the Teams personal app route

- PR: https://github.com/EratoLab/erato/pull/931
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds a new Microsoft Teams personal-tab entry point to the add-in (ERMAIN-553,
stacked on #930's local Teams manifest tooling), reusing the host-neutral
core from #922: a new `src/teams/` tree (TeamsJS lifecycle bootstrap, NAA
authentication over the existing Entra auth source, theme bridging) mounts
the same host-neutral chat page at a new `/office-addin/teams` route.

- Confirmed in `frontend_environment.rs`: the backend's CSP
  `frame-ancestors` directive gains a new `TEAMS_M365_FRAME_ANCESTORS` list
  (`teams.microsoft.com`, `*.teams.microsoft.com`, `*.microsoft365.com`,
  `*.office.com`, `*.cloud.microsoft`, plus two specific
  `outlook.office365.com`/`outlook-sdf.office365.com` origins not covered
  by the wildcards), appended to the existing Outlook origins whenever
  `integrations.ms_office.addin.enabled` is on. **Worth noting**: this is
  gated on the *same* existing Outlook add-in flag, not a separate
  Teams-specific toggle — so any deployment that already has the Outlook
  add-in enabled automatically permits framing from these Teams/Microsoft
  365 origins too, even if that deployment has no interest in exposing a
  Teams tab. This is a CSP-widening side effect of enabling the (already
  existing) Outlook integration flag, worth flagging to a security-
  conscious maintainer even though the added origins are all legitimate
  Microsoft-owned hosts.
- Confirmed via full read of `isTeamsNestedAppAuthSupported.ts` and
  `TeamsAuthProvider.tsx`: authentication correctly detects whether the
  Teams host actually installed the NAA (nested app auth) bridge
  (`window.nestedAppAuthBridge`) before attempting to build an MSAL auth
  source; if absent, it degrades to an explicit `UnsupportedAuthSource`
  rather than crashing or silently failing, with a diagnostic
  `console.warn` (itself wrapped so a failing diagnostic call can't take
  down the component tree) including the host's own `isNAAChannelRecommended()`
  read for troubleshooting. The auth source is built *below*
  `TeamsProvider` specifically because the NAA bridge only exists after
  the TeamsJS handshake completes — building it earlier would permanently
  freeze the client into "unsupported" mode.
- Not independently verified in detail, given scope: the `TeamsProvider.tsx`
  lifecycle/context bootstrap (132 lines), `TeamsThemeProvider.tsx`, the
  445-line `TeamsApp.test.tsx` coverage, the `ARCHITECTURE.md` documentation
  update (95-line diff, presumably documenting the Teams extensibility
  seam this PR uses), or the ESLint config changes (65 lines, presumably
  extending #922's core/host boundary rules to also forbid Teams-specific
  imports in the neutral core).

## Compatibility and configuration

No new user-facing configuration keys — the Teams tab activates via the
existing `integrations.ms_office.addin.enabled` flag plus the manifest
changes from #930 (currently local-dev-only tooling; a production Teams
manifest/deployment path is not part of this diff). As noted above, this
flag now also widens the backend's CSP `frame-ancestors` to include
Teams/Microsoft 365 origins, which deployments with strict CSP auditing
should be aware of.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the `frontend_environment.rs` CSP diff
(confirming the additive origin list and its gating flag) and the
`isTeamsNestedAppAuthSupported.ts`/`TeamsAuthProvider.tsx` new files

Proposed category: Features and enhancements. Early-stage/foundational —
