# PR #858: Show the user message when returning to a streaming chat

- PR: https://github.com/EratoLab/erato/pull/858
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a bug where reopening (or reloading into) a chat whose response was
still generating could fail to show the user's own message that triggered
that generation. Root cause, confirmed by reading
`handleUserMessageSaved.ts`'s full diff: the handler for the
`user_message_saved` SSE event looked for a matching optimistic ("temp")
user message already in the store to reconcile against the server-
confirmed one; when no match was found (e.g. because the page had
reloaded, or a `resumestream` replayed this event after the original
optimistic message was already gone), the **old code only logged a
warning and never inserted the server-confirmed message into the store at
all** — so the user's own message simply never appeared. The fix removes
that early-exit: the server-confirmed message is now always inserted
(`newUserMessages[finalUserMessage.id] = finalUserMessage`) regardless of
whether a temp message was found to reconcile against; the server-supplied
message id keeps a repeated/replayed delivery idempotent, and a later
merge step is stated to give the API-fetched copy precedence in case of
disagreement.

Also confirmed in the same diff, though logic-preserving rather than new:
the assistant-placeholder anchoring logic (deciding whether to keep an
existing assistant stream anchor, adjust its timestamp, or create a fresh
optimistic placeholder) is restructured into a single computed
`nextStreaming` value shared by both the reconciled and directly-inserted
paths, rather than being duplicated separately per branch as it was in
the code being replaced — reducing duplicate logic rather than changing
its behavior. The assistant's timestamp continues to be pinned to
`serverConfirmedMessage.created_at + 1ms` specifically so ordering (by
`createdAt`) can't be inverted by client/server clock skew.

A new backend integration test,
`test_get_chat_messages_returns_in_flight_user_message`, confirms (read
directly) that `GET /chats/{id}/messages` mid-generation already correctly
includes the in-flight turn's user message — establishing that the bug
was purely a frontend reconciliation gap, not a backend data-completeness
issue. Additional coverage: a new comprehensive unit test suite for
`handleUserMessageSaved` (reconciliation, direct insertion, idempotency,
background-stream handling), an integration test that starting a new chat
correctly marks the previous chat's cached messages stale, and an updated
E2E assertion that both sent messages remain visible during a resumed
stream.

## Compatibility and configuration

None. Pure frontend bug fix; no configuration or API changes. Behavior
change: a user's own message now reliably reappears when returning to
(or reloading into) a chat whose response is still streaming, instead of
sometimes being silently dropped from the UI.
