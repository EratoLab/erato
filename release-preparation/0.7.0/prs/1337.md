# PR #1337: Refuse a Word replace when a copy of the passage could take its place (ERMAIN-937)

- PR: https://github.com/EratoLab/erato/pull/1337
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Word selection editing

## Summary

Per the PR description: fixes ERMAIN-937, a correctness bug in the
paragraph resolver shared by v1 paragraph edits, Show in Word, and
selection Replace (introduced across #1334/#1336 earlier in this batch) —
**this is the exact `twinThenInsertAfter` wrong-target-write scenario that
PR #1336's own "Native gate" section disclosed as an unmet acceptance gate
("Hard gate not met: stays draft")**. Confirmed directly in
`wordParagraphResolver.ts`: the paragraph `WordParagraphAnchor` gains
`counts` (how often each narrower context window and each span paragraph's
text occurred at capture time) and `aboveId` (the ID of the paragraph
immediately above the span). Without paragraph IDs, a single resolver
match whose text has since become more common than at capture time now
refuses as `ambiguous` instead of silently writing into whichever copy
matched. With IDs, a moved ID is now caught by checking whether the
paragraph actually above it still matches the captured `aboveId` — closing
a gap where Word moving an ID onto a copy, amid a run of identical twin
paragraphs, previously fooled the existing context-above check. Per the
commit history, this took three iterations within the same PR branch: an
initial fix, a locale correction (addressing the user as "Sie" in German),
and a follow-up after CI's property-based tests found two further edge
cases (an inserted unrelated paragraph hiding an extra occurrence on the
ID path, and a copied *middle* span paragraph not being counted on the
text path).

## Compatibility and configuration

Bug fix, no config keys. Behaviorally: a selection Replace or paragraph
edit that previously could silently land on a copy of the intended
paragraph now refuses with "This passage now appears more than once, so
Erato can't tell which one you meant. Nothing was replaced." (localized
into de/es/fr/pl per the diff) — a user who previously got a (possibly
wrong) silent write will now sometimes see a refusal instead. No database
migration.
