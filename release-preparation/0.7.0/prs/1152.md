# PR #1152: Add a per-tool Ask decision, the effective state on the wire and bulk tool decisions

- PR: https://github.com/EratoLab/erato/pull/1152
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Stacked on #1150, largest PR in this MCP-approval cluster (#1146–#1152).
Adds a per-tool `Ask` decision (a user can force a specific tool to
always park for approval regardless of policy preset), widens the wire
shape to carry `policy`/`user_decision`/`effective` states separately,
and adds a batch decision-update endpoint. Given the scope, review
focused on the disclosed safety-critical fix. Confirmed by reading the
complete `effective_mcp_tool_state` function and its test suite in
`mcp_tool_approval.rs` in full:

- **The disclosed review-caught safety bug and its fix, confirmed
  exactly**: `effective_mcp_tool_state` matches in order —
  `Some(UserToolDecision::Denied) => Denied` unconditionally first, then
  `AlwaysAllow` only when `config.allow_always`, then `Ask` only when
  `config.enabled`, falling through to the raw policy verdict otherwise.
  A dedicated test case, `(&disabled, &auto, Some(Decision::Denied),
  State::Denied)`, annotated "A denial needs no policy at all," directly
  proves a stored denial produces `Denied` even when the entire approval
  gate is configured `enabled: false` — precisely the scenario the PR
  states the first draft of this refactor got wrong (a stored `Denied`
  row being read as "run without asking" when the approval
  gate/park-and-continue machinery was otherwise inert). This is the most
  safety-critical property in the whole PR and it is directly,
  non-vacuously pinned by a test.
- **Three-valued gate logic matches the described precedence exactly**:
  the full nine-case table in `user_decisions_layer_over_the_policy_verdict`
  covers every combination the PR's prose describes — a grant only
  counting while `allow_always` is on, an ask only parking while
  approvals are enabled, and an "inert" row (a decision whose gate is
  off) correctly falling back to the raw policy verdict rather than
  either the stored decision or a hardcoded default — every case
  confirmed matching its expected `McpToolEffectiveState`.
- Per the PR (not independently re-verified given the very large
  remaining scope): the migration `0046` widening the `decision` CHECK
  constraint from `always_allow | denied` to `always_allow | ask |
  denied`; the `gate_mcp_tool_call` rewrite returning a three-way `Run |
  Ask(request) | Refuse(reason)` (renamed from `mcp_tool_approval_request`),
  stated to now read the stored decision unconditionally before
  evaluating rather than only when the policy already asked *and*
  `allow_always` was set; the wire-shape split on `GET /me/mcp_servers/
  {id}/tools` carrying `policy`/`user_decision`/`effective`/
  `ask_available` as distinct fields, with the frontend stated to render
  only `effective` and never re-derive it client-side; the new batch
  endpoint `PUT /me/mcp-tool-approval-settings/batch` (whole-request
  validation — unknown server, unauthorized, duplicate entries,
  `always_allow` without `allow_always`, `ask` without approvals enabled
  — applied in one transaction, with `null` clearing a row); the
  disclosed fix adding the missing rego authorization check to the
  existing single-decision `POST` endpoint (previously missing it); the
  disclosed react-query cache-staleness fix (the roster now invalidates
  after an in-chat "Always allow" grant); the disclosed "Asks before
  running" badge keying on `effective` rather than `policy` (so the badge
  reflects what will actually happen, not just the server-side default);
  and a disclosed unrelated drift-inheritance fix (regenerating
  `component-registry.generated.ts` for exports `main` itself hadn't
  regenerated since #1102, needed only because CI's registry check
  fails without it — explicitly not this PR's own drift).

## Compatibility and configuration

New migration `0046` (widens a CHECK constraint additively — existing
`always_allow`/`denied` rows remain valid, `ask` is a new allowed value,
no behavior change for existing rows). New wire fields and a new batch
endpoint. The core safety property (a user's denial always wins,
regardless of approval-gate configuration state) is now directly
test-pinned, closing a gap the PR states a pre-merge review caught before
it shipped.

## Release note disposition

Proposed category: Features and enhancements, completing the per-tool
MCP approval control stack (#1146–#1152). Worth a mention: users can now
force a specific MCP tool to always ask for approval (not just
always-allow or never), and the Settings approval panel and composer
tool browser now show exactly what will happen for a tool (allow/ask/deny)
rather than just the server's raw policy, with the ability to set
decisions for multiple tools at once.
