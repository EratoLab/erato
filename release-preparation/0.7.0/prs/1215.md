# PR #1215: Add validated client submissions with bounded corrections

- PR: https://github.com/EratoLab/erato/pull/1215
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds an opt-in extension to the existing client-tool mechanism: a client
tool can be configured as a "submission," whose arguments are validated
against a JSON Schema both offline (at config load) and per-call, with a
bounded number of correction attempts, and whose successful result ends
the generation immediately rather than resuming the tool loop for
another inference round. Application-neutral infrastructure — the PR
explicitly states domain schemas, parsers, review UI, and execution stay
with each downstream consumer. Confirmed the core schema-compilation,
bounded-attempts, and native-strict-mode gating mechanisms directly:

- **Offline schema compilation rejects external references, confirmed
  exactly**: the new `client_tool_schema::compile` function requires
  `type: "object"` and builds the schema with a custom `NoExternalReferences`
  retriever whose `retrieve` always errors — meaning any `$ref` resolving
  outside the document itself fails compilation, while a local `$ref`
  (e.g. into the schema's own `$defs`) is confirmed accepted by a
  dedicated unit test. This matches "Compile and validate configured
  JSON Schema offline before client dispatch" and the module's own doc
  comment "No HTTP or file references" precisely.
- **Compilation and `max_attempts` bounds are enforced at config load,
  confirmed exactly**: `AppConfig`'s client-tool validation loop now
  panics if `submission.max_attempts` is outside `1..=10`, and separately
  panics if `client_tool_schema::compile` fails on the tool's
  `parameters` — both checks gated strictly behind `tool.submission`
  being `Some`, so an ordinary (non-submission) client tool's validation
  path is completely unchanged, matching "keep ordinary client tools
  unchanged" precisely.
- **Bounded corrections default to three attempts, confirmed exactly**:
  `ClientToolSubmissionConfig::default()` sets `max_attempts:
  default_submission_max_attempts()` which returns `3` — matching "Bound
  corrections to three attempts by default."
- **A successful or cancelled result ends generation without further
  tool-loop inference; an exhausted attempt budget also stops retrying,
  confirmed exactly**: `SubmissionPolicy::finish_after` returns `true` for
  `ClientToolOutcome::Result(_) | ClientToolOutcome::Cancelled { .. }`
  *or* when `attempt >= self.max_attempts` — directly substantiating both
  "a successful client result ends generation without another inference
  call" and the practical effect of the bounded-attempts limit (a client
  that keeps failing validation stops being asked to retry once the bound
  is reached, rather than looping forever).
- **Correction feedback never echoes the submitted artifact back,
  confirmed exactly, a detail not explicitly called out as its own PR
  bullet but consistent with its stated diagnostics design**: validation
  issue messages are built from `error.masked().to_string()` with an
  inline comment "Do not echo the proposed artifact into a correction
  response" — a privacy/data-minimization property of the correction
  loop worth noting alongside the disclosed "parser-owned JSON Pointer/
  code/message diagnostics" claim.
- **Native strict-argument support is a distinct, opt-in model
  capability, confirmed exactly**: `ModelCapabilities` gains
  `supports_strict_tool_calling: bool` (default `false`), documented as
  "Opt-in, independent of model name. Currently wired for OpenAI-
  compatible Chat Completions and Responses adapters. Other adapters use
  local validation unless native enforcement is required (then
  preparation fails)" — matching "Enable native strict arguments only for
  an explicitly capable model, a compatible schema and an adapter that
  forwards the setting... Current native support covers compatible Chat
  Completions/Responses endpoints; Gemini/Vertex and Ollama use local
  validation and feedback" precisely.
- **`auto`/`off`/`required` native-schema modes exist exactly as named,
  confirmed exactly**: `ClientToolNativeSchema` is a three-variant enum
  (`Auto` default, `Off`, `Required`) — matching "`auto`, `off` and
  `required` control fallback."
- Per the PR (not independently re-verified given remaining scope): the
  "reject parallel submissions and stop on timeout without retrying a
  potentially staged draft" claim (plausibly implemented in the
  337-line `message_streaming.rs` diff's route-level handling, not
  traced to its exact mechanism in this review); the `native_strict_for_submission`/
  `native_schema_compatible` functions' exact compatibility-determination
  logic beyond their names and the general capability-gating confirmed
  above; the cross-instance delivery of diagnostics (relevant to the
  background-task/delegation infrastructure this session has reviewed
  extensively elsewhere in this release, `background_tasks.rs`'s 21-line
  diff, not traced here); the full 359-line `client_tools.rs` diff beyond
  the `SubmissionPolicy`/`compile`-consuming sections read; the new
  276-line `client_submissions.rs` integration test file and the 57-line
  `config.rs` integration test additions; and the disclosed validation
  (1,243/1,243 backend tests with 4 skipped, 2,508/2,508 frontend tests
  with 11 skipped, documentation site build, and the disclosed
  integration-test scenario explicitly covering "server schema failure →
  client parser failure → acceptance with no further tool-loop
  inference" using a deterministic mock provider with no paid model
  calls).

## Compatibility and configuration

Additive and opt-in at every level: `ClientToolConfig.submission` is
`Option<ClientToolSubmissionConfig>` (absent by default, confirmed no
change to ordinary client-tool validation when absent);
`ModelCapabilities.supports_strict_tool_calling` defaults to `false` for
every model unless explicitly set; `ClientToolNativeSchema` defaults to
`Auto`, which per its own documentation only engages native enforcement
for "an explicitly capable model, a compatible schema and an adapter that
forwards the setting" — never silently rewriting a schema to fit. No
breaking change to any existing client-tool configuration.

## Release note disposition

Proposed category: Features and enhancements. This is infrastructure for
downstream consumers (the PR explicitly notes a separate, rebased
consumer branch exists but is out of scope here) rather than an
end-user-visible feature on its own — no domain schema or UI ships in
this PR. Worth a brief mention as a platform capability: client tools can
now be configured to validate structured arguments against a JSON
Schema (locally and, where supported, via the model provider's native
strict mode) with bounded correction attempts, finishing the turn
immediately on a successful submission rather than requiring another
inference round.
