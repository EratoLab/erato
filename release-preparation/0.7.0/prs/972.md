# PR #972: Align chat add menu with the dropdown theme-token channel

- PR: https://github.com/EratoLab/erato/pull/972
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Continues the theming-consistency sweep (#843–#856, #851–852): converts
the chat composer's "+" add menu — and the Outlook/Teams host rows
injected into it — onto the same shared `DropdownMenu` theme-token
classes/tokens the kebab menus already use, so a customer theme that
retunes dropdown styling now reaches this menu identically. Confirmed by
reading `ChatInputAddMenu.tsx` in full:

- Row styling switches from a mix of hardcoded utilities
  (`rounded-[var(--theme-radius-control)] px-3 py-2 ... hover:bg-theme-bg-hover`,
  no focus state) to the shared `dropdown-item-geometry` + `theme-transition`
  classes with the canonical `fg-secondary`→`fg-primary` hover/focus color
  recipe, plus a previously-missing focus ring
  (`focus:ring-1 focus:ring-inset focus:ring-theme-border-dropdown`); the
  checkmark icon on a selected tool row moves from the accent color
  (`fg-accent`) to the primary text color (`fg-primary`), matching the
  convention other selection checks use elsewhere.
- Section headers now derive their horizontal padding from
  `--theme-spacing-dropdown-padding-x` instead of a hardcoded `px-3`.
- **Confirmed the described close-timing behavior precisely, including
  its stated rationale**: selecting an ordinary action row now delays the
  menu's close by 100ms (matching `DropdownMenu`'s own item-click delay,
  so the selected state stays visible for a beat), via a
  `closeAfterSelect` timer. Host-injected content (`extraContent`, i.e.
  the Outlook/Teams rows) instead closes **immediately** on selection via
  a separate `closeNow` path — confirmed the code's own comment states
  this is because a host typically opens a dialog on selection, and
  `AnchoredPopover` returns focus to the trigger on close; a delayed close
  overlapping with the host dialog's own focus grab would steal focus
  away from an already-open modal, so immediate closure avoids that race
  (the same convention already used by `DropdownMenu`'s own confirm
  dialogs). Two supporting correctness details confirmed: opening the
  menu (`handleOpenChange`) cancels any leftover pending-close timer from
  a prior session, so a stale timer can't immediately close a freshly
  reopened menu; and an action row's click handler checks for an
  already-pending close timer and no-ops if one exists, so a rapid
  re-activation during the 100ms linger window can't re-trigger the
  selected action a second time.
- `ModelSelector`/`FacetSelector` drop their own hand-rolled chevron SVG
  markup in favor of the shared `ChevronDownIcon` component (not
  independently re-verified, small mechanical change per the diff stat).

## Compatibility and configuration

None new. Pure frontend visual/interaction consistency fix; no
configuration or API changes. Visual/behavioral delta: the add menu's row
styling now follows the same theme tokens as other dropdown menus
(matters for a custom theme retuning dropdown appearance), rows gain a
visible focus ring they previously lacked, and selecting a regular action
row now has a brief visible-selection delay before closing (100ms) while
host-injected rows (Teams/Outlook) still close immediately as before.
