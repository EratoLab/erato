# PR #866: Serve shared chats via a dedicated active-thread-only messages route

- PR: https://github.com/EratoLab/erato/pull/866
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a real privacy bug: shared chats reused the owner's
`GET /chats/{chatId}/messages` endpoint, which returns **every** message
branch (including edits and regenerations superseded by later ones) to
anyone holding a valid share link — so a shared-chat viewer could see
stale/discarded branches the owner never intended to expose (reported as
"Geteilte Chats zeigen alle Bearbeitungen und Regenerierungen"). Confirmed
by reading the code:

- New `GET /share-links/{share_link_id}/messages` route
  (`share_link_messages`), which resolves the share link to its chat (a
  plain lookup with no validity checks in Rust) and authorizes via a new
  `Action::SharedRead` (confirmed calling `authorize!(policy, subject,
  Chat, SharedRead)` in the new `get_shared_chat_messages` model
  function).
- **Server-side, non-bypassable filtering**: `get_shared_chat_messages`
  calls a newly-extracted private `fetch_chat_messages(..., active_thread_only:
  bool, ...)` with `active_thread_only = true`, which adds a DB-level
  `messages::Column::IsMessageInActiveThread.eq(true)` filter to both the
  page query and the count query — confirmed this is a real database
  predicate, not a frontend or response-shaping filter, so it cannot be
  bypassed by any client behavior. The existing owner route
  (`get_chat_messages`, unchanged authorization via `Action::Read`) calls
  the same helper with `active_thread_only = false`, preserving its
  existing all-branches behavior for the owner.
- New `Action::SharedRead` (`shared_read`) is confirmed, by reading
  `backend.rego`'s diff, to be a genuinely separate OPA policy action from
  `read`: the rule that previously granted a share-link holder the
  **generic** `action_read` on the chat resource (via
  `can_read_shared_chat`) is changed in this diff to grant `action_shared_read`
  instead — meaning a share-link holder directly hitting the *old*
  `GET /chats/{chatId}/messages` route would now be denied there too
  (that route still authorizes via `Action::Read` only), independently
  closing off the bypass at the policy layer, not just by adding a new
  preferred route. New Rego tests cover: allow with an active link; deny
  without a link, with a disabled link, with sharing disabled, or with an
  archived chat; and confirm `shared_read` grants neither `update` nor
  `submit_message`.
- **One point flagged for maintainer attention, not fully resolved by
  this review**: the PR description states "Removing the generic
  `Chat::Read` grant for share links lands in ERMAIN-486 (#878), stacked
  on this" — implying a further, separate `Chat::Read` grant via share
  link still exists after this PR and is removed only in a follow-up.
  However, direct inspection of `backend.rego`'s `allow` rules found only
  one `resource_kind_chat`-scoped grant conditioned on
  `can_read_shared_chat`, and this PR's diff already changes that single
  rule from `action_read` to `action_shared_read`. No other
  `Chat`/`action_read` grant conditioned on share-link state was found in
  this file. It's possible the remaining generic grant #878 addresses
  lives in a Rust-level authorization path not expressed in this Rego
  policy file (not located in this review), or the description's framing
  of what #878 specifically removes doesn't map cleanly onto what was
  visible in this diff — worth the maintainer double-checking #878's own
  diff against this note rather than assuming this PR alone fully closes
  the described gap.
- Backend also extracts a shared `assemble_chat_messages_response` helper
  (DTO assembly: feedback, files, capabilities, image-URL regeneration,
  stats) reused by both the owner and shared routes, confirmed via the
  diff to avoid duplicating that logic — not read in full itself.
- Frontend: `SharedChatPage` now uses a generated `useShareLinkMessages`
  hook keyed by `shareId` against the new route, with no client-side
  filtering (renders the response verbatim) — confirmed the frontend no
  longer needs to filter, since the backend now guarantees active-thread-
  only content.
- A new regression E2E spec asserts, at the API level, that the
  recipient's response from the new route contains zero
  `is_message_in_active_thread: false` entries and that its role order
  matches the owner's own active-thread view exactly.

Per the PR, freezing/snapshotting a share at the time it was created
(rather than the shared view auto-updating live as the owner continues
editing) is explicitly out of scope here.

## Compatibility and configuration

None new. No configuration keys; this is a policy/routing fix affecting
only shared-chat access. Behavior change: a shared chat link now shows
only the active thread (matching what the owner currently sees as the
"real" conversation), never a discarded edit/regeneration branch that a
viewer previously could see.
