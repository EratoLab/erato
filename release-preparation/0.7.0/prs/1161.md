# PR #1161: Hand a message renderer the MCP notices and the action-facet context

- PR: https://github.com/EratoLab/erato/pull/1161
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

First of a stacked series (ERMAIN-810) extending #1145's fix — a
component-kit `ChatMessageRenderer` override replaces the *whole*
message, so it silently drops any host chrome it doesn't rebuild. This
PR identifies and fixes two specific pieces being lost: the MCP notices
(disabled servers/tools, needs-auth) and the action-facet selection quote
on a user message. Confirmed by reading the complete new `McpNotices.tsx`
and the relevant `ChatMessage.tsx` diff in full:

- **Needing-auth-minus-switched-off exclusion moved verbatim into the new
  shared component, confirmed exactly**: `McpNotices.tsx`'s filter logic
  (`serversNeedingAuth = (message.mcp_servers_needing_auth ?? []).filter(
  serverId => !serversDisabledByUser.includes(serverId))`) and its
  accompanying design-rationale comments are byte-identical to what was
  previously inlined in `ChatMessage.tsx` — confirmed the old inline
  version (three separate `length > 0`-guarded blocks plus the filter
  logic and its full comment block) is removed entirely and replaced by
  a single `<McpNotices message={message} showConnect=
  {!controlsContext.isSharedDialog} />` call, with `showConnect`'s wiring
  preserved unchanged.
- **`McpNotices`/`ActionFacetContext` genuinely added to the host-instance
  channel, confirmed exactly**: `ChatMessageHostComponents` gains
  `McpNotices: typeof McpNotices` and `ActionFacetContext: typeof
  ActionFacetContext`, and `CHAT_MESSAGE_HOST_COMPONENTS` populates both
  with the host's real component references — matching the PR's stated
  design that this is "the only identity-safe channel," since a kit
  importing these from the shared library directly would get a second
  copy of the module (and therefore a second, disconnected React context
  instance for `ActionFacetContext`).
- **Behavior-preserving for the host, confirmed by construction**: since
  each notice sub-component already returns `null` for an empty list
  (confirmed for `McpNeedsAuthNotice` specifically in this session's
  earlier #1018 review), removing the outer `length > 0` guards and
  always rendering `<McpNotices>` produces byte-identical output for the
  host's own (non-kit) rendering — consistent with the PR's claim that
  this is a pure refactor for the host, not a behavior change.
- Per the PR (not independently re-verified): the `ChatMessage.test.tsx`
  regression net asserting the host-components bag carries the actual
  host component references (not a stand-in) by identity — the one
  property a call site couldn't otherwise distinguish; and the disclosed
  compatibility note for kit authors that `hostComponents?.McpNotices`/
  `?.ActionFacetContext` must be optionally-chained rather than
  destructured, since a kit built against this host but loaded by an
  older one would receive `undefined` for both new fields.

## Compatibility and configuration

None breaking, and no behavior change for the host's own rendering
(confirmed via the null-returning-sub-component equivalence above). For
component-kit consumers: a `ChatMessageRenderer` override built against
this host can now render the MCP notices and action-facet context by
consuming the new `hostComponents.McpNotices`/`.ActionFacetContext`
props, closing a silent feature-loss gap analogous to the one #1145
fixed for the chat history row; an override built against an older host
continues to silently lack these two pieces until rebuilt (same
degradation shape as before this PR, not made worse).
