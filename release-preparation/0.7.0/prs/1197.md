# PR #1197: Let a client ask for the reaction a delivered task result never got (ERMAIN-781-B)

- PR: https://github.com/EratoLab/erato/pull/1197
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Top of the "Async re-entry" stack, stacking on #1196 (ERMAIN-781-A,
reviewed above). Adds `POST /me/chats/{chat_id}/react`, a client-facing
route that explicitly runs the reaction turn a `delivered` task result
never got (complementing #1196's automatic 5-minute sweep). The PR
description is exceptionally detailed about its own design decisions;
this review verified essentially every one of them directly against the
code, since each is a small, precisely statable, independently checkable
claim:

- **Dedicated `RefuseParked` lease helper, confirmed exactly**: a new
  `acquire_task_result_generation_lease` function (distinct from the
  existing `acquire_user_generation_lease`) calls `try_start_task(...,
  Takeover::RefuseParked, ...)`, with a doc comment stating the identical
  reasoning as the PR body: "a person parked on an approval card is
  mid-decision, and a reaction turn — whose content the server wrote — is
  not a good enough reason to move them off it... the two stay separate
  helpers rather than one with a `takeover` argument so the decision reads
  at the call site." Matches "`RefuseParked`, in a lease helper of its
  own" precisely.
- **Precondition order: `already_reacted` before `tip_moved`, confirmed
  exactly, word-for-word reasoning**: `task_result_still_reactable`'s step
  10 (`already_reacted`) runs strictly before step 11 (`tip_moved`), with
  a doc comment stating verbatim "Once a reaction has run the assistant
  row IS the tip, so both would fire — and the two mean opposite things to
  a client... The reverse order silently degrades the UI to the wrong one
  of the two" — matching the PR's "Precondition order is part of the
  contract" section exactly.
- **A failed tip read is a 500, never `tip_moved`, confirmed exactly**:
  `get_active_thread_tip`'s `Err` branch returns
  `StatusCode::INTERNAL_SERVER_ERROR` directly, before the tip is ever
  compared against `task_result_message_id` — so a database hiccup cannot
  produce a false `tip_moved` — matching "An `Err` from
  `get_active_thread_tip` is a **500**, never `tip_moved`: `None` means
  'no anchor', `Err` means 'we do not know'" precisely.
- **`reacted` accepted at the "was this delivered?" check, refused one
  step later, confirmed exactly**: step 9's `matches!` filter accepts
  both `ResultDeliveryState::Delivered` and `::Reacted`, with step 10
  separately refusing `Reacted` (or a `Delivered` row that already names a
  `reaction_message_id`) as `already_reacted` — matching "`reacted` is
  accepted by the 'was this delivered?' check and refused by the next
  one; rejecting it earlier would report `not_delivered` for a row that
  plainly was" exactly.
- **No `scheduling` check, confirmed by absence**: `task_result_still_reactable`
  has no reference to `scheduling`/`silent` anywhere — matching "No
  `scheduling` check... `/react` is a request, not a re-application of the
  task author's policy," and leaving the PR's own disclosed "Open question
  1" (whether `/react` should respect a `silent` scheduling choice)
  genuinely unresolved pending an owner ruling, as stated.
- **404 everywhere, never 403, confirmed exactly, including the
  authorization choice**: `react_not_found()` is a single shared function
  returning a generic `404 "Not found"` reused for the disabled-feature
  gate, an unknown/foreign chat, and an inaccessible row; the route
  authorizes via `Action::SubmitMessage` directly (not a read-access
  helper) with a comment stating "a 500 here would tell a prober the chat
  exists" — matching "The route authorizes `SubmitMessage` itself rather
  than inheriting a read helper's gate... a 500 would tell a prober the
  chat exists. The ERMAIN-485 class" exactly.
- **`expect_claim_token = None` on the `delivered -> reacted` write,
  confirmed exactly, with the precise stated fencing substitute**: the new
  `mark_delivery_reacted` passes `None` for `expect_claim_token` to
  `set_delivery_state`, with a doc comment explaining this is "the first
  write in `task_delivery.rs` that passes `None`" because "the delivering
  process took the claim, and that claim is finished by the time a client
  asks to react" — fenced instead on `state = 'delivered'` plus the
  delivery's own id (confirmed by this session's own prior review of
  #1196: `set_delivery_state_in` pins `delivery_id` unconditionally in
  every write) — matching the PR's "Decisions worth stopping on" item
  exactly, including the stated race it closes (a branch requeue minting
  a new `delivery_id` cannot be stamped back over).
- **`mark_delivery_reacted` added beside the existing state setters,
  confirmed exactly**: it's a new, narrow `pub(crate)` function in
  `task_delivery.rs` rather than a widened `set_delivery_state` visibility
  — matching "`mark_delivery_reacted` is added beside the state setters
  rather than widening `set_delivery_state`... the ladder's correctness
  is that only that module decides which transitions exist" precisely.
- **`selected_facets_of_tip` becomes `pub(crate)`, confirmed exactly**:
  its visibility changes from private to `pub(crate)` with a doc comment
  stating the reaction route reuses it rather than re-implementing "which
  facets does a reaction speak with" — matching "Two seams in 780's
  module... `selected_facets_of_tip` becomes `pub(crate)`" exactly.
- **`GenerationRunningError.initiator` hardcoded `"user"` even on the
  task-result lease path, confirmed exactly, candidly disclosed as a
  known gap**: `acquire_task_result_generation_lease`'s error path sets
  `initiator: "user".to_string()` with a comment stating directly "the
  chats row records no initiator, so this handler cannot tell a
  delivery's lease from a person's... belongs to the delivery change, not
  here" — matching the PR's "Open question 4" disclosure exactly, and
  confirming it is a real, acknowledged limitation rather than an
  oversight.
- Per the PR (not independently re-verified given remaining scope): the
  `NothingToReactError`/`GenerationRunningError` wire shapes beyond the
  core logic read (confirmed the four `REACT_REASON_*` constants exist
  and are used exactly as the precondition function's control flow
  dictates, but the full OpenAPI schema generation and the
  `frontend/src/lib/generated/...` regenerated client (`fetchReactToTaskResultSse`/
  `useReactToTaskResultSse`) were not independently inspected); the
  disclosed "No `?` between the lease and the spawn" claim about
  `with_generation_task_lifecycle` releasing cleanly on an abandon path
  (not traced); the ten new `#[sqlx::test]`s in `api/delegation.rs` (764
  lines, including the two disclosed mutation-verified tests and the two
  tests disclosed as staged differently from the original plan); the
  `779-B` SSE-client JSON-409-parsing note (a note to a downstream
  consumer, not a code claim about this PR); and the disclosed
  verification (1204/1204 `cargo nextest run --retries 2`, up from 1194
  on #1196's tip; clean clippy; clean `gen-openapi`/`gen-config-reference
  --check`; config-reference coverage unchanged at 98 undocumented).

## Compatibility and configuration

Additive. New route `POST /me/chats/{chat_id}/react`, entirely behind
`delegation.tasks.enabled` (confirmed: the route's first precondition
checks the gate and returns the generic 404 if off, consistent with "with
the gate off, this is always the real compare-and-set" — meaning the
route simply doesn't exist from a caller's perspective when the feature
is off). Regenerates `openapi.json` and the frontend generated API client
only — no frontend source, config leaf, or migration changes, confirmed
consistent with the changed-files list.

## Release note disposition

Proposed category: Features and enhancements. This PR completes the
"Async re-entry" stack's stated goal: "no result is ever silently lost."
Combined with #1188-#1196, the cumulative release-note-worthy behavior is
that the model can dispatch a task without waiting (`run_mode = "async"`,
off by default), its result reliably reaches the conversation it came
from even across a crash or rolling deploy, and — new in this PR — a
client has an explicit route to trigger the reaction turn for a result
that arrived without one. As the PR itself notes, the remaining gap
(learning about a recovered or deliverable result without a manual
reload — sidebar/live-arrival behavior) is scoped to a separate,
not-yet-reviewed PR (782/ERMAIN-779-B et al.).
