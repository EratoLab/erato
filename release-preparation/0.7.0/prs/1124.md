## Summary

Despite the title, this PR bundles two distinct things:

**1. Dev-only profiling infrastructure** (the bulk of the diff): a new
opt-in `profiling-dial9` Cargo feature integrating the Dial9 profiler
(Tokio runtime events, application spans, process resource usage, sampled
allocations, and Linux CPU samples), run via `just run_dial9` from a
separate `target/dial9` build directory (documented at length in
`backend/README.md`). Only spans explicitly marked `dial9 = true` are
recorded (HTTP method/path without query strings, diagnostic stages,
synchronous policy evaluation and its queries, translation compilation,
frontend path/file operations), independent of `RUST_LOG`. Also adds a
`load-tests/` directory under `e2e-tests/` (k6-style scripts:
`direct.mjs`, `sse.mjs`, `dex-auth.mjs`, a `run.py` harness) for local
concurrency/load testing against Dex auth.

**2. A real production concurrency fix in the policy engine**, apparently
discovered via this same profiling work: `backend/erato/src/policy/engine.rs`
previously ran OPA policy evaluation (`evaluate_policy_snapshot`)
synchronously inline on the calling async task. It's now moved onto
Tokio's blocking-task pool (`spawn_blocking`) and gated by a new
process-wide semaphore capping concurrent evaluations at
`MAX_CONCURRENT_POLICY_EVALUATIONS = 4` (hardcoded, not configurable) —
per the code comment, this bounds "CPU-heavy evaluations across all
policy engines, including reloads." Callers queue for a permit before
checking snapshot freshness or acquiring the engine's read lock, so a
queued caller doesn't hold a stale read lock while waiting. New
`backend/erato/src/latency.rs` (99 lines) adds lightweight stage-timing
instrumentation (`latency::stage`, `StageTimer`, `sync_span`) used
throughout the policy engine, message streaming, and background-task code
to measure lock-wait/hold and evaluation durations — this appears
independent of the dial9 profiling feature (regular tracing spans) and
usable in production builds.

## Compatibility and configuration

The `profiling-dial9` feature and load-test scripts are entirely
development/testing tooling with no effect on normal production builds
(opt-in Cargo feature, not enabled by default). The policy-evaluation
concurrency change, however, **is a production behavior change**: policy
authorization checks now execute off the async runtime's worker threads
and are capped at 4 concurrent evaluations process-wide (not configurable
via any exposed setting found in this diff). Under very high concurrent
authorization load, requests could now queue for an evaluation slot where
they previously ran inline — this is presumably a deliberate fix for CPU
contention/runtime-thread starvation under load (the underlying reason for
introducing profiling in the first place), but the specific concurrency
cap (4) and its non-configurability are worth the maintainer's explicit
confirmation before release, since it changes a load-bearing hot path for
every authorized request.
