# PR #898: Enable cross-replica sharing of generation state

- PR: https://github.com/EratoLab/erato/pull/898
- Status: pending
- Category: Stability improvements
- Theme: Multi-replica / cross-replica generation state

## Summary

Adds a Postgres-backed shared registry so a chat's in-progress generation,
started on one backend replica ("pod"), can be observed/interacted with by
a different replica that later handles a request for the same chat (e.g.
a client reconnecting an SSE stream, or aborting/submitting a client-tool
result from a different connection). Previously, generation state
(`StreamingTask` and friends, per `message_streaming.rs`) appears to have
lived only in the memory of the pod that started it, so requests for that
chat's live state landing on a different replica behind a load balancer
would not see it.

Three new `UNLOGGED` (ephemeral, not WAL-replicated — intentionally
discarded on a database restart) Postgres tables are added via migration
`0033_add_shared_generation_streaming_state`:
`temp_chat_generations` (one row per active generation: `chat_id` unique,
`owner_pod`, `state`, `heartbeat_at`, `ended_at`),
`temp_chat_generation_events` (an append-only event log per generation,
JSONB payloads), and `temp_chat_generation_commands` (an inbox for
cross-replica commands like abort or client-tool-result, with
`consumed_at` marking processed commands). `backend/erato/src/services/background_tasks.rs`
(348-line diff) adds `get_shared_generation`, `get_shared_events`,
`enqueue_abort`, `enqueue_client_tool_result`, plus a periodic heartbeat
updater and a "reaper" that clears generations whose `heartbeat_at` has
gone stale (the owning pod died or lost connectivity) beyond a configured
interval, reconciling the chat's lease. `backend/erato/src/server/api/v1beta/message_streaming.rs`
gets a substantial (241-line) diff wiring this shared state into the
streaming/generation flow. New E2E infrastructure
(`e2e-tests/tests/multi-replica.setup.ts`,
`e2e-tests/tests/shared-streaming.multi-replica.spec.ts`) and a new local
k3d dev scenario (`infrastructure/k3d/erato-local/config/erato.scenario-multi-replica.toml`)
were added to test this against multiple backend replicas.

## Compatibility and configuration

New database migration adds three `UNLOGGED` tables — safe, additive, no
backfill; these tables hold only ephemeral runtime coordination state, not
durable application data (explicitly documented in the migration's own
comment: "a database restart discards them and the application reaper
reconciles the corresponding chat lease"). No new top-level configuration
keys were confirmed in this diff (not fully verified — the periodic
heartbeat/reap interval and staleness threshold may be configurable but
this was not located in the reviewed portion of the diff). This is
primarily a reliability/scaling improvement for deployments running
multiple backend replicas behind a load balancer; single-replica
deployments should see no behavior change beyond the added (empty,
low-traffic) tables.
