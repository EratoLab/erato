# PR #941: feat(frontend): client-side PDF preview (ERMAIN-566)

- PR: https://github.com/EratoLab/erato/pull/941
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes PDF preview being completely broken inside sandboxed iframe hosts
(the Teams personal tab from #931, and potentially browser-OWA's add-in
frame) — per the [whatwg/html#6946](https://github.com/whatwg/html/pull/6946)
spec change, a sandboxed frame is forbidden from using the browser's
native PDF viewer, so `FilePreviewContent`'s previous plain
`<iframe src={blobUrl}>` PDF branch could only render Chrome's "content is
blocked" placeholder there. DOCX/PPTX/XLSX previews were already
client-side WASM and unaffected; PDF was the one format still delegating
to the browser. Confirmed by reading the core new files:

- New `PdfPreview.tsx` (375 lines, not read in full) renders through
  EmbedPDF (PDFium-in-WebAssembly, MIT-licensed), lazy-loaded only at the
  preview boundary. Because it hangs off the shared `FilePreviewContent`
  component, both the Outlook add-in and the Teams tab get this fix
  automatically through the packed frontend library, with no add-in-side
  code required, per the PR (consistent with the general shared-library
  pattern already established in this codebase, e.g. #825/#826).
- **Confirmed, via full read of the new `pdfEngine.ts`, all three of the
  PR's specific technical claims precisely**:
  1. The PDFium wasm binary's URL is explicitly converted to an absolute
     URL (`new URL(pdfiumWasmUrl, document.baseURI).href`) rather than
     left root-relative, because the engine's worker is spawned from a
     `blob:` URL which has no document base to resolve a relative path
     against — the code comment states this exact failure mode
     ("Failed to parse URL") and a companion unit test locks in that the
     URL is always same-origin and absolute.
  2. `fontFallback: null` disables EmbedPDF's default CDN font-fallback
     behavior (which would otherwise fetch ~150MB of font packages from
     `cdn.jsdelivr.net`, unreachable from an air-gapped/on-prem
     deployment) — PDFium substitutes its own built-in faces instead when
     a document doesn't embed its own fonts.
  3. `encoderPoolSize: 0` disables an extra worker pool EmbedPDF would
     otherwise spawn via a bundler-resolved `new Worker(new URL(...))`
     call — the one asset-resolution path in this stack that isn't
     inlined and would have to separately survive both the library build
     and the add-in's re-bundling step; the PR states this was verified
     absent from the actual built chunk.
  4. A single shared engine instance (module-level singleton, built once
     per session) is used rather than one per preview, since EmbedPDF
     never revokes its own object URLs (each open would otherwise strand
     ~0.7MB permanently) and, under the library build where the binary
     travels as a base64 data URI, a fresh engine per open would re-decode
     and recompile a 6MB module every time.
- The PDFium binary itself ships as an inlined `data:` URI inside the
  lazily-loaded chunk (Vite library mode's asset-inlining, the same
  mechanism already used for the existing DOCX/XLSX WASM previews per the
  PR), so there is no separate asset path for a consuming add-in or Teams
  tab bundle to resolve at all.
- `FilePreviewModal` gains an optional `notPreviewableReason` prop so a
  size-refusal or failed-download case (from the Teams picker's file
  attachment flow, #940) can show its own specific message instead of the
  generic, previously-incorrect "Preview is not available for this file
  type."
- The PR documents (not independently re-verified, since it requires a
  running browser) that it built and traced the actual consumed artifact:
  the PDF-preview chunk is dynamically imported (so its 7.1MB cost is
  paid only when a PDF is actually opened, keeping the library entry at
  174kB), confirmed via a real headless-Chromium Playwright run against a
  10-page PDF to render with zero external network requests and correct
  page-nav/zoom/rotate behavior.
- Explicitly not covered per the PR: live validation in browser-OWA's
  sandboxed add-in frame (this fix should address it, but wasn't tested
  live there) and the desktop WebView2 handoff; new UI strings are left
  untranslated in de/es/fr/pl, matching an existing precedent from the
  #939/#940 branch.

## Compatibility and configuration

None. Pure frontend bug fix; no configuration or API changes. Adds new
npm dependencies (`@embedpdf/*` packages, confirmed via the large
`pnpm-lock.yaml` diffs in both `frontend` and `office-addin`) under an
MIT license, stated by the PR to fit the project's license policy — not
independently re-verified against that policy's specific criteria.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: PDF file previews now
render using a fully client-side viewer instead of the browser's native
PDF viewer — fixing PDF preview being completely broken inside the Teams
personal tab (and any other sandboxed host frame), and working correctly
in fully offline/air-gapped deployments without depending on any external
CDN.
