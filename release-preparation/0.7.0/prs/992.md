# PR #992: Delegated chat lifecycle: archive cascade, age reaping, orphan cleanup, in-flight guard (ERMAIN-627)

- PR: https://github.com/EratoLab/erato/pull/992
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Closes a real resource-leak in the delegation feature (#978–#987):
delegated-run chats are hidden from every listing (#982), so no user ever
archives one, so the existing `CleanupWorker` — which only ever looks at
`archived_at IS NOT NULL` — never reaches them, and they accumulate
forever. Given this PR explicitly widens a path that *hard-deletes user
data*, and includes several subtle SQL correctness details, review
verified the most consequential mechanisms directly against the code.

- **`COALESCE(..., FALSE)` NULL-handling bug avoided, confirmed
  precisely**: both `chat_generation_is_running` and the shared
  `generation_unfinished_condition` predicate wrap their `generation_state`
  comparison in `COALESCE(..., FALSE)`. Confirmed this matters exactly as
  the PR states: without it, a chat with no `generation_state` at all (the
  overwhelming majority of chats) would evaluate the underlying boolean
  expression to SQL `NULL` rather than `false`, and `NOT (NULL)` is itself
  `NULL` — which a `WHERE` clause treats as not-matching, silently
  excluding those rows from *both* the archive cascade and the age-based
  reaper rather than correctly including them as "safe to touch."
- **Archive cascade, confirmed via full read of
  `archive_delegated_descendants`**: a single `WITH RECURSIVE ... UPDATE`
  statement walks `origin_chat_id` edges from the archived parent.
  Confirmed it uses `UNION` (not `UNION ALL`) specifically so a corrupted
  cyclic provenance chain can't recurse indefinitely (`UNION`'s
  deduplication naturally terminates the walk once no new distinct ids
  appear). Confirmed the query is scoped to `owner_user_id = $2` on every
  recursive step — a defense against a *future* cross-user provenance kind
  reaching another user's chats, even though today's delegation design
  guarantees child owner == origin owner. Confirmed three distinct skip
  conditions correctly exclude a chat from being swept into the cascade:
  an unfinished generation (`running` with a fresh heartbeat, **or**
  `awaiting_approval` — the parked-approval state is deliberately included
  here, since #918/#981's `reject_if_archived` would otherwise 409 the
  user's own pending approval decision and strand the run permanently);
  and a race-condition guard for a chat with `generation_state IS NULL`
  created within the staleness window (covering the narrow gap between
  dispatch creating the child chat and it actually claiming its
  generation lease). Skipping a chat also correctly stops the recursive
  walk there, so a live child's own descendants remain reachable rather
  than being silently orphaned from cleanup forever.
- **A genuinely disclosed and confirmed security-relevant bug fix**,
  unrelated to the archive/reaping work itself: in the
  `previous_message_id`-resolution branch of `message_submit_sse`, the
  tuple value later used as the "is this chat a delegated run" flag
  (feeding #980/#981's depth-1 no-nested-delegation check) was hardcoded
  `false` rather than actually computed — confirmed via the diff this is
  replaced with a real `crate::models::chat::chat_is_delegated_run(&chat)`
  call. This means mention validation previously skipped the "no
  delegation inside a delegated run" rule specifically on this one submit
  code path, a real (if narrow) gap in the depth-1 guarantee #981 was
  built around.
- A new in-flight write guard (`accept_user_write_into_delegated_run`,
  confirmed called on both `message_submit_sse` resolution branches, plus
  edit and regenerate) rejects a user write into a *live* delegated run
  with `409`, mirroring the existing `reject_if_archived` pattern — the
  PR states this checks both the in-memory task map (this replica's own
  knowledge) and the chat's generation lease (the cross-replica source of
  truth), since only the lease is valid when the live generation is
  running on a different backend replica. It is explicitly *not* applied
  to `continue_message` (the tool-approval continuation), which resumes
  the parked generation rather than starting a competing second one.
- New age-based reaping (`assistants.delegation.auto_archive_after_days`,
  default 7, `0` meaning never) independent of whether the parent chat was
  ever archived, running on the existing 5-minute cleanup cron. Per the
  PR, **pinned runs, adopted runs (a new `adopted_at` provenance field,
  stamped the first time a user writes into a finished delegated run,
  confirmed to exist as a new field on `ChatProvenance`), and runs with an
  active share link are all deliberately exempt** from this automatic
  reaper specifically because the product has no unarchive path — the PR
  frames unconditional auto-archiving as irreversible deletion-on-a-delay
  with no user action involved, and treats these three signals as the
  available "the user actually cares about this one" indicators. These
  exemptions apply only to the *automatic* reaper, not to the cascade
  (where a human explicitly archived the parent chat).
- The PR states a dedicated test,
  `test_delegated_run_retention_blast_radius`, runs both cleanup passes
  over a fixture set covering ordinary chats, shared chats, another
  user's chats/delegated runs, pinned/adopted/running/parked delegated
  runs, and asserts exactly the intended deletion set (one genuinely-old
  archived chat) with no message-row orphaning and share links left
  intact on survivors — not independently re-run, but the described
  coverage directly targets the blast-radius concern this PR itself
  raises.

## Compatibility and configuration

New, optional config field, non-destructive default:
```toml
[assistants.delegation]
auto_archive_after_days = 7  # default; 0 = never auto-archive
```
Behavior change for any deployment with delegation enabled: archiving a
chat now cascades to archive its delegated-run descendants (skipping any
still actively running or awaiting an approval decision), and a delegated
run left quiet for the configured number of days is auto-archived
independent of its parent — both feeding into the existing archived-chat
cleanup/deletion cycle. A live delegated run now rejects a concurrent user
write with `409` rather than racing a second generation against it.

the blast-radius test).

## Release note disposition

Proposed category: Bug fixes, part of the combined delegation feature
entry (#978–#992). Worth a specific mention if the delegation feature
ships enabled anywhere: delegated-run chats are now properly cleaned up
(archived alongside their originating chat, or automatically after a
configurable idle period) instead of accumulating indefinitely, and a
live delegated run can no longer be concurrently written into from two
places at once.
