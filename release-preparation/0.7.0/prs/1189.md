# PR #1189: Carry a delegated task's result back into the chat that started it (ERMAIN-777)

- PR: https://github.com/EratoLab/erato/pull/1189
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 4 "Async re-entry", position 2 of 5, based on #1188 (ERMAIN-776,
reviewed above). Defines the wire shape, storage model, and prompt-
composition rule for a delivered async task result — explicitly disclosed
as shipping entirely dark ("Nothing writes any of it yet — the writer is
ERMAIN-780"). The PR's central engineering concern is a prompt-injection
defense: a delegated child's answer is untrusted text, and the result
must be presented to the model with facts (status/reason/ids) and safety
framing that the operator's own customizable template cannot remove or
corrupt. Confirmed this defense precisely, along with the "history, not
an instruction" composition-walk claims, by reading the complete
`render_task_result` implementation, its four dedicated unit tests, and
the relevant `prompt_composition`/`message.rs` diffs:

- **`result_template` validation, confirmed exactly**: `DelegationConfig::validate`
  rejects an empty template and separately rejects one missing the literal
  `{{result}}` placeholder, with a code comment stating exactly the
  failure mode this guards against: a template that renders fine but
  "renders... a task result with the answer silently missing" — matching
  "`{{result}}` required, empty rejected at load" precisely.
- **Facts and framing live outside the operator template and cannot be
  edited away by it, confirmed exactly**: `render_task_result` builds the
  `<{UNTRUSTED_TAG}>`-framed block, the status/reason line, and
  `RESULT_UNTRUSTED_GUIDANCE` entirely in Rust, and only substitutes the
  *resulting* framed string into the operator-controlled `template` via
  `{{result}}` — then wraps that templated body with the status/reason/
  guidance line in an outer `format!` that the template has no access to.
  This is directly proven by the dedicated test
  `a_retuned_result_template_cannot_drop_the_status_frame_or_guidance`,
  which renders with the most hostile template that still passes config
  validation (bare `"{{result}}"`) and asserts the status, reason,
  guidance sentence, and untrusted-data frame all survive.
- **Only the child's answer sits inside the untrusted frame, confirmed
  exactly**: the dedicated test
  `only_the_child_answer_is_inside_the_untrusted_frame` asserts the
  status line and the guidance sentence are both *outside* the frame's
  open/close tags — matching the stated reasoning that framing
  server-generated facts alongside child-authored bytes would both invite
  spoofing and blur what the frame means.
- **`{{result}}` substituted last, so chained replacement cannot re-scan
  child-authored bytes, confirmed exactly**: `template.replace("{{truncated_note}}",
  truncated_note).replace("{{result}}", &framed)` — the truncation-note
  substitution runs first, the already-fully-rendered `framed` string
  (built separately, containing the child's text) is substituted last and
  is never itself subject to a further `.replace()` call. This matches
  "`{{result}}` is substituted last, after the truncation note, so
  chained replacement cannot re-scan child-authored bytes" exactly.
- **A child cannot escape the frame from inside it, confirmed exactly**:
  reuses the established `framed_untrusted_block` escape-not-strip
  pattern from #1163 (`<`/`>` HTML-entity-escaped, confirmed by this
  session's earlier review of that PR), and the dedicated test
  `a_child_answer_cannot_escape_the_untrusted_frame` feeds a hostile
  summary containing a literal closing tag and asserts the rendered
  output still contains exactly one closing tag.
- **Truncation note only appears when truncated, confirmed exactly**: the
  dedicated test `the_truncation_note_appears_only_when_the_answer_was_shortened`
  confirms the note's text appears only when `part.truncated` is true, and
  that an absent note leaves exactly one space (not two) — matching the
  code comment "Carries its own leading space so an absent note leaves no
  double space."
- **A delivered result rides a user-role row and bypasses the
  current-row-only gate, confirmed exactly**: in
  `build_abstract_sequence_with_facet_tool_expansions`, a new loop
  collecting `ContentPart::TaskResult` parts into
  `AbstractChatSequencePart::TaskResult` is placed *before* the existing
  `if prev_msg.id == *previous_message_id` check that otherwise drops
  every user row but the current one — with a comment stating directly "A
  delivered task result is history, not something the user typed, so it
  is emitted for EVERY prior turn — the current-row check below
  deliberately does not gate it." This matches the PR's claim precisely.
- **The directive-strip predicate deliberately does not match it,
  confirmed exactly**: `AbstractChatSequencePart::TaskResult` is a
  distinct variant from the two directive markers
  (`ActionFacetMarker`/`DelegationPreambleMarker`), and in `resolve_sequence`
  its own match arm renders it as a kept `InputMessage` with a comment
  stating "Unlike them it is NOT stripped from prior turns: the result
  stays in the conversation" — matching "a result is history, not an
  instruction for this turn" exactly.
- **Resolved as a marker at request-build time, not baked into stored
  text, confirmed exactly**: `ContentPart::TaskResult` is stored as a
  structured `ContentPartTaskResult` (raw, per its own doc comment: "It is
  stored RAW — the untrusted-data frame and the safety guidance are
  applied when the conversation is composed for the model"), and the
  `AbstractChatSequencePart::TaskResult` variant's doc comment states
  "Rendered in the resolver step so the configured result template and
  the untrusted-data frame are applied at request-build time rather than
  baked into what was stored" — directly confirming "retuning the
  operator template changes old turns too."
- **`full_text()` returns empty for the part, confirmed exactly, with the
  exact stated rationale**: `MessageSchema`'s full-text collector adds
  `ContentPart::TaskResult(_)` to the same `None`-returning match arm as
  the two marker types, with a code comment stating verbatim the PR's own
  reasoning: "letting it through here would let a delegated run write the
  chat's title." The corresponding `InputMessage` text-rendering match
  arm is updated identically.
- Per the PR (not independently re-verified given remaining scope): the
  precise wire shape and derivation of `ChatMessage.initiator?`/
  `ChatMessage.task_result?` in `mod.rs` (34 lines, not read — though the
  underlying `GenerationInitiator`/`TaskResultInput` types backing them
  were read in full in `message.rs` and match the PR's description), the
  `ResultDelivery` state/row definition itself (described as defined here
  but "nothing writes any of it yet"), the `file_resolution.rs` diff (48
  lines), the `genai.rs`/`genai_langfuse.rs` diffs (4+13 lines), the
  133-line new `prompt_composition/tests.rs` additions beyond the four
  `delegation.rs` unit tests read directly, the 62-line `config.rs`
  integration test additions, and the disclosed verification (1152/1152
  `cargo nextest run`, clean clippy `-D warnings`, clean frontend `tsc
  --noEmit`).

## Compatibility and configuration

Additive and entirely inert in this PR: new config key
`delegation.tasks.result_template` (built-in default, validated
non-empty and `{{result}}`-containing at load), new `ContentPart` variant
`task_result` and derived `ChatMessage.initiator?`/`.task_result?`
fields — all additive wire surface with nothing yet producing these
values at runtime, per the PR's own explicit "ships entirely dark"
framing (the writer lands in a later PR, ERMAIN-780). `openapi.json` and
frontend generated types are regenerated in this same commit.
