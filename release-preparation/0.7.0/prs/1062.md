# PR #1062: Keep the composer upload button usable after a file error (ERMAIN-163)

- PR: https://github.com/EratoLab/erato/pull/1062
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a real dead-end bug on the default desktop web composer (no cloud
providers, no host-registered selector): rejecting an upload (e.g. too
large) previously swapped `FileUploadButton`'s entire subtree — including
the dropzone root and file input — for a disabled danger button, and
dismissing the error banner above the input only cleared `ChatInput`'s
local error mirror, not the shared upload store the button itself read
from, so the button stayed disabled until a drag-and-drop, chat switch,
or reload. Confirmed by reading the three core changed files in full:

- **The dead-end removed, confirmed exactly via
  `FileUploadWithTokenCheck.tsx`**: `uploadError`/`resolvedUploadError`
  is no longer passed to `FileUploadButton` at all — a code comment
  states the rationale directly: the composer's dismissible alert now
  owns upload errors, and passing the error into the button would swallow
  its picker.
- **Dead error plumbing removed, confirmed via `useChatFileSources.tsx`**:
  the `uploadError`/`externalUploadError` param, the local `cloudLinkError`
  state, and the `resolvedUploadError` aggregation are all removed from
  the hook entirely, matching the PR's stated cleanup scope exactly.
- **Cloud-link failures now route to the shared store, confirmed
  exactly**: the cloud-link catch block changes from
  `setCloudLinkError(error instanceof Error ? error : new Error(...))`
  to `setError(new CloudLinkError())` — `setError` is the shared
  `useFileUploadStore`'s setter (confirmed via the same setter being
  destructured and exposed in `ChatInput.tsx` as `setUploadStoreError`),
  so a cloud-link failure now surfaces through the same alert as a disk
  upload error, where previously — per the PR, consistent with this
  code path having no renderer before this change — it had no visible
  surface at all when cloud providers were configured.
- **Dismiss clears both copies, confirmed exactly via `ChatInput.tsx`**:
  a new `handleDismissFileError` callback calls both `setFileError(null)`
  (the local mirror) and `setUploadStoreError(null)` (the shared store),
  and is wired as the alert's `onDismiss` — replacing the previous
  `onDismiss={() => setFileError(null)}`, which left the store's copy
  intact and was the direct cause of the dead-end. Confirmed both
  remaining `uploadError`/`externalUploadError` pass-sites to
  `FileUploadButton`/`FileUploadWithTokenCheck` within `ChatInput.tsx`
  are removed as part of the same diff.
- Per the PR (not independently re-verified): `FileUploadButton`'s own
  error-state rendering is untouched and remains used by `FileUpload` in
  its `buttonOnly` mode (a different, unaffected code path); mobile/add-in
  surfaces and cloud-provider deployments render `FileSourceSelector`,
  which never consumed `uploadError` and was therefore unaffected by the
  original bug; and the e2e spec addition
  (`chat.basic.spec.ts`) exercises the exact repro (60 MB upload error →
  dismiss → upload a valid file through the same button) but was not run
  locally per the PR's own note (local stack on Entra auth, which the
  headless e2e setup can't log into).

## Release note disposition

Proposed category: Bug fixes. Worth a mention: the composer's file-upload
button no longer gets stuck disabled after a rejected upload (e.g. a file
that's too large) — dismissing the error banner now fully clears it, and
cloud-link upload failures are now visibly surfaced instead of silently
swallowed.
