# PR #827: Share host modules with component kits via import maps

- PR: https://github.com/EratoLab/erato/pull/827
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Replaces #826's `window.ERATO_KIT_RUNTIME` window-global-bag approach (per
the PR, in response to review feedback to "keep that surface minimal")
with a browser **import-map** mechanism that solves the module-identity
problem structurally rather than via a runtime object: a component kit's
separately-built bundle now imports host modules (React, lingui, router,
and Erato's own hooks/providers/components) as ordinary bare-specifier
`import` statements, resolved by the browser at load time to the *same*
already-loaded chunk the host app itself uses — one evaluation, one shared
module/context instance, no duplicated React/i18n state (the root cause
of the cited Beckhoff regressions: lost archive-confirm dialog, feedback
silently off, degraded loading indicator).

Given this PR's scale (2443 insertions/857 deletions across 71 files,
spanning a new build-plugin system, a rewritten Vite config, and a new
Storybook loader for the example kit), review focused on verifying the
backend wiring and the shared-module manifest rather than the full
frontend build-tooling rewrite:

- Confirmed in `frontend_environment.rs`: the backend now loads
  `import-map.manifest.json` from a served frontend's bundle directory
  (`load_import_map_json`) and, when present and valid, injects
  `<script type="importmap">...</script>` as the **first** child of
  `<head>` (via `el.prepend`, confirmed as necessary since an import map
  must precede every `<script type="module">` in document order) — a
  missing or malformed manifest disables injection rather than failing
  startup, so older bundles built before this change keep serving
  unaffected.
- `frontend/shared-modules.config.ts` (new, 50 lines, read in full) is
  confirmed as the single source of truth the PR describes: each entry
  becomes an extra Rollup input sharing a chunk with the app entry, an
  import-map entry, and a `./shared` type export. The file itself lists 9
  third-party specifiers (react, react/jsx-runtime,
  react/jsx-dev-runtime, react-dom, @lingui/core, @lingui/react,
  @tanstack/react-query, react-router, react-router-dom) plus one
  `@erato/frontend/shared` barrel entry; that barrel itself (`shared/index.ts`,
  read in full) re-exports from 12 further Erato-owned modules (auth token
  store, ModelSelector, messaging store, starter prompts, themed-icon hook,
  voice runtime, and five context providers/stores) plus 2 named API
  hooks — the PR's stated "37 entries" figure is plausible as the combined
  count across this whole nested surface, though not independently
  recounted exhaustively.
- `ERATO_SHARED_SURFACE_VERSION = 1` (confirmed, in `shared/index.ts`) is
  the version handshake the PR describes, intended for a kit to check at
  load and warn on mismatch.
- Confirmed `componentKitHostRuntime.ts` (from #826) is fully deleted (-87
  lines) in this diff, matching the stated "removed before gaining a
  consumer," while `componentKitReactRuntime.ts`
  (`ERATO_REACT`/`ERATO_LINGUI_REACT`/`ERATO_FEATURES`) is kept with only
  a 5-line addition (a freeze/deprecation-pointer comment, per the PR),
  consistent with the stated backward-compatibility intent for
  already-deployed kits.
- On the "add-in mounts never receive a map" claim: the code actually
  computes `addin_import_map_json`/`addin_legacy_import_map_json` via the
  same generic `load_import_map_json` call used for the web frontend, so
  structurally an add-in-served frontend *could* get a map — but since
  `load_import_map_json` returns `None` whenever
  `import-map.manifest.json` isn't found at that bundle path, and the
  add-in's own build doesn't emit that manifest (it isn't built through
  the web frontend's shared-modules Rollup config), the practical effect
  matches the PR's claim: the add-in mount resolves to `None` in
  practice, not because of a hardcoded exclusion but because its build
  output never produces the manifest the loader looks for.
- Not independently verified: the entire `component-kit-host.plugins.ts`
  (new, 513 lines) build-plugin implementation, the Storybook
  build/preview import-map wiring for `component-kit-example`, the CSP
  "unchanged" claim (not independently re-diffed against
  `build_content_security_policy`), and the stated bundle-size reduction
  (10,197 kB → 7.4 kB) for the example kit.

## Compatibility and configuration

No new user-facing configuration keys. Backend behavior change: served web
(and, structurally, add-in) HTML now gets an `<script type="importmap">`
tag injected as the first `<head>` child whenever the corresponding
frontend bundle directory contains an `import-map.manifest.json` — for
existing web-frontend builds produced by this same release's build
pipeline, this will be present; older/externally-built bundles without
that manifest see no change. This is new backend-served-HTML surface
worth a maintainer's attention, though the PR states CSP itself is
unchanged (`frame-ancestors` only) and flags that a future `script-src`
CSP directive would require a nonce/hash on the inline import map.
