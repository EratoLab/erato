## Summary

No GitHub description beyond a Linear reference (ERMAIN-931); evaluated
from the diff and the extensive new `configuration.mdx` section it adds
(confirmed to be complete and precise against the new `[chat_history_compaction]`
config struct). Adds a new, opt-in `[chat_history_compaction]` feature
letting a user manually replace a long conversation's context with a
summary, generated by a configured chat provider, while keeping the
original transcript visible behind an expandable summary marker
(`CompactionMarker.tsx`/`.test.tsx` on the frontend). A new backend
endpoint (`server/api/v1beta/chat_history_compaction.rs`, 661 lines) and
service (`services/chat_history_compaction.rs` + 245-line test file)
implement the actual summarization run, consumed by the prompt
composition pipeline via a new `adapters.rs`/`transforms.rs` hook (with
its own `compaction.rs` test-case file) so a stored checkpoint replaces
everything before it in the replayed conversation. Per the docs:
assistant knowledge files are always retained across compaction, other
files are included via bounded previews, and compaction only ever runs
after an explicit user click — never automatically, even with
`trigger_mode` set, which only governs a *suggestion* appearing in the
UI (`CompactionSuggestion.tsx`) at a configurable context-usage
threshold. Frontend wiring includes a new `useChatCompaction` hook and
`compactionStore`, and `ChatInputTokenUsage.tsx` is extended to surface
the suggestion inline with existing token-usage display.

## Compatibility and configuration

New, entirely optional top-level table, disabled by default:
```toml
[chat_history_compaction]
enabled = false                                      # default
chat_provider_id = "gpt-4o-mini"                      # required when enabled; a configured chat provider
mode = "summarize"                                    # default and only supported value
trigger_mode = "suggest_with_user_approval"            # default and only supported value; never auto-triggers
trigger_on_token_limit_threshold_percentage = 80       # default; 0-100
target_compaction_token_limit_percentage = 10          # default; 0-100, a soft target, not an enforced cut
```
No breaking change: disabling the feature (the default) still honors
compaction checkpoints already stored in existing conversations, per the
docs. If the conversation plus retained-file previews don't fit the
summarizer provider's own context window, the operation fails without
modifying history — no partial/corrupting compaction. New
`openapi.json`/generated frontend API client entries (195/56/72 lines)
reflect the new endpoint and schemas. No database migration mentioned in
the diffed files list (no new migration file in the `--stat`), though
compaction checkpoints presumably persist as part of the existing
message/conversation model (`models/message.rs`, 56-line diff) rather
than a new table.
