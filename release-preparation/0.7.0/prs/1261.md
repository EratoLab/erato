# PR #1261: Implement tool call limit continuation approval workflow

- PR: https://github.com/EratoLab/erato/pull/1261
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Streaming/generation stability

## Summary

Turns hitting the per-message tool-call limit
(`generation.max_tool_calls_per_message`, added as a hard-abort-with-error
in #888) into a user-driven continuation decision instead of an outright
failure. New `backend/erato/src/services/tool_call_budget.rs` reuses the
existing MCP tool-approval protocol/UI (from #915) with a new
`ToolApprovalKind::ToolCallLimit` request kind: when the budget is
reached, the user is shown an approval card (not a real tool call — a
synthetic `tool-budget:<uuid>` ID keeps it "out of tool execution," per
the code comment) offering three outcomes:
- **Approve** ("Continue"): doubles the effective budget for this message
  (`budget.max(snapshot.saturating_mul(2))`, via `effective_budget`) and
  generation resumes.
- **Reject** with no special reason ("Answer now"): generation stops
  calling tools and produces a final answer with what it has gathered so
  far.
- **Reject with reason `"withdrawn"`** ("Stop"): generation halts entirely.

Budget-choice decisions are read strictly *after* their own request in the
message content sequence, so an earlier approval can't accidentally settle
a later, unrelated budget prompt (`choices` iterates forward from each
request's index). `frontend/src/components/ui/Message/McpToolApprovalCard.tsx`
(39-line diff) renders this new request kind alongside the existing MCP
tool-approval cards, presumably with distinct labels ("Continue" / "Answer
now" / "Stop" rather than the generic tool-approval wording).

## Compatibility and configuration

No new configuration keys — this changes what happens when the existing
`generation.max_tool_calls_per_message` limit (from #888, default 15) is
reached: previously an error aborted the turn; now the user is prompted to
continue (doubling the budget), get an answer with partial results, or
stop. No migration. This is a strict UX improvement over the prior hard
failure — no deployment loses functionality, though the interaction now
requires a user response mid-generation when the limit is hit, rather than
generation ending unconditionally.
