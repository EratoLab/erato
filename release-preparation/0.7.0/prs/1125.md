# PR #1125: Blink a pending dot on the tab favicon for the open chat

- PR: https://github.com/EratoLab/erato/pull/1125
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds a favicon badge (blinking grey while generating, solid green on
completion, amber when parked on a tool approval) for the specific chat
the current browser tab has open, visible only while the tab itself is
hidden. Confirmed by reading the complete `useTabChatActivity.ts` and
`blink.worker.ts`/`blinkDriver.ts` in full:

- **The "no ready state exists" problem and its fix, confirmed exactly**:
  a code comment states the store deliberately writes a `"cleared"`
  tombstone (not a readable "finished" state) when the completing chat is
  the one currently being viewed, since terminal indicators are
  suppressed for the sidebar row of the chat in view — so there is
  genuinely no store field this hook could read to know "the tab's own
  chat just finished." The fix: `useTabChatActivity` tracks
  `wasWorking.current` via a ref and, in a `useEffect`, sets `ready(true)`
  exactly on the falling edge (`wasWorking.current && !working &&
  document.hidden`) of `isStreaming || isFinalizing` — confirmed this is
  read directly from `useMessagingStore`, not reused from
  `useGenerationIndicatorCount`, matching the PR's explicit statement
  that it intentionally does not reuse that hook (which serves a
  different purpose — counting attention-worthy chats across the whole
  app, not this tab's specific chat).
- **Only a hidden tab carries a marker, confirmed exactly**: the hook
  returns `"idle"` unconditionally whenever `!hidden || isFramed()` —
  confirmed `isFramed()` checks `window.self !== window.top`, explicitly
  excluding the Teams tab (framed) scenario, where the favicon belongs to
  the host page and nothing this hook drives would ever be visible
  anyway.
- **Worker-based blink timing to survive the 1 Hz hidden-tab clamp,
  confirmed exactly**: `blink.worker.ts` runs a plain `setInterval(...,
  600)` inside a dedicated Web Worker (exempt from the main thread's
  hidden-tab timer throttling), posting a tick message back;
  `blinkDriver.ts`'s `startBlink` wraps worker construction in a
  `try`/`catch`, falling back to an ordinary main-thread `setInterval`
  when `new Worker(...)` throws (unsupported browser/build) — matching
  the PR's stated fallback-for-builds-without-worker-support design
  exactly. `shouldBlink()` checks `matchMedia("(prefers-reduced-motion:
  reduce)")`, consistent with the PR's disclosed reduced-motion
  accommodation (a static, non-blinking dot).
- Per the PR (not independently re-verified given remaining scope): the
  measured 250ms-held-exactly-across-1625-iterations claim for the worker
  timer versus 1000ms main-thread clamping (a runtime measurement, not
  something derivable from the code alone); the SVG-in-SVG icon
  composition approach (`composeBadgedIcon.ts`, 116 lines) chosen over
  canvas specifically to keep the base icon's own `prefers-color-scheme`
  rules live and avoid needing a canvas mock in tests; the base-icon
  source resolving from `/favicon.svg` with branch selection driven by
  the response's `Content-Type` header (since the backend serves a
  theme's `.ico` bytes at that path when that's all the theme ships,
  picking up customer theme favicons "for free"); and the disclosed
  browser-support gap (Safari never re-reads the icon `<link>` element at
  all — verified via a zero-favicon-fetch network trace against Chrome's
  43 fetches on the same page — needing no special handling since
  favicon-swap support can't be feature-detected, so Safari simply
  displays the static icon with no error path).

## Compatibility and configuration

None. Purely additive UX feature with no configuration surface; degrades
gracefully on browsers that don't support dynamic favicon swapping
(Safari, per the PR's disclosed finding) and respects
`prefers-reduced-motion`.
