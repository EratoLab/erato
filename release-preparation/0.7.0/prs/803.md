# PR #803: fix(edit): mirror regenerate action-facet fallback in edit_message_sse

- PR: https://github.com/EratoLab/erato/pull/803
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a bug where editing a message that was originally sent with an
action facet (e.g. `outlook_rewrite_selection`, carrying `selected_text`
args) silently dropped that facet context from the regenerated response —
`edit_message_sse` mapped `request.action_facet` directly with no
fallback, unlike the `regenerate` path (fixed earlier via
`fallback_action_facet`, per the PR body). Confirmed in
`message_streaming.rs`: `edit_message_sse` now resolves a
`resolved_action_facet` that prefers an explicit `action_facet` on the
edit request, falling back to the facet stored on the message being
edited, re-validated (`validate_action_facet`) against the **current**
config and platform — if that validation fails (e.g. the facet was
removed from config since the original send), the stored facet is dropped
with a `tracing::warn!` rather than failing the edit request with a 400.
The resolved facet is both persisted onto the new edit message's
`input_parameters` and fed into the generation request, since (unlike
regenerate, which reuses the existing user-message row) an edit creates a
new sibling message.

**One discrepancy from the PR description**: the description states the
fallback reads the stored facet "via
`get_generation_action_facet_from_message`", but the actual code calls a
different function, `get_input_action_facet_from_message` — confirmed
both functions exist in `backend/erato/src/models/message.rs` and are NOT
interchangeable: `get_generation_action_facet_from_message` reads a
message's `generation_parameters` (what an assistant message was actually
generated with; used by the regenerate path), while
`get_input_action_facet_from_message` reads a message's `input_parameters`
(what a user message's own submission carried; used here). Since
`message_to_edit` is the user's own message, `input_parameters` is the
semantically correct field to read — the PR description simply names the
wrong (but analogous) helper function; the shipped behavior itself is
correct.

## Compatibility and configuration

None. Pure bug fix restoring previously-dropped facet context on edit; no
configuration keys, API shape changes, or migrations. Behavior change:
editing a message sent with an action facet now correctly carries that
facet's context into the regenerated response, instead of silently losing
it, unless the facet no longer validates against current config (in which
case it is dropped with a warning log, same as before, but now
intentionally rather than incidentally for the "still valid" case too).
