# PR #1338: Let the user pick among identical passages and point to Word's Undo on the web (ERMAIN-928)

- PR: https://github.com/EratoLab/erato/pull/1338
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Word selection editing

## Summary

Per the PR description: two usability follow-ups on top of #1337's
ambiguous-target refusal (ERMAIN-937), landed immediately after it in the
same stack. First, when Replace refuses because the passage now matches
more than once (`AMBIGUOUS_TARGET`), the review card now offers "Replace
selected passage" instead of dead-ending: it takes a fresh capture of
whatever the user currently has selected and reuses the *same* already-
reviewed proposal, without a new model call, but only if the newly
selected text is byte-identical with matching shape and paragraph count
(`isSameWordPassage`) — otherwise it explains why and still writes
nothing, and the normal proven-target check still has final say. Second,
on Word for the web specifically, a Replace covering more than a new
`WORD_WEB_REVERT_MAX_PARAGRAPHS` constant's worth of paragraphs no longer
offers Erato's own in-app Undo; the card instead points the user at
Word's native Ctrl+Z/⌘Z. Confirmed directly in `wordReplaceSelection.ts`:
this constant is set to `5`, matching the PR's own measured rationale
(Word for the web's native restore ran roughly 4.4-5 seconds per
paragraph in testing, so a 10-paragraph Erato-side revert exceeded its 40
second budget; the PR's own commit history shows the limit was first set
even more conservatively and then raised back to 5 once that budget math
was worked out). Desktop Word and shorter web replacements are
unaffected.

## Compatibility and configuration

Pure UX refinement to the Replace flow introduced earlier in this batch
(#1334/#1336); no config keys, no database migration. The only
behavioral change for existing capability is the Undo-availability
threshold on Word for the web, which is a hard-coded constant, not
configurable.

## Evidence and review

Verified via this PR's merge commit against its parent (both present
locally). Confirmed directly: `WORD_WEB_REVERT_MAX_PARAGRAPHS = 5` and its
guard condition (`platform !== "OfficeOnline" || paragraphs <=
WORD_WEB_REVERT_MAX_PARAGRAPHS`) in `wordReplaceSelection.ts`, matching the
PR description's stated threshold and reasoning exactly. Not read in
full: the 278-line `WordSelectionCard.tsx` diff implementing the
"Replace selected passage" re-capture-and-compare flow, or its associated
test files (over 100 lines across two files). The PR's own commit
history (an initial attempt superseded by a corrected paragraph-count
threshold, with the measured per-paragraph timing stated as the reason)
is treated as credible first-party evidence of how the final `5` value
was derived.
