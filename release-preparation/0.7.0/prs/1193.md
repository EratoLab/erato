# PR #1193: Speed up MCP server listing with bounded parallel probes

- PR: https://github.com/EratoLab/erato/pull/1193
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Replaces the server-by-server sequential connection-check loop behind
`list_mcp_servers` with bounded concurrent probing, and fixes each
probe's own inefficiency (shared-cache churn, double credential
resolution, waiting on best-effort remote cleanup). Confirmed every
concrete claim by reading the complete diffs to `mcp_servers.rs`,
`mcp_session_manager.rs`, and the relevant `mcp_oauth.rs` addition:

- **Bounded to four concurrent probes, confirmed exactly**: the endpoint
  builds a `Vec` of probe futures and runs them via
  `stream::iter(probes).buffer_unordered(4).collect().await` — matching
  "Run up to four probes concurrently" exactly, with a code comment
  stating the intent directly: "A slow server must not prevent other
  checks from starting or completing."
- **Results re-sorted after the unordered collection, confirmed exactly**:
  `servers.sort_by(|a, b| a.id.cmp(&b.id))` runs immediately after the
  `buffer_unordered` collect — since `buffer_unordered` completes futures
  in whatever order they finish, this re-sort is necessary and
  sufficient to restore deterministic ordering, matching "preserving
  sorted results."
- **Ten-second deadline per probe, confirmed exactly**: a new
  `CONNECTION_PROBE_TIMEOUT: Duration = Duration::from_secs(10)` wraps the
  per-server probe body in `tokio::time::timeout`, mapping a timeout to
  `McpServerConnectionStatus::Failure` with a `warn!` log — matching "a
  ten-second deadline per probe" exactly, and consistent with "the
  overall request can exceed ten seconds" with more than four servers
  queued, since the bound is per-probe, not per-request.
- **Each probe owns a temporary connection outside the session cache,
  confirmed exactly**: `probe_connection` previously called
  `get_or_create_session(Uuid::nil(), server_id, auth_context)` (a shared
  cache entry under the nil probe-chat-id, invalidated after every call)
  and separately resolved `session_auth_key` a second time purely to
  perform that invalidation. It's replaced with a direct
  `create_mcp_service(server_id, &config, auth_context)` call that never
  touches the session cache at all — the `ENUMERATION_CHAT_ID` doc comment
  is updated accordingly to state "connection probes never enter this
  cache" (previously it described the nil-id probe cache as a distinct,
  deliberately-churned entry). This matches "Each probe owns a temporary
  connection outside the session cache" precisely.
- **Credentials resolved once per probe, confirmed exactly, by
  elimination**: the prior code's two separate resolution points (one
  implicit inside `get_or_create_session`'s connect path, one explicit via
  `Self::session_auth_key(...)` purely for the cache-invalidation key) are
  both gone in the new code, which resolves auth exactly once inside
  `create_mcp_service` — matching "resolves OAuth credentials once."
- **Cleanup does not wait for remote session deletion, confirmed exactly,
  with the precise stated mechanism**: a code comment states directly
  "Dropping the service cancels it without delaying the result for the
  transport's best-effort remote session deletion" — the probe's
  `service` value is simply dropped at the end of the `async` block
  (implicit via scope-end, no explicit `.delete_session()`-style await),
  letting the result return without waiting on it.
- **Missing OAuth grants fail before any discovery request, confirmed
  exactly**: `resolve_oauth_access_token` now loads stored credentials
  first via `DatabaseCredentialStore::load()` and returns
  `Err(AuthError::AuthorizationRequired)` immediately if no
  `token_response` is stored — *before* `configured_authorization_manager`
  (the discovery/refresh path) is ever called — with a code comment
  stating "an unavailable authorization server must not delay reporting
  this state." This matches "Missing grants return `NEEDS_AUTHENTICATION`
  before any discovery request" precisely (mapping `AuthorizationRequired`
  to the `NEEDS_AUTHENTICATION` status is consistent with this session's
  established understanding of this codebase's MCP connection-status
  vocabulary from prior PRs' reviews).
- Per the PR (not independently re-verified given remaining scope): the
  disclosed regression coverage (bounded concurrency, sorted results with
  an unavailable server, no discovery for missing grants, initialization/
  tool-list deadlines, cancellation cleanup, a stalled remote session
  deletion) in the 126-line `mcp_progress_tests.rs` and 175-line
  integration test additions — not independently reproduced; and the
  disclosed validation (`just lint` across all three feature
  configurations, `just test` 1,130 passed with four pre-existing skips,
  `just generate_open_api_check` passed).

## Compatibility and configuration

None. Pure backend performance/correctness fix to the existing
`list_mcp_servers` endpoint's internal implementation — no wire, config,
or API shape changes (the response shape and sorted-by-id ordering are
both preserved, confirmed above). No new config keys; the 10-second
per-probe timeout and the 4-way concurrency bound are both hardcoded
constants, not configurable.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: the MCP servers settings
pane (web and Office add-in) no longer waits on each server's connection
check in sequence — up to four are checked concurrently with a 10-second
per-server cap, so one slow or unreachable server no longer holds up the
whole list, and a server with no stored OAuth grant is reported
immediately instead of waiting on a discovery round trip that was always
going to fail.
