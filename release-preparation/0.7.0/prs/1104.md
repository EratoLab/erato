# PR #1104: Support shared mailboxes in the Outlook add-in (ERMAIN-752)

- PR: https://github.com/EratoLab/erato/pull/1104
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Makes the Outlook add-in available in shared mailboxes and delegated
folders on Exchange Online (previously hidden entirely, since
`SupportsSharedFolders` defaults to `false` and was absent from every
manifest), while explicitly refusing on Exchange SE, where no supported
data plane can read a shared item correctly. Confirmed by reading the
complete `useOutlookMessageFetcher.ts` diff in full — the file where the
central async-race bug and its fix live:

- **The core async-race bug and its fix, confirmed exactly**: the hook's
  memoized result now checks `isLoadingSharedContext` *before* branching
  on on-prem/cloud, returning `{ fetcher: null, mailboxRoot: null,
  unavailableReason: "mailbox-location-pending" }` whenever the
  shared-context probe hasn't resolved yet — a lengthy code comment states
  the exact failure mode this closes: since `mailItem` resolves
  synchronously while `sharedContext` resolves async in the same effect,
  the first render(s) would otherwise hand out a `/me`-rooted fetcher for
  a conversation that actually lives in someone else's mailbox, and
  because `useCurrentThread` keys its query on item ids alone with
  `staleTime: Infinity`, that empty wrong-store answer would be cached
  permanently — never refetched once the real owner resolved. Four
  independent reviewers are stated to have found this in the first draft.
- **Shared-vs-narrow Graph scope split, confirmed exactly**: a new
  `GRAPH_SHARED_MAIL_SCOPES = ["Mail.Read.Shared"]` is requested only when
  `sharedMailboxRoot` is non-null; the common, non-shared path keeps
  requesting the narrower `GRAPH_MAIL_SCOPES = ["Mail.Read"]` — matching
  the PR's stated reasoning that Entra consent has no scope hierarchy, so
  a deployment's existing `Mail.Read` grant does not cover
  `/users/{owner}` requests without an explicit additional grant.
- **`targetMailbox ?? owner`, not `owner` alone, confirmed exactly**: the
  Graph mailbox root is derived as `sharedContext.targetMailbox ??
  sharedContext.owner` — matching the disclosed second-round review fix,
  since Office documents `targetMailbox` as the mailbox location to
  address and warns it can differ from `owner` between clients.
- **Honest refusal on Exchange SE, confirmed exactly**: when
  `isOnPrem && sharedMailboxRoot` is true, the hook returns `{ fetcher:
  null, mailboxRoot: null, unavailableReason: "shared-mailbox-unsupported"
  }` instead of falling through to the EWS fetcher — matching the PR's
  stated rationale that an EWS fetch in a shared-mailbox scenario
  *succeeds* but silently answers out of the delegate's own mailbox
  (Microsoft does not support EWS for shared-mailbox reads), so refusing
  is safer than a confidently wrong answer.
- **`mailboxRoot` exposed for cache-key correctness, confirmed exactly**:
  the hook's return type gains a `mailboxRoot: string | null` field
  (documented as required for any item-id-keyed consumer to distinguish
  "same item, different store"), consistent with the PR's disclosed
  second-round fix that the thread query previously keyed on item ids
  alone and would have served a cached empty answer forever once the
  owner resolved.
- **Selection-event churn stability, confirmed via the dependency
  derivation**: `sharedMailboxRoot` is derived as a primitive string from
  `sharedContext.targetMailbox`/`.owner` rather than depending on the
  `sharedContext` object itself — a code comment states the provider
  mints a fresh object on every selection event (hosts fire two per
  selection) and depending on the object identity would otherwise restart
  every effect keyed on it for a byte-identical owner, consistent with the
  PR's disclosed fifth review fix (a stable identity being torn down and
  rebuilt on a redundant re-fire).
- Per the PR (not independently re-verified given remaining scope): the
  manifest changes (`<SupportsSharedFolders>true</SupportsSharedFolders>`,
  positioned as the schema-required literal first child of the V1_1
  `DesktopFormFactor` block, verified against Microsoft's schema
  validation service per the PR) apply only to the cloud/funnel manifests,
  deliberately leaving the two on-prem manifests untouched since they
  have no V1_1 block and adding one would trip #1065's
  `manifest_supports_launch_events()` hard-error guard; the disclosed
  5-second probe timeout added in the second review-fix commit (addressing
  a host that never answers `getSharedPropertiesAsync`, the "ERMAIN-431
  class" of dropped-callback bug); and the empty-string-`targetMailbox`
  normalization fix (`""` previously not falling through to `owner` via
  `??`, silently routing an on-prem item to the narrow scope and skipping
  the SE refusal).
- **Explicitly disclosed deployment prerequisites, per the PR**: the
  `Mail.Read.Shared` scope must be separately granted on the Entra app
  before this reaches production (existing `Mail.Read` grants do not
  cover it, and every `/users/{owner}` request 403s until then); customers
  hold a snapshotted manifest file uploaded through Integrated Apps, so
  this change reaches zero existing tenants until each one re-uploads the
  new manifest; and the feature is stated as not yet exercised against a
  real shared mailbox (only unit/mutation-tested), with a manual
  verification matrix tracked separately on the linked issue.

## Compatibility and configuration

New manifest capability declaration (`SupportsSharedFolders`) — requires
a manifest re-upload by each customer through Microsoft's Integrated Apps
admin flow before it takes effect for that tenant; shipping this code
alone changes nothing for any existing deployment. Requires the
`Mail.Read.Shared` Entra app scope to be granted separately from the
existing `Mail.Read` scope. On-prem Exchange SE deployments see the
add-in correctly refuse (not silently misbehave) when opened against a
shared mailbox or delegated folder.

## Release note disposition

Proposed category: Features and enhancements, but **contingent on
deployment prerequisites explicitly disclosed by the PR**: this ships
inert code until (a) each customer re-uploads a new manifest through
Integrated Apps and (b) the `Mail.Read.Shared` Entra scope is granted.
Worth noting for the release notes with that context: the Outlook add-in
can now be used from shared mailboxes and delegated folders on Exchange
Online (requires a manifest re-upload and an additional Graph permission
grant); it correctly declines to operate against a shared mailbox on
on-premises Exchange, where no reliable data path exists.
