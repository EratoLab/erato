# PR #1268: Per-tool Ask/Never decisions for client tools, enforced in the backend like MCP

- PR: https://github.com/EratoLab/erato/pull/1268
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Extends the existing MCP tool approval mechanism (the stack this session
reviewed extensively in #1146-1152, #1195, #1230) to client tools (today:
the desktop sidecar's `desktop/*` tools, reviewed in #1213/#1216/#1219),
so a user can set **Always allow**, **Ask**, or **Never** per tool, with
the decision enforced server-side at dispatch rather than racing the
client-tool park timeout in the browser. Confirmed the backend data
model and dispatch-gating logic precisely:

- **New per-user, per-tool decision storage, confirmed exactly**: a new
  nullable-free JSONB column `user_preferences.client_tool_decisions`
  (migration 0055, `DEFAULT '{}'::jsonb NOT NULL CHECK (jsonb_typeof(...)
  = 'object')`) backs a new `ClientToolDecision` enum with exactly the
  three named variants `NeverAllow`/`Ask`/`AlwaysAllow` — matching
  "**Always allow**, **Ask**, or **Never**" precisely.
- **A decision is merged in without touching other tools' stored
  decisions, confirmed exactly, with the exact stated reasoning**:
  `set_client_tool_decision` writes via `ON CONFLICT (user_id) DO UPDATE
  SET client_tool_decisions = user_preferences.client_tool_decisions ||
  EXCLUDED.client_tool_decisions` — a genuine JSONB merge (`||`), not a
  whole-column replace — with a doc comment stating "so an answer given
  on an approval card cannot drop a decision saved in another tab,"
  matching "persisted atomically into `client_tool_decisions` (a jsonb
  merge, other keys kept)" exactly.
- **A corrupted stored entry fails closed, confirmed exactly, a
  defensive detail consistent with this session's repeated observations
  of this codebase's safety posture**: `client_tool_decisions_from_json`
  maps any entry that fails to deserialize to `ClientToolDecision::NeverAllow`
  rather than dropping it or defaulting to permissive, with the comment
  "so a corrupted decision cannot silently re-enable a tool."
- **Decisions are read fresh at dispatch, never cached, confirmed
  exactly**: `find_client_tool_decision` queries the database on every
  call via `get_user_preferences`, with a doc comment "read fresh so a
  decision stored while a generation runs holds for its next call" —
  matching "Decisions are re-read on every call."
- **The three decisions gate dispatch exactly as described, confirmed
  exactly**: a new `ToolApprovalKind::ClientTool` variant sits alongside
  the existing `McpTool`; the gating match is `None | Some(AlwaysAllow)
  => ToolCallGate::Run` (no stored decision means today's behavior,
  matching "No stored decision means today's behaviour (the tool
  runs)"), `Some(NeverAllow) => refuse_denied_tool_call(...)` (matching
  "withheld from the model at offer time and on resume, and refused at
  dispatch... No `client_tool_call` is sent"), and `Some(Ask) =>
  ask_for_tool_call(..., ToolApprovalKind::ClientTool, ...)` (matching
  "the backend stops the turn durably with a `ContentPartToolApprovalRequest`
  ... and resumes via `/messages/continuestream`").
- **A card decision persists the correct standing decision, confirmed
  exactly**: the match `(ClientTool, ToolApprovalDecision::ApproveAlways)
  => Some(AlwaysAllow)` and `(ClientTool, ToolApprovalDecision::RejectAlways)
  => Some(NeverAllow)` reuses the exact `ApproveAlways`/`RejectAlways`
  decision variants this session confirmed in PR #1195's review —
  matching "Card decisions: Allow always → `always_allow`, Never →
  `never_allow`... allow once / deny are not stored" (only the two
  "always" variants map to a persisted decision; the plain
  `Approve`/`Reject` variants are absent from this match, consistent
  with them not being stored).
- **A continuing client's declared tool registration is captured and
  consulted, confirmed exactly**: the continuation route captures
  `registered_client_tools` from the `X-Erato-Client-Tools` header
  (reusing the exact header and parsing function —
  `crate::services::client_tools::registered_client_tools` — this
  session confirmed was added by PR #1213 for the sidecar tools'
  availability-advertisement mechanism), and a `registered_kind` check
  converts an `Ask` gate directly to `Run` for "a registered operation
  kind [that] is not asked about again" per the code's own comment —
  consistent with "If the continuing client declares its tools... and
  cannot run this one [the behavior differs]" from the PR's own
  description (the exact fallback behavior for the "cannot run"
  sub-case was not traced further in this review).
- Per the PR (not independently re-verified given remaining scope): the
  web Settings UI listing the sidecar's supported tools with the shared
  `McpToolDecisionControl` (`SidecarToolDecisions.tsx`, a new 99-line
  component, and its integration into `DesktopSidecarTabContent.tsx`);
  the "not shown in strict delegation mode" visibility rule; the full
  continuation-route wiring beyond the gating match shown (the remaining
  ~300 lines of the 374-line `message_streaming.rs` diff); the new
  `ms_teams_bot/host.rs` diff (121 lines — presumably wiring the same
  mechanism into the Teams bot's own client-tool dispatch, given this
  session's review of the Teams bot in #1253); and the disclosed
  motivation for the backend-side design (a first browser-side version
  racing the backend's `timeout_ms` client-tool park deadline, with a
  late decision reaching the model as a timeout and the result silently
  dropped) — a stated history, not independently verified, but
  consistent with and well-supported by the confirmed durable-park
  mechanism this design replaces it with.

## Compatibility and configuration

Additive database migration (sqitch 0055), non-null with a safe empty-
object default — no effect on any existing user until they set a
decision. No config keys; this extends the existing MCP approval UI/
mechanism to a second tool class (client tools) rather than introducing
a new one. No breaking change to the existing MCP approval flow,
confirmed by `ToolApprovalKind::ClientTool` being added as a new
variant alongside the untouched `McpTool`.

## Release note disposition

Proposed category: Features and enhancements. Worth a mention: a user
can now set a standing Always-allow/Ask/Never decision for individual
client-side tools (such as the desktop sidecar's tools), enforced by the
backend the same durable way MCP tool approvals already work — closing
a gap where a slow approval decision in the browser could previously
race the tool's own execution timeout and silently lose the result.
