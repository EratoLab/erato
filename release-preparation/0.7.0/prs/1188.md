# PR #1188: Refuse a second write into a generating chat instead of taking it over (ERMAIN-776)

- PR: https://github.com/EratoLab/erato/pull/1188
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 4 "Async re-entry", position 1 of 5, based on `main` (a new,
independent stack from the "Dynamic Delegated Tasks" one reviewed in
#1180/#1181). Makes the `chats` row the single arbiter of which
generation owns a chat via a database compare-and-set, replacing the
previous "last `start_task` call wins" behavior that silently dropped a
legitimate writer once a delegated task can also deliver a result into
the same conversation. Confirmed the full mechanism — the CAS semantics,
the `Takeover` person-vs-system distinction, the heartbeat identity
guard, and the bounded-not-assumed-bounded abort handling — by reading
the core of `background_tasks.rs` and the config/CHANGELOG additions in
full, and by tracing every call site of the new `Takeover` enum:

- **New `multitask_strategy` config key, confirmed exactly**: a
  `MultitaskStrategy` enum (`Reject`/`Enqueue`/`Interrupt`, `#[default]`
  `Reject`) added to `DelegationTasksConfig`. `DelegationConfig::validate`
  rejects `Enqueue`/`Interrupt` at load with the exact documented
  messages ("...is not supported yet"), via a `match` that only lets
  `Reject` pass — directly confirming "`\"enqueue\"` and `\"interrupt\"`
  are reserved and fail at load with a documented message" and the code's
  own stated reasoning that an unimplemented name silently behaving as
  `reject` would promise something false.
- **CAS claims exactly the described states, confirmed exactly**: the
  `claim_lease_in_txn` SQL's `WHERE` clause is `generation_state IS NULL
  OR generation_state IN ('completed', 'errored') OR (generation_state =
  'running' AND heartbeat older than stale_after_secs) OR ($4::bool AND
  generation_state = 'awaiting_approval')` — matching "claims only a
  lease which was never started, has ended, or went stale" precisely,
  with the fourth, parked-approval condition gated on the `take_parked`
  boolean passed in from `Takeover`.
- **Per-chat advisory lock around all three statements, confirmed
  exactly**: `pg_advisory_xact_lock(hashtextextended($1::text, 0))` is
  acquired first, transaction-scoped so it releases on commit or
  rollback either way; the UPDATE/DELETE/INSERT against `chats` and
  `temp_chat_generations` all run inside that same transaction — matching
  "a compare-and-set behind a per-chat advisory lock" and the stated
  reasoning that without it a loser could delete the winner's shared-row
  entry on its way out.
- **`Takeover` distinguishes person vs. system exactly as described,
  confirmed exactly across every call site**: `Takeover::TakeParked` is
  used at the user-initiated write routes — submit/regenerate/edit in
  `message_streaming.rs` (line ~2006) and `client_operations.rs` — while
  `Takeover::RefuseParked` is used at the system-initiated continuation
  site in `message_streaming.rs` (line ~2054, with a comment "a person
  parked on [approval] may be taken over" implied by contrast) and in
  `task_delivery.rs`'s delegated-task-result delivery path (commented "a
  [delegated] delivery takes this chat's lease for itself, and
  `RefuseParked`...") — directly confirming "a person may [abandon a
  parked approval], a system-initiated turn may not."
- **Heartbeat identity guard, confirmed exactly**: a new
  `lease_identity_guard: Arc<AtomicBool>` field, toggled via
  `with_lease_identity_guard(enabled)`, is commented as being "Enabled
  together with `delegation.tasks.enabled`, because that is what turns
  the lease from best-effort status reporting into admission control.
  With it off, nothing about the historical behaviour changes." — this
  directly substantiates the PR's claim that the gate controls this
  entire feature's activation, and that it's opt-in.
- **Only positive evidence of displacement triggers an abort, confirmed
  exactly**: `abort_displaced_generations`'s SQL only matches rows where
  `chats.generation_state = 'running' AND chats.active_generation_id IS
  DISTINCT FROM active.generation_id` — i.e., a row that actively names a
  *different* generation as the holder — with an explicit code comment
  warning that treating "my heartbeat did not land" as displacement would
  kill healthy generations whose best-effort start write was merely
  swallowed, which is precisely the race the un-guarded heartbeat exists
  to repair. Matches "aborts generations the row says someone else took,
  on positive evidence of displacement only" exactly.
- **Abort-requested generations stop being heartbeated and stop counting
  as live holders, confirmed exactly**: `heartbeat_targets` filters out
  `task.is_abort_requested()` before refreshing, and `try_start_task`'s
  own in-memory fast-path check (`!existing.is_completed() &&
  !existing.is_abort_requested()`) likewise treats an abort-requested
  task as not holding the lease — so such a row stops being refreshed and
  falls through to the CAS's stale-heartbeat branch on the normal
  schedule, matching "A generation whose abort was requested is therefore
  no longer heartbeated and no longer counts as a live holder, so the row
  ages out on the normal schedule" exactly, including the explicit
  reasoning about MCP session discovery/guardrails/file parsing running
  inside the lease with no timeout or abort arm (a code comment names
  these three specifically) and the consequence described (Stop
  returning 200 and changing nothing) being bounded rather than
  eliminated — deferred to ERMAIN-825 per the PR's own disclosure.
- **Publish-after-claim ordering, confirmed exactly**: the new task is
  only inserted into the in-memory `tasks` map *after* the CAS commits
  successfully — a code comment states "Publish the task only now, so a
  refused caller never leaves a map entry behind" — and a displaced
  existing task found during that insert is explicitly told via
  `displaced.request_abort()`, since it "no longer owns the chat and will
  never be told so by the heartbeat, because it is no longer in the map
  to be checked."
- Per the PR (not independently re-verified given remaining scope): the
  exact 409 response body shape and wiring across all four routes
  (`submit`/`regenerate`/`edit`/`continuestream`) beyond the one call
  site read directly (confirmed the `GenerationRunningError` struct with
  `code: "generation_running"` and the OpenAPI doc comments listing all
  four routes' 409 conditions, but did not trace every route's handler
  function individually); the claim that every other 409 on these routes
  remains byte-identical plain text; the disclosed test that pins
  "nothing changes with the gate off"; and the disclosed verification
  (1152/1152 `cargo nextest run`, clean clippy with `-D warnings`, clean
  `cargo fmt --check`). The 436-line `generating.rs` and 41-line
  `messages.rs` integration test additions were not read.

## Compatibility and configuration

Gated behind `delegation.tasks.enabled` (confirmed: the
`lease_identity_guard` is explicitly wired to that same flag per its own
doc comment) plus the new `delegation.tasks.multitask_strategy` key
(default `"reject"`, the only implemented value; `"enqueue"`/`"interrupt"`
rejected at startup). With the gate off, confirmed no behavior changes
(the heartbeat's un-guarded historical re-assertion path is preserved
verbatim when the `AtomicBool` is false). With the gate on: a second
write into a chat whose generation is still running now receives `409 {
code: "generation_running", chat_id, initiator, started_at? }` instead of
silently taking over the lease — a disclosed, intentional visible
behavior change restricted to this flag.

## Release note disposition

Proposed category: Features and enhancements / Wire changes (the PR's own
drafted `CHANGELOG.md` entry, confirmed accurate against the
implementation above). Release-note-worthy once `delegation.tasks.enabled`
ships enabled: a second write into an already-generating chat is refused
with `409 generation_running` rather than silently taking over the
running turn's lease — closing a correctness gap that becomes load-bearing
once a delegated task can deliver its own result into the conversation
concurrently with a human's own write.
