# PR #1146: Enumerate an MCP server's tools for the user with the effective projection

- PR: https://github.com/EratoLab/erato/pull/1146
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds `GET /me/mcp_servers/{server_id}/tools`, listing a configured MCP
server's tools with an "effective" projection (normalized annotations,
an `approval: auto | ask` verdict, whether the user has an always-allow
grant, whether the tool is the delegation wait-tool), plus a Settings UI
surfacing backend-decided badges. Confirmed by reading the complete new
`services/mcp_tool_approval.rs` module and the relevant consumption
sites in both `message_streaming.rs` and `mcp_servers.rs` in full:

- **Single shared evaluation function genuinely used by both the runtime
  gate and the new endpoint, confirmed exactly — not just claimed**: the
  new `evaluate_mcp_tool_approval(config, tool) -> McpToolApprovalVerdict`
  is imported and called directly inside `mcp_tool_approval_request` (the
  existing runtime gate in `message_streaming.rs`) *and* inside the new
  enumeration handler in `mcp_servers.rs` — confirming the PR's central
  correctness claim that "badges can no longer drift from the gate" is
  structural, not aspirational: both code paths literally call the same
  function rather than two independently-maintained implementations of
  the same logic.
- **Pessimistic annotation defaults, confirmed exactly**: `normalize_tool_annotations`
  defaults absent hints to `read_only_hint: false`, `destructive_hint:
  true`, `idempotent_hint: false`, `open_world_hint: true` — i.e. an
  unannotated tool is read as maximally risky by default, not
  maximally safe, matching the PR's stated `annotated` field semantics
  ("an unannotated tool is not read-only: the defaults are the
  pessimistic reading") and confirmed by a dedicated test
  (`absent_hints_fall_back_to_protocol_defaults`).
- **`annotated` correctly distinguishes "no annotations object" from "an
  empty-but-present one," confirmed via a dedicated test**: `annotated:
  tool.annotations.is_some()` is `false` only when the tool has no
  `annotations` field at all, and `true` even for a `ToolAnnotations`
  object with every individual hint unset — confirmed by the
  `annotated_is_false_only_without_any_annotations` test asserting both
  cases explicitly.
- **Review note 1's `user_decision: always` guard, confirmed exactly**:
  `always_allowed_tools` (the set driving a tool's `Always` decision) is
  populated only `if global.approval.allow_always` — the config flag —
  and is otherwise built from actual persisted grants; `user_decision`
  reports `Always` only when a tool's name is in that set. This precisely
  matches the disclosed review finding: the badge cannot report "Always"
  while the config has disabled persistent approvals or while no grant
  actually exists, keeping it consistent with what the runtime gate
  would actually do.
- **Disabled-gate short-circuit confirmed by a dedicated test**:
  `disabled_gate_never_requires_approval` confirms `requires_approval` is
  always `false` when `config.enabled` is `false`, regardless of preset
  or annotations — matching `requires_approval = config.enabled &&
  match config.preset { ... }`.
- Per the PR (not independently re-verified given remaining scope): the
  dedicated enumeration cache key (`ENUMERATION_CHAT_ID`, distinct from
  the connection-probe's nil key, which `GET /me/mcp_servers` invalidates
  on every call — so enumeration results don't get evicted by an
  unrelated probe); returning `session.tools` specifically so the listed
  rows already reflect `allow_tools`/`exclude_tools` filtering (matching
  what a real generation would actually see, not the server's raw tool
  list); the review-disclosed 404-before-403 check for an unconfigured
  server id via a new dedicated `authorized_server_config` helper
  (deliberately not changing the existing OAuth helper's reversed
  ordering, to avoid an unrelated behavior change); the review-disclosed
  cache invalidation on OAuth disconnect; the `McpServerStatusValue`
  reuse so an unconnected OAuth-gated server reports
  `NEEDS_AUTHENTICATION` rather than a generic error; and the frontend
  `useListMcpServerTools` hook plus the new `McpServerToolList.tsx` (201
  lines) rendering the backend-decided badges in Settings.

## Compatibility and configuration

None breaking. New additive `GET` endpoint and OpenAPI schema; no
configuration changes. Internal refactor (hint normalization/preset
evaluation extracted into a shared module) preserves existing runtime
gate behavior, confirmed via the shared function being the same one the
gate already used, not a reimplementation.
