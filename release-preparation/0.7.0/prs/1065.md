# PR #1065: Let deployments declare Office add-in launch events in config

- PR: https://github.com/EratoLab/erato/pull/1065
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds a typed configuration surface so a deployment can subscribe the
Outlook add-in to launch events (e.g. `OnNewMessageCompose`) — a
capability the Office manifest schema already supports but which erato
had no way to express, since the manifest renderer only substituted
branding scalars. Confirmed by reading the complete `config.rs` diff and
the relevant `router.rs` sections in full:

- **Typed config and validation, confirmed exactly**: `MsOfficeAddinConfig`
  gains `launch_event_runtime: Option<MsOfficeAddinLaunchEventRuntimeConfig>`
  (both default `None`/empty) and `launch_events:
  Vec<MsOfficeAddinLaunchEventConfig>`. `validate_launch_events` enforces
  the runtime is present exactly when at least one event is declared
  (erroring in both directions — runtime-without-events and
  events-without-runtime), rejects a `function_name` that doesn't match
  the JavaScript-identifier pattern `[A-Za-z_$][A-Za-z0-9_$]*`, and
  rejects a duplicate `event` value across the list — confirmed matching
  the PR's stated rationale that duplicate-`Type` validity is undocumented
  in Outlook's runtime and unenforced by the manifest XSD, so this is the
  only guard against it.
- **Root-relative-only runtime paths, confirmed exactly**: `page_path`/
  `script_path` are validated to start with `/` and not contain `..`,
  confirmed distinct from the neighboring icon-path validation (not
  independently re-read) which per the PR also accepts absolute URLs.
- **Escaping inversion, confirmed exactly via `router.rs`**: the generated
  `<LaunchEvent .../>`, `<Runtimes>`, and `<bt:Url .../>` XML blocks are
  built via `format!` and inserted into the manifest template verbatim
  (`replace_manifest_block`, a direct string substitution with no
  block-level escaping), while every individual scalar interpolated into
  them — `launch_event.event.as_str()`, `launch_event.function_name`,
  the composed `page_url`/`script_url` — passes through `xml_escape`
  first. This is confirmed the inverse of the surrounding renderer's
  usual whole-value-escaping pattern, exactly as the PR flags.
- **Manifest variant keyed by name, not shape, confirmed exactly**:
  `manifest_supports_launch_events(manifest_name)` is a plain string
  comparison against `OFFICE_ADDIN_MANIFEST_FILE_NAME` — the Exchange
  Server variant (lacking `VersionOverridesV1_1`) always renders empty
  launch-event blocks regardless of its template content, and
  `ensure_office_addin_manifests_support_launch_events` tolerates that
  variant's manifest file being entirely absent (a `NotFound` read error
  is swallowed via `continue` specifically when the variant doesn't
  support launch events).
- **Byte-identity when no events are declared, confirmed by construction**:
  `OfficeAddinManifestLaunchEventBlocks::render` returns
  `Self::default()` (all-empty strings) whenever the variant doesn't
  support launch events or `addin_config.launch_events.is_empty()` —
  `replace_manifest_block`'s doc comment states an empty block causes the
  entire placeholder line to be dropped, which is what preserves
  byte-identity with the pre-change template; a dedicated test
  (`render_office_addin_manifest_without_launch_events_matches_the_previous_template`,
  confirmed present by name) pins this against the stripped-placeholder
  baseline.
- **Startup fail-fast, confirmed exactly via `state.rs`/`router.rs`**:
  `AppState::new` calls
  `ensure_office_addin_manifests_support_launch_events` immediately after
  `Distribution::load`, before constructing the rest of app state — the
  function no-ops when no launch events are configured or the add-in
  bundle is disabled, otherwise it re-renders both manifest variants and
  cross-checks: each placeholder must be present in the raw template for
  a launch-event-capable variant, and after rendering, launch events must
  appear in the output exactly for the variants that support them (an
  explicit error if a supporting variant fails to render them, or if a
  non-supporting variant somehow does).

## Compatibility and configuration

New optional config keys: `integrations.ms_office.addin.launch_event_runtime`
(`page_path`, `script_path`) and
`[[integrations.ms_office.addin.launch_events]]` (`event`, `function_name`).
Both default to unset/empty, and the PR's stated byte-identical-rendering
guarantee for that default state is confirmed by the code's empty-block
fallback. A deployment configuring launch events against an add-in bundle
whose manifest template predates the placeholder markers now **fails to
start** with an actionable error — a deliberate, disclosed deviation from
this configuration area's usual warn-and-degrade behavior, confirmed
structurally as the first hard startup-refusal gated on bundle contents.
