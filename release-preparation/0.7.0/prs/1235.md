# PR #1235: Track EWS IDs on sidecar file uploads

- PR: https://github.com/EratoLab/erato/pull/1235
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Small, focused follow-up stacking on #1234 (the file-approval migration,
not independently reviewed in this pass since it wasn't in the evaluated
list). Threads the sidecar's EWS (Exchange Web Services) item identifier
through to uploaded files so a client can link an uploaded attachment or
exported document back to its original Outlook item, and fixes a
deduplication gap where two distinct Outlook items with identical byte
content would have been treated as the same upload. Confirmed both core
changes directly:

- **New nullable `external_id_ews_id` column, confirmed exactly**:
  migration 0049 is a single `ALTER TABLE file_uploads ADD COLUMN
  external_id_ews_id text;` with no `NOT NULL` constraint — matching
  "Adds nullable `external_id_ews_id`" exactly, and consistent with "the
  file-approval migration from #1234" being 0048 (this migration follows
  it in sequence).
- **Deduplication now keys on content hash *and* EWS ID together,
  confirmed exactly, with the exact stated rationale**: the frontend's
  upload-dedup map is renamed from `uploadedByHash` (keyed on
  `attachment.sha256` alone) to `uploadedByIdentity`, keyed on
  `JSON.stringify([attachment.sha256, externalIdEwsId ?? null])` — so two
  attachments with identical bytes but different EWS IDs are no longer
  deduplicated into a single upload. A code comment states the exact
  reasoning: "Equal bytes can belong to distinct Outlook items. Preserve
  their identities" — matching "Attachment deduplication includes the EWS
  ID, preserving distinct identities even when file contents match"
  precisely.
- **The EWS ID is threaded through both relevant upload paths, confirmed
  exactly**: `SidecarAttachmentUpload`'s signature gains an optional
  trailing `externalIdEwsId` parameter; both the conversation-attachment
  upload path (extracting `attachment.external_ids?.find(id => id.key ===
  "ews_id")?.value`) and the `get_sidecar_document` tool's export-upload
  path (extracting the same from the document-fetch response's
  `external_ids`) pass this value through to the upload call — matching
  "Sidecar document exports and approved conversation attachments now
  carry their own `ews_id` through upload" exactly, for both of the two
  named sources.
- Per the PR (not independently re-verified given remaining scope): the
  backend's own persistence of `external_id_ews_id` through the upload
  query parameter into `file_uploads` and its appearance in file
  responses (the small 1-2 line diffs across `file_upload.rs`,
  `message_streaming.rs`, `audio_transcription.rs`,
  `message_streaming_file_extraction.rs`, `mod.rs`, and
  `assistants.rs`/`assistant.rs` — each touched minimally, consistent
  with a field being added to an existing response/request shape
  pervasively but shallowly, not traced individually); the "Parent IDs
  are kept separate from the uploaded item's identity" claim; and the
  disclosed validation (60 frontend tests, TypeScript/ESLint checks, a
  backend upload round-trip integration test passing after rebase with
  temporary in-memory file storage, and sqitch/formatting/diff checks).

## Compatibility and configuration

Additive database migration (sqitch 0049), nullable column, no backfill
needed. No config keys. New optional request parameter and response
field; existing uploads without an EWS ID are unaffected (the column is
nullable and the frontend normalizes a missing value to `null` in the
dedup key, so pre-existing dedup behavior for non-EWS-sourced files is
unchanged).
