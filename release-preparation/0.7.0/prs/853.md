# PR #853: Edit user messages in place instead of in the composer (ERMAIN-471)

- PR: https://github.com/EratoLab/erato/pull/853
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

The planned refactor #850 was preparing for: editing a user message
previously hijacked the bottom composer (swapping it into `mode="edit"`,
prefilling from the target message, swapping back on save/cancel), while
the message being edited stayed rendered as static text elsewhere in the
list — visually disconnected from where the edit happened, and requiring
fragile compose-draft save/restore logic around the mode swap (the source
of several of the bugs fixed in #850/#841). This PR replaces that with
true in-place editing. Confirmed by reading the code:

- `MessageItem` now checks a new opt-in `MessageEditContext`
  (`useMessageEdit()`); when the current row's id matches
  `editingMessageId`, it renders a new `MessageEditorRow`/`MessageEditor`
  in place of the normal message renderer, instead of the composer being
  involved at all. Confirmed the design note that this replaces the whole
  renderer (rather than editing inline within it) specifically so a
  component-kit's custom `ChatMessageRenderer` override (from #825) still
  gets editing for free. Without a `MessageEditContext` provider, rows
  render read-only — for embedders of `MessageList` with no edit
  affordance.
- New `MessageEditor.tsx` (145 lines, read in full): a textarea seeded
  from the message's own content, auto-grow height, Escape-to-cancel,
  Enter-to-submit/Shift+Enter-for-newline, removable attachment chips
  (the row's own files, editable for this turn), and Cancel/Submit
  buttons — Submit disabled when the draft is empty or `isSubmitBlocked`.
- Confirmed via `MessageEditorRow` (in `MessageItem.tsx`) that the token
  limit check runs the same way it did in the composer
  (`ChatInputTokenUsage`, scoped per-row so a draft keystroke doesn't
  re-render the whole list) and that Submit is additionally blocked while
  `messageEdit.isStreaming === true` — confirmed as a genuinely new
  capability enabled by this move: the PR states the old composer-based
  edit mode had this scenario locked out entirely behind the broader
  `sendLocked` gate, so a stream-in-flight submit-block for an *in-place*
  edit was only reachable after this refactor. Cancel remains available
  throughout, so a draft can always be discarded but never silently lost.
- Dictation into the new editor is deliberately not carried over, per the
  PR.
- Both `Chat` and `AddinChat` now own `editingMessageId` state directly and
  pass the same submit handler down, rather than routing through the
  composer's props.
- **Confirmed the composer's entire edit mode is deleted**: the `mode`
  prop's edit branch, `editMessageId`, `editInitialContent`,
  `onEditMessage`, `onCancelEdit`, the prefill effect, the audio-mode-exit
  effect, the dictation-into-edit target, the submit branch, the Cancel
  button, and related testid/aria-label are all removed from
  `ChatInput.tsx` (confirmed via direct diff inspection: every named prop
  and its usages are gone). `EditMessageState` — previously exported from
  the library — has no remaining producer and is removed too. `initialFiles`
  is confirmed retained, since it's a general compose prop unrelated to
  edit mode specifically.
- The PR explicitly flags a coverage gap: nothing asserts that the host's
  `isPendingResponse` actually reaches the editor end-to-end (the wiring
  itself, as opposed to the editor's own blocked-state rendering, which is
  unit-tested) — proposing a follow-up E2E test for exactly this seam.

## Compatibility and configuration

None. Frontend-only UX redesign; no configuration or API changes. New
locale strings for the editor's Cancel/Submit/aria-label added across
de/en/es/fr/pl. Component-kit-facing: the composer's `mode="edit"` and
related props no longer exist — any external consumer that relied on
`ChatInput`'s edit-mode props directly (rather than going through the
standard message actions) would need to migrate to the new
`MessageEditContext` mechanism.
