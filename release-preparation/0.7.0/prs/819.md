# PR #819: Slot→appointment loop: copy-exact ISO slots + resilient scheduling stickiness

- PR: https://github.com/EratoLab/erato/pull/819
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Outlook scheduling and shared mailboxes

## Summary

Fixes two bugs found via live end-to-end testing of the "find a slot →
book it" flow (#801/#804/#818), both confirmed by reading the code:

1. **Model-reassembled times were wrong.** `suggestedSlots` previously only
   gave the model separate `day`/`start`/`end`/`utcOffset` fields, which it
   had to reassemble into an ISO timestamp for the `erato-appointment`
   fence — an error-prone step. Each slot now also carries fence-ready
   `startIso`/`endIso` strings (e.g. `2026-07-06T10:30:00+02:00`,
   confirmed built directly from the same zoned-instant data, not
   re-derived), and the calendar legend now explicitly instructs: "copy
   its startIso/endIso VERBATIM as the erato-appointment start/end — never
   rebuild times from day/start/utcOffset," and to use a resolved
   attendee's `email` (not display name) in the fence.
2. **The scheduling facet dropped out mid-negotiation.** The sticky-facet
   check previously only looked at the single latest assistant message
   for a scheduling signal, so any intervening clarifying turn (e.g. "did
   you mean 2pm or 3pm?", asking for a subject) — which has no tool call
   or fence itself — silently lost the `outlook_schedule` facet on the
   next send, stranding the model without instructions or the
   create-appointment tool. New `newestSchedulingSignalAt` now scans the
   **entire** ordered history backwards for the newest assistant message
   carrying a scheduling signal (a `fetch_availability` tool use, an
   `erato-appointment` fence, or a `propose_client_action` appointment
   proposal — confirmed via `containsSchedulingSignal`'s three-way check),
   restricted to `role === "assistant"` (a user-pasted fence deliberately
   doesn't count, preventing a user from spoofing stickiness). The
   existing 60-minute freshness gate (`SCHEDULING_THREAD_MAX_AGE_MS`,
   unchanged) still applies at send time, so a reopened stale chat still
   can't hijack the facet. The PR's stated rationale — misclassification
   costs are asymmetric (a facet riding an off-topic turn self-neutralizes
   via its own "respond normally otherwise" instruction, while a dropped
   facet breaks the flow entirely) — is confirmed in the code's own doc
   comment justifying the bias toward over-retaining stickiness.
