# PR #891: Add optional file scanning with magika

- PR: https://github.com/EratoLab/erato/pull/891
- Status: pending
- Category: Features and enhancements
- Theme: None

## Summary

Adds an optional, content-based file-type detector using Google's Magika
model as an alternative to Erato's existing "naive" detection (filename
extension for images, storage-provided MIME type otherwise, with
byte-signature inference as a fallback, and `.eml` always treated as
`message/rfc822`). New `file_type_detection.mode` config
(`backend/erato/src/config.rs`, `FileTypeDetectionMode` enum:
`naive` (default) | `magika`). New service
`backend/erato/src/services/file_type_detection.rs` (189 lines) wraps
Magika inference; `backend/erato/src/services/file_processing_cached.rs`
integrates it into the existing file-processing/caching pipeline (234-line
diff) so results are cached per unchanged file and Magika inference runs
on a blocking worker thread (one ONNX inter-op/intra-op thread each per
the docs) to avoid blocking async request handling. New Prometheus metrics
`erato_file_type_detection_duration_seconds` (histogram) and
`erato_file_type_detection_total` (counter), both labeled by `mode` and
`outcome`, track cold-path detection performance/failures
(`backend/erato/src/metrics.rs`). Magika itself is only initialized (and
its dependency/model overhead paid) when `mode = "magika"` is configured;
detection failures fall back to the naive behavior.

## Compatibility and configuration

New configuration key, defaulting to the pre-existing behavior:
```toml
[file_type_detection]
mode = "naive"  # or "magika"
```
(Environment variable equivalent: `FILE_TYPE_DETECTION__MODE`.) No
migration. Deployments that don't set this see no change — Magika is not
even initialized in the default `naive` mode. Enabling `magika` changes
how uploaded files are classified as images vs. text for extraction,
based on actual file content rather than extension/reported MIME type,
which could reclassify a mislabeled or extension-spoofed file more
correctly (or, in principle, differently than before) than the naive
heuristic — worth noting as a security-relevant hardening option (reduces
risk from a file whose extension/MIME type doesn't match its real
content), though this PR does not itself change any access-control or
validation logic beyond routing.
