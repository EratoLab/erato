# PR #1011: Ask wait-or-background when sending a message with tracked mentions (ERMAIN-640)

- PR: https://github.com/EratoLab/erato/pull/1011
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

First frontend layer of the background-delegation feature (on top of the
now-complete backend stack #1004–#1009): when sending a message that
carries at least one tracked assistant mention (#984/#987), a compact
popover anchored at the send button asks whether the delegated run(s)
should be awaited or run in the background, with the choice carried as
`delegation_run_mode` down the same threading chain #1004 established
server-side. Confirmed by reading the new `DelegationRunModePopover.tsx`
in full — the component matches its own detailed design rationale
precisely:

- **"Enter means wait," confirmed exactly**: the "Wait for the answer"
  row is auto-focused one animation frame after the popover opens
  (deferred by a frame specifically because the portal-rendered rows
  don't exist yet at the moment the panel is positioned), so an Enter
  keypress still arriving from the original send gesture activates the
  safe "wait" choice via native button activation. A panel-level
  `keydown` fallback additionally resolves an Enter that lands with *no*
  row focused (e.g. after clicking the section header) to "wait" — but
  confirmed this fallback explicitly checks the event target isn't
  already inside a `<button>`, so it never double-handles a real button
  activation, meaning arrow-key navigation to "Run in the background"
  followed by Enter still correctly confirms *that* choice rather than
  being silently overridden to "wait." Escape or a click away from the
  popover (`onOpenChange(false)`) calls `onCancel`, which abandons the
  send entirely while leaving the draft untouched in the composer.
- **"Wait" is expressed by omission, confirmed via the callback
  signature**: `onChoose(runMode?: DelegationRunMode)` — the wait row
  calls `onChoose(undefined)`, the background row calls
  `onChoose("background")` — matching #1004's wire design exactly (only
  `"background"` is ever transmitted or persisted; absence always means
  wait).
- **Deliberately not remembered, confirmed via the component's own doc
  comment**: the PR explicitly frames this as asymmetric-risk reasoning —
  a wrongly-backgrounded run produces "a confidently wrong answer built
  without the delegate's result," while wrongly waiting merely costs
  time — so a persisted "always background" preference could silently
  fire and produce a bad outcome with no chance to reconsider, and the
  popover is shown fresh on every mentioned send rather than caching a
  prior choice.
- The affordance is gated on `assistants.enabled && delegation.enabled &&
  allow_background` via a new `ASSISTANTS_DELEGATION_ALLOW_BACKGROUND`
  frontend-environment key (confirmed added to the window-injection
  mechanism, not the OpenAPI spec, matching the pattern of other
  UX-only frontend gates) — so a deployment where the server would
  silently downgrade a background choice back to `wait` (per #1004's
  gate) never shows the popover offering that choice in the first place.
- Per the PR (not independently re-verified given remaining scope): the
  interception point sits in a chokepoint before the submit handler that
  clears the draft, so opening the popover can never destroy an in-progress
  draft; the message-queue path (#840/#841) asks at *queue* time and
  snapshots the chosen mode alongside the queued draft, with the drain
  later sending that snapshot rather than re-asking, and restoring a
  queued draft back to the composer (e.g. via cancel/edit) drops the
  snapshotted mode so the next actual send re-asks fresh; and edit/
  regenerate requests stay silent on this field entirely, relying on the
  backend's existing persisted-mode replay (#1004) rather than
  re-prompting.

## Compatibility and configuration

No new backend configuration (reuses #1004's `allow_background` flag,
now also exposed to the frontend via the new environment key). No
behavior change for any deployment without both `delegation.enabled` and
`allow_background` set — the popover never appears otherwise, and every
send behaves exactly as before this PR.
