# PR #1004: Carry a per-request delegation run mode through submit, edit and regenerate (ERMAIN-634)

- PR: https://github.com/EratoLab/erato/pull/1004
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

First layer of a new "background delegation" sub-stack on top of the
completed delegation feature (#978–#1000). Per the PR, this layer is
"the wire only — nothing behavioural": it adds an optional
`delegation_run_mode: "wait" | "background"` field (default `wait`) to
`MessageSubmitRequest`/`EditMessageRequest`/`RegenerateMessageRequest`
and threads it through persistence, following the same pattern
`mentioned_assistant_ids` (#980) already established. Confirmed by
reading the core logic and its tests in full:

- New `DelegationRunMode` enum (`Wait` default, `Background`) stored on
  `InputParameters.delegation_run_mode`. Confirmed the described
  persistence asymmetry exactly: only `Background` is ever written to
  storage — `Wait` being the default means its absence is
  indistinguishable from an explicit `Wait`, so every pre-existing
  persisted envelope (predating this field) stays byte-identical, with no
  migration or backfill needed.
- Confirmed `resolve_delegation_run_mode`'s precedence and gating logic
  matches the description exactly, via its full unit test suite: an
  explicit per-request value always wins over a persisted one; absent
  both, the default is `Wait`; and a `Background` mode is **downgraded**
  to `Wait` (never rejected with an error) unless the deployment has both
  `assistants.delegation.enabled` and the new
  `assistants.delegation.allow_background` (default `false`) set —
  confirmed both gate conditions are tested independently (either one
  alone being false still downgrades). Confirmed the described rationale
  for persisting the *requested* mode rather than the gate-downgraded
  result: `allow_background` is applied fresh at dispatch/execution time
  on every use, so if a deployment enables background delegation later,
  an edit/regenerate replaying an earlier request's original intent
  correctly picks it up rather than being permanently stuck at whatever
  the gate said the first time.
- Edit resolves as "explicit request value wins, else inherit from the
  message being edited" — confirmed via `get_input_delegation_run_mode_from_message`,
  which mirrors the existing `get_input_mentioned_assistant_ids_from_message`
  pattern exactly — with an explicit `wait` on the edit request correctly
  clearing a previously-inherited `background` value (not merely being
  ignored in favor of the persisted one).
- OpenAPI, generated config reference, the TypeScript client, site
  documentation, and the `erato.template.toml` example block are all
  regenerated; the PR states a config test parses that template block
  against the actual Rust defaults to keep documentation and code from
  drifting (the same pattern already established in #978).

Per the PR, this layer introduces `resolve_delegation_run_mode` and its
tests but doesn't yet wire the resolved mode into actual dispatch
behavior — that's deferred to the next layer in the ERMAIN-633
background-delegation stack.

## Compatibility and configuration

New, optional, default-off config field:
```toml
[assistants.delegation]
allow_background = false  # default; requires assistants.enabled too
```
No behavior change for any deployment — confirmed this PR is genuinely
wire-only, since `resolve_delegation_run_mode` exists and is tested but
isn't yet consumed by the actual delegation dispatch path (deferred to a
later stacked PR). A `background` request without the gate enabled is
silently downgraded to `wait`, never rejected.
