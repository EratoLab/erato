# PR #802: Client tools: portable-name hygiene + offering-loop hardening

- PR: https://github.com/EratoLab/erato/pull/802
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Outlook scheduling and shared mailboxes

## Summary

Backend follow-up from the adversarial review of #801, fixing two latent
config/offering bugs in the #786 `client_tools` foundation before any
deployment enables it. Both confirmed by reading the code:

**Name hygiene.** `ClientToolConfig.name` is now documented and validated
against the portable cross-provider name pattern
`^[a-zA-Z0-9_-]{1,64}$` (OpenAI/Azure and Anthropic reject anything else
at request time — Gemini is laxer, accepting dots/colons up to 128 chars).
A name outside that pattern loads with a **startup warning** (via
`startup_log::warn_preinit`, since `tracing` isn't initialized yet at
config-load time) rather than failing config validation, since a
deliberately Gemini-only deployment may intentionally use a non-portable
name. Separately, `timeout_ms = 0` now hard-fails config validation with a
panic, since every parked call would immediately time out before a client
could ever respond. Confirmed the dotted example name
`outlook.fetch_availability` introduced in #801 is renamed dot-free
(`fetch_availability`) throughout fixtures/tests, while dotted
`client_actions` ids (e.g. `outlook.reply`) are deliberately left alone,
since those are enum values inside `propose_client_action`'s input, never
model-facing tool names themselves.

**Offering-loop hardening**, in a new pure, unit-tested
`select_client_tools` function in `client_tools.rs`: config uniqueness for
client tools is qualified-name-only (`namespace/name`), so two tools can
legitimately share a bare model-facing name across platform-disjoint
packages (e.g. `outlook/ping` and `teams/ping`). Previously both could be
offered in the same request, producing duplicate tool names that a
provider would reject with a 400 from otherwise-valid config, and
iteration order came from an unordered `HashMap`, making both the
offering order and any collision "winner" nondeterministic across
restarts (churning provider prompt-cache prefixes). `select_client_tools`
now sorts allowlist-matched tools by qualified name before selecting,
deduplicating by bare name with a deterministic first-in-order winner, and
classifies every skip reason (`ReservedName`,
`McpCollision { explicitly_selected }`, `DuplicateBareName
{ winner_qualified }`). The MCP-collision case is escalated to
**error-level** logging specifically when the allowlist named the client
tool exactly (not via a wildcard) — confirmed in the code as
`explicitly_selected`, computed by checking whether any allowlist pattern
equals the tool's exact qualified name — since that combination (an admin
explicitly asked for a client tool that an MCP tool of the same name then
silently shadows) is always a config bug rather than an expected
cross-package collision. The per-tool park timeout lookup is also fixed to
resolve from the tools actually offered to the request (threaded through
`PreparedChatRequest`) rather than re-finding the config entry by bare
name afterward, which could previously pick up the wrong `timeout_ms` from
an unrelated, never-offered duplicate elsewhere in config.

## Compatibility and configuration

No new configuration keys (confirmed: the PR notes and the diff show no
config-reference regeneration was needed). Behavior changes for any
deployment already using `[client_tools.tools.*]`:
- A non-portable tool `name` (containing `.`, `:`, or exceeding 64 chars)
  now logs a startup warning instead of loading silently.
- A tool configured with `timeout_ms = 0` now fails to start (previously
  would have loaded and always immediately timed out).
- If two client tools share a bare name across namespaces and both match
  an active allowlist, only one (the alphabetically-first by qualified
  name) is now offered per request, deterministically, instead of both
  potentially being sent to the provider and causing a request-time 400.
