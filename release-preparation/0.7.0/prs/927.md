# PR #927: fix(office-addin): fix background color inconsistency in add-in chat view

- PR: https://github.com/EratoLab/erato/pull/927
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a visible background-color mismatch in the Outlook add-in's chat
view (ERMAIN-549): the header area (dropdown menu + "New Chat" button)
had no explicit background class and inherited `body`'s
`--theme-bg-primary`, while the conversation area below it explicitly set
`--theme-bg-secondary` — two visibly different colors, most noticeable in
dark mode (`#111827` vs `#1f2937` in the default theme, per the PR's own
color table).

**The actual fix differs in mechanism from what the PR description
literally states**, though it achieves the same described visual result.
The description says the fix "adds `bg-theme-bg-secondary` to the outer
wrapper div of `AddinChat`," but the diff (against `AddinChatCore.tsx`,
the post-#922-refactor location of this component) instead applies the
semantic shell-region CSS classes introduced in #852:
`.app-shell-skin` (which resolves to `--theme-shell-app` →
`--theme-bg-primary` in the default theme — unchanged) on the **outer**
wrapper, `.chat-header-skin` (→ `--theme-shell-chat-header` →
`--theme-bg-secondary`) on the **header** sub-div, and `.chat-body-skin`
(→ `--theme-shell-chat-body` → `--theme-bg-secondary`, replacing the
previous literal `bg-theme-bg-secondary` utility) on the **conversation**
sub-div. Confirmed via `globals.css`'s token definitions that
`--theme-shell-chat-header` and `--theme-shell-chat-body` both alias to
`--theme-bg-secondary` in the default theme — so the header and
conversation areas do end up visually consistent (both secondary),
matching the PR's stated goal, even though the outer wrapper itself keeps
the *primary* background (now simply never visible, since both its child
regions opaquely cover it). The net effect described in the issue is
achieved; the specific token/class named in the PR's write-up just isn't
quite what was actually applied — likely because the fix was implemented
using the newer semantic shell tokens (from #852, landed after this PR's
initial description was written) rather than the literal utility class
originally planned.

A new test assertion in `NeutralAddinChatPage.test.tsx` (11 lines) is
added, presumably checking for the presence of these classes — not
independently verified in detail.

## Compatibility and configuration

None. Pure visual bug fix; no configuration or API changes. A custom
theme that sets `--theme-shell-chat-header` and `--theme-shell-chat-body`
to different values than `--theme-bg-secondary` would now see the add-in
header and conversation area follow those distinct tokens correctly
(consistent with the broader #851/#852 theming-hook work), rather than
the header falling back to an unrelated default.
