# PR #1325: Implement audio transcription via OpenAI interface

- PR: https://github.com/EratoLab/erato/pull/1325
- Status: pending
- Category: Features and enhancements
- Theme: Audio

## Summary

No GitHub description beyond a Linear reference (ERMAIN-930); evaluated
from the diff and `configuration.mdx`'s own new documentation. Adds a
new provider kind, `openai_audio_transcriptions`, for chat providers
that implement the dedicated OpenAI-compatible `/v1/audio/transcriptions`
API — distinct from the existing chat-completion-based audio path. A new
~765-line `services/audio_transcription.rs` implements it (uploading
each WAV chunk as multipart form data, appending `audio/transcriptions`
to the configured `base_url`, bearer auth via `api_key` unless an
explicit `Authorization` header is set via
`additional_request_headers`), replacing a large chunk of the previous
genai-chat-based implementation that used to live inline in
`server/api/v1beta/audio_transcription.rs` (265 lines removed there).
Confirmed in `config.rs`: a provider marked
`is_audio_transcription_provider()` (i.e.
`provider_kind == "openai_audio_transcriptions"`) is explicitly filtered
out of both `available_chat_providers()` and `determine_chat_provider()`
— so it's configured like a normal chat provider entry but never appears
in the chat-model picker or ordinary chat routing, only reachable through
the three audio modes' own provider selection
(`audio_transcription`/`audio_dictation`/`audio_conversational`,
explicit `chat_provider_id` or `priority_order` fallback). A new test
(`transcription_providers_work_for_all_audio_modes_but_are_not_chat_models`)
confirms this exclusion for all three audio-mode validation paths at
once. The provider keeps the existing audio modes' chunking, retry, and
hallucination-suppression logic; chat-specific prompts, reasoning
options, and output-token budgets don't apply to this API, per the docs.

## Compatibility and configuration

Additive: a new optional `provider_kind` value for `[chat_providers.providers.<id>]`,
with no change to any existing provider kind's behavior.
```toml
[chat_providers.providers.transcriber]
provider_kind = "openai_audio_transcriptions"
model_name = "whisper-1"
api_key = "your-api-key"
base_url = "https://api.openai.com/v1/"  # optional; defaults to OpenAI's

[chat_providers.providers.transcriber.model_capabilities]
supports_audio_input = true

[audio_dictation]
enabled = true
chat_provider_id = "transcriber"
```
No migration. Existing deployments using a chat-completion-based
provider for audio transcription are unaffected; this is an additional
provider kind, not a replacement.
