# PR #1017: Assistant editor: attach MCP servers with per-user connection affordance (ERMAIN-657)

- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Second layer of the OAuth-MCP-visibility stack (on #1016). Adds a
frontend control for a backend capability that had existed with no UI at
all: assistants already had a validated, generation-enforced
`mcp_server_ids` field restricting which MCP servers an assistant can use,
but nothing in the assistant editor let a user actually set it. This adds
a checkbox list (`McpServerSelector`) fed by `GET /me/mcp_servers`,
surfacing per-user connection state honestly rather than hiding it: a
server the *editing* user personally hasn't OAuth-connected (per #1016's
new classification) stays selectable with a "Requires connection" caption
and a "Connect in Settings" link — since MCP OAuth tokens are per-user,
someone else on a shared assistant may already be connected, so the
editor doesn't prevent attaching a server just because the current editor
hasn't personally authorized it. A genuinely failing/unavailable server,
by contrast, can't be newly attached but stays deselectable if already
present.

Confirmed the two backend correctness touches this required, by full
diff read:

- **The empty-selection-clears-a-restriction fix, confirmed exactly**: a
  new shared `normalize_assistant_id_list` helper (generalizing the
  existing facet-id normalization) collapses an empty `Vec` to `None` on
  both `create_assistant` and `update_assistant`, for both
  `mcp_server_ids` and `facet_ids`. This matters because generation-time
  filtering treats `None` as "no restriction" but `Some([])` as
  "restrict to nothing" — without this normalization, an explicit empty
  selection sent to clear a restriction would instead have permanently
  bricked the assistant into offering zero servers.
- **Migration `0037`, confirmed to correctly backfill only the affected
  rows**: `UPDATE ... SET mcp_server_ids = NULL WHERE mcp_server_ids IS
  NOT NULL AND cardinality(mcp_server_ids) = 0` (and identically for
  `facet_ids`) rewrites only true pre-existing empty arrays, leaving both
  populated and already-`NULL` rows completely untouched — necessary
  because the UI's new "empty selection reads as unrestricted" copy would
  otherwise silently and incorrectly flip meaning for a legacy
  restrict-to-zero-servers row the instant it was saved again.

Per the PR (not independently re-verified given remaining scope): the
editor presents the enforced backend semantics honestly — an empty
selection is described as "all servers," switching to an explicit subset
on the very first pick — and a configured-but-no-longer-listed server id
warns the same way an unavailable facet already does elsewhere in the
assistant editor.

## Compatibility and configuration

New database migration (`0037`, data normalization only, no schema
change — confirmed no revert-data-loss risk since it only collapses an
already-semantically-equivalent empty array to NULL). No behavior change
for any assistant whose `mcp_server_ids`/`facet_ids` were never
persisted as an empty array. New frontend UI surface in the assistant
editor; no change to how generation-time server filtering itself works.
