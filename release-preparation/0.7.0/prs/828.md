# PR #828: Recover the turn when the model calls an unoffered tool (no more empty assistant message)

- PR: https://github.com/EratoLab/erato/pull/828
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a generation-loop bug where a model calling a tool name that wasn't
in the request's tool allow-list (e.g. due to facet/allowlist drift, or a
plain hallucinated tool name) previously hit a `return Err(...)` in
`stream_generate_chat_completion`, killing the entire turn — the user saw
a blank assistant message with no explanation. Per the PR, this was
observed concretely via #819's mid-conversation `outlook_schedule` facet
drop (now fixed separately): history could coach the model to keep
calling `fetch_availability`/`propose_client_action` on a turn that no
longer offered them, but the failure mode itself is general to any
tool/allowlist mismatch.

Confirmed by reading the diff in `message_streaming.rs`: instead of
returning an error that aborts the whole streamed turn, the code now
records an error `ToolUse` content part (status `Error`, with the
rejection message as `output.error`) and pushes a corresponding
`genai::chat::ToolResponse` error back into the conversation, then
`continue`s the loop rather than returning — refusing the individual
*call* while letting the model recover in prose on its next iteration.
This mirrors an existing fallback pattern a few lines below for
client-action proposals, per the PR. A `tool_call_started_at.remove(...)`
timestamp lookup that could now legitimately return `None` (since the
entry may already have been removed) falls back to `now_timestamp()`
rather than panicking or producing a missing timestamp. A model that
keeps re-calling the same refused tool is still bounded by the
generation loop's pre-existing iteration budget, unchanged by this PR.

## Compatibility and configuration

None. Pure bug fix; no configuration keys, API shape, or migration
changes. Behavior change: an assistant turn that calls a
not-currently-offered tool now ends with the model's own recovery text
(having been told the call was refused) instead of an empty message.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the complete `message_streaming.rs` diff
(confirming the exact continue-not-return behavior, the ToolUse/ToolResponse
construction, and the timestamp fallback) and the new integration test,
`test_unoffered_tool_call_recovers_instead_of_killing_the_turn` (confirms
a two-turn mock LLM exchange: turn 1 hallucinates an unoffered tool, turn
2 receives the rejection message and finishes with recovery text, and the
final SSE stream contains no error event). PR description is accurate and
matches the shipped code precisely.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: when the model tries to
call a tool that isn't actually available for the current turn (e.g. due
to a dropped facet or a stale tool reference), the assistant now recovers
with an explanatory response instead of returning a blank message.
