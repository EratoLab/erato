# PR #1077: Let an audience expire: read-time expires_at in the starting-assistant resolver

- PR: https://github.com/EratoLab/erato/pull/1077
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Follow-up to the #1071/#1072/#1073 starting-assistant stack. Adds an
optional `expires_at` to `ExperienceAudience`, letting an admin
time-box an audience pin. Confirmed by reading the complete
`experience_policy.rs` diff and the relevant `starting_assistant.rs`
change:

- **Strict-less-than boundary, confirmed exactly**: `is_active_at(now)`
  is `self.expires_at.is_none_or(|expires_at| now < expires_at)` — a new
  unit test confirms the exact boundary: `is_active_at(expires_at -
  1s)` is `true`, `is_active_at(expires_at)` itself is `false` — matching
  the PR's stated "at the instant itself the audience is inert" precisely.
- **Fall-through, not degrade-to-welcome, confirmed exactly**:
  `match_winning_audience`'s filter predicate becomes `audience
  .is_active_at(now) && audience.subjects.iter().any(...)` inside the
  existing `priority_order.iter().find_map(...)` — so an expired audience
  is simply excluded from matching and the search continues to the next
  `priority_order` entry, exactly as if no subject had matched it. This
  is confirmed structurally distinct from the pre-existing
  degrade-to-welcome-screen behavior, which only fires once a *winning*
  audience is found but its pin then fails to *resolve* (e.g. revoked
  share, stale hub id) — expiry is evaluated before a winner is even
  chosen, so it participates in audience selection itself rather than
  invalidating a selection already made.
- **One clock read per request, confirmed exactly**: `let now =
  Utc::now();` is read once before calling `match_winning_audience`, with
  a code comment stating every audience in the priority order is judged
  against the same instant — avoiding a pathological case where two
  audiences straddling the expiry boundary could be evaluated
  inconsistently within a single request.
- **Expired audiences stay in the document, never filtered at parse or
  load time, confirmed via a dedicated test**: `parse_experience_policy`
  on a document containing an audience with a past `expires_at` succeeds,
  and the audience remains present in both `document.audiences` and
  `document.priority_order` — a code comment states this is deliberate so
  the admin panel can render an expired audience as inert rather than
  simply gone.
- **Timestamp validation and normalization, confirmed via tests**: a
  malformed `expires_at` (a non-RFC-3339 string, a date without a time
  component, or a datetime missing a timezone offset) rejects the whole
  document via `parse_experience_policy`'s `Err` — consistent with
  #1071's existing "malformed policy keeps the previous policy" load-path
  semantics. Two differently-offset RFC 3339 spellings of the same
  instant (`Z` vs. `+02:00`) are confirmed to parse to the identical
  `DateTime<Utc>` value, since comparison is instant-based, not
  string-based.
- Per the PR (not independently re-verified): `expires_at` is
  deliberately per-audience rather than a top-level document setting
  (stated as a design fork noted and deliberately not re-litigated in the
  linked ERMAIN-706 spec); no migration and no `runtime_configuration`
  schema change, since the field is carried inside the existing encrypted
  JSON policy document; no wire-contract change to `GET
  /me/starting-assistant`'s response shape; and a disclosed cross-repo
  hard dependency — the admin panel (a separate repository/release train)
  must ship its own write-path increment before `expires_at` can actually
  be set through the UI, and any hand-written value in the interim is
  stripped by the next panel save (implying the panel's own write path
  round-trips the full document and currently has no `expires_at` field
  to preserve).

## Compatibility and configuration

None. Purely additive, optional field (`#[serde(default)]`, absent means
never expires) on an already-inert-until-consumed document type — no
migration, no API/wire-contract change on the read endpoint. No effect on
any policy document written before this field existed (confirmed via a
dedicated test that such documents deserialize with `expires_at: None`).
