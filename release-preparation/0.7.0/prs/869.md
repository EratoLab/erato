# PR #869: Extend sidecar protocol with mailbox listing and email listing

- PR: https://github.com/EratoLab/erato/pull/869
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Desktop Sidecar for local sources

## Summary

Adds two new JSON-RPC methods to the desktop-sidecar protocol spec
(`desktop-sidecar-protocol/`, no backend/frontend application integration
in this PR — protocol schemas, generated TypeScript types/validators, and
mock test-server support only):
- `outlook.list_mailboxes.v1`: takes no required params, returns a
  `mailboxes` array (each an `OutlookMailbox` record — `id`, `displayName`,
  optional `emailAddress`, optional `profileName` "omitted when the
  platform or standalone store has no profile concept", and `source`, an
  implementation-defined string whose "known values include `pst`, `ost`,
  `macOsProfile`, and `windowsOutlook`" — i.e. covers both raw PST/OST data
  files and the native Outlook installations on both Windows and macOS,
  capped at 1024 items) and a `warnings` array (`OutlookListingWarning`:
  `{message, path?}`, "a local Outlook source that could not be inspected
  without hiding successful results", capped at 1024) for partial-failure
  reporting when some but not all local sources could be enumerated.
- `outlook.list_emails.v1`: takes a required `mailboxId` (a 32-hex-char
  opaque ID "returned by outlook.list_mailboxes.v1"), and returns email
  summaries (`email-summary.schema.json`): `id` (required, source-specific
  stable message identifier), plus optional `subject`, `senderName`,
  `senderEmailAddress`, `receivedAtUnixSeconds`, and `internetMessageId`.

Per the new "§12. Local Outlook actions" section added to `SPEC.md`, this
method surface is deliberately narrow and privacy-conscious: a mailbox's
`id` "MUST be unique among mailboxes advertised by one sidecar runtime,"
SHOULD stay stable across sidecar restarts, and SHOULD be derived from "a
versioned hash of normalized profile, address, source, and private store
identity" — clients must treat it as opaque and never parse it.
`outlook.list_emails.v1` returns **at most 50 of the newest locally
indexed messages**, and both methods return **metadata summaries only** —
per the spec, "neither action returns message bodies or attachments," and
implementations "MUST use read-only storage access." A full enumeration
failure for the active platform's own Outlook profile is a
`sidecar_internal` protocol error, distinct from the partial per-source
`warnings` used when only some local stores are inaccessible.

Both result schemas set `additionalProperties: true`, consistent with the
protocol's forward-compatibility approach documented elsewhere. This is
purely additive protocol surface; the actual sidecar application
implementing these methods against a real local Outlook data source is
not part of this PR — only the deterministic mock `test-server` implements
them (returning one hardcoded mock mailbox and one hardcoded mock email,
and an explicit "Unknown Outlook mailbox" JSON-RPC error for any
`mailboxId` other than the mock's own), for protocol-conformance testing.

## Compatibility and configuration

No configuration keys or migrations; no production runtime behavior
change. This is protocol-specification and generated-client work, adding
two new optional capability methods that a real sidecar (and Erato client
code consuming it) can adopt in later work. Not itself wired into any
Erato frontend/backend feature in this diff.
