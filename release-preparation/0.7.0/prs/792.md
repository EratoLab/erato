# PR #792: Add per-process cache key for theme translations

- PR: https://github.com/EratoLab/erato/pull/792
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes an HTTP caching bug for JIT (just-in-time)-compiled translation JSON
files (`/public/common/locales/<lang>/messages.json`) served by
`backend/erato/src/frontend_environment.rs`. Previously, the `ETag`/cache
headers for all static/non-HTML frontend assets were derived solely from
`ERATO_DEPLOYMENT_VERSION` (`DeploymentVersion(Option<String>)`). When
`translation_po_compilation_mode` is `JustInTime` — i.e. `.po` translation
files are compiled to JSON at request time/startup rather than at build
time — the compiled `messages.json` content can differ between backend
processes running the same deployment version (e.g. after a `.po` file is
edited without changing the deployment version — see the related mirroring
work in #897/#914/#989), yet clients/proxies would treat the cached
response as still valid because the ETag only reflected the deployment
version.

`DeploymentVersion` now carries a second field: a random 16-byte hex string
generated once per process (`random_hex_string()`, via the new `rand`
dependency, `rand = "0.9.4"` added to `backend/erato/Cargo.toml`). A new
`etag_value_for_path` method appends this per-process suffix
(`"{version}-{random_hex}"`) to the ETag only when the compilation mode is
`JustInTime` and the request path is an i18n `messages.json` path
(`is_i18n_messages_json`); for `Precompiled` mode, or any other static
asset path, the ETag remains exactly the deployment version as before,
unchanged.

## Compatibility and configuration

No configuration keys added. No migration. Effect: when
`translation_po_compilation_mode` is `JustInTime` (an existing setting, not
introduced here), locale `messages.json` responses get a distinct ETag per
backend process — cache validation (`If-None-Match` / 304 responses) will
no longer treat two different processes' JIT-compiled translations as
identical just because they share a deployment version, avoiding stale
translations being served from a cache/proxy/CDN after a `.po` file change
that didn't also bump the deployment version. This only affects response
caching behavior; it does not affect translation content itself.
