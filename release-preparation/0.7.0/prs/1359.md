# PR #1359: Resolve EntraID groups on overages (#1359)

- PR: https://github.com/EratoLab/erato/pull/1359
- Status: pending
- Category: Features and enhancements
- Theme: Security / Entra ID

## Summary

No GitHub description beyond "Related Linear issue: ERMAIN-957"; evaluated
from the diff and its own extensive inline documentation. Azure AD/Entra ID
omits the `groups` claim from a token when a user belongs to more groups
than fit (an "overage"), signaling this via `_claim_names.groups` or
`hasgroups: true`. Previously, an overage user's token carried no group
information at all, so `allow-for-group-members` model/MCP-server/facet
permission rules could never match them.

This adds a new `integrations.entra_id.group_overage` resolver
(`backend/erato/src/services/entra_group_overage.rs`, 333 lines + 530 lines
of tests) that, on an overage signal, calls Microsoft Graph's
`/me/transitiveMemberOf` (using a forwarded delegated-`User.Read` access
token in `X-Forwarded-Access-Token`, after verifying Graph's `/me` identity
matches the token's `oid`) to resolve the full membership set — nested
groups, directory roles, and administrative units, as object IDs, matching
oauth2-proxy's own resolution scope. This works **independently** of
`integrations.entra_id.enabled` (the directory-listing feature) — group
overage resolution can be on even when the Entra ID directory integration
itself is off. A token without an overage signal is untouched and never
queries Graph or the cache. Successful lookups cache per-replica for 10
minutes; failures get a 30-second cooldown; both paths share a 3-second
timeout and never return a partial membership list on failure (missing
prerequisites or lookup failure leaves groups empty, so normal
group-authorization then denies access — fails closed, not open).

## Compatibility and configuration

New optional config, enabled by default but inert unless the overage
signal and prerequisites are actually present:

```toml
[integrations.entra_id.group_overage]
enabled = true  # default
```

Requires `integrations.entra_id.auth_via_access_token = true` (startup
validation added: `self.group_overage.enabled && !self.auth_via_access_token`
is rejected with an explicit error) and the proxy forwarding a Graph access
token plus an `oid` claim. No migration; a deployment not hitting the
overage condition (most users, below the group-count threshold) sees no
behavior change. Deployments wanting to disable it can set
`group_overage.enabled = false`, which the docs state still never
interprets overage source identifiers as group IDs even while disabled (so
disabling is a true no-op, not a fallback to a weaker check).

## Release note disposition

Proposed category: Security (authorization-relevant: closes a gap where
overage users silently lost group-based access instead of being correctly
evaluated) or Features and enhancements. Worth a specific mention: users
whose Entra ID group membership exceeds the token's overage threshold now
have their groups resolved via Microsoft Graph for permission evaluation,
instead of being treated as having no groups at all.
