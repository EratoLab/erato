# PR #1072: Serve the per-user starting assistant on GET /me/starting-assistant (ERMAIN-695)

- PR: https://github.com/EratoLab/erato/pull/1072
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Stack 2/3, on top of #1071's experience-policy document type. Adds
`GET /me/starting-assistant`, resolving the org-wide policy into one
answer for the calling user. Confirmed by reading the complete new
`starting_assistant.rs` in full:

- **Correctly placed on the authenticated `/me` tree, confirmed by the
  route's own module doc comment**: stated explicitly as a deliberate
  choice, since resolution depends on the caller's identity/groups, unlike
  the translation-bundle routes which are identical for every user and
  sit outside the authenticated tree.
- **Audience matching uses `MeProfile.groups`, not
  `organization_group_ids`, confirmed exactly**: `subject_matches` for
  `AudienceSubject::OrganizationGroup` compares against
  `identity.groups` (sourced from `AudienceIdentity::from_profile`'s
  `&profile.groups`) — confirmed distinct from the later eligibility
  check.
- **`priority_order`-driven winner selection, confirmed exactly**:
  `match_winning_audience` is `policy.priority_order.iter().find_map(...)`,
  filtering each named audience by whether any of its subjects matches —
  confirmed this makes the `audiences` HashMap's iteration order
  irrelevant to the outcome, consistent with #1071's design.
- **Eligibility is a real, separate re-check using the share-grant
  vocabulary, confirmed exactly**: after a winning audience is found, the
  handler builds `ShareSubject`s from the *matched* subjects specifically
  — `AudienceSubject::OrganizationGroup { group_id }` becomes
  `ShareSubject::organization_group(group_id)` (confirmed this is the
  correctly-distinct "group id as organization_group_id subject" step the
  PR contrasts against the earlier `MeProfile.groups` match), and
  `AudienceSubject::User` is checked under *both*
  `ShareSubject::organization_user`/`ShareSubject::user` forms — then
  calls `share_grant::is_resource_shared_with_any_subject` against the
  resolved live `assistants.id`. A code comment states this check exists
  because a grant can be revoked in Erato with no knowledge of the admin
  panel, and hub grants are recreated per republish against the freshly
  cloned assistant, so a pin valid at write time can dangle by read time.
- **Always 200, confirmed exactly via every failure branch**: no
  experience policy loaded, `assistant_hub` disabled, no matching
  audience, a `get_published_current_version` resolution failure, and
  both the `Ok(false)` (not shared) and `Err` (infrastructure failure)
  outcomes of the eligibility check all return the same `no_pin()` closure
  (`StartingAssistantResponse { starting_assistant: None }` wrapped in
  `Ok`) — confirmed there is no code path in this handler that returns an
  error status for a resolution failure, matching the explicit design
  goal that a pin can never turn into an error page for the users it
  targets.
- **Exactly-one-winner semantics, confirmed exactly**: a code comment
  states directly that if the winning audience's pin fails to resolve,
  the handler degrades to the welcome screen rather than falling through
  to try the next-priority audience — matching the PR's stated design
  that this is deliberate, not a fallback chain.
- Per the PR (not independently re-verified): the new
  `is_resource_shared_with_any_subject`/related helpers in
  `share_grant.rs` (104 lines, not read in full); the resolved wire
  contract's field names (`priority_order`, `entra_group_id`,
  `pinned_assistant_hub_assistant_id`) differing from an earlier ticket
  sketch, with `parse_experience_policy` (from #1071) as the stated
  authority; and a disclosed, explicitly out-of-scope design note left in
  a code comment that the grant-interpretation logic in this handler
  arguably belongs in the PolicyEngine/rego layer rather than Rust, with a
  pointer to `share_grant::is_resource_shared_with_any_subject` for why it
  can't move there yet.

## Compatibility and configuration

None breaking. New authenticated GET endpoint, additive OpenAPI schema
(`StartingAssistantResponse`/`StartingAssistantInfo`). No effect on any
existing deployment, since the previous PR's `experience_policy` field is
`None` unless an admin panel actually writes a policy row — and even then,
this endpoint's existence alone doesn't change any other behavior (per
the PR's stack framing, nothing on the client reads this endpoint yet;
that's PR 3/3).
