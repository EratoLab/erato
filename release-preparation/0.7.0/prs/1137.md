# PR #1137: Add configmap hash based redeployment to Helm chart

- PR: https://github.com/EratoLab/erato/pull/1137
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Applies the standard Helm "checksum annotation" pattern to force pod
restarts when a ConfigMap they consume changes, for both the backend and
oauth2-proxy deployments (`infrastructure/charts/erato/templates/backend-deployment.yaml`,
`oauth2-proxy-deployment.yaml`). Each pod template now always gets
`checksum/config` (and, for the backend, `checksum/metrics-config`)
annotations computed as the SHA-256 hash of the rendered
`backend-configmaps.yaml`/`backend-metrics-configmap.yaml`/
`oauth2-proxy-configmap.yaml` templates. Because these annotations change
whenever the underlying ConfigMap content changes, a `helm upgrade` that
only changes configuration (not the image tag or other pod-spec fields)
now triggers a rolling restart of the affected pods — previously, per the
diff, pod annotations were only rendered *if* `podAnnotations`/
`commonAnnotations` were explicitly set, so a config-only change with no
custom annotations configured would not have forced a redeploy, silently
leaving old pods running stale configuration until they were restarted for
some other reason.

## Compatibility and configuration

No new configuration keys; this changes existing Helm template rendering
behavior. No migration. Behavior change: a `helm upgrade` that changes
only ConfigMap-sourced configuration (e.g. `erato.toml` contents via
values, oauth2-proxy config) will now always trigger a rolling restart of
the backend and/or oauth2-proxy pods to pick up the change, where
previously it may have silently not done so. This is a correctness fix
(config changes should take effect), but means upgrades that used to be a
no-op restart-wise for config-only changes will now cause pod churn.
