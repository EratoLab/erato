# PR #1319: Locate Word paragraphs by exact text when Word gives no paragraph IDs (ERMAIN-927)

- PR: https://github.com/EratoLab/erato/pull/1319
- Status: pending
- Category: Bug fixes
- Theme: Word selection editing

## Summary

Fixes Word paragraph edits and "Show in Word"/Locate on hosts where
`Paragraph.uniqueLocalId` is always null — perpetual/LTSC Office, and
Microsoft 365 with Connected Experiences off (a confirmed upstream
office-js limitation, office-js#4258) — where `isSetSupported` still
reports API 1.6 support, so every edit was previously reported as
"changed" (refused) and nothing could be located, since the old code
matched targets only by that ID via `getParagraphByUniqueLocalId`. The
new `wordParagraphResolver.ts` (confirmed from the diff: pure, no
Office.js dependency, explicitly reusable by the later selection-editing
work) implements a two-path resolution: a surviving ID is decisive but
only if its paragraph's text still matches exactly (so a stale ID whose
text changed is refused rather than silently repointed); when an ID is
missing on either side, the captured span plus up to 3 neighboring
paragraphs per side (`WORD_ANCHOR_CONTEXT`) must occur **exactly once**
in the current document — a second occurrence is refused with a new
`"ambiguous"` rejection status (translated into de/es/fr/pl), since a
copied block and the original are textually indistinguishable. Paragraph
edits and Locate both now read every paragraph's ID and text once and
resolve through the shared resolver instead of the old ID-only lookup;
the in-place writer gains a `no-paragraph-ids` fallback-to-full-document
-import reason, and a new `window.WORD_FORCE_NO_PARAGRAPH_IDS` dev switch
forces no-ID mode for testing on any host.

## Compatibility and configuration

None breaking. On Microsoft 365 hosts where IDs are present, behavior is
unchanged except one improvement: an edit whose target ID disappeared
(paragraph cut-and-pasted, or IDs regenerated) can now succeed via its
unique surrounding text instead of being refused outright. No config
keys. Performance note from the PR itself: applying edits now reads
every paragraph's text (not just the targets'), matching the cost the
capture step already pays on every send — not a new cost class, per the
author.
