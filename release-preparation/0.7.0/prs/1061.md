# PR #1061: Paint the code block surface on the element that clips

- PR: https://github.com/EratoLab/erato/pull/1061
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Follow-up to #1056, fixing two visual issues found in use, plus a
disclosed latent bug found while investigating. Confirmed by reading the
complete `SyntaxHighlightedCode.tsx` and `CollapsibleCodeBlock.tsx` diffs:

- **Corner-clipping fix, confirmed exactly**: `SyntaxHighlightedCode`
  gains a `surface?: "own" | "hoisted"` prop; when `"hoisted"`, a new
  `HOISTED_SURFACE` constant blanks `background: "transparent"`, `border:
  0`, `borderRadius: 0` on the Prism-rendered element (which is
  `min-width: max-content` per the PR, so its own right-hand corners sit
  off-screen once a line is wider than the message column). A new
  `useCodeBlockSurfaceStyle()` hook resolves the same box styling
  (background/border/radius) for an ancestor to paint instead, confirmed
  consumed by `CollapsibleCodeBlock`'s new `surfaceStyle` prop, which is
  spread directly onto the clipping div (the element with
  `overflow-hidden` and the `max-height` clamp) — so the box and the clip
  are now the same element, and the box's corners hold regardless of
  horizontal scroll position.
- **Disclosed latent bug, confirmed exactly**: `useCodeBlockSurfaceStyle`
  collapses `background`/`backgroundColor` into a single `background` key
  (`resolved.backgroundColor ?? resolved.background`) rather than
  emitting both — a code comment states the bug precisely: when a preset
  switch flips which of the two keys is set, React applies the shorthand
  (`background`) and then blanks the longhand (`backgroundColor`) it just
  set in the same style object, since object property order in a style
  merge determines final value and the two can disagree on which one a
  given preset populates — resulting in no background at all in light
  mode for certain preset combinations.
- **Toggle repositioning, confirmed exactly**: the reveal control is no
  longer a full-width footer `<button>` with a bottom border (which
  previously sat below the clipped element, squaring off its bottom
  corners); it is now an absolutely positioned `Button` (`absolute
  bottom-2 left-1/2 -translate-x-1/2`) floating *inside* the same relative
  container as the clipped content — confirmed its icon changed from
  `DisclosureChevron` to a vertical expand/collapse arrow pair
  (`ExpandVerticalIcon`/`CollapseVerticalIcon`), matching the PR's stated
  rationale that the diagonal icon pair was already claimed by the
  media-expand feature (#1053/#1057) and the block grows vertically, not
  diagonally.
- Per the PR (not independently re-verified): `DisclosureChevron` is
  removed from the kit-facing shared surface entirely since the code
  block was its only registry-reachable path in, checked against every
  known consumer (`office-addin`, `component-kit-example`,
  `customer-customisations`, `kit-40955b5f2f-desktop`) with none
  importing it; Mermaid's code view keeps `surface="own"` and is
  otherwise untouched; and the clamped block's horizontal scrollbar
  remains out of reach until expanded, unchanged from #1056.

## Compatibility and configuration

None functionally for end users beyond the visual corner-clipping and
button-repositioning fixes. Shared-surface change for component-kit
consumers: `ExpandVerticalIcon`, `CollapseVerticalIcon`, and
`useCodeBlockSurfaceStyle` join `@erato/frontend/shared`;
`DisclosureChevron` leaves it — per the PR, verified against all known
kit consumers as unused, though this repository cannot independently
confirm no external, unlisted kit imports it.
