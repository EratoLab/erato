# PR #1039: Add chat_providers.providers.<id>.validate_availability

- PR: https://github.com/EratoLab/erato/pull/1039
- Status: pending
- Category: Features and enhancements
- Theme: None

## Summary

Adds a new per-model config flag,
`chat_providers.providers.<provider-id>.validate_availability` (default
`false`), that queries the provider's model-listing endpoint before
exposing that model to users. When enabled,
`AppState::available_models_with_headers_context`
(`backend/erato/src/state.rs`) calls a new
`chat_provider_model_is_available` for each candidate model: it builds a
request to the provider's model-listing endpoint (base URL, request
headers — rendered per-user via the existing header-templating mechanism
used for generation — and API key, per the documentation), parses the
response (`model_names_from_listing_response`, with specific handling for
OpenAI-style and Gemini-style listing formats, including stripping a
Gemini model-name prefix), and checks whether the configured `model_name`
appears in the result. If the model isn't listed, or the check request
fails, the model is silently skipped from the available-models response
(logged at `info`/`warn` respectively) rather than shown to the user as
selectable and then failing when they try to use it.

## Compatibility and configuration

New optional per-model key, defaulting to `false` (no behavior change for
existing configs):
```toml
[chat_providers.providers.<provider-id>]
validate_availability = true
```
No migration. **Performance/reliability note**: this check is made on
every call to the available-models listing (no caching was found in this
diff) — enabling `validate_availability` on a model means every request
that lists available chat models (e.g. populating the model-selector
dropdown) now makes a live, synchronous HTTP request to that provider's
model-listing endpoint, adding latency and a new external-dependency
failure mode to what was previously a purely local/config-derived
response. This is worth confirming with the maintainer, since it could be
a meaningful UX/performance regression for any deployment that enables
this flag on a provider with a slow or occasionally-unreliable listing
endpoint.
