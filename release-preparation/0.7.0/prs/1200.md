# PR #1200: React to a delivered task result without a reload (ERMAIN-779-B)

- PR: https://github.com/EratoLab/erato/pull/1200

- Category: Features and enhancements

## Summary

Final PR of the "Async re-entry" stack, stacking on #1199 (ERMAIN-782,
reviewed above) — the "Stop after 779-B" line in the stack's own cut
list. Closes the remaining live-attach gap: an open chat now streams a
server-initiated reaction turn in place, a delivered result that never
got answered is requested via `/react` (#1197), and a draft blocked by a
409 while a reaction holds the lease is queued instead of shown as an
error. Frontend-only, very large (1875 insertions), with the same
density of self-documented design rationale as the rest of this stack.
Confirmed the central mechanisms by reading the two new small utility
modules in full and the relevant core logic of the large new
`useReactToTaskResult.ts`:

- **`serverAttachKey` normalizes three disagreeing timestamp
  serializations to whole seconds, confirmed exactly**: the function is
  `Math.floor(Date.parse(startedAt) / 1000)`, falling back to a distinct
  `\`${chatId}:enter\`` key when parsing fails — matching "`Math.floor(Date.parse(s)/1000)`
  is the only comparison all three agree on" and "`:enter` is the honest
  identity there" precisely, with a doc comment naming the exact three
  producers and their exact disagreeing formats (client-clock ISO
  milliseconds; server-clock chrono microseconds; the 409 body's
  truncated-to-the-second `to_char` string) matching the PR's own
  enumeration verbatim.
- **Refusals discriminated on `code`, never status, confirmed exactly,
  with the exact stated reason**: the new `readConflictRefusal` in
  `conflictRefusal.ts` best-effort-`JSON.parse`s the error body and
  returns `{ status, code?, reason? }`, with a doc comment stating
  directly "Both of `/react`'s refusals are `409`... the generated
  `ReactToTaskResultSseError` names only `GenerationRunningError` and
  `NothingToReactError` is unreachable through the union. Casting a 409
  to either type would be wrong about half of them" — matching the PR's
  "Refusals are discriminated on `code`, never on the status" section
  precisely, and confirming the parse genuinely falls back gracefully
  for a non-JSON (archived-chat) 409 body.
- **The trigger predicate is the active-thread tip, not "any row,"
  confirmed exactly**: `useReactToTaskResult`'s effect reads `tipId =
  messageOrder.at(-1)`, requires `tip.role === "user"` and
  `tip.task_result` present — directly mirroring the backend's
  `get_active_thread_tip`-based precondition 11 this session confirmed
  in #1197 — matching "The predicate is the tip, not 'some row carries a
  `task_result`'... It is also what makes the trigger self-limiting: once
  the reaction's assistant row lands, that row is the tip and the
  predicate goes false" exactly.
- **`scheduling === "silent"` gate, confirmed exactly, with the exact
  stated reasoning tying it to the server-side gate**: the effect returns
  early `if (delivery.scheduling === "silent")`, with a comment stating
  "The server's `/react` handler has no `scheduling` check, deliberately:
  a client call is a person's request, not a re-application of the task
  author's policy. An automatic fire is not a person's request, so it
  reproduces the gate `deliver_task_result` itself applies" — matching
  the PR's "design decision 2" section verbatim, and consistent with
  #1197's confirmed absence of a scheduling check in the backend route
  itself (the client adds the gate the server deliberately omits, for the
  opposite reason — an automated fire isn't a person's explicit request).
- **One ask per row per session, marked inside the `open` callback —
  confirmed exactly, including the refused-vs-attempted distinction**:
  `attemptKey = \`${chatId}:${tip.id}\`` is checked against an
  `attemptedByRow` set *before* attempting, but is only added to that set
  *inside* `attachToServerGeneration`'s `open` callback — i.e., only once
  a real request is actually being made — with a comment stating "The ask
  is real from here on, so this is where the row is marked — and before
  the socket exists, so the store update that registering it causes
  cannot re-enter this effect into a second request." This precisely
  confirms "a refused ask is retried" (declined before `open` is ever
  called — e.g., because another socket is live — never marks the row,
  so the effect retries later) "while an ask that was made and refused is
  not" (marked the instant the real HTTP request begins, regardless of
  its eventual 404/409 outcome).
- **404 is silent by design, confirmed exactly**: the error handler's
  first check is `if (refusal.status === 404) { ... stay silent ... }`
  with no `logger.error`/`logger.warn` call on that branch — matching "A
  **404 says nothing at all**... surfacing it would paint an error on
  every delivered tip in a deployment running `run_modes = ["wait"]`,"
  and confirmed the handler never calls `setError` anywhere in this file
  (consistent with "this route is silent by design").
- **`already_reacted` suppresses, `tip_moved` kept distinct, confirmed
  exactly**: the reason-`switch` has separate `case "already_reacted"`
  (silent) and `case "tip_moved"` (explicitly commented as "NOT the same
  as `already_reacted`, and deliberately not collapsed into it: the
  backend tests `already_reacted` first") branches — matching the PR's
  stated distinction precisely.
- **`/react` reuses `createSSEConnection` directly rather than the
  generated fetch helper, confirmed exactly**: the POST to
  `/api/v1beta/me/chats/${targetChatId}/react` is made via
  `createSSEConnection` with its own `onMessage: processStreamEvent`,
  `onError`, and `onClose` handlers — not through
  `fetchReactToTaskResultSse` — with a comment explaining the stream
  "opens straight into assistant deltas with no `user_message_saved` and
  no `chat_created`, exactly as `resumestream` does" — matching the PR's
  stated reasoning exactly.
- Per the PR (not independently re-verified given this PR's unusual
  size): the single-socket `attachToServerGeneration` guard mechanism and
  its interaction with `attemptResumeStream`'s `force: true` (the
  "How the single-socket guard works" section, in the 301-line
  `useChatMessaging.ts` diff, not read in full); the two poller-seam
  wiring in `GenerationStatusPoller.tsx` (73 new lines, building on
  #1199's confirmed edge-detection/backstop logic, but this PR's specific
  consumption of it was not traced); the composer-side 409-handoff/draft-
  queueing mechanism via `resolveSessionId`/`handoffSubmitKey` (the
  "Which 409 paths are wired" section); the disclosed fix to the
  reaction socket's `onError`/`onClose` mirroring `attemptResumeStream`'s
  tail (reconciling a dropped stream with no terminal event); and the
  extensive disclosed mutation-checked test suite (`serverAttachKey.test.ts`,
  the "server-started generation attach guard" cases in
  `useChatMessaging.test.ts`, the 17-case `useReactToTaskResult.test.ts`,
  and the `GenerationStatusPoller.test.tsx` additions) and verification

## Release note disposition

Proposed category: Features and enhancements. This PR completes the full
"Async re-entry" stack (#1188-#1200): the model can dispatch a task
without waiting, its result reliably reaches the originating conversation
even across a crash, and now the open conversation streams that result's
reaction turn live, with no reload, including recovering an answer the
server's own attempt had already failed to deliver. The stack's own
stated remaining gap — retrying a task that failed outright or whose
replica died (ERMAIN-783) — remains explicitly out of scope. This PR, not
any single earlier one, is the natural anchor point for the combined
"async delegated tasks" release-note entry, since it is the point at
which the feature (once `delegation.tasks.enabled` and `run_modes`
include `"async"`) is fully live end to end for a user.
