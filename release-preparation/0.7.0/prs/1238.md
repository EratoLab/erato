# PR #1238: Composer: say in advance when delegated work needs approving

- PR: https://github.com/EratoLab/erato/pull/1238
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Closes ERMAIN-847 (one of the three follow-ups filed, not fixed, by PR
#1230's review). `DELEGATION_TASKS_APPROVAL_MODE` had been shipped to the
client since the approval-gating PRs but nothing rendered it, so a user
got no warning before a delegated-task approval interruption landed —
reading as a refusal rather than a disclosed policy. Confirmed the
mode-to-copy mapping and both gating conditions precisely:

- **Mode-to-copy mapping matches the PR's table exactly, word for word**:
  `advisoryFor`'s switch returns exactly the four strings in the PR's
  table — `"always"` → "Any task run for you here needs your approval
  first.", `"plan"` → "If this is split into separate tasks, you will be
  asked to approve the plan before any of it runs.", `"async_only"` →
  "If any of this runs as a background task, you will be asked to
  approve it first.", `"never"` → `null` (renders nothing) — confirmed
  character-for-character against the PR description's table.
- **Both independent gates confirmed exactly, in the order and with the
  exact reasoning the PR describes**: `ChatTaskPlanAdvisory` first
  returns `null` if `!delegationTasksEnabled` (the mode is published
  "ungated" by the backend, so a deployment can configure `mode =
  "always"` while `delegation.tasks.enabled = false` with no dispatch to
  stop), then separately returns `null` if `delegationTasksApprovalMode
  === "async_only" && !delegationTasksAllowAsync` (an `async_only` policy
  is a no-op until `async` is actually an offered run mode) — matching
  "Two independent gates, and the second is the one the issue did not
  call out" and "On a default deployment both are false and nothing
  renders" exactly, since `defaultStaticFeatureConfig` sets both
  `delegationTasksEnabled: false` and `delegationTasksAllowAsync: false`.
- **The missing plumbing is exactly what's added, confirmed exactly**: a
  new `delegationTasksEnabled: boolean` field is added to
  `AssistantsFeatureConfig`, sourced from `Boolean(environment.delegationTasksEnabled)`
  — with a code comment explaining the existing `env.ts` field "carries
  no `assistants` prefix... it is the backend's own
  `DELEGATION_TASKS_ENABLED`," i.e. the environment variable itself
  already existed (per the PR's "no new env var" claim) and this PR only
  adds the missing `FeatureConfigProvider` consumption of it — matching
  "`env.ts` already read `delegationTasksEnabled` but never plumbed it
  into `FeatureConfig`; this adds that — frontend-only, no new env var"
  precisely.
- **The published mode is the global one, never a per-facet override,
  confirmed structurally**: `delegationTasksApprovalMode` is read as a
  single top-level value off `useAssistantsFeature()`, with no facet-id
  parameter or per-facet resolution anywhere in `ChatTaskPlanAdvisory` —
  matching "The published mode is the **global** one... a per-facet
  override is resolved per turn and is deliberately not surfaced."
- Per the PR (not independently re-verified given remaining scope): the
  disclosed seven vitest cases (default deployment, `never`, each active
  mode, `async_only` with async unoffered, tasks-off across all three
  modes — in the 120-line new `ChatTaskPlanAdvisory.test.tsx`, not read);
  the two new Playwright e2e specs
  (`task-approval-advisory.approvals.spec.ts`/`.basic.spec.ts`) and the
  disclosed claim that both were verified against real k3d deployments
  rather than only in CI intent; the Office add-in needing no change
  (plausible given it already seeds `window.DELEGATION_TASKS_ENABLED`
  per the PR's own note, consistent with the shared `env.ts` module, but
  not independently traced); and the disclosed verification (2687 tests
  across 248 files, clean typecheck/lint:strict/prettier).

## Compatibility and configuration

None. Pure frontend addition consuming an already-shipped backend
environment variable (`DELEGATION_TASKS_ENABLED`, confirmed pre-existing
per the PR's own description and this diff only adding its
`FeatureConfigProvider` plumbing). No backend change, no new environment
variable, no migration — confirmed consistent with the all-frontend
changed-files list (aside from one `CHANGELOG.md` line).
