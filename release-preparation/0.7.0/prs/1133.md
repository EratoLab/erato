# PR #1133: Move the sidebar bands and toggles onto SidebarBand and SidebarToggle

- PR: https://github.com/EratoLab/erato/pull/1133
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Eighth (of nine) styling-primitives-consolidation topics, after #1092,
#1096, #1100, #1101, #1105, #1115, #1129 — every one confirmed by this
session to match its description precisely across extensive spot-checks.
Consolidates the sidebar's header/footer bands and its open/close toggle
control (drawn independently by the host sidebar, the hidden-mode
floating trigger, and the add-in's pane trigger/drawer header) onto two
new primitives, `SidebarBand` and `SidebarToggle`. Confirmed by reading
the complete new `SidebarToggle.tsx` in full — the file containing all
three disclosed adversarial-review findings:

- **Finding 1 — the `data-variant` clobber, confirmed exactly**: `Button`
  internally writes `data-variant` before spreading a caller's own props,
  so any prop named `data-variant` passed through would silently
  overwrite `variant="sidebar-icon"` — the exact attribute both shipped
  customer themes key their sidebar-control CSS rules on. `SidebarToggle`
  confirmed emits its own shape distinction as `data-surface={surface}`
  and never touches `data-variant` at all, closing this exact clobber
  risk.
- **Finding 2 — the rotation seam, confirmed exactly**: `iconClassName=
  {expanded && flipOnExpand ? "rotate-180" : undefined}` is passed to
  `Button`'s dedicated icon-class prop, not applied to the button
  element's own className — confirmed this means only the glyph rotates;
  the `CountBadge` (rendered as a sibling via `children`, positioned
  `absolute -right-0.5 -top-0.5` on the outer button) is unaffected by
  the rotation, closing the disclosed bug where a whole-button rotation
  would have flipped the badge upside down and moved it from the
  top-right corner to the bottom-left.
- **Finding 3 — badge-vs-face DOM ordering, confirmed exactly**: `Button`
  only renders its own `aria-hidden` icon span when given an `icon` prop
  (here `hasFace ? undefined : <SidebarToggleIcon />`), and
  `SidebarToggle`'s JSX renders `{children}` (a custom face like the
  sidebar logo) *before* the conditionally-rendered `CountBadge` — so
  when a custom face is present, it is unambiguously the first
  `aria-hidden` node in the button, not the badge. A code comment states
  directly this matters because an e2e geometry probe measures "the
  glyph" as the first `[aria-hidden="true"]` node — confirming the
  disclosed bug (the badge being mistaken for the glyph, misaligning the
  rail centerline measurement against a 16px pill) is structurally
  prevented, contingent on the custom face's own inner icon also being
  marked `aria-hidden` (stated by the PR as fixed in `SidebarLogo`, not
  independently re-verified in this review).
- Per the PR (not independently re-verified given remaining scope): the
  new `SidebarBand.tsx` (52 lines) and the two new unlayered
  `globals.css` channels (`.sidebar-band-flush`, relying on source order
  alone against `.sidebar-section-skin` at equal specificity — described
  as letting the add-in drop an `!important` it only needed because its
  own rule previously came first in source order; and
  `.floating-control-skin`, carrying an opaque base so floating controls
  outside `[data-ui="sidebar"]` don't become translucent-with-no-blur
  under a theme that gives the sidebar shell partial alpha); the removal
  of all four inline `borderRadius` style objects across the family
  (including a fourth, in `OutlookStartViewSwitcher`, that the PR states
  the original plan didn't count); the deliberate decision to keep the
  Outlook start-view switcher as a plain `Button` rather than a
  `SidebarToggle` (reasoned as a view-switcher with no `aria-expanded`
  semantics and a swapping, not flipping, glyph); the add-in drawer
  trigger's `flipOnExpand={false}` (preserving its pre-existing
  non-rotating behavior rather than changing it just because a new
  primitive now supports rotation); `SidebarLogo`'s hover-swap moving
  from React state (`onMouseEnter`/`onMouseLeave`) to a CSS
  `group-hover` rule, stated as what made the aria-hidden-overlay fix in
  Finding 3 possible (the overlay is now always in the DOM at
  `opacity-0`); and the new `sidebarChannels.test.ts` pinning the
  flush-after-skin CSS source order specifically (stated as unobservable
  by any component-level test, and the exact property a future
  `globals.css` reorder could silently regress).

## Compatibility and configuration

None functionally breaking. Three genuine, disclosed bug fixes (the
`data-variant` clobber risk, the rotation-flips-the-badge visual bug, and
the badge-measured-as-glyph e2e geometry bug) ride along with the
consolidation — all three previously shipped green with no test coverage
per the PR's own account, closed here with new dedicated tests. No API
or configuration changes.

## Release note disposition

Proposed category: Bug fixes. Worth a brief mention if any of the three
fixed defects were previously customer-visible: a theme's sidebar-toggle
styling rule could have silently stopped applying under certain prop
combinations (now fixed structurally), and an attention-count badge on
the sidebar toggle no longer risks flipping upside down when the toggle
rotates. The broader sidebar-chrome consolidation itself is internal
styling infrastructure with minimal default-visible effect.
