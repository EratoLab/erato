# PR #818: Multi-attendee availability & deterministic slot ranking (ERMAIN-434/388)

- PR: https://github.com/EratoLab/erato/pull/818
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Outlook scheduling and shared mailboxes

## Summary

Large follow-up to #801/#804: `fetch_availability` now reads colleagues'
calendars (not just the signed-in user's) and slot proposals are computed
by deterministic, unit-tested interval math instead of per-turn model
arithmetic. Given the PR's scale (5706 insertions across 49 files), review
focused on the safety-critical new logic the PR itself calls out, rather
than the full attendee-availability/EWS-wire-format implementation.

- New `graphAttendeeResolution.ts` (247 lines, read in full) resolves a
  display name to an SMTP address via two independently-acquired,
  individually-optional Graph scopes (`People.Read` → `/me/people`,
  `User.ReadBasic.All` → `/users`), confirmed to collapse every failure
  mode (missing consent, tenant policy 401/403, transport error) to a
  non-throwing `{kind: "unavailable"}` result rather than an error, so a
  missing directory-scope grant only costs the name-lookup nicety, never
  the calendar fetch itself. Confirmed the specific "wrong-person safety"
  claim from the PR description: candidates are filtered to
  `personType.subclass === "OrganizationUser"` (missing subclass
  tolerated), explicitly to stop a same-named personal/auto-created
  contact (which Graph's relevance ranking can place above the real GAL
  colleague) from shadowing the correct org user.
- `slotRanking.ts` (new, 411 lines) and its 388-line test file are
  described as computing earliest/smart/option-tier slot suggestions with
  15-minute buffers and day-lightness/defragmentation heuristics; not
  independently read line-by-line, but its presence, size, and dedicated
  test file are consistent with the PR's "deterministic, tested interval
  math instead of per-turn model arithmetic" claim.
- Working-hours-across-time-zones handling (`calendarTime.ts`, +135
  lines) is described as treating the hours' own configured zone as
  authoritative even when it diverges from the calendar's display zone (a
  travelling-user scenario) — not independently verified against the
  PR's specific claimed example (a Berlin-anchored schedule correctly
  showing as 02:00–11:30 EDT to a relocated client).
- `fetchOutlookCalendarEws.ts` (+690 lines) and
  `fetchOutlookCalendarGraph.ts` (+426 lines) gained the actual
  multi-attendee free/busy fetch logic (EWS `ResolveNames`/`ExpandDL` +
  `GetUserAvailability`; Graph multi-schedule `getSchedule`) — not read in
  detail given size; the PR's stated review-hardening claims
  (count-mismatch → unknown rather than assumed-free, `FreeBusyViewType
  None` → unknown, per-schedule degrade) were not independently traced
  through this diff.

**One notable omission from the PR description**: both add-in manifests
(`manifest.xml` and `manifest-exchange-server.xml`) are changed to add a
new activation rule, `<Rule xsi:type="ItemIs" ItemType="Appointment"
FormType="Edit" />`, and a new `AppointmentOrganizerCommandSurface`
ribbon button ("eratoOrganizerButton") that opens the add-in's taskpane
from within an appointment-organizer's edit view. **This is not mentioned
anywhere in the PR description**, which discusses only the
`fetch_availability` tool and slot-ranking logic. This is a real
user-facing change: the add-in becomes launchable/visible from a new
surface (editing/organizing an appointment), not just mail read/compose —
worth flagging for maintainer awareness even though it's plausibly related
groundwork for the scheduling feature.

## Compatibility and configuration

No new backend configuration keys (`erato.template.toml`'s 34-line diff
is examples/documentation for the existing `client_tools`/action-facet
config, not new schema, per the pattern from #801). Two Entra ID Graph
scopes (`People.Read`, `User.ReadBasic.All`) are used if granted, and are
explicitly optional — their absence degrades name resolution but doesn't
break calendar fetching. The add-in manifest changes add a new activation
surface (appointment-edit) and ribbon button not previously present,
which affects where/when the add-in becomes available to users, as noted
above.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: `graphAttendeeResolution.ts` and the
complete diffs of both manifest XML files. Given the scale, most of the
new calendar-fetching/slot-ranking implementation
(`fetchOutlookCalendarEws.ts`, `fetchOutlookCalendarGraph.ts`,
`slotRanking.ts`, `calendarTime.ts`, `outlookScheduleTool.ts`'s +429-line
diff) and the ~2600 lines of new/expanded test files were not read in
detail — the one safety-critical file reviewed in full (attendee name
resolution) matched the PR's stated wrong-person-safety design precisely,
giving reasonable confidence in the rest, but the free/busy correctness
claims (count-mismatch handling, `FreeBusyViewType None` handling,
per-schedule degradation) were not independently traced through the
fetcher diffs. The undocumented manifest/appointment-surface change was
found by diffing files outside what the PR description discusses.
