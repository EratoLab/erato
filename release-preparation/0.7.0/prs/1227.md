# PR #1227: Add global log filter that sanitizes URLs

- PR: https://github.com/EratoLab/erato/pull/1227
- Status: pending
- Category: Security
- Theme: Observability / Langfuse tracing

## Summary

Adds a global, always-on log-output sanitizer that strips credentials and
query parameters from every HTTP(S) URL appearing anywhere in a log
event — not just explicitly-logged URLs, but also "opaque dependency
errors and span fields" (e.g. an HTTP client library's error message that
happens to embed a URL with an API key in its query string). New
`backend/erato/src/telemetry/log_redaction.rs` (298 lines) implements a
`RedactingFormatter` that wraps the existing `tracing_subscriber` format
layer for both `Plain` and `Json` logging formats
(`backend/erato/src/telemetry.rs`), post-processing the fully rendered log
line (text) or the parsed JSON value's every string field/key, replacing
each detected `http(s)://...` URL via `sanitize_url`.

`sanitize_url`'s design is fail-closed: it clears the username, password,
query string, and fragment (dropping *every* query parameter, deliberately
not maintaining a denylist of "secret-looking" parameter names — the
comment states "drop every query parameter, including unknown names,
rather than maintaining a denylist of secrets"), and returns `<redacted>`
outright for anything that fails to parse as a URL or isn't `http`/`https`
— never falling back to emitting the raw, unredacted input. The formatter
itself is similarly fail-closed: if the underlying event formatting or
JSON re-parsing fails, the entire log line is replaced with "Log event
omitted: formatting failed" rather than risk emitting anything
unsanitized, and `log_internal_errors(false)` prevents `tracing_subscriber`
from falling back to an unredacted internal-error log line. This is
applied unconditionally to all logs, in both formats, with no
configuration flag to disable it. Extensively unit tested, including
adjacent/nested URLs without whitespace separators (e.g. inside serialized
JSON) and formatter-failure fallback behavior.

## Compatibility and configuration

No configuration keys — this is always active for every log line the
backend emits, in both `Plain` and `Json` logging formats. No migration.
Behavior change: any credentials or query-string data that may have
previously leaked into logs via a URL (e.g. an OAuth token in a query
parameter, a signed URL, or an API key passed as a query param by a
misbehaving library) is now stripped before the log line is written —
this could make some log lines less informative for debugging (URLs lose
their query string entirely) in exchange for materially reducing the risk
of credential leakage through logs, which is a meaningful, universally-applicable
security hardening with no opt-out.
