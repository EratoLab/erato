# PR #1369: Add support for stateless MCP (#1369)

## Summary

No GitHub description beyond "Related Linear issue: ERMAIN-801"; evaluated
from the diff and its documentation addition. Adds support for the
stateless Streamable HTTP MCP protocol variant (per the docs, the
`2026-07-28` MCP protocol revision), as an alternative to the existing
session-based ("legacy") Streamable HTTP initialization.

Confirmed via `config.rs`: a new `protocol_mode` field (`auto` (default) /
`legacy` / `stateless`) is added to `McpServerConfig`. In `auto` mode, Erato
probes for the stateless protocol first and falls back to legacy
initialization for older servers; per the docs, authentication failures,
rate limits, and modern-protocol errors do **not** trigger a fallback
downgrade (only an actual stateless-protocol absence does). `protocol_mode
= "stateless"` is rejected at startup when combined with `transport_type =
"sse"` (stateless requires Streamable HTTP) — confirmed via the new check
added to `validate_mcp_server_ids`.

Per the detailed documentation addition (not independently traced through
the session-management/caching implementation itself): legacy servers keep
per-chat, per-auth-context cached sessions as before; stateless servers
instead cache only HTTP connection pools and tool metadata (no idle MCP
sessions or notification streams), with tool-list caching honoring the
server's own `ttlMs` (capped at 24h, defaulting to 30s if omitted, 0
disabling reuse), and explicitly-public tool lists shareable across
authentication contexts while private lists stay credential-specific. A
failed refresh never replaces a valid cached catalog with an empty one;
expired catalogs aren't served on error either. Progress notifications may
not surface for stateless calls (the response helper drains them before
the first result). A new mock-server surface
(`/mcp/legacy/file`, `/mcp/stateless/file`, `/mcp/dual/file`, and matching
auth/progress/file-output/deep-research routes) exercises both protocol
variants explicitly in tests.

## Compatibility and configuration

New optional per-server key, defaulting to `auto` (probes for stateless,
falls back to legacy — a behavior change in *mechanism* for
`streamable_http` servers, but not in observable behavior for a server
that only supports the legacy protocol, since auto-probing falls back
transparently):

```toml
[mcp_servers.<server-id>]
transport_type = "streamable_http"
protocol_mode = "auto"   # "auto" (default), "legacy", or "stateless"
```

Startup-rejected combination: `protocol_mode = "stateless"` with
`transport_type = "sse"`. No migration; `legacy` can be pinned explicitly
for troubleshooting compatibility per the docs.
