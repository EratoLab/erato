# PR #1249: Add disabled durable client-operation foundation

- PR: https://github.com/EratoLab/erato/pull/1249
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

A large (6,521 insertions, 35 files), explicitly disabled architectural
foundation: a generic mechanism letting a client tool survive longer
than the in-memory execution window by escalating to a persisted,
account-scoped "durable operation" that can be claimed and resumed on
any backend replica. The PR is explicit that this is "the neutral
prerequisite for reshaping #1237 (ERMAIN-862) [the native local-evidence
feature reviewed above], not the sidecar integration itself," and its
closing line states "No merge or deployment performed." Given this
framing — matching the pattern of #1237, which builds directly on this
PR — this review verified the two most concrete, security-relevant
structural claims rather than tracing the full claim/continuation/replay
pipeline:

- **The governing flag defaults to disabled, confirmed exactly, and
  traced to its origin**: `ClientToolsConfig.durable_operations_enabled:
  bool` is added here with `#[serde(default)]` on a `Default`-deriving
  struct, resolving to `false` — this is the same flag this session
  already confirmed (consuming, not originating, side) in PR #1237's
  review; this PR is where it's actually defined. Matches "Default
  `client_tools.durable_operations_enabled = false`; the production
  registry is empty" exactly.
- **The persisted request shape structurally cannot hold a composed
  `ChatRequest` or credentials, confirmed exactly — a directly checkable
  structural property, not merely a stated policy**: the new migration
  0051's `client_operation_attempts.request` column is `jsonb NOT NULL`,
  but what's actually serialized into it is `OperationRequest` — a
  narrow, purpose-built struct with named fields limited to identity and
  policy metadata (`attempt_id`, `operation_id`, `kind`, `realm`,
  `chat_id`, `message_id`, `tool_call_id`, `account_id`, `binding`,
  `base_revision`, `consent`, `expires_at`) plus one `input: Value`
  field for the specific tool call's own arguments. There is no field
  for a conversation history, system prompt, model configuration, or any
  credential/token — the shape is categorically incapable of holding a
  full composed chat request, directly substantiating "Never persist a
  composed `ChatRequest` or authentication credentials."
- Per the PR (not independently re-verified given this PR's scope and
  its own "not for merge" framing): the full claim/result/cancel/
  continuation API surface (`client_operations.rs`, 406 new lines, and
  the 1,068-line `message_streaming.rs` diff implementing the escalation/
  resume logic); the account/device/realm/host binding enforcement and
  claim-token fencing described in detail; the idempotent-identical-
  result-retry and fenced-supersession/cancellation/stale-write
  guarantees; the "Confirmed review fixes" section describing three
  rounds of review findings and their fixes (synthetic-kind offer-hook
  policy, fixed per-call validation feedback for invalid fast results,
  continuation re-matching tools by qualified identity) and a fourth
  round covering consent/withdrawal/crash-accounting gaps (routing
  `Ask`/native-consent kinds to the durable inbox, sharing authorization
  checks across claim and first-result acceptance, persisting
  charges/ordinals/expiry by logical call id to prevent double-charging
  on recovery — disclosed as caught by a fault-injection test); the
  disclosed design-record limitations (continuation stays detached after
  a park, fixed attempt/claim durations, UUID pagination restarting each
  sweep, a noted Word-style multi-call-turn gap); the `700`-line
  `client_operations/store.rs` beyond the one struct inspected; the
  `2,193`-line new `client_operations.rs` integration test file; and the
  extensive disclosed validation (backend 1,399/1,399, a combined run
  with #1250 passing 260 selected tests, focused HTTP/integration
  coverage across eleven named scenarios, frontend foundation validation
  unchanged at 2,734/2,734, and the migration's disclosed deploy/verify/
  revert/redeploy testing against a disposable database).

## Compatibility and configuration

Additive and explicitly inert by design. New config key
`client_tools.durable_operations_enabled`, confirmed to default to
`false`; "the production registry is empty," meaning no actual client
tool kind is wired to use this mechanism yet (per the PR, #1237's local-
evidence feature is the intended first consumer, itself also disabled).
New migration 0051 (additive table only). The PR's own framing is
explicit that no merge or deployment is requested, pending the ordered
follow-up work it describes (rebasing and shrinking #1237 onto this
foundation).

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read: the relevant `ClientToolsConfig` diff in
`config.rs` (confirming the flag's default-off origin), the new
migration 0051's deploy SQL (confirming the `client_operation_attempts`
table shape), and the `OperationRequest` struct definition in
`client_operations/mod.rs` (confirming its narrow, credential-free,
non-`ChatRequest` shape). Given this PR's scope and its own "not for
merge" framing, this review did not attempt to trace the claim/binding/
continuation/replay implementation, the extensive integration test
suite, or the interaction with PR #1250 (not itself in this evaluation's
scope). **Given this foundation underlies the security-sensitive native
local-evidence feature reviewed in PR #1237, both warrant coordinated,
dedicated security review before any future enablement.**

## Release note disposition

Proposed category: Features and enhancements, but **not release-note-
worthy in this release**, per the PR's own explicit "No merge or
deployment performed" and the fact that the flag it introduces defaults
to disabled with no production consumer registered. Exclude from this
release's notes.
