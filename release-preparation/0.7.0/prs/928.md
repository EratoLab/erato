# PR #928: fix(eml-preview): recover PDF MIME type from extension when email declares octet-stream (ERMAIN-550)

- PR: https://github.com/EratoLab/erato/pull/928
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes clicking a PDF attachment inside an `.eml` email preview triggering
a browser download (of a filename-less bare UUID) instead of showing the
inline PDF preview. Root cause, confirmed by reading the code: some email
clients send PDF attachments with `Content-Type: application/octet-stream`
rather than `application/pdf`; `EmlPreview` created the attachment's
`Blob` typed exactly as declared, and browsers only render a `blob:` URL
inline in an `<iframe>` when its MIME type names a renderable format —
`application/octet-stream` forces a download instead, and since blob URLs
carry no filename metadata, the downloaded file has no extension and a
UUID-only name.

Fix, confirmed via full diff: a new `recoverMimeType(mimeType, filename)`
helper upgrades a generic `application/octet-stream` type to a specific
one derived from the file's extension (`.pdf` → `application/pdf`, `.eml`
→ `message/rfc822`), falling through to `octet-stream` unchanged for any
other extension or when the declared type is already something more
specific. This is applied consistently at all three places that
previously did the bare `mimeType.length > 0 ? mimeType : OCTET_STREAM`
fallback: `attachmentBlob()` (so the actual `Blob` object gets the correct
type, fixing the inline-vs-download decision), the direct-attachment path
in `EmlPreviewBody`, and the nested-thread-message attachment path in
`EmlThreadBody` — confirmed both call sites are covered, not just the
top-level one.

## Compatibility and configuration

None. Pure frontend bug fix; no configuration or API changes. Behavior
change: a PDF (or nested `.eml`) attachment mislabeled as
`application/octet-stream` by the sending email client now correctly
opens in the inline preview instead of downloading as an unnamed file.
