# PR #868: Show per-chat generation status in the history sidebar

- PR: https://github.com/EratoLab/erato/pull/868
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Large feature (ERMAIN-475, 4285 insertions across 53 files): the chat
history sidebar now shows each chat's generation status (Running /
Finished / Error) so a long-running generation can be left and picked up
later. Given the scale, review focused on the two most correctness-
critical mechanisms — the backend lease/heartbeat/reap system and the
frontend's poll-only-when-needed claim — both confirmed by reading the
code directly.

**Backend**, confirmed via `sqitch` migration `0030` and
`background_tasks.rs`:
- New `chats` columns (`active_generation_id`, `generation_state`,
  `generation_started_at`, `generation_heartbeat_at`,
  `generation_ended_at`) plus a partial index on rows with a non-null
  `generation_state`, exactly as described.
- `BackgroundTaskManager::start_task` claims a per-generation lease (a
  fresh `Uuid` per generation, written as `active_generation_id`) via a
  best-effort DB write — a failed status write is logged and swallowed,
  never fails the generation itself.
- `remove_task` now takes the `generation_id` it's removing and only acts
  if the currently-tracked task for that chat still matches it — confirmed
  this fixes a genuine pre-existing race: without this gate, a
  slow-to-finish superseded task could remove/mark-terminal a newer
  replacement generation that had already taken over the same chat slot.
- A constructor-spawned maintenance loop (interval from
  `GenerationStatusConfig`, confirmed config-driven) does three things
  each tick: heartbeats every currently-tracked task (`generation_heartbeat_at
  = now()`, re-asserting `active_generation_id` from the in-memory map,
  which the comment notes is necessary since two same-chat starts could
  otherwise race their initial claim), reaps rows whose heartbeat is older
  than `stale_after_secs` into `errored`, and clears terminal rows past
  the retention window. The first tick fires immediately (no initial
  delay), confirmed matching the description's "deploys have no graceful
  shutdown" rationale for an immediate startup reap pass.
- `TaskOutcome::{Completed, Errored}` maps an aborted generation to
  `completed` and a wrapper error or stream `Error` event to `errored`
  (not independently traced through the full outcome-mapping call sites,
  but the enum and its two variants are confirmed to exist and match the
  description).
- `GET /me/generating` (not read in full) is described as returning
  running chats plus recently-ended ones (60s retention) with an outcome
  and resolved title in one response, so a client can distinguish
  completed from errored and patch the row title in the same update.

**Frontend**, confirmed via the new `GenerationStatusPoller.tsx` (122
lines, read in full):
- The `/me/generating` poll is driven by `useQuery`'s `refetchInterval`
  computed from `pollInterval()`, which returns `false` (disabling the
  query entirely) whenever zero chats are currently tracked as running in
  `generationStatusStore` — confirmed this really does produce zero idle
  network requests, not merely a very long interval.
- An adaptive interval not mentioned in the PR description at all: a
  "young" generation (started under 2 minutes ago) polls every 3 seconds;
  otherwise every 10 seconds — a reasonable refinement, but the
  description simply states "with backoff," so the specific two-tier
  scheme was verified directly rather than assumed.
- `patchTerminalChats` merges a terminal (non-`running`) entry's
  server-resolved title and clears `active_generation_started_at` on the
  matching cached recent-chats row in one query-cache update — confirmed
  via full read, including its careful no-op short-circuit (returns the
  same object references when nothing actually changed, avoiding
  unnecessary re-renders).

Not independently verified in this review, given the scale: the
`generationStatusStore.ts` state machine itself (295 lines: seeding from
list rows/local streams/poll responses, tombstoning consumed/unknown
states, the "seed-grace guard" for a just-started follow-up turn), the
per-row sidebar indicator UI (`ChatHistoryList.tsx`'s 118-line diff:
colored dot, `motion-reduce` fallback, aggregate badge, debounced
`sr-only` live region), the untitled-chat placeholder-from-first-words
behavior, the mock-llm-server's new `delayed error` prompt, or the ~1400
lines of new backend/frontend/E2E test coverage (`generating.rs` alone is
763 lines).

## Compatibility and configuration

New database migration (`0030_add_generation_state_to_chats`, additive
columns + index, includes a revert script) — requires a migration run on
upgrade. New `[generation_status]` config section (heartbeat/stale-after
intervals, confirmed config-driven rather than hardcoded, per
`config.rs`'s 49-line diff, not read in full) documented in
`configuration.mdx`. `RecentChat` gains a new
`active_generation_started_at` field (running-only, per the PR — terminal
states are deliberately ephemeral client-session state, not persisted
across a refresh). New `GET /me/generating` endpoint.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the `0030` migration SQL, the core
lease-claim/heartbeat/reap/cleanup logic in `background_tasks.rs`
(confirming the race-fix rationale for the generation-id-gated
`remove_task`), and the complete `GenerationStatusPoller.tsx`. Given the
PR's large scale, most of the frontend state-management store, the UI
indicator components, and the extensive test suites were not read in
detail — the two mechanisms verified are the ones most likely to hide a
subtle correctness bug (a distributed lease/heartbeat system, and a
polling-efficiency claim), and both matched their descriptions precisely.

## Release note disposition

Proposed category: Features and enhancements. Worth a clear mention: the
chat history sidebar now shows each chat's generation status (running,
finished, or errored) with a live indicator, so a user can start a long
generation, navigate away, and see when it completes without having to
keep that chat open.
