# PR #1149: Switch MCP servers off per chat from the composer connectors

- PR: https://github.com/EratoLab/erato/pull/1149
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Stacked on #1148. Adds `chats.disabled_mcp_server_ids text[]` (migration
`0044`, default `{}`) — a per-chat set of MCP servers a user has switched
off — using the same carrier pattern (`MessageSubmitRequest` seed for a
new chat, whole-list-replace `PUT` for an existing one, inherited by
delegated children) #1148 established for the write toggle. Confirmed by
reading the complete `filter_mcp_tools_by_disabled_servers` function and
its integration into `resolve_generation_mcp_tools` in `message_streaming.rs`:

- **Strictly subtractive, and runs last, confirmed exactly**:
  `filter_mcp_tools_by_disabled_servers` is confirmed called after
  `filter_mcp_tools_by_write_access`'s result, and its own doc comment
  states precisely: "Strictly subtractive: it runs last, so it can only
  narrow what the policy, the assistant and the facets already allow" —
  matching the PR's stated enforcement ordering (deny → write-suppressed
  → server-disabled). A dedicated test
  (`disabled_servers_lose_every_tool_and_other_servers_keep_theirs`)
  confirms every tool on a disabled server's id is dropped while a
  same-named tool on a *different*, non-disabled server is untouched —
  correctly scoping the subtraction per-server rather than per-tool-name.
- **Reported disabled-server ids correctly scoped to the generation's
  actual authority, confirmed exactly matching review note 2**: the
  `disabled_server_ids` collected for reporting on `ChatMessage`/the
  completion event are filtered through
  `effective_server_filter.as_ref().is_some_and(|in_scope|
  in_scope.contains(*server_id))` before being sorted/deduped and used —
  so a server id in the chat's disabled list that the current
  generation's policy/assistant/facet scope wouldn't have reached anyway
  is silently excluded from the report, matching the PR's stated review
  note exactly: "Only ids inside the generation's scope are reported;
  unknown or out-of-scope ids are silent no-ops."
- Per the PR (not independently re-verified given the very large
  remaining scope): the migration `0044` itself (additive, default `{}`,
  no behavior change for existing chats); the collision-snapshot staying
  upstream of this filter (so a disabled server cannot free its tool
  names for a same-named client tool to claim, extending #1147's
  collision-snapshot fix to this third filtering stage); the
  continuation-refusal priority order stated as denied → write-suppressed
  → server-disabled → retryable outage; the new composer server-toggle
  rows joining the Connectors section (`useChatDisabledMcpServers.ts`,
  162 lines, optimistic whole-list PUT with a new-chat seed, locked until
  the chat row is read) and the new `McpDisabledServersNotice.tsx` (49
  lines) surfacing the reported servers on the affected message; the
  add-in's parallel send-chain wiring; and the disclosed review-round
  fixes (a `toggleServer` bug that could re-enable servers by PUTting
  from an unloaded base state; a forgotten shared-component-registry
  regeneration; a vacuous test assertion) plus the disclosed known
  ergonomic debt that `get_or_create_chat` and the kit's `onSendMessage`
  have both grown to nine positional parameters across this stack
  (#1148/#1149/#1150-equivalent), with bundling the new-chat seeds into
  one object flagged as an obvious follow-up not done here.
- **Disclosed review note 1, a real but accepted edge case, per the
  PR**: subtraction happens *after* discovery, so a server the user
  disabled is still actually connected to during discovery for that
  generation and may simultaneously appear in
  `mcp_servers_needing_auth`/`mcp_servers_unavailable` for the same
  generation — the PR states the frontend kit resolves this by letting
  `mcp_servers_disabled_by_user` win client-side when both apply to the
  same server, not independently re-verified in the frontend code.

## Compatibility and configuration

New migration `0044` (additive column, default `{}` — confirmed no
behavior change for existing chats). New request/response fields
mirroring #1148's pattern. A user can now switch off specific MCP
servers for a chat from the Connectors section, on top of the per-chat
write-operations toggle from #1148.
