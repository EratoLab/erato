# PR #1247: Precompile prompt injection patterns at startup and reuse

- PR: https://github.com/EratoLab/erato/pull/1247
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Guardrails and prompt-injection filtering

## Summary

Fixes a performance issue in the prompt-injection guardrail (from #789)
where each configured regex pattern was compiled fresh
(`Regex::new(&pattern.pattern)`) on every single chat request that needed
scanning, rather than once. `backend/erato/src/services/prompt_guardrails.rs`
introduces `CompiledPromptGuardrails`, built once from
`GuardrailsConfig` at startup (via `AppState`, per the 5-line
`state.rs` diff) and reused across all requests — regex clones from the
compiled set share compiled code and only allocate independent search
scratch space per use. A misconfigured/invalid regex pattern now fails
fast at backend startup (`invalid_regex_fails_during_startup_compilation`
test) instead of only failing (or silently degrading?) the first time a
request happened to select that pattern.

`scan_chat_request_for_prompt_injection` is now `async` and, per the code
comment "parsing structured tool results and matching must run off the
async worker," moves the actual pattern-matching work onto a blocking
task (consistent with the same CPU-bound-work-off-the-async-runtime
pattern applied to policy evaluation in #1124 this cycle). Confirmed by a
new test, `scan_yields_to_the_blocking_pool`. Scanning behavior itself
(which content parts are scanned, tag/ID selection, exclude-list
handling from #789) is unchanged — this is purely a compile-once/run-off-runtime
performance and startup-validation fix, not a behavior change to what
gets flagged.

## Compatibility and configuration

No configuration keys or migrations; existing `guardrails.prompt_patterns`
and `filter_input_prompt_injection` settings behave identically at the
detection level. Startup behavior change: a deployment with an invalid
regex in `guardrails.prompt_patterns` will now fail to start at all
(previously it may have failed later, only when a request happened to
exercise that specific pattern) — this is a stricter, fail-fast validation
that surfaces a misconfiguration immediately rather than intermittently in
production.
