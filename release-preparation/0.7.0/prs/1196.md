# PR #1196: Recover a stranded async task result without a user request (ERMAIN-781-A)

- PR: https://github.com/EratoLab/erato/pull/1196
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stacks on #1192 (ERMAIN-780, reviewed above), adding the backstop sweep
that was 780's documented, accepted gap: a crash or rolling deploy
between an async task's delivery claim and its reaction could otherwise
strand that delivery indefinitely. This PR adds a 5-minute `CleanupWorker`
tick that requeues stale claims and delivers anything stuck `pending`
purely via SQL — no LLM turn, no lease, no request context. Unusually
detailed PR description with its own "Design notes a reviewer will ask
about" and "Review fixes in commit 5" sections; this review prioritized
verifying the two disclosed review-commit bug fixes (both genuine
concurrency hazards) and the actor-naming collision fix, given their
safety stakes, over exhaustive coverage of the ~2300-line diff:

- **Actor-registry-collision fix, confirmed exactly, matching every
  stated detail**: a new `WorkerNames` struct derives
  `"{supervisor_name}.cleanup_worker"`/`"{supervisor_name}.cleanup_worker_cron"`
  from the supervisor's own name; `WorkerSupervisorArgs.workers:
  Option<WorkerNames>` is `None` whenever the supervisor itself is
  unnamed (confirmed in `manager.rs`: `supervisor_name.as_deref().map(WorkerNames::derived_from)`),
  and `pre_start` returns an idle state with **no spawned children at
  all** the instant `workers` is `None` — checked *before* even the
  `cleanup_enabled`/`any_route_enabled` gate — matching "an **unnamed**
  supervisor starts no timed children at all... that, not a uniquified
  suffix, is what keeps many managers collision-free" exactly, including
  the stated test-process cron-leakage concern.
- **`CleanupTickJob` carries its worker name as a field, built through one
  shared constructor, confirmed exactly**: `cleanup_tick_job(&names)`
  builds `CleanupTickJob { worker_name: names.cleanup_worker.clone() }`,
  used both by the supervisor's own scheduling call and (per the PR,
  confirmed structurally since the function is `pub`) by a test driving
  the same construction — matching "`CleanupTickJob` carries the worker
  name as a field so a rename is a compile error" and the "Review fixes"
  item "`CleanupTickJob` is built by `supervisor::cleanup_tick_job`, which
  the test now drives."
- **`ActorFailed` restart comparison moved to the derived name, confirmed
  exactly**: the panic-restart handler now checks `name ==
  names.cleanup_worker` (read from `state.cleanup`) rather than the
  literal `"cleanup_worker"` — matching "The `ActorFailed` arm's string
  compare had to move in the same commit... a literal there would
  silently stop matching and a panicked worker would never be restarted."
- **Retention and delivery-backstop gating split exactly as described,
  confirmed exactly**: the spawn condition is `!config.cleanup_enabled &&
  !config.delegation.any_route_enabled()` — using `any_route_enabled()`
  rather than inspecting `tasks.run_modes` directly — with a code comment
  giving the identical reasoning as the PR body: "facet overrides can
  widen list-valued keys at request time, so the config read here is not
  the last word... The sweep self-gates cheaply instead." `CleanupWorkerArgs`
  gains its own `cleanup_enabled: bool` field (distinct from the
  supervisor-level spawn gate), consistent with "The tick's two halves
  have different gating now."
- **Review fix: the delivery-state write is now fenced on `delivery_id`,
  not only on state, confirmed exactly, with the exact stated hazard**:
  `set_delivery_state_in`'s `UPDATE` gains `AND
  ("assistant_configuration" #>> '{provenance,result_delivery,delivery_id}')
  = $3` unconditionally (alongside the pre-existing state check and the
  optional `claimed_by` token check, now `$4`), with a new doc comment
  explaining precisely: "A branch requeue... mints a new `delivery_id`
  and returns the row to `pending`... a caller holding a copy read before
  that would otherwise match on the state alone and write the stale
  envelope back over it, silently swallowing the redelivery the user's
  branch asked for." This is a genuine, independently-verifiable
  correctness fix (without it, a state-only fence genuinely would let a
  stale write clobber a concurrent #1190-style branch requeue).
- **Review fix: the free-origin gate is now atomic with lease acquisition
  via a per-origin advisory lock, confirmed exactly, reusing the exact
  expression #1188 uses**: before evaluating whether the origin is free,
  the sweep's per-child transaction runs `SELECT
  pg_advisory_xact_lock(hashtextextended($1::text, 0))` on
  `origin_chat_id` — the identical key-and-hash expression this session
  confirmed in #1188's `claim_lease_in_txn` for the live delivery path's
  own lease CAS. A code comment states the exact race this closes: "a
  user turn that takes the lease after the gate was evaluated would
  anchor its message before the sweep's insert existed and write a
  sibling of it" — matching "A user turn taking the origin's lease after
  the gate was evaluated... The child transaction now takes
  `pg_advisory_xact_lock(...)` — the same key and expression
  `claim_lease_in_txn` uses — before any origin decision" precisely.
- **No `SELECT ... FOR UPDATE`; the free-lease test is an `EXISTS` using
  `generation_unfinished_condition`, confirmed exactly, with the stated
  reasoning**: the sweep's claim `UPDATE` gates on `EXISTS (SELECT 1 FROM
  chats o WHERE o.id = $4 AND o.archived_at IS NULL AND NOT {unfinished})`
  where `unfinished = generation_unfinished_condition("\"o\"", 5)` — no
  row lock anywhere in this statement — matching "The heartbeat is one
  batched statement over all of a replica's running chats, so a row lock
  on one of those rows blocks the whole statement" and the PR's claim
  that `rg "FOR UPDATE" backend/erato/src` finds only comments (not
  independently re-run, but consistent with the SQL read).
- **Rotation (phase 9b) is a separate, committed, similarly-fenced write,
  confirmed exactly**: when the claim fails (zero rows), the transaction
  rolls back and a *separate* rotation write bumps `attempts` and
  `updated_at`, fenced on `pending` *and* the read `delivery_id` — with a
  comment giving the identical fairness reasoning as the PR body ("a
  deferred child that wrote nothing... sorts to the front of every future
  pass... would hide row 201 forever") and the identical delivery-id-fence
  reasoning as the main fix above.
- Per the PR (not independently re-verified given this PR's unusual
  size): commit 3's `build_result_envelope`/`child_answer_for_delivery`
  becoming generic over `ConnectionTrait` (so the sweep can pass its
  `&DatabaseTransaction`) — plausible and consistent with the sweep code
  read, which does call these through a `txn`, but the generic signatures
  themselves were not inspected; the full phase-(i)/phase-(ii) sweep scan
  logic beyond the per-child claim transaction shown above (the
  `pending`-scan query, `SWEEP_BATCH_LIMIT = 200`, and the one-pass-not-two-ticks
  claim); the "deliberately left `claimed_by`/`claimed_at` in place" by
  phase (i) diagnostic-trail claim; the `result_missing` append-not-close
  behavior for a run whose answer row is gone; the five "Deliberately out
  of scope, flagged" items (S7/S13/S14, `child_archived`'s missing
  frontend label, the omitted `pg_try_advisory_xact_lock` leader
  election) — all self-disclosed scope boundaries, not verified against
  code since they describe what was *not* built; the 10-line
  `config.rs` comment-only change; `cron_jobs.rs` (15 lines); and the
  disclosed verification (1194 passed/4 skipped `cargo nextest run
  --retries 2`, clean clippy, clean `gen-openapi`/`gen-config-reference
  --check`, config-reference coverage at its 98-undocumented budget).

## Compatibility and configuration

No route, wire schema, OpenAPI/codegen regeneration, frontend file, or
sqitch migration changes, confirmed consistent with the changed-files
list (backend-only, no `config_reference.json`/`openapi.json` diffs). The
only `erato_config` change is a comment narrowing `cleanup_enabled`'s
documented scope to the retention half specifically — no behavioral or
schema change to that key. The delivery backstop sweep itself runs
regardless of `cleanup_enabled` (confirmed above) but is a no-op scan
when no async task was ever dispatched, since nothing is ever in
`pending`/`claimed` state in that case.

## Release note disposition

Proposed category: Features and enhancements (backend reliability
infrastructure for the still-off-by-default async delegated-task
feature introduced in #1188-#1192). Not independently release-note-worthy
on its own — no route, wire, or config-visible change — but materially
strengthens the async-tasks feature's eventual release note: a crash or
rolling deploy can no longer silently lose a finished task's result,
since a 5-minute sweep recovers any stranded delivery (though as the PR
candidly discloses, the user still needs a fresh request to actually see
the recovered result — full "proactive" recovery is a later PR, #1197,
per the stack's own sequencing).
