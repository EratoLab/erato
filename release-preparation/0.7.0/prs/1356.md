# PR #1356: Add support for `authorization_params` for MCP server Oauth2 flow (#1356)

## Summary

No GitHub description beyond "Related Linear issue: ERMAIN-956"; evaluated
from the diff. Adds a new optional `authorization_params` map to an MCP
server's OAuth2 authentication config, letting a deployment inject literal,
non-secret query parameters (e.g. `audience`, `prompt`) into the OAuth
authorization URL some providers require.

Confirmed exactly via the `erato_mcp_oauth` diff: a `PROTECTED_AUTHORIZATION_PARAMS`
allowlist-of-exclusions (`response_type`, `client_id`, `client_secret`,
`redirect_uri`, `scope`, `state`, `code_challenge`, `code_challenge_method`,
`resource`, `response_mode`, `request`, `request_uri`) is checked
case-insensitively; any configured parameter matching one of these protected
names, or an empty key, is dropped with a `tracing::warn!` (value never
logged) rather than silently applied or rejecting startup. `replace_authorization_params`
then removes any existing query pairs with the same key from the real
authorization URL and appends the configured values, leaving the SDK's own
flow parameters (PKCE, state, scope, etc.) untouched. A new unit test
(`authorization_params_replace_endpoint_pairs_and_keep_flow_parameters`)
confirms this exact replace-not-append behavior, including correct URL
encoding of special characters in a configured value.

## Compatibility and configuration

New optional map, empty by default (no behavior change for existing MCP
OAuth2 server configs):

```toml
[mcp_servers.<server-id>.authentication]
mode = "oauth2"
authorization_params = { audience = "https://api.example.com/", prompt = "consent" }
```

No migration. A configured key matching a protected OAuth flow parameter
name is silently ignored (with a warning log), not rejected at startup —
confirmed via the filter function; this is a deliberate design choice per
the code comment ("Protected OAuth flow parameters are ignored with a
warning"), not a bug.
