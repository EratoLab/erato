# PR #1218: Allow client tool calls to attach files to response

- PR: https://github.com/EratoLab/erato/pull/1218
- Status: pending
- Category: Features and enhancements
- Theme: MCP controls

## Summary

Extends Erato's "client tools" mechanism (browser/frontend-executed tools,
e.g. Outlook add-in actions) so a client-side tool executor can return
files alongside its JSON result, which get attached to the assistant
message as if they were regular uploads. Per the new documentation, a tool
executor returns
`{ ok: true, result: {...}, fileUploadIds: [file.id] }`, having already
uploaded the file(s) through the ordinary files API; the client then sends
these IDs in a new `file_upload_ids` field of
`POST /api/v1beta/me/messages/clienttoolresult`
(`backend/erato/src/server/api/v1beta/file_resolution.rs`,
`message_streaming.rs`, `client_tools.rs`). The backend re-checks access
authorization on each referenced file, extracts its text for model
context, and attaches only authorized files to the assistant message
(documents get rich previews, images render inline); attachments persist
across chat reloads. Safety/robustness details, all backend-enforced:
duplicate IDs are ignored; at most `min(frontend.max_files, 20)` unique
files are considered per result (bounding attachment count even if a
malicious/buggy client sends more); a file whose text extraction fails or
hits its length limit is still attached, with the tool result noting the
content is unavailable/truncated; an error or rejected/failed-validation
tool result never attaches files; and IDs nested inside the arbitrary
result JSON (as opposed to the dedicated `file_upload_ids` field) are
never treated as attachments — preventing a client from smuggling
arbitrary file references through untrusted result content.

## Compatibility and configuration

No new configuration keys; this extends the existing `client_tools.*`
mechanism and its pre-existing `frontend.max_files` limit (reused as a
cap, not introducing a separate one). No migration. Purely additive to
the client-tool-result API shape (`file_upload_ids` is a new optional
field) — existing client tool executors that don't return files are
unaffected. Per the existing docs note quoted in this diff's context,
deployments should "deploy the backend, frontend, and rebuilt add-in
together before enabling these tools; older backends do not gate optional
tools or resolve their attachment references" — i.e. this specific
capability requires the matching frontend/add-in version.
