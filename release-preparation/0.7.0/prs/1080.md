# PR #1080: Make MCP server configuration reloadable

- PR: https://github.com/EratoLab/erato/pull/1080
- Status: pending
- Category: Features and enhancements
- Theme: MCP controls

## Summary

Extends the admin-panel-driven configuration hot-reload mechanism from
#991 (which handled translation overrides) to also cover MCP server
configuration: `mcp_servers`, `mcp_servers_global`, and
`mcp_server_permissions` can now be changed at runtime without a backend
restart. New `McpRuntimeConfig` (`backend/erato_config/src/config.rs`) is
a narrow, separately-deserializable subset of `AppConfig` covering just
these three sections; `from_toml_sources` re-parses the mirrored TOML
config sources (both the backend's own `erato.toml` files and any
admin-panel-provided TOML overrides, both mirrored into
`runtime_configuration` per #897) through the same config-parsing/env-var
pipeline used at startup (`app_environment_source`, factored out for
reuse), then re-runs the existing `mcp_server_permissions`/
`mcp_servers_global` validation.

On each reload (triggered by the same Postgres `NOTIFY
configuration_changed` mechanism from #913/#991),
`ReloadableAppState::load` compares the newly-parsed `McpRuntimeConfig`
against the previous one; if unchanged, nothing happens. If changed, it
calls `McpServers::reconfigure(&mcp_config)`
(`backend/erato/src/services/mcp_session_manager.rs`), which — per its new
test `reconfigure_reports_only_servers_with_effective_session_changes` —
compares old vs. new per-server config and invalidates/recreates sessions
only for servers whose *effective* configuration actually changed
(unrelated servers keep their live sessions), returning the list of
affected server IDs for logging.

## Compatibility and configuration

No new top-level configuration keys — this changes *how* existing
`mcp_servers.*`/`mcp_servers_global.*`/`mcp_server_permissions.*` settings
can be updated (live, via the admin-panel/runtime-configuration mechanism)
rather than adding new settings. Only takes effect when
`runtime_configuration.enabled = true` (from #897/#913). No migration
beyond what #897/#991 already introduced. Behavior for deployments not
using this mechanism (the default) is unchanged — MCP config still only
takes effect from `erato.toml`/env vars at startup.
