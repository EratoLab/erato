# PR #910: Add sidecar.progress.v1: poll-based incremental progress delivery (ERMAIN-534)

- PR: https://github.com/EratoLab/erato/pull/910
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds a new `sidecar.progress.v1` method to the `desktop-sidecar-protocol`
spec (protocol-only; no erato backend/frontend/add-in application code in
this repo is touched, confirmed by diff stat — all changes are under
`desktop-sidecar-protocol/`). Since the protocol has no server-to-client
push, observing a long-running sidecar request's progress becomes a
client-driven poll: `sidecar.progress.v1 { requestId }` returns `{ state,
trace }`, where `trace` is the same append-only step log a final result
may embed. Confirmed by reading `client.ts` in full:

- The reference client's `invoke()` gains an `InvokeOptions.progress`
  parameter (`{ onProgress, intervalMs? }`, default 1000ms poll interval,
  minimum 50ms). When set, a background poll loop starts immediately
  alongside the actual request and continues until the request settles,
  at which point one final poll runs so the caller always observes the
  terminal progress state (when the sidecar still remembers the request).
- **Confirmed the described isolation guarantee precisely**: `#pollProgress`
  never throws — any error (including a validation failure of the
  response) is swallowed, and polling never touches the client's own
  readiness/connection state, so a failing or misbehaving progress poll
  can never affect the request it's merely observing.
- Confirmed graceful degradation for version skew: if a sidecar
  advertises the `sidecar.progress.v1` capability but doesn't actually
  implement it (answers `-32601` "method not found"), the client sets a
  session-scoped `#progressUnsupported` flag and stops polling entirely
  for the rest of that session, rather than repeatedly erroring.
- Per the PR (not independently verified against the spec/schema files):
  an unknown request ID is a *successful* response with `state: "unknown"`
  rather than an error; each poll returns the whole bounded trace log (no
  cursor/pagination), and clients are expected to apply steps by
  `sequence` number (last one wins), so a log delivered incrementally
  across several polls and the same log delivered once at completion
  render identically.
- `diagnostics.echo.v1` gains an optional bounded `delayMs` parameter
  (reporting the pause as a `delay` trace step) specifically so the new
  progress-poll and existing cancellation mechanisms can be exercised
  against a controllable, artificially-delayed request in tests — not
  independently verified.
- Spec package version bumped to `0.1.9`; new shared `local-trace`/
  `local-trace-step` JSON schemas, generated TypeScript types/validators,
  and a large new conformance fixture (`progress-poll.json`, 160 lines)
  are added — not read in detail.

A client that never sets `InvokeOptions.progress` is entirely unaffected
by this change, per the PR and confirmed structurally (polling only
starts when explicitly requested).

## Compatibility and configuration

None for the erato backend/frontend/add-in in this repository — this PR
only changes the standalone `desktop-sidecar-protocol` package. No erato
server or web/add-in behavior changes as a direct result of this PR;
consuming this new capability from the actual Outlook add-in or sidecar
implementation is not part of this diff.
