# PR #1241: Persist Outlook source references on uploaded files

- PR: https://github.com/EratoLab/erato/pull/1241
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

The persistence step following #1239 (the standalone protocol contract
reviewed above): `/me/files` now accepts and stores the
`OutlookFileProvenance` JSON shape that PR defined, returning it from
every relevant file response. Confirmed every concrete claim precisely:

- **New nullable JSONB column, confirmed exactly**: migration 0050 is a
  single `ALTER TABLE file_uploads ADD COLUMN outlook_provenance jsonb;`
  with no `NOT NULL` — matching "stores it in a nullable JSONB column"
  exactly.
- **64 KiB limit, confirmed exactly, down to the literal constant**:
  `MAX_OUTLOOK_PROVENANCE_BYTES: usize = 64 * 1024` (= 65,536 bytes),
  enforced while reading the multipart field's chunks, returning `413
  Payload Too Large` the instant the accumulated bytes would exceed it —
  matching "The metadata field is limited to 64 KiB" precisely.
- **Must occur exactly once, before any file parts, confirmed exactly**:
  the handler's multipart loop checks `if outlook_provenance.is_some() ||
  !uploaded_files.is_empty() || field.file_name().is_some() { return
  Err(BAD_REQUEST); }` upon encountering an `outlook_provenance` field —
  rejecting a second occurrence, one that arrives after any file has
  already been processed, or one disguised as a file (`field.file_name()`
  present) — matching "must occur once before the file parts" exactly.
- **Applies to every file in the request, confirmed exactly**: the parsed
  `outlook_provenance` value is cloned and passed to *every* file's
  creation call inside the same multipart loop, for both the
  chat-associated and standalone-upload code branches — matching
  "applies to all files in that request" and "Each origin keeps the
  document's identity separate from its containing message" (the stored
  value is the same `OutlookFileProvenance` shape #1239 defined, with its
  confirmed origins-array/document-vs-topLevelParent structure intact end
  to end).
- **Invalid metadata rejected, confirmed exactly**:
  `OutlookFileProvenance::parse(&bytes)` is called before the bytes are
  stored anywhere, mapping any parse failure to `BAD_REQUEST` — matching
  "Invalid or unsupported metadata is rejected."
- **Legacy `external_id_ews_id` remains fully independent, confirmed
  exactly**: the query-parameter-sourced `external_id_ews_id` is still
  read and passed through unchanged, entirely separately from the new
  `outlook_provenance` value, on every file-creation call — matching
  "Legacy uploads and `external_id_ews_id` retain their existing
  behavior" and "The original EWS ID query parameter remains
  independent; a containing email's ID never replaces it."
- **Returned from every stated response surface, confirmed exactly, at
  all five call sites**: `outlook_provenance: file_upload.outlook_provenance`
  is added to `FileUploadItem` (both the chat-upload and standalone-upload
  construction sites), `AssistantFile` (in `frequent_assistants`),
  the chat-history message-assembly path (`assemble_chat_messages_response`),
  `get_file`, and `link_sharepoint_file_impl` — matching "returns it from
  upload, file lookup, chat history, and assistant-file responses"
  precisely, confirmed at every one of the named surfaces rather than
  just some of them.
- **Proper TypeScript nullability via the established pattern, confirmed
  exactly**: `FileUploadItem.outlook_provenance` carries both
  `#[serde(skip_serializing_if = "Option::is_none")]` and
  `#[schema(value_type = Option<...>, nullable = false)]` — the same
  dual-attribute pattern this session has now confirmed repeatedly
  (PRs #1191, #1201) is required in this codebase to avoid a
  `field?: null | undefined` dead-end type in the generated TypeScript
  client.
- Per the PR (not independently re-verified given remaining scope): the
  full `OutlookFileProvenance` Rust struct and its validation logic in
  `outlook_provenance.rs` (253 lines total; only the module's top-level
  constant and `parse` function signature were confirmed, not its full
  field-by-field validation against the protocol schema's constraints
  confirmed in #1239's review — e.g. the hex-pattern check on
  `outlook_entry_id`/`outlook_store_id`); the claim that Rust validation
  was tested against the canonical protocol schemas/fixtures; the 313-line
  expanded `api/files.rs` integration test coverage (chat/standalone
  uploads, file lookup, chat/assistant reloads, all shared provenance
  fixtures, multiple origins, legacy metadata, multipart limits/order,
  denied access); the migration's disclosed deploy/verify/revert testing
  including legacy-NULL and JSON-identifier round-tripping; and the
  disclosed validation results (backend 1,367/1,367 with 4 skipped across
  three lint configurations; frontend 2,687/2,687 with 11 skipped, with
  one disclosed flaky PDF-suite WASM-loading issue specific to a clean
  temporary checkout that passed on rerun in the main checkout).

## Compatibility and configuration

Additive database migration (sqitch 0050), nullable column, no backfill
(confirmed: "There is no backfill or inference of a parent from the
scalar EWS ID" in the PR's own description, consistent with the
migration adding only a new nullable column with no data migration
statement). No config keys. Existing uploads and clients that don't send
`outlook_provenance` are completely unaffected — the field is optional
on both the request and every response shape. This PR is explicitly
scoped as upload-API/persistence only: "Collecting/sending provenance
from the frontend, sidecar native navigation, host routing, and Open in
Outlook UI remain separate follow-ups."
