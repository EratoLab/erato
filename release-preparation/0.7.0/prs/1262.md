# PR #1262: Returning to assistant landing page clears active chat

- PR: https://github.com/EratoLab/erato/pull/1262
- Status: pending
- Category: Bug fixes
- Theme: None

## Summary

Fixes a bug where navigating back to an assistant's "new chat" landing
page (i.e. `chatId` becomes `null`/absent) could leave stale streaming
state from a just-created chat attached to the fresh composer. New
`releaseNewChatStream` action in `frontend/src/hooks/chat/store/messagingStore.ts`
detaches the temporary "new chat" stream key
(`NEW_CHAT_STREAM_KEY`) alias from the real chat ID it had been pointing
at, freeing that temporary key up for the next new-chat composer, while —
per the code comment — "keep[ing] the real chat's buffers and connection
so its generation can continue in the background" (i.e. a still-generating
chat the user navigated away from isn't killed, only detached from the
now-stale temporary key). `useChatMessaging.ts` calls this from a new
`useLayoutEffect` (chosen specifically to run *before paint*, per the
comment, "so the old stream cannot render or disable it, even if it is
still running") whenever `chatId` becomes falsy and either the previous
render had a real `chatId` (returning to the landing page) or the
temporary key is still aliased to a chat that was never recorded as
"newly created" (covering a provider remount after navigation already
consumed the created ID).

## Compatibility and configuration

None. Purely a frontend bug fix for chat-composer state cleanup; no
configuration, API, or migration changes. A chat that was still generating
when the user navigated back to the landing page continues generating in
the background (not aborted) and can be resumed by navigating back to it.
