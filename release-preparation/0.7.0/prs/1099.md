# PR #1099: Fully wire up tool progress updates and show progress message

- PR: https://github.com/EratoLab/erato/pull/1099
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: MCP controls

## Summary

Implements live progress reporting for in-flight MCP tool calls, end to
end. Previously, the MCP client transport used an `EmptyClientHandler`
("doesn't handle any client-side notifications") — meaning any MCP
`notifications/progress` message sent by a server during a long-running
tool call was simply dropped, even though a `progress_message` field
already existed on the frontend's tool-call data model (rendered as a
muted inline label next to the tool name in `ToolUseStep.tsx`, per this
diff) with nothing populating it from real progress events.

`backend/erato/src/services/mcp_transports.rs` replaces `EmptyClientHandler`
with a new `ProgressClientHandler`: each MCP connection owns its own
per-connection `ProgressToken` → notification-channel registry (not a
global namespace), with a `ProgressRegistration` guard that deregisters a
token automatically on drop. `backend/erato/src/services/mcp_session_manager.rs`
(127-line diff) and `mcp_manager.rs` (21-line diff) wire this registry
into the tool-call execution path so a call registers for progress
updates on its token before invoking the tool and forwards received
`ProgressNotificationParam` messages. `backend/erato/src/server/api/v1beta/message_streaming.rs`
(350-line diff) threads these progress updates into the generation loop,
emitting `StreamingEvent::ToolCallUpdate`/SSE events with an updated
`progress_message` as they arrive, so the UI can show live status text
(e.g. "Searching...", "50% complete") while a tool is still running,
rather than only a static "running" spinner. A new
`backend/erato/src/services/mcp_progress_tests.rs` (229 lines) covers this
behavior.

## Compatibility and configuration

No configuration keys or migrations. This only affects the display of MCP
tool calls that use MCP's standard progress-notification mechanism; MCP
servers not emitting progress notifications are unaffected (no
`progress_message` shown, matching prior behavior). No breaking change —
this is purely additive, surfacing previously-discarded information.
