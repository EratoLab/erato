# PR #1071: Add experience policy document as a runtime configuration source type (ERMAIN-694)

- PR: https://github.com/EratoLab/erato/pull/1071
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Stack 1/3 for an audience-resolved start screen (an admin can pin a
starting assistant for an Entra group; nothing reads this document yet —
purely plumbing to carry it into the running backend). Confirmed by
reading the complete new `experience_policy.rs` and the relevant
`runtime.rs` diff:

- **New `runtime_configuration` source type, confirmed**: a third
  `source_type` (`experience_policy`) alongside the existing
  `erato_toml`/`translation_po`, requiring no migration since the table
  already has the needed columns.
- **`priority_order` as a separate ordered key, confirmed exactly**:
  `ExperiencePolicyDocument.priority_order: Vec<String>` is distinct from
  `audiences: HashMap<String, ExperienceAudience>`, with a doc comment
  stating the same rationale the PR describes — a `HashMap`'s iteration
  order is not deterministic across restarts, so "first match wins" can
  never live inside the map itself, mirroring the existing
  `chat_providers.priority_order`/`language_detection_priority` pattern.
- **Pin resolves through `assistant_hub_assistants.id`, confirmed
  exactly**: `ExperienceAudience.pinned_assistant_hub_assistant_id: Uuid`
  carries a doc comment stating precisely why — `clone_source_assistant`
  mints a fresh `assistants.id` on every republish, so a pin stored
  against that id would go stale silently, and resolution to the live id
  is deferred to read time (the next PR in the stack).
- **Structural validation beyond what serde expresses, confirmed
  exactly**: `parse_experience_policy` rejects a `priority_order` entry
  naming an unknown audience, a duplicate `priority_order` entry, an
  audience with zero subjects, and a subject whose id is present but
  blank (whitespace-only) — matching the doc comment's stated scope
  (unknown `subject_type` and a missing id are already rejected by serde
  itself via the tagged enum). Confirmed `audiences.is_empty()` in
  `priority_order` is allowed (staged rollout), per the doc comment.
- **Both disclosed load-path departures from the ticket, confirmed
  exactly via `runtime.rs`**: `load_experience_policy` returns `Ok(None)`
  when zero rows exist (a valid, complete "no policy" state — the admin
  panel unpins by deleting the row) but returns `Err` when rows exist but
  none matches the live filename slug (`experience/policy.json`) — the
  caller in `ReloadableAppState::load` treats *any* error from
  `load_experience_policy` (this includes both the foreign-filename case
  and a decrypt failure, since `app_state.decrypt(&row.config)?`
  propagates through the same function) by logging via `tracing::error!`
  and falling back to the previously-held policy captured before the
  reload began, rather than propagating the error and failing the whole
  `load()` call — confirmed this means neither a stray/foreign-named row
  nor a decrypt failure can take the app down or silently unpin the
  entire org; a cold start with no prior policy degrades to `None`.
- **Filename contract, confirmed exactly**: `experience_policy_slug`
  accepts only `experience/<slug>.json` where `<slug>` is non-empty,
  contains no `/`, and is alphanumeric/`-`/`_` only — rejecting path
  traversal (`../experience/policy.json`) and nested paths. A companion
  `experience_policy_filename` builder round-trips through the same
  parser so writer and reader cannot drift, confirmed via a dedicated
  test.
- Per the PR (not independently re-verified): the multiple-matching-rows
  case (no DB uniqueness constraint on `(source_service, source_type,
  source_filename)`) logs a `tracing::warn!` and deterministically uses
  the first match rather than erroring; `AudienceSubject`'s three variants
  (`Organization`/`OrganizationGroup`/`User`) mirror the existing
  `share_grants` subject-type vocabulary exactly, deliberately
  identity-provider-agnostic; and `pg_notify('configuration_changed')`
  needed no change since it already reloads the whole bundle.

## Compatibility and configuration

None. Purely additive: a new, currently-inert runtime-configuration source
type with no read path yet (explicitly deferred to PR 2/3). No migration,
no behavior change for any existing deployment — this PR carries data
into memory that nothing consumes.
