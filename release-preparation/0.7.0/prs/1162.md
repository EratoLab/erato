# PR #1162: Accept the delegation status vocabulary and the `delegate_task` tool name (ERMAIN-763)

- PR: https://github.com/EratoLab/erato/pull/1162
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

First of five stacked PRs (Level D "Dynamic Delegated Tasks") preparing
the frontend to accept a new `delegate_task` route and its status
vocabulary *before* any backend change emits them, so the backend PR that
follows can ship without a coordinated frontend deploy. Confirmed by
reading the complete `delegationEnvelope.ts` diff and the relevant
`localTraceStore.ts` change in full:

- **Status vocabulary widened exactly as described**: `RUN_STATUSES`
  (renamed from `SETTLED_STATUSES`) now includes `queued`, `working`,
  `input_required`, and `dispatched` alongside the existing settled
  values (`completed`, `failed`, `cancelled`) — confirmed matching the
  PR's stated list exactly.
- **`timeout` retained as legacy tolerance, not dead code, confirmed
  exactly**: `timeout` stays in `RUN_STATUSES`, with a code comment
  stating precisely why: the backend is retiring it in favor of
  `cancelled` + `reason: "timeout"`, but already-persisted parts written
  before that change replay forever, so removing it would break
  historical trace rendering.
- **The admission gate genuinely widened, not just the label set,
  confirmed exactly**: the early-return guard in `parseDelegationEnvelope`
  changes from checking `delegateChatId === undefined &&
  !SETTLED_STATUSES.has(status)` to `delegateChatId === undefined &&
  !RUN_STATUSES.has(status)` — so a status-only part with `status:
  "queued"` and no `delegate_chat_id` at all is now admitted (previously
  it would have fallen through to plain tool-call rendering, per the
  PR's stated bug) — a code comment confirms the exact rationale: "a slot
  queued behind `max_parallel` has not launched anything yet."
- **New fields read exactly as described**: `reason` (a closed
  vocabulary per the doc comment, but rendered verbatim if unrecognized —
  "so a newer backend degrades to readable"), `parentToolCallId` (from
  `record.parent_tool_call_id`), and `delegateChatId` now falling back to
  `record.child_run_id` when `record.delegate_chat_id` is absent — a code
  comment states this dual-read exists so "neither writer can leave the
  run unopenable," consistent with two envelope-writer generations
  coexisting during the rollout.
- **Discrimination by tool name, never by envelope shape, confirmed
  exactly**: `DELEGATE_TASK_TOOL_NAME = "delegate_task"` and
  `DELEGATION_TOOL_NAMES = new Set([DELEGATION_TOOL_NAME,
  DELEGATE_TASK_TOOL_NAME])` with a new `isDelegationToolName` helper —
  the parsing/admission logic itself never branches on whether
  `assistantName` is present, matching the PR's stated design that a
  task-route step must not be distinguished by a missing assistant name,
  since a task child speaking under the default `inherit` persona
  legitimately carries an assistant name just like an @-mention run.
- **`SIDECAR_TRACE_RESULT_TOOLS` gains both routes, confirmed exactly**:
  the set now spreads `...DELEGATION_TOOL_NAMES` instead of the single
  `DELEGATION_TOOL_NAME` — matching the PR's stated fix that without
  this, a `delegate_task` step would render an empty nested trace after a
  page reload (the persisted-trace-replay path this set gates).
- Per the PR (not independently re-verified given remaining scope): the
  `DelegationStep.tsx` diff (125 lines) and `ToolUseStep.tsx` diff (9
  lines) presumably consuming the widened vocabulary and the new
  `isDelegationToolName` discrimination to route a `delegate_task` call
  through the delegation-specific step renderer; and the relevant
  `message_streaming.rs` backend diff (20 lines) in this PR (minimal,
  consistent with the stated "frontend learns the vocabulary before
  anything emits it" framing).

## Compatibility and configuration

None breaking. Purely additive acceptance of a wire vocabulary nothing
currently emits (the actual backend change is a separate, later PR per
the stack framing) — no behavior change for any currently-running
generation. Existing `delegate_to_assistant` envelopes and legacy
`timeout`-status parts continue to parse identically.
