# PR #782: Switch base image from trixie to chainguard/glibc-dynamic:dev

- PR: https://github.com/EratoLab/erato/pull/782
- Status: pending (diff reviewed)
- Category: Chores & Developer experience
- Theme: Backend image slimming/hardening

## Summary

Changes the backend runtime container's base image in `backend/Dockerfile`
from `debian:trixie-slim@sha256:5cf544f...` to
`registry.eratolabs.com/erato/chainguard-glibc-dynamic:2026-06-25-dev` (a
custom/private image, presumably built and published by this project from a
Chainguard base — not independently verified since that image's own
Dockerfile/source is outside this PR's diff, and no `chainguard`-related
file exists anywhere else in this repository, confirmed by a repo-wide
search). The explicit `apt-get install ca-certificates` step is removed,
implying the new base image already provides CA certificates (or TLS
trust is otherwise handled, e.g. by the rustls switch in #781).
`.hadolint.yaml` adds `registry.eratolabs.com` to `trustedRegistries` so
hadolint's Dockerfile linting accepts the new `FROM` reference. The tag
itself, `2026-06-25-dev`, carries a `-dev` suffix, which reads as a
development/pre-release tag rather than a versioned, stable release tag —
worth the maintainer confirming this is the intended tag to ship in a
release image, as opposed to a placeholder used during development of
this PR that should have been pinned to a stable tag before merge.

## Compatibility and configuration

No user-facing configuration change. This affects only how the backend
Docker image is built; behavior should be unaffected as long as the new
base image provides equivalent glibc/runtime library compatibility for the
Rust binary. Self-hosters who build the backend image from source (rather
than pulling the published image) would need access to
`registry.eratolabs.com/erato/chainguard-glibc-dynamic:2026-06-25-dev` — it
is unclear from this diff alone whether that image is publicly pullable.
Supporting (not conclusive) evidence leans toward the registry allowing at
least some anonymous pulls: `infrastructure/charts/erato/values.yaml`
defaults `backend.image.pullSecrets`, `oauth2Proxy.image.pullSecrets`, and
the sqitch-migrator image's pull secrets to `[]` (empty) for the other
`registry.eratolabs.com/erato/*` images the Helm chart references, meaning
those are assumed pullable by a fresh cluster with no registry credentials
configured by default. Whether the same holds for
`chainguard-glibc-dynamic` specifically — and whether a self-hoster
building the backend from source (rather than using CI, which explicitly
authenticates via `docker/login-action` against `registry.eratolabs.com`
in `.github/workflows/docker-build.yml` for pushing) can also pull it
anonymously — should still be confirmed explicitly by the maintainer
before release, since it could otherwise be a build-time breaking change
for external contributors building the backend image from source.
