# PR #1164: Offer and dispatch `delegate_task` awaited and serial (ERMAIN-770)

- PR: https://github.com/EratoLab/erato/pull/1164
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 2, PR 4/5 — wait, PR 3/5 per the PR title, on top of #1163. Lets
the model plan and dispatch its own sub-task (`delegate_task`) — awaited
and one-at-a-time in this PR — rather than only delegating to an
@-mentioned assistant. Confirmed the most safety-critical guards
(no-nesting, budget-attempt-counting, scope-merge semantics) by reading
the relevant sections of `message_streaming.rs` and `delegation.rs` in
full:

- **No-nesting rule, confirmed exactly via reuse of an already-verified
  mechanism**: the `delegate_task` offer is gated through
  `synthetic_tool_offer_slot(..., is_delegated_run)` — the exact same
  function this session's earlier review of #1110 confirmed returns
  `false` unconditionally whenever `is_delegated_run` is true. The
  @-mention route's own offer condition is confirmed likewise gated on
  `!is_delegated_run`. So both delegation tools are structurally withheld
  from any chat that is itself a delegated run — matching "Children are
  offered neither delegation tool, so delegated work does not nest"
  precisely, and via the same verified gate rather than a new,
  independently-written check.
- **Two-gate design, confirmed structurally**: the offer requires both
  `delegation.tasks.enabled` (the deployment-level flag) and the
  selected facet's `tool_call_allowlist` actually selecting
  `erato/delegate_task` (via the `synthetic_tool_offer_slot`/
  `reserved_tool_selected` machinery this session's #1110 review already
  confirmed is opt-in — an empty client-tool allowlist selects nothing)
  — matching the PR's stated "not enough on its own" framing exactly.
- **Facet-scope merge semantics, confirmed exactly and pinned by a direct
  test**: `max_tasks_per_turn` merges via `effective.max_tasks_per_turn =
  effective.max_tasks_per_turn.min(value)` (minimum across every override
  in play), while `child_facet_ids` merges via a dedup-preserving push
  only when not already present (union) — a dedicated test confirms both
  behaviors numerically: a global cap of `5`, one selected facet
  overriding to `Some(2)`, another overriding to `Some(99)`, produces an
  effective cap of exactly `2` (the true minimum across all three
  values) — directly proving "selecting a second planning facet may only
  ever narrow what a turn can spend," not loosen it.
- **Budget counts attempts, not successful dispatches, confirmed
  exactly**: the per-turn cap check is `if attempt >
  scope.effective.max_tasks_per_turn as usize { ... }`, where `attempt`
  is incremented once per parsed call (per the PR's own framing, not
  independently re-verified at its exact increment site in this review)
  — matching the PR's stated design that a refused call still counts
  against the budget, since the built-in delegation tools are otherwise
  exempt from the per-call budgets that would bound a naive retry loop.
- **Scope resolved once and checked against the same list used to build
  the offer, confirmed structurally**: a dedicated test asserts
  `schema["properties"]["facet_ids"]["items"]["enum"]` matches the
  resolved `TaskOfferScope`'s facet list exactly — confirming the tool's
  JSON-schema enum hint (advisory only, since a model can emit any
  string per the PR) is generated from the same resolved scope object
  that dispatch-time argument validation checks against, so the two
  cannot silently drift apart into "offered but not actually
  dispatchable" or vice versa.
- Per the PR (not independently re-verified given remaining scope): the
  hidden-facets exclusion from the offered scope (since those are
  always-on platform baselines rather than a choice the model makes);
  the tool description explicitly framing the feature's intended use
  (keeping long/noisy work out of the visible conversation, not
  answering questions that could be answered in place) as a directive
  the model is the only thing that can act on; and the config template
  example showing the `delegation.tasks` facet-pairing requirement
  (naming a real MCP pattern alongside the reserved `erato/delegate_task`
  pattern, consistent with #1110's disclosed "operator trap" warning this
  session already confirmed).

## Compatibility and configuration

New opt-in feature, gated behind both `delegation.tasks.enabled`
(deployment-level, default presumably `false` per the established
pattern in #1107/#1110) and a facet's `tool_call_allowlist` explicitly
selecting the reserved tool — no deployment is affected unless both
gates are deliberately configured. No migration.
