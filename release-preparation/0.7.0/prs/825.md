# PR #825: Pass host MessageContent to ChatMessageRenderer overrides

- PR: https://github.com/EratoLab/erato/pull/825
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Follow-up to #822's library-export expansion: gives a component kit's
custom `ChatMessageRenderer` override (the component a kit substitutes for
the default `ChatMessage` via `MessageItem`'s existing `messageRenderer`
prop) an identity-safe way to render using the *host's own*
`MessageContent` component, instead of maintaining a forked copy of it (the
motivation named in #822: a ~2000-line frozen Beckhoff-kit copy that
caused a missing-status-indicator regression). Confirmed by reading the
code:

- New `ChatMessageHostComponents` interface (`{ MessageContent: typeof
  MessageContent }`) and a module-level constant
  `CHAT_MESSAGE_HOST_COMPONENTS` in `ChatMessage.tsx`; `ChatMessageProps`
  gains an optional `hostComponents?: ChatMessageHostComponents` field.
- `MessageItem.tsx` passes `hostComponents={CHAT_MESSAGE_HOST_COMPONENTS}`
  to whichever component is currently assigned as the message renderer
  (`messageRenderer: Renderer = ChatMessage` — defaulting to the stock
  `ChatMessage`, but substitutable by a kit). Confirmed this constant is a
  **stable module-level reference** (not re-created per render), which
  matters for `ChatMessage`'s existing custom `memo` comparison (unread in
  full, but the PR explicitly calls this out as the reason it's a module
  constant rather than an inline object).
- The default `ChatMessage` itself does not consume `hostComponents` (it
  already imports `MessageContent` directly) — the field exists purely for
  a kit's own override component to read via props. Exported from
  `@erato/frontend/library` as `ChatMessageHostComponents` alongside the
  existing `ChatMessage`/`ChatMessageProps` exports.
- Confirmed the PR's stated rationale for using props rather than a
  library re-export or a `window` global: a kit builds and ships as a
  separately bundled JS artifact, so importing `MessageContent` from
  `dist-library` inside the kit's own bundle would instantiate a second
  copy of React context state (the lingui i18n instance, theming context),
  silently breaking i18n/theming inside the kit's rendering — receiving
  the host's live component instance via props is the only channel that
  preserves module/context identity.

## Compatibility and configuration

None for the base product — this is additive plumbing consumed only by an
external component kit that opts into rendering via a custom
`ChatMessageRenderer` (the "first consumer" cited, the Beckhoff kit, is
described as a separate, pending change in a customer repo, not part of
this PR). No behavior change for the default `ChatMessage` rendering path.
