# PR #1086: Make the centered new-chat composer layout the default (ERMAIN-736)

- PR: https://github.com/EratoLab/erato/pull/1086
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Part 1 of the ERMAIN-731 stack. Flips the default new-chat composer
layout from bottom-anchored to vertically centered, and restructures the
empty-state rendering into a persistent three-row frame. Confirmed by
reading the backend config default, the frontend env fallback, and the
complete new `ChatEmptyStateLayout.tsx`:

- **Default flip, confirmed exactly at both the backend and frontend
  layers**: `default_chat_input_empty_state_layout()` in
  `erato_config/src/config.rs` changes its return value from
  `"bottom"` to `"centered"` (with new dedicated tests asserting the
  default and the explicit-`"bottom"`-override paths), and
  `normalizeChatInputEmptyStateLayout` in `frontend/src/app/env.ts`
  changes from `value === "centered" ? "centered" : "bottom"` to `value
  === "bottom" ? "bottom" : "centered"` — confirming any unrecognized or
  missing value now resolves to `"centered"` at both layers, not just the
  documented default.
- **Persistent three-row frame, confirmed exactly via the new
  `ChatEmptyStateLayout.tsx`**: for `mode === "centered"`, the outer
  container is `grid grid-rows-[minmax(0,1fr)_auto_minmax(0,1fr)]`
  (matching the PR's stated `minmax(0,1fr) auto minmax(0,1fr)` row
  template exactly); critically, the component always renders all three
  slots (`above`/`composer`/`below`) in its JSX regardless of `mode`
  (`centered`/`bottom`/`conversation`) — only the wrapping row's CSS
  classes differ per mode — confirmed this is the structural mechanism
  behind the PR's "one mounted composer" claim: the composer's `<div
  data-ui="composer-cluster">` slot is the same DOM node across a mode
  transition, not conditionally mounted/unmounted.
- **`mt-auto` over `justify-end`, confirmed exactly**: the centered mode's
  upper row wraps its content in `<div className="mt-auto ...">` with a
  code comment stating precisely the PR's disclosed deviation: `justify-
  end` would make overflowing content unscrollable from its top, while
  `mt-auto` lets it scroll correctly.
- Per the PR (not independently re-verified given the remaining scope):
  `Chat.tsx`'s 216-line diff removes the previous `MessageList
  emptyStateComponent` path and the `!translate-y-0` clone hack, composing
  both centered and bottom modes through the new shared layout component
  instead; `ChatUsageAdvisory` is extracted as its own component and
  `ChatInput` gains a `renderUsageAdvisory` prop defaulting to `true` (so
  the add-in and any direct `ChatInput` consumer render unchanged); a new
  additive `Chat.emptyStateBelowComponent` slot is wired but nothing
  passes it yet (deferred to the stacked ERMAIN-737 PR); shared-chat
  loading/error surfaces (`forceCenteredEmptyState`/`readOnly`) still
  render without a composer; and the committed Storybook+Playwright
  geometry harness (`e2e-tests/storybook-welcome-layout/`) measures
  pixel-exact shell centering and independent upper/lower-row scrolling
  at several viewport sizes, not independently reproduced here. The PR
  also explicitly flags as a known follow-up that the Outlook add-in
  inherits this default through the shared env and asks the team to
  confirm that's wanted for its narrow pane — an open question, not a bug.

## Compatibility and configuration

**Real, intentional default behavior change**: `chat_input_empty_state_layout`
now defaults to `"centered"` instead of `"bottom"` for every deployment
that doesn't explicitly configure it — confirmed the template TOML shows
how to opt back into `"bottom"` (per the PR, not independently re-read).
A deployment that already explicitly sets `chat_input_empty_state_layout
= "bottom"` (or `"centered"`) is unaffected by the default change, since
an explicit value always wins over the default.
