# PR #1023: Do not seed a pending sidebar chat from replayed chat_created frames (ERMAIN-666)

- PR: https://github.com/EratoLab/erato/pull/1023
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Fixes a ghost "New Chat" sidebar row left behind when opening a delegated
run mid-generation. `resumestream` replays a chat's full event history,
and the replayed `chat_created` frame previously ran the same new-chat
bookkeeping (pending sidebar placeholder, store writes, stream-key rebind,
navigation) as a genuine first-turn submit — but for a delegated run the
chat may never become listable for the opening user, so no listing
refetch ever replaced the placeholder and it lingered forever. Confirmed
by reading the complete `useChatMessaging.ts` diff:

- **Replay detection, confirmed exactly**: a new guard,
  `if (previousStreamKey === responseData.chat_id) { ...; break; }`,
  precedes all `chat_created` handling. This matches the PR's stated
  mechanism precisely: a resume stream is already keyed by the chat's own
  id, while a genuine submit stream is still keyed by the new-chat
  sentinel — so the check distinguishes replay from creation without any
  new field or backend signal.
- **Gated at the single call site, confirmed**: `handleChatCreated`
  itself is unchanged except for a new doc comment stating the calling
  contract; the previously two separate blocks (pending-chat seeding, and
  the stream-key-rebind/cleanup-transfer block gated separately on
  `responseData.chat_id && previousStreamKey !== responseData.chat_id`)
  are confirmed collapsed under the one new early-return guard, since both
  were already implicitly conditioned on the same replay check.
- **Hygiene backstops, confirmed**: `assistant_message_completed` now
  calls `clearPendingChat(activeStreamKey)` unconditionally (placed after
  the awaited listing invalidation, per an inline comment, so a normally-
  listable chat still swaps placeholder for real row without an
  intermediate frame showing neither); and both the resume `onError` and
  `onClose` handlers now call `clearPendingChat(resumeStreamKey)`
  unconditionally at the top, confirmed moved out of their respective
  `stillStreaming`-gated blocks (previously the clear only ran when
  streaming state was still considered active) — with inline comments
  stating the clear is idempotent and chat-scoped, so calling it
  unconditionally is safe.
- No backend changes, consistent with the PR's claim that
  `chat_was_created` semantics are untouched — this is a purely
  client-side bookkeeping-timing fix.

## Compatibility and configuration

None. Pure frontend fix; no API or configuration changes. Affects only
the client-side sidebar-placeholder bookkeeping around SSE resume/submit
streams.
