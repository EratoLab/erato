## Summary

Stack 4 "Async re-entry", position 5 of 5 backend-side — the capstone PR
the rest of the stack (#1188-#1191) was built toward, finally making the
feature live (though still off by default: `run_modes` defaults to
`["wait"]`). A very large PR (4176 insertions across 31 files, three
logical commits plus a fourth conformance pass against
`BUILD-RECONCILED.md`). Given the scope, this review prioritized the
highest-stakes correctness/concurrency mechanisms — the config offer/
union/re-check logic and the delivery pipeline's compare-and-set fencing
— over exhaustive line-by-line coverage. Confirmed the following directly
against the code:

- **`run_modes`/`scheduling` config, confirmed exactly**: new
  `TaskRunMode` (`Wait`/`Async`, default `Wait`) and `TaskScheduling`
  (`Silent`/`WhenIdle`/`Interrupt`, default `WhenIdle`) enums; both global
  and per-facet-override validation reject an empty or duplicate
  `run_modes` list and reject `scheduling = "interrupt"` at load (both at
  the global `DelegationConfig::validate` level and in the per-facet
  startup-panic loop) — matching "Non-empty and duplicate-free;
  `scheduling = \"interrupt\"` is a reserved spelling rejected at startup"
  exactly, confirmed at both scopes.
- **`run_modes` unions per facet with `wait` always floored back in,
  confirmed exactly**: `effective_tasks_config` pushes each facet-override
  mode into the global list only if not already present (a true union,
  deduplicated), then unconditionally re-inserts `Wait` at index 0 if
  absent — with a code comment stating precisely the PR's own reasoning:
  "Intersection is the only other candidate and it can yield an empty
  list, whose only repair is a silent downgrade to `wait` under a name
  that promised otherwise" — matching "Per facet the list unions... with
  `wait` floored back in, because the enum must not be empty and the
  refusal's 'available: …' must stay true" exactly.
- **Dispatch re-checks the effective offer and refuses rather than
  downgrades, confirmed exactly**: the dispatch-time `run_mode` resolution
  checks `scope.effective.run_modes.contains(&run_mode)` and returns an
  explicit `Err` naming what's available if not, with a code comment
  stating "An explicit unavailable mode is refused rather than quietly
  downgraded, so a model cannot believe it detached work that in fact ran
  inline" — word-for-word matching the PR's claim, and this re-check is
  against the *effective* scope (not the schema string), so a model
  cannot exploit a stale or mismatched schema.
- **CAS #1 — claim, confirmed exactly, including the C-1 fence design**:
  `deliver_task_result`'s claim step generates `claim_token =
  Uuid::new_v4().to_string()` fresh per attempt (not a replica/pod id) and
  writes it into `claimed_by` via a `jsonb_set` gated on `state = 'pending'
  AND delivery_id = $2` — a genuine compare-and-set, confirmed structurally
  (zero rows updated means another attempt won). A code comment states
  exactly: "two attempts from ONE process must not collide, which is
  exactly the case a pod name cannot distinguish... leaves `claimed_at`
  free to mean only 'when'" — matching the PR's "Third commit" table entry
  C-1 precisely.
- **A delivery never forces a busy or parked chat, confirmed exactly**:
  an `awaiting_approval` origin causes an immediate `Deferred` (lease
  never even attempted), and the subsequent `try_start_task` call for a
  non-parked origin explicitly passes `Takeover::RefuseParked` (this
  session's own review of #1188 established `RefuseParked`'s semantics) —
  matching "it takes the lease with `RefuseParked`, and a refusal puts the
  claim back in the queue with its attempt counted" (confirmed via
  `release_pending` incrementing `claimed.attempts` before release on
  every deferred path).
- **Lease-cleanup guard armed immediately on acquiring the lease,
  confirmed exactly — one of the disclosed "five defects" fixed**:
  `TaskCleanupGuard::new(...)` is constructed directly after
  `try_start_task` succeeds, before any further fallible step, so a panic
  anywhere in the delivery body still releases the lease rather than
  leaving it heartbeated forever — directly substantiating the "Third
  commit" disclosure "the lease was held bare through the append (a panic
  there wedges the chat permanently...)" as a genuine defect that is fixed
  in the code actually shipped here (not merely claimed fixed).
- **Probe + append + `delivered` write are one transaction, confirmed
  exactly — the C-2 conformance item**: the duplicate probe
  (`POSTGRES_QUERY_DELIVERY_DUPLICATE_PROBE`), the
  `append_message_unchecked` call building the `task_result` row, and the
  CAS #3 `set_delivery_state_in(&txn, ..., ResultDeliveryState::Claimed,
  Some(&claim_token))` write all run inside one `txn` from a single
  `app_state.db.begin()`, with a single `txn.commit()` at the end and an
  explicit `txn.rollback()` if the final fence check fails — matching "C-2
  | probe + append + `delivered` write are one transaction... a fence
  across three transactions cannot stop 781's sweeper double-inserting"
  precisely, and the code comment states the identical reasoning: "if the
  append commits first, a sweeper that requeues this claim in between
  hands it to a second holder whose probe now misses, and the same result
  is appended twice."
- **The duplicate-probe error is not swallowed into "no row," confirmed
  exactly — another of the disclosed "five defects"**: a failed probe
  query explicitly `tracing::warn!`s and returns `Deferred` rather than
  falling through as if `existing` were `None` — directly substantiating
  the disclosed fix for "the duplicate probe and the tip read swallowed
  errors into values meaning 'no row' and 'no anchor' respectively."
  `get_active_thread_tip`'s error path is handled identically (an `Err` is
  `tracing::warn!`ed and deferred, not folded into `tip = None`).
- **Owner-mismatch and archived-origin checks close the delivery rather
  than silently skip or force it, confirmed exactly**: both checks write
  a fenced `Failed`/`Superseded` state transition (via `set_delivery_state`,
  itself gated on `state = Claimed AND claimed_by = $claim_token`) before
  returning `Closed` — matching "Writing into a chat whose owner differs
  from the run's is the ERMAIN-485 class; the refusal is the point, and it
  appends nothing" and the archived-origin re-check occurring a second
  time *under the lease* (since "Archiving never takes the lease, so the
  step-2 read can be stale by now").
- **`TaskScheduling::as_str()` lives on the enum, confirmed exactly — the
  C-6 conformance item**: confirmed directly in `config.rs`.
- **Reaction suppression and the `async` CHANGELOG draft, confirmed
  consistent with the code read**: `CHANGELOG.md`'s drafted entry states
  "it is deliberately not offered the `delegate_task` tool: a reaction
  that could plan its own tasks is a loop with nothing to bound it" —
  matching the PR body's identical stated reasoning; this specific
  suppression wiring itself (in `message_streaming.rs`'s 336-line diff)
  was not independently traced to its exact call site in this review.
- Per the PR (not independently re-verified given the review's scope and
  this PR's unusual size): `ProvenanceRunMode` as a wire-distinct type
  from `DelegationRunMode` (ensuring `"async"` in a submit body is a
  deserialization failure, and that `Wait`-only envelopes written before
  this type existed still deserialize) — the type's existence and import
  were confirmed, but its full deserialization-boundary behavior was not
  traced; the drain mechanism "hanging off all five tails" and its
  queue-scan re-selection-of-rejected-rows fix (one of the five defects);
  the sidebar P5 fix recognizing `async` as a detached run; the
  `erato.scenario-assistants.toml` change enabling `["wait","async"]` for
  a later PR's dependency; the `DELEGATION_TASKS_ALLOW_ASYNC` frontend-
  environment derivation (`frontend_environment.rs`, 53 lines); the
  `result_missing` terminal-failure path when a run's answer row is gone;
  the archive-retention exemption for a chat with a result still owed;
  the 1675-line new integration-test additions covering (per the PR's own
  description) the nine end-to-end delivery scenarios, the offer/refusal/
  cap/wire-rejection/config-validation tests, and the race/crash-recovery
  tests; and the disclosed final verification (1176/1176 `cargo nextest
  run --retries 2`, clean clippy `-D warnings`, clean `gen-openapi`/
  `gen-config-reference --check`, clean frontend `tsc`, 524/524 vitest).
  The PR's own "Documented degradation (accepted, until ERMAIN-781)"
  section is a candid, specific disclosure of a known gap (a crash between

## Compatibility and configuration

New config keys `delegation.tasks.run_modes` (default `["wait"]`) and
`delegation.tasks.scheduling` (default `"when_idle"`), both per-facet
overridable, confirmed validated as non-empty/duplicate-free with
`"interrupt"` rejected at load. Off by default: with `run_modes =
["wait"]` the tool schema is unchanged and no delivery path runs, per the
PR's own claim and consistent with every delivery/dispatch code path
confirmed above being reachable only via an explicit `async` run mode.
Wire-additive: a dispatched async task's tool part carries `"run_mode":
"async"`, `RecentChat.provenance_run_mode` may read `"async"`,
`ProvenanceRunMode` is a new schema type, `TaskResultInput.result_message_id`
becomes optional, and the frontend environment gains
`DELEGATION_TASKS_ALLOW_ASYNC`.

## Release note disposition

Proposed category: Features and enhancements. The PR's own drafted
`CHANGELOG.md` entries (quoted and partially verified above) are detailed
and accurate against the portions of the implementation this review
traced directly: the model can dispatch a task it does not wait for
(`run_mode = "async"`, off by default), and a finished async task's
result now arrives back in its origin conversation with a reaction turn
(unless `scheduling = "silent"`), fenced by idempotent compare-and-set
writes so a crash or rolling deploy cannot duplicate a delivery. This is
the user-visible payoff of the whole "Async re-entry" stack (#1188-#1192)
and should be the stack's primary release-note entry, with #1188's
`409 generation_running` behavior change called out as a secondary,
narrower visible effect already live independent of the `async` flag.
