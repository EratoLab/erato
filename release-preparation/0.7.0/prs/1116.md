# PR #1116: Surface provider content blocks in audio transcription as a user-facing error

- PR: https://github.com/EratoLab/erato/pull/1116
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a real, observed production bug: a dictation blocked by Vertex AI's
content filter (a documented false positive on `gemini-3.7-flash`/
`gemini-3.8-flash` for harmless speech phrased as assistant instructions)
previously surfaced as a raw, unreadable genai error dump including the
full base64 audio request payload, and every subsequent chunk of the same
dictation then failed too since the client's expected chunk index fell
out of step with the server. Confirmed by reading the complete backend
error-classification logic and the new frontend
`audioTranscriptionErrors.ts` in full:

- **Root-cause extraction confirmed exactly**: `AudioTranscriptionProviderError
  ::from_response_body` reads `promptFeedback.blockReason` from the
  provider's raw JSON response via `response_body.pointer(...)` — when
  present, classifies as `ProviderContentBlocked`; otherwise
  `ProviderError`. `classify_transcription_failure` falls back to a third
  code, `TranscriptionFailed`, for any error that isn't this specific
  provider-error type — matching the PR's stated three-way classification
  exactly.
- **Session-survival fix (the "Unexpected chunk index" bug), confirmed
  exactly**: on a dictation chunk failure, `*next_chunk_index += 1` is
  incremented before returning the failure frame — a code comment states
  directly: "the passage is lost either way; stay in step with the client
  so the chunks after it are still transcribed instead of failing on
  their index." This is the exact fix for the cascading-failure symptom
  described in the PR's problem statement.
- **No raw request payload in the log line, confirmed by direct
  inspection**: the `warn!` call logs `chunk_index`, `error_code`, and
  `error = %error` (the short `Display`-formatted user-safe message, e.g.
  "The AI provider's content filter blocked this passage (reason:
  SAFETY)"), not the raw response body or the request's base64 audio —
  consistent with the PR's stated change that the request payload is no
  longer logged.
- **Frontend message mapping, confirmed exactly matching the PR's own
  example**: `describeAudioTranscriptionFailure` switches on the three
  protocol error codes, formatting a passage-position-qualified message
  (via `formatPassageStart`, `m:ss`) for each, and appends a quotable
  `Error code: <code>` suffix to every known-code message — confirmed the
  `provider_content_blocked` branch's message text matches the PR's
  quoted example verbatim ("This also happens with harmless speech.
  Please say it differently or type it."). An unrecognized code falls
  back to the raw server text or the caller's default, so older/newer
  protocol mismatches degrade gracefully rather than rendering nothing.
- Per the PR (not independently re-verified given remaining scope): the
  block is stated to be deterministic per passage at `thinkingLevel: LOW`,
  unaffected by `safetySettings: OFF`, with no console-level mitigation
  available, and that internal deployments were separately switched to
  `gemini-3.6-flash` (which doesn't exhibit the false positive) as a
  workaround outside this code change; the dictation hook's handling of a
  failed chunk resolving with an empty transcript so the composer's
  ordered-append logic isn't blocked; and the `useAudioTranscriptionRecorder.ts`
  (non-dictation, file-attachment transcription) diff applying the same
  classification for that path.

## Compatibility and configuration

None. Pure bug fix; no API contract change beyond the additive
`error_code` field on existing `ChunkFailed`/error socket frames (new
enum variant `ChunkFailed` on the dictation protocol, additive field on
the existing non-dictation error frame). No configuration changes.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: when a provider's content
filter blocks a dictation or audio-transcription passage (a known false
positive on some Gemini models for harmless speech), the user now sees a
clear, actionable, quotable error message instead of a raw technical
error dump, and the rest of the dictation continues transcribing
correctly instead of cascading into further failures.
