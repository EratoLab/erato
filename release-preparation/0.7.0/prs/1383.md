# PR #1383: Word for the web: reading comments never changes the document, and legacy files keep their anchors (ERMAIN-983) (#1383)

- Theme: Word add-in comment reading

## Summary

Per the PR's detailed body (references its own native gate "ERMAIN-948
gate F1/F2"; treated as reliable, not independently re-verified
line-by-line). Fixes two defects discovered by that gate: on Word for the
web, merely *reading* comments (for the comment map/picker/section view,
or "Show in Word") previously called `Comment.getRange()`, which has the
side effect of un-hiding hidden text and persisting that as a document
change — so opening the comment pane could silently edit the document.
Separately, a legacy file's comment anchors (whose web package IDs don't
match `Comment.id`) were lost entirely.

- **Fix, as described**: the web code path now never calls
  `Comment.getRange()` for any read operation. Instead, each paragraph's
  own `getComments()` (reported as ~20ms per 100 paragraphs) supplies a
  thread's first/last paragraph, and the paragraph's underlying package is
  used to place threads within it — by `durableId` normally, or by a
  unique content+author match for legacy files whose web package IDs
  aren't real `Comment.id`s. A thread Word lists in no paragraph is
  recovered from the packages directly. Anchors spanning multiple
  paragraphs are represented at paragraph granularity with
  `position: unknown` rather than lost.
- PC and Mac code paths are explicitly unchanged by this PR (web-only
  fix).
- A new refusal path, `HIDDEN_TEXT` (web only), is introduced elsewhere in
  this cycle (per the PR's own cross-reference to #1384) specifically
  because root comment *writes* on the web still have this side effect —
  this PR only fixes *reads*.

## Compatibility and configuration
