# PR #1275: Allow deployment-specific Teams app package versions

- PR: https://github.com/EratoLab/erato/pull/1275
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Follow-up to the Teams bot cluster (#1253/#1254/#1260, reviewed earlier
in this session). Previously a Teams app package's version always
followed the Erato release version, so a deployment that needed to
update only its bot or branding configuration (with no new application
release) couldn't bump the installed package's version — and Teams
requires a strictly-increasing version to accept an update. Confirmed
every claim precisely:

- **New optional `manifest.version` config field, falling back to the
  release version, confirmed exactly**: `MsOfficeTeamsManifestConfig.version:
  Option<String>` defaults to `None`, and the manifest renderer computes
  `document["version"] = json!(manifest.version.clone().unwrap_or_else(release_version))`
  — matching "Add optional `integrations.ms_office.teams.manifest.version`
  and preserve the release-version default" exactly.
- **App identity and bot configuration are unaffected by the override,
  confirmed exactly**: `document["id"]` is untouched by this diff (still
  set from `app.app_id`), and the new dedicated test
  `deployment_version_override_preserves_app_identity_and_bot` explicitly
  sets a custom `version`, enables the bot with a specific `app_id`, and
  asserts both `manifest["id"]` and `manifest["bots"][0]["botId"]` remain
  exactly what was configured — directly confirming "preserve... existing
  app identity" and that bot configuration survives the override intact.
- **Validation enforces exactly the three-component, 0–65535,
  no-leading-zero format Teams requires, confirmed exactly, by both the
  validation logic and its dedicated accept/reject test cases**:
  `validate()` splits the version on `.` and rejects unless there are
  exactly 3 parts, each non-empty, all-ASCII-digit, parseable as `u16`
  (bounding each component to 0–65535), and free of a disallowed leading
  zero (a bare `"0"` is still allowed, but `"01"` is not). The new test
  module confirms acceptance of `"0.6.3"`, `"1.0.0"`, and the boundary
  value `"65535.65535.65535"`, and rejection of empty string, too-few/
  too-many components (`"1"`, `"1.2"`, `"1.2.3.4"`), a leading zero
  (`"01.2.3"`), a negative component (`"1.2.-3"`), a leading `+` sign,
  a SemVer-style prerelease suffix (`"1.2.3-beta"`), an out-of-range
  component (`"1.2.65536"`), and leading/trailing whitespace — a
  thorough boundary-case test set matching the error message's own
  stated rule ("must have three numeric components (0..65535), without
  leading zeros") exactly.
- **This Office-manifest mechanism is explicitly left unchanged,
  confirmed structurally**: the PR touches only the Teams-specific
  `MsOfficeTeamsManifestConfig`/`teams.rs` rendering path; no change
  appears to the existing four-component Office XML manifest version
  scheme (`release major.minor.patch.deployment`) this PR's own
  description says is unaffected ("That Office mechanism is unchanged").
- Per the PR (not independently re-verified): the disclosed live-
  deployment validation (both MS deployments now serving package 0.6.3
  with existing IDs, separate conversational bots, and staging yellow
  icons; live package integrity/identity/readiness/bot-authentication-
  rejection checks; the explicit disclosure that interactive Teams
  catalog installation/sign-in was not exercised); and the disclosed CI
  run passing backend, frontend, e2e, and CodeQL checks.

## Compatibility and configuration

Additive. New config key `integrations.ms_office.teams.manifest.version`
(optional, `Option<String>`, defaults to `None` meaning "use the Erato
release version" — confirmed byte-for-byte unchanged default behavior
when unset). Validated at load against Teams' required three-component
numeric format. Documentation updated accordingly in
`configuration.mdx`.

## Release note disposition

Proposed category: Features and enhancements. Worth a brief mention for
Teams-bot-enabled deployments: a deployment can now set an explicit
`integrations.ms_office.teams.manifest.version` to push a Teams app
package update (branding or bot configuration changes) without cutting
a new Erato release, as long as the version is increased each time.
