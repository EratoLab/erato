# PR #1094: Support MCP server file output of non-image files

- PR: https://github.com/EratoLab/erato/pull/1094
- Status: pending
- Category: Features and enhancements
- Theme: MCP controls

## Summary

Extends the MCP file-output mechanism (from #867, previously "File-output
processing currently supports image MIME types only") to support any MIME
type, including DOCX and PDF, with arrays that mix images and documents.
Per the updated `site/content/docs/features/mcp_servers.mdx`: the original
MIME type is now passed through to file storage; images continue to use
the existing image renderer, while other file types appear as attachment
cards with the same preview options as user-uploaded files, remain
available for text extraction in subsequent model context when a text
extractor supports the format, and can always be downloaded even without a
preview/extractor.

Two related, security-relevant hardening changes are bundled in:
1. **Filename validation**: MCP-provided file names are now rejected if
   they contain path separators, colons, or control characters, or if they
   are exactly `.` or `..` — closing off a path-traversal-style filename
   from an MCP server being used unsafely. A new test,
   `invalid_file_outputs_have_recoverable_errors`, exercises this (using
   `"../report.pdf"` and `".."` as rejected examples).
2. **Recoverable failure**: invalid Base64 content or an unsafe filename
   now fails the specific tool call with a recoverable error (consistent
   with #995's "make MCP errors recoverable" fix) *before* any files in a
   multi-file result are stored — avoiding partial storage of a malformed
   batch.
3. `structuredContent` support: the tool result can now provide the
   file-bearing object via MCP's `structuredContent` field (in addition
   to the existing JSON-in-text-content path), with `structuredContent`
   taking precedence when both are present.

Also (independent of the file-name annotation from #867): without a
`chat.erato/file_name_field` annotation, a plain sibling `name` field is
now used as a fallback display name before falling back to a generated
name.

## Compatibility and configuration

No configuration keys or migrations. Purely additive/hardening changes to
the existing MCP file-output mechanism — MCP servers that already return
image files are unaffected; servers returning non-image files (documents)
now get proper preview/download support instead of (implicitly) being
unsupported before. The filename-safety validation is a backward-compatible
tightening: any MCP server that was already returning safe filenames sees
no change; one that (perhaps unintentionally) returned a path-like or
control-character filename would now have that specific tool call fail
with a recoverable error instead of whatever the prior (unvalidated)
behavior was.
