## Summary

Follow-up to #939 (1974 insertions, stacked on it): when attaching a
Teams transcript, the composer now also fetches and uploads what selected
messages actually carried — pasted images and shared OneDrive/SharePoint
files — alongside the text transcript, with each in-text marker stamped
with the uploaded filename so the model can join a file to the message it
came from by name. Confirmed by reading the two core new modules in full:

- **Caps confirmed exactly as described**: `teamsTranscriptAssets.ts`
  defines `MAX_TRANSCRIPT_IMAGES = 10`, `MAX_IMAGE_BYTES = 4MB`,
  `MAX_TRANSCRIPT_FILES = 10`, a per-file fallback cap
  `MAX_SHARED_FILE_BYTES = 10MB` (used only when the deployment's own
  configured upload limit isn't available to the add-in), and a
  `MAX_TOTAL_FILE_BYTES = 25MB` ceiling across all shared files in one
  transcript (confirmed via a running `fileBudgetUsed` counter that stops
  fetching once exhausted, correctly floored so the total budget can never
  undercut a single file the deployment's own limit would allow). An
  oversized file is explicitly tracked in a `tooLargeFileUrls` set and
  stamped as "too large to attach" in the transcript text, rather than
  silently vanishing — confirmed matching the code's own stated design
  principle: every other failure (a failed fetch, no file-read grant,
  hitting the image/file count caps) degrades silently to the bare
  `[image]`/`[attachment: …]` marker, but a size rejection is the one
  case that explicitly discloses itself, "because silence there would
  read as an oversight."
- **Files.Read.All / partial-consent fallback confirmed**: `downloadFile`
  is typed as nullable specifically to represent "`Files.Read.All` was
  not granted," in which case file markers stay bare rather than the
  feature failing outright — consistent with the description's "same
  partial-consent fallback as channels" claim (from #939's channel-access
  gating pattern), though the actual consent-check call site granting or
  withholding this token wasn't independently traced in this review.
- **OneDrive/SharePoint resolution confirmed via full read of
  `teamsSharedFilesGraph.ts`**: a shared file's Teams message only carries
  its web URL, which is resolved via Graph's `/shares/{shareToken}/driveItem`
  endpoint (the share token being a specific `u!`-prefixed base64url
  encoding of the URL, confirmed implemented correctly per the code's own
  wire-format comment) to get the file's size and a pre-authenticated
  download URL — deliberately a two-step process specifically so an
  oversized file can be rejected using only its metadata, before
  downloading a single byte of it.
- Deduplication: both images and files are hashed (FNV-1a 64-bit) so
  the same asset referenced by multiple selected messages is only
  uploaded once, reusing the same generated filename across all its
  markers.
- Pasted images resolve via `hostedContents` using Graph scopes the add-in
  already holds (no new consent needed for that path), per the PR — not
  independently re-verified, but consistent with the file-download path
  correctly gating its *own* new scope (`Files.Read.All`) separately.

Not independently verified, given continued scale: the 324-line
`TeamsChatPickerDialog.tsx` UI diff (how these fetches surface progress/
errors to the user), the `useTeamsFileFetcher.ts`/`useTeamsTranscriptBuild.ts`
wiring, or the ~800 lines of new/expanded test coverage across 5 test
files.

## Compatibility and configuration

Requires a new `Files.Read.All` Graph delegated permission grant to
resolve OneDrive/SharePoint file attachments; per the PR, this follows
the same partial-consent-tolerant pattern established for channel access
in #939 — without that grant, shared-file markers in an attached
transcript stay as bare placeholders rather than the feature failing.
Pasted-image attachment needs no new grant. No backend configuration
changes; the per-file size fallback correctly defers to the deployment's
own configured upload limit when available.
