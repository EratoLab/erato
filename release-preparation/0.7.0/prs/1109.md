# PR #1109: Split `dispatch_delegate_tool_call` into launch and await (ERMAIN-756)

- PR: https://github.com/EratoLab/erato/pull/1109
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 1, PR 3 of 4, on top of #1108. Splits the monolithic
`dispatch_delegate_tool_call` into `launch_delegation` (file validation,
owner re-resolve, background-cap check, chat creation, lease, seeding,
spawn) and `await_delegation` (the join/timeout/abort-forwarding/trace
`select!` loop), stated as a behavior-preserving refactor that enables
bounded fan-out in a later stack (multiple children launched before
blocking on the first). Confirmed by reading the complete diff in full:

- **The split matches the described signatures exactly**: `launch_delegation
  (app_state, policy, context, target: DelegationTargetSpec, run_mode:
  DelegationRunMode, brief: DelegateBrief) -> Result<LaunchOutcome,
  String>` and `await_delegation(app_state, launched: LaunchedDelegation,
  parent: Option<DelegationParentStream<'_>>, tool_call) ->
  DelegationDispatchOutcome` — both confirmed present with exactly these
  signatures.
- **`DelegationTargetSpec::{Assistant(Uuid), Task { facet_ids }}`,
  confirmed exactly**, including the `Task` arm's `#[allow(dead_code)]`
  annotation and its body returning `Err("task route not available"
  .to_string())` with a code comment stating "2.3 fills this in; until
  then the offer path cannot produce it" — matching the PR's claim that
  the task route is reserved but unreachable until a later PR registers
  its tool.
- **`run_mode` is a launch parameter, not read internally, confirmed
  exactly**: it's a plain argument to `launch_delegation`, with a doc
  comment stating the mention route passes `context.run_mode` straight
  through while a future task route will choose per call.
- **`LaunchedDelegation`/`LaunchOutcome`, confirmed matching the
  description**: `LaunchedDelegation` carries `assistant_id: Option<Uuid>`
  and `target_name: Option<String>`, with doc comments noting both become
  `None` "once the task route lands a child on the bare model" — not yet
  reachable in this PR, since the `Task` variant always errors before
  reaching that point. `LaunchOutcome::{Launched(LaunchedDelegation),
  Dispatched { assistant_id, assistant_name, delegate_chat_id }}`
  confirmed matches the awaited-vs-background split.
- **`await_delegation` destructures the launched state and falls back
  safely on this route, confirmed exactly**: `assistant_id.unwrap_or_else
  (Uuid::nil)` and `target_name.unwrap_or_default()`, with a code comment
  stating these fallbacks are unreachable on the current (mention-only)
  route since the launch there always resolves a real assistant — the
  fallbacks exist purely so `await_delegation`'s body doesn't need to
  handle an `Option` for a case this PR's target routes never produce.
- Per the PR (not independently re-verified beyond what's visible in the
  diff structure above): the claim that the `await_delegation` body
  itself preserves every `select!` arm from the original function
  byte-for-byte (the join, timeout classification, parent-abort
  forwarding with `CHILD_ABORT_GRACE`, and the trace tap) — plausible and
  consistent with the diff being a pure extraction of the tail of the old
  function, but the full ~150-line body of `await_delegation` was not
  independently re-diffed line-by-line against the pre-PR
  `dispatch_delegate_tool_call`; the disclosed acceptance condition that
  this diff touches only `delegation.rs` with no test file edited
  (consistent with the diff stat showing exactly one file changed); and
  the disclosed, reasoned decision not to add the two unit tests and one
  integration test the linked issue proposed, because
  `DelegationDispatchContext` is `pub(crate)` (unreachable from the
  integration-test crate) and an in-crate unit test would need an
  `AppState` test constructor that lives only in the integration crate —
  with the PR arguing the property those tests targeted (no event emitted
  at launch) is already indirectly covered by an existing test asserting
  every `in_progress` frame has empty `output.status` and non-empty
  `localTrace.steps`.

## Compatibility and configuration

None. Internal refactor with no behavior change on any currently-reachable
path (the `Task` route is unreachable, erroring before any new logic
executes). No API, configuration, or database changes.
