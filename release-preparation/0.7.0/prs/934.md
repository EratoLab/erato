# PR #934: feat: enforce configured file-size limits across all local upload paths

- PR: https://github.com/EratoLab/erato/pull/934
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes inconsistent enforcement of the configured per-file upload size
limit (ERMAIN-34): previously, some upload entry points relied on
`react-dropzone`'s own rejection UX (visible before upload starts) while
others had no size check at all before starting the actual upload
request, and error messaging inconsistently referenced a hardcoded 20MB
rather than the runtime-configured limit. Confirmed by reading the core
utility and one representative enforcement point in full:

- New pure utility `validateFileSizes(files, maxSizeBytes)` — confirmed
  exactly matches its documented semantics: a file more than `maxSizeBytes`
  is oversized; a file exactly at the limit is valid; any one oversized
  file in a batch fails the whole batch, returning the offending files for
  the error message.
- Confirmed via full read of `useFileDropzone.uploadFiles`: the size
  preflight runs immediately after the file-type check and the
  `maxFiles` trim, and — critically — **before any `await`, state
  mutation, or network call** (no `setUploading`, no silent-chat creation,
  no `FormData`/`fetchUploadFile`), so a caller's `isUploading` state never
  transiently flips true for a request that's about to be rejected. The
  existing HTTP-413-from-server fallback path (`isUploadTooLarge`) is also
  fixed to pass the offending filenames into `UploadTooLargeError`, where
  it previously constructed the error with no filenames at all.
- Per the PR's own detailed tables (not independently re-verified for
  each of the remaining ~10 call sites, given the scale, but consistent
  with the pattern confirmed above): the same preflight is applied to
  `useStandaloneFileUpload.uploadFiles` (also fixing a "Maximum size: —"
  regression where `UploadTooLargeError` wasn't always given the
  formatted limit), `useChatFileSources.handleSelectedFiles` (protecting
  the Outlook/Teams add-menu's custom `File[]` path), and at the UI/
  selection layer (`FileUploadButton`, `useConversationDropzone`,
  `AssistantFileUploadSelector`, `Chat.tsx`, and both add-in conversation
  hosts) for early, pre-upload rejection UX via `react-dropzone`'s own
  `maxSize` option plus a new `onError` callback wiring.
- The Outlook add-in's direct email-source upload path
  (`AddinChatInput.tsx`) gets its own preflight after
  `resolveSelectedFilesForSend()`, with oversized files setting a local
  `emailUploadError` (merged into the shared `chatInputProps.uploadError`)
  while still allowing the message itself to send without the rejected
  file's id — leaving its chip in place for the user to retry or remove.
- `UploadTooLargeError`, `isUploadTooLarge`, and `validateFileSizes` are
  newly exported from `@erato/frontend/library` for add-in/kit
  consumption.
- Explicitly out of scope per the PR/issue: cloud-linked files (the
  browser never holds their bytes locally to check), audio transcription
  WebSocket uploads, any backend-side limit change, file compression, and
  automatic retry of a rejected oversized file.

## Compatibility and configuration

None. No new configuration keys — reuses the existing runtime-configured
per-file size limit (`maxSizeBytes`/`maxSizeFormatted` from
`useUploadFeature()`) consistently everywhere, replacing any
inconsistent/hardcoded assumptions in client code. Behavior change: a
file exceeding the configured limit is now rejected consistently and
immediately at every entry point (drag-and-drop, file picker, Outlook
add-menu, Outlook email-source attachments), with the same
correctly-formatted size-limit message, rather than sometimes starting an
upload that then fails later or shows an unhelpful message.
