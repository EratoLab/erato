# PR #1014: Delegated runs list: dismiss finished background runs (ERMAIN-643)

- PR: https://github.com/EratoLab/erato/pull/1014
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Final layer of the background-delegation frontend stack: makes a
finished/failed background run dismissible from #1013's runs bar, so the
list drains instead of accumulating indefinitely. Confirmed by reading
the code, this is a client-side-only, per-device persisted dismissal
(explicitly documented as a deliberate v1 trade-off, since there's no
per-user seen/dismissed backend schema yet) — but the PR also discloses
and fixes a genuine bug found during its own manual testing, confirmed
precisely via `generationStatusStore.ts`:

- **The disclosed bug and its fix, confirmed exactly**: a reported
  "dismissed runs reappear after reload" turned out not to be a failure
  of the persisted dismissal mechanism at all, but a *different*, pre-
  existing gap — opening (visiting) a finished run consumed its outcome
  into the store's `"cleared"` tombstone state, which previously carried
  no information about *what* outcome it had consumed. Since `"cleared"`
  intentionally renders nothing for notification surfaces (badges, dots),
  a visited run's row lost its settled-state information entirely — it
  only *looked* dealt-with while the tab stayed open, but a reload
  dropped the ephemeral tombstone and the durable backend outcome
  (#1008) resurrected the row as if newly finished. The fix adds an
  optional `consumed?: "finished" | "error"` field to the `cleared`
  variant, populated at every site that transitions a status to
  `cleared` (poll-snapshot consumption, local terminal marking, explicit
  outcome consumption, and the chat-switch path) — confirmed via the
  diff that all four call sites correctly carry the real outcome kind
  forward rather than discarding it. This means a status *resolver* (the
  delegated-runs checklist, the trace pill) can keep stating a visited
  run's true settled state, while a genuinely dismiss-oriented
  *notification* surface (a sidebar badge count) still correctly stops
  counting it — the same underlying tombstone now serves both purposes
  without them contradicting each other across a reload.
- A new `consumeTerminalOutcome` store action specifically records that
  "the user acknowledged a finished/error outcome without opening the
  chat" (e.g. via the new dismiss checkbox) — confirmed it correctly
  no-ops if the current status isn't actually `finished`/`error` (e.g. a
  run that started generating again has nothing to consume yet).
- Per the PR (not independently re-verified in `DelegatedRunsSection.tsx`'s
  98-line diff): the dismiss action only ever appears on terminal
  (completed/failed) rows, never on running or parked-approval rows; the
  section's count/badge only reflects undismissed runs; dismissing one
  run doesn't affect any other; there's no success toast (the row simply
  disappearing is the intended feedback, per an existing repo
  convention); and opening the run itself remains untouched as the actual
  way to read its result.
- The PR explicitly flags, as a known and accepted follow-up rather than
  a bug, that the dismissal storage is per-device/per-browser-profile,
  not per-user — a dismissal on one device won't follow to another until
  a real backend user-preference store exists.

## Compatibility and configuration

None. Pure frontend feature; no configuration or API changes. Uses the
repo's existing client-side persisted-state storage mechanism, keyed per
delegated-run chat id.
