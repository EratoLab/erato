# PR #1018: Chat: point at unconnected MCP servers instead of silently dropping their tools (ERMAIN-657)

- PR: https://github.com/EratoLab/erato/pull/1018
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Third and top layer of the OAuth-MCP-visibility stack (on #1016's backend
classification and #1017's assistant-editor UI). Surfaces #1016's
`mcp_servers_needing_auth` field directly on the affected assistant
message: a quiet, informational footnote naming the servers skipped for
this specific user, with an inline "Connect" affordance. Confirmed by
reading both changed files in full:

- **Strictly informational, never error-toned, confirmed via the new
  `McpNeedsAuthNotice.tsx`**: renders as `role="note"` with muted
  (`text-theme-fg-muted`) styling and an info icon, not an alert — a code
  comment states the rationale precisely: the response itself succeeded,
  the servers are healthy, and connecting is optional. The component
  returns `null` outright when `serverIds` is empty, so it only ever
  renders when there is something genuinely unconnected to report.
- **Keyed strictly off `mcp_servers_needing_auth`, never
  `mcp_servers_unavailable`, confirmed via `ChatMessage.tsx`**: the new
  block is gated on `message.mcp_servers_needing_auth?.length > 0`
  exclusively; a broken/unavailable server (the pre-existing, separate
  field) never reaches this component, consistent with #1016's
  distinction that only a needing-auth server has a user-side remedy.
- **Connect-button suppression on share-link surfaces, confirmed via
  `ChatMessage.tsx`**: `showConnect={!controlsContext.isSharedDialog}` is
  passed straight from the existing `isSharedDialog` context flag used
  elsewhere in this file for the same purpose — the informational text
  still renders unconditionally (a code comment notes it's "part of the
  record of how the response was produced"), only the button is withheld.
  Confirmed a second, independent guard inside `McpNeedsAuthNotice`
  itself: the Connect button additionally requires
  `openMcpServersSettings` (from the new `useOpenMcpServersSettings` hook)
  to be non-null, which a code comment states covers routerless hosts
  (component-kit / the Outlook add-in) that have no settings-dialog
  chrome to deep-link into — i.e. the add-in's lack of an equivalent
  "shared" signal is handled by this same fallback rather than being a
  gap, since it has no Router at all and would fail this check regardless.
- **Server identification, confirmed**: the notice joins and displays raw
  server *ids* (`serverIds.join(", ")`), not display names — a code
  comment states the listing API exposes no separate display label, so
  this matches what Settings itself shows for the same servers.
- Per the PR (not independently re-verified given remaining scope): the
  new `useOpenMcpServersSettings` hook centralizes the settings-dialog
  deep-link query-param contract, also now consumed by #1017's
  `McpServerSelector` (refactored in this PR to use the shared hook
  instead of its own inline implementation); the MCP docs page gains a
  "Server selection in chats" section documenting that facets remain the
  chat-side tool-selection primitive, servers reach a chat via facet
  allowlists or assistant attachment, and a facet-less chat offers all
  authorized+connected servers by default.

## Compatibility and configuration

None. Purely additive frontend surface consuming #1016's already-shipped
API field; no configuration or backward-incompatible API changes. A user
who has connected every MCP server their assistants use sees no change at
all, since the notice only renders when `mcp_servers_needing_auth` is
non-empty.
