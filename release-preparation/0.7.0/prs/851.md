# PR #851: Move popover and sidebar-row surfaces out of inline styles

- PR: https://github.com/EratoLab/erato/pull/851
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes two of the documented `data-ui` theming hooks
(`[data-ui="dropdown-panel"]`, `[data-ui="chat-history-item"]`) being
silently inert for a custom `theme.css`, because an inline React `style`
prop always outranks any author CSS rule regardless of specificity or
load order. Per the PR, a real customer theme had already hit this and
worked around it by overriding the underlying CSS custom properties
instead of the documented hook. Confirmed by reading the code:

- `AnchoredPopover`'s panel surface (`backgroundColor`, `borderColor`,
  `borderRadius`, `boxShadow`, `maxWidth`) moves from an inline `style`
  object to a new `.anchored-popover-skin` class in `globals.css`. The
  `style` prop is reduced to only genuinely runtime/computed values
  (`visibility`, and whatever `panelStyle` the caller passes) plus
  positioning, which is written directly to the DOM node in
  `updatePosition()` and untouched by this PR. A dropped `boxSizing:
  "border-box"` is confirmed redundant since Tailwind's preflight already
  sets it globally.
- The sidebar chat row's surface (`minHeight`, `borderRadius`,
  selected-state `backgroundColor`) moves similarly from inline
  `sidebarRowStyle`/`activeSidebarRowStyle` objects to new
  `.sidebar-row-geometry`/`.sidebar-row-selected` classes.
- **CSS placement is confirmed load-bearing and correct**: both new
  classes are declared in `globals.css` *after* `@tailwind utilities`
  (line 3) and *outside* the `@layer components` block (which closes
  around line 1385, before these rules at ~1388+) — verified directly by
  locating both boundaries in the file. This placement is exactly what the
  PR states is required: it lets the new classes still outrank a Tailwind
  utility a caller passes through `panelClassName`/`className` (Tailwind's
  own utilities live inside `@layer utilities`, which the cascade resolves
  before plain, later-declared rules of equal specificity), while
  remaining overridable by a deployment's `theme.css`, which `ThemeProvider`
  appends after this stylesheet.
- Confirmed the PR's claim that the existing tests had been asserting the
  defect: they previously checked the inline style values directly (i.e.
  enforcing that the values stayed inline, the very thing wrong), and are
  now rewritten to assert the new class is applied and that the skin
  longhand properties are *absent* from the inline style. One existing
  test is noted as having been vacuous even before this fix — it expected
  `--theme-border-divider` where the component actually set
  `--theme-border-dropdown`, and passed regardless because jsdom cannot
  resolve `var()` (both sides normalize to an empty string) — not
  independently re-verified against jsdom's actual `getComputedStyle`
  behavior, but a plausible and specific enough claim to trust.
- The PR states this fix was validated by building the actual stylesheet
  and loading it in a real browser with a theme rule appended after it (as
  `ThemeProvider` does at runtime), confirming a themed dark-panel border
  and row radius — both previously inert — now take effect; this
  browser-level verification is not independently reproducible from a
  diff review and is taken on trust.
- The PR explicitly scopes itself as the first of several: 13 of 16
  documented `data-ui` hooks still carry inline skin styling (these two
  were prioritized as the only ones with currently-visible wrong pixels),
  with a follow-up contract test (asserting no skin longhand appears
  inline on any documented hook) proposed once the remaining hooks are
  migrated. One nuance is flagged as deliberately left as-is: the sidebar
  row's `<a>` wrapper reads `--theme-radius-shell` via its own class, so a
  token override keeps both elements in sync, but a theme rule targeting
  `border-radius` directly on the `data-ui` hook itself only reaches the
  inner row element, not the wrapper.

## Compatibility and configuration

No new configuration keys. This is a fix specifically for custom-theme
authors: `theme.css` rules targeting `[data-ui="dropdown-panel"]` or
`[data-ui="chat-history-item"]` for background/border/radius/shadow now
actually take effect, where they previously had no effect at all. No
change for the default/stock theme's rendering.
