## Summary

The convergence of a 17-commit, previously-per-position-reviewed stack
(#1203-#1228, per the PR's own statement — these individual PR numbers do
not appear in this release's PR list, consistent with having been
reviewed and then landed together as this one squash target rather than
merged individually) adding MCP-tool-approval support to delegated
tasks: a task child can now park on an approval instead of having the
call silently refused, the model's own task dispatch can require user
approval before launching, and an extensive new end-to-end test suite
covers the interaction of approvals with the async-task stack this
session has reviewed in detail (#1188-#1202). This is an exceptionally
large PR (18,440 insertions across 80 files) describing seven distinct
backend mechanisms (ERMAIN-757/761/766/769/772/773/844) plus new e2e
infrastructure. Given the scale, this review verified two of the most
concretely-stated, independently checkable claims directly against the
code — one a small, precise regression fix this session could trace
against its own prior review of the affected function, the other a
config-surface claim with clear validation semantics — rather than
attempting to trace all seventeen commits' worth of claims individually:

- **ERMAIN-844's adoption-write fix, confirmed exactly, and directly
  traceable to a bug this session already read the *symptom* comment
  for**: `mark_delegated_run_adopted` previously did a full read-modify-
  write of the whole `assistant_configuration` JSON column
  (`chat_active.assistant_configuration = ActiveValue::Set(Some(configuration.to_json()?));
  chat_active.update(conn).await?`) — exactly the hazard this session's
  own review of PR #1190 already quoted from a *different* function's doc
  comment ("`mark_delegated_run_adopted` above replaces the entire
  `assistant_configuration` column from a possibly stale in-memory row,
  with no transaction and no version guard"). This PR replaces that
  whole-column write with a scoped `jsonb_set` targeting only
  `{provenance,adopted_at}`, gated by `WHERE ... provenance.kind =
  'delegation' AND provenance.adopted_at IS NULL` — a genuine compare-
  and-set. The companion doc comment on
  `requeue_or_supersede_branched_deliveries` (the function whose comment
  originally named this hazard) is updated accordingly to state both
  writers now merge into disjoint JSON paths and "two of them landing in
  either order each keep what the other wrote" — directly confirming
  "Adoption's whole-column write could erase a delivery record. Now a
  path-scoped `jsonb_set`" and closing a real, previously-documented race
  this session had independent evidence of.
- **ERMAIN-769's approval-mode config, confirmed exactly, including the
  inert-by-default framing and the facet-merge strictness rule**: the new
  `DelegationTasksApprovalConfig { mode: TaskApprovalMode, plan_min_tasks:
  u32 }` (nested under `DelegationTasksConfig.approval`) defaults `mode`
  to `TaskApprovalMode::AsyncOnly` ("async_only"), with a doc comment
  stating "it is equivalent to 'never' until 'async' is in
  delegation.tasks.run_modes" — matching "Default `async_only`, which is
  inert until `async` is offered — upgrading changes nothing until you
  opt in" precisely. `plan_min_tasks` defaults to `2` and is validated
  `>= 2` at load (`"must be at least 2"` panic/error, with the comment
  "A threshold of 1 or 0 is not a stricter `plan`, it is `always` under a
  name that promises a review of something with nothing to choose
  between"). Per-facet overrides exist for both fields
  (`FacetDelegationApprovalOverrides`), and `TaskApprovalMode::strictest`
  merges two facets' modes by taking the stricter one via an explicit
  `strictness()` ranking (`Never < AsyncOnly < Plan < Always`) — matching
  the established narrowing-only per-facet-merge convention this session
  has observed repeatedly elsewhere in the delegation config surface
  (e.g. `max_parallel`'s clamping in PR #1181), applied here to policy
  strictness rather than a numeric cap.
- Per the PR (not independently re-verified given this PR's exceptional

## Compatibility and configuration

New config keys, all additive: `delegation.tasks.propagate_child_mcp_approvals`
(default `true`, confirmed), `delegation.tasks.approval.mode` (default
`async_only`, confirmed), `delegation.tasks.approval.plan_min_tasks`
(default `2`, validated `>= 2`, confirmed), plus two per-facet overrides
for the latter two. No migrations (confirmed consistent with no sqitch
files in the changed-files list). Per the PR's own summary, every new
key is "off or inert by default" in the sense that the broader async-
tasks/approval-gated feature set they govern remains behind
`delegation.tasks.enabled` and `run_modes` as established across the
whole stack this session has reviewed (#1188-#1202); `propagate_child_mcp_approvals`
itself defaults `true` but has no observable effect until a task child
can actually encounter an approval-gated MCP call, which requires the
broader feature to be enabled first.

## Release note disposition

Proposed category: Features and enhancements. This PR completes
"Delegation Level D" by adding MCP tool approval support to the async-
delegated-tasks feature reviewed throughout #1188-#1202: a task child
that needs a person's approval for a tool call now parks and asks rather
than having the call silently fail, and a deployment can optionally
require the user's approval before the model's own task dispatch runs at
all (per batch, or only for detaching `async` tasks). Given this PR's own
framing as the convergence of a 17-commit stack, and that the combined
async-tasks feature is still gated behind `delegation.tasks.enabled` with
`run_modes` defaulting to `["wait"]`, this is best treated as the final
major increment to that feature's eventual combined release-note entry
rather than a release-note-worthy change on its own in a deployment that
hasn't opted into the broader feature.
