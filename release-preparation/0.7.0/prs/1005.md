# PR #1005: Detached delegation dispatch: background runs return at launch (ERMAIN-635)

- PR: https://github.com/EratoLab/erato/pull/1005
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Second layer of the background-delegation stack (on #1004): the actual
behavioral change making `delegation_run_mode: "background"` do something.
When the effective mode is `background`, dispatching a
`delegate_to_assistant` call now returns immediately after launching the
child, rather than awaiting its completion. Confirmed by reading the
full `services/delegation.rs` and `message_streaming.rs` diffs:

- `DelegationDispatchOutcome` becomes an enum: `Completed { envelope,
  trace }` for the existing awaited path (unchanged shape/behavior,
  confirmed) versus a new `Dispatched { assistant_id, assistant_name,
  delegate_chat_id }` for a background launch. Confirmed the background
  branch drops both the child's broadcast receiver (`child_rx`, so no
  trace is tapped — #985's trace-streaming machinery simply never
  engages) and the `tokio::spawn` join handle immediately, with a code
  comment stating this is what genuinely detaches the child: no trace
  tap, and a parent abort is no longer forwarded to it (the child keeps
  running independently, stoppable only through its own chat id via the
  existing cross-replica abort mechanism).
- **"No backfill," confirmed precisely**: since the parent's assistant
  message is written once at turn end, the dispatched tool part is
  frozen at its launch shape forever — there is no mechanism, and none is
  added, to retroactively update it once the child finishes. The PR
  states (and the code comment confirms) this is deliberate: how the
  background run actually went is meant to be read off the child chat
  itself (via later layers surfacing it in an origin-chat run list), not
  by mutating history the model would otherwise replay.
- **Two genuinely distinct output shapes for the same dispatch event,
  confirmed via the exact JSON construction**: the value fed to the
  **UI** (`output_value`, rendered by #985's trace-step UI) carries
  `{assistant_id, assistant_name, delegate_chat_id, background: true}`
  with **no `status` field at all** — confirmed the code comment states
  this precisely, because the existing trace-step renderer treats any
  status other than `"completed"` as an error, and the presence/absence
  of `status` (plus the new `background: true` marker) is exactly what a
  later UI layer will key its background-specific presentation off of.
  The value fed to the **model** (the tool's `ToolResponse` content)
  instead carries an explicit `{"status": "dispatched", ...,
  "note": "the result will not be returned to this conversation"}` — so
  the model's own final prose to the user correctly describes work that
  was *started*, not an answer it never actually received.
- The tool-offer description text and the delegation preamble's
  result-disposition sentence are both confirmed to change per run mode:
  for `Background`, the offer explicitly states the tool "returns as soon
  as the run is launched and the delegate's answer will NOT come back to
  this conversation, so the task brief must be fully self-contained — no
  follow-up is possible," and the preamble similarly tells the delegate
  itself that its final message must stand alone since the origin
  conversation won't receive it automatically. The preamble's disposition
  text moves to a `{{result_disposition}}` template placeholder, filled
  per mode — the PR notes a custom deployment template without this
  placeholder simply renders without that section rather than erroring.
- `ChatProvenance` gains a `run_mode` field, confirmed via the diff to
  only ever be written for `Background` (mirroring #1004's persistence
  asymmetry pattern — old envelopes stay byte-identical).
- Explicitly flagged as an interim state, not yet addressed: a detached
  background child has **no bound** on how long it can run or how many
  can exist concurrently — the PR states this is the next layer in the
  stack, with `allow_background` defaulting to `false` serving as the
  only guard until then.

## Compatibility and configuration

None new beyond #1004's `allow_background` gate — this layer makes that
gate actually functional. No behavior change for any deployment without
`allow_background = true`, since a `background` request downgrades to
`wait` without it (per #1004, unchanged here). With it enabled, a
background-mode delegation call now genuinely detaches rather than
blocking the parent turn — this PR's own stated caveat is that such a
detached run is not yet resource-bounded.
