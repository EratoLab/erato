# PR #781: Switch from native-tls to rustls

- PR: https://github.com/EratoLab/erato/pull/781
- Status: pending (diff reviewed)
- Category: Dependency changes
- Theme: Backend image slimming/hardening

## Summary

Switches the backend's TLS implementation from `native-tls` (OpenSSL-backed)
to `rustls` across all crates that make outbound HTTPS/TLS connections, by
changing feature flags in `backend/erato/Cargo.toml` and
`backend/rmcp-sse/Cargo.toml`:
- `sea-orm`: now `default-features = false` with an explicit feature list
  including `runtime-tokio-rustls` (was `runtime-tokio-native-tls`).
- `sqlx`: now `default-features = false` with `tls-rustls` (was
  `tls-native-tls`), plus explicit `json`, `macros`, `migrate`, `chrono`,
  `uuid` features.
- `reqwest` (both `erato` and `rmcp-sse` crates): now
  `default-features = false` with an explicit `rustls` feature (was pulling
  in the default TLS backend).
- `opentelemetry-otlp`: adds `reqwest-rustls` feature.
- `graph-rs-sdk`: now `default-features = false` with `rustls-tls`.
- `sentry`: features changed from `["...", "native-tls"]` to
  `["...", "rustls"]`.

`backend/Cargo.lock` changed by 127 removed / 27 added lines. The full
lockfile diff (not just the earlier-reviewed stat) confirms exactly which
crates left the dependency tree: `openssl`, `openssl-sys`,
`openssl-probe`, `openssl-macros`, `native-tls`, `tokio-native-tls`,
`hyper-tls`, `security-framework` (macOS Keychain integration used by
`native-tls` on macOS), and `foreign-types`/`foreign-types-shared` (FFI
glue used by the `openssl` crate's bindings) — the entire OpenSSL/native-tls
chain, 10 crates total. The only new crate pulled in is `webpki-roots`
(a bundled Mozilla CA root list); `rustls` (`0.23.36`) and
`rustls-native-certs` (`0.8.3`, the crate that loads the OS's own trust
store for rustls) were both **already present** in the lockfile before
this PR (pulled in transitively by some other already-rustls-based
dependency), so this PR does not introduce rustls to the tree — it only
switches which of the backend's own crates use the rustls path that
already existed alongside native-tls.

## Compatibility and configuration

No configuration keys, migrations, or user-facing behavior change. This is
a build-time TLS backend swap; functionally, HTTPS/TLS connections (database,
outbound HTTP, OTLP export, MS Graph API, Sentry) should behave the same
in the common case. One nuance worth flagging: rustls does not use the
operating system's certificate-verification API the way `native-tls` does
(OpenSSL on Linux, Secure Transport/Keychain on macOS via
`security-framework`) — it instead needs an explicit trust source. Because
`rustls-native-certs` (which loads the OS trust store into rustls) is
already a lockfile dependency and is unaffected by this diff, the backend
most likely continues to trust OS/system-installed CA certificates (e.g. an
enterprise-internal CA added to the container's trust store) after this
switch — but this PR's diff does not itself show the call site that wires
`rustls-native-certs` into `reqwest`/`sqlx`/`sea-orm`'s TLS config, so
this is inferred from the dependency graph, not confirmed against the
actual TLS-config code path. The newly-added `webpki-roots` (a bundled,
non-OS Mozilla CA list) is a transitive dependency of one of the
newly-rustls-enabled crates; whether it or the OS trust store is what's
actually consulted at connection time depends on code outside this diff
and was not traced further. A deployment relying on a custom/internal CA
certificate for outbound HTTPS (e.g. to an internal MCP server, chat
provider, or OTLP collector behind a corporate TLS-inspecting proxy)
should verify this explicitly after upgrading, since a silent trust-store
behavior change would manifest as TLS handshake failures rather than a
clear error. Likely motivated by removing the OpenSSL system dependency
from the build/runtime image, complementing the parallel `backend/Dockerfile`
changes in this release cycle (e.g. #782's chainguard base image, whose
own summary notes it drops the explicit `ca-certificates` install step —
consistent with this PR removing the need for OpenSSL's system-level cert
integration).

## Evidence and review

Verified via `git diff fb80522f20eb0df7c180269c00fe44f6eeda3942...1b60fdd7c3fc7a5a1191c12d33c4d20b6b942243`
(PR base/head, both present locally); integration/merge commit
`6c32f6a42d90`. Files read: `backend/erato/Cargo.toml`,
`backend/rmcp-sse/Cargo.toml`, and the **full** `backend/Cargo.lock` diff
(not just the diff stat as in an earlier pass of this summary) — every
added/removed crate name was enumerated and is listed above. Searched the full current repository (`grep -rn "rustls_native_certs\|native_certs\|webpki_roots\|ClientConfig::builder\|rustls::RootCertStore"` across `backend/**/*.rs`) and found **no direct code** constructing a rustls `ClientConfig` or root-cert store anywhere in this codebase — the backend does not wire up TLS trust manually. Trust-store selection is therefore entirely delegated to how `reqwest`'s plain `"rustls"` feature flag (used in `backend/erato/Cargo.toml` and `backend/rmcp-sse/Cargo.toml`; not `rustls-tls-native-roots` or `rustls-tls-webpki-roots` explicitly) resolves its own default dependencies at that pinned `reqwest` version, and similarly for `sqlx`'s `tls-rustls` and `sea-orm`'s `runtime-tokio-rustls`. Since `rustls-native-certs` is present in the lockfile, native/OS trust-store support is at least compiled in, but confirming it is what's actually used by default (versus `webpki-roots`) would require inspecting the pinned `reqwest`/`sqlx`/`sea-orm` crate sources themselves, which are outside this repository. PR description is empty; this summary is based on the Cargo.toml/Cargo.lock diff plus this repository-wide search for TLS-config code.
