## Summary

**Correction to merge-order assumption**: this PR's actual first parent in
the git graph is PR #1368's merge commit (`113deabb5`), not #1364's — the
PR numbers in this batch do not correspond to merge order; #1365 merged
*after* #1366, #1367, and #1368 despite its lower number. Diffed correctly
against `c90239cd8e72f51fb3cf738f6a3f7942d4fdc21b`'s true parent.

Adds read-only Word comment-thread context: the add-in can now send Word
comment threads to the model as context, following a defined precedence
(comments anchored in the current selection, a picked or caret-adjacent
thread, all currently-open comments, or a whole-document comment map,
per the PR's "contract §8" ordering). The model can request more via a new
`word_read_comments` tool, and the chat UI shows exactly what was sent (a
"Sent context" summary line plus a row per comment read).

**Explicitly dark-launched**: per the PR description, "nothing reaches
users until ERMAIN-951 advertises the carriers; until then facet args match
main byte for byte and Word makes no comment calls." This PR ships the
entire comment-reading pipeline, UI (chip, coverage popover, picker, "Show
in Word", a new precedence setting under Word behavior preferences), and
~24,000 lines (mostly tests) inert — a separate, not-yet-landed PR
(ERMAIN-951) is what will actually enable it.

Implementation notes per the PR body (not independently re-verified given
the PR's size and inert status): a shared envelope/parser used by both the
add-in and web app; an Office.js-based reader with per-phase read budgets
plus a separate OOXML reader that joins comment marks by a durable ID
(matched by content in legacy files, by text on the web, since legacy Word
packages lack per-comment date metadata); session-scoped thread references;
and several explicitly documented deviations from the Linear-referenced
design contract (an optional `why` field and `remaining` count not in the
published contract; a `replies_unread` flag for threads where Word's own
replies weren't read; a 3-hour midnight window for `day_uncertain` instead
of the research spec's −14/+12-hour window).
