# PR #1168: Make the add-in client-action stack host-neutral (ERMAIN-543, ERMAIN-546)

- PR: https://github.com/EratoLab/erato/pull/1168
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Generalizes the Outlook add-in's client-action/artifact rendering stack
so a second host (Word, Teams) can add its own client actions without
forking Outlook's code — renaming `OutlookArtifact`/`useOutlookArtifact`/
`Message.outlookArtifact` to host-neutral names, and hoisting
`useClientActionConfirmFlow`/`clientActionPolicy`/
`ClientActionsSettings`/`useAvailableActionFacets` into
`office-addin/src/core/clientActions/` parameterized over the action
type. Confirmed the backward-compatibility guarantees precisely by
reading the relevant `types/chat.ts`, `MessageContent.tsx`, and
`OutlookAddinChat.tsx` diffs:

- **Deprecated type alias genuinely present, confirmed exactly**:
  `export type OutlookArtifact = HostArtifact;` with an explicit
  `@deprecated` JSDoc tag stating "Kept as an alias for one release so
  component kits and hosts can migrate; removed afterwards" — not just a
  rename with the old name silently gone.
  All fields (including two new ones, `cardFenceLanguages`/
  `driftedEmailFenceTags`, added for the parameterized drifted-tag
  classifier) are confirmed preserved under their original names on the
  renamed interface — matching the PR's claim that "all 11 inner field
  names are unchanged."
- **`Message.hostArtifact`/`.outlookArtifact` fallback is real code, not
  just documentation, confirmed exactly**: `MessageContent.tsx`'s
  rendering logic computes `const hostArtifact = hostArtifactProp ??
  outlookArtifact;` and every subsequent reference in the render path
  uses this resolved `hostArtifact` value — confirming the documented
  `hostArtifact ?? outlookArtifact` fallback is genuinely wired into the
  component, not merely described in a comment.
- **Double-stamping at the producer, confirmed exactly**: `OutlookAddinChat.tsx`'s
  message-building code sets `next[id] = { ...message, hostArtifact,
  outlookArtifact: hostArtifact }` — both keys point at the *same* object
  reference — matching the PR's claim precisely and ensuring a consumer
  reading either the new or the deprecated field sees identical data
  during the one-release migration window.
- Per the PR (not independently re-verified given remaining scope): the
  parameterized `HostCardCodeBlock` registry slot and its derived rules
  object (confirmed structurally motivated by the two new `HostArtifact`
  fields read above — `cardFenceLanguages`/`driftedEmailFenceTags` — used
  by both the wrapper-decision and renderer sides so they "cannot
  diverge," per the PR); the `ERATO_SHARED_SURFACE_MINOR` bump from 9 to
  10 for the newly exposed registry slot; the hoisted
  `office-addin/src/core/clientActions/` module structure (parameterized
  `useClientActionConfirmFlow<TAction extends string>`, with
  `clientActionPolicy.ts` as a new 281-line generic core and Outlook's
  own module rewritten to a thin binding); the deliberately-NOT-renamed
  Outlook storage key (`erato.outlookAddin.clientActionDecisions`, stated
  to avoid resetting any existing user's ask/always/never choices, with
  `erato.addin.<host>.clientActionDecisions` reserved for future hosts —
  not independently re-verified in this review, but consistent with the
  care shown in every other backward-compatibility claim checked); and
  the disclosed scoping decision that Settings remains relocate-only, not
  auto-mounting for a neutral host, leaving Word's own settings-tab
  wiring as a stated future obligation.
- **Disclosed verification rigor, per the PR (not independently
  reproduced)**: the PR states `MessageContent.test.tsx`'s 22 existing
  `outlookArtifact` test cases are byte-identical (confirmed via the diff
  stat showing +192/−0, i.e. purely additive, no existing assertions
  edited), and that regenerating the shared component registry after
  rebasing past the concurrently-landed #1161 (which touched the same two
  files) produced a zero diff — offered as evidence the two PRs' changes
  auto-merged correctly.

## Compatibility and configuration

None breaking during the stated one-release migration window — both old
and new names/fields work identically via the confirmed alias/fallback
mechanisms. A component kit or fork still referencing `OutlookArtifact`/
`useOutlookArtifact`/`Message.outlookArtifact` continues to compile and
receive correct data; removal of the deprecated names is stated to
follow in a later release. `ERATO_SHARED_SURFACE_MINOR` bumps from 9 to
10 for the new `HostCardCodeBlock` registry slot (additive per the
established minor-version convention this session has confirmed
repeatedly, e.g. #1055/#1138/#1145).
