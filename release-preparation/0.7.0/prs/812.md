# PR #812: Ensure stable translation ids for assistant/assistant-hub pages

- PR: https://github.com/EratoLab/erato/pull/812
- Status: pending (diff reviewed)
- Category: Chores & Developer experience
- Theme: None

## Summary

Converts Lingui `t\`...\`` macro calls (whose message IDs are auto-derived
by hashing the English source text) to explicit
`t({ id: "some.stable.id", message: "English text" })` calls throughout
all 8 non-locale files in the diff:
`frontend/src/pages/AssistantChatSpacePage.tsx`,
`AssistantCreatePage.tsx`, `AssistantEditPage.tsx`,
`AssistantHubDetailPage.tsx`, `AssistantHubMyPage.tsx`,
`AssistantHubReviewPage.tsx`, `AssistantsListPage.tsx`, and
`assistantHubUtils.tsx`. Every one of these 8 files was read in full for
this summary (not just spot-checked) and confirmed to contain exactly this
one mechanical transformation — `t\`Assistants\`` →
`t({ id: "assistants.title", message: "Assistants" })` — with no wording,
logic, or behavior changes; the English source text is preserved verbatim
at each call site, including interpolated templates (e.g. `t\`Version
${versionNumber}\`` → `t({ id: "assistantHub.version.label", message:
\`Version ${versionNumber}\` })`, identically in all three of
`AssistantHubDetailPage.tsx`, `AssistantHubMyPage.tsx`, and
`AssistantHubReviewPage.tsx`, which duplicate this exact snippet). Some
new IDs are deliberately shared across files for identical English text
(e.g. `assistant.loading` / "Loading assistant..." appears in both
`AssistantChatSpacePage.tsx` and `AssistantEditPage.tsx`), so a single
stable key now backs several call sites rather than each getting its own
hash.

The bulk of the diff (~1180 of 1347 added lines) is in the five
`frontend/src/locales/*/messages.po` files. Spot-checking the `en` locale
file's exact rename mechanics confirms the expected pattern precisely:
each renamed string's old hash-ID entry (e.g. `msgid "Assistant created
successfully!"` / `msgstr "Assistant created successfully!"`) is marked
obsolete with a `#~` comment prefix (Lingui's convention for "no longer
referenced, kept for history" rather than being deleted outright), and a
new entry appears with the stable ID as `msgid` (e.g. `msgid
"assistant.create.success"`), the original English text preserved as
`msgstr`, and a `#. js-lingui-explicit-id` marker comment identifying it
as an explicit (non-hash) ID — the same marker/shape referenced by the
later JIT-compilation fix in #945 this cycle. With hash-derived IDs, any
future edit to the English source text would silently mint a new message
ID and orphan existing non-English translations of the old text; stable,
hand-assigned IDs decouple the translation key from the exact source
wording.

## Compatibility and configuration

No configuration keys or migrations. No end-user-visible text changes.
Deployments that maintain external translation overrides keyed by the old
auto-generated (hash-based) message IDs for these specific strings would
need to update those keys to the new stable IDs — relevant given the
config-mirroring work for `.po` files elsewhere this cycle (#897, #914,
#989, #991).
