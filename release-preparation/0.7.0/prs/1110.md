# PR #1110: Select reserved `erato/*` tools with the client-tool collector (ERMAIN-758)

- PR: https://github.com/EratoLab/erato/pull/1110
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 1, PR 4 of 4 (final), on top of #1107–#1109. Adds the selection
machinery for how a reserved `erato/*` built-in tool (like #1107's
reserved namespace) would be offered to the model, plus load-time
warnings for ways an operator could misconfigure it into silently doing
nothing or breaking MCP tool access. Explicitly non-functional yet — no
tool is registered under this machinery in this PR (the task route's
`delegate_task` tool registration is deferred to a later PR), so this
changes no currently-offered tool set. Confirmed by reading the complete
relevant sections of both `message_streaming.rs` and `config.rs`:

- **Opt-in selection semantics, confirmed exactly**: `reserved_tool_selected`
  returns `ReservedSelection::No` immediately when the client-tool
  allowlist is empty — a doc comment states precisely why this differs
  from MCP allowlisting: `build_mcp_tool_allowlist` treats an absent/`None`
  allowlist as "everything allowed," which would make every reserved
  built-in offered by default in a deployment with no MCP allowlist
  configured, so the client-tool collector is deliberately used instead,
  where empty means nothing is selected.
- **`ReservedSelection::{No, Pattern, Exact}` and the MCP-wins precedence,
  confirmed exactly**: `synthetic_tool_offer_slot` consolidates the
  feature gate, the selection check, MCP-name-collision precedence, and
  delegated-run suppression (`!feature_enabled || is_delegated_run` return
  `false` immediately) into one function. When an MCP tool claims the same
  bare name, the built-in stands down in both cases, but confirmed the
  diagnostic severity differs exactly as described: `tracing::error!` when
  the allowlist named the tool by its *exact* `erato/<name>` pattern (an
  operator explicitly asked for it and got silently overridden), versus
  `tracing::warn!` when it was only matched by a wildcard pattern.
- **Reserved patterns dropped from facet template expansion, confirmed by
  the code comment and surrounding diff**: a new filtering step precedes
  `expand_tool_patterns_with_discovered_tools`, with a comment stating
  reserved patterns name a built-in, not a discovered MCP tool, and would
  otherwise render literally (e.g. `erato/delegate_task`) in a planning
  facet's prompt template as if it were a real discovered tool.
- **All three disclosed load-time warnings, confirmed exactly matching
  the PR's own description, including the "operator trap" condition's
  precise logic**: (1) `delegation.tasks.enabled` true with no global or
  per-facet allowlist selecting `DELEGATE_TASK_TOOL_NAME` warns that the
  tool will never be offered; (2) a facet with `delegation.is_some()`
  whose own allowlist doesn't select the tool warns that its overrides
  never apply; (3) the trap — a facet whose `tool_call_allowlist` is
  non-empty, every pattern in it names only the reserved namespace
  (`pattern_names_reserved_namespace`, which deliberately excludes a bare
  `*` per its own dedicated test), *and* the global allowlist is empty —
  warns that selecting this facet removes every MCP tool from the turn,
  since an empty global allowlist normally means "no restriction," and
  adding any facet-level pattern flips the derived filter into a concrete
  (here: empty-of-MCP-tools) set. All three warnings are confirmed
  non-fatal (`startup_log::warn_preinit`, not a panic).
- **`delegate_to_assistant` deliberately left un-gated, confirmed by a
  code comment at the offer site**: the existing @-mention delegation
  tool's offer condition remains validated-mentions-plus-`delegation
  .assistants.enabled`, explicitly not passed through the new allowlist
  machinery — the comment states gating it would silently disable
  in-chat delegation for every deployment whose facets already carry
  narrow allowlists, which was judged worse than the inconsistency of one
  synthetic tool bypassing the new selection mechanism.
- Per the PR (not independently re-verified): the disclosed testing
  limitation that the three warnings are asserted only indirectly (each
  trap configuration is tested to still boot and preserve the operator's
  values, plus direct unit tests of the selection predicates that decide
  whether a warning fires) because `startup_log`'s internal buffer is
  private and not readable from tests — stated as a reasonable follow-up
  if the messages themselves need pinning, not attempted here.

## Compatibility and configuration

None. No new config keys (confirmed the PR states
`just check_config_reference_docs` reports no new keys), no change to any
currently-offered tool set (the reserved-tool selection machinery exists
but has no registered tool to select yet in this PR). Purely additive
groundwork.
