# PR #1117: Keep the selected microphone across device-list churn (ERMAIN-795)

- PR: https://github.com/EratoLab/erato/pull/1117
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a real, reproduced bug: picking a non-default microphone in
Preferences → Audio silently reverted to "System default microphone."
Root cause was an auto-clear effect in `useAudioInputDevicePreference`
that every mounted instance of the hook ran independently (the
Preferences tab *and* the transcription/dictation recorders in
`ChatInput`), wiping the shared stored device id whenever that
instance's own enumerated device list didn't contain it — including
transiently, before microphone permission had been granted, when Chrome
returns a single placeholder device with an empty `deviceId`. Confirmed
by reading the complete `useAudioInputDevicePreference.ts` diff and the
relevant `useAudioDictationRecorder.ts` diff:

- **The auto-clear effect is removed entirely, confirmed exactly**: the
  `useEffect` that compared `selectedAudioInputDeviceId` against the
  instance's own `audioInputDevices` list and called
  `setSelectedAudioInputDeviceId("")` when absent is deleted outright,
  not merely narrowed — closing both bug triggers the PR describes (the
  pre-permission placeholder-list false clear, and any later enumeration
  that transiently omits the selected device, e.g. Bluetooth auto-switch).
- **Recorders no longer enumerate at all, confirmed exactly via
  `useAudioDictationRecorder.ts`**: the recorder previously called
  `useAudioInputDevicePreference({ enabled })` (the full enumerating
  hook, which is what ran its own copy of the now-deleted auto-clear
  effect); it now reads `selectedDeviceId` directly from
  `useAudioInputDeviceStore` via a plain selector, with no enumeration of
  its own — confirmed matching the PR's stated fix that only the
  Preferences tab enumerates now, and no instance validates the shared
  value against a possibly-transient local list.
- **Capture-time fallback no longer wipes the stored preference,
  confirmed exactly**: the `getUserMedia` retry-with-default-constraints
  path (on `OverconstrainedError`, now also `NotFoundError`, per the code
  comment addressing a genuine race between enumeration and capture) no
  longer calls a clear-preference setter at all — it falls back to the
  system default for that capture attempt only, leaving the stored
  selection untouched for the next session.
- **Gated, resolved-state device-id tracking added, confirmed exactly**:
  a new `hasResolvedDeviceIds` state is set `true` only when
  `audioInputs.length > 0 && audioInputs.every(device => device.deviceId
  !== "")` — i.e. only once real (post-permission) device ids are known,
  distinguishing the placeholder pre-permission state from a genuine
  resolved list — matching the PR's stated use of this to gate the
  "unlisted stored device" UI hint so it doesn't fire on the placeholder
  state.
- **Device label persisted alongside the id, confirmed exactly**: the
  store gains `selectedDeviceLabel`/`setSelectedDevice(deviceId, label)`
  (replacing `setSelectedDeviceId`), and the hook exposes
  `selectedAudioInputDeviceLabel` — per the PR (not independently
  re-verified in `AudioInputTabContent.tsx`), consumed to show an
  unlisted-but-stored device as "&lt;label&gt; (not connected)" with a
  hint, rather than silently falling back to the default.

## Compatibility and configuration

None. Pure frontend bug fix; no API or configuration changes. Fixes a
user-facing preference-persistence bug affecting any user who selected a
non-default microphone, particularly Bluetooth/AirPods users and anyone
granting microphone permission from inside the Preferences dialog itself.
