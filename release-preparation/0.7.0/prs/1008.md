# PR #1008: Derive a delegated run's outcome from its chat so completion survives retention (ERMAIN-638)

- PR: https://github.com/EratoLab/erato/pull/1008
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Fixes a real gap that would have undermined the whole point of background
delegation: a background run's completion was only observable within the
60-second retention window after it finished (#868's generation-status
retention), by a client that happened to already be watching when it
started — so "3 runs finished while you were away" (the actual use case
for background mode) was inexpressible. Rather than adding a new table or
extending retention, this derives a run's outcome directly from the chat's
own message data, confirmed via full read of the SQL in `models/chat.rs`.

- `RecentChat` gains `delegated_run_outcome: Option<String>` —
  `"completed"`, `"failed"`, or absent (while the run is live/parked, or
  for any non-delegated chat).
- **Both correctness safeguards the PR calls out are confirmed present
  and correctly implemented in the SQL**:
  1. **Non-empty text required** (`has_text_answer`, checking the latest
     message's `content` array for a `text`-typed part whose trimmed text
     is non-empty). Confirmed this exists because the assistant message
     row is created *before* generation starts, so a hard-killed run
     (replica crash, a SIGKILL past the abort-grace window from #981)
     leaves an empty assistant "husk" as the latest message — without this
     check, once retention eventually clears the `errored` generation
     state, nothing would distinguish that husk from a real completion.
  2. **`latest_msg.created_at >= chats.created_at`**. Confirmed this
     guards against #979's `seed_chat_lineage`, which copies a parent
     conversation's messages *preserving their original timestamps* —
     meaning a seeded parent message necessarily predates the child chat
     itself. Without this floor, a run killed between context-seeding and
     ever producing its own brief could have the seeded parent's own
     answer misread as if it were the delegate's own completed response.
  3. A generation-error check (`NOT has_generation_error`, reading
     `generation_metadata.error` the same way the delegation result
     envelope already does) and `generation_state IS DISTINCT FROM
     'errored'` round out the `completed` condition; anything failing any
     of these falls through to `'failed'`.
- Confirmed a deliberate, documented edge case: a user-aborted run that
  persisted a partial answer reads as `completed`, not `failed` —
  consistent with `derive_outcome` (from #981/#1006) already mapping an
  abort to `Completed` rather than a distinct cancelled state, so
  reporting it as `failed` here would contradict the system's own existing
  outcome classification elsewhere.
- For the frontend, this establishes a clean three-way signal on a
  delegated run: `active_generation_started_at` (running),
  `pending_tool_approval_at` (parked on approval, from #918/#982), and now
  `delegated_run_outcome` (terminal, durable indefinitely) — with no
  overlap between the three states by construction (the `NULL` branch of
  the `CASE` covers exactly the running/awaiting-approval states the other
  two fields already represent).

## Compatibility and configuration

None. Purely additive field on `RecentChat`; `null`/absent for any
existing or non-delegated chat, so no behavior change for any existing
client. No configuration changes — reuses the existing
`generation_status.stale_after_secs` config value already used elsewhere
for heartbeat staleness.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Full diff read for `models/chat.rs` — confirms both of
the PR's stated correctness safeguards (the non-empty-text requirement
and the timestamp floor against seeded-lineage copies) are precisely
implemented as described, along with the generation-error check and the
documented abort-reads-as-completed edge case. Not read in full: the
`server/api/v1beta/mod.rs` diff (10 lines, response wiring) or the
443-line new integration test suite, though its described coverage
(retention-survival, each failure shape individually, the aborted-partial
edge case, live/non-delegated exclusion) is a direct and appropriate test
of the SQL logic verified above.
