# PR #1166: Render what a delegated task actually ran (ERMAIN-775)

- PR: https://github.com/EratoLab/erato/pull/1166
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 2, PR 5/5 — the final PR in the "dynamic delegated tasks" series
(#1162–#1166), on top of #1165. Purely frontend rendering: shows the
brief the model wrote for a task's sub-task in the trace step, since a
task child under the default persona is otherwise indistinguishable from
an @-mention run by identity alone. Confirmed by reading the complete
relevant `DelegationStep.tsx` diff and the `DelegatedRunHeader.test.tsx`
addition in full:

- **Brief rendered only on the task route, confirmed exactly**: `brief =
  part.tool_name === DELEGATE_TASK_TOOL_NAME ? taskBrief(part.input) :
  undefined` — discriminated purely by `tool_name`, consistent with the
  rule #1162 established this session already confirmed (discriminate by
  tool name, never by a missing/present assistant name). A mention
  step's `brief` is always `undefined`, matching the PR's stated
  rationale that a mention step already names its delegate, and its
  brief would just repeat the visible conversation.
- **Bounded like the result, confirmed exactly**: `taskBrief` truncates
  to `BRIEF_PREVIEW_CHARS = 160` characters (code-point-aware, via
  spreading the string), directly analogous to the existing
  `RESULT_PREVIEW_CHARS = 280` bound for the delegate's answer — matching
  "bounded like the result" precisely, including the same "the step is a
  summary, the run itself is one click away" design rationale stated in
  both constants' comments.
- **The delegated-run header deliberately left alone, confirmed exactly
  via its own added test**: `DelegatedRunHeader.test.tsx` gains one new
  test asserting a bare-persona run (`assistantName: undefined`) still
  renders the generic "Delegated run" text rather than any
  task-specific label — with a code comment in the test itself stating
  the exact reasoning the PR's description gives: a task child dispatched
  on the bare model has no assistant name, and one dispatched under the
  default persona is indistinguishable from a mention run at the API
  level, so the header correctly avoids claiming a distinction the data
  doesn't actually support. Confirmed no source change accompanies this
  test — `DelegatedRunHeader.tsx` itself is untouched in this diff.
- Per the PR (not independently re-verified): the two other explicitly
  disclosed scope-narrowing decisions — the runs-list row being
  deliberately excluded from this stack (since that list only shows
  background runs via `provenance_run_mode === "background"`, and an
  awaited task run in this stack stores no run mode at all, so no task
  child from this PR series could ever appear there; that's reserved for
  a later async-route stack, ERMAIN-780/782) — and `delegationTasksEnabled`
  reaching `env.ts` but going unconsumed, since `AssistantsFeatureConfig`
  has no tasks field yet and rendering itself keys purely on `tool_name`,
  needing no feature flag at all.

## Compatibility and configuration

None. Pure frontend rendering addition for the not-yet-user-facing
`delegate_task` feature (gated behind `delegation.tasks.enabled` plus a
facet allowlist selection from #1164, off by default). No behavior
change for the @-mention delegation route.
