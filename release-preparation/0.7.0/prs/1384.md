# PR #1384: Word: add, reply to, resolve and edit comments behind consent, as you or as Erato (ERMAIN-949) (#1384)

## Summary

Per the PR's own body, explicitly confirmed by the `config.rs` diff
(default validation, new settings struct): lets the Word add-in add,
reply to, resolve, reopen, edit, and delete comments behind a consent
card, posted either as the user (with a configurable label) or — on Word
for Windows and Mac — as "Erato (AI) for `{user}`". **The PR's own body
states this "ships dark: nothing reaches users until ERMAIN-951
advertises the tool and actions"** — i.e. this PR lands the capability
but does not itself expose it to any model/client_action configuration,
so it is inert on its own.

- **Three new client actions, confirmed via `config.rs`**:
  `word.add_comments`, `word.respond_to_comments`, `word.modify_comments`
  — validated to require `grant_scope` (if set) to only ever apply to
  `word.*` actions, to already be present in the facet's
  `client_actions`, and to be one of exactly `"device"` or
  `"session_document"` (`ACTION_FACET_GRANT_SCOPES`).
- **New `integrations.ms_office.addin.default_settings` fields, confirmed
  exactly**: `comment_label` (default `"Erato AI:"`, ≤40 plain-text
  chars, validated), `comment_author` (`user` default or `assistant`),
  `comment_author_enforced` (bool, locks the user out of changing it),
  `comment_assistant_author` (default `"Erato (AI) for {user}"`, must
  contain `{user}` exactly once, ≤60 chars, validated), and
  `comment_writes` (per-action-class `post`/`copy` mode plus
  `max_rows` caps on `add`/`respond`/`modify`, each 1-50, default 50 new
  comments / 20 other changes per the doc comment).
- Every write re-verifies its target before acting (reusing the
  ERMAIN-955/983 verification rules this cycle's other Word PRs
  established) and reports one of a fixed outcome set
  (applied/applied_as_user/unchanged/refused+code/failed/unverified);
  Revert is single-use. A new `HIDDEN_TEXT` web-only refusal exists
  because root comment writes there would otherwise un-hide hidden text
  in the paragraph (replies are unaffected) — the read-side counterpart
  of this exact issue was fixed separately in #1383.
- Per the PR (not independently re-verified): the actual comment
  read/write implementation in
  `frontend/src/lib/wordReview/wordCommentChanges.ts` (325 new lines) and
  its 109-line test file, and the `message_streaming.rs`/
  `ClientActionsSettings.tsx`/`clientActionPolicy.ts` wiring that offers
  these as model-facing tools once a deployment configures them.

## Compatibility and configuration

**Additive and inert by default**: all three `word.*` comment actions
require explicit `client_actions` configuration on an action facet before
anything reaches a user (confirmed by the PR's own "ships dark" framing
and by the `grant_scope` validation requiring the action already be
listed in `client_actions`). All new `default_settings` fields have safe
defaults (post as the user, with the "Erato AI:" label, uncapped at the
documented 50/20 row caps). No database migration.
