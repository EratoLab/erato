# PR #1102: Let theme packs declare optional assets instead of 404ing on them

- PR: https://github.com/EratoLab/erato/pull/1102
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a real, observed production issue: a theme pack shipping neither the
assistant avatar nor the sidebar logo had no way to say so, so every
branded deployment received a by-convention path regardless of whether
the file existed, and `Avatar`/the sidebar logo rendered it unconditionally
— producing one failed GET per avatar mount (i.e. per assistant message)
and a repeated probe for the sidebar logo, with no configuration able to
suppress it. Confirmed by reading the complete `resolveThemeAssetPath`
function and its surrounding `ThemeProvider.tsx` diff in full:

- **`theme.json` gains a tri-state `assets` block, confirmed exactly**:
  a key can be omitted (fall back to filename convention, probed once),
  set to an object with `path`/optional `darkPath` (trusted, never
  probed), or set to `null` (declared absent, never requested at all).
- **The `null`-vs-absent distinction is genuinely load-bearing in the
  code, confirmed exactly**: `resolveThemeAssetPath` tests `assets && key
  in assets` rather than truthiness — a code comment states precisely why
  this matters: `assets["sidebarLogo"] ?? fallback` or any truthiness
  check would collapse an explicit `null` declaration into
  "undeclared," silently reintroducing the exact convention-path request
  the declaration exists to suppress. The `null` branch returns
  immediately with no path and no probe.
- **Four-tier precedence, confirmed exactly matching the code's own doc
  comment**: (1) an environment override (`VITE_ASSISTANT_AVATAR_PATH`/
  `VITE_SIDEBAR_LOGO_PATH`/`VITE_SIDEBAR_LOGO_DARK_PATH`) wins
  unconditionally and is never probed, since setting it asserts the file
  exists; (2) a `theme.json`-declared path is trusted and never probed;
  (3) an explicit `null` declaration stops resolution with no request;
  (4) with no declaration at all, the convention path is probed once via
  `probeAssetOnce`. Confirmed the light/dark asymmetry is deliberate: a
  light-mode env override does not substitute for a missing dark one, so
  a deployment mixing an env override with a `theme.json`-adjacent dark
  file keeps getting the dark file in dark mode.
- **Resolution gated on theme-load settling, confirmed exactly**: a new
  `isThemeLoadSettled` state is set `false` at the start of a theme load
  and only `true` once it completes (for both the custom-theme and
  no-custom-theme branches) — a code comment states this prevents
  resolving assets while `customThemeConfig` is still `null`, which would
  otherwise make a pack's "declared absent" indistinguishable from "not
  loaded yet" and fire the convention-path request regardless.
- **Probe memoization, confirmed exactly**: `assetProbeCache` is a
  module-level `Map<url, Promise<boolean>>` (not a boolean cache), with
  `probeAssetOnce` returning the cached in-flight promise on a second
  call — confirmed this means a missing convention-based asset costs one
  HEAD request per page load total (shared across every avatar mount),
  not one per component instance as before.
- Per the PR (not independently re-verified given remaining scope):
  `Avatar.tsx`'s 18-line diff switches to reading `assetPaths.
  assistantAvatar` from a new non-throwing `useOptionalTheme` hook (so
  rendering `Avatar` without a provider — tests, stories — stays valid);
  `ChatHistorySidebar.tsx`'s duplicate `checkFileExists` probe (40 lines
  removed) is deleted in favor of the centralized resolution; and
  `themeConfig.ts`/`themeUtils.ts` gain the supporting
  `resolveDeclaredAssetPath`/`THEME_ASSET_KEYS`/`ThemeAssetKey` types and
  path-resolution rules (matching the existing `icons` resolution rules:
  `./x.svg`/bare `x.svg` resolve against the theme pack directory, `/x.svg`
  is deployment-absolute, absolute URLs pass through).

## Compatibility and configuration

None breaking. New optional `assets` block in `theme.json` — absent for
every existing theme pack, so resolution falls through to the same
filename-convention probing behavior as before (now memoized instead of
per-mount, which is itself a fix, not a behavior change in what gets
requested). A theme pack author can now add `"assets": { "sidebarLogo":
null }` (or similarly for `assistantAvatar`) to eliminate the repeated
404s this PR documents as the observed production symptom.

Proposed category: Bug fixes. Worth a mention: theme packs can now
