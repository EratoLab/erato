# PR #1118: Give every dropped file feedback and stage drops through a visible pipeline

- PR: https://github.com/EratoLab/erato/pull/1118
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Large UX fix (2327 lines) giving every dropped file visible feedback on
both the web app and the Outlook add-in: wrong-type/oversized rejections
are named, a mixed batch uploads its supported files while naming only
the unsupported ones, and the add-in's email-drop staging shows a visible
multi-phase pipeline. Given the scope, review focused on the two most
concrete, testable behavior changes. Confirmed by reading the complete
`validateFileSizes.ts` and the relevant `useFileDropzone.ts` diffs:

- **Type-vs-size rejection precedence, confirmed exactly**:
  `oversizedRejectionNames` now filters out any rejection that also
  carries the `file-invalid-type` code before checking for
  `file-too-large`, via a new shared `rejectionNames(rejections, code)`
  helper — a file that is both wrong-type and too-large is named only in
  the unsupported-type error, matching the PR's stated "type wins in one
  place" design.
- **Partial batch upload — a genuine, disclosed behavior change,
  confirmed exactly**: the preflight capability check in `useFileDropzone.ts`
  previously threw `UnsupportedFileTypeError` and aborted the *entire*
  batch when any file failed validation (the removed code comment
  literally read "If there are invalid files, throw error and don't
  upload ANY files"). It now calls `setError(...)` to report the
  unsupported names and continues with `files = valid`, returning early
  only when `valid.length === 0` — so a mixed drop (e.g. a supported PDF
  alongside an unsupported zip) now uploads the PDF while naming only the
  zip as rejected, matching the PR's headline claim precisely. Confirmed
  a subtlety handled correctly: since `uploadFiles` itself clears the
  error slot at the start of its own run, the drop handler re-sets the
  unsupported-type error *after* `uploadFiles` resolves (in a `.then`),
  so the accepted-files upload's own error-clearing doesn't silently wipe
  the still-relevant unsupported-file report.
- **Raw-text catch-all removed, confirmed exactly**: the previous
  `onDrop` rejection handler's fallback branch (joining every rejection's
  raw `error.message` strings into one opaque `UploadUnknownError`) is
  removed entirely, replaced by the structured `rejectionNames`-based
  type/size classification — matching the PR's stated removal of
  `useFileDropzone`'s raw-text `UploadUnknownError` catch-all.
- Per the PR (not independently re-verified given the very large
  remaining scope): the add-in's new `useDropPipeline()` hook
  (`idle|receiving|reading|resolving|staging` phases, with an idempotent
  `begin(total)`/`progress()`/`stage()`/`end()` API and nested-drop
  pending-counter semantics); the new two-pass `parseDroppedFiles`
  (sequential email-unit reading in pass 1, `mapWithConcurrency`-bounded
  `.msg` mailbox lookups at a concurrency limit of 4 in pass 2, claiming
  in original input order); the new `yieldToRenderer()` utility
  (`scheduler.yield()` where available, else `setTimeout(0)`) called
  before each pipeline step so progress UI paints during long batches;
  the forwarded-email naming cap (`nestedMessageName` falls back to
  `message.eml` above 2 MiB); the skipped-email feedback surface
  (`no-fetcher`/`unparseable` reasons, one localized message per reason);
  and the identical wrong-type/partial-batch fix applied to the other
  four upload surfaces (`useConversationDropzone`, `useChatFileSources`,
  `FileUploadButton`, `AssistantFileUploadSelector`) beyond the one
  (`useFileDropzone`) read directly.

## Compatibility and configuration

None breaking. Real, intentional behavior changes: a mixed-validity file
drop now uploads its valid files instead of rejecting the whole batch
(disclosed as the headline fix); drops in the Outlook add-in now show
visible staging progress instead of an unexplained pause. No API or
configuration changes.
