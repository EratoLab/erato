# PR #981: delegate_to_assistant: tool offer, dispatch branch, awaited child run (ERMAIN-622)

- PR: https://github.com/EratoLab/erato/pull/981
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Fourth and largest layer of the 5-part delegation stack (on top of
#980): the actual runtime that offers a `delegate_to_assistant` tool on
mention-carrying turns, dispatches it, runs the mentioned assistant as an
awaited child chat, and returns a result envelope to the parent turn.
Given this is the highest-stakes layer in the whole series (real agentic
recursion, with real timeout/abort/resource-safety implications), review
targeted the specific safety properties most likely to be wrong if this
were rushed — all confirmed by direct code reading against the live
source at this PR's head commit.

- **Delegation depth is capped at one, confirmed exactly**: mentions
  submitted from inside an already-delegated child chat are rejected with
  `400` ("Assistants cannot be mentioned inside a delegated run"), checked
  via a new `chat_is_delegated_run` flag before any other validation —
  the code comment states plainly why this exists: a delegated run never
  offers the tool anyway, so an unrejected mention there would validate
  and then silently do nothing, which is worse than an explicit error.
  The child's own provenance records `depth: parent_depth + 1`, so even if
  a future change relaxed the "never offer" rule, depth tracking is
  already in place.
- **The child run's future is explicitly boxed** (`Box::pin(async move {
  ... })`) — confirmed present in the dispatch code. This matters because
  a nested generation future would otherwise make the parent turn's own
  future recursively sized (each level of delegation nesting adding the
  full size of the inner generation future to the outer one) — directly
  relevant given #976 already needed to bump the Tokio worker stack size
  to 16MiB for the *non-recursive* case; an unboxed recursive future here
  could have made that problem arbitrarily worse.
- **Timeout/abort handling never hard-cancels the child, confirmed
  exactly**: both the parent-abort-forwarding path and the
  `run_timeout_seconds` timeout path follow the identical pattern —
  request a cooperative abort on the child task, then wait a bounded grace
  period (`CHILD_ABORT_GRACE`) for it to actually stop; if it doesn't,
  the child is explicitly **detached** (a `tracing::warn!` is logged, but
  the task is left running to finish on its own) rather than forcibly
  killed. The code comment states this precisely: a hard cancel would
  skip the child's own cleanup tail (persisting a final state, releasing
  its generation lease, closing its DB listener), leaking those resources
  — so "never hard-cancel" is a deliberate resource-safety choice, not an
  oversight.
- **Suppression inside a delegated run, confirmed at multiple independent
  call sites**: `crate::models::chat::chat_is_delegated_run(&chat)` is
  checked — freshly, from the chat row, not a cached flag — at every
  relevant offering point in `message_streaming.rs`: gating whether client
  tools are offered at all, whether the `delegate_to_assistant` tool
  itself is offered (preventing depth-2 delegation), and whether an
  approval-gated MCP tool call is parked awaiting user approval or refused
  outright in-run (confirmed via a distinct branch,
  `if !has_active_always_allow && is_delegated_run`) — matching the PR's
  claim that a delegated child always resolves to a terminal state
  (`completed | failed | timeout | cancelled`) and is never left stuck in
  an `awaiting_approval` state a human can never see or act on (since
  there's no UI surface for a delegated child chat).
- Per the PR (not independently re-verified in this review, given the
  remaining scope): the tool offer itself enum-constrains `assistant_id`
  to the validated mention targets and `file_ids` to the parent chat's own
  attachments (pass-by-reference, not copy); every dispatch-time failure
  (an unoffered target, malformed arguments, a foreign file id, or a
  target archived/access-revoked since validation) refuses the individual
  tool call rather than aborting the whole turn — matching the general
  "refuse the call, not the turn" pattern from #828; the child chat is
  seeded from the parent's replay anchor via #979's `seed_chat_lineage`
  when conversation context is requested, with #979's ContextRebase then
  giving it the delegate assistant's own prompt head; and the final result
  is explicitly bound to the child task's own assistant-message id, stated
  to prevent seeded (copied-in) history from being mistaken for the
  delegate's actual answer.

## Compatibility and configuration

None new beyond #978's existing `[assistants.delegation]` config gate,
still entirely inert unless `assistants.delegation.enabled = true`. The
`delegate_to_assistant` tool name joins the existing reserved-name list
(from #802/#786's client-tools collision-guard machinery) so it can't be
accidentally shadowed by a same-named MCP or client tool; MCP tools still
win any name collision, per the established precedence.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read directly at the commit's own head state (rather
than only the unified diff, to see full function bodies in context):
the depth-1 rejection and provenance-depth recording, the `Box::pin`
future-boxing, both the abort-forwarding and timeout grace/detach
branches with their code comments, and every `chat_is_delegated_run` call
site in `message_streaming.rs` gating client-tool/delegation-tool
offering and MCP approval handling. Given the exceptional scope of this
layer (2652 insertions, ~1631 of them integration tests per the PR's own
count), the tool-offer construction itself, the full dispatch branch's
argument validation, and the file pass-by-reference mechanism were not
independently re-traced beyond confirming the safety properties above —
those are lower-consequence-if-wrong than the recursion/resource-safety
properties prioritized here.

## Release note disposition

Proposed category: Features and enhancements — the first functionally
complete layer of the delegation stack (with #982's listing layer still
to come). Worth a clear mention once the full stack lands: the assistant
can delegate part of a task to another @-mentioned assistant within the
same chat, running it as a bounded, awaited sub-task with its own timeout
and no further nested delegation.
