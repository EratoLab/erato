# PR #1274: Fix undefined client-operation cursors and button timer cleanup

- PR: https://github.com/EratoLab/erato/pull/1274
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Two independent fixes bundled together. Confirmed both precisely and in
full:

- **The core bug and its fix, confirmed exactly**: `resolveUrl`'s
  `queryParams` type widens from `Record<string, string>` to
  `Record<string, unknown>`, and the URL-building logic changes from
  `new URLSearchParams(queryParams).toString()` (which stringifies an
  `undefined` value to the literal text `"undefined"`, producing
  `?after=undefined`) to `new URLSearchParams(Object.entries(queryParams).filter(([,
  value]) => value !== undefined).map(([key, value]) => [key,
  String(value)])).toString()` — omitting any key whose value is
  genuinely `undefined` before building the query string. This directly
  confirms "Fresh client-operation polls sent `after=undefined`, which
  the backend rejected as an invalid UUID with HTTP 400. Omit undefined
  query parameters."
- **Every other value type is preserved exactly as before, confirmed
  exactly by a dedicated test with deliberately tricky values**: a test
  passing `{ after: undefined, limit: 0, active: false, empty: "", q: "a
  b&c+ü", literal: "undefined", nullable: null }` asserts the resulting
  URL is `?limit=0&active=false&empty=&q=a+b%26c%2B%C3%BC&literal=undefined&nullable=null`
  — confirming falsy-but-defined values (`0`, `false`, `""`) are kept
  (not swept up by a naive "drop falsy" fix), URL encoding is unchanged,
  a value that is the *string* `"undefined"` is preserved distinctly
  from an actual `undefined`, and `null` still serializes (only
  `undefined` specifically is filtered) — matching "Defined values, URL
  encoding, and subsequent UUID cursors retain their existing behavior"
  precisely. The same test also asserts the original `queryParams`
  object (frozen via `Object.freeze`) still has its `after` key present
  afterward, confirming the fix never mutates the caller's input.
- **The fix survives clean codegen regeneration via the existing
  postprocessor, confirmed exactly, including its fail-loudly guarantee**:
  a new `fixFetcherQueryParams` function is added to
  `fix-codegen-types.mjs`, applying the identical type-widening and
  filter-based replacement to a freshly generated fetcher file; it skips
  a replacement already present (idempotent across repeated runs via
  `if (content.includes(to)) continue;`) and throws an explicit error —
  "Unexpected fetcher query parameter template; update
  fixFetcherQueryParams before regenerating" — if the expected original
  text isn't found exactly once, rather than silently failing to apply.
  A dedicated test (`generatedFixture`) genuinely runs the real
  `@openapi-codegen/typescript` generator against a minimal OpenAPI
  fixture, applies the real postprocessor script as a subprocess, and
  transpiles/executes the *actual resulting generated code* via
  TypeScript + Node's `vm` module against a mocked `fetch` — confirming
  the patched fetcher really omits an `undefined` `after` while
  preserving a defined one, that the patch is a no-op on a second
  application, and that regenerating from scratch and re-patching
  produces byte-identical output. A second dedicated test deliberately
  corrupts the generated serializer line and asserts the postprocessor
  exits with status 1 and the exact documented stderr message — directly
  confirming "The patch is idempotent and fails clearly if the generator
  template changes."
- **Regression tests exercise the real adapters and coordinator,
  confirmed exactly**: tests import and call the genuine
  `ClientOperationCoordinator`/`clientOperationApi` and
  `localTaskApi.receipts` adapters (not mocks of them), confirming a
  first poll omits the `after` cursor entirely and a subsequent poll
  with a real UUID cursor includes it correctly, that
  `coordinator.reconcile()` correctly follows server-returned pagination
  across repeated calls, and that the coordinator correctly disables
  itself and stops polling when the server reports the feature as
  disabled — matching "Regression tests exercise the real API adapters,
  coordinator pagination and disablement, and freshly generated
  fetchers" exactly.
- **The button timer fix, confirmed exactly**: `Button`'s `handleClick`
  now clears any existing `pressTimerRef.current` before scheduling a
  new 200ms timer, and the new timer's own callback resets the ref to
  `null` once it fires — so a rapid second click properly supersedes
  (rather than leaks) the first click's timer. Two dedicated tests
  confirm this: one asserting `data-pressed` stays `true` until 200ms
  after the *second* (latest) click rather than the first, and one
  asserting `vi.getTimerCount()` is exactly `0` immediately after
  unmounting a component that received two rapid clicks — directly
  confirming "cancel the previous button press-feedback timer before
  scheduling a replacement... Rapid clicks previously left an untracked
  timer running after unmount, causing an uncaught `window is not
  defined` exception during CI teardown."
- Per the PR (not independently re-verified): the disclosed validation
  (257 test files, 2,825 tests with 11 skipped; the explicit disclosure
  that both new Button regression tests fail before the timer fix and
  pass after; `pnpm codegen` preserving the cursor fix across clean and
  repeated generation; `pnpm run build:app` passing with both fixes).

## Compatibility and configuration

None breaking. Both are pure bug fixes with no behavior change for any
already-working call site — a defined query parameter value, however
falsy, continues to serialize exactly as before; only a genuinely
`undefined` value is newly omitted instead of corrupting the request.
No backend, config, or wire changes.
