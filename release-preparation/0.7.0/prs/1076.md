# PR #1076: Improve frontend bundle splitting; Bucket icon catalogs

- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Performance PR (ERMAIN-705), claimed to reduce entrypoint bundle size
from 12MB to 700KB and total main-page load to ~3MB. Confirmed the core
mechanism by reading the two most load-bearing files in full:

- **Root cause, confirmed via `ResolvedIcon.tsx`**: the component
  previously did `import * as Icons from "iconoir-react"` and `import *
  as SimpleIcons from "simple-icons"` — pulling every icon in both
  libraries into the eager bundle regardless of which icons the app
  actually renders. Confirmed this is replaced with a curated static list
  of ~25 commonly-used iconoir icons imported directly by name (still
  eager, but a small fixed set) and everything else resolved on demand via
  `loadIconoirIconBucket`/`loadSimpleIconBucket`, imported from a new
  virtual module `virtual:erato-icon-catalogs`.
- **Per-first-character bucketing, confirmed exactly via the new
  `vite.icon-catalogs.ts`**: a custom Vite plugin reads both
  `simple-icons`'s and `iconoir-react`'s package exports at build time,
  normalizes each icon's name, and groups them via `bucketForToken =
  (token) => token.charAt(0) || "other"` into per-first-letter buckets
  (e.g. all icons starting with "a" become one dynamically-imported
  chunk) — confirmed `ResolvedIcon.tsx`'s own `bucketForToken` helper is
  identical logic, keeping the runtime resolution and the build-time
  chunking in agreement about which bucket a given icon name falls into.
  This means requesting an icon at runtime only pulls in the one
  first-letter chunk containing it, not the entire icon library.
- Per the PR (not independently re-verified given the remaining scope):
  the stated 12MB→700KB entrypoint reduction and ~3MB total main-page
  load figures; `App.tsx`'s 61-line diff and `main.tsx`'s 38-line diff
  presumably restructuring top-level lazy-loading/code-splitting
  boundaries; `FilePreviewContent.tsx`'s 81-line diff presumably
  lazy-loading heavy preview dependencies (PDF/DOCX/XLSX renderers); the
  new `vite.config.ts`/`vite.library.config.ts`/
  `vite.component-kit-host.config.ts` build configuration additions (20,
  7, and 7 lines respectively); and the Storybook config addition
  (`.storybook/main.ts`, 13 lines) presumably wiring the same virtual
  module for Storybook's own build.

## Compatibility and configuration

None functionally — icon rendering behavior is intended to be unchanged,
only how and when the underlying icon code is loaded. This is purely a
build/bundling change; no API or runtime configuration changes. A
customer component kit referencing icons by name should be unaffected
since the resolution API surface (`ResolvedIcon`) is unchanged in shape,
only its internal loading mechanism.
