# PR #874: Move profiling image build into manual triggered job

- PR: https://github.com/EratoLab/erato/pull/874
- Status: pending (diff reviewed)
- Category: Chores & Developer experience
- Theme: None

## Summary

Moves the `build-and-push-profiling-linux` job (which builds and pushes
`erato/backend:*-profiling` and `erato/app:*-profiling` images, built with
`ERATO_FEATURES=profiling`) out of `.github/workflows/docker-build.yml` —
where it previously ran automatically as part of every regular Docker
build (`needs: [build-and-push-amd64]`) — into a new, separate workflow
file `.github/workflows/docker-build-profiling.yml`, triggered only
manually via `workflow_dispatch` with a required `git_sha` string input
(described as "the matching amd64 frontend image must already exist").
The new workflow validates that input strictly — a step fails the run
with `::error::git_sha must be a full 40-character lowercase Git SHA`
unless it matches `^[0-9a-f]{40}$` — and then checks out that exact
commit (`actions/checkout@v4` with `ref: ${{ inputs.git_sha }}`) before
building, so the profiling image is guaranteed to be built from the
requested revision rather than whatever the default branch happens to be
at dispatch time.

Beyond just moving the job to a manual trigger, its tagging logic was also
narrowed: the original job additionally tagged/referenced a
`${RELEASE_VERSION}-profiling` variant whenever it ran as part of a
tagged-release build (`env.RELEASE_VERSION != '' && format(...) || ''`
conditionals for both the image tags and the combined image's
`BACKEND_IMAGE`/`FRONTEND_IMAGE` build-args). The new standalone workflow
has no `RELEASE_VERSION` concept at all — it always tags only
`latest-profiling` and `<git_sha>-profiling`, and the combined image's
build-args always reference the SHA-tagged backend/frontend images, never
a release-version-tagged one. So even after manually triggering a
profiling build for a release commit, there will be no
`<version>-profiling` tag published — only `latest-profiling` (overwritten
by whichever profiling build runs most recently, regardless of source) and
the SHA-specific tag. Also confirmed no other job in
`docker-build.yml` depended on `build-and-push-profiling-linux` (the
following `create-manifests` job only lists
`needs: [build-and-push-amd64, build-and-push-arm64]`), so removing the
job doesn't orphan any downstream dependency.

## Compatibility and configuration

No runtime configuration keys or migrations; this is a CI/build-pipeline
change only. Operationally: profiling-tagged images
(`*-profiling` tags on `erato/backend` and `erato/app`) will no longer be
automatically published for every commit/release going forward — anyone
relying on a profiling image being available for a given tag without
manually triggering the new workflow would need to trigger it explicitly,
supplying the exact 40-character commit SHA. Additionally, even a manually
triggered profiling build for a tagged release commit no longer produces a
`<version>-profiling` tag (e.g. `0.7.0-profiling`) — only `latest-profiling`
and `<sha>-profiling` — so any tooling or documentation that referenced a
version-pinned profiling image tag would need to switch to referencing the
commit SHA instead.
