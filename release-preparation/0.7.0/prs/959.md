# PR #959: Fix JIT translation to correctly integrate fallback

- PR: https://github.com/EratoLab/erato/pull/959
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes the backend's just-in-time `.po`→JSON translation catalog
compilation (`TranslationPoCache`) not falling back to the default
language for a message that's missing or left untranslated (empty
`msgstr ""`) in the requested locale. Confirmed by reading the full diff
and its new test: `compile_messages_json` now first compiles the
configured fallback locale's own `messages.po` (located as a sibling
`<locales_dir>/<fallback_locale>/messages.po` directory, skipped if it
would resolve to the same file being compiled) into a base message map,
then merges the target locale's own compiled entries **on top** of it —
so a target-locale entry present and non-empty overrides the fallback,
while a missing or empty entry silently falls through to the fallback
locale's text instead of rendering blank. The fallback locale itself is
now threaded through from the actual configured default language
(`config.i18n.language.default_language`) via `frontend_environment.rs`,
rather than a hardcoded value — confirmed by the diff, `Default` still
falls back to `"en"` for cases (e.g. tests) that use it directly. A new
test with realistic English (fully translated) and German (one message
correctly translated, one deliberately left empty, one entirely absent)
`.po` fixtures confirms exactly this three-way behavior: the German
catalog ends up with its own translation where present, and the English
text for both the empty and the missing message.

## Compatibility and configuration

None. Pure bug fix; no configuration or API changes. Behavior change: a
UI string missing or left untranslated in a non-default locale's
`messages.po` now renders in the deployment's configured default
language instead of appearing blank or missing.
