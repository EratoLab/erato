# PR #980: Mention validation & persistence on submit/edit/regenerate (ERMAIN-621)

- PR: https://github.com/EratoLab/erato/pull/980
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Third of the 5-part delegation stack (on top of #979). Adds an optional
`mentioned_assistant_ids` field to all three message-streaming request
types (submit/edit/regenerate) and validates/persists it — per the PR,
independently mergeable since the actual delegation-execution runtime
(#981) is what will consume the validated output. Confirmed by reading
the full new `services/delegation.rs`:

- `validate_mentioned_assistants` enforces every rule the PR describes,
  in order: returns empty immediately if the delegation feature gate
  (`assistants.delegation.enabled`, from #978) is off — but only rejects
  with `400` when mentions were actually supplied (an empty/absent field
  is always fine, so existing non-delegating requests are unaffected);
  deduplicates ids preserving first-mention order (`dedupe_mentions`, a
  simple, correct `HashSet`-backed filter); enforces the deduplicated
  count against `max_mentions_per_message` with `400`; rejects the chat's
  own currently-bound assistant being self-mentioned; and resolves every
  remaining id through the same checked "owner or viewer" assistant
  lookup used by `POST /me/chats` (explicitly *not* a laxer bind-time
  path), which also naturally excludes archived assistants as a side
  effect of that lookup's own rules. Confirmed the rejection message is
  deliberately uniform ("Mentioned assistant {id} is not available")
  regardless of whether the assistant is missing, archived, or simply
  inaccessible to the caller — a sound enumeration-resistance choice, not
  an oversight (the PR states this explicitly and the code matches).
- A separate `resolve_persisted_mentions` wraps the same validation
  function but converts any failure into an empty result plus a warning
  log, rather than failing the request — confirmed this exists
  specifically for the replay paths (regenerate without an explicit
  field, or edit falling back to the original message's mentions), and
  mirrors the established pattern from #803 (a stored action facet that
  no longer validates against current config is silently dropped on
  replay, not treated as a hard error) — an explicit, freshly-submitted
  mention list, by contrast, still fails hard via
  `validate_mentioned_assistants` directly.
- `InputParameters` gains a persisted `mentioned_assistant_ids` field,
  described as using the same mechanism that already keeps action facets
  stable across edit/regenerate (per #803): regenerate without an
  explicit field re-reads the persisted value, and edit falls back to the
  original message's mentions and re-persists the resolved set onto the
  new sibling message row — not independently traced through the
  287-line `message_streaming.rs` diff in this review, but consistent
  with the validated `services/delegation.rs` primitives and the
  established #803 pattern.

## Compatibility and configuration

None new beyond #978's existing delegation config gate. Additive,
optional request field on all three streaming endpoints; no behavior
change for any request that doesn't supply `mentioned_assistant_ids`
(the empty/absent case is a fast no-op, confirmed in the validation
function). OpenAPI spec and generated TypeScript client types updated
accordingly.
