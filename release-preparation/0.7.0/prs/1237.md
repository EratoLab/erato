# PR #1237: ERMAIN-862: Native local evidence as a durable client operation

- PR: https://github.com/EratoLab/erato/pull/1237
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

An exceptionally large (14,797 insertions, 147 files) and
security-sensitive feature: a delegated research task can collect
evidence locally via the native desktop sidecar, wait for native
approval of an exact snapshot, then resume the same assistant message
once an authenticated frontend returns — cryptographically signed and
explicitly scoped to a single backend replica. Critically, the PR's own
closing line states "No merge, deployment or enablement is requested,"
and both governing feature flags are confirmed off by default. Given the
scale and that this PR is explicitly presented as a reviewable
checkpoint rather than a ship-ready change, this review verified only
the two gating flags and one directly security-relevant test, rather
than attempting to trace the cryptographic signing/receipt verification
pipeline, the native protocol schemas, or the frontend coordinator in
full:

- **Both governing flags confirmed to default to `false`, exactly as
  claimed**: `ClientToolsConfig.durable_operations_enabled: bool` (in
  `config.rs`) carries `#[serde(default)]` on a `Default`-deriving
  struct, and the new `LocalDelegationConfig.enabled: bool` likewise
  carries `#[serde(default)]` on a `Default`-deriving struct — both
  resolving to `false` when unset. This directly confirms "Both
  `client_tools.durable_operations_enabled` and
  `desktop_sidecar.local_delegation.enabled` must remain off until host
  qualification" and "remains disabled by default" for the local-task
  profile.
- **Load-time validation requires a canonical HTTPS origin and a bounded
  set of public verification keys when the feature is enabled,
  confirmed exactly**: `DesktopSidecarConfig::bootstrap_fields` (only
  reached `if self.local_delegation.enabled`) requires
  `backend_origin` to parse as an HTTPS URL whose canonical ASCII
  serialization matches the configured string exactly, and requires
  `1..=8` verification keys — rejecting both an insecure/malformed
  origin and an empty or implausibly large key set at startup.
- **The native-facing bootstrap payload is proven, by a dedicated test,
  to carry no private key material, confirmed exactly — a concrete,
  directly security-relevant property**: the new test
  `strict_bootstrap_contains_only_public_delegation_authority` configures
  a `LocalDelegationConfig` with both a `signing_private_key_pem` field
  containing a literal marker string and a `verification_keys` map, then
  asserts the serialized `bootstrap_fields()` output contains the public
  key but *not* the string `"PRIVATE_KEY_MARKER"` and not the field name
  `"signing_private_key_pem"` at all. This directly substantiates the
  PR's trust-boundary claims — "There is no native backend connection or
  backend credential" and "The backend signature attests durable
  acceptance, not native-device attestation" — by proving the specific
  mechanism (what gets sent to the native installer) that would make
  those claims false if it leaked the private signing key.
- Per the PR (not independently re-verified, given this PR's exceptional
  scope and the author's own "not for merge" framing): the entire
  signing/receipt-verification pipeline (`services/local_delegation/signing.rs`,
  198 lines — the component that would need the most scrutiny to confirm
  "The frontend receives no unapproved content or derived metadata" and
  "identical retries preserve the receipt; stale claims and conflicting
  packages fail"); the removal of the private `local_jobs.rs` module and
  migration to the shared durable-attempts table (described as the
  primary architectural change, affecting `client_operations/store.rs`
  and the new `local_delegation/{contract,store,tool,uploads}.rs`
  modules totaling over 1,100 new lines); the new sqitch migration 0052
  (`add_local_evidence_exports`, confirmed to add only "immutable native
  binding/plan and receipt metadata" per the PR's own description, not
  independently re-read); the `erato/local_collect_evidence` synthetic
  tool registration and its stated policy (async leaf, depth-one,
  exclusive tool scope, other delegated-child client tools suppressed);
  the entire desktop-sidecar-protocol surface (over 2,000 lines across
  new JSON schemas for binding/plan/receipt-claims/security/status, a
  new 285-line `DELEGATION.md`, and a 6,142-line regenerated
  `validators.mjs`); the frontend `localTaskCoordinator.ts`/
  `clientOperations/coordinator.ts` (483 and 313 new lines); the
  dependency on two external repositories' PRs (native sidecar #68,
  subscription-content #25) being merged first; and the extensive
  disclosed validation across five separate test suites (backend 1,433
  tests, frontend 2,763 tests, protocol 115 tests, Office 2,052 tests,
  and a companion native macOS ARM64 suite of 308 tests) plus the
  explicit, candid "Remaining qualification" section listing interactive
  native selection, real Office/browser hosts, full process-kill
  recovery, PostgreSQL restart, and specific Windows/macOS host
  combinations as unqualified, with one named test host unreachable
  during this session.

## Compatibility and configuration

Additive and explicitly inert by design. New config keys
`client_tools.durable_operations_enabled` and
`desktop_sidecar.local_delegation.{enabled, backend_origin,
verification_keys, ...}`, both confirmed to default to a fully-disabled
state. New migration 0052, additive (new table/columns only, per the
PR's description). The PR's own framing is explicit that this is not
ready for deployment: "No merge, deployment or enablement is requested,"
pending "host qualification" work described in detail as remaining.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read: the relevant `LocalDelegationConfig`/
`ClientToolsConfig` definitions and `bootstrap_fields` validation logic
in `config.rs` (confirming both flags' default-off state and the
load-time HTTPS/key-count validation), and the complete new
`strict_bootstrap_contains_only_public_delegation_authority` test
(confirming the private-key-never-leaves-the-backend property). Given
this PR's exceptional scope (147 files, nearly 15,000 insertions,
spanning Rust backend services, JSON Schema protocol definitions, a
desktop-sidecar-protocol TypeScript client, a frontend coordinator, and
Office add-in wiring) and its own explicit "not for merge" framing, this
review did not attempt to trace the cryptographic signing/verification
implementation, the migration SQL, the protocol schemas, or the
frontend/Office coordinator logic. **Given the security-sensitive nature
of this feature (native code signing, cross-process trust boundaries,
receipt verification) and its current scope, this PR warrants dedicated
security-focused human review before any future enablement, independent
of this evaluation pass.**
