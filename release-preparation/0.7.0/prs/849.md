# PR #849: Drop the whole superseded tail when editing or regenerating a non-last message (ERMAIN-469)

- PR: https://github.com/EratoLab/erato/pull/849
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a display bug (ERMAIN-469) where editing a user message, or
regenerating an assistant message, that is **not** the last turn in the
chat left every downstream turn visible on screen — rendered *above* the
new streaming reply — until a post-stream refetch quietly cleaned them up.
With `[u1, a1, u2, a2, u3, a3]`, editing `u2` briefly showed `u1, a1, u3,
a3, u2(edited), <streaming reply>`, since the message list sorts purely
by `createdAt` and the stale later turns kept their original (older)
timestamps.

Root cause, confirmed by reading the code: the backend deactivates the
entire downstream tail and reactivates only the new lineage
(`submit_message`), but the frontend pruned far less — edit removed only
the edited message plus the single immediately-following assistant
message (stopping at the next user message), and regenerate hid only the
single target assistant message, leaving every message after that
untouched until the refetch's active-thread filter caught up.

Fix, confirmed in the diff:
- New pure helper `collectSupersededMessageIds` (`messageUtils.ts`):
  orders all messages by `createdAt` and returns the anchor message plus
  every message after it — mirroring the backend's "deactivate the whole
  tail" behavior exactly.
- New shared `dropSupersededMessages` in `useChatMessaging.ts`: calls both
  a renamed/pluralized `hideMessageIds` (was `hideMessageId`, singular) and
  a new `removeUserMessages` store action, so both the API-message
  snapshot and any locally-held optimistic user messages are cleared
  together — confirmed this closes a real gap the PR calls out: edit had
  an inline `setState` block compensating for locally-held user messages,
  but regenerate did not, so a superseded turn held only as a local user
  message (not yet reconciled from the API) could still render after a
  regenerate. Both `editMessage` and the regenerate path now call the same
  `dropSupersededMessages(collectSupersededMessageIds(...))` sequence,
  confirmed removing the large duplicated inline `setState` block edit
  used to have.
- Edit's previous hard-delete from `apiMessagesByKey` is replaced with
  hide-only (matching what regenerate already did) — confirmed via the
  store diff (`removeUserMessages` only touches `userMessagesByKey`, never
  `apiMessagesByKey`) — so a request that fails before streaming starts is
  restored by the refetch (which also clears hidden ids) instead of having
  permanently destroyed the API snapshot.
- `editMessage`'s `useCallback` dependency array drops `messages`/
  `messageOrder` (confirmed in the diff), since the superseded-id
  computation now reads live state via
  `useMessagingStore.getState().getRenderableMessages(streamKey)` instead
  of the render-closure values — meaning the callback is no longer
  recreated on every stream chunk.
- The Outlook add-in consumes the same shared hook, so it's covered by the
  same fix automatically; the PR states its own exchange-anchor lookup
  resolves before `editMessage` mutates the store, so the broader pruning
  doesn't affect add-in-specific behavior — not independently traced
  through `AddinChat.tsx`.

New E2E coverage (`edit-regenerate-lineage.many-models.spec.ts`) is added,
which the PR states was confirmed to fail against the pre-fix code (3
user messages visible mid-stream instead of 2), and which itself caught
an additional real defect (the local-user-message gap `removeUserMessages`
addresses) that the existing unit tests had missed — with a pre-existing
unit test that had the buggy behavior pinned as expected (`msg-user-later`
asserted to *survive* an edit) now corrected.

## Compatibility and configuration

None. Pure frontend bug fix; no configuration or API changes. Behavior
change: editing or regenerating a non-last message in a chat now
immediately hides every downstream turn (matching the backend's own
lineage-deactivation), instead of showing stale turns until a refetch
catches up.
