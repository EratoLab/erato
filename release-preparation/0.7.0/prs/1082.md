# PR #1082: Audience snapshot provenance, and the gate for re-keying the audiences map by id (ERMAIN-721)

- PR: https://github.com/EratoLab/erato/pull/1082
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Another pure-groundwork follow-up to the starting-assistant/experience-
policy stack (#1071–#1081), adding a deserialize-only provenance record to
`ExperienceAudience` (for a future admin-panel feature that snapshots an
audience from an overlap of two others) and documenting — but not acting
on — the precondition ordering for a future one-time re-key of the
`audiences` map from name-keyed to id-keyed. Confirmed by reading the
complete `experience_policy.rs` diff:

- **Deserialize-only, confirmed exactly**: `AudienceProvenance` and
  `AudienceProvenanceSource` derive `Deserialize` only (no `Serialize`) —
  matching the doc comment's stated reason that erato never writes this
  document (the admin panel is the sole writer), so it can never be the
  one to invent or rewrite provenance.
- **Dangling source references parse by deliberate decision, confirmed
  exactly**: `parse_experience_policy` performs no structural check that
  `source_a`/`source_b`'s `audience_id`/`audience_name` correspond to
  anything else in the document — a dedicated test
  (`dangling_provenance_source_ids_parse`) confirms a document with
  provenance pointing at nonexistent source audiences parses successfully,
  matching the PR's stated reasoning that nothing joins on provenance, so
  a reference check would let a deleted source audience take down the
  whole document.
- **`taken_at` required and strictly validated, confirmed exactly**: it's
  a non-`Option` `DateTime<Utc>` field, so a document with no `taken_at`
  at all fails to deserialize (a required-field rejection, matching "an
  absent `taken_at` also rejects"), and a dedicated test confirms a
  malformed (unparseable) `taken_at` value likewise rejects the whole
  document — consistent with the existing `expires_at` validation
  precedent this PR explicitly follows.
- **`kind` is an open string, confirmed exactly**: `pub kind: String`, not
  an enum, with a doc comment and a dedicated test
  (`unknown_provenance_kinds_parse`) confirming an arbitrary/unrecognized
  `kind` value parses fine — so a newer admin-panel writer minting a new
  provenance kind can never wedge an older erato reader into rejecting the
  whole document.
- **Provenance genuinely never affects resolution, confirmed via a
  specifically-constructed proof test**: `a_document_resolves_identically_
  to_its_provenance_stripped_twin` parses two documents — one with
  provenance whose source references *deliberately dangle* (so a
  resolution path that accidentally dereferenced them couldn't pass by
  luck), and its provenance-stripped twin — then asserts
  `resolution_order_for` and `match_winning_audience` (the two actual
  resolution entry points, not the document alone) produce identical
  output for both. A guard assertion (`parsed.audiences["overlap"]
  .provenance.is_some()`) confirms the test isn't vacuously passing due to
  a typo in the fixture's provenance key.
- **The re-key gate, confirmed by direct inspection of the doc comment on
  `ExperiencePolicyDocument::audiences`**: records (but does not perform)
  the ordered preconditions for a future one-time switch from
  name-keyed to id-keyed audiences — a value-held `name` field dual-written
  into every audience, every replica reporting/tagging from that
  value-held name rather than the map key, `priority_order` already
  dropped (per #1081's gate, itself nested inside this one), and the
  writer pinned last. Confirmed this PR's diff makes no code change
  implementing any part of this sequence — it is purely documented as a
  precondition ordering for a later PR.

## Compatibility and configuration

None. Purely additive, currently-inert field (`Option<AudienceProvenance>`,
absent in every document written so far) with no read path anywhere in
the resolver — proven not to affect resolution by the twin-comparison
test above. No migration, no wire-contract change.
