# PR #1179: Bound how long a turn waits on a silent chat provider (ERMAIN-824)

- PR: https://github.com/EratoLab/erato/pull/1179
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds a configurable idle timeout so a turn whose provider connection
stalls without closing no longer stays "running" forever — the existing
heartbeat only proves the backend process is alive, not that the
generation is progressing. Confirmed the core mechanism, its
per-item/not-per-turn semantics, its content-vs-socket measurement, and
the configuration surface by direct code inspection:

- **New `provider_idle_timeout_secs` config field, confirmed exactly**:
  added to `GenerationStatusConfig` in `config.rs` with
  `#[serde(default = "default_generation_status_provider_idle_timeout_secs")]`
  returning `600`, and wired into the struct's `Default` impl. A code
  comment states precisely the PR's own framing: "an IDLE budget, not a
  total one," measured on content rather than socket traffic since
  keep-alive pings/empty deltas/SSE comments are dropped by the provider
  adapter before reaching the turn, and `0` disables the bound — matching
  the PR description's every claim about this field.
- **Per-item budget reset, confirmed exactly**: `next_provider_stream_item`
  races `stream.next()` against `provider_idle_elapsed(budget)` inside a
  `biased` `tokio::select!` (biased so a same-poll item wins the tie over
  a same-poll deadline, avoiding a false stall report when data actually
  arrived). Because this function is called once per stream item inside
  the read loop, every item genuinely restarts the budget — confirmed
  directly by the `the_budget_bounds_silence_rather_than_the_whole_answer`
  unit test, which streams three chunks each paced just under the budget
  and asserts all three arrive, substantiating "a long answer that keeps
  streaming never trips it, however long it takes."
- **Content-vs-socket measurement, confirmed exactly**: the code comment
  on `next_provider_stream_item` states directly that what restarts the
  budget is "an item the ADAPTER surfaced, which is not the same as
  traffic on the socket," since genai drops keep-alive pings/empty
  deltas/SSE comments before this loop sees them — matching the PR's
  "Measured on CONTENT, not on socket traffic" claim precisely, and this
  is the same justification given in the confirmed `config.rs` comment
  above.
- **Zero disables the bound, confirmed exactly**: `provider_idle_elapsed`
  resolves to `std::future::pending()` when `budget` is `None`, which
  `tokio::select!` never picks — confirmed directly by the
  `a_zero_budget_waits_on_the_provider_indefinitely` test, which asserts a
  one-hour outer timeout still elapses (i.e., the idle branch never
  fires) when the budget is `None`.
- **Idle failure reported as a provider error with the exact stated
  wording, confirmed exactly**: `ProviderStreamFailure::Idle { after }`
  converts to `GenerationErrorType::ProviderError` with description "The
  model provider produced no content for {N} seconds, so the generation
  was stopped." — confirmed by the
  `an_idle_failure_is_reported_as_a_provider_error` test asserting the
  description contains "45 seconds" for a 45-second budget, and
  `status_code: None`.
- **Initial-connection guard, confirmed as stated "belt-and-braces"**: a
  code comment on the streaming path explicitly states genai builds the
  request lazily and doesn't connect until the stream is first polled, so
  in the current adapter this guard costs nothing extra but covers a
  future adapter that connects eagerly — a candid disclosure that the
  stream-loop idle check (not a separate connection-phase timer) is doing
  the real work today.
- **Non-streaming error-recovery path also bounded, confirmed exactly**:
  `fetch_non_streaming_error` (invoked when a stream ended without saying
  why) wraps its re-ask of the same upstream in
  `tokio::time::timeout(Duration::from_secs(secs), attempt)` when
  `provider_idle_timeout_secs != 0`, with a code comment stating plainly
  that re-asking an unbounded upstream here "would hand the turn straight
  back to the hang it was recovering from" — matching the PR's implicit
  claim that the timeout applies consistently across both the primary
  stream and its error-recovery fallback.
- Per the PR (not independently re-verified given remaining scope): the
  chat-lease-release behavior once a generation is failed via this path
  (the PR's "the chat lease is released" claim — plausible given the
  existing generation-failure machinery this session has seen in other
  PRs, but not re-traced here), the ~123-line integration test additions
  in `generating.rs` and the 33-line `test_utils.rs` helper (a mock
  provider that streams partial content then stalls), and the
  documentation/config-reference updates (`config_reference.json`,
  `site/content/docs/configuration.mdx`, the k3d local config example).

## Compatibility and configuration

Additive, non-breaking: new optional config field
`generation_status.provider_idle_timeout_secs`, default 600 seconds.
Setting it to `0` restores the previous fully-unbounded wait behavior
exactly (confirmed via the `None`/`std::future::pending()` path). No
existing behavior changes for a healthy, actively-streaming provider —
only a stalled-but-still-open connection is newly bounded.
