# PR #945: Fix missing fallback for empty translation strings in JIT-compiled mode

- PR: https://github.com/EratoLab/erato/pull/945
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes `compile_po_catalog_to_json` in `backend/erato/src/translation_po.rs`
(the backend's JIT `.po`-to-JSON translation compiler, relevant to the
`file_type_detection`-adjacent JIT translation path introduced/extended by
#792/#897/#914 this cycle). For an entry using Lingui's explicit message
ID convention (`#. js-lingui-explicit-id`, where `msgid` is a stable
translation key like `"navigation.page.new_chat"` rather than the
source-language text) with an empty `msgstr` (untranslated), the compiler
previously still emitted that entry into the compiled catalog using the
`msgid` itself as the message text — so Lingui would render the literal
key string (e.g. `"navigation.page.new_chat"`) instead of falling back to
the message hardcoded at the `t({id, message})` call site, which is
Lingui's normal fallback behavior for a missing/empty translation. Now,
entries with an explicit ID and empty `msgstr` are skipped entirely from
the compiled output, so Lingui correctly falls back to the call site's
`message` default instead. Entries using the default (message-hash-derived)
ID scheme are unaffected — those already fell back correctly since `msgid`
there already contains the actual source-language text.

## Compatibility and configuration

No configuration keys or migrations. This only affects deployments using
JIT `.po`-to-JSON translation compilation (`file_type_detection`... no —
`translation_po_compilation_mode = "JustInTime"`, per #792) with
explicit-ID message keys that are untranslated in a given locale; those
locales will now correctly show the English (or call-site) fallback text
instead of a raw translation key. Precompiled translation catalogs are not
affected by this code path.
