# PR #1022: Delegated runs list: surface a background run the moment it is dispatched (ERMAIN-664)

- PR: https://github.com/EratoLab/erato/pull/1022
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Fixes a latency gap in #1013's delegated-runs bar: the bar previously only
refreshed on the parent turn's terminal invalidation, so a background run
(dispatched mid-stream, its child chat already existing server-side) stayed
invisible above the composer until the entire parent turn finished
streaming — even though the client already receives the dispatch frame
(`{assistant_id, assistant_name, delegate_chat_id, background: true}`) as
soon as it happens. Confirmed by reading both changed files in full:

- **Cache-seed mechanism, confirmed via the new
  `delegatedRunDispatch.ts`**: `seedDispatchedDelegatedRun` gates strictly
  on `update.tool_name === DELEGATION_TOOL_NAME` and a parsed envelope
  with `envelope.background === true` and a defined `delegateChatId` —
  matching the PR's stated "only the frozen background-dispatch frame
  triggers" claim exactly (this is the same three-way envelope shape
  #1012 confirmed distinguishes a genuine detached dispatch from an
  awaited run's mid-stream progress). Confirmed it writes directly into
  the React Query cache via `setQueryData` rather than triggering a
  refetch, with an early-return no-op if a chat with that id is already
  present (no duplication) — and confirmed the query key it writes to is
  built by the same exported `delegatedRunsListingParams(originChatId)`
  helper, so the seed cannot target a different cache entry than the
  section's own query.
- **No fabricated generation markers, confirmed**: the seeded `RecentChat`
  row includes `provenance_kind`, `provenance_run_mode: BACKGROUND_RUN_MODE`,
  `origin_chat_id`, and a fresh `last_message_at`, but no
  `active_generation_started_at` field at all — consistent with the PR's
  stated rationale that a marker-less run already resolves as "running"
  in the documented dispatch-before-lease state, and a fabricated marker
  would risk a false terminal transition via the generating-status poller.
- **Wiring confirmed via `useChatMessaging.ts`**: the seed call is placed
  directly in the `tool_call_update` stream-event handler, invoked on
  every update (the seeder itself does the filtering, not the call site),
  with the origin chat id resolved from the active stream key or, for a
  brand-new chat, the store's `newlyCreatedChatId` — so a background run
  dispatched from a chat that only just got its id can still be seeded
  correctly.
- Per the PR (not independently re-verified given remaining scope): the
  provisional row's `title_resolved` uses the existing
  `UNTITLED_BACKEND_SENTINEL` so the row falls through to displaying the
  assistant's name until the real title arrives with the next refetch; the
  existing turn-end terminal invalidation is unchanged and still replaces
  the seed with server truth; and the 16-line `DelegatedRunsSection.tsx`
  diff (not read) adapts the section to consume the shared
  `delegatedRunsListingParams` helper rather than building its own params
  inline, closing the drift risk the PR calls out.

## Compatibility and configuration

not yet enabled anywhere), already-shipped delegated-runs bar from #1013.

hunks are independent of #1021's concurrent changes to the same file.
