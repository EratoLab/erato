# PR #1360: Add configurable MCP tool_annotations defaults/overrides (#1360)

- PR: https://github.com/EratoLab/erato/pull/1360
- Status: pending
- Category: Features and enhancements
- Theme: MCP

## Summary

No GitHub description beyond "Related Linear issue: ERMAIN-958"; evaluated
from the diff and its extensive documentation addition. MCP tool
annotations (`read_only_hint`, `destructive_hint`, `idempotent_hint`,
`open_world_hint`) drive tool-call approval gating, the chat's write
toggle, and tool enumeration — but previously came only from whatever the
MCP server itself declared, which can be missing, partial, or wrong. This
lets an operator supply or override these hints at three levels: globally
(`mcp_servers_global`), per server (`mcp_servers.<id>`), and per exact tool
(`mcp_servers.<id>.tools.<tool-name>`), each split into a `default_tool_annotations`
(fills in only what the server omitted) and `override_tool_annotations`
(takes precedence over whatever the server declared).

Confirmed via `config.rs`: a new `McpToolAnnotationsConfig` struct (4 boolean
hint fields, all `Option<bool>` so "unset" is distinguishable from
`false`) is added at all three levels, with a custom deserializer that
rejects non-boolean values (strings/numbers) specifically for these fields,
since "hints affect approval and write visibility" per the code comment.
The documentation specifies an exact 8-tier resolution order (tool override
> server override > global override > server-supplied hint > tool default >
server default > global default > MCP protocol fallback), states explicit
`false` participates in merging (not treated as absent), and that protocol
fallbacks remain the MCP spec defaults (`read_only_hint = false`,
`destructive_hint = true`, `idempotent_hint = false`, `open_world_hint =
true`). Per the docs (not independently verified in the session logic):
runtime config reload invalidates cached MCP sessions for a changed
server/tool so new hints take effect without a restart.

## Compatibility and configuration

New optional config at three levels, all inert (falls back to the MCP
protocol defaults / server-supplied hints) unless set:

```toml
[mcp_servers_global.default_tool_annotations]
open_world_hint = true

[mcp_servers.company_search.default_tool_annotations]
read_only_hint = true
destructive_hint = false

[mcp_servers.company_search.tools.rebuild_index.override_tool_annotations]
read_only_hint = false
destructive_hint = true
```

No migration. Per-tool keys are matched by exact, case-sensitive tool name
(no wildcards); a configured tool name absent from the server's actual
discovery is simply unused, not an error. The docs explicitly warn: broad
defaults/overrides also apply to newly discovered tools on that server, so
pair a broad default with an `allow_tools` allowlist if a server might
later add write-capable tools you don't want silently defaulted to
`destructive_hint = false`. Also explicitly noted: these are operator
assertions about behavior, not access-control rules — existing "Always
allow" decisions and user denials still apply independently.
