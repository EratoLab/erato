# PR #863: Map invalid and archived chat ids to 404/409 instead of 500

- PR: https://github.com/EratoLab/erato/pull/863
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes chat access/write endpoints (`submitstream`, `regeneratestream`,
`editstream`) returning a generic HTTP 500 for a missing, unauthorized, or
archived chat, instead of a specific, correct status code — a real
security/correctness issue, since a 500 both leaks less information about
*why* access failed and gives the frontend nothing actionable to react to.
Confirmed by reading `message_streaming.rs`:

- A new `reject_if_archived` helper returns `409 CONFLICT` for any write
  attempt (`submitstream`/`regenerate`/`edit`) resolved onto an already-
  archived chat. Its doc comment explicitly scopes this: reads
  (`get_chat_messages`), abort, client-tool-result, and resume are out of
  scope and must not call it — confirmed it's only invoked from the three
  write entry points. A brand-new chat (created inline, `archived_at =
  None`) is correctly unaffected.
- Every chat-resolution error path across `message_submit_sse`,
  `regenerate_message_sse`, and `edit_message_sse` now inspects the
  underlying error string for `"not found"`/`"Access denied"`/`"not
  authorized"` substrings and maps those to `404 NOT_FOUND`, falling back
  to `500 INTERNAL_SERVER_ERROR` only for genuinely unexpected failures —
  confirmed this pattern is applied consistently across all three
  endpoints' chat-resolution call sites, replacing what were previously
  unconditional `500` mappings.
- OpenAPI documentation (`#[utoipa::path]` `responses`) is updated on all
  three endpoints to document the new `404`/`409` response variants;
  `backend/generated/openapi.json` reflects the same.
- A related, somewhat separate improvement in the same diff: when a
  spawned background message-submission task fails unexpectedly, the code
  now broadcasts an explicit error event to every listener (the original
  stream and any `resumestream` reconnection) instead of leaving them
  waiting for a completion event that will never arrive — addressing the
  "avoids infinite spinners on failed or dropped streaming requests" claim
  in the PR description; a generic client-facing message is sent while the
  detailed error is captured server-side only.

Frontend: `ChatDetailPage.tsx` gains a redirect effect — confirmed by
reading the full diff — that sends the user to `/chat/new` when the
current chat's history GET resolved to a definitive 404
(`isNotFoundError`, checking a numeric `status: 404` on the generated
API client's error shape). The condition carefully excludes two cases
that would otherwise false-positive: a brand-new chat still shown via the
sidebar's #861 pending-chat placeholder (whose history GET returns 200
once its row exists, and which is additionally guarded by
`isNewChatPending`/`pendingChatId !== currentChatId` checks), and an
archived chat (still readable, returns 200, so it never matches the
404 check and is never redirected away from).

## Compatibility and configuration

None. Pure bug fix improving HTTP status-code accuracy; no configuration
keys or migrations. Behavior/API change: `submitstream`/`regenerate`/
`edit` now return `404` for a missing/unauthorized chat and `409` for an
archived one, instead of `500` — any client code inspecting status codes
from these endpoints should be updated to expect these more specific
codes (the OpenAPI spec documents the change). A submission to an
archived chat now surfaces a visible error in the UI rather than
whatever generic 500-handling previously applied.
