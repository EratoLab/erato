# PR #1240: Settle an origin slot its own turn will never come back for

- PR: https://github.com/EratoLab/erato/pull/1240
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Closes ERMAIN-762. Fixes a gap in the `wait`-path approval-propagation
mechanism (ERMAIN-766, part of the Delegation Level D stack reviewed in
#1230): a `wait` child's answer is normally written into the origin's
reserved slot by the same in-process turn that dispatched it, but if that
turn is gone (specifically: the origin chat was archived), nothing ever
writes the slot, leaving a permanently-stale "needs your input" card for
a question the user already answered on the child's own card. Confirmed
every claim in this unusually precise PR description directly against
the single new function it adds:

- **Hung off `settle_tail_deliveries`, the tail every child-side
  generation already runs, confirmed exactly**: `reconcile_orphaned_parent_slot`
  is called from inside `settle_tail_deliveries`, immediately after the
  existing `drain_pending_deliveries` call — matching "The reconcile
  hangs off `settle_tail_deliveries`... the same reasoning that hook's
  own doc gives for the `async` half" precisely.
- **Only `wait` children reach this path; `async` children are
  deliberately excluded, confirmed exactly**: the function returns
  immediately if `provenance.run_mode == Some(ProvenanceRunMode::Async)`,
  with the comment "Re-armed through its delivery row instead; doing
  both tells the origin twice" — matching `rearm_delivery_after_child_decision`'s
  stated scope (covering only `async` children's `result_delivery` rows)
  precisely.
- **D20 is genuinely preserved: an open covering approval stands the hook
  down, confirmed exactly**: the function returns if
  `origin_approval_covering_child(...).is_some()` — the exact same
  function the PR states `D20`'s own test asserts a child-side decision
  is refused against — matching "D20 is untouched: while the origin
  holds the open approval naming this child, its card owns the answer
  and the hook does nothing" word for word.
- **No archived-origin check, deliberately, and archived origin is
  confirmed to be the only reachable route — both of the PR's "two
  findings," confirmed exactly, in one and the same code comment**: the
  function performs *no* `reject_if_archived`-style check before
  rewriting the slot, with the comment stating verbatim: "Deliberately
  no archived check, unlike the `async` path's
  `DELIVERY_REASON_ORIGIN_ARCHIVED`: that one appends a row and runs a
  reaction turn, this rewrites a slot already in the row. An archived
  origin is also the only route that reaches here at all — a withdrawal
  or a settlement closes the child's own copy, so those never run
  again." This single comment directly substantiates both of the PR's
  "Two findings that narrowed this from the issue's framing": that only
  the archived-origin route reaches finished-child code, and that
  settling (not closing, unlike the async delivery path) is the correct
  behavior for it.
- **A live origin lease stands the hook down too, confirmed exactly**:
  `if origin_chat.generation_state.as_deref() == Some("running") {
  return; }`, with the comment "A running lease means the dispatching
  turn may yet write the slot itself" — matching "A live lease on the
  origin is left alone for the same reason."
- **Idempotent against a slot already settled by another path, and
  against a child that merely parked again, confirmed exactly**: the
  function only proceeds if it finds the named tool-call part still
  `MessageToolCallStatus::InProgress` (returning otherwise, "A settled
  slot means another path got there first; this is what keeps repeat
  tails idempotent"), and separately returns if the freshly-built
  envelope's own status is `InputRequired` ("writing that back would
  swap one `input_required` for another and call the orphan closed") —
  matching "as is a child that merely parked again" and "a slot some
  other path already settled" exactly.
- **A missing answer row is guarded against, confirmed exactly**: the
  `answered` check requires a message row at `child_assistant_message_id`
  that belongs to `child_chat_id` and postdates `spawned_at`, with the
  comment "`build_result_envelope` reads a missing answer as
  `completed`/`no_answer`, which would report a task that never spoke as
  one that did" — matching "a run whose answer row is missing" from the
  invariants list.
- **The park's own `localTrace` is carried across rather than rebuilt,
  confirmed exactly, word for word**: the code copies
  `slot.output[DELEGATION_LOCAL_TRACE_KEY]` (the previous park-written
  value) into the newly-built envelope's output object before writing it
  back, with the comment "The envelope is composed apart from the trace
  on purpose, so the park's copy in this slot is the only one and has to
  be carried over by hand" — matching "The settled slot carries the
  run's `localTrace` across rather than rebuilding it: the park wrote
  what the child did into that slot and it is the only copy, since the
  envelope is composed apart from the trace on purpose" essentially
  verbatim.
- **No new wire shape, no new `reason` value, confirmed structurally**:
  the function reuses `build_result_envelope` (the same function this
  session confirmed elsewhere in the delegation stack) and writes a
  `Success`/`Error` `MessageToolCallStatus` with the ordinary envelope
  shape — matching "the settled slot is the ordinary terminal envelope
  the awaited path already writes."
- Per the PR (not independently re-verified): the disclosed two new
  integration tests (the orphan-settles test, asserting status,
  `ended_at`, the child's answer text, and the run id — and disclosed as
  checked against a disabled hook to confirm it fails without the fix;
  and the covered-child-never-settles test) in the 130-line new test
  additions, not read; and the disclosed verification (1364/1364 `cargo
  nextest run`, clean clippy, clean `cargo fmt --check`).

## Compatibility and configuration

No migration, no wire shape change, no new config key, no new `reason`
value — confirmed consistent with the minimal, backend-only
changed-files list (one new function plus its call site, no schema or
config diffs). The disclosed residual gap — a stale, still-open approval
card remaining visible after unarchiving even though the underlying slot
is now correctly settled — is explicitly left unfixed, with the PR
candidly framing closing that card as "a further step into D20's
authority rule" it chose not to take unasked.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both

## Release note disposition

Proposed category: Bug fixes. Worth a mention if the broader delegation-
approval feature (#1230 and surrounding PRs, still gated off by default)
is release-noted: a delegated task's approval request is no longer left
permanently stuck asking for input the user already provided, when the
origin conversation that dispatched it was archived while the task was
parked waiting for an approval decision.
