## Summary

No GitHub description beyond "Related Linear issue: ERDSCAR-39"; evaluated
from the diff. Extends the desktop-sidecar-protocol with a new OS-permission
status/request flow, addressing repeated macOS "allow access to data from
other apps" prompts. Confirmed via the `SPEC.md` diff:

- `sidecar.status.v1`'s result now includes an extensible `permissions` map
  keyed by permission name, each valued `granted`, `not_granted`, `unknown`,
  or `not_appliccable_different_platform` (the PR's own spec text flags this
  exact spelling as intentional, likely a typo baked into the wire protocol).
  The first defined permission is `macos_full_disk_access`. Clients omit
  permissions not applicable to the sidecar's own platform, fall back to
  showing an unrecognized key's raw name, and must tolerate older sidecars
  that don't report this field at all.
- A new `sidecar.request_permission.v1` method takes
  `{"permission": "macos_full_disk_access"}` and returns an `opened` result
  that only acknowledges the OS permission flow was opened — never that the
  permission was actually granted. On macOS this opens System Settings'
  Privacy & Security > Full Disk Access pane; the user must enable the
  running sidecar app and restart it. Unknown permission keys, or a request
  for a permission not applicable to the current platform, return
  `InvalidParams`. Status polling itself must never trigger a permission
  dialog. Since macOS has no public status API for Full Disk Access, the
  spec directs implementations to a best-effort protected-file access check,
  falling back to `unknown` when that can't determine the answer.

Per the diff stat (not independently re-verified beyond the spec text):
corresponding schema files, generated TypeScript validators/types, a new
`SidecarPermissions.tsx` settings UI component (185 lines) with its own
test file, and locale updates across de/en/es/fr/pl.

## Compatibility and configuration

No backend config keys. Protocol-level addition, backward compatible by
design: an older sidecar that doesn't report `permissions` is explicitly
tolerated per the spec text above, and the new method is purely additive.
