# PR #1334: Replace a selected whole paragraph on its proven target (ERMAIN-928, block 2)

- PR: https://github.com/EratoLab/erato/pull/1334
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Word selection editing

## Summary

Per the PR description: block 2 of ERMAIN-928. "Rewrite this paragraph"
now leads to a review card offering **Replace**, which writes the model's
rewrite only onto the exact paragraph captured when the user sent the
request, and only if a final re-read proves that paragraph's content is
still unchanged; otherwise it refuses with "This passage changed after
your request. Nothing was replaced." Confirmed directly in the new
`wordReplaceSelection.ts` (332 lines, read in full): the write path proves
the target then writes it inside a single Word.js run (comment: "a final
read that comes right before the one write sync"), and reads the result
back in a *separate*, fresh run afterward — with a code comment citing a
known Word-on-the-web quirk that same-run reads immediately after a write
return stale data. A timeout before the write leaves the document
untouched; a timeout after it is reported as `unverified`, deliberately
distinct from "nothing written" so the UI never claims a write didn't
happen when it might have. Undo restores the paragraph's prior OOXML via a
captured `WordSelectionBackup`, except under Track Changes, where Word's
own Reject already undoes the tracked deletion. New `WordSelectionCard`
(883 lines) and `WordShowInWordButton` (89 lines) give this review flow its
UI, gated behind the `word_selection` facet advertising
`word.replace_selection` — per the PR, this is "the release switch" and
requires the matching add-in to already be deployed.

## Compatibility and configuration

Per the PR: no behavior for existing users until an operator's facet
advertises `word.replace_selection` (an existing allowlist-gated action,
consistent with other Word/Outlook action facets reviewed earlier this
session) and the matching add-in build is deployed — ordering matters
here since the add-in is the consumer of the new tool. No new top-level
config key; gating is via the existing facet `tool_call_allowlist`
mechanism. No database migration.
