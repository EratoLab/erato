# PR #1191: Render a delivered task result in the conversation (ERMAIN-779-A)

- PR: https://github.com/EratoLab/erato/pull/1191
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 4 "Async re-entry", position 4 of 5, the "A" half of ERMAIN-779,
based on #1190. Adds the frontend card that renders a `task_result`
content part (defined dark in #1189), plus two backend type-level fixes
that surfaced while wiring it up. Still dark overall — "Nothing writes a
`task_result` row until ERMAIN-780, so the card does not render in any
deployment yet" — but the PR notes this is "the first genuinely useful
stopping point of the stack": with #1188 already merged, a user whose
chat is already generating now gets their draft queued and re-sent
instead of a red error. Confirmed every concrete claim by reading the
complete `TaskResultCard.tsx`, the `message.rs`/`messageAdapter.ts`
diffs, and the `reasonLabel` relocation:

- **`#[schema(nullable = false)]` fix applied to both affected fields,
  confirmed exactly**: added to `reason: Option<String>` on both
  `TaskResultInput` and `ContentPartTaskResult` in `message.rs` — matching
  "Fixed on both `ContentPartTaskResult` and `TaskResultInput`" precisely,
  and plausible given the stated utoipa behavior (an
  `Option<String>` + `skip_serializing_if` combination otherwise renders
  as `reason?: null | undefined` in the generated TypeScript, a type that
  can never hold the string it's meant to carry).
- **`initiator`/`task_result` no longer dropped by the message adapter,
  confirmed exactly**: `mapApiMessageToUiMessage` gains `initiator:
  apiMessage.initiator ?? undefined` and `task_result: apiMessage.task_result
  ?? undefined`, with a code comment stating directly "The adapter is an
  explicit whitelist: a field the server derives is dropped unless it is
  named here" — confirming these two fields (derived onto `ChatMessage` by
  #1189) were genuinely being silently dropped before this fix, and that
  fixing it here deliberately leaves the `/react` trigger (mentioned as
  landing later) a pure-frontend change.
- **Summary rendered as plain text, never markdown, confirmed exactly**:
  `TaskResultCard` renders `part.summary` directly inside a `<div
  className="whitespace-pre-wrap ...">` with no markdown-rendering
  component in the tree — matching "rendered as plain text — never
  markdown — so it cannot draw links or headings in the transcript" and
  the stated parity with how the trace already treats a delegation
  result.
- **Card is self-identifying, confirmed exactly**: the card renders its
  own title ("Result of a task you delegated") regardless of surrounding
  context — matching "the card is therefore self-identifying rather than
  relying on its surroundings," consistent with the stated reasoning that
  it rides a user-role row (so the transcript draws a "You" header above
  it) and must not be mistaken for something the user actually wrote.
- **`sequence` is 0-based with the redelivery badge gated on `> 0`,
  confirmed exactly**: `{part.sequence > 0 && (...Delivered again...)}`,
  with a code comment stating "`sequence` is 0-based: 0 is the first
  delivery, so anything above it means this result reached the
  conversation more than once" — matching the PR's claim verbatim.
- **`reasonLabel` relocated out of the trace step into a shared module,
  confirmed exactly**: the entire `reasonLabel` function (the closed
  six-value `reason` vocabulary — `timeout`/`no_answer`/`parent_abort`/
  `cap_exceeded`/`approval_pending`/`approval_unavailable`, falling back to
  the raw value) is deleted from `DelegationStep.tsx` and now lives as
  `delegationReasonLabel` in the new `lib/delegation/delegationLabels.ts`
  (47 lines), imported by both `DelegationStep.tsx` (the trace) and the
  new `TaskResultCard.tsx` (the card) — matching "the card and the trace
  cannot drift on the same closed vocabulary" exactly, and confirmed to
  live under `lib/` rather than `components/`, consistent with the
  claimed "the registry generator keeps it off the kit surface" (`lib/`
  paths are not scanned by the component-registry generator the way
  `components/ui/` paths are, per this session's established
  understanding of the registry-generation pattern from prior PRs).
- **`ERATO_SHARED_SURFACE_MINOR` bumped for the new registry-reachable
  component, confirmed exactly**: `TaskResultCard` is added to
  `component-registry.generated.ts` (the general component registry, not
  `kit-surface.ts`'s explicit extension-point pins), and
  `ERATO_SHARED_SURFACE_MINOR` bumped `13 → 14` — matching "Shared-surface
  minor bumped 13 → 14 for the new registry-reachable `TaskResultCard`;
  no new extension point (a kit that wants its own card overrides
  `MessageContent`, as today)" precisely: `TaskResultCard` is reachable
  via the general registry for kit customization of its *contents*, but
  there is no dedicated extension-point slot specifically for swapping it
  — a kit still has to override the whole `MessageContent` renderer to
  change how a task result card is presented.
- Per the PR (not independently re-verified given remaining scope): the
  precise rendering of the status/reason/truncated sub-sections beyond
  what's shown in the component body (read in full, so this is largely
  confirmed, but the component's interaction with `useDelegatedRunOpener`/
  the opener-vs-plain-link fallback was not traced into
  `DelegatedRunOpenProvider` itself); the ~950-obsolete-entry-per-locale
  lingui prune claim and the 1149→1155 active-string count (not
  independently counted); the 103-line new `TaskResultCard.test.tsx`; and
  the disclosed verification (107/107 frontend vitest across touched
  trees, clean `tsc --noEmit`, 1152/1152 `cargo nextest run`).

## Compatibility and configuration

No new config keys. Additive `ERATO_SHARED_SURFACE_MINOR` bump (13 → 14)
for the new `TaskResultCard` registry entry; no new extension point. Zero
runtime effect in any current deployment, since nothing produces a
`task_result` row until ERMAIN-780 (per this PR's own disclosure,
consistent with #1189/#1190's identical "ships dark" framing). The
`initiator`/`task_result` adapter fix and the `#[schema(nullable =
false)]` fix are themselves inert today for the same reason, though they
are latent corrections that will matter once the underlying data exists.
