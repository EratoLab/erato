# PR #1012: Delegation trace: settled background presentation for detached runs (ERMAIN-641)

- PR: https://github.com/EratoLab/erato/pull/1012
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Fixes the delegation trace UI (#985) not knowing how to render a detached
background dispatch (#1005): `DelegationStep` was built assuming every
non-`completed` envelope status was an error, and "still running" required
an active stream — so a backgrounded run (whose tool part is frozen at
launch with no `status` key at all, per #1005's design) would previously
have rendered either as a red error pill printing a raw/missing status
string, or as if it were still awaited and running forever. Confirmed by
reading both changed files in full:

- **The background/mid-stream discrimination is conjunctive and
  precisely guarded against misfiring, confirmed via
  `parseDelegationEnvelope`**: a parsed envelope's `background` field is
  only ever `true` when the raw payload's `background === true` **and**
  `status === undefined` **and** a `delegateChatId` is present. This
  three-way conjunction is what correctly distinguishes a genuine
  detached-dispatch envelope (which #1005 confirmed carries exactly this
  shape) from an *awaited* run's ordinary mid-stream progress frame
  (which also has no `status` while streaming, but never carries the raw
  `background` marker at all) — so the regression guard the PR describes
  ("a status-less envelope without the marker still renders as running")
  is structurally enforced by the parser itself, not left to the renderer
  to get right.
- **The settled presentation, confirmed via `DelegationStep.tsx`**: when
  `envelope.background` is true, `stepStatusFor` returns `"done"`
  unconditionally (before any other status logic runs) — with a code
  comment clarifying this "done" describes the *hand-off* completing, not
  the delegate's actual run, since the frozen part can never learn the
  run's eventual outcome. The rendered pill switches from the normal
  (potentially error-toned) `ToolStatusPill` to a new, calm
  `SettledInfoPill` reading "Sent to background" — confirmed this
  background state is checked and rendered *before* any approval-status
  consideration, i.e. it outranks even a pending tool-approval indicator,
  since the frozen part's defining fact is that it detached, not any
  approval state that happened to exist at that moment. No spinner or
  elapsed-time indicator is shown for this state (not independently
  re-verified beyond the absence of the running-specific `isRunning`
  branch being reached), consistent with the "must not imply progress it
  cannot observe" design goal.
- Per the PR (not independently re-verified): the existing "open the
  delegated run" link (from #985) still renders correctly targeted for a
  backgrounded step, and the full pre-existing `DelegationStep` test suite
  (awaited completed/failed/timeout rendering, refusal/malformed-envelope
  fallback to the plain tool step) is confirmed unchanged and green.
