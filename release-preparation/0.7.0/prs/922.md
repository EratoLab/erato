# PR #922: Extract host-neutral add-in core, isolate Outlook composition

- PR: https://github.com/EratoLab/erato/pull/922
- Status: pending (diff reviewed)
- Category: Chores
- Theme: None

## Summary

Very large internal refactor of the Outlook add-in's source tree (3628
insertions/2763 deletions across 165 files), splitting the previously
monolithic, Outlook-specific `AddinChat.tsx` (1036 lines, deleted) and
`AddinChatProvider.tsx` (586 lines, deleted) into a host-neutral "core"
layer (`src/core/`: `AddinChatCore.tsx` 620 lines,
`AddinChatProviderCore.tsx` 352 lines, `AddinChatInputCore.tsx`,
`SharedAddinShell.tsx`, `NeutralAddinChatPage.tsx`) plus a separate
Outlook-specific composition layer (`src/outlook/`: `OutlookAddinChat.tsx`
432 lines, `OutlookAddinSessionController.tsx` 235 lines, `OutlookApp.tsx`,
etc.), with the bulk of the remaining diff being pure file moves (dozens
of existing hooks/utils/components relocated from flat `src/` paths into
`src/outlook/`, tracked as renames with zero content diff). A new
`ARCHITECTURE.md` documents the intended core/host boundary and
extensibility seams for supporting future Office hosts (Teams, Word,
Excel) beyond Outlook.

Given the enormous scope, review focused on verifying the one concrete,
mechanically-checkable claim the PR makes — that the boundary is actually
enforced, not just documented — rather than re-deriving the entire
refactor's behavioral equivalence to the pre-refactor monolith:

- Confirmed new ESLint rules in `eslint.config.mjs`: files under
  `src/core/**` get `import/no-restricted-paths` (forbidding imports from
  outside `src/core` except from within it) plus `no-restricted-imports`
  patterns banning `OfficeProvider`, anything Outlook-prefixed,
  `sessionPolicy`, and `useOutlook*` hooks, plus `no-restricted-globals`
  banning the bare `Office`/`OfficeRuntime` identifiers outright in core
  files. A second rule set applies to the "shared ring"
  (`hooks`/`providers`/`utils`/`auth`, outside `core`), banning imports
  from `src/outlook/**` (with a carve-out for test mocks) — enforcing that
  shared code can't quietly grow an Outlook dependency either. These are
  real, mechanically-enforced lint errors, not just documentation.
- Spot-checked one new core file in full,
  `AddinChatInputCore.tsx` (51 lines): confirmed genuinely host-neutral —
  it wraps the shared library's `ChatInput` with no Office.js references,
  no Outlook-specific imports, and an explicit doc comment stating "It has
  no host context, chips, or action facets," consistent with the stated
  design (host-specific behavior is meant to be composed in by the
  Outlook layer, not baked into the core).

Not independently re-verified, given the scale: that `AddinChatCore.tsx`
+ `OutlookAddinChat.tsx` together preserve every behavior the original
1036-line `AddinChat.tsx` had (this would require a careful line-by-line
comparison across the split, which wasn't performed); the correctness of
the ~130 pure file-move renames (git's rename detection reports these as
0-line-diff moves, which is consistent with no content change, but each
was not individually re-diffed); the new `AddinChatProviderCore.tsx`,
`SharedAddinShell.tsx`, `OutlookAddinSessionController.tsx`, or
`NeutralAddinChatPage.tsx`; or the extensive locale-file reflows (324
lines changed per language, likely message-key relocation following the
file moves, not independently verified as translation-preserving).

## Compatibility and configuration

None externally visible — this is described as, and structurally appears
to be, an internal architectural refactor with the goal of preserving
existing Outlook add-in behavior while establishing a boundary for future
non-Outlook host support. No configuration or API changes. Given the
scale of file moves and the extraction of a genuinely new core/host split,
this carries meaningfully more regression risk than a typical refactor
PR, even though no specific behavioral bug was found in the portions
reviewed.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the complete `eslint.config.mjs` diff
(confirming the boundary-enforcement rules are real and specific) and the
complete `AddinChatInputCore.tsx` new file (confirming genuine host-
neutrality). Given the PR's exceptional scale (165 files, a full
architectural split of the add-in's core chat/provider/session logic),
this review does not claim to have verified full behavioral equivalence
between the pre- and post-refactor code — that would require substantially
more time than allocated per PR in this pass. The two things checked
(boundary enforcement, and one core component's neutrality) both matched
the PR's description precisely, which is the strongest evidence available
within this review's scope that the refactor's stated goal was actually
achieved, without constituting a full correctness guarantee.

## Release note disposition

Proposed category: Chores/internal refactor. Not independently
user-visible; a pure internal restructuring intended to be behavior-
preserving. Not a release-note candidate on its own, though it's
foundational groundwork the maintainer may want to note internally given
its scale and the architectural intent (future non-Outlook Office host
support).
