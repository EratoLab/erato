# PR #1010: Generate SBOM and license artifacts before the source copy (ERMAIN-656)

- PR: https://github.com/EratoLab/erato/pull/1010
- Status: pending (diff reviewed)
- Category: Chores
- Theme: None

## Summary

CI/build-only fix for a real, deterministic Docker build failure
introduced by #963's license-generation steps once the build cache warmed
up. Diagnosed root cause: BuildKit's registry cache exports build
*layers* but never the contents of a `--mount=type=cache` mount — so on a
warm build where the `pnpm install` layer is a cache hit (a pure blob
pull, `pnpm install` never actually re-executes), the job-local
`/pnpm/store` cache mount stays empty for that build. Since the original
Dockerfile placed the SBOM/license-generation steps *after* the full
source copy (`COPY frontend /app/frontend`), any application source
change invalidated everything after it including those steps — forcing
`pnpm licenses list --prod` to re-run against the now-empty store and
emit an invalid/truncated JSON response the normalize script then failed
on. Confirmed via full diff read: the SBOM and license steps (for both
the frontend and the office-addin builds) move to immediately after their
respective `pnpm install`, *before* the source copy, and the normalize
script itself is copied before the install it's used by. This gives the
license-generation steps the same cache-invalidation lineage as the
install step that populates the store — so they can now only ever
execute in a build where the install also genuinely ran, making the
previous failure mode structurally impossible rather than merely less
likely. Per the PR, the actual generation commands and their inputs
(manifest, lockfile, `node_modules`) are otherwise unchanged.

## Compatibility and configuration

None. CI/Docker build-only fix; no application code changes.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Full diff read (1 file, 21 lines changed) — confirms
the described reordering exactly, for both the frontend and office-addin
sections of the Dockerfile. The PR's own stated cold-build validation
(all steps execute, four non-empty SBOM artifacts produced) was not
independently reproduced, but the fix itself is a straightforward,
verifiable reordering that directly addresses the diagnosed cache-lineage
mismatch.
