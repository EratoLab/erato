# PR #1239: Define Outlook source references for uploaded files

- PR: https://github.com/EratoLab/erato/pull/1239
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

A pure, additive contract-definition PR entirely within
`desktop-sidecar-protocol/` — no implementation consumes it yet,
explicitly: "this PR does not yet expose an Open in Outlook action." It
defines the JSON Schema shape an uploaded Outlook file's source metadata
will eventually carry, so a later PR can let a user reopen the original
email after a chat reload. Confirmed the schema shapes directly against
the described contract:

- **`OutlookFileProvenance` with an array of origins, confirmed exactly**:
  the new `file-provenance.schema.json` defines `version: const 1` and
  `origins: array` (`minItems: 1`) of objects, each with optional
  `document` (the uploaded item's own message reference) and
  `topLevelParent` (the outermost containing message) fields, both
  `$ref`-ing the same `message-reference.schema.json`, with
  `minProperties: 1` requiring at least one of the two per origin entry
  and `additionalProperties: false` elsewhere — matching "Separate
  references for an email's own identity and its outermost containing
  message. Multiple origins preserve both messages when identical
  attachment bytes are deduplicated" precisely (the array-of-origins
  shape is exactly what lets deduplication preserve more than one
  containing-message context for the same uploaded bytes). The schema's
  own description states directly: "Never substitute this reference for
  the uploaded document's own identity" on `topLevelParent` — confirming
  the two fields are deliberately kept distinct rather than collapsed.
- **Native `outlook_entry_id`/`outlook_store_id` keys with hex-pattern
  validation, confirmed exactly**: the new `message-reference.schema.json`'s
  `external_ids` field layers a conditional schema on top of the shared
  `external-ids.schema.json` base: when `key` is `"outlook_entry_id"` or
  `"outlook_store_id"`, `value` must match `^(?:[0-9a-fA-F]{2})+$` (a
  hex-encoded byte string of any length, in whole-byte pairs) — matching
  "Defined native `outlook_entry_id` / `outlook_store_id` keys alongside
  existing EWS and Internet Message-ID keys, including their scope and
  validation rules" exactly, with the validation rule itself (hex-pair
  pattern) being the concrete, checkable detail.
- **A message reference always resolves to something, confirmed
  exactly**: the schema's `anyOf` requires either a present `documentId`
  (a sidecar catalog UUID) or a non-empty `external_ids` array —
  preventing a reference that carries neither a catalog pointer nor any
  external identifier, which would be unresolvable by either path. The
  `documentId` field's own description notes it "Requires resolution
  against that catalog and is not portable across devices" — a candid
  scope note distinguishing catalog-indexed references from portable
  external-ID references.
- **Protocol version bumped, confirmed exactly**: `package.json`'s
  `version` changes `"0.1.25"` → `"0.1.26"`, matching "the shared
  contract in desktop-sidecar-protocol 0.1.26" exactly.
- **Existing RPC schemas unchanged, confirmed structurally**: the
  changed-files list contains only new schema/fixture/generated files
  under `outlook/` plus the generation script and index additions — no
  modification to any existing method-result schema file, consistent
  with "Existing RPC schemas are unchanged" and "This standalone contract
  does not add a field to existing v1 RPC responses" (stated directly in
  the new schema's own description).
- Per the PR (not independently re-verified given remaining scope): the
  new `mailbox-reference.schema.json`'s exact shape (53 lines, not read,
  though referenced correctly by `message-reference.schema.json` above);
  the "Mapping guidance for search, conversations, exports, legacy
  metadata, shared mailboxes, and thread anchors" documented in the
  80-line `SPEC.md` addition (not read); the 236-line new conformance
  fixture and 132-line new test file; and the disclosed validation
  (`pnpm run package-spec` passing formatting, 69-schema validation,
  generated-code consistency, TypeScript checks, and all 96 tests,
  including the stated compatibility-fixture coverage for both previous
  responses and the new native identifier keys).

## Compatibility and configuration

Purely additive, standalone protocol contract — no existing schema,
fixture, or generated type is modified in a breaking way (confirmed:
only new files plus generation-script/index additions). No runtime
behavior change anywhere in this release, since nothing yet produces or
consumes an `OutlookFileProvenance` value; this PR is explicitly scoped
as "the first dependency PR for Outlook source navigation," with upload
persistence, native opening support, host routing, and UI stated as
following in later PRs once this contract is reviewed and merged.
