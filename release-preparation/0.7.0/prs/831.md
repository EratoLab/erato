# PR #831: Composer UX consistency: token-driven styling, attachment tree restructure, first-message consent fix

- PR: https://github.com/EratoLab/erato/pull/831
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Three unrelated fixes bundled together, all confirmed by reading the code:

1. **Native checkbox/radio theming.** A new global CSS rule in
   `globals.css` — `input[type="checkbox"], input[type="radio"] {
   accent-color: var(--theme-fg-accent); }` — fixes checkboxes/radios
   rendering with the browser's default (unthemed) appearance in every
   theme, since the pre-existing Tailwind utility classes
   (`rounded`/`border-*`/`text-*`) have no effect on native form-control
   rendering; `accent-color` is confirmed as the actual themable lever.
2. **Hardcoded sizing replaced with theme tokens.** The add-in's "New
   Chat" button changes from `rounded-md` to
   `rounded-[var(--theme-radius-control)]`; the grouped-attachment card
   and its selectable rows move from `rounded-md` to
   `rounded-[var(--theme-radius-message)]`/`rounded-[var(--theme-radius-base)]`
   respectively — confirmed these prior hardcoded values only
   *coincidentally* matched the default theme's token values, so a
   customer theme changing those radius tokens previously produced
   visibly inconsistent corners between the composer input and the
   attachment tree.
3. **Grouped-attachment tree restructure**
   (`GroupedFileAttachmentsPreview.tsx`), confirmed via the diff: fixed
   disclosure/selection/text columns per row, a new keyboard-accessible
   chevron toggle button (rendered only when a thread message actually
   has attachments, avoiding a dangling disclosure control), file
   metadata (e.g. "1 file") folded into the same stacked text line as the
   filename instead of floating separately, and selectable rows made into
   single chip-style surfaces via a new additive `chromeless` prop on
   `FilePreviewBase`. A new "Toggle attachments" string is added,
   translated into de/es/fr/pl (confirmed in the locale diffs).
4. **Add-in consent-prompt bug** in `AddinChat.tsx`: the "fresh completion"
   tracker (which stamps a completion `isFreshCompletion` to gate the
   reply-consent card) previously reset itself and dropped the in-flight
   send's item identity whenever the tracked chat id changed — including
   the very first send of a brand-new chat, whose id transitions from
   `null` to a real id. That transition was being misclassified as "the
   user switched to a different chat," so the consent prompt (behind
   `presentation = "auto_prompt"`) silently never appeared for a new
   chat's first reply draft (failing closed to buttons-only, no visible
   error). Confirmed fix: a new `isNewChatGettingItsId` check
   (`freshTrackerChatIdRef.current == null && currentChatId != null`)
   exempts exactly this transition from the reset, mirroring an existing
   analogous pattern the PR cites from the draft-dedup logic.

The PR explicitly flags that items 2–3 are an intentional, visible change
to the default web rendering (rounder cards, restructured attachment rows)
— done to keep base and customer themes rendering from one consistent
code path — with moving the attachment card onto the newer
`--theme-shell-chat-input` surface family deliberately deferred as a
follow-up.

## Compatibility and configuration

None new. Purely visual/CSS-token and bug-fix changes; no configuration
keys, API, or migration changes. Any deployment/theme that customizes
`--theme-radius-control`, `--theme-radius-message`, or
`--theme-radius-base` will now see the add-in "New Chat" button and the
web/add-in grouped-attachment tree actually follow those tokens, where
they previously ignored them.
