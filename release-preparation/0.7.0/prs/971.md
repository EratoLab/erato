# PR #971: Pin Teams message windows to creation time, pace chat reads, gate add-menu rows on the file limit

- PR: https://github.com/EratoLab/erato/pull/971
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes three defects found in a post-#967 review sweep, all pre-existing
(not regressions from the recent Teams work, per the PR). Confirmed by
reading the code:

1. **"Last N messages" could pick up an edited or reacted-to old message
   instead of a genuinely recent one.** `listChatMessagesPage` sent no
   `$orderby`, and Graph's documented default for `/chats/{id}/messages`
   is `lastModifiedDateTime desc`, which moves whenever a message is
   edited **or reacted to** (e.g. a thumbs-up) — so an old message could
   get pulled into the "newest N" window, displacing a message that was
   actually sent more recently. Fixed by adding
   `$orderby=createdDateTime%20desc` to the initial request URL (Graph
   documents this as supported alongside `$top`); `@odata.nextLink` pages
   are followed verbatim, unaffected. Confirmed the PR is candid that
   **channel** messages can't be fixed the same way, since that Graph
   endpoint supports no `$orderby` at all and sorts by the reply chain's
   last activity — the code comment notes this is "unfixable server-side,"
   with the renderer instead re-sorting root messages chronologically as a
   client-side mitigation.
2. **Host "+"-menu rows (Teams chats, Outlook email-thread/attachment
   rows) ignored the attachment count limit.** `ChatInput` already
   computed `uploadDisabled` and its own built-in file-source rows
   honored it, but the host-contribution extension slot only ever
   received the broader `disabled` flag — so a host row stayed clickable
   at the file-count cap, and the resulting overflow was then silently
   dropped by the composer's `slice(0, maxFiles)` merge rather than
   surfacing any feedback. Fixed by adding `uploadDisabled` to
   `ChatAddMenuExtraContentProps` and wiring it through
   `ChatInputAddControls` to both the Outlook and Teams add-menu
   extension components, confirmed via the diff.
3. **The cross-chat concurrency gate bounded in-flight requests, not
   actual request-start rate**, against a Graph ceiling
   ("List chats"/"Get chat": 5 request *starts* per second per user, not 5
   concurrent). The prior `runWithChatReadSlot` capped concurrency at 4
   but freed a slot to the next waiter the instant a response landed, so a
   run of fast responses could start well over 5 requests/second — and
   `listTeamsChatsPage` wasn't covered by any gate at all. Fixed with a
   new shared, per-user `runAtChatMetadataRate` pacer (220ms between
   starts) applied to both `listTeamsChatsPage` and `getTeamsChat`,
   confirmed placed innermost in the request pipeline (inside the
   per-chat gate, wrapping the actual `graphFetch` call) so it paces real
   request starts rather than admission into an outer queue. Confirmed
   via the refactored `runPaced` helper that this new gate correctly
   releases its queue at request **start** (`releaseOnStart: true`, since
   Graph's ceiling counts starts, and requests may legitimately overlap in
   flight), unlike the pre-existing per-chat gate which still releases at
   **completion** (1 request/sec plus headroom, deliberately unchanged).
   The existing per-chat 1.1s gate, `Retry-After` handling, and the
   concurrency-slot mechanism are all left as-is.

Also includes an unrelated, mechanical fix: regenerates
`component-registry.generated.ts` for a `FilterSortIcon` export that #970
left un-regenerated, and updates the office-addin lockfile's library-
tarball hash.

## Compatibility and configuration

None. Pure bug fixes; no configuration or API changes. Behavior change:
"show me the last N messages" in a Teams chat now reliably returns
messages by actual send time rather than occasionally substituting an old
message that was merely edited or reacted to; host-contributed add-menu
rows (Teams chats, Outlook attachments) now correctly disable at the file
count limit instead of silently dropping the overflow; Teams chat-list/
chat-metadata reads now stay reliably under Graph's rate ceiling instead
of occasionally bursting past it.
