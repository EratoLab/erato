## Summary

Frontend-only (no backend/database changes, confirmed by the changed-files
list containing only `frontend/`/`office-addin/` paths), adding waiting/
setup UI states, click guards, and readiness confirmation around the MCP
OAuth grant flow for both the web app and the Office add-in. Confirmed
essentially every concrete, checkable claim in the PR description by
reading the two new core modules (`mcpAuthorization.ts`,
`McpOauthCallbackBoundary.tsx`) and `mcpOauthCallback.ts` in full:

- **Callback recognition scoped exactly as described, confirmed exactly**:
  `McpOauthCallbackBoundary`'s `isReturn` requires `pathname === "/"`
  (the application root) **and** `(associatedServerId !== null ||
  params.has("mcpOauthServerId"))` — a saved session-storage state
  association (`getMcpOauthServerId(state)`, set by
  `storeMcpOauthCallback` before the redirect) or the explicit legacy
  `mcpOauthServerId` query marker — **and** `state` **and** (`code` or
  `error`). Any other route or query-parameter combination falls through
  `if (!isReturn) return children;` untouched — matching "Recognize
  callbacks only at the application root with a saved MCP state
  association or an explicit legacy MCP marker... unrelated routes and
  query parameters retain their normal UI" precisely.
- **Legacy server IDs validated before processing, confirmed exactly**:
  `validateServer = isReturn && !!callback && !associatedServerId` — only
  the legacy path (no saved association) triggers a `useListMcpServers`
  lookup, and `canComplete` requires `knownServer` (`server.id ===
  callback.serverId && server.authentication_mode === "oauth2"`) to be
  true before `completeMcpAuthorization` is ever called — matching
  "Validate legacy server IDs against the available OAuth servers before
  processing a grant" exactly, and confirming this is a genuine
  authorization-relevant guard (an unrecognized or non-OAuth legacy ID
  cannot trigger a completion attempt).
- **Per-server operation guards and late-response protection, confirmed
  exactly**: a module-level `operations: Map<string, Operation>` in
  `mcpAuthorization.ts` is explicitly commented "Runtime-owned, not
  dialog-owned: closing settings doesn't lose an operation. The operation
  identity fences late responses after a retry or cancellation." Every
  async continuation (`connected`, the `complete`/`checkMcpConnection`/
  `watchMcpAuthorization` callbacks) re-checks `operations.get(serverId)
  !== operation` before applying its result — directly substantiating
  both "per-server operation guards... and protection against late
  responses" and "Closing settings preserves active operations."
- **Request timeouts, confirmed exactly**: `startMcpAuthorization` uses a
  60-second timer, `complete` (the callback-exchange path) 90 seconds,
  and both `checkMcpConnection` and the `watchMcpAuthorization` probe use
  20 seconds — each firing `finish(..., "timeout"/"unavailable")` on
  expiry.
- **Callback deduplication, confirmed exactly**: `completeMcpAuthorization`
  keys an in-flight `callbacks: Map<string, Promise<void>>` by
  `callback.state` and returns the existing promise rather than starting
  a second exchange — matching "callback deduplication" precisely.
- **A failed callback checks readiness once rather than replaying the
  grant, confirmed exactly**: `complete`'s `catch` block performs exactly
  one `fetchListMcpServerTools` call (not a retry of
  `fetchCompleteMcpServerOauth`/the OAuth flow itself) and falls through
  to an `"error"` phase if that single check doesn't show success —
  matching "A failed callback response checks readiness once without
  automatically replaying the grant" exactly.
- **Polling backoff/bounds, confirmed exactly**: `watchMcpAuthorization`
  sets a 10-minute `deadline`, starts at a 3-second `interval`, doubles it
  on each inconclusive probe capped at `Math.min(interval * 2, 60_000)`
  (once per minute), stops immediately on a `"FAILURE"` status
  (`finish(..., "unavailable")`, no further scheduling), and an `inFlight`
  flag plus a `Date.now() - lastProbe < interval` check prevent
  overlapping probes even when focus/visibility events fire together —
  matching "Readiness checks never overlap, back off to once per minute,
  stop on failure, and end after ten minutes" precisely, including the
  stated focus/visibility race protection in the code's own comment.
- **Success confirmations clear after ten seconds while the row's
  connection status persists, confirmed exactly**: `McpAuthorizationNotice.tsx`
  sets `window.setTimeout(() => { ...; clearMcpAuthorization(serverId); },
  10_000)`. `clearMcpAuthorization` only clears the ephemeral `phases`
  zustand-store entry for that server — the row's actual
  `connection_status: "SUCCESS"`, written into the `listMcpServersQuery`
  cache by `connected()` via `queryClient.setQueryData`, is a separate
  piece of state untouched by this timer — confirming "Success
  confirmations clear after ten seconds while the row retains its
  connection status" structurally as well as by the literal 10-second
  value.
- Per the PR (not independently re-verified given remaining scope): the
  "Reconcile notices with the available server list, cancel operations
  for removed servers, and discard success messages contradicted by newer
  status" claim (plausibly implemented in `ServersToolsPane.tsx`'s 85-line
  diff, not read in this review); the add-in-specific "reopen the
  authorization page through a direct link while waiting, without
  resetting the operation or starting another poller" behavior
  (`AddinSettingsDialogCore.tsx`, 10 lines, and the add-in's own hook
  `useMcpBrowserAuthorization.ts`, 29 lines — not read); the shared
  `Alert` component's polite status announcements (`Alert.tsx`, 6 lines);
  the five-locale translation additions (`de`/`en`/`es`/`fr`/`pl`
  `messages.po`, ~89 lines each, not spot-checked for translation
  accuracy); and the disclosed validation claims (230 frontend suites/
  2,430 tests passing with 11 pre-existing skips, 120 add-in suites/1,364
  tests passing, formatting/lint/TypeScript/i18n checks, production
  builds, and the explicit disclosure that native Office/WebView and live
  external-provider OAuth smoke tests remain manual, and the backend

## Release note disposition

Proposed category: Bug fixes. Worth a mention: starting or returning from
an MCP server's OAuth authorization now shows clear waiting/connecting
feedback across the web app and Office add-in, guards against duplicate
authorization attempts, and confirms success once the server actually
responds — closing a gap where a user could be left without feedback or
could retry an authorization that was already in progress.
