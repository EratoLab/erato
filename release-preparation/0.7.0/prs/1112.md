# PR #1112: Fix to use the Application root URL as OAuth2 callback URL

- PR: https://github.com/EratoLab/erato/pull/1112
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: MCP controls

## Summary

Fixes the MCP-server-OAuth callback (`redirect_uri`) construction
(`oauth_callback_url` in `backend/erato/src/server/api/v1beta/mcp_servers.rs`)
so it no longer embeds server-specific query parameters
(`?preferencesDialog=open&preferencesTab=mcpServers&mcpOauthServerId=<server_id>`)
into the registered OAuth redirect URI — it now always resolves to the
bare application root URL (scheme + host + optional path prefix from
`X-Forwarded-*` headers, with no query string). Many OAuth providers
require the `redirect_uri` sent in the authorization request to exactly
match a pre-registered, fixed callback URL; the previous per-server,
per-connection-parameterized URL would either fail that exact-match check
outright or require registering every possible server-ID variant with the
provider — neither is workable for a real OAuth client registration.

The information that used to travel in the callback URL (which MCP server
and preferences-dialog state to restore after the redirect) now travels
via a new client-side mechanism instead: `frontend/src/lib/mcpOauthCallback.ts`
stores the OAuth `state` → `serverId` association in `sessionStorage`
(keyed by the OAuth `state` parameter, which the backend already validates
independently) before redirecting to the provider, and looks it up again
when the fixed callback URL is hit on return — "keep the server
association across the redirect without adding it to the registered
callback URL," per its code comment. Two new backend unit tests confirm
the callback URL is now exactly the application root (with and without
`X-Forwarded-*` overrides) and that a missing `Host` header is rejected.

## Compatibility and configuration

No configuration keys or migrations. **Behavior/compatibility fix**: any
deployment that had already registered a specific per-server callback URL
(with the old query-parameter shape) with an OAuth provider for MCP-server
authentication would need to re-register the provider's redirect URI as
just the application root URL after upgrading — the old URL shape is no
longer generated. This is a correctness fix (the old shape likely didn't
work reliably with strict providers in the first place), but worth calling
out as a required provider-side reconfiguration for anyone who worked
around the old behavior.
