# PR #1284: Fix Gemini tool call ID reuse overwriting prior Python calls

- PR: https://github.com/EratoLab/erato/pull/1284
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a correctness bug where Gemini providers (and other providers that reuse or generate short tool call IDs) could silently overwrite previously issued tool call results, because the backend was sending namespaced IDs that the provider did not recognise.

**Root cause.** The backend uses namespaced tool call IDs of the form `{assistant_message_id}:{turn}:{call_id}` to route results back to the correct slot. Before this PR, these namespaced IDs were sent verbatim to the provider inside `ToolResponse` content parts. Gemini (and potentially other providers) generates short IDs such as `"call_1"`, `"call_2"` and reuses them across turns. When the provider received a `ToolResponse` with ID `"uuid:1:call_1"` instead of the expected `"call_1"`, it could not correlate the response with its pending tool call, causing it to issue a new tool call with a fresh ID—overwriting the earlier Python-invoked tool call that should have been referenced.

**Fix.** Two new functions in `message_streaming.rs`:

- **`provider_tool_call_id(tool_call_id: &str) -> String`**: Parses a namespaced ID by splitting on `:`. If the first segment is a valid UUID and the second parses as a `usize`, the function returns only the third segment (the original provider ID). Otherwise it returns the ID unchanged (safe for non-namespaced IDs).

- **`restore_provider_tool_call_ids(chat_request: &mut ChatRequest)`**: Iterates over all messages in the request and applies `provider_tool_call_id` to every `ToolCall.call_id` and `ToolResponse.call_id`, recovering the provider's own IDs before the request is sent.

The restore step is called just before the chat request is dispatched to the provider, so the provider always sees its own call IDs in both the tool call requests and the tool responses, regardless of how the backend internally tracks them.

**Frontend deletions.** The large number of deleted frontend files (Word review components: `WordDocumentPlanReview`, `WordHistoryCards`, `WordPlanChangeRow`, etc.) are artifacts of the branch rebasing past the Word card-review refactor (#1281). Those deleted files were already replaced by the new card-based implementation; this PR removes the superseded originals that were still present in the branch's history.

## Compatibility and configuration

No config changes. The fix is purely internal; all existing provider configurations work unchanged.

## Evidence and review

- `provider_tool_call_id` guards against non-UUID first segments: if `Uuid::parse_str(message_id).is_err()` or `turn.parse::<usize>().is_err()`, the function returns the original ID. This ensures that provider-generated IDs that happen to contain `:` are not incorrectly truncated.
- `restore_provider_tool_call_ids` is called once per generation turn, on a clone of the request, so the internal namespaced IDs in the stored chat history are unaffected.
- The change affects every provider uniformly (not just Gemini), which is correct because the namespacing convention is backend-internal and providers should always see their own IDs.
