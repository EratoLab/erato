# PR #1119: Stage emails before send: eager resolution, per-part verdicts and a composer size gate

- PR: https://github.com/EratoLab/erato/pull/1119
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Large Outlook add-in composer fix (2370 lines): dropped/thread emails are
now resolved into their final upload files as soon as staged, so the
composer can show real trimmed sizes, per-part accept/reject verdicts,
and a hard size/count gate before send — and every refused send restores
the user's draft instead of silently discarding it. Given the scope,
review focused on the two claims most critical to data-loss safety and
validation correctness. Confirmed by reading the complete
`validateStagedPart.ts` and the relevant `declineSend`/send-failure
handling in `AddinChatInput.tsx`:

- **Type checked before size, confirmed exactly**: `validateStagedPart`
  checks the file-capability table first — a part with no matching,
  operation-supporting capability returns `{ verdict: "unsupported" }`
  immediately, before the size check ever runs. Only a part that passes
  the type check reaches the `limits.maxBytes` comparison. This means an
  oversized-and-unsupported part correctly reports `unsupported` (with
  its read-only, no-checkbox rendering), not `too-large` (which keeps a
  dismissible checkbox) — matching the PR's stated design decision
  exactly, and consistent with the same type-wins-over-size precedent
  this session already confirmed in #1118's `oversizedRejectionNames`.
- **Disclosed review-fix: capability table sourced from the backend's
  real table, confirmed exactly**: `validateStagedPart` imports
  `findCapabilityByExtension`/`hasSupportedOperations` from the shared
  `@erato/frontend/library` barrel — the same backend-capability-derived
  matcher the web dropzone uses — rather than a separately maintained
  add-in-local list, matching the PR's disclosed adversarial-review
  finding and fix.
- **One consolidated path for every refused send, confirmed exactly**: a
  single `declineSend(error)` closure — `setSendFailure({error,
  dropKeys}); lastSentDraftFingerprintRef.current =
  previousDraftFingerprint; restoreDraft(message, inputFileIds);` — is
  called from all four disclosed failure branches (the size preflight,
  `EmailTrimError`, the 413/`UploadTooLargeError` branch, and the generic
  `UploadUnknownError` catch-all), confirmed via direct inspection of
  multiple call sites in the diff. This guarantees a refused send always
  and identically restores the draft and holds the error next to the
  composer, rather than each failure branch independently (and
  potentially inconsistently) handling its own recovery — directly
  addressing the data-loss risk a send failure would otherwise pose.
- Per the PR (not independently re-verified given the very large
  remaining scope): the eager drop-resolution machinery in
  `OutlookEmailSourceProvider.tsx` (286 lines) using `useDeferredValue`
  plus a per-key cache to expose `resolvedDrops`/`resolvedParts`/
  `resolvedTotalBytes`/`resolvedFiles`/`isDropResolutionStale`, with a
  failed trim surfaced via `resolvedDrops[i].error` rather than thrown
  immediately; the composer size gate (`ChatInput.tsx`'s new
  `sizeLimitExceeded`/`isComposerBlocked`, covering the send button,
  Enter key, queueing, the drain effect, placeholder text, error border,
  and aria-label); the new per-drop Remove control; the "Won't be read by
  the AI" unsupported-part copy; and the disclosed second adversarial-
  review fix (a new refused-drop's error now replaces rather than
  stacking beside an earlier held failure).
- **Explicitly disclosed known limitations, not fixed in this PR**:
  nothing gates send on `isThreadEmlStale`/`isDropResolutionStale`, so a
  send during the deferred-resolution lag can upload a stale resolution;
  the composer's own size gate lags one deferred pass behind a
  dismissal/restore; a failed-trim drop is invisible to the gate and only
  surfaces its error at actual send time; the thread-group size meta sums
  across parts while the gate itself is per-part (an open design
  question per the PR); no copy explains a message held by the size gate
  while queued; and two chip-size-fallback/doc-staleness items are left
  as-is.

## Compatibility and configuration

None breaking. Real, disclosed behavior changes in the add-in composer:
staged drops now show resolved (trimmed) sizes and per-part verdicts
before send; a send that would exceed size/count limits is now refused
client-side with the draft preserved, rather than failing server-side
(or previously, per the PR's framing, less consistently). No API or
configuration changes. The PR notes a fresh checkout needs `pnpm run
build:lib` (frontend) and a lockfile-free reinstall (office-addin) before
typechecking, due to new shared-library barrel exports.
