# PR #1114: Align host i18n ids with the component kit

- PR: https://github.com/EratoLab/erato/pull/1114
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a customer-affecting theming gap (related to CBCKHOF-42): 20 host
strings used auto-hash-keyed `t\`...\`` calls, while the openwebui
component kit addresses the same wording by explicit Lingui ids — a
hash-keyed string cannot be overridden by a theme or kit catalog unless
the hash happens to match, so a customer rename keyed on the kit's ids
never reached the equivalent host-rendered surfaces. Confirmed by reading
the relevant `ChatHistoryList.tsx` diff in full:

- **Hash-keyed calls converted to explicit ids matching the kit,
  confirmed exactly for the chat-history menu strings**:
  `t\`Remove\`` → `t({id: "chat.history.menu.remove", message: "Remove"})`,
  and the two confirmation strings similarly converted to
  `chat.history.menu.confirm_remove.title`/`.message` — matching the
  PR's stated id list exactly for this file.
- **The disclosed "fixed in passing" file-count bug, confirmed exactly**:
  the row's file-count display previously used two different mechanisms
  for the same information — a ternary-built raw template string
  (`` `${session.metadata?.fileCount ?? 0} files` ``, untranslated for
  the plural/N>1 case) for the `title` tooltip attribute, and a separate
  `<Plural>` React component for the visible text — now unified into one
  `getFileCountLabel` helper using `plural()` under a single explicit id
  (`chat.history.files.count`), used for both the tooltip and the visible
  text. Confirmed the code comment states the placeholder must stay named
  `count` specifically because component-kit catalogs merge last and
  format this id with `{count, plural, ...}` — a mismatched placeholder
  name would silently break the kit's own translation of this string.
- Per the PR (not independently re-verified given remaining scope): the
  remaining ~15 string conversions across `AttachmentTile.tsx`,
  `FilePreviewBase.tsx`, `FilePreviewButton.tsx`, `FilePreviewLoading.tsx`,
  `GroupedFileAttachmentsPreview.tsx`, `ThreadMessageCard.tsx`,
  `TeamsConversationView.tsx`, and `AssistantWelcomeScreen.tsx`; the
  disclosed second "fixed in passing" bug where the welcome screen's "And
  N more conversations..." was assembled from three untranslatable string
  fragments, now one plural under a host-owned id
  (`assistant.welcome.more_conversations.count`) deliberately kept
  separate from the kit's own placeholder-less equivalent id; the catalog
  backfill across `de`/`fr`/`pl`/`es` (stated as sourced from existing
  host translations where present, the kit's translations where the host
  had none, with four specific strings previously untranslated in any
  locale and the new plural wording flagged as needing a native
  speaker's review); the two ids that deliberately keep host English text
  despite sharing the kit's id (`assistant.welcome.edit`/`.history`,
  stated as pinned by a test); and the `translation_po.rs` backend diff
  (4 lines).
- **Explicitly deferred/out-of-scope items disclosed by the PR**: a
  canonical-id conflict between the kit's `chat.untitled` and the host's
  `chat.history.rename.generated.fallback` (left unresolved); several
  hand-rolled file-count plurals in other components not touched;
  `AssistantForm`'s own System Prompt/Default Files labels; and two kit
  ids with no host counterpart at all.

## Compatibility and configuration

None functionally breaking for end users of the default build. For
customers running the openwebui-based component kit or theme overlay:
renaming a string via the kit's catalog (the PR's motivating example is
Beckhoff's fork renaming "Remove" to "Archivieren") now correctly
propagates to the equivalent host-rendered surface, where it previously
did not. The PR also flags a layering-order caveat for that specific
customer fork: once it syncs past a certain upstream commit (kit-catalog
loading landing after the fork's current baseline), the kit's own
catalog entry will start overriding the fork's theme-layer rename for
these now-shared ids — noted as something that rename should then move
into the kit catalog or runtime-overrides layer to address, outside this
PR's scope.
