# PR #1266: Enforce schema openness to ensure evolvability of sidecar protocol

- PR: https://github.com/EratoLab/erato/pull/1266
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

No GitHub description beyond a Linear reference (ERMAIN-881); evaluated
directly from the diff. A large but largely mechanical PR (119 files,
~3,250 insertions/deletions, the bulk a generated `validators.mjs`
diff): every desktop-sidecar-protocol JSON Schema's
`"additionalProperties": false` becomes `true`, and the Rust backend's
Outlook-provenance parsing drops its `#[serde(deny_unknown_fields)]`
attributes in favor of an explicit, narrower null-rejection check — both
changes aimed at letting a newer sidecar protocol version add fields
without an older Erato backend (or an older sidecar's schema) rejecting
the whole message. Confirmed the core mechanism and its security-
relevant boundary precisely:

- **Schema openness is a sweeping, uniform change across every protocol
  schema, confirmed directly for a representative file**:
  `delegation/plan.schema.json`'s `"additionalProperties": false` →
  `true` — and the diff stat shows the identical one-line flip repeated
  across dozens of schema files (bootstrap, delegation, indexing,
  search, sources, outlook), consistent with "Enforce schema openness"
  being applied mechanically and comprehensively rather than to one
  schema at a time.
- **Openness is specifically tested against the most security-sensitive
  delegation objects, confirmed exactly**: a new conformance test,
  "accepts additive fields throughout security-sensitive delegation
  objects," feeds `validateLocalTasksStartV1Params` a payload with
  injected `futureRequestField`/`futureBindingField`/`futurePlanField`
  keys alongside the real `binding`/`plan` fixture data and asserts it
  still validates as `true`, and separately confirms
  `validateLocalTasksStatusV1Result` tolerates an unknown
  `futureStatusField`. This directly demonstrates the change's intent —
  these are the exact claim/binding/plan/receipt schemas backing the
  native local-evidence-collection feature this session reviewed in
  #1237 — and confirms openness is additive tolerance of *unknown*
  fields, not a weakening of the required/typed fields those same
  schemas still enforce (not independently re-verified that every
  required-field check survived unchanged, but the schema diffs shown
  only ever touch the `additionalProperties` key, never `required` or
  any field's `type`/`pattern`).
- **The Rust backend's Outlook provenance parser is given an equivalent,
  more surgical openness fix, confirmed exactly**: `#[serde(deny_unknown_fields)]`
  is removed from all five `Outlook*` structs
  (`OutlookFileProvenance`/`OutlookFileOrigin`/`OutlookMessageReference`/
  `OutlookExternalId`/`OutlookMailboxReference`), and the previous
  "serialize-and-compare" trick used to catch `null`-for-optional-field
  values (which also incidentally caught unknown fields, since
  `deny_unknown_fields` already did) is replaced by a new, narrower
  `reject_null_optional_fields` function that walks exactly the known
  optional reference fields (`document`/`topLevelParent` on an origin;
  `documentId`/`mailbox` on a message reference; `mailboxId`/
  `emailAddress`/`profileName` on a mailbox reference) and rejects only
  an explicit `null` there — confirming unknown fields are now
  genuinely tolerated while the protocol's own "omit, don't null" rule
  for optional fields is still enforced, just by a purpose-built check
  rather than as a side effect of `deny_unknown_fields`.
- **A dedicated test proves both halves of the new behavior at once,
  confirmed exactly**: `future_fields_are_ignored_but_explicit_null_is_still_rejected`
  parses a payload containing `futureEnvelopeField`/`futureOriginField`/
  `futureReferenceField`/`futureIdField` (all genuinely unrecognized)
  successfully, while a separate payload with `"documentId": null`
  (recognized but explicitly null) is still rejected — directly
  confirming the PR's intent (evolvability for unknown fields, continued
  strictness for the protocol's own null-vs-absent rule) in one test.
  Consistent with this, a previously-rejected test case using an unknown
  `"launchUrl"` field was removed from the "must be rejected" fixture
  list in this same diff, since that field is no longer unknown-field-
  rejected under the new policy.
- Per the PR (not independently re-verified given this PR's size and
  largely generated/mechanical nature): the remainder of the ~80
  individual schema-file diffs beyond the one read directly; the
  regenerated `validators.mjs` (the bulk of this PR's line count, purely
  derived from the schema changes); the protocol version bump and
  `README.md`/`SPEC.md` documentation updates; the new `generate` script
  step running `pnpm run format` before `pnpm run build` (a minor
  tooling improvement, not independently verified as load-bearing); and
  the frontend's `desktop-sidecar-protocol.types.ts` consumption and its
  309-line new `desktopSidecarProtocolExtensibility.test.ts` (beyond the
  one backend test read directly).

## Compatibility and configuration

Additive and backward/forward compatible by design: loosening
`additionalProperties` to `true` only ever makes previously-rejected
payloads (those carrying an extra, unrecognized field) now accepted —
it cannot make a previously-valid payload invalid. No required field or
type constraint changes anywhere in the diffs read. No config keys.
