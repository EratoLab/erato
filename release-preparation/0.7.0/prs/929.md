# PR #929: Expose Erato in Outlook organizer appointment compose

- PR: https://github.com/EratoLab/erato/pull/929
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Outlook scheduling and shared mailboxes

## Summary

Large feature (1172 insertions across 28 files): makes the appointment-
organizer compose window (editing/creating a meeting as its organizer) a
first-class add-in surface, alongside the existing mail read/compose
surfaces. Given the scale, review focused on the identity-isolation
mechanism, since a mistake there could leak data between unrelated
calendar items (the highest-consequence failure mode for this kind of
change).

- **Manifest**: a new activation rule and
  `AppointmentOrganizerCommandSurface` ribbon button are added to the
  local dev XML manifests (both override generations) and the unified
  manifest gains a `meetingDetailsOrganizer` context — not independently
  re-verified in this diff (manifest XML/JSON not read in full), but
  consistent with #818's earlier addition of the same activation rule to
  the shipped manifests.
- **Facet pipeline**: appointment context/rewrite flows through two new
  config-defined facets (`outlook_review_appointment`,
  `outlook_rewrite_appointment_selection`), shipped via a companion
  content-repo PR rather than this diff. Both sends and the UI's context
  chips are gated on the backend's advertised `GET /me/facets`, so the add-in
  can't claim to attach context a send wouldn't actually carry.
- **Live re-read at send time**: since editing an appointment form fires
  no `ItemChanged` event (unlike a mail item), the add-in re-reads
  appointment fields from the live item immediately before sending rather
  than relying on potentially-stale bind-time state, with per-field
  fallback so one wedged field degrades gracefully rather than blocking
  the whole send; start/end times are sent as local-offset ISO strings
  plus a separate `timezone` argument.
- **Sticky-scheduling interaction fixed**: the scheduling facet's
  confirm-and-book flow (from #801/#804/#818/#819) always opens a *new*
  appointment form, which would never be correct while the user is
  already editing an existing one — confirmed the appointment-compose
  surface is excluded from claiming the scheduling facet's "sticky" slot,
  and that a proposal from that facet would otherwise incorrectly refresh
  the stickiness window every time; calendar reads (`fetch_availability`)
  remain reachable in appointment-compose mode via the review facet's own
  tool allowlist instead.
- **Identity isolation, confirmed via full read of `outlookAnchor.ts`**:
  an appointment-compose item gets a fresh, page-load-scoped minted
  identity (`getOrMintItemIdentity`, a `WeakMap`-cached random UUID per
  live item object) rather than using Office.js's own `seriesId` —
  confirmed this is deliberate and correct: Office.js reports the *parent
  series'* id on every occurrence of a recurring meeting, so two different
  occurrences of the same series would otherwise collide on the same
  identity, sharing a chat and passing the insert/send safety gate meant
  to keep them separate. The minted identity doesn't survive a task-pane
  reload (matching how a brand-new, unsaved message compose already
  behaves) and correctly fails toward "different item" rather than
  toward false-equality, which is the safe direction for this kind of
  gate. `strictAnchorsEqual`/`composeInheritsAnchorsEqual` are updated to
  compare on `itemKind` first, so an appointment anchor can never be
  mistaken for a message anchor even if their other fields happened to
  coincide.
- **Cross-contamination guards**: appointment attachments are confirmed
  never surfaced as email context (the mail-item provider skips reading
  them entirely for an appointment item; the separate email-source
  provider explicitly nulls its own source via an `emailItem` alias when
  the active item isn't a message) — not independently traced through the
  full 242-line `OutlookMailItemProvider.tsx` diff, but the described
  mechanism is consistent with the identity-isolation pattern verified
  above.
- Broader type cleanup: `isMessageRead`'s type guard is widened from a
  message-only union to the new `SupportedOutlookItem` union (message
  read/compose + appointment compose), letting eight compound
  type-narrowing guards elsewhere be deleted; `itemKind` becomes a
  required field on the facet-resolver's anchor type; dedup-marker
  constant names are updated from `...` to `...DraftFingerprint` to
  reflect their now-broadened scope (covering appointment drafts too) —
  not independently re-verified across all call sites given scale.

## Compatibility and configuration

Additive; the two new appointment facets ship via a separate content-repo
config package, not this code diff, so this PR alone has no effect until
that companion config is deployed and a deployment's own `erato.toml`
enables the corresponding facets. No behavior change for any deployment
without that companion configuration. New locale strings across
de/es/fr/pl (and a smaller en diff) for the new appointment-surface UI.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the complete `outlookAnchor.ts` diff,
confirming the appointment-identity minting mechanism, the `seriesId`-
avoidance rationale, and the updated anchor-equality comparisons
precisely. Given the PR's large scale, the following were not read in
full: the manifest XML/JSON changes, the 198-line `AddinChatInput.tsx`
diff, the 242-line `OutlookMailItemProvider.tsx` diff (the attachment/
email-source cross-contamination guards, taken on trust from the
identity-isolation pattern already verified), the 105-line
`outlookActionFacet.ts` diff (the sticky-scheduling exclusion for
appointment-compose), the live-re-read-at-send-time logic in
`outlookComposeWrite.ts`, or the ~400 lines of new/expanded test coverage
across the touched files.
