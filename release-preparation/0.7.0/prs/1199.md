# PR #1199: Tell the sidebar a delegated run is still in flight (ERMAIN-782)

## Summary

Final PR of the "Async re-entry" stack (stacks on #1197/ERMAIN-781-B,
reviewed above), and per the PR's own framing the last one that "has to
be right on its own" for a minimum shippable set. Closes the remaining
gap: the delivery machinery from #1188-#1197 existed, but no client was
told any of it was happening, so a dispatched async task's answer sat in
the database until a manual reload. This PR adds two wire fields
(`RecentChat.delegated_runs_in_flight`, `GeneratingChat.initiator`) and
the frontend poll-cadence/refetch logic that consumes them. The PR
description is unusually rigorous about *why* each SQL and effect-branch
decision is shaped the way it is; this review verified the core backend
predicate and the frontend poll/refetch logic directly, line for line
against the stated reasoning:

- **The `EXISTS` predicate matches every stated detail exactly**: in
  `get_recent_chats`, the new `delegated_runs_in_flight` column is an
  `EXISTS` correlated on `child.origin_chat_id = chats.id`, scoped to
  `provenance.kind = 'delegation' AND provenance.run_mode = 'async'`
  (confirmed scoped to async only, matching "an awaited run stores no run
  mode" / background runs would otherwise hold the indicator on
  forever), with the OR condition reading exactly: `COALESCE(generation_state
  = 'awaiting_approval' OR (generation_state = 'running' AND heartbeat
  fresher than stale_after_secs), FALSE) OR result_delivery.state IN
  ('pending', 'claimed')`. Confirmed precisely: the `COALESCE(...,
  FALSE)` wraps only the generation-liveness disjunct (not the whole OR),
  matching "The `COALESCE(..., FALSE)` around the lease arm" exactly
  (a `NULL` heartbeat on an approval-parked chat would otherwise
  propagate `NULL` through the outer `OR`); the delivery arm is a
  positive `IN ('pending', 'claimed')`, never a `NOT IN` of terminal
  states, matching "never a `NOT IN` of the terminal states... a negative
  predicate would pin every sweep-recovered result true forever";
  `delivered` is confirmed absent from that list, matching "deliberately
  excluded"; and there is no `child.archived_at IS NULL` filter anywhere
  in the subquery, matching "No `AND child.archived_at IS NULL`."
- **Typed string spellings used throughout, confirmed exactly**: the SQL
  template interpolates `ChatProvenanceKind::Delegation.as_str()`,
  `ProvenanceRunMode::Async.as_str()`, `ResultDeliveryState::Pending.as_str()`,
  and `::Claimed.as_str()` rather than bare literals — matching "for the
  same reason those `as_str` helpers exist at all: this predicate and the
  delivery writers compare the same strings."
- **`delegated_runs_in_flight` is a required `bool`, confirmed exactly**:
  the `RecentChat` struct field has no `Option`/`skip_serializing_if`,
  unlike its sibling `delegated_run_outcome: Option<String>` two lines
  above it in the same struct — directly confirming the deliberate
  required-vs-optional distinction the PR argues for.
- **`GeneratingChatRow.initiator` sourced from a `LEFT JOIN LATERAL` on
  the latest active-thread generation, confirmed exactly**: the new
  lateral subquery selects `m.generation_parameters ->> 'initiator'`
  filtered to `m.is_message_in_active_thread AND
  m.generation_parameters IS NOT NULL`, ordered `created_at DESC LIMIT
  1`, joined with `LEFT ... ON true` — matching "comes from a `LEFT JOIN
  LATERAL` onto the chat's **latest active-thread** generation... `LEFT`
  rather than `INNER`, or a chat with no generation-parameters row would
  vanish from the poll entirely" exactly.
- **Poll cadence correctly includes the new `awaitingDeliveryChatIds`
  slice, confirmed exactly**: the exported `pollInterval` function reads
  `awaitingDeliveryChatIds` from the store alongside `statusByChatId`,
  and when nothing is `running`, returns the existing `SLOW_POLL_INTERVAL_MS`
  (10s) when *either* a status is `action_required` *or*
  `awaitingDeliveryChatIds` is non-empty — matching "A delivery
  outstanding (or an approval parked) with nothing running → **10s**"
  exactly, and confirming `pollInterval` is now `export`ed for unit
  testing per the stated "Both gates were taught about deliveries"
  concern.
- **Branch A — in-flight→not-in-flight edge with a 60s backstop,
  confirmed exactly, including the mount-time structural guarantee**:
  `liveChatIdsRef` tracks the previous snapshot's running/parked chat ids
  (`useRef<Set<string>>(new Set())`, empty on mount); `aRunEnded =
  [...previouslyLive].some(id => !live.has(id))`; a separate
  `DELIVERY_LISTING_REFRESH_MS = 60_000` backstop fires the same listing
  invalidation when `Date.now() - lastListingRefreshRef.current >=` that
  value — matching "A **60s backstop** bounds how long a *missed* edge
  can hide an arrived result" and "`previouslyLive` is empty on mount, so
  `aRunEnded` is structurally false for the first snapshot of every
  mount" exactly (both are directly observable from the ref's initial
  value and the set-difference check).
- **Branch B — task-result turn dedup keyed on `chatId:startedAt`,
  confirmed exactly**: the reaction-detection filter matches
  `entry.chat_id === currentChatId && entry.initiator === "task_result" &&
  entry.state !== "running" && entry.state !== "action_required"`, and
  dedups via `reactionKey = \`${reaction.chat_id}:${reaction.started_at}\``
  compared against `reactedRef.current` — matching "keyed on
  `chatId:startedAt`... a *second* async task delivering into the same
  origin surfaces as the same `chat_id` with a new `started_at`" exactly;
  a match invalidates only the open chat's `chatMessagesQuery`, not the
  listing.
- **`applyPollSnapshot` untouched, confirmed exactly**: it's still called
  as a single `applyPollSnapshot(data.chats)` pure-store-update call, with
  both new effect branches living entirely in the poller's own `useEffect`
  body alongside it, not inside the store reducer — matching "`applyPollSnapshot`
  is untouched: it is a pure `set((prev) => …)` with no query client, so
  the refetch lives in the effect that holds one."
- Per the PR (not independently re-verified given remaining scope): the
  `awaitingDeliveryChatIds` store slice's own implementation and
  `clearStatus`/archived-row-handling logic in `generationStatusStore.ts`
  (102 lines, not read — though its *consumption* by `pollInterval` was
  confirmed directly); `selectPollDriverCount`'s distinct-chat-id counting
  across the three reasons (running/parked/awaiting); the recent-chats
  `COUNT` query deliberately not gaining the `EXISTS` (plausible given the
  stated per-page-scan cost reasoning, not independently checked); the
  "Contract owed to ERMAIN-779-B" seam-naming section (a forward-looking
  design commitment, not a verifiable code claim about this PR alone); the
  bootstrap-window "near-zero, not provably zero" disclosure about
  `launch_delegation`'s synchronous lease-then-spawn ordering; the four
  disclosed mutation-verification claims (adding `'delivered'`, dropping
  the `async` scope, dropping the `COALESCE`/approval arm, dropping the
  active-thread filter, switching `LEFT` to `INNER`); and the extensive
  disclosed test suite (353+171 lines of new backend integration tests,
  298 lines of new `GenerationStatusPoller.test.tsx`, 91 lines of
  `generationStatusStore.test.ts`) and verification commands (all

## Compatibility and configuration

Additive wire fields only: `RecentChat.delegated_runs_in_flight` (always
present, required `bool`) and `GeneratingChat.initiator` (optional
string, absent for a user-initiated or pre-existing generation). No new
config leaf — confirmed by the PR's own disclosed empty diff against
`config_reference.json`/`current_schema.sql`, consistent with reusing the
existing `generation_status.stale_after_secs` for the staleness window.
No migration; the correlated `EXISTS` is served by the existing
`origin_chat_id` partial index per the PR's claim (not independently
re-verified via `EXPLAIN`). Required-field change to `RecentChat`'s
generated TypeScript type means every frontend construction site had to
be updated (confirmed via the changed-files list touching
`useChatHistory.ts`, `delegatedRunDispatch.ts`, `mockDataGenerator.ts`,
`lib/mocks/handlers.ts`, and associated test files) — a compiler-enforced
completeness property rather than incidental churn, as the PR argues.

## Release note disposition

Proposed category: Features and enhancements. This is the PR that makes
the whole "Async re-entry" stack (#1188-#1199) user-visible end to end:
dispatching a `when_idle` async task from a chat and keeping that chat
open now shows the answer arriving live, with no reload required. As the
PR itself discloses, two related gaps remain explicitly out of scope for
a later PR: the composer does not yet queue or retry its own draft off a
delivery's arrival (ERMAIN-779-B), and retrying a failed or reaped task
is a separate follow-up (ERMAIN-783). This PR should anchor the stack's
combined release-note entry, since per `BUILD-RECONCILED`'s own framing
it is "the last PR in the stack that has to be right on its own" for a
minimum shippable async-tasks feature.
