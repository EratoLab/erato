# PR #1007: Recent chats: optional origin_chat_id filter (ERMAIN-637)

- PR: https://github.com/EratoLab/erato/pull/1007
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Small, targeted addition to `GET /me/recent_chats`: a new optional
`origin_chat_id` query parameter lets a client ask "the runs spawned from
this specific chat" directly, rather than paging through the whole
history — described as the query a planned background-runs sidebar
section will need. Confirmed by reading the full `models/chat.rs` diff:

- Reuses infrastructure already in place from #979/#982 (the
  `origin_chat_id` generated column and its index) — this PR is genuinely
  just one new SQL condition plus its parameter binding.
- **The described positional-parameter numbering fix, confirmed
  precisely**: both the list query and its paired count query previously
  built positional parameters (`$1`, `$2`, ...) with hardcoded indices
  for each optional filter. A new `search_param_count` (0 or 1, based on
  whether a search query is present) now drives the origin filter's own
  parameter index dynamically: `origin_condition(4 +
  search_param_count)` for the list query (after the three fixed
  parameters and the optional search), `origin_condition(2 +
  search_param_count)` for the count query. Confirmed the actual
  parameter values are pushed in the exact same order (search, then
  origin) that the index arithmetic assumes, so the two stay in sync
  regardless of which optional filters are present.
- Confirmed `origin_chat_id` **composes with** `include_delegated` rather
  than overriding it: the `origin_condition` is entirely independent of
  the pre-existing `delegated_condition`, so filtering by origin alone
  (without also setting `include_delegated=true`) correctly returns
  nothing for delegated children, since they're still excluded by the
  unrelated delegation-hiding condition — matching the PR's stated
  design and its own documented parameter description.
- An unparseable `origin_chat_id` value returns `400`, confirmed
  documented in the endpoint's response spec.

## Compatibility and configuration

None. Purely additive, optional query parameter; no behavior change for
any existing client that doesn't pass it.
