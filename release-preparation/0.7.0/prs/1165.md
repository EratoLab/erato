# PR #1165: Bound a task run with two independent tool-call budgets (ERMAIN-774)

- PR: https://github.com/EratoLab/erato/pull/1165
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 2, PR 4/5, on top of #1164. Adds two independent per-task-run
tool-call budgets (server-executed and client-executed, never summed),
resolved at launch and frozen into the run's `TaskSpec` rather than
re-read from live config. Confirmed the most correctness-critical pieces
— the classification logic and the completed-not-cancelled outcome
framing — by reading the relevant sections of `delegation.rs` in full:

- **MCP-first classification, confirmed exactly, including the subtle
  "wait in reverse" edge case**: `classify_task_tool_call(tool_name,
  is_mcp_tool)` checks `is_mcp_tool` before anything else, falling to
  `is_budget_exempt_tool_name` (which groups both delegation tools and
  the wait tool as `Exempt`) only when the call isn't a discovered MCP
  tool. A doc comment states the precise reasoning and directly
  identifies the edge case the PR's description alludes to: an MCP
  server that happens to expose a tool literally named `wait` is checked
  against the MCP branch *first*, so it is correctly billed as `Server`
  work rather than falling through to `Exempt` — "classifying it as
  exempt would let a server exposing a tool called `wait` run
  unbudgeted." This directly confirms both halves of the PR's claim: MCP
  wins the precedence, and the backend's own `wait` tool is exempt
  specifically because it never reaches the MCP check, not because of a
  naive "non-MCP tools are client work" fallback that would have
  incorrectly billed it to the client budget.
- **`completed` + `reason: cap_exceeded`, never `cancelled`, confirmed
  exactly**: the reason-assignment guard is `if hit_tool_budget && status
  == DelegationRunStatus::Completed && reason != Some(NoAnswer) { reason
  = Some(CapExceeded); }` — the condition is gated on the status already
  being `Completed`, so a budget-exhausted run can only ever surface as
  `completed`/`cap_exceeded`, never as `cancelled` — matching the PR's
  stated design exactly: "telling the origin model the run failed would
  tell it to throw the work away," when in fact the model finished in
  prose with a partial-but-usable answer.
- **Budgets exist only for task runs, confirmed exactly**: `launch_delegation`
  derives `task_scope` as `matches!(target, DelegationTargetSpec::Task {
  .. }).then_some(context.task_scope.as_ref()).flatten()`, and
  `max_server_tool_calls_per_task`/`max_client_tool_calls_per_task` on
  the persisted `TaskSpec` are both `task_scope.map(|scope| ...)` —
  `None` for any @-mention run, which is confirmed to keep being bounded
  only by the pre-existing per-message cap, matching "Only a task run
  carries budgets: a mention run is bounded by the ordinary per-message
  cap, as it always has been."
- Per the PR (not independently re-verified given remaining scope): the
  disclosed default values (`max_server_tool_calls_per_task` = 5,
  `max_client_tool_calls_per_task` = 30); the two-budgets-never-summed
  design rationale (server calls hold backend session/connection/slot
  capacity that scales slowly, client calls run on the user's own
  device, so a `0` on one axis forbids that class outright without
  affecting the other); the "budget hit recorded out of band on the
  streaming task" mechanism (`background_tasks.rs`, 18 lines, stated as
  the same shape as the existing approval-pending flag, since a refused-
  on-budget tool-call part is otherwise indistinguishable from any other
  refusal from the outside); and the pre-existing per-message cap's
  `return Err` backstop being confirmed still present but now
  unreachable while a task budget is in force, per the PR (not
  independently located in this review).

## Compatibility and configuration

Purely additive to the not-yet-shipped `delegate_task` feature from
#1164 (itself gated behind `delegation.tasks.enabled` plus a facet
allowlist selection, defaulting to no observable effect). No
configuration change for any deployment not already opted into task
delegation; no migration.
