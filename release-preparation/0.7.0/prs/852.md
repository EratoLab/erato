# PR #852: Move the remaining documented hooks' surfaces out of inline styles

- PR: https://github.com/EratoLab/erato/pull/852
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Direct continuation of #851 (stacked on it), applying the same fix to
every remaining documented `data-ui` theming hook that still held its
surface styling inline (which outranks any `theme.css` author rule,
silently making the hook inert): `app-shell`, `page-shell`, `sidebar`,
`sidebar-header`, `sidebar-footer`, `chat-input-shell`, `chat-body`,
`chat-header`, `chat-message`, `chat-history-list`, `modal-shell`,
`modal-overlay`. Confirmed by reading the diff:

- Each moves to a new dedicated class (`.app-shell-skin`,
  `.page-shell-skin`, `.sidebar-skin`, `.sidebar-section-skin`,
  `.chat-input-shell-skin`, `.chat-body-skin`, `.chat-header-skin`,
  `.chat-message-skin`, `.modal-shell-skin`, `.modal-overlay-skin`) added
  to `globals.css` at the same after-`@tailwind utilities`,
  outside-`@layer components` position #851 established — confirmed via
  the diff hunk location, consistent with #851's documented placement
  rule (outranks a consumer utility, stays overridable from a later-loaded
  `theme.css`).
- Confirmed the one genuinely mixed case: the sidebar shell's `width` is
  computed at runtime from slim/expanded state and correctly stays
  inline — only its background/border/shadow move to `.sidebar-skin`.
  Three now-orphaned module constants
  (`compactShellPaddingStyle`/`sidebarDividerColor`/
  `sidebarSectionBackground`) used only by the removed inline styles are
  deleted, confirmed via the `ChatHistorySidebar.tsx` diff.
- Confirmed `chat-history-list` is included even though its blocked
  property is padding, not a visual "surface" per se, per the PR's own
  framing — it was equally inert as an inline style regardless of which
  CSS property was involved.
- The PR states it checked the one real customer theme present in the
  repo against this change and found no currently-dead rule gets
  activated by it, because that theme consistently overrides via
  `background-image` and CSS custom properties (techniques an inline
  style doesn't block) rather than the specific properties this PR
  unblocks — not independently re-verified by inspecting that theme
  directly, but a specific, checkable claim consistent with the general
  pattern established in #851.
- Per the PR, 7 existing test assertions had been asserting the inline
  values directly (enforcing the defect) and are now rewritten to assert
  the class is applied and the skin longhands are absent from inline
  style — not independently re-verified line by line across all 7 test
  files touched.
- Explicitly out of scope, per the PR: elements with no documented
  `data-ui` hook (sidebar item rows, attachment previews, `Alert`) still
  hold radius inline, and the modal close button keeps its own padding
  token inline alongside positioning, since converting it would orphan a
  token that exists specifically to align it with the modal's own
  padding. The PR proposes a follow-up contract test — render each
  documented hook and assert no skin longhand appears in its inline
  `style` — now that the tests which previously enforced the opposite are
  gone.

## Compatibility and configuration

No new configuration keys. Fix specifically for custom-theme authors:
`theme.css` rules against any of the 12 hooks listed above now actually
take effect for background/border/radius/shadow/padding, where they
previously had no effect. No visual change for the default/stock theme,
and — per the PR's own downstream check — no known effect on the one
existing customer theme in the tree either.
