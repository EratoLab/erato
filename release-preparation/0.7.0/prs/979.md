# PR #979: Chat provenance envelope, seed_chat_lineage, ContextRebase (ERMAIN-620)

## Summary

Second of a 5-part stacked delegation series (on top of #978's config
layer). Ships the shared, reusable primitives for copying chat context
between chats and re-composing prompts correctly afterward — per the PR,
mergeable standalone since nothing user-facing changes until the later
runtime layer (#981) actually calls these functions. Given the
correctness-critical nature of this layer, all three of its core
mechanisms were verified by direct code reading.

- **Provenance envelope + generated column, confirmed via the migration**:
  `chats.origin_chat_id` is a Postgres `GENERATED ALWAYS ... STORED`
  column computed directly from the JSON
  `assistant_configuration.provenance.origin_chat_id` path — not a
  separately-written column, so it can never drift out of sync with the
  JSON it's derived from. Confirmed **no foreign key** is added (matching
  the stated design: origin ids are plain values, so a deleted origin
  chat leaves a tolerated dangling reference rather than blocking
  deletion or requiring cleanup-order coordination). Two partial indexes
  are added: one on `origin_chat_id` (non-null only) and one specifically
  for listing delegated runs (`WHERE provenance.kind = 'delegation'`,
  ordered by `owner_user_id, updated_at DESC`) — the latter presumably
  feeding the later "listing" layer (#982).
- **`seed_chat_lineage`, confirmed via full read**: walks a message chain
  from a given source message back to its root via `previous_message_id`,
  with cycle protection (a `visited` set that breaks the walk rather than
  looping forever on a corrupted chain); copies each message into the
  target chat with a fresh database-generated id, correctly rewires
  `previous_message_id` to the new chain (not the original), explicitly
  clears `sibling_message_id` (no branch groups carried over), forces
  `is_message_in_active_thread: true` for every copied message, and
  copies every payload/timestamp column verbatim (confirmed the function
  doc's framing that "snapshots are audit truth" — genuinely a byte-for-
  byte copy, not a re-derivation). File references are deduplicated
  (`BTreeSet`) and linked via one `chat_file_uploads` join row per
  distinct file, with an existence check to avoid a duplicate-key
  conflict. Confirmed the function does **not** create the target chat,
  check authorization, or write provenance itself — those remain the
  caller's responsibility, exactly as the PR states.
- **ContextRebase, confirmed via full read of the `transforms.rs` diff**:
  a chat's `rebase_cutoff` (from its own provenance) is read directly
  inside the shared prompt-composition function
  (`build_abstract_sequence_with_facet_tool_expansions`) — confirmed this
  is the same function token estimation composes through, so the PR's
  "applies it identically" parity claim follows structurally, not just by
  assertion. When the most recent history message with generation input
  predates the cutoff, `should_add_system_prompts` and the
  assistant-files-injection condition are both widened to also fire in
  that case (previously true only for a chat's first message) — meaning
  the current assistant's system prompt, hidden-facet prompts, and files
  are freshly injected, while the existing "a snapshot never contributes
  system messages once a new head exists" resolution rule (unmodified by
  this PR) correctly drops the replayed old snapshot's own system plane.
  Confirmed the mechanism is genuinely self-retiring: once a post-cutoff
  generation's own snapshot becomes the new replay anchor, its
  `created_at` naturally falls after the cutoff and the condition stops
  firing on its own, with no explicit "unset the flag" step needed.

## Compatibility and configuration

New database migration (`0036_add_chat_provenance`, additive generated
column + two partial indexes, includes a revert script) — requires a
migration run on upgrade. No behavior change for any existing chat or
deployment: `provenance` is an optional field on `assistant_configuration`
that nothing writes yet in this PR, so `origin_chat_id` resolves to `NULL`
for every pre-existing row and the ContextRebase branch never fires
without a provenance envelope present.
