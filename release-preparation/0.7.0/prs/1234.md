# PR #1234: Add approval flow for file uploads from client tools

- PR: https://github.com/EratoLab/erato/pull/1234
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Desktop Sidecar for local sources

## Summary

Adds a user-facing approval gate before a client tool (e.g. the desktop
sidecar's `get_sidecar_document` tool from #1229, which uploads a local
document the model asked for) actually uploads a file to the chat. New
`ClientToolFileApproval` enum: `never_allow` | `ask` (default) |
`always_allow`. A new organization-wide default,
`desktop_sidecar.file_upload_approval` (defaults to `ask`), is
overridable per-user via a new `user_preferences.client_tool_file_approval`
database column (nullable, `CHECK` constrained to the same three values;
migration `0048_add_client_tool_file_approval`). On the frontend, a new
`ClientToolFileApproval.tsx` message component
(`frontend/src/components/ui/Message/`) presumably shows an inline
approve/deny prompt when a client tool wants to upload a file and the
effective setting is `ask`; a new `ClientToolFileApprovalSetting.tsx` in
the desktop sidecar settings tab (from #916) lets a user change their
personal override; `useClientToolFileApproval.ts` and a new Zustand-style
`clientToolFileApprovalStore.ts` manage the approve/deny interaction
state. `frontend/src/lib/desktopSidecar/chatTools.ts`'s `get_sidecar_document`
tool (121-line diff total) is updated to route through this approval gate
before uploading.

## Compatibility and configuration

New optional org-wide config key, defaulting to the safest, most visible
option:
```toml
[desktop_sidecar]
file_upload_approval = "ask"  # default; or "never_allow" | "always_allow"
```
Plus a new per-user override stored in `user_preferences`, settable from
the desktop sidecar settings tab. New additive database migration (a
nullable `CHECK`-constrained column, safe on existing rows — `NULL` means
"no user override, use the org default"). No breaking change; this gates a
capability (#1218/#1229's client-tool file uploads) that was itself newly
introduced this same release cycle, so there's no prior "always allowed"
behavior being newly restricted for existing users of a stable feature.
