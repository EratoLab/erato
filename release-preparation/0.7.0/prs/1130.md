# PR #1130: Match the Markdown field's focus highlight to its frame

- PR: https://github.com/EratoLab/erato/pull/1130
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a real, reported-from-the-running-app visual bug: focusing the
assistant Description field (a `MarkdownPreviewInput`) drew a fully
rounded focus ring inside a frame that is square where it meets the
tab strip — because `MarkdownPreviewInput` tried to flatten the inner
`Textarea` via suppressing classes (`rounded-none border-0
focus:ring-0`) passed through `className`, but with no `tailwind-merge`
in this repo, those classes merely raced the `Textarea`'s own base
utility classes at equal specificity, and (measured by the PR author in
Chromium) two of the three suppressors lost that race. Confirmed by
reading the complete `Textarea.tsx` diff and the relevant
`MarkdownPreviewInput.tsx` diff:

- **`frame` is a variant, not a suppressing class, confirmed exactly**:
  `Textarea` gains an additive `frame?: boolean` prop (default `true`).
  When `false`, the entire block of frame-related classes (`border-radius`,
  `border`, the focus-border/ring color classes, `focus:ring-2`) is
  omitted from the `clsx` call entirely via a conditional array
  (`frame && [...]`) — not emitted-then-overridden — so there is no class
  for a container to lose a specificity race against. Confirmed this
  structurally eliminates the exact bug class the PR diagnoses (an
  emission-order race with no `tailwind-merge` to resolve it), not just
  this one instance of it.
- **The container now owns the focus indicator via `:has()`, confirmed
  exactly**: `MarkdownPreviewInput`'s frame div gains
  `[&:has(textarea:focus)]:border-...` / `:ring-2` / `:ring-theme-focus`
  rules (and the equivalent error-state variant) — confirmed scoped
  specifically to `textarea:focus`, not `:focus-within`, with a code
  comment stating this is deliberate: the frame also contains the
  Markdown/Preview tab buttons, and `:focus-within` would light up the
  whole field a second time whenever a tab (not the textarea) receives
  focus, stacking on top of the tab's own focus ring.
- **`frame` is excluded from the passthrough prop type, confirmed
  exactly**: `MarkdownPreviewInputProps extends Omit<TextareaProps,
  "className" | "frame">` — preventing any caller from re-enabling the
  inner textarea's own frame via prop spreading, which would reintroduce
  the double-frame bug this PR fixes.
- **The refuted alternative approach, confirmed consistent with the
  actual fix**: the PR's own prose states that simply squaring the
  textarea and relying on the frame's `overflow-hidden` to clip its ring
  was tried first and rejected, since the textarea's horizontal extent
  matches the frame's padding box exactly — both vertical edges of a
  clipped ring would fall entirely inside the clipped-away region,
  producing two disconnected floating horizontal bars rather than a
  clean ring. This reasoning (not independently re-simulated in this
  review) is consistent with why the actual fix moves the ring to the
  container rather than attempting to make the clipped child's ring work.

## Compatibility and configuration

None breaking. Visual bug fix: the Markdown/preview field (used for the
assistant Description field, among other surfaces) now shows a focus
ring that matches its own square-cornered-at-the-tab-strip frame, instead
of a fully rounded ring floating inside it — most visible under themes
with a larger `--theme-radius-input` (the PR measures 24px under
`open-webui-like` versus 16px at stock).
