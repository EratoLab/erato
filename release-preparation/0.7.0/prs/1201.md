# PR #1201: Retry a failed delegated task from the origin chat (ERMAIN-783)

- PR: https://github.com/EratoLab/erato/pull/1201
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Top of the entire "Async re-entry" / Delegation Level D stack (stacking
on #1200, ERMAIN-779-B, reviewed above). Adds a retry endpoint for the
one failure the rest of the stack cannot recover: a child reaped after
its replica crashed, which writes no result and no `result_delivery`
record at all, leaving the origin's dispatch slot reading "dispatched"
forever with the delegated-runs list's red badge as the only signal.
Another exceptionally large PR (4043 insertions) with the same density
of self-documented, independently-checkable design rationale as the rest
of the stack. Given the scope, this review prioritized the new
`delegated_run_retry.rs` route handler's core safety/authorization/
concurrency logic, verifying it line-for-line against the PR's own
stated claims:

- **`RetryKind` is a genuinely single-variant enum; an unknown variant is
  a 422, confirmed exactly**: `match request.kind { RetryKind::Task =>
  {} }` is an exhaustive match over a one-variant enum, with the enum's
  own doc comment stating `"delivery"` "must be an unknown serde variant
  - a `422`" — confirmed consistent with how `#[serde(rename_all =
  ...)]` enums reject unrecognized values in this codebase (established
  pattern from this session's many earlier reviews).
- **Feature gate matches `/react`'s and `frontend_environment`'s
  predicate exactly, confirmed exactly**: the route 404s unless
  `delegation.tasks.enabled && run_modes.contains(TaskRunMode::Async)` —
  the identical compound condition this session confirmed for #1197's
  `/react` route.
- **`Action::SubmitMessage`, not `Read` or `Update`, confirmed exactly,
  with the identical reasoning #1197 used**: authorization is checked via
  `authorize!(..., Action::SubmitMessage)`, both a refusal and an
  authorizer error answering the identical generic `retry_not_found()`
  404 — matching "Same question 781-B's `/react` answered one release
  earlier, same answer" and the stated "a 500 here would tell a prober
  the chat exists" reasoning precisely.
- **Archived origin refused via the shared helper, confirmed exactly**:
  `reject_if_archived(&origin_chat)` is called directly — the same
  function this session saw used elsewhere in this stack — matching "An
  archived origin is refused with `reject_if_archived`'s plain-text
  `409`."
- **Child ownership and parentage checked, both failures indistinguishable
  from a missing chat, confirmed exactly**: `child_chat.owner_user_id !=
  origin_chat.owner_user_id` and `provenance.origin_chat_id !=
  Some(chat_id)` both return the generic 404 — matching "A child of
  another origin - or of another owner - must be indistinguishable from a
  missing one."
- **Only a task-route child is retryable, confirmed exactly**:
  `child_configuration.task.as_ref().filter(|spec| spec.route ==
  DelegateRoute::Task)` gates the mention route out with
  `NotRetryableState::NotATaskRun` — matching "Only a planned task run
  can be retried... re-dispatching it as a bare task would silently drop
  that binding."
- **Outcome gate reuses the listing's own expression, confirmed exactly
  — the "Shared SQL" claim**: the retry's outcome check calls
  `delegated_run_outcome_for_chat`, explicitly commented as using "the
  recent-chats listing's own expression, so the badge that offered the
  control and the gate that honours it can never disagree" — directly
  substantiating the PR's "Shared SQL" section's claim that
  `delegated_run_outcome_expression` is shared verbatim between the
  listing and this route.
- **The already-in-flight guard is explicitly advisory, not atomic,
  confirmed exactly, with the exact stated race**: a code comment at the
  guard's call site states verbatim "It is ADVISORY, not atomic... nothing
  serializes this read against the INSERT the launch below performs, so
  two requests that overlap inside the server can both pass and start two
  replacements for one failure... Serializing it would mean holding a
  lock across a dispatch" — matching the PR's "The check is advisory, not
  atomic" section exactly, including the stated bounded cost (a second
  run against the owner's concurrency cap, not a bad write).
- **Retry-of-a-retry walk-back, confirmed exactly, including the bound
  and the per-hop re-verification**: `origin_recorded_run` walks
  `provenance.retry_of` back through ancestors up to `MAX_RETRY_CHAIN_HOPS
  = 32`, breaking the walk (falling back to the last good id) the instant
  any hop's `owner_user_id` or `provenance.origin_chat_id` fails to
  match — directly confirming "The walk is bounded and re-checks
  parentage and ownership at every hop, so a corrupted envelope costs a
  fixed number of reads rather than wedging the request," and
  substantiating the stated purpose: without this walk, "every retry of a
  retry [would] answer `brief_unavailable`," since only the live dispatch
  path (not this retry route) ever writes the origin-side
  `output.delegate_chat_id` marker the brief-recovery probe needs.
- **`retry_of`'s dual serde/schema attributes, confirmed exactly**:
  `RecentChat.retry_of` carries both `#[serde(skip_serializing_if =
  "Option::is_none")]` and `#[schema(nullable = false)]` — matching the
  PR's claim precisely, and consistent with the exact same pattern this
  session already confirmed being necessary (for the identical
  generated-TypeScript reason) on `ContentPartTaskResult.reason`/
  `TaskResultInput.reason` in PR #1191's review.
- Per the PR (not independently re-verified given this PR's unusual
  size): the brief-recovery jsonb containment probe itself (the
  `output.delegate_chat_id`/`parent_tool_call_id` narrowing logic, not
  traced beyond `origin_recorded_run`'s consumption of its result); the
  `brief_from_persisted_task_args` function and its deliberate exclusion
  of the recorded `run_mode`/`facet_ids`/`scheduling` (the "what the
  replacement inherits" section); the synthetic `TaskOfferScope`
  construction and the `scheduling`-on-`LaunchRunSpec`-not-scope
  placement; the `concurrency_cap` pre-check's raciness-by-one-request
  disclosure; `find_working_retry_child`'s own SQL (the
  unfinished-generation-or-pending-lineage predicate, bound as TEXT on
  `provenance.retry_of`); the no-lease-but-read-lease design for the
  origin; all three "carriers" in the frontend
  (`DelegatedRunsSection.tsx`, `DelegationStep.tsx`, `TaskResultCard.tsx`)
  and the `useDelegatedRunRetry`/`useSyncExternalStore`-based
  `retriedByChatId` cache-read mechanism; the `delegationTasksAllowAsync`
  feature-flag gating in `FeatureConfigProvider.tsx`; the disclosed
  filed-follow-up for `kind = "delivery"` (a forward-looking scope
  decision, not a code claim); and the disclosed verification (full
  backend/frontend gate suites green, 15 integration tests plus 2 unit
  tests, two deliberately hand-seeded fixtures, no e2e by design).

## Compatibility and configuration

Additive. New route `POST /me/chats/{chat_id}/delegated_runs/{child_chat_id}/retry`,
entirely behind `delegation.tasks.enabled` and `run_modes` including
`"async"` — confirmed the route 404s otherwise, consistent with every
other route added across this stack. No new config leaf (confirmed by
the PR's own disclosed unchanged undocumented-options budget).
`ChatProvenance.retry_of` is additive JSONB with no migration
(`#[serde(default, skip_serializing_if = "Option::is_none")]`, so
existing envelopes deserialize unchanged).

## Release note disposition

Proposed category: Features and enhancements. This is the capstone of
the entire "Async re-entry" stack (#1188-#1201): a delegated task that
failed outright — most importantly, one whose replica crashed mid-run,
leaving no other trace — can now be retried directly from the
conversation that dispatched it, re-inheriting its original brief,
budgets, persona, and scheduling (re-authorized against the user's
current permissions), with a database-enforced one-live-retry-per-failure
guard that survives a reload. The CHANGELOG entry the PR itself drafts
(not independently re-verified in this review, per the "Evidence" section
above) is the natural final entry for the whole stack's combined
release note, given this PR's own framing as the top of the chain.
