# PR #997: Reduce build cache thrash by using branch-aware cache tags

- PR: https://github.com/EratoLab/erato/pull/997
- Status: pending
- Category: Chores & Developer experience
- Theme: None

## Summary

Fixes Docker build-cache contention in
`.github/workflows/docker-build.yml`. Previously every build (main branch
and every PR branch alike) shared a single `:latest-<arch>-buildcache` tag
per image, so concurrent builds from different branches would repeatedly
overwrite each other's registry build cache, causing frequent cache misses
("thrash"). A new `resolve-registry-cache-refs` job computes a
branch-aware cache scope: pushes to `main` use the `main` scope as before,
while a pull request gets its own scope derived from
`sha256(repository:branch)` (truncated to 32 hex chars) for both its base
and head branch. Each `build-and-push-*` job then reads
`CACHE_TARGET`/`CACHE_SOURCE`/`CACHE_DESTINATION` from this resolver job
and uses them to build a layered `cache-from` list (the PR's own branch
cache, falling back to its source/head branch's cache, falling back to
`main`'s cache) while always writing (`cache-to`) to its own branch-scoped
cache tag — so a PR branch no longer clobbers `main`'s (or another
branch's) build cache, while still benefiting from `main`'s cache as a
fallback for anything not yet built on the PR's own branch. The
`pull_request` trigger's `branches: [ main ]` restriction was also
removed, so this workflow now runs on PRs targeting any branch, not just
`main`.

## Compatibility and configuration

No configuration keys, migrations, or production runtime changes; this is
purely a CI build-caching optimization. No behavior change to the images
themselves — image tags, contents, and push destinations for the final
Docker images are unaffected; only the intermediate `*-buildcache`
registry tags used to speed up Docker layer reuse are now branch-scoped.
Removing the `branches: [ main ]` restriction on the `pull_request`
trigger means this workflow will now also run for PRs targeting
non-`main` branches (e.g. this release-preparation branch itself, or
other long-lived branches), which could mean more CI minutes consumed
depending on branching practices.
