# PR #1009: Drain in-flight generations on shutdown so their fate is recorded (ERMAIN-639)

- PR: https://github.com/EratoLab/erato/pull/1009
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Fixes a real, previously-existing gap (not specific to delegation, but
made consequential by it): the backend served requests with no
`with_graceful_shutdown` at all, so a SIGTERM (how Kubernetes asks a pod
to stop) simply dropped the whole Tokio runtime, killing every in-flight
generation mid-stream with no record of what happened. For an ordinary
chat the user is watching this, and retries; for a background delegated
run (#1005), the parent turn had already reported the work as dispatched
— so losing it on a pod restart was silent, unrecoverable data loss.
Confirmed by reading the full `main.rs` diff, this is an unusually
carefully sequenced fix:

- **Aborts are triggered from inside the shutdown-signal future itself,
  before `axum::serve`'s graceful connection drain completes — confirmed
  precisely, with the deadlock this avoids explained in the code's own
  comments**: `with_graceful_shutdown`'s built-in behavior waits for every
  open response to finish before returning, but a live SSE stream (an
  in-progress chat generation) only ends once its underlying generation
  actually stops. If the abort were issued only *after* `serve` returned,
  the server would sit blocked waiting for its own open SSE connections
  to close — which nothing would ever cause, reproducing exactly the bug
  being fixed (only reachable via SIGKILL). The fix calls
  `background_tasks.request_abort_all()` from inside the same future
  passed to `with_graceful_shutdown`, so aborting happens concurrently
  with (and before) the connection drain waits on those same streams to
  end.
- **A single shared deadline budgets both shutdown phases, confirmed via
  the `tokio::sync::watch` channel mechanism**: a new
  `generation_status.shutdown_drain_secs` config value (default 25,
  chosen to fit inside Kubernetes' default 30-second termination grace
  period) sets one deadline the moment the shutdown signal fires. The
  `axum::serve(...).with_graceful_shutdown(shutdown)` future is raced
  (`tokio::select!`) against that same deadline elapsing — so a wedged
  handler or a stalled SSE tail can no longer block shutdown indefinitely,
  confirmed via a code comment stating that without this race, everything
  after `serve` (the abort sweep, the generation drain, final logging)
  would simply never run. Once `serve` actually returns (or the deadline
  forces it), the subsequent generation-drain phase is given only
  whatever time remains of the *same* deadline, not a fresh window —
  confirmed via the `saturating_duration_since` calculation reading back
  from the shared `drain_deadline_rx`.
- A second, redundant `request_abort_all()` sweep runs after `serve`
  returns, confirmed present, specifically to catch a generation spawned
  by a request that slipped past the listener in the narrow window before
  shutdown fully engaged.
- `tokio`'s `signal` feature is made explicit in `Cargo.toml` rather than
  relied upon via feature unification from another dependency — a minor
  but real build-robustness fix (an unrelated dependency change could
  otherwise silently remove `signal` support).
- Per the PR (not independently re-verified in `background_tasks.rs`'s
  134-line diff): the drain loop re-issues its idempotent abort on every
  poll iteration, specifically because a winding-down parent generation
  could still complete an in-flight tool call and dispatch a *new*
  background child that registers after both abort sweeps already ran —
  the PR states this per-iteration re-abort is what catches that case,
  with each task's own existing cleanup tail persisting its outcome as
  usual.
- The PR explicitly frames the chosen behavior as "abort cleanly and
  record the fate," not "finish the work" — restart-durable generations
  that survive and resume across a pod restart are named as separate,
  future work, not attempted here.

## Compatibility and configuration

New, optional config field:
```toml
[generation_status]
shutdown_drain_secs = 25  # default; 0 = no wait, aborts still fire immediately
```
Behavior change for every deployment on upgrade: a pod shutdown (SIGTERM)
now cleanly aborts and records the outcome of in-flight generations
(ordinary and delegated) within the configured drain window, instead of
abruptly dropping all connections and losing that state — a genuine
reliability improvement for any deployment doing rolling restarts, not
specific to the still-gated background-delegation feature.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read the complete `main.rs` diff in full — confirming
the precise sequencing (abort-before-drain-completes, the single shared
deadline spanning both shutdown phases, and the redundant post-serve
sweep) exactly as described, including the specific deadlock scenario the
ordering avoids. Not read in full: the 134-line `background_tasks.rs`
diff implementing `request_abort_all`/`drain` themselves (including the
claimed per-iteration re-abort behavior), though the PR's own unit tests
(abort-all reaches every registered task, drain completes promptly on
self-cleanup, drain gives up at its deadline, a task registered mid-drain
still gets aborted) are a plausible and appropriately targeted test suite
for the claims made.

## Release note disposition

Proposed category: Bug fixes (reliability). Worth a mention independent
of the delegation feature it was motivated by: an in-progress chat
response is no longer abruptly lost during a server restart/deployment —
it's now cleanly stopped and its partial outcome recorded within a
configurable grace window.
