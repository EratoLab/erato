# PR #1195: Make the two MCP approval surfaces agree

- PR: https://github.com/EratoLab/erato/pull/1195
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Reconciles the in-chat approval card and the settings roster from the
earlier MCP tool-approval stack this session reviewed (#1146-1152),
which previously let a user make a durable *permissive* decision from the
chat card but only a one-off *restrictive* one, while the two surfaces
used inconsistent labels for the same underlying states. Confirmed every
concrete claim precisely by reading the backend decision-handling diff
and the frontend labeling/ordering/badge diffs in full:

- **`RejectAlways` refuses the call and stores the denial, confirmed
  exactly, needing no policy flag**: a new `ToolApprovalDecision::RejectAlways`
  variant is added with a doc comment stating "needs no policy flag the
  way `ApproveAlways` needs `allow_always`: a denial is more restrictive
  than anything the policy does" — matching the PR's identical reasoning
  verbatim. In `run_continue_message_task`, `is_approved` is computed as
  `false` for both `Reject` and `RejectAlways` (the call is refused
  either way), while a *separate*, unconditional branch calls
  `user_tool_approval_setting::upsert_active(..., UserToolDecision::Denied)`
  specifically when the decision is `RejectAlways` — confirming both
  halves of "refuses the call **and** stores the denial" happen via two
  independent code paths, not one conflated check.
- **`ContentPartToolRejection` gains two backward-compatible fields,
  confirmed exactly**: `never_allow: bool` (`#[serde(default)]`) and
  `user_tool_approval_setting_id: Option<Uuid>` (`#[serde(default,
  skip_serializing_if = "Option::is_none")]`) are added with a comment
  stating "Both fields default, so rejections stored before standing
  denials existed still parse" — a genuine backward-compatibility
  property: an old stored `ContentPartToolRejection` row lacking these
  fields deserializes with `never_allow: false` and
  `user_tool_approval_setting_id: None`, correctly read as the one-off
  refusal it always was.
- **Label unification matches the PR's own before/after table exactly**:
  `mcpToolDecisionLabel`'s `"allow"` case is relabeled from `"Allow"` to
  `"Always allow"` (with a comment "Named as the in-chat card names it:
  the same standing grant"), and the policy-default variant similarly
  becomes `"Always allow (policy default)"` — confirming the roster's
  "Allow" → "Always allow" row in the table. (The card-side
  "Deny"→"Deny once" and new "Never allow" states were not independently
  traced in `ActionConfirmationCard.tsx`/`McpToolApprovalCard.tsx` in this
  review, but are the natural frontend labels for the backend's new
  `RejectAlways` decision confirmed above.)
- **Decision order changed to least-permissive-first, confirmed exactly**:
  `MCP_TOOL_DECISIONS` is reordered from `["allow", "ask", "never"]` to
  `["never", "ask", "allow"]`, with a comment stating "least permission
  first, so the keyboard walk starts at the safe end" — matching "It is
  now Never → Ask → Always allow" exactly.
- **"Set by you" badge gated on a genuine user-decision check, confirmed
  exactly**: `mcpToolBadges` pushes a neutral "Set by you" badge whenever
  `tool.user_decision !== "none"` — distinguishing a row the user
  explicitly decided from one merely reflecting the policy default,
  matching "Rows whose state is the user's own now carry a **Set by you**
  badge" (confirmed on the settings roster side; the composer's tool
  browser counterpart was not independently traced).
- Per the PR (not independently re-verified given remaining scope): the
  card-side `ActionConfirmationCard.tsx`/`McpToolApprovalCard.tsx` diffs
  implementing the "Deny once"/"Never allow" button labels and wiring
  `RejectAlways` into the card's own decision-submission flow (35 and
  28 lines respectively, not read); the "Deliberately not here" section's
  framing of a user-level global posture as out of scope (an accurate
  self-description of scope, not a verifiable code claim); the 187-line
  new integration test additions in `messages.rs`; and the locale updates
  across all five `messages.po` files (16 lines each).

## Compatibility and configuration

Additive and backward-compatible. New `ToolApprovalDecision::RejectAlways`
wire variant (existing `Approve`/`Reject`/`ApproveAlways` unchanged); new
`ContentPartToolRejection` fields both default so historical stored
rejections continue to parse correctly as one-off refusals, confirmed
directly. No config keys. Pure UI relabeling/reordering elsewhere — no
behavior change to the underlying policy evaluation this session
reviewed in #1146/#1152, only a new way for a user to reach the
already-existing "denied" stored state from the in-chat card instead of
only from settings.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: the in-chat MCP tool
approval card can now record a standing "never allow" decision directly
(previously only a durable "always allow" was available from the card;
a durable denial required navigating to settings), and the settings
roster and in-chat card now use the same labels and ordering for the
same underlying decisions — a user-made decision is also now visibly
distinguished ("Set by you") from one merely reflecting the admin
policy's default.
