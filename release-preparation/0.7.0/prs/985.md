# PR #985: Delegation trace: nested child steps in the tool call, open-run link (ERMAIN-624)

- PR: https://github.com/EratoLab/erato/pull/985
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Second of the 3-part delegation frontend stack (on top of #984). Makes a
delegated child run's execution visible in the origin chat: the tool-call
trace now streams the child's own steps as nested sub-steps live, and the
finished step links to the delegated chat itself. Given the exceptional
scope (2798 insertions), review prioritized the single most
security-relevant property the PR itself calls out: that the delegation
trace, once persisted for the UI's benefit, must never leak back to the
model on a later turn.

- **Confirmed the model-leak prevention precisely, via full diff of
  `transforms.rs`**: the PR's own reasoning is that leaving
  `model_response_text()` untouched is *not* sufficient, because the
  trace has to be persisted on the tool-call's `output` field for the UI
  to render it after a reload — and history replay (`resolve_sequence`,
  the same shared composition path #979 confirmed token estimation also
  goes through) pushes a stored tool-use part back into the prompt
  verbatim as a `ToolResponse`, which would hand the origin model the
  delegate's entire tool inventory and whatever content steered it on the
  *next* turn. The fix, `strip_ui_only_tool_output`, is applied
  unconditionally to every replayed `ToolUse` in `resolve_sequence`: it
  removes the trace's specific JSON key
  (`DELEGATION_LOCAL_TRACE_KEY`) from the output object if present, and
  is confirmed to be a true no-op for every other tool's output (since
  that key simply won't exist there). A backend test (not independently
  re-run) asserts a follow-up turn's request body carries the delegated
  chat's id but never the trace.
- **Transport design, confirmed by reading the PR's own stated
  reasoning as internally consistent** (not independently re-verified
  against `delegation_trace.rs`'s 458 new lines): rather than a new SSE
  event type, child progress rides the *existing* `ToolCallUpdate` frame
  shape with `status: in_progress`, each frame carrying the full
  cumulative trace so far — since the frontend is already last-write-wins
  on a tool part's `output`, live streaming, a `resumestream` replay, and
  the eventually-persisted record all collapse onto the same reader with
  no new store or stream-event handler needed, and re-emitting a
  `sequence` number makes replay idempotent. The tap into the child's
  broadcast receiver is stated to be inline in the dispatch future (not a
  separately spawned task), so it can't outlive dispatch or leak on the
  abort/detach path from #981, and terminates on all four of that PR's
  exit paths (child join, parent abort, run timeout, stream end); frames
  coalesce (structural changes always flush; in-progress updates within
  one step are rate-limited to every 300ms) since every frame is both
  broadcast live and persisted. Trace steps deliberately exclude the
  child's own text, tool outputs, and MCP progress messages — described
  as untrusted third-party content that would otherwise render inside the
  *parent's* chat. A timed-out or cancelled child still persists its
  partial trace, since that's exactly the case where it's most useful to
  see.
- Frontend: a new `DelegationStep` component (selected inside
  `ToolUseStep` by tool name) renders "Delegating to {name}" with a
  running-state pill, a result summary on completion, and distinct
  wording for failed/timed-out/cancelled outcomes — with an explicit
  fallback to the plain generic tool rendering for a malformed envelope
  or an unexpected refusal shape (never throwing). The "open the delegated
  run" link opens `getChatUrl(delegate_chat_id, ...)` in a new tab and,
  since `delegate_chat_id` arrives on the very first progress frame, is
  available while the delegation is still running, not only once it
  finishes. `SidecarLocalTraceView` (from #976) is refactored to extract
  its generic row/rail rendering into a new `NestedTraceView`, reused by
  both the sidecar-search trace and this new delegation trace — stated to
  leave the existing sidecar view's behavior and test ids unchanged.
- The persisted-trace reader from #976's `localTraceStore` is extended to
  also accept a top-level `localTrace` field (needed because the
  delegation envelope's own `result` field is itself a string, so the
  existing `output.result.localTrace` lookup path could never match it)
  — confirmed the PR states the existing tool-name allowlist gate (the
  anti-forgery mechanism verified directly in #976) is kept in place for
  this new path too, so a non-delegation tool still can't claim a trace
  this way.

Per the PR, the new `e2e-tests/tests/delegation.assistants.spec.ts` was
authored but **not executed** (it requires the k3d stack), and enabling
delegation in that E2E scenario additionally switches its chat-provider
priority order to the mock LLM (since a delegated child always inherits
`chat_providers.priority_order[0]` rather than its parent's specific
provider), which the PR notes also changes what an existing, unrelated
test in that same scenario receives — flagged as a reason to re-run the
whole `assistants` E2E project, not just the new spec, before merging.

## Compatibility and configuration

None new beyond the existing delegation config gate (#978). No new SSE
event type, no OpenAPI regeneration, confirmed per the PR's stated design
(reusing the existing `ToolCallUpdate` frame shape). No behavior change
for any deployment without delegation enabled.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the relevant `transforms.rs` diff,
confirming the model-leak-prevention mechanism (`strip_ui_only_tool_output`)
precisely — this is the property whose correctness matters most in this
PR, since a failure here would leak a delegate's execution details back
into the origin model's context on every subsequent turn. Given the
PR's very large remaining scope, the following were not independently
read: the new 458-line `delegation_trace.rs` (the actual event-tapping/
coalescing implementation), the 214-line `DelegationStep.tsx`, the
164-line `NestedTraceView.tsx` extraction, the 82-line
`delegationEnvelope.ts` parser, the mock-LLM-server additions (247+ lines
across several files supporting the new E2E scenario), or the unexecuted
E2E spec itself.
