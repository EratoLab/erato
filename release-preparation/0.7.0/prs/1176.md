# PR #1176: Show a trace step as running from its own status, not its position (ERMAIN-771)

- PR: https://github.com/EratoLab/erato/pull/1176
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Standalone PR (position 4 in the "Dynamic Delegated Tasks" stack, no
dependency on the rest). Fixes `stepStatus`, which previously only ever
rendered the *last* step of an active trace as "running" — correct for
reasoning (only the tail is being written) but wrong for a tool call,
which carries its own liveness and can be one of several running in
parallel (relevant once a turn dispatches several delegated tasks
concurrently, per the broader stack this PR is part of). Confirmed by
reading the complete `useTraceState.ts` diff and the relevant
`DelegationStep.tsx` changes in full:

- **The position-based restriction removed for tool calls, kept for
  reasoning, confirmed exactly**: the `tool_use` branch of `stepStatus`
  changes from `return isLastStep && isTraceActive ? "running" : "done"`
  to `return isTraceActive ? "running" : "done"` — an unfinished tool
  call (neither `success` nor `error`) is now `running` regardless of its
  position in the timeline, as long as the trace is active. The
  `reasoning` branch is confirmed completely unchanged, still gated on
  `isLastStep && isTraceActive` — matching "Reasoning keeps the last-step
  rule" precisely.
- **Queued slots explicitly excluded from the pulse despite inheriting
  "running" from the rail, confirmed exactly**: `DelegationStep` computes
  `isQueued = envelope.status === "queued"` and then `isRunning =
  stepStatus === "running" && isStreaming && !isQueued` — so a queued
  slot (which the three-state rail would otherwise classify as
  "running," since it's neither settled nor erroring) is deliberately
  carved out of the pulsing-animation condition. A code comment states
  this exactly: "nothing about it is in flight, so it must not pulse or
  call itself running in the title."
- **Queued slots get their own copy instead of a false-past-tense label,
  confirmed exactly**: `stepTitle` gains an `isQueued` parameter and, for
  the task route specifically, returns `"Task queued"` when `isQueued` is
  true — checked before the existing `isRunning ? "Running a task" :
  "Ran a task"` branching — so a queued slot never falsely claims to have
  already run ("Ran a task") or to be actively in flight ("Running a
  task"). Confirmed gated to `toolName === DELEGATE_TASK_TOOL_NAME`
  specifically, consistent with the PR's stated "only the task route can
  queue" comment.
- **No new `TraceStepStatus` value needed, confirmed structurally**: the
  queued presentation (the pill and the rail-status-inheritance seam)
  already existed from #1162 (this session's earlier review of that PR
  confirmed the `queued` status was added to the accepted vocabulary
  there) — this PR only had to add the pulse-suppression gate on top of
  an already-existing rendering path, matching the PR's stated minimal
  scope exactly.
- Per the PR (not independently re-verified): the disclosed
  mutation-verification claim (restoring the last-step condition fails
  the new trace test, and dropping the queued gate fails the delegation
  test) and the new `toolUsePartHelpers.test.ts` characterizing what
  parallel tool-call slots need from the underlying helpers (distinct
  indices preserving call order, two in-flight parts settling by id) —
  not independently reproduced or read in this review.

## Compatibility and configuration

None. Pure frontend bug fix. Affects any turn with more than one
concurrent unfinished tool call — most visibly relevant once the
not-yet-enabled parallel-task-dispatch feature (later in the same
stack) ships, but also fixes any other scenario where multiple tool
calls are genuinely in flight within a single turn's trace.
