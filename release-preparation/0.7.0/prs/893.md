# PR #893: Add runtime_configuration table and startup mirroring

- PR: https://github.com/EratoLab/erato/pull/893
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds a new, opt-in `runtime_configuration` database table and startup
logic to mirror the backend's own loaded config source files into it.
The PR description is minimal ("Related ERMAIN-514"), so the following is
derived directly from reading the code, migration, and documentation:

- New migration `0031_add_runtime_configuration`: a `runtime_configuration`
  table (`source_service`, `source_filename`, `config` (text),
  `created_at`/`updated_at`) with an index on `source_service`. The
  `source_service` column (populated as the constant `"erato_backend"` by
  this PR) suggests this table is designed to hold mirrored config from
  more than one service, though only the erato backend's own mirroring is
  implemented here.
- Gated entirely behind a new `runtime_configuration.enabled` config flag
  (default `false`) — confirmed in `main.rs`: when disabled, no source
  files are even read into memory and `mirror_erato_backend_sources` is
  never called, so this feature has zero effect on any deployment that
  doesn't explicitly opt in.
- When enabled, every raw config file that was actually loaded (`erato.toml`
  plus any auto-discovered `*.auto.erato.toml` files) is read from disk
  verbatim, passed through `redact_toml_keys` (a new TOML-aware redaction
  utility, read in full, that surgically replaces a matched key's value
  with a literal `<redacted>` marker while preserving all surrounding
  formatting/comments byte-for-byte elsewhere), then encrypted (AEAD, via
  the existing `app_state.encrypt`, keyed by `server.encryption_key`) and
  written into the `runtime_configuration` table inside a transaction
  guarded by a Postgres advisory lock (serializing concurrent
  replacements — e.g. multiple backend replicas starting simultaneously —
  so one writer's delete-then-insert can't interleave with another's).
- **Confirmed and worth flagging clearly for maintainer/deployment
  awareness**: `RUNTIME_CONFIGURATION_REDACTION_PATHS` currently redacts
  **only** `server.encryption_key` itself (necessarily, since that value
  is the very key used to encrypt this data, and persisting it — even
  encrypted with itself — would be circular and unsafe). **No other
  secret-shaped config value is redacted.** This means, when this
  opt-in feature is enabled, a deployment's chat-provider API keys, OIDC
  client secret, database credentials (if configured in the TOML rather
  than solely via environment variables), MCP server auth tokens, SMTP
  credentials, and any other secret present in the loaded `erato.toml`
  are all mirrored into this new database table — encrypted at rest with
  the server's own encryption key, but otherwise fully recoverable by
  anyone who can both read that table and either access or derive that
  key (which the running application itself always can, by design). The
  documentation confirms this is the intended, documented behavior
  ("The encryption key value is redacted from the mirrored document
  before encryption, while the rest of the source file formatting and
  contents are preserved") rather than an oversight — but it's a
  meaningful new data-exposure surface for anyone enabling this feature,
  worth an explicit callout rather than treating it as an unremarkable
  detail.
- `runtime_configuration.validate()` requires `server.encryption_key` to
  be configured whenever the feature is enabled (confirmed a panic-on-
  invalid-config gate exists in `config.rs`, not read in full for its
  exact message).

## Compatibility and configuration

New, optional, default-`false` config section:
```toml
[runtime_configuration]
enabled = false  # default; requires server.encryption_key when true
```
No behavior change for any deployment that doesn't set this. New database
migration (`0031`, additive table, includes a revert script) — requires a
migration run on upgrade regardless of whether the feature is enabled.
**When enabled**, see the data-exposure note above: the full (minus the
encryption key itself) contents of the deployment's `erato.toml`/
`*.auto.erato.toml` files, including any secrets they contain, are
mirrored into the database, encrypted with the server's own encryption
key.

## Release note disposition

Proposed category: Features and enhancements (backend/operator-facing
infrastructure, opt-in). Given the security-relevant nature, worth an
explicit, clearly-worded release-note entry rather than a passing
mention: a new opt-in `runtime_configuration.enabled` setting can mirror

encryption key rather than omitted.
