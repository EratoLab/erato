# PR #840: Keep chat composer usable while a response streams (ERMAIN-466/470)

- Theme: None

## Summary

Follow-up to #837 (which kept the composer's text/file/facet surfaces
editable during generation but still blocked Send). This PR (ERMAIN-470)
adds an actual depth-1 message queue: pressing Enter/Send while a
response is still streaming now **queues** the draft instead of doing
nothing, and it auto-sends once the current turn finishes — unless a
tool-consent confirmation card (the add-in's `ActionConfirmationCard`) is
still pending, in which case the queued message waits. The auto-generated
PR description is a mechanical bullet list; the actual mechanism (read
directly from `ChatInput.tsx` and the two new stores) is considerably more
carefully designed than the description conveys:

- New `useMessageQueueStore` (Zustand, 67 lines, read in full): a single
  queued `ComposeDraftState` per `composeSessionId` (the same stable
  session id used for draft persistence, so the queue survives a
  new-chat's `null`→real-id rename and stays isolated per chat).
- New `useConfirmationRegistryStore` (90 lines, read in full): a
  per-`chatId` set of currently-pending confirmation-card registration
  ids. Cards register while pending and deregister on resolve or
  unmount — explicitly designed to be "best-effort": an unmounted card
  (e.g. scrolled out of a virtualized list) deregisters rather than
  permanently wedging the queue.
- `enqueueCurrentMessage` in `ChatInput.tsx`: Enter while
  `isPendingResponse` (specifically, not the broader send-lock — deliberately
  excluding the initial-history-load state, which produces no completion
  edge to drain on) queues the trimmed message + attached files and clears
  the composer. If a message is *already* queued, the user gets a
  confirmation dialog (`queueReplacePending`/`ConfirmationDialog`) before
  the new draft overwrites it, rather than silently discarding the earlier
  one — confirmed a proper data-loss-safety gate, not a silent clobber.
- The drain (a `useEffect` gated on a new `isDrainArmed` flag, set on the
  turn's completion edge) holds — re-checking on each dependency change —
  while: a new turn has already started, `chatId` is still `null` (a
  brand-new chat's confirmation registry is keyed by the real id, which
  arrives after the queue itself can exist, so draining too early could
  race past a card about to register), a confirmation card is pending for
  that chat, or the composer surface reports `disabled` (e.g. the add-in
  mid-email-drop). A failed turn (`messagingError`) returns the queued
  draft to the composer instead of sending it. The actual send is
  deferred one extra tick (`setTimeout(..., 0)`) specifically so a
  just-completed turn's confirmation card — registered in a post-commit
  effect — gets a chance to register and hold the drain before the code
  commits to sending. Model/facet selection is read live at send time
  (not snapshotted when queued), so a selection change made while a
  message waits in queue applies to the eventual send.
- Leaving a chat (switching `composeSessionId`) with a message still
  queued drops it back into that chat's saved draft (merged with whatever
  the user has typed since, via a new `mergeComposeDrafts` helper that
  concatenates non-empty texts and de-dupes files) rather than sending it
  in the background or losing it — it reappears in the composer when the
  user returns to that chat.
- Incidental cleanup: a duplicated `mergeUniqueFilesById` helper is
  consolidated into `@/utils/file/mergeUniqueFilesById` and reused from
  both the compose-draft-merge logic and `useFileUploadStore.ts`. New
  confirmation-registry hooks are exported from the library index for
  add-in consumption. New locale strings (de/es/fr/pl, per the PR
  description; English source strings confirmed via `en/messages.po`'s
  diff) cover the queued-message chip and its cancel action.

## Compatibility and configuration

None. Pure frontend UX feature; no configuration or API changes. Behavior
change: sending a message while a response is still generating now queues
it for auto-send after the current turn finishes (holding if a tool
confirmation is pending), instead of the Send action being blocked
outright (per #837) or silently doing nothing.
