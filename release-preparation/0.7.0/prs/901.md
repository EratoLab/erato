# PR #901: Add optional backend service load balancer to Helm chart

- PR: https://github.com/EratoLab/erato/pull/901
- Status: pending
- Category: Features and enhancements
- Theme: Multi-replica / cross-replica generation state

## Summary

Adds an optional "intermediate sticky load balancer" layer to the Helm
chart for multi-replica backend deployments: a namespaced Traefik instance
(new `backend-load-balancer-deployment.yaml`, `-service.yaml`, `-route.yaml`,
`-rbac.yaml` templates) placed between oauth2-proxy and the backend pods,
using Traefik's `hrw` (highest random weight) load-balancing strategy to
give client-IP affinity — i.e. consistently route a given client's
requests to the same backend pod, reducing (but per the chart's own
README, not eliminating the need for, given #898's cross-replica sharing)
cross-replica generation-state churn. When enabled, oauth2-proxy is
automatically re-pointed at the new load-balancer Service instead of
directly at the backend Service, and is configured to preserve the
ingress-provided `X-Forwarded-For` header so Traefik's HRW strategy sees
the real client IP. Requires the Traefik `IngressRoute` CRD to already be
installed in the cluster (uses Traefik's Kubernetes CRD provider), and a
new `NetworkPolicy` template covers the added component.

On the backend side, a new `backend/erato/src/deployment_identity.rs`
reads `ERATO_POD_NAME`/`ERATO_NODE_NAME` environment variables (falling
back to `"unknown-pod"`/`"unknown-node"`) and exposes a `Server` HTTP
response header of the form `erato/<version> pod=<pod> node=<node>`, plus
(per the chart's own docs) `pod_name`/`node_name` labels on the
`erato_info` Prometheus metric — making it possible to verify routing and
diagnose per-pod caching/generation behavior in a multi-replica
deployment.

## Compatibility and configuration

New `backend.loadBalancer.*` Helm values, disabled by default
(`enabled: false`) — no behavior change for existing deployments. Notable
default worth flagging: `backend.loadBalancer.forwardedHeaders.insecure`
defaults to `true` ("Trust forwarded headers from every source"), which
per the chart's own README "is suitable only when the load-balancer
Service is reachable exclusively by trusted in-cluster clients" — for
production use with this feature enabled, the docs explicitly recommend
setting `insecure: false` and providing `trustedIPs` CIDRs, since trusting
forwarded IP headers from untrusted sources can enable IP-spoofing-based
routing/rate-limit bypass. This is a security-relevant configuration
default that should be called out. No migration; purely additive Helm
chart resources.
