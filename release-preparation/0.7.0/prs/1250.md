# PR #1250: Replay earlier-turn client tool calls as receipts; count tool parts in token estimate (ERMAIN-868)

- PR: https://github.com/EratoLab/erato/pull/1250
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Two independent parts bundled together. Part A lets a client tool opt
into having its calls from *earlier* user turns (not the current one)
replayed to the model as small, field-bounded receipts rather than full
arguments/results — intended for a tool like Word's document-read
capture, whose full payload is large and stale by the next turn. Part B
fixes the token-usage preflight estimate to actually count replayed
tool-call/tool-response content, which it previously ignored entirely.
Confirmed the core config validation and the token-counting fix
precisely:

- **All four disclosed config-validation panic cases, confirmed exactly**:
  (1) non-empty `keep_input_fields`/`keep_output_fields` with `mode !=
  "receipt"` panics ("lists replay receipt fields but replay.mode is not
  'receipt'"); (2) `parse_receipt_field_path` requires a `$.`-prefixed
  path whose segments are plain `[A-Za-z0-9_-]` keys — no array-index or
  wildcard syntax is even parseable, so any attempt at one is rejected
  as "has an invalid key"; (3) `MAX_CLIENT_TOOL_RECEIPT_FIELDS: usize =
  32` is checked against both field lists, panicking above it; (4) a
  `replay_by_name: HashMap` keyed by the tool's *model-facing* name (not
  its qualified namespace+name) panics if two same-named tools disagree
  on `replay`, with the comment "the stored call carries only the
  model-facing name, so tools that share it across namespaces must agree
  on how it replays" — directly matching the PR's stated reason for this
  specific rule.
- **`ClientToolReplayConfig`/`ClientToolReplayMode` derive `Serialize`,
  confirmed exactly — the disclosed compile-fix needed for the #1249
  merge**: both types carry `Serialize` in their derive list, matching
  "the merged tree compiles with #1249's serialized `ClientToolConfig`"
  and the dedicated `replay_config_round_trips_through_json` test
  (confirmed present) asserting exactly this round-trip property, plus
  that an empty JSON object deserializes to the all-default config.
- **Token estimate now counts `ToolCall` name+arguments and
  `ToolResponse` content, definitions excluded, confirmed exactly, word
  for word matching the stated reasoning**: `chat_request_token_chunks`
  (extracted from `count_tokens_for_chat_request`) now matches
  `ContentPart::ToolCall(call) => format!("{} {}", call.fn_name,
  call.fn_arguments)` and `ContentPart::ToolResponse(response) =>
  response.content.clone()` alongside the pre-existing `Text` handling,
  with a doc comment stating "Tool definitions (`chat_request.tools`)
  are not counted: `history_tokens` is derived from this total, and
  definitions are not history" — matching Part B's description
  essentially verbatim.
- Per the PR (not independently re-verified given remaining scope): the
  receipt-extraction mechanics themselves in the new 391-line
  `replay_policy.rs` (the `kept`/`omitted_from_replay` shape, the
  512-byte-per-field size-marker fallback, the origin-gating against
  `generation_parameters.client_tools` so an un-recorded or MCP-shadowed
  call always replays in full, and the "a call that never produced a
  result keeps replaying without one instead of receiving a receipt"
  behavior); the claim that `replay_assistant_content` itself is
  unchanged and that `message_streaming.rs` is not touched by this PR
  (consistent with the changed-files list containing no
  `message_streaming.rs` entry); the disclosed decisions on the three
  "open questions" (nested-table key shape, unresolved-preceding-turn
  non-exemption, action-facet directive placement left unaddressed); the
  disclosed review-fix history (origin-scoped compaction preventing
  same-named-MCP-tool compaction, removal of key-presence-based receipt
  detection, no-receipt-without-a-result, and the corrected estimator
  comment); the extensive disclosed test suite (`prompt_composition/tests.rs`'s
  `prior_turn_receipts` module covering eight distinct scenarios, the
  token_usage unit test, and the `token_usage_tool_parts` integration
  test asserting a ~200 KiB replayed tool response raises
  `history_tokens` by more than 30k tokens where it previously stayed at
  11); the disclosed joint-regression note for whichever of this PR or
  #1249 (the durable-operations foundation reviewed above) lands second,
  regarding the required invariant that a durably-parked turn's
  continuation must rebuild through `replay_assistant_content` (full)
  rather than through prompt composition (which would compact it); and
  the disclosed "Depends on #1249 to take effect" framing — this PR is
  inert on `main` today since nothing yet records
  `generation_parameters.client_tools`, a claim consistent with this
  session's own review of #1249 as the PR that adds that record.

## Compatibility and configuration

Additive, opt-in, and byte-identical by default: `[client_tools.tools.<id>.replay]`
defaults to `mode = "full"` (today's behavior, confirmed via
`ClientToolReplayConfig`'s `Default` derive and `ClientToolReplayMode`'s
`#[default] Full` variant), so no existing deployment's behavior changes
until a tool explicitly opts into `mode = "receipt"`. No migration (per
the PR's own disclosed note, consistent with no sqitch files in the
changed-files list). Confirmed functionally inert until PR #1249 lands
(or another change records `generation_parameters.client_tools`), since
the origin-gating this review did not independently trace is described
as depending on that record's presence.

## Release note disposition

Proposed category: Features and enhancements. Part B (honest token
preflight counting replayed tool traffic) is a real bug fix worth noting
on its own: a chat with large replayed tool-call/response content
previously under-reported its token usage estimate dramatically (the
disclosed ~200 KiB-response test case going from under-counting by
30,000+ tokens to being accurate). Part A (per-tool receipt replay) has
no effect in this release on its own, since it depends on PR #1249
(itself not enabled in this release) to activate.
