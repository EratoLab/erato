# PR #923: Default appointment card and sidecar client identity

- PR: https://github.com/EratoLab/erato/pull/923
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Two independent library-side follow-ups from an architecture review,
stacked on #922. Confirmed by reading the code:

**ERMAIN-544**: previously, an `erato-appointment` fenced JSON block
(emitted by the scheduling facet's confirm step, from #804/#818) only
rendered as a card when a host had registered a renderer for it via
`componentRegistry.EratoAppointmentCodeBlock` — meaning on the **web app**
and in **shared chat links**, which have no such registration, it fell
back to rendering as a raw JSON code block, exposing the model's internal
data payload directly to the user. Confirmed via the `MessageContent.tsx`
diff: `isEratoAppointmentLanguage` no longer checks whether a registry
override exists — the fence now **always** renders as a card, via a new
default `EratoAppointmentBlock` component (173 lines, not read in full,
but its stated behavior — a read-only subject/when/where/attendees
summary, with validation mirroring the add-in's own parser, and a muted
raw-payload fallback while the JSON is still streaming or malformed — is
consistent with a sensible default). The Outlook add-in's own richer
renderer still takes priority when registered, via
`resolveComponentOverride`.

**ERMAIN-545**: `DesktopSidecarProvider` previously identified itself to
the local sidecar via a "legacy platform sniff" baked into the provider
itself — meaning any future non-Outlook Office host built on the new
core/host split from #922 (e.g. a future Teams composition) would
automatically report itself to the sidecar as "the Office add-in" too,
since the identity wasn't actually tied to which host was running.
Confirmed via the diff: `SharedAddinShell` now accepts an optional
`sidecarClientInfo` prop, and `OutlookApp.tsx` explicitly constructs and
passes its own identity (`createBrowserClientInfo({ name:
"erato-office-addin", ... })`) — confirmed, per the code's own comment, to
be **wire-identical** to what the old legacy sniff produced, so this is a
non-breaking, purely structural fix: it closes the door on a future host
silently masquerading as Outlook to the sidecar (which could otherwise be
used to gain trust/capabilities the new host hasn't actually earned),
without changing the sidecar's current behavior for the existing Outlook
composition at all.

## Compatibility and configuration

None. Both changes are non-breaking. The appointment-card change is a
real user-visible fix: an `erato-appointment` fence sent to a web-app user
or a shared-chat viewer (who has no add-in renderer available) now shows
a readable summary card instead of raw JSON. The sidecar-identity change
has no observable effect on the current Outlook add-in (wire-identical
per the PR); it only forecloses a latent identity-spoofing gap for a
not-yet-built future host.
