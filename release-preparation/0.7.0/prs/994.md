# PR #994: Pin continuestream tool scope, share the generation task lifecycle (ERMAIN-628)

- PR: https://github.com/EratoLab/erato/pull/994
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Last of three ERMAIN-617 delegation-hardening follow-ups (after #992,
#993). Two unrelated pieces of work: closing a real test-coverage gap
around the tool-approval continuation flow (and correcting a wrong
assumption in its own originating ticket along the way), and a
generation-task-lifecycle refactor shared between the ordinary submit
path and the delegated-child-run path.

- **Genuine, disclosed self-correction of the ticket's own premise**:
  the ticket assumed a hallucinated `delegate_to_assistant` call on a
  `continuestream` continuation would be refused with a specific message,
  "Delegation is not available for this request." Confirmed by reading
  `run_continue_message_task`'s diff: `allowed_tool_names` there is
  derived purely from MCP tool discovery (`chat_request.tools`), with no
  delegation-dispatch context threaded in at all — and a new code comment
  explains precisely why: the arguments a delegate call would need are
  request-scoped and were never persisted alongside the parked message,
  so there's nothing to dispatch against even if the call were allowed
  through. Since the delegation tool was never in `allowed_tool_names` to
  begin with, the model's hallucinated call is instead caught by the
  pre-existing unoffered-tool guard from #828 (which runs before any
  dispatch branch in the tool-call loop) and refused with the generic
  "Proposed tool call 'delegate_to_assistant' is not allowed for this
  request" — still fail-closed, just via an earlier, more general
  mechanism than the ticket assumed. New tests
  (`test_continuestream_resumes_a_parked_tool_approval`,
  `test_continued_turn_does_not_reoffer_the_delegation_tool`) pin the
  *actual* observed message and behavior rather than the ticket's
  assumption — and, per the PR, this closes a real prior gap where no
  backend test exercised `continuestream` end-to-end at all (existing
  `awaiting_approval` fixtures were faked via raw SQL rather than a real
  MCP approval park).
- **Shared generation-task lifecycle** (`with_generation_task_lifecycle`,
  not independently re-read in full): consolidates the previously-
  duplicated guard→run→error-broadcast→`StreamEnd`→outcome→`remove_task`
  sequence between `message_submit_sse` and `run_delegated_child` (#981),
  netting −70 lines. Per the PR, the two hadn't actually diverged despite
  #992's lifecycle changes, since `start_task` is called outside this
  wrapper on both sides — so unifying was purely cosmetic cleanup with one
  flagged **behavior change**: a failed delegated child now flows through
  `capture_report` (reaching Sentry/error tracking), where previously it
  was only a `tracing::warn!` that reached no error-tracking system at
  all. `regenerate_message_sse`/`edit_message_sse`/`continue_message_sse`
  are deliberately excluded from this consolidation, since they form a
  genuinely different self-consistent family (mpsc-based streaming,
  `forward_error_report` instead of a broadcast `Error` frame, no
  `StreamEnd` sent) that folding in would have changed on the wire.
- Several smaller, disclosed correctness fixes: `SeedStats` now carries
  `lineage_tip_id` directly from #979's `seed_chat_lineage` rather than
  re-deriving it via a `created_at DESC` query that the PR admits could
  theoretically mis-pick on a timestamp tie (acknowledged as not
  practically reachable today, since each message write is its own
  transaction with a distinct Postgres `now()`, but removed as an
  unpinned invariant for future safety); `build_result_envelope`'s
  previous `.ok().flatten()` swallowed a DB read failure indistinguishably
  from "the delegate never answered," misreporting a genuinely-successful
  delegate run as failed — now logged with context instead; the same
  silent-degradation pattern found and fixed eight lines away in
  `prepare_delegated_chat` (previously silently downgrading
  `include_conversation_context` to "no context" on a DB error); and
  `render_action_facet_template` renamed to `render_placeholder_template`
  since it was always generic `{{key}}` substitution, not action-facet-
  specific, and now genuinely has two distinct callers.
- New coverage specifically targets the wrapper's previously-untested
  failure branch, per the PR: unit tests pinning the exact frame sequence
  on both the `Err` (`[Error, StreamEnd]`) and `Ok` (`[StreamEnd]`) paths,
  plus an integration test that triggers a real early wrapper failure
  (before any assistant message row exists) specifically because that's
  the blind spot every existing `find_map(message_type == "error")`-style
  assertion elsewhere in the suite would miss. The PR states these are
  mutation-checked in both directions (removing either the `Error` or
  `StreamEnd` send breaks specific tests).
- Explicitly flagged as a known, pre-existing, out-of-scope issue rather
  than fixed here: `continue_message_sse` calls `start_task` but never
  broadcasts `StreamEnd`, so a `resumestream` tailing a continuation never
  sees a terminating frame.

## Compatibility and configuration

None. Pure backend bug fixes and internal refactor; no configuration or
API changes. Behavior change: a delegated child run that fails now
reaches Sentry/error-capture (previously only a warning log), and a
hallucinated delegation-tool call on a continuation is now correctly
tested against its actual (always-was-fail-closed) rejection behavior.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both

its new code comment, confirming the delegation-not-threaded-through-

`services/delegation.rs` (123-line diff), or the ~630 lines of new test
coverage across `integration_tests/api/delegation.rs` and
`integration_tests/api/messages.rs`.
