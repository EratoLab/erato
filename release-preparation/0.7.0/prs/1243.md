# PR #1243: Open source emails from previews and upload consent

- PR: https://github.com/EratoLab/erato/pull/1243
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Completes the Outlook-provenance chain started in #1239 (protocol
contract) and #1241 (persistence): adds an "Open in Outlook" action to
upload-consent previews and the shared file preview, consuming the
provenance data those two PRs defined and stored. Given the overall
feature's three-PR arc already reviewed, this review focused on the two
most security-relevant mechanisms — the Outlook add-in's native opener
(which must never fabricate an EWS id from a local store id) and the
standalone/Windows native-launch URI builder (which must never let the
sidecar's own discovery payload dictate what gets executed):

- **Local store IDs are never converted to EWS; only a genuine EWS id
  opens the Office.js path, confirmed exactly, by construction**: the
  new `createOutlookSourceNavigator`'s `canOpen`/`open` both exclusively
  call `uniqueOutlookId(reference, "ews_id")` — there is no code path
  anywhere in this function that reads `outlook_entry_id`/
  `outlook_store_id` or derives an EWS value from them. If no genuine,
  unambiguous `ews_id` external-id entry exists, `open` rejects with "No
  unambiguous EWS message ID." This directly confirms "Local store IDs
  are never converted to EWS" — not merely as a stated policy, but as a
  structural property of the function (the conversion path simply does
  not exist).
- **Async-then-sync Office.js capability fallback, confirmed exactly**:
  `useAsync` requires `Mailbox 1.9` support and
  `mailbox.displayMessageFormAsync` to exist; `useSync` requires
  `Mailbox 1.1` and `mailbox.displayMessageForm`; the async path is
  preferred when available, with a 15-second timeout guarding against a
  host callback that never arrives ("A host callback is not guaranteed
  to arrive after the task pane changes") — matching "using the async
  API where supported and the Mailbox 1.1 API on older hosts" exactly.
- **`uniqueOutlookId` requires a single, unambiguous, injection-safe
  value, confirmed exactly**: it collects distinct values for a given
  `external_ids` key via a `Set`, and returns a value only if there is
  *exactly one* distinct value, it's non-empty after trimming, at most
  8192 characters, and contains no `\r`/`\n`/NUL — rejecting ambiguous
  (multiple conflicting values for the same key) or malformed references
  outright rather than guessing which one to use.
- **The native-launch URI is built only from a hardcoded prefix, never
  from the discovery payload, confirmed exactly — a concrete, directly
  verifiable security boundary not spelled out as its own PR bullet but
  critical to the feature's safety**: `outlookSidecarUri`'s code comment
  states directly "Build only the registered, known URI; discovery must
  never supply a URL to execute." Concretely: `LAUNCH_PREFIX =
  "erato-launch://outlook/open?reference="` is a hardcoded module
  constant; the discovery extension's `descriptor.launchUriPrefix` is
  only ever *compared* against this constant (rejecting the whole
  attempt if they don't match) and is never itself used to construct the
  returned URI — so a compromised or malicious sidecar advertising a
  different `launchUriPrefix` in its discovery payload cannot redirect
  the browser to execute an arbitrary URI scheme; it can only cause the
  feature to decline to offer the link at all.
- **Multiple layers of reference validation before building the URI,
  confirmed exactly**: every `external_ids` entry is checked for
  injection characters; `outlook_entry_id`/`outlook_store_id` values are
  separately required to match the hex-pair pattern
  (`^(?:[a-fA-F0-9]{2})+$`) — the identical validation rule this
  session confirmed in the protocol schema itself in PR #1239's review;
  the reference must resolve to *both* a message (`outlook_entry_id` or
  `email_message_id`) and a mailbox (`outlook_store_id`, or a mailbox id/
  email matching known UUID or 32-hex-char formats) before a URI is
  built at all; and the final serialized reference is capped at the
  smaller of a hardcoded `16_384`-byte ceiling and the sidecar's own
  advertised `maxReferenceBytes` — multiple independent, defense-in-depth
  checks rather than a single gate.
- **Gated to Windows and a ready, validated sidecar snapshot, confirmed
  exactly**: `outlookSidecarUri` returns `null` immediately unless
  `clientOs === "windows" && snapshot.state === "ready"` — matching
  "offer the registered sidecar link on Windows when validated discovery
  advertises Classic Outlook navigation."
- **Deduplicated, parent-preferring reference extraction, confirmed
  exactly**: `outlookSourceReferences` prefers `origin.topLevelParent ??
  origin.document` for each origin (matching "Prefer the containing
  mailbox message for attachments, including nested mail"), and dedups
  by a composite key over the document id, mailbox identity, and sorted
  external-id pairs — matching "Multiple saved origins can be selected
  explicitly" (distinct origins survive; duplicates collapse) and
  "Identical attachment bytes from different parents remain distinct"
  (consistent with #1235's confirmed EWS-aware dedup and #1241's
  confirmed origins-array persistence).
- Per the PR (not independently re-verified given remaining scope): the
  claim that "The link is activated only by a user click" (the rendering
  component `OutlookSourceAction.tsx`, 102 lines, not read — this review
  confirmed the URI is only ever *built* safely, not that its
  activation is click-gated in the UI); the full
  `ClientToolFileApproval.tsx`/`ActionConfirmationCard.tsx` consent-flow
  integration (57 and 16 lines changed); the preservation claims around
  conversation-message identity, attachment-parent relationships, and
  document-export provenance during upload (in `chatTools.ts`'s 150-line
  diff, not traced in full); the Outlook add-in's `OutlookEmailSourceProvider.tsx`
  wiring (65 lines changed); the explicit dependency on two unmerged
  native-sidecar PRs (#69, #74) for the Windows desktop path to actually
  work; the disclosed manual verification in a Windows Parallels VM
  (hash-matched sidecar executable, validated live discovery digest,
  confirmed reconnection after a sidecar restart); the four items of
  "Remaining manual coverage" explicitly flagged as not yet done; and the
  disclosed automated validation (2,718 frontend tests with 11 skips,
  plus the base feature's earlier-validated 2,052 add-in tests and 97
  protocol tests).

## Compatibility and configuration

None breaking. Purely additive frontend/add-in feature consuming the
already-shipped, additive `outlook_provenance` API (#1241) and protocol
contract (#1239) — "no backend migration or RPC schema change." Inert
for any file uploaded before provenance existed, or any file with an
unverified mailbox reference, per the PR's own disclosed limitation
("Older uploads without provenance and independently dropped files
without a verified mailbox reference cannot be linked retroactively").

## Release note disposition

Proposed category: Features and enhancements. Worth a mention: a
retrieved Outlook email or attachment — whether shown during upload
consent or in the regular file preview, including one reopened from a
citation or after a chat reload — now offers an "Open in Outlook" action
that opens the original message directly in the Outlook add-in (via
Office.js) or, on Windows with a compatible desktop sidecar, in Classic
Outlook via a validated native link. Older uploads made before this
provenance tracking existed cannot be linked retroactively.
