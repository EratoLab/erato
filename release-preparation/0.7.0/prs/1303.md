# PR #1303: Guide first-time Teams bot setup and harden its public endpoint

- PR: https://github.com/EratoLab/erato/pull/1303
- Status: pending
- Category: Features and enhancements
- Theme: Teams bot guided setup

## Summary

Collapses Teams bot setup from several deploy round-trips down to one
deploy + one Cloud Shell command + one package upload, and hardens the
messaging endpoint that this now-easier setup makes more likely to be
exposed to the internet. Per the PR's own detailed description (41 files,
~4,540 insertions), confirmed against the code for the security-critical
parts:

- **Configuration defaults reduce required input**: when
  `[integrations.ms_office.teams.bot]` is enabled, `app_id`/`sso_app_id`
  default to the add-in's `msal_client_id`, `tenant_id` to a
  tenant-specific `msal_authority`, and `oauth_connection_name` to
  `graph-sso` — explicit values still win. A new `messaging_endpoint` key
  names a public hostname/URL in front of an internal-only deployment. The
  manifest derives `sso_resource` as `api://<host>/botid-<app_id>` per
  download host.
- **New public, secret-free setup-status endpoint**
  (`/office-addin/teams/bot-setup.json`) reports whether a Teams message
  reached the backend and whether Entra currently accepts the bot's
  credential.
- **Credential check is on-demand, single-flight, and rate-limited,
  confirmed exactly in `connector.rs`**: `check_credential()` gates on a
  `next_credential_check` mutex set to `Instant::now() + 60s`
  (`CREDENTIAL_CHECK_INTERVAL`), so at most one token request per instance
  per minute; a failed token response is classified via Entra's numeric
  `error_codes` (`AADSTS7000229`/`700016` → "app not in tenant" vs. any
  other 4xx → "rejected secret") into a `CredentialState` stored in an
  `AtomicU8`, readable without re-requesting a token. This works before
  any Azure Bot exists, since the token request only needs the app
  registration.
- **Attachment-download hardening, confirmed exactly**: a dedicated
  `downloads` HTTP client (`download_client`) is built `https_only(true)`
  with a custom redirect policy that re-validates **every** redirect hop
  against an explicit host allowlist (`smba.trafficmanager.net`,
  `.botframework.com`, `.skype.com`, `.teams.microsoft.com`,
  `.sharepoint.com`) via a `host_in` helper doing exact-or-subdomain
  matching (`.example.com` matches subdomains, a bare `example.com`
  matches only itself) — directly confirming the PR's claim that
  `attackersmba.trafficmanager.net` no longer receives the bot token,
  since suffix matching is anchored to the dot-prefixed pattern, not a
  naive `ends_with` on the bare domain. The bot's bearer token is attached
  only when the *request* host (pre-redirect) matches the narrower
  `BOT_TOKEN_DOWNLOAD_HOSTS` set (no SharePoint), with a comment noting
  reqwest drops the header once a redirect leaves that host.
- **Cloud Shell helper 1.1.0** (new pinned release, checksum-pinned same
  as prior versions): creates/adopts the single-tenant Azure Bot,
  registers `Microsoft.BotService` if needed, corrects endpoint/Teams
  channel on an existing bot (scoped to the same tenant/type/app), grants
  `oauth2PermissionGrants` consent (denied grant keeps other changes and
  links the admin-consent page; `-SkipConsent` defers consent), reads the
  tenant's app-management policies (secret lifetime caps, blocked
  secrets, Application ID URI restriction) before attempting changes, and
  names the failing step on error.
- **Welcome card** shown when the bot is installed into someone's
  personal chat, pointing an unrecognized user to the tab.
- **`sso_enabled`** (default `true`) lets an existing bot keep running
  without SSO and its existing Teams package, unchanged, if set `false`.
- **Helm**: `msTeamsBot.appPassword.existingSecret` reuses an existing
  secret (e.g. oauth2-proxy's) as the bot's `app_password`; new
  `msTeamsBot.publicIngress` template routes only the messaging path on a
  separate public hostname, with the network policy admitting
  `ingressFrom` for either route.
- Per the PR (not independently re-verified beyond the pieces above): the
  full `AddinSetupPage.tsx` UI diff (486 lines) and its accessibility
  fixes, the `nbf` enforcement and 256 KB body-limit claims in
  `inbound_auth.rs` (393-line diff, not read in full), the `ms_teams.mdx`
  documentation restructure, and the full set of new Helm chart template
  tests.

## Compatibility and configuration

Additive and backward compatible for existing bots: new keys
(`messaging_endpoint`, `sso_enabled`) and new defaults only ever reduce
required explicit configuration; an existing bot's prior explicit values
still win and its Teams package is unchanged if `sso_enabled = false`.
The "configured together" validation rule the PR mentions removing
applies only to the newly-optional id/tenant/connection-name fields
gaining defaults — not independently re-verified against
`erato_config/src/config.rs`'s full 327-line diff. No database migration.
Operationally significant: the messaging endpoint must now be reachable
from the internet for the bot to work at all (Bot Connector has no IP
allowlisting), which is exactly why this PR pairs the easier setup with
endpoint hardening.
