# PR #917: Implement distribution customization for desktop-sidecar

- PR: https://github.com/EratoLab/erato/pull/917
- Status: pending
- Category: Features and enhancements
- Theme: Desktop Sidecar for local sources

## Summary

Implements "organization bootstrap personalization" for Windows
desktop-sidecar downloads: the backend now embeds a small, immutable JSON
policy document — currently just `allowed_origins`, the browser origins the
locally-running sidecar will accept requests from — directly into the
downloaded Windows executable/MSI before serving it, rather than relying
solely on a user-writable local config file. Per the updated
`desktop-sidecar-protocol/DISTRIBUTION.md` (new §6/6.1/6.2, extensively
detailed): a versioned JSON document
(`{"version": 1, "organization_configuration": {"allowed_origins": [...]}}`)
is written into a fixed 4096-byte `.erato` PE section of the standalone
`.exe` (with a magic header, format version, and length-prefixed payload,
validated by the sidecar before it opens its listener), and into a
separate `bootstrap.json` file inside the MSI's own CAB stream (not
recompressing/patching the executable cabinet). This bootstrap policy
**takes precedence over any user-writable configuration**, including the
`sidecar.configure.v1` protocol method added in #871 — per the spec,
neither that runtime configuration channel nor a user's local config
directory can add or replace production allowed origins. A template slot
with zero length is treated as an unpersonalized, fail-closed artifact
(empty allowlist, i.e. refuses everything).

New backend config key `desktop_sidecar.allowed_origins` (default `[]`,
must be normalized lowercase `scheme://host[:port]` origins with no
path/query/fragment) is the source of this policy; it feeds the personalization
logic in `backend/erato/src/services/desktop_sidecar_distribution.rs`
(498-line diff) and new endpoint logic in
`backend/erato/src/server/api/v1beta/desktop_sidecar.rs` (141-line diff)
that presumably personalizes each downloaded artifact per-request or
per-build.

## Compatibility and configuration

New key, defaulting to an empty list:
```toml
[desktop_sidecar]
allowed_origins = []  # empty by default — refuses all production browser origins
```
No migration. This is security-relevant: an empty `allowed_origins` list
is explicitly documented as fail-closed (refusing every production browser
request), so deployments that want the sidecar to actually accept
connections from their Erato web origin must set this explicitly — a
correctness-critical step for anyone adopting the desktop sidecar
distribution feature (#872) in production. Development origins are called
out as "an explicit local development-mode option," separate from this
production policy.
