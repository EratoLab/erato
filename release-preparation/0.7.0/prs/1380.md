## Summary

Per the PR's detailed body (native-gate tested; treated as reliable
consistent with this cycle's other Word add-in entries, not
independently re-verified line-by-line): switches Word for Windows and
Mac to write document-edit plans in place by default (previously only
Word for the web did), confirmed exactly via `config.rs`'s one-line
default change: `DESKTOP_DEFAULTS.in_place` goes from `false` to `true`
(whole-document import remains the fallback for what in-place can't
write — sections, other stories, moves — and stays the per-host kill
switch). Two correctness fixes needed for this to be safe, per the PR:

- **Heading-restyle bug, confirmed via the PR's description of the
  mechanism**: Word identifies a built-in style by name, not by ID. A
  document with a custom style literally named "Heading2" previously
  confused the in-place writer (Word silently renames the custom style to
  "Heading20" and repoints headings when it later adds its own built-in
  "heading 2"). Built-in styles are now matched and set by name only
  (the part before the first comma), with or without `w:customStyle`, in
  both the live writer and its compiler.
- **Table-cell Revert fix**, found by the native gate per the PR: table
  cell paragraphs needed their own OOXML-comparison handling, now added.

## Compatibility and configuration

**Default behavior change on Word for Windows/Mac, not a breaking
removal**: documents edited via the Word add-in on desktop now have
changes written in place (touching only the modified paragraphs,
preserving co-authors' edits/comments/Word metadata elsewhere) rather
than via a whole-document import, by default. The existing per-host
`in_place` flag (confirmed present as a kill switch in prior code,
reused here) lets an operator revert to the old import-based behavior if
needed. No database migration.
