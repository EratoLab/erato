# PR #1131: Add an unarchive endpoint for chats (ERMAIN-794)

- PR: https://github.com/EratoLab/erato/pull/1131
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

First of four in a stack adding archived-chat support. Adds `POST
/chats/{chat_id}/unarchive`, plus four adjacent fixes the PR states the
new route would otherwise inherit or expose. Confirmed by reading the
complete `models/chat.rs` diff and the relevant `server/api/v1beta/mod.rs`
error-mapping changes in full — every claim below independently verified
against the code, not merely taken on trust:

- **`unarchive_chat`, confirmed exactly matching its description**: looks
  up the chat, authorizes, and returns the chat unchanged (`Ok(chat)`)
  when `archived_at` is already `None` (the stated 200 no-op); otherwise
  sets only `archived_at = None` and updates — no cascade to descendants,
  no other column touched.
- **Re-archiving no longer resets the retention clock, confirmed
  exactly**: `archive_chat` branches on `already_archived =
  chat.archived_at.is_some()`; when already archived and not pinned, it
  returns the chat completely unmodified (no DB write to `archived_at` at
  all); when an update *is* needed (not yet archived, or already archived
  but still pinned and needing the pin cleared), the `archived_at` field
  is only set (`ActiveValue::Set(Some(Utc::now()...))`) when `!already_archived`
  — so re-archiving an already-archived chat genuinely never overwrites
  its original timestamp, confirmed matching the stated fix precisely.
- **Pin-clearing wired through every archive path, confirmed exactly**:
  `archive_chat`'s update branch unconditionally sets `is_pinned =
  ActiveValue::Set(false)` (so calling archive again on an
  already-archived-but-still-pinned row does clear the stale pin, matching
  the PR's own stated note that "archiving one again now unpins it");
  `archive_delegated_descendants`'s cascade SQL adds `"is_pinned" =
  false` to its `UPDATE` SET clause; and
  `archive_all_unarchived_chats_for_owner`'s bulk update likewise sets
  `is_pinned: ActiveValue::Set(false)`.
- **The pin-write 409 guard, confirmed exactly**: `update_chat_is_pinned`
  gains `if is_pinned && chat.archived_at.is_some() { return
  Err(eyre!("... is archived and cannot be pinned")); }` — placed after
  authorization but before the actual column write, and confirmed
  unpinning (`is_pinned: false`) is never blocked by this check regardless
  of archived state, matching "Unpinning stays allowed" exactly.
- **Archived rows carry no generation marker, confirmed exactly**: both
  `active_generation_started_at` and `pending_tool_approval_at`'s `CASE`
  expressions in `get_recent_chats` gain a new leading condition,
  `"chats"."archived_at" IS NULL AND ...`, so neither marker can ever be
  non-null for an archived row regardless of its stale `generation_state`/
  `generation_heartbeat_at` values — directly closing the disclosed
  "phantom running/action-required indicator on an archived row" bug.
- **404 instead of 500 for a non-owner, confirmed exactly**: a new shared
  `chat_write_error_status(error)` function maps both a `"not found"` and
  a `"not authorized"` substring match to `StatusCode::NOT_FOUND`,
  applied identically at `unarchive_chat_endpoint` and
  `archive_chat_endpoint` (and, per the PR, `update_chat`, not
  independently re-checked at that third call site) — replacing the
  previous mapping that only recognized `"not found"` and let every other
  error (including the policy-denial text) fall through to the generic
  internal-error/Sentry path.
- Per the PR (not independently re-verified): the continue-stream 409 fix
  (moving the archived-chat check out of the already-spawned generation
  task and before the spawn, so continuing an archived chat parked on a
  tool approval surfaces as a clean HTTP status rather than an error
  inside an already-open SSE stream) in `message_streaming.rs`; and the
  `global_policy_engine.invalidate_data()` call on unarchive, matching
  the same call archive already makes (per the PR, so a share link on a
  restored chat stops 404-ing immediately — plausible given this
  session's earlier confirmed reading of #1128's related policy-engine
  invalidation work, though that PR replaced this exact global-invalidate
  mechanism with granular per-entity invalidation; whether this PR
  predates or coexists with that rework was not cross-checked).

## Compatibility and configuration

New additive endpoint (`POST /chats/{chat_id}/unarchive`), no migration.
Real, intentional behavior changes bundled in: re-archiving a chat no
longer resets its 30-day retention clock (a genuine bug fix); pinning an
already-archived chat now returns 409 instead of silently succeeding into
an invisible state; archiving a chat (single, bulk, or via cascade) now
also clears its pin. The final "clear the pin on archive" commit is
explicitly flagged by the PR as droppable — implementing a recommendation
nobody had signed off on as of the PR — isolated last so it can be
reverted independently if the team decides against it.
