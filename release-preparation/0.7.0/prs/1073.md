# PR #1073: Let a person override or clear their start screen, and land them there (ERMAIN-696)

- PR: https://github.com/EratoLab/erato/pull/1073
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Stack 3/3, completing the audience-resolved starting-assistant feature
(#1071, #1072). Lets a person override or clear an admin's audience pin
and actually navigates them to the resolved assistant. Given the large
scope (2969 lines), review focused on the correctness-critical backend
pieces: the tri-state storage design, the patch-conflict resolution, and
the precedence logic. Confirmed by reading the complete migration SQL,
the relevant `user_preference.rs` patch-resolution function, and the
complete `starting_assistant.rs` diff:

- **Tri-state storage, confirmed exactly via migration `0039`**:
  `starting_hub_assistant_id`/`starting_assistant_id` (both nullable,
  `ON DELETE SET NULL`) plus a separate `starting_assistant_cleared
  boolean NOT NULL DEFAULT false`, with two CHECK constraints — one
  forbidding `cleared` alongside either id, one forbidding both ids at
  once. A code comment on the migration notes precisely why a single
  nullable column couldn't work: the existing `normalize_optional_text`
  helper already collapses `""`/whitespace/explicit-null to `NULL` for
  other text preferences, which would have silently re-applied the
  admin's audience pin the moment a user "cleared" their override —
  exactly the one behavior this feature was built to prevent. A further
  comment notes the `ON DELETE SET NULL` cascade can only ever land on a
  `(NULL, false)` row (a stranded pick resets to "inherit", never to a
  contradictory "cleared-with-an-id" state), which is consistent with the
  CHECK constraints as written.
- **Patch-conflict resolution, confirmed exactly via
  `apply_starting_assistant_patch`**: this function (a plain Rust
  Option-in/Option-out transform, not going through
  `normalize_optional_text` at all, since the stored values are `Uuid`s
  and a boolean, not text) applies patches in the fixed order
  assistant-id → hub-id → cleared, with each non-`None` "set" patch
  clearing the other two fields — so a single request setting both a pick
  and `cleared: true` resolves to cleared (applied last), and a request
  setting both pick columns resolves to the hub pick (applied after the
  plain-assistant patch) — confirmed both outcomes match the code
  comment's explicit statement of this ordering exactly.
- **Resolution precedence, confirmed exactly via
  `starting_assistant.rs`**: the handler checks
  `me_user.preference_starting_assistant_cleared` first (returns no-pin
  immediately if true), then the plain-assistant pick
  (`preference_starting_assistant_id`) — confirmed placed *before* the
  `assistant_hub.enabled` config gate, matching the PR's stated rationale
  that a self-made assistant has nothing to do with the hub and disabling
  the hub must not silently re-steer such a user — then the
  hub-assistant-enabled gate, then the hub pick
  (`preference_starting_hub_assistant_id`), and only with no override at
  all does it fall through to the audience-pin resolution from #1072.
  This is confirmed to match `cleared > own pick > audience pin > welcome
  screen` precisely.
- **Plain-pick resolution correctly reuses the ordinary assistant access
  path, confirmed via `resolve_assistant_pick`**: it calls
  `assistant::get_assistant_by_id(&app_state.db, policy,
  &me_user.to_subject(), pick)` — the same function `GET /assistants/{id}`
  uses (owner or viewer/editor grant, archived excluded), with a doc
  comment stating this path also refuses hub-version clones, so a
  stranded clone id stored in `starting_assistant_id` can never
  accidentally resolve through this leg (hub assistants are required to
  go through `resolve_hub_pick` instead, which calls
  `assistant_hub::get_published_current_version`).
- **A stale/withdrawn own-pick degrades to the welcome screen, not to the
  audience pin, confirmed exactly**: both `resolve_hub_pick` and
  `resolve_assistant_pick` return `starting_assistant: None` directly on
  any resolution `Err`, rather than falling through to the audience-pin
  logic below in the function — matching the PR's stated design that a
  user who deliberately overrode their start screen should not be
  silently re-steered by policy once their own choice disappears.
- Per the PR (not independently re-verified given the remaining scope):
  the settings-dialog UI (`StartingAssistantSetting.tsx`, 274 lines) and
  its fix for a previously-broken "chosen but nothing selected" Save-button
  state; `HomePage.tsx`'s redirect-on-resolved-payload logic (38 lines);
  a 422-instead-of-500 fix for a well-formed UUID naming a nonexistent
  assistant; a codegen fix for nullable patch fields narrowing incorrectly
  in the generated TypeScript client; and the disclosed known defect where
  a hard-deleted stored pick combined with a stale cached profile in the
  settings dialog causes every preference save (including unrelated ones)
  to fail with a generic error until the user changes their start-screen
  choice — stated as narrow and real, applying to both pick columns, not
  independently reproduced.

## Compatibility and configuration

New migration `0039` (additive columns + CHECK constraints, no
backward-incompatible schema change — confirmed both new id columns
default `NULL` and the boolean defaults `false`, so an existing row reads
as "never set"/inherit). New optional fields on the existing user
preferences patch endpoint. No effect on a deployment with no audience
policy configured (per #1071/#1072) and no user having set an override —
confirmed the resolution falls through cleanly to the pre-existing
welcome-screen behavior in that case.

## Release note disposition

Proposed category: Features and enhancements, completing the 3-part
audience-resolved-starting-assistant stack (#1071/#1072/#1073, ERMAIN-693).
Worth a combined mention: admins can pin a starting assistant for an
Entra group or the whole organization, and each person can override that
pin with their own choice (a hub assistant or a private one) or clear it
back to the welcome screen — landing there automatically on login.
