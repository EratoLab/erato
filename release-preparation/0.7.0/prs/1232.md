## Summary

**By far the largest PR in this release** (45,113 insertions across 233
files) — an entirely new Word/document Office add-in surface, almost
entirely self-contained under `office-addin/src/word/` (roughly 220 of
the 233 changed files), with only a small, tractable set of backend
changes to `erato` itself (router, config, frontend-environment
injection) providing the scaffolding that lets a second, distinct add-in
identity exist alongside the established Outlook/mail add-in. Given the
scale — this single PR is roughly 2.5x the size of the next-largest PR
reviewed in this entire release (#1230, Delegation Level D, at ~18,400
insertions) — this review verified only the backend scaffolding that
connects this new add-in to the rest of the product, and explicitly
flags the bulk of this PR (the actual document-authoring implementation:
typed document plans, paragraph/table/media/structure editing, stale-read
recovery, diffing, native OOXML round-tripping) as not independently
traceable within the scope of this evaluation pass:

- **A genuinely separate document add-in identity, confirmed exactly**:
  new `MsOfficeAddinDocumentConfig` nests under `MsOfficeAddinConfig`
  with its own `addin_id` (a distinct hardcoded UUID,
  `15a5d0e8-e96a-4e26-b6a1-bd8f429468c2`, versus the mail add-in's
  pre-existing `ee94d041-bd77-446c-8854-421648f50e7c`) and its own
  `manifest.{display_name, description}` (defaulting to "Erato for
  Documents" / "Erato AI assistant for Word documents"). Validation
  explicitly rejects an empty id or one matching the mail add-in's id,
  with the comment "A catalog rejects two add-ins with the same identity"
  — directly substantiating "separate document-add-in branding
  configuration" and confirming this isn't merely cosmetic: a
  misconfiguration that collided the two identities would fail at
  startup rather than silently breaking one add-in's catalog
  registration.
- **A new, separate manifest route composes document branding over
  inherited mail-manifest structure, confirmed exactly**: a new
  `office_addin_document_manifest` handler serves `manifest-document.xml`
  via `OFFICE_ADDIN_DOCUMENT_MANIFEST_FILE_NAME`, and
  `render_office_addin_manifest` detects this case
  (`is_document_manifest`) to build a composed `MsOfficeAddinManifestConfig`
  that copies the document-specific `display_name`/`description` while
  spreading (`..addin_config.manifest.clone()`) every other field from
  the mail config, and substitutes the document-specific `addin_id` into
  the rendered template in place of the mail add-in's — matching "Word
  host routing... local/deployment manifests" and the code's own comment
  "Serde defaults do not inherit customer branding from the mail block;
  compose it explicitly," confirming this inheritance is handled
  deliberately rather than accidentally defaulting to empty/wrong values.
- Per the PR (not independently re-verified, given this PR's scale —
  this is effectively the entire substance of what the PR adds): the
  typed document-plan system for paragraphs, headings, lists, tables,
  captured media, drawings, native structures, document parts, and
  section layout (`wordDocumentPlan.ts`, 829 lines, and its ~15 related
  utility modules); client-side validation of source coverage, read
  proofs, document identity, and current state before writing
  (`wordDocumentIdentity.ts`, `wordWriteGate.ts`,
  `wordAuthoringContract.ts`, and others); request-owned document
  snapshots and stale-read recovery for follow-up edits
  (`useWordDocumentSource.ts`, `wordDocumentReadRequest.ts`); saved
  originals for document recovery and apply/revert outcomes
  (`WordWriteProvider.tsx`, `wordDocumentCapture.ts`); bounded review for
  many edits, exact text comparisons, and the structure/draft/source/
  parts views (`WordReviewPanel.tsx`, `WordDocumentPlanReview.tsx`,
  `wordFullDocumentComparison.ts` at 1,272 lines, `wordXmlComparison.ts`
  at 493 lines); the native OOXML read/write/round-trip machinery
  (`wordDocumentXml.ts` at 891 lines, `wordNativeContent.ts`,
  `wordContentControlWrite.ts`, `wordTableContent.ts`/`wordMediaContent.ts`
  each over 1,000 lines); the shared frontend component/theme additions
  (`Select.tsx`, `FormField.tsx`, `TextComparison.tsx`, theme tokens, Card
  footer slots) and the Outlook-side extraction of a host-neutral
  proposal validator (`proposedClientAction.ts`); the claim that
  deployment supplies model instructions/action policies with no
  subscription prompts embedded here; and the disclosed validation
  (2,044 add-in tests plus 112 affected frontend tests in prior branch
  review; 69 focused tests plus Chromium visual checks across two
  viewport widths/both palettes for final UI fixes; the explicit
  disclosure that native Word evidence is from Mac testing during
  development and the final UI changes have **not** had a new native Word
  run; and that publication bypassed commit/push hooks with `--no-verify`
  at the owner's request and does not rerun the full test/build suites).

## Compatibility and configuration

Additive. New, independently-identified document add-in alongside the
existing mail add-in, with its own catalog identity, manifest, and
branding configuration (confirmed above) — no change to the existing
mail add-in's identity or behavior. New config keys under
`integrations.ms_office.addin.document` (`addin_id`, `manifest.display_name`,
`manifest.description`), all with safe defaults, validated distinct from
the mail add-in's own `addin_id` at startup. The backend additions
reviewed (router, config, frontend-environment) are small and additive;
the overwhelming majority of this PR's surface area is new, isolated
frontend code under `office-addin/src/word/` that does not touch
existing Outlook/mail add-in code paths, per the changed-files list.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read: the relevant `MsOfficeAddinDocumentConfig`/
`MsOfficeAddinDocumentManifestConfig` additions in `config.rs` (confirming
the distinct identity, its validation, and its defaults) and the relevant
`render_office_addin_manifest`/`office_addin_document_manifest` additions
in `router.rs` (confirming the new manifest route and its branding-
composition logic). Given this PR's scale — 233 files, 45,113 insertions,
roughly 220 of those files being new Word-specific frontend code with
well over 100 new test files — this review did not, and could not
within a reasonable scope, trace the document-authoring implementation
itself: the plan/diff/apply/revert pipeline, the native OOXML
read/write logic, or the review UI. **This PR warrants dedicated,
focused human review attention beyond what this evaluation pass
provides**, given its size dwarfs every other PR in this release by a
wide margin and it introduces an entirely new product surface (Word
document editing) rather than extending an existing one.

## Release note disposition

Proposed category: Features and enhancements. This is a major new
capability: a Word add-in that can read the open document and propose
either targeted paragraph edits or a complete structured rewrite
(reorganizing structure and rich content, not just replacing text),
reviewed and applied with independent recovery if something goes wrong.
Given its scope and the PR's own disclosure that the final UI changes
have not had a fresh native-Word validation pass, this is a strong
candidate for the release's headline feature entry, but also one where
the release owner should confirm current native-Word behavior has been
re-verified before shipping, per the PR's own stated caveat.
