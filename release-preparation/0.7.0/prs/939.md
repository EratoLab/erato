# PR #939: feat(office-addin): add Teams chats as a context source in the chat composer

- Status: pending (diff reviewed)

## Summary

Very large feature (11384 insertions across 66 files, stacked on #932's
Teams-tab groundwork): adds a "Teams chats" picker to the add-in composer
letting a user browse Teams 1:1/group chats and channels, drill into a
conversation, search message content, select whole conversations or
individual messages, and attach the selection as a markdown transcript.
Given the extreme scale — far beyond what can be exhaustively verified in
this pass — review focused on the two most specific, safety-relevant
correctness claims the PR itself calls out, both confirmed by direct
code reading:

- **"Channel search hits probe at tick time instead of failing at
  attach"**: confirmed via full read of the new
  `useTeamsChannelHitProbe.ts` (98 lines). A channel search hit from
  Graph's `/search/query` is structurally ambiguous — a reply message is
  indistinguishable from a thread-root message in the search result
  itself (no `replyToId`, no parent link) — so whether a given hit can
  actually be addressed and attached isn't knowable until queried
  directly. The hook resolves this with a single gated `GET` per hit at
  the moment the user ticks it (not when they click "Attach"): a 200
  response means it's a genuine thread root (Graph's per-message channel
  endpoint only returns root messages), a 404 means it's a reply (and is
  reported as such rather than crashing the attach flow), and any other
  outcome is a generic failure state. This directly and precisely matches
  the PR's "wire-verified addressing" claim for channel replies.
- **Search results require a second hydration request**: confirmed via
  the module-level doc comment in the new `teamsChatGraph.ts` (643
  lines, not read in full beyond this header): Graph's chat-message
  search endpoint returns hits with no message body, and the PR's own
  code comment states this explicitly ("a search hit carries NO body...
  `hitId` is an Exchange item id and never addresses a Teams message"),
  requiring a second `GET` joined on `(resource.chatId, resource.id)` to
  fetch actual content — consistent with the description's claim that
  "channel search hits probe at tick time" rather than assuming the
  search response is directly usable.
- Also noted, not independently verified: a documented per-chat rate gate
  (`teamsChatRateGate.ts`, 1 request/sec per chat) is stated to span the
  pager, drill-down query, and hydration calls uniformly via a single
  `runGatedByChat` wrapper, "so the gate cannot live in any one of them" —
  plausible given the amount of dedicated rate-limiting code
  (`teamsChatRateGate.ts` at 89 lines plus a 51-line test file) but not
  traced through every call site.

Given the PR's size, the following substantial pieces were **not**
independently read or verified in this review: the transcript-building
logic (`buildTeamsTranscriptFile.ts` 320 lines, `collectTeamsTranscript.ts`
449 lines), the picker UI itself (`TeamsChatPickerDialog.tsx`, 1129 lines
— the single largest new file in the PR), the selection-state management
(`teamsChatSelection.ts`), the pagination logic (`teamsChatPager.ts`),
message-text rendering/sanitization (`teamsMessageText.ts`), the new
`GraphTokenProvider.tsx`/`EntraGraphTokenProvider.tsx` auth refactor (a
173-line diff to an existing file, alongside a new 161-line file), or the
~4000 lines of new test coverage across 15+ test files (extensive, but
not independently re-verified as actually exercising the claims made).

## Compatibility and configuration

No new backend configuration — this is entirely an Outlook/Teams add-in
frontend feature layered on the existing Teams-tab and Graph-token
infrastructure from #931. Requires the user to be running the add-in in a
context with Teams Graph access (delegated `Chat.Read` per the module
comment); no effect on any deployment without that.
