# PR #1134: Share an unarchive action across both chat hosts (ERMAIN-794)

- PR: https://github.com/EratoLab/erato/pull/1134
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Second of four in the archived-chat stack (on #1131), frontend
foundation only — no UI ships here, per the PR. Adds a shared
`useUnarchiveChat` hook consumed by both the web app and the Outlook
add-in's chat context, plus three fixes found during review. Confirmed
by reading the complete `useUnarchiveChat` implementation and the
relevant `useChatHistory.ts` diff in full:

- **Settle in-flight fetches before invalidating, confirmed exactly**:
  `useUnarchiveChat` calls `queryClient.cancelQueries({queryKey:
  recentChatsQuery({}).queryKey})` before its `invalidateQueries` calls —
  a code comment states precisely why: a list-query variant disabled
  mid-fetch is marked stale but never automatically refetched, and its
  late resolution after invalidation would silently clear the
  just-set stale flag, leaving a stale cached variant behind. This
  matches the PR's disclosed review finding exactly, including the noted
  detail that `refetchType: "all"` would not have fixed this (since the
  query client skips disabled queries regardless of refetch type).
- **Chat-detail query invalidated on unarchive, confirmed exactly**: the
  `Promise.all` in `useUnarchiveChat` includes
  `queryClient.invalidateQueries({queryKey: chatDetailQuery(...)
  .queryKey})` alongside the recent-chats and generating-chats list
  invalidations.
- **The archive-path status-clearing ordering bug and its fix, confirmed
  exactly via `useChatHistory.ts`**: the `useGenerationStatusStore
  .getState().clearStatus(chatId)` / `useChatHistoryStore.getState()
  .clearTitleHint(chatId)` calls are confirmed moved from *before* the
  `await archiveChatMutation(...)` call to *after* it succeeds (inside
  the `try` block, right after the mutation resolves) — precisely
  matching the disclosed defect: previously, awaiting a failed mutation
  would have already cleared this state with no rollback path restoring
  it, silently losing the generation status/title hint for a chat whose
  archive attempt actually failed.
- **Missing chat-detail invalidation added to both archive branches,
  confirmed exactly**: a `chatDetailQuery` invalidation call is added
  both to the early-return "all chats" branch (near the top of the
  function, unconditional) and to the success path of the targeted
  single-chat archive — matching "Both now refresh" precisely, closing
  the disclosed bug where archiving a chat and reopening it within the
  60-second query stale-time window would show a cached detail row still
  reporting the chat as active.
- Per the PR (not independently re-verified given remaining scope): the
  `mapRecentChatToSession` change carrying through the API's archived
  timestamp (described as the single choke point every list surface —
  web sidebar, search page, add-in drawer, kit overrides — passes
  through, which is what lets a later UI slice mark a row as archived at
  all); the `generationStatusStore.ts` diff (9 lines, presumably the
  `clearStatus` semantics the PR notes as "deleted rather than
  tombstoned" for unarchive specifically, with a stated reason that a
  tombstone would keep a stale `startedAt` the returning generation's own
  seed would then lose a comparison against); and the stated
  `removeArchivedChatFromLists` pre-existing forward-paging offset skew,
  explicitly left unfixed as out of scope for this PR.

## Compatibility and configuration

None. Pure frontend foundation work; no UI changes ship in this PR (per
its own framing). Fixes two real bugs along the way: a failed chat
archive could previously lose the chat's generation-status/title-hint
state permanently, and reopening a just-archived chat within the cache's
stale-time window could show it as still active.
