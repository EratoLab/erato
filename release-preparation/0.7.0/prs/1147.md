# PR #1147: Let a user deny an MCP tool for themselves and enforce it at both generation sites

- PR: https://github.com/EratoLab/erato/pull/1147
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Stacked on #1146. Adds a per-user "Never allow" decision for an MCP tool
alongside the existing "always allow," and — the substantive fix —
closes a real tool-filtering gap in the tool-approval continuation path.
Confirmed by reading the complete `evaluate`/`resolve_generation_mcp_tools`
call sites in `message_streaming.rs` in full:

- **The security-relevant bug and its fix, confirmed exactly**: previously,
  `run_continue_message_task` (the handler resuming a chat parked on a
  tool approval) resolved the approved tool call against an *unfiltered*
  `discover_tools_for_server_ids(chat.id, None, …)` result, then built
  the continued turn's entire offered tool set from that same raw list —
  meaning that once a user approved one call, the model's continued turn
  was offered every tool on every MCP server the chat was authorized to
  reach, bypassing whatever facet selection, assistant configuration, or
  allowlist would have restricted the original turn. Confirmed the fix:
  the continuation handler now reconstructs `effective_selected_facet_ids`
  from the *persisted* `GenerationParameters` (the parked turn's actual
  facet selection) and calls the same `resolve_generation_mcp_tools`
  function the fresh-submit path uses, with the chat's real assistant
  configuration and the user's current denials — a code comment states
  the rationale precisely: "Rebuild the tool set the parked turn was
  offered instead of trusting a fresh, unfiltered discovery... so a
  denial stored while the approval was pending wins." The approved call
  is then looked up (`approved_tool = available_mcp_tools.iter().find(...)`)
  *within* this properly filtered set, not the raw discovery.
- **Review note 1's stale-card guard, confirmed exactly**: the
  `ApproveAlways` grant upsert is now gated on both
  `matches!(request.decision, ToolApprovalDecision::ApproveAlways)` *and*
  `approved_tool.is_some()` — since `approved_tool` only resolves to
  `Some` when the tool survives the freshly-recomputed filtered set
  (including current denials), a stale approval card for a
  since-denied/since-unavailable tool can no longer write an
  always-allow grant that would overwrite a denial recorded in the
  meantime.
- **One shared filter chain genuinely used at both call sites, confirmed
  exactly**: `resolve_generation_mcp_tools` is confirmed called both from
  the regular submit/edit/regenerate path and from
  `run_continue_message_task` — not two independently-maintained
  implementations of the same filtering logic, directly substantiating
  the PR's claim that this is "one filter chain for both enforcement
  sites."
- Per the PR (not independently re-verified given remaining scope): the
  new `decision` column on `user_tool_approval_settings`
  (`always_allow`/`denied`, migration `0042`, defaulting to
  `always_allow` for existing rows — stated as no behavior change for
  existing grants); the deliberate choice that a deny decision is *not*
  gated by `approval.enabled`/`allow_always` config (since a deny can
  only make the system more restrictive, unlike an allow grant, which
  the config gates to prevent the system becoming more permissive than
  configured); the full reader audit replacing "row exists ⇒
  always-allow" assumptions across `find_active`→
  `find_active_always_allow`, a new `list_denied`, the list/tools
  endpoints carrying `decision` explicitly, and the frontend mapping
  decision to a three-state radio (Ask each time / Always allow / Never
  allow); the "collision snapshot" fix ensuring the three synthetic-tool
  name-collision checks (`propose_client_action`, `client_tools`,
  `delegate_to_assistant`) evaluate against `mcp_claimed_names`
  snapshotted *before* denial filtering, so denying an MCP tool cannot
  accidentally free up its name for a client tool to claim; the
  disclosed review finding that denial was previously checked *after*
  server-outage classification (fixed so denied-tool refusal is
  distinguished from a retryable outage/auth/credential error, with a
  new `missing_credential_server_ids` field on `ToolDiscoveryResult` kept
  out of user-visible metadata); and an explicitly off-ticket,
  separately-isolated commit fixing a pre-existing vitest teardown flake
  unrelated to this PR's substance.
- **One noted, accepted loose end, per the PR**: the wait-tool
  name-collision check still reads the post-deny tool list rather than
  the pre-deny snapshot the other three synthetic-tool checks now use —
  stated by the PR itself as benign (outside the three predicates the
  collision-snapshot fix targets) and left as-is.

## Compatibility and configuration

New migration `0042` (additive column, safe default — confirmed no
behavior change for existing rows per the PR). New endpoint field
(`decision`) on the existing tool-approval-settings POST; a user can now
explicitly deny an MCP tool for themselves regardless of the
`approval.enabled`/`allow_always` deployment-level config. The
continuation-path fix is a genuine, security-relevant correctness fix:
any deployment using the tool-approval continuation flow was previously
exposed to over-broad tool availability on a resumed turn.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: users can now explicitly
deny an MCP tool for themselves (in addition to the existing always-allow
grant), and — more importantly — a tool-approval continuation no longer
offers the resumed turn a broader set of MCP tools than the original turn
was authorized to use.
