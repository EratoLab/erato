# PR #1108: Rename `AssistantConfiguration` to `ChatConfiguration` with an optional assistant and a task spec (ERMAIN-755)

- PR: https://github.com/EratoLab/erato/pull/1108
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Delegation

## Summary

Stack 1, PR 2 of 4, on top of #1107. Splits the `chats
.assistant_configuration` JSONB column's contents into three independent
concerns — assistant binding, provenance envelope, and a new Rust-only
`TaskSpec` — so a delegated child chat can exist with no assistant bound
at all (groundwork for the later async-task-delegation stack). No SQL
migration, no API/wire-contract change. Confirmed by reading the complete
`ChatConfiguration`/`StoredChatConfiguration`/`TaskSpec` definitions and
the relevant `get_chat_assistant_configuration` change in full:

- **Byte-identical serialization preserved, confirmed exactly and pinned
  by a dedicated test**: `ChatConfiguration::new(id)` still serializes to
  exactly `{"assistant_id": "..."}` (confirmed via
  `skip_serializing_if = "Option::is_none"` on both `provenance` and
  `task`), matching the `new_id_to_json_is_byte_identical` test's own
  assertion — so the overwhelming majority of existing rows (plain
  assistant-bound chats) are unaffected by this change's on-disk shape.
- **Row-state invariant enforced, confirmed exactly**: a bare task child
  with no assistant omits the `assistant_id` key entirely rather than
  writing `null` or `{}` — confirmed via the `assistant_id: Option<Uuid>`
  field's `skip_serializing_if`, and directly asserted by the
  `bare_configuration_omits_the_assistant_key_entirely` test's own name
  and comment: the generated `chats.assistant_id` column must stay NULL
  so its foreign key is never evaluated.
- **The legacy lift, confirmed exactly matching the PR's description**:
  `#[serde(from = "StoredChatConfiguration")]` routes every deserialize
  through one conversion point. `ChatProvenance`'s old
  `expected_output`/`constraints` fields are renamed to
  `legacy_expected_output`/`legacy_constraints` with `#[serde(rename =
  "expected_output"/"constraints", skip_serializing)]` (unconditional
  `skip_serializing`, not `skip_serializing_if` — confirmed these fields
  can never be written again, only read once). The `From` impl takes
  `task.or_else(|| ...)`, so an already-present `task` value short-circuits
  and the legacy brief is discarded even if present — confirmed matching
  the PR's stated "an explicit `task` wins over a legacy brief" test case
  exactly.
- **`DelegateRoute` recorded explicitly, not inferred, confirmed
  exactly**: `TaskSpec.route: DelegateRoute` (`Assistant` default, or
  `Task`) is a first-class field on every task spec — matching the PR's
  stated rationale that inferring the route from a null `assistant_id`
  would risk misreading a future bare-model *assistant* run as a task.
- **`get_chat_assistant_configuration`'s new `Ok(None)` branch, confirmed
  exactly**: after parsing succeeds, a new `let Some(assistant_id) =
  config.assistant_id else { return Ok(None); }` guard is added before
  resolving the assistant — a code comment states this precisely:
  previously an existing envelope always implied a bound assistant, but
  now a bare task child can carry a valid `provenance`/`task` envelope
  with no assistant at all, and that must resolve to "no assistant"
  rather than being treated as parse failure or an inconsistent state.
- **`create_delegated_chat`'s signature change, confirmed exactly**:
  `assistant_id: Uuid` becomes `assistant_id: Option<Uuid>`, and a new
  `task: Option<TaskSpec>` parameter is added — matching the PR's
  described new signature exactly.
- Per the PR (not independently re-verified given remaining scope): the
  disclosed rollback cost (LD-A15) — since the legacy-brief lift is lazy
  (rewriting a row canonically only the next time something writes it,
  not eagerly on read), rolling this PR back after deployment would leave
  any row rewritten in the interim unreadable by the old code's
  `provenance.expected_output`/`constraints` fields, degrading (not
  breaking) that specific run's preamble rendering — stated as accepted
  during design review; and the disclosed note for later stacks that
  `get_recent_chats`'s `INNER JOIN LATERAL` on the latest message makes a
  chat with zero messages invisible to the listing regardless of
  assistant/provenance, relevant to a later async-re-entry stack where a
  child chat can exist before its first message.

## Compatibility and configuration

None. No SQL migration (the column keeps its name and type; the FK/
generated-column behavior on NULL is unchanged), no API/OpenAPI change
(confirmed the PR states `just generate_open_api_check` reports no diff,
since `ChatDetail` still exposes `expected_output`/`constraints`, now
sourced from the lifted `task` field instead of `provenance`). Purely an
internal data-model refactor plus one forward-looking behavior addition
(bare assistant-less delegated children can now exist, though nothing in
this PR creates one yet — that's deferred to a later stack per the PR's
"Stack 1 of 4" framing).
