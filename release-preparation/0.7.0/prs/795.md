# PR #795: Honor global tool_call_allowlist for client tools (globally-active)

- PR: https://github.com/EratoLab/erato/pull/795
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Outlook scheduling and shared mailboxes

## Summary

Follow-up to #786 (client_tools foundation). Previously, a client tool was
only offered to the model when the currently *active action facet's* own
`tool_call_allowlist` selected it — meaning a client tool had no way to be
globally active without an action facet present. This PR adds a new
`effective_client_tool_allowlist` function that unions three allowlist
sources before deciding which client tools to offer: (1) the **global**
`experimental_facets.tool_call_allowlist` ("applied regardless of selected
facets"), (2) any currently-selected regular facets' own
`tool_call_allowlist`, and (3) the active action facet's
`tool_call_allowlist` (unchanged from before). An empty union still offers
nothing — client tools remain strictly opt-in.

Confirmed by reading the code: this is a deliberately *separate* function
from the existing MCP-tool allowlist-merging path
(`build_mcp_tool_allowlist`/`merge_action_facet_into_mcp_allowlist`), per
an explicit code comment listing three policy differences that make
sharing logic unsafe: (1) client tools are opt-in on empty (offer
nothing), while the MCP path treats an empty allowlist as "all tools
allowed" (opt-out) — reusing the MCP path would have offered *every*
client tool when none were configured; (2) the MCP path short-circuits to
"unrestricted" when no facets are configured at all, but client tools
deliberately skip that shortcut so a global allowlist alone can activate a
tool with zero facets involved; (3) the action facet is folded in as a
first-class allowlist source here, whereas the MCP path only ever
additively extends an existing `Some` allowlist. A new unit test,
`effective_client_tool_allowlist_unions_global_facets_and_action_facet`,
exercises the union (global + selected regular facet + action facet) and
confirms an unknown facet id contributes nothing rather than erroring.
The rest of the diff is mechanical: the collision-guard warning log
messages against a reserved/MCP-colliding client tool name drop their
now-inapplicable `action_facet.id` reference, since the offering path no
longer requires an action facet to be active.

## Compatibility and configuration

No new configuration keys or schema changes — this changes how the
*existing* `experimental_facets.tool_call_allowlist` (both the top-level
global list and per-facet lists) and `action_facets.*.tool_call_allowlist`
(from #786) are combined when deciding which client tools to offer; no
new TOML keys are introduced. Per the PR's own notes, "No config-schema /
API change (OpenAPI + config reference unchanged)." No migration. No
behavior change for any deployment that hasn't configured
`client_tools` and a corresponding allowlist entry — this remains inert
until both are set up, same as #786.
