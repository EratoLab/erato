# PR #1253: Add Teams bot tables and user Entra object ID

## Summary

A large (5,205 insertions, 51 files) new feature: a Microsoft Teams
conversational bot integration (personal chats, group chats, and channel
mentions), with its own new `ms_teams_bot` module (`activity.rs`,
`cards.rs`, `connector.rs`, `graph.rs`, `handler.rs` at 753 lines,
`host.rs` at 647 lines, `inbound_auth.rs`, `render.rs`, `streaming.rs`,
`user_token.rs` — roughly 3,500 lines of new Rust across these files
alone), new database tables, a new per-user Entra object ID binding, and
Teams manifest generation for the bot. Unlike the stack-foundation PRs
reviewed earlier in this session (#1237, #1249), this PR's description
is auto-generated-style rather than first-person engineering prose, but
is still substantive and specific rather than a boilerplate stub.
Given the scale, this review verified the database schema and the
Entra-identity-binding logic — the two places where a design mistake
would have the most direct security consequence (user impersonation or
cross-tenant data leakage) — rather than tracing the full bot message-
handling pipeline:

- **The feature is off by default, confirmed exactly — not explicitly
  stated in the PR's own description, but confirmed directly in code**:
  `TeamsBotConfig.enabled: bool` carries `#[serde(default)]` with a doc
  comment stating "Whether the Teams bot endpoint
  `/api/integrations/ms_teams/messages` is enabled. Defaults to
  `false`." This is a materially important fact the PR description
  itself never states, and worth flagging precisely because this
  review's job is to verify claims against code, not merely transcribe
  them — here the code confirms a safe default the prose omits.
- **The database schema matches its stated purpose precisely, confirmed
  exactly**: migration 0053 adds `users.entra_object_id text` with a
  `UNIQUE` index scoped to `WHERE entra_object_id IS NOT NULL` (so the
  column can stay unset for non-Teams users while guaranteeing no two
  users ever share one once set); `ms_teams_conversations` (one row per
  conversation-and-user, matching the stated "a personal chat has one
  row; group chats and channel threads have one row per user who talks
  to the bot there" design, with `current_chat_id` nullable and
  `ON DELETE SET NULL` so a deleted Erato chat doesn't orphan the
  conversation mapping); and `ms_teams_token_exchanges` (a bare
  `exchange_id text PRIMARY KEY` table) with a code comment explaining
  its exact purpose: "Teams sends the same SSO token-exchange invoke to
  every open client of a user; the first replica to insert the exchange
  ID processes it" — a sound, minimal idempotency mechanism (a
  duplicate-key constraint violation on a second replica's attempt is
  the natural "someone already handled this" signal).
- **An Entra object ID binding is never silently reassigned from one
  user to another, confirmed exactly — the most security-relevant
  property in this diff**: `record_entra_object_id` first checks whether
  another user already owns the given `entra_object_id` via a lookup
  against the same unique column; if so, it logs a warning
  ("Entra object ID is already recorded on another user; not
  reassigning it") and returns without writing anything — it never
  overwrites an existing binding to point at a different user. This is
  precisely the property needed to prevent a race or misconfiguration
  from letting one user's web login silently capture another user's
  already-established Teams-bot identity, which would otherwise let
  Teams messages be misattributed between accounts. The companion
  `find_user_by_entra_object_id` is a simple, read-only lookup — how the
  bot resolves an incoming Teams activity to an Erato user — whose own
  correctness depends on the token/activity's `oid` claim having already
  been cryptographically verified elsewhere (in `inbound_auth.rs`, not
  read in this review).
- Per the PR (not independently re-verified given this PR's scope): the
  bot-request authentication/signature-verification logic in
  `inbound_auth.rs` (249 lines — the component that would need the most
  scrutiny to confirm incoming Teams activities are genuinely
  tenant-scoped and unforgeable, given `TeamsBotConfig.tenant_id`'s
  doc comment states "every incoming activity must originate from it");
  the full message-handling pipeline (`handler.rs`, `host.rs`,
  `streaming.rs`, `connector.rs`, `graph.rs`, `cards.rs`, `render.rs`);
  the Teams manifest generation changes for the bot (SSO support, valid
  domains) in `distribution/teams.rs`; the `MessageSubmitRequest`/
  `ContinueStreamRequest` "utility constructors for in-process surfaces"
  and the described refactor allowing the streaming message-submission
  flow to be shared between HTTP routes and in-process integrations like
  this bot (in the 277-line `message_streaming.rs` diff); the
  `security_groups_only` policy-engine interaction (default `true`,
  described as needing to "match the `groups` claim configuration of the
  web login" — a configuration-coupling worth an operator's attention);
  the infrastructure/Helm chart changes for exposing the bot endpoint
  (gateway-api/ingress/network-policy templates and their new tests); and
  the disclosed `ms_teams_bot.rs` integration test file (388 lines).

## Compatibility and configuration

Additive. New config section `[integrations.ms_office.teams.bot]`
(`TeamsBotConfig`), confirmed to default to `enabled = false`. New
database tables and a new nullable, uniquely-indexed `users.entra_object_id`
column (sqitch migration 0053) — no backfill, no effect on existing
users until a Teams-authenticated login records the field. New
infrastructure templates (Helm chart ingress/gateway-api/network-policy
additions) are presumably also conditional on the bot being enabled,
though this was not independently verified.

## Evidence and review

Verified via this PR's squash-merge commit against its parent (both
present locally). Read in full: the complete migration 0053 deploy SQL
(confirming the three schema additions and their stated purposes) and
the complete new `record_entra_object_id`/`find_user_by_entra_object_id`
functions in `models/user.rs` (confirming the never-silently-reassign
identity-binding safety property), plus the relevant `TeamsBotConfig`
definition in `config.rs` (confirming the default-disabled state). Given
this PR's substantial scope — a genuinely new subsystem spanning
roughly 3,500 lines of new bot-handling Rust code, Teams manifest
generation, and infrastructure templates — this review did not trace
the authentication/signature-verification logic, the message-handling
pipeline, or the infrastructure template changes. **Given this
introduces a new authenticated external entry point (the Teams bot
endpoint) with its own token-exchange and identity-binding logic, it
warrants dedicated security review of `inbound_auth.rs` and the
activity-handling pipeline before enabling in any production deployment,
independent of this evaluation pass.**

## Release note disposition

Proposed category: Features and enhancements. Worth a release-note
mention as a new, opt-in capability: a deployment can now configure a
conversational Microsoft Teams bot (personal chats, group chats, and
channel mentions) backed by the same assistants and policy engine as the
web app, with Entra ID-based user identification tying a Teams user to
their existing Erato account. Off by default; requires explicit Azure
Bot resource configuration (`app_id`, `app_password`, `tenant_id`, OAuth
connection) to enable.
