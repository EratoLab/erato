# PR #799: Client-tool round-trip — frontend (executor registry + result handler)

- PR: https://github.com/EratoLab/erato/pull/799
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Outlook scheduling and shared mailboxes

## Summary

Frontend counterpart to #786's backend `client_tools` foundation. When the
backend suspends a turn and emits a `client_tool_call` streaming event,
the shared frontend streaming loop looks up a registered executor for
that tool name, runs it, and POSTs the outcome to
`POST /me/messages/clienttoolresult` to resume the turn. This layer is
explicitly host-agnostic — the shared code has no Outlook-specific logic;
a host (e.g. the Outlook add-in) registers its own executors separately
(the `outlook.fetch_availability` executor is a follow-up PR, per the
description).

Confirmed by reading the code: `clientToolExecutors.ts`'s
`registerClientToolExecutor(name, executor)` (exported from
`@erato/frontend/library`) stores executors in a module-level `Map` keyed
by tool name and returns an unregister function; a capped
(`MAX_ANSWERED_TOOL_CALLS = 500`) in-memory `Set` of already-answered
`tool_call_id`s prevents a `resumestream` replay (which re-emits the same
event) from re-running an executor — the guard is set synchronously
*before* any `await`, so a live event and its replay can never both run
the tool concurrently. `handleClientToolCall.ts` looks up the executor; if
none is registered, or the executor throws, it still POSTs an error result
(rather than leaving the turn parked until the backend's per-tool timeout
from #786 elapses) so the backend can recover promptly. A successful-but-empty
result (`outcome.result` nullish) is explicitly coalesced to `null` before
sending, "so an empty success is delivered as a result, not treated by the
backend as 'no result → tool error.'" If the result POST itself fails
(network error or non-2xx), the answered-mark is rolled back
(`unmarkClientToolCallAnswered`) so a subsequent `resumestream` replay can
retry — since client tools are required to be idempotent (per #786's
config-type documentation), retrying is safe. `useChatMessaging.ts` wires
this in as a new `case "client_tool_call"` in the existing streaming-event
switch.

## Compatibility and configuration

None. Purely additive frontend plumbing: a new executor-registry module, a
new streaming-event case, and generated API types/client code for the
`client_tool_call` event and `/me/messages/clienttoolresult` endpoint
(regenerated from #786's backend OpenAPI spec). No configuration keys; no
behavior change for any deployment, since no executor is actually
registered by any host in this PR (the Outlook-specific executor is a
separate, later PR) — the registry simply has nothing in it yet, so a
`client_tool_call` event would just hit the "no executor registered"
error path if it somehow occurred (which it can't yet, since #786's
backend offering requires a configured `client_tools` entry that no
consumer sets up until later in this arc).
