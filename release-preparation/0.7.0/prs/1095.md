# PR #1095: Resolve dropped .msg emails that ANSI-encode the Message-ID, and attach ones the mailbox cannot find

- PR: https://github.com/EratoLab/erato/pull/1095
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a customer-reported bug where dropped `.msg` email files silently
vanished from the composer — no chip, no error — plus a related
pre-existing sender-address corruption bug found while investigating.
Confirmed by reading the complete `extractMsgInternetMessageId.ts` diff
and the relevant `formatAddress`/`formatDisplayName` functions in
`synthesizeThreadEml.ts`:

- **Root cause and fix, confirmed exactly**: `extractMsgInternetMessageId`
  previously read only the `__substg1.0_1035001F` stream (`PT_UNICODE`,
  UTF-16LE). Per [MS-OXMSG], a `.msg` file stores a given property as
  either entirely Unicode or entirely non-Unicode, never mixed — the
  customer's files used the ANSI form (`__substg1.0_1035001E`,
  `PT_STRING8`), so the old code returned `null`, which silently
  short-circuited the whole upload with no error surfaced anywhere.
  Confirmed the fix tries the UTF-16LE stream first, falling back to
  decoding the `001E` stream as windows-1252 — with a code comment
  correctly noting RFC 5322 restricts message-ids to printable US-ASCII,
  so windows-1252 decoding is safe regardless of the file's actual
  declared code page.
- **A second, independent latent bug fixed in the same diff, confirmed
  exactly**: both stream lookups are now root-anchored (`/__substg1.0_...`
  with a leading slash) via a new shared `readStream` helper, with a code
  comment explaining `CFB.find` otherwise matches a bare stream name
  against *every* leaf in the compound-file tree — so a `.msg` containing
  an embedded forwarded message could have its own Message-ID shadowed by
  the forwarded copy's, producing a wrong (not just missing) lookup ID.
- **Display-name comma-splitting bug and its fix, confirmed exactly via
  `formatAddress`/`formatDisplayName`**: `formatDisplayName` now wraps a
  name containing any RFC 5322 special character (comma included, tested
  via `/[()<>[\]:;@\\,."]/`) in a quoted-string, closing the bug where
  Outlook's default "Lastname, Firstname" display name previously emitted
  unquoted, causing the comma to be read as the address-list separator
  and splitting one sender into two bogus addresses. Confirmed the code
  comment states this affects the pre-existing thread-synthesis feature
  too, not just the new local-parse path, since both go through this same
  `formatAddress` function.
- **Fabricated-sender fix, confirmed exactly**: `formatAddress` returns
  `null` (causing the caller to omit the `From` header entirely) when an
  address is empty and the display name is either blank or not printable
  ASCII — a code comment explains precisely why: an RFC 2047 encoded-word
  placed before an empty `<>` angle-addr is read back *as* the address by
  a MIME parser, so a non-ASCII name with no real address has no faithful
  representation and would otherwise fabricate a bogus sender address.
- Per the PR (not independently re-verified given remaining scope): the
  new `msgProperties.ts` (223 lines, root-anchored MAPI property reads,
  codepage-aware) and `parseMsgLocally.ts` (225 lines) implement local
  parsing of a `.msg` file the mailbox lookup cannot resolve (archived,
  in a PST, in a shared mailbox, or deleted), feeding a new
  `synthesizeMessageEml()` (confirmed to exist and match its described
  single-message, non-thread-wrapped shape, per the code read above) back
  into the existing `parseEmlBytes` pipeline so preview/attachment-
  selection/upload all work unchanged; RTF body decompression is
  deliberately skipped as the heaviest part of the format, relying on the
  more-reliably-present plain-text body; and the PR's disclosed
  before/after validation against a local, uncommitted 25-file corpus of
  real Outlook `.msg` files (sender addresses surviving 6/25 → 20/20,
  fabricated addresses 0) was not independently reproduced.

## Compatibility and configuration

None. Pure Outlook add-in bug fix; no API or configuration changes.
Affects only `.msg` file handling in the drag-and-drop/attachment flow.

## Release note disposition

Proposed category: Bug fixes. Worth a mention: `.msg` email files that
ANSI-encode their Message-ID (rather than Unicode) no longer silently
fail to attach, files the mailbox can't look up (archived, shared
mailbox, deleted) now attach via local parsing instead of being dropped,
and sender display names containing a comma (e.g. Outlook's default
"Lastname, Firstname") no longer corrupt into two bogus addresses.
