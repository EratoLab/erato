# PR #1236: Settle crash-orphaned tool calls, and stop calling them done

- PR: https://github.com/EratoLab/erato/pull/1236
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Closes ERMAIN-765, fixing two related problems with a tool call left
behind by a hard process crash mid-turn (no graceful exit through
`drain_in_flight` reaches it): the trace rendered such a call as `done`
(a false green check) after a reload, and nothing ever settled the
underlying stored row, so it stayed replayable as an unanswered call in
model history forever. Confirmed both halves — the new frontend
`interrupted` trace state and the backend DB-only sweep — precisely by
reading the complete new `interrupted_parts.rs` module and the relevant
`useTraceState.ts`/`cleanup_worker.rs` diffs:

- **`interrupted` fires only when the chat is neither `running` nor
  `action_required`, confirmed exactly**: the new `useIsCurrentChatBusy`
  hook returns `true` only for `kind === "running" || kind ===
  "action_required"` from the generation status store (and `false` for a
  chat the poll has no entry for at all — "the honest answer for a cold
  load of an old chat"). `stepStatus` now takes an `isChatBusy` parameter
  and, for a `tool_use` step whose trace is no longer active, returns
  `"done"` if `isChatBusy` and `"interrupted"` otherwise — matching "It
  fires only on positive evidence that nothing is left to settle the
  part: the chat's generation status must be neither `running` nor
  `action_required`" exactly, including the stated preservation of
  rendering for an approval-parked turn or a generation still live on
  another replica (both read as "busy" via the poll).
- **Backend sweep reuses `generation_unfinished_condition` rather than a
  respelled check, confirmed exactly, with the historical correction
  independently verifiable**: both the scan query (`NOT {unfinished}`)
  and the live-children query (`{unfinished}`) call the same
  `generation_unfinished_condition(...)` function this session has seen
  reused across multiple PRs in the async-delegation stack (first
  encountered in #1188's lease-claim CAS and #1196's sweep) — directly
  substantiating "`generation_unfinished_condition` is the one spelling
  of 'this chat still owes an outcome'... reused rather than respelled."
  The PR's own disclosed correction — that the ticket's original
  `generation_state = 'running'` predicate would have matched nothing
  because the existing heartbeat-reaper always wins that race first — is
  consistent with this session's own understanding of the reaper
  mechanism confirmed in PR #1188's review.
- **Only genuine wait-path placeholders are settleable; a detached async/
  background dispatch is structurally excluded, confirmed exactly**:
  `is_settleable_placeholder` requires `content_type: "tool_use"`,
  `status: "in_progress"`, and `output.status` in `{"working",
  "queued"}` — the exact two placeholder shapes this session confirmed
  the wait-path pop loop writes in PRs #1180/#1181's reviews. A detached
  dispatch's committed output shape (confirmed in earlier reviews to
  carry a different structure, e.g. a `"dispatched"` marker rather than
  `working`/`queued`) never matches, substantiating "A detached dispatch
  carries no `status` at all and never matches the scan."
- **A live child guards the settle even on the wait path, fail-closed on
  error, confirmed exactly**: `live_children` queries named children via
  `generation_unfinished_condition` and, on a query error, returns every
  child as alive rather than none — with the comment "Fail closed: an
  unreadable child is treated as alive, so a transient error can only
  ever delay a settle, never cause one that should not have happened" —
  a sound conservative design matching "Belt and braces for the wait
  path... if the named child chat is somehow still writing, its slot is
  left alone."
- **The settle is a minimal, key-preserving raw write, confirmed
  exactly**: `settle_part` only ever inserts/overwrites `status`
  (`"error"`) and `ended_at` on the part, and `status`
  (`DelegationRunStatus::Cancelled`) and `reason`
  (`DelegationRunReason::Interrupted`) on its `output` object — every
  other existing key (child ids, assistant identity, etc.) is left
  untouched — matching "Everything already on the output is kept... Only
  the two keys that state the outcome are written" exactly, and
  confirming the DB-only write needs no `PolicyEngine`/`Subject` (it's a
  raw JSON-field mutation, not a call through `update_message_content`).
- **Wired above the retention opt-in, confirmed exactly**:
  `run_cleanup_tick` calls `sweep_interrupted_tool_parts` immediately
  after the already-reviewed task-result delivery backstop (#1196) and
  *before* the `if !args.cleanup_enabled` gate, with a comment stating
  "it deletes nothing, and a row whose tool call will never be answered
  is not something an operator should have to opt into repairing" —
  matching "it deletes nothing and does not sit behind the
  data-retention opt-in" precisely.
- **Errors are swallowed per-tick rather than propagated, confirmed
  exactly**: `sweep_interrupted_tool_parts` returns an `InterruptedPartsOutcome`
  (never a `Result`) and logs-and-continues on both the scan query's own
  failure and any individual row's malformed JSON — matching "Returns
  rather than errors: this runs inside the cleanup tick beside the
  delivery backstop, and one bad row must not take the rest of the tick
  — or the retention pass behind it — down."
- Per the PR (not independently re-verified given remaining scope): the
  disclosed two-layer validation strategy — the Postgres-level settle/
  guard tests (not read), and the described "Layer 2" automated test that
  drives a real `delegate_task` dispatch and extracts the server's own
  committed placeholder bytes to test against "production bytes rather
  than a hand-written fixture," including the disclosed detail that this
  test initially failed for the right reason (the live-child guard
  correctly refusing to settle a slot whose child was still running,
  requiring the test to be restructured to tick twice around the run's
  actual lifetime) — a specific, credible, falsifiable-methodology claim
  not independently reproduced here; the `SWEEP_BATCH_LIMIT = 200`
  per-tick bound (confirmed to exist in the code, consistent with the
  analogous bound this session saw in #1196's delivery sweep, but its
  specific value not independently justified); the frontend pill/icon
  rendering details (`ToolStatusPill.tsx`, `icons.tsx`,
  `DelegationStep.tsx` — confirming `working`/`queued` inherit the new
  state and `input_required` never does was not independently traced
  beyond the `stepStatus` function itself); and the disclosed
  verification (1355/1355 backend tests, clean clippy/fmt; 2636 frontend
  tests, clean typecheck/lint/prettier).

## Compatibility and configuration

No migration. Additive: a new `interrupted` value on the frontend's
closed `TraceStepStatus` vocabulary, and a new `DelegationRunReason::Interrupted`/
terminal-status pairing on the backend (both confirmed to exist and be
consumed exactly as described). Pre-existing crash-orphaned rows (if any
exist in a deployment from before this PR) are settled by the first
cleanup tick after upgrade, per the PR's own disclosed release note — a
one-time, additive correction with no destructive effect (the sweep only
ever writes `error`/`cancelled`/`interrupted` onto rows that already
represent dead, unanswerable work, confirmed by the positive-evidence-only
gating above).

## Release note disposition

Proposed category: Bug fixes. The PR's own drafted note is accurate per
the above verification: a tool call orphaned by a hard crash mid-turn no
longer renders as successfully completed after a reload (it now shows a
distinct "interrupted" state instead of a false green check), and the
underlying row is automatically settled by the next cleanup tick so it
stops being replayed into model history as an unanswered call. No
migration required; pre-existing orphaned rows self-heal on upgrade.
