# PR #881: Emit chat_created before the policy rebuild (ERMAIN-494)

- PR: https://github.com/EratoLab/erato/pull/881
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes new-chat creation blocking on a full OPA policy-data rebuild before
the client could navigate to the newly created chat, and a rebuild
failure previously stranding the user outside the chat entirely.
Confirmed by reading the code:

- In `run_message_submit_task`, the `ChatCreated` streaming event is now
  sent to the client **before** the policy rebuild runs, rather than
  after — reordered from "rebuild, then notify" to "notify, then rebuild."
  The code comment confirms this reordering is authz-safe: the chat row
  is already committed and the global policy engine invalidated before
  this background task was even spawned, so the client's post-navigation
  requests (hitting the request-authorization middleware) will themselves
  wait on — or perform — the same rebuild via `rebuild_data_if_needed`,
  and can never observe pre-create policy data. A rebuild failure now
  surfaces as an error frame inside the already-created chat instead of
  suppressing the navigation event that would have gotten the user there.
- New `PolicyEngine::rebuild_lock` (a `tokio::sync::Mutex<()>`, shared
  across request-scoped clones of the engine) serializes rebuilds
  process-wide with a **double-checked-locking** pattern in
  `rebuild_data_if_needed`: it checks the staleness flag once
  lock-free, acquires the lock only if stale, then re-checks after
  acquiring — so a rebuild that completed while a caller was waiting on
  the lock is recognized and skipped rather than redundantly repeated.
  Confirmed this is what lets the submit task's own rebuild and the
  navigating client's concurrent middleware-triggered rebuild coalesce
  into a single actual rebuild instead of both performing one (a
  "stampede").
- The submit task's own rebuild now explicitly goes through the **global**
  policy engine (`app_state.global_policy_engine`) rather than the
  request-scoped `policy` clone passed into the function — confirmed via
  the code comment: a request-scoped clone's staleness flag is created
  fresh (severed) per clone, so it can never see the handler's own prior
  invalidation and would silently skip a needed rebuild.
- Two `invalidate_data()` calls at stream-completion time (in both the
  background and foreground completion-update paths) are removed
  entirely — confirmed via the diff — since nothing in the policy dataset
  actually changes when a message finishes generating; only chat
  *creation* itself needs a rebuild. MCP-extracted files (a separate
  policy-relevant resource) now invalidate at their point of creation
  instead, per the diff's mention of `message_streaming_file_extraction.rs`'s
  4-line addition (not independently traced in detail).
- Per the PR description (not independently verified in this diff, which
  doesn't show the periodic-refresh code): the existing 60-second periodic
  policy refresh now claims its time slot up front so only one worker per
  refresh window actually performs the time-based rebuild — consistent
  with the same single-flight goal as the request-path fix.

The PR notes this is deliberately minimal in scope: the existing
`data_needs_rebuild` flag and `clone_for_request` semantics are otherwise
unchanged, with a larger generation-counter-based rewrite of the whole
staleness mechanism split out into a separate, stacked follow-up PR (not
part of this diff).

## Compatibility and configuration

None. Pure backend correctness/latency fix; no configuration, API, or
migration changes. Behavior change: creating a new chat now navigates the
user there immediately rather than waiting for a policy-data rebuild to
complete first, and a rebuild failure at that point no longer prevents
the user from reaching the newly created chat.
