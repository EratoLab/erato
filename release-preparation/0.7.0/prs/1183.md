# PR #1183: Share assistant welcome configuration with component kits

- PR: https://github.com/EratoLab/erato/pull/1183
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Continues the same kit-extraction pattern as the ERMAIN-810 series
(#1145, #1161, #1173, #1174, #1178) — this time letting a kit (OpenWebUI)
replace the assistant welcome screen's identity header/hero while the
host retains modal state, permission warnings, prompt truncation, file
listing, and edit navigation. Confirmed the central render-prop mechanism
and the "no behavior change by default" claim by reading the complete
diff:

- **`renderHeader` replaces only the header, host keeps everything behind
  the modal, confirmed exactly**: `AssistantWelcomeUpperProps` gains
  `renderHeader?: (state: AssistantWelcomeHeaderState) => ReactNode`. When
  supplied, it replaces the avatar/name/description header block only;
  the `ModalBase` (open/close state via `isConfigurationOpen`), the
  `inaccessibleFiles` permission warning, the prompt's 500-character
  truncation, the file-chip listing, and `handleEditAssistant`'s
  navigation logic are completely unchanged and still rendered
  host-side inside the modal — directly confirming "the kit can keep
  that presentation while the host owns modal state, permission
  warnings, prompt truncation, file listing and edit navigation."
- **`AssistantWelcomeHeaderState` carries exactly what a custom header
  needs, confirmed exactly**: the interface is `{ assistantInitial:
  string; configurationLabel: string; openConfiguration: () => void;
  editAction: { label: string; onClick: () => void } | null }` —
  `editAction` is derived once (`assistant.can_edit ? { label, onClick:
  handleEditAssistant } : null`) and handed to a custom header so it can
  render its own edit affordance while the navigation logic
  (`handleEditAssistant`) stays host-owned; the host's own default
  fallback Edit button is correspondingly suppressed via `!renderHeader &&
  editAction` so a kit supplying `renderHeader` doesn't get a duplicate
  button.
- **`configurationClassName` scopes styling without touching contents,
  confirmed exactly**: it's spliced only into `ModalBase`'s
  `contentClassName` via `clsx("max-w-2xl", configurationClassName)` —
  matching "Scope custom configuration styling without rebuilding its
  contents" precisely.
- **Default host rendering is byte-for-byte unchanged when `renderHeader`
  is omitted, confirmed exactly**: the default branch
  (`renderHeader ? renderHeader(...) : (<div data-testid="assistant-welcome-screen-default"...>...</div>)`)
  reproduces the original header markup verbatim — same classes, same
  `data-testid`/`data-testid="assistant-welcome-avatar-button"`/
  `"assistant-welcome-avatar-initial"` attributes, same conditional
  description rendering — confirming "Default host rendering remains
  unchanged." The only structural change is the component's outer root
  becoming a `<>` fragment (to allow the conditional header as one of two
  siblings alongside `ModalBase`) in place of the previous wrapping
  `<div>`, which carries no visual or test-selector effect.
- **No new host component introduced, confirmed structurally**: this PR
  only modifies the existing `AssistantWelcomeUpper` function and its
  previously-private `AssistantWelcomeUpperProps` type (now exported) —
  no new component file is added, matching "No new host component is
  introduced."
- **Kit-surface pins match the PR's own list precisely, confirmed
  exactly**: `AssistantWelcomeUpper`/`AssistantWelcomeHeaderState`/
  `AssistantWelcomeUpperProps` ("welcome... header types"),
  `ModelSelector` ("selector"), `StarterPromptsSection` ("starter"),
  `getChatUrl` ("routing helper"), and `useThemedIcon` ("themed-icon
  hook") are all confirmed added both as explicit exports in
  `kit-surface.ts` and as string entries in `ERATO_KIT_SURFACE_EXPORTS` —
  matching "Pin the consumed welcome/selector/starter components, header
  types, routing helper and themed-icon hook" exactly, word for word
  against the actual exports.
- **Minor version bump, confirmed exactly**: `ERATO_SHARED_SURFACE_MINOR`
  bumped `12 → 13` in `surfaceVersion.ts` — matching "shared surface
  1.13" and the established additive-only versioning convention verified
  repeatedly in prior reviews (#1055/#1138/#1145/#1168/#1174/#1178).
- Per the PR (not independently re-verified given remaining scope): the
  companion `data-ui="assistant-configuration-prompt"`/
  `data-ui="assistant-configuration-file"` attributes added to the
  prompt/file-chip markup (plausibly for the kit's own styling hooks, not
  called out as a distinct bullet in the PR body but visible in the diff
  and consistent with the stated goal), the office-addin mock-contract
  coverage (`eratoLibraryMock.tsx`, 5 lines) for the newly pinned names,
  and the disclosed validation claims (2,391 frontend tests passing with
  11 skipped, strict lint/TypeScript/i18n/formatting, library/import-map
  builds, 8 office mock tests, consumer-kit typecheck/build and 28 kit
  tests, desktop/narrow light/dark visual comparisons) — none
  independently reproduced here.

## Compatibility and configuration

None breaking, and no behavior change for the host's own default
rendering, confirmed directly (the default branch reproduces the prior
markup exactly). Additive `ERATO_SHARED_SURFACE_MINOR` bump only. This PR
contains only host-side changes; no companion kit PR is mentioned as a
separate delivery in this PR's own description (unlike the preceding
PRs in this series), though the PR's framing implies OpenWebUI's
duplicated modal will subsequently be replaced with a `renderHeader`-based
consumption of this surface.
