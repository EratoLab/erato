# PR #804: ERMAIN-387: create-appointment confirm path (outlook.create_appointment + erato-appointment fence)

- PR: https://github.com/EratoLab/erato/pull/804
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Outlook scheduling and shared mailboxes

## Summary

Adds the confirm-and-create step to the appointment-scheduling seam from
#801: once the model picks a slot, it now proposes a new, user-confirmed
`outlook.create_appointment` client action that opens Outlook's own native
new-appointment form, **prefilled but never saved or sent automatically**
— the user still reviews and Saves/Sends in Outlook's own window.
Confirmed by reading the code:

- New `office-addin/src/utils/outlookCreateAppointment.ts`:
  `parseAppointmentDetails` parses the model's `erato-appointment` fenced
  JSON defensively (never throws — unparseable JSON, a non-object, a
  missing/unparseable `start`/`end`, or an inverted/zero-length range all
  return `null`, so the card simply doesn't render rather than opening a
  bad form). `openNewAppointmentForm` calls
  `Office.context.mailbox.displayNewAppointmentForm[Async]` with a 15s
  timeout guard against a wedged host; recurrence is deliberately never
  prefilled (the form API has no recurrence property). Mobile gate
  confirmed: `isCreateAppointmentSupported` returns `false` on
  `OutlookIOS`/`OutlookAndroid`, since `displayNewAppointmentForm` is
  unsupported there.
- `outlookClientActions.ts` now partitions `IMPLEMENTED_CLIENT_ACTIONS`
  into `EMAIL_CLIENT_ACTIONS` (`outlook.reply`, `outlook.reply_all`) and
  `APPOINTMENT_CLIENT_ACTIONS` (`outlook.create_appointment`), each with
  its own `offerable*ClientActions` filter — confirmed this means a facet
  advertising `outlook.create_appointment` can structurally never surface
  a reply button, and vice versa, since each renderer only ever consults
  its own kind's offerable set.
- `computeShouldRenderEmailCard` is now restricted to the email-action
  set specifically (previously used the general offerable-actions list),
  so an appointment proposal can never get promoted into an insertable
  whole-body email card — confirmed in the updated doc comment and logic.
- New `buildOutlookArtifact` (extracted, pure function) stamps an
  `OutlookArtifact` through either of two doors: a `body_format` facet arg
  (existing email-shaped paths: compose/rewrite/reply/review), or the
  facet advertising client actions this add-in implements (new: the
  scheduling facet's appointment fence, which carries no `body_format`
  at all). `bodyFormat` on the resulting artifact is stamped ONLY from the
  first door — confirmed this is what gates the drifted-tag-rescue and
  whole-body-card paths off for action-fence-only (appointment) messages,
  addressing the PR's stated goal that "scheduling prose can never card as
  an insertable email."
- `useClientActionConfirmFlow.ts` (new, 221 lines) is described as an
  extraction of the existing confirm-card state machine and auto-prompt
  one-shot logic out of the email renderer, now shared by both
  `OutlookEratoEmailRenderer` and the new (406-line)
  `OutlookEratoAppointmentRenderer` — not independently re-verified line
  by line, but the PR states the email-renderer test suite stayed green
  through the extraction, and the file's presence/size is consistent with
  the described refactor.
- A `NO_ITEM_SEND_IDENTITY` sentinel lets the item-independent appointment
  action still auto-prompt from the pinned no-item pane, while item-bound
  reply executors treat that sentinel as an identity mismatch (fail
  closed) — not independently traced through `OutlookMailItemProvider.tsx`
  (11-line diff) beyond confirming the described intent is plausible given
  the file touched.

## Compatibility and configuration

Additive; the actual facet TOML (the `outlook_schedule` facet's step-4
rewrite plus `client_actions`/`presentation = "auto_prompt"`/
`client_actions_always_ask`) ships in a companion content-repo PR, not
this diff — `backend/erato.template.toml`'s 12-line change is limited to
documentation. `outlook.create_appointment` joins
`IMPLEMENTED_CLIENT_ACTIONS` as a fixed, code-defined allowlist entry (not
runtime-configurable); no behavior change for any deployment that hasn't
configured a facet advertising it. New locale strings added across all 5
supported languages (de/en/es/fr/pl) for the appointment confirm-card
labels.

## Release note disposition

Proposed category: Features and enhancements, "Outlook scheduling and
shared mailboxes". User-visible: after the assistant finds a meeting slot
(from #801), it can now propose opening a prefilled new-appointment form
