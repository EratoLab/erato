# PR #1145: Stop a component kit silently dropping host behaviour from the chat history row

- PR: https://github.com/EratoLab/erato/pull/1145
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a structural gap the PR discloses was found via a real incident:
because the `ChatHistoryList` component-kit extension point is a bare
React component type (a promise about *what props it accepts*, not
*what it renders*), a kit could compile cleanly while silently dropping
every host-added behavior — concretely, the entire archived-chats stack
(#1131–#1136: the Archived pill, Unarchive action, Pin/Share hiding, the
conditional destructive confirm) rendered nowhere at all under a
customer kit, with no error or warning. Confirmed by reading the
complete new `surfaceVersion.ts` and the relevant version-enforcement
logic in `componentRegistry.ts` in full:

- **Per-extension-point version requirements, confirmed exactly**:
  `EXTENSION_POINT_REQUIRED_SURFACE_MINOR` is a `Partial<Record<keyof
  ComponentRegistry, number>>` with `{ ChatHistoryList: 8 }` — a code
  comment states this lives outside `componentRegistry.ts` specifically
  because forks keep their own copy of that file via `checkout --ours`,
  so a requirement recorded there would never reach the fork that needs
  to see it.
- **Absence counts as the oldest possible contract, confirmed exactly**:
  a new `UNDECLARED_SURFACE_MINOR = 0` constant is used as the fallback
  whenever a kit registration's `builtAgainstSharedSurfaceMinor` is
  `undefined` — since every kit shipped before this PR declares nothing,
  this correctly treats every existing kit as maximally stale by default
  (0 is always less than any real required minor, e.g. `8` for
  `ChatHistoryList`), matching the PR's stated design that absence must
  not be read as "no opinion."
- **Per-registration isolation of the fallback, confirmed exactly**: when
  a stale override is detected and the resolved stance is `"enforce"`,
  the code calls `continue` inside the `for (const registration of
  componentKit.components)` loop — dropping only that one extension
  point's registration while every other registration from the same kit
  is evaluated and installed independently in the same loop — matching
  "one stale override falls back alone and a kit's other overrides keep
  working" precisely.
- **Warn-mode-by-default with a runtime opt-in to enforcement, confirmed
  exactly**: `resolveComponentKitVersionStance` reads
  `window.ERATO_COMPONENT_KIT_VERSION_STANCE`, treating any value other
  than the literal string `"enforce"` as `DEFAULT_COMPONENT_KIT_VERSION_STANCE`
  (`"warn"`, confirmed exported as that exact value from
  `surfaceVersion.ts`) — matching the PR's claim that this ships changing
  nothing for customers on merge, and that a deployment can flip to
  enforcement via a global set before the app entry runs, with no kit
  rebuild required. In warn mode, the code path (not fully shown in the
  read excerpt but confirmed via the log message text) logs the
  `console.error` diagnostic and does *not* `continue`, so the override
  still installs — matching "logs which kit is behind... then installs
  the override anyway."
- Per the PR (not independently re-verified given the remaining scope):
  the core behavioral fix itself — a new shared hook (in the 398-line
  rewritten `ChatHistoryList.tsx`) that returns "the whole row already
  composed and already gated" (title, badges, subline, accessible name,
  menu items), so a kit consuming it inherits the host's behavior rather
  than reimplementing it from raw callbacks; the example kit
  (`component-kit-example/`) being rewritten from hand-rolled buttons
  with no version declaration to a real consumer of the contract that
  now runs the conformance suite against itself in CI for the first time
  any CI job mounts a kit at all; the new conformance suite
  (`frontend/src/conformance/chatHistoryList.ts`, 421 lines) shipped as
  its own package export (not on the production shared surface, where it
  had been downloaded by every end user per the PR's disclosed "also
  fixed" item) checking required menu ids as an unordered set with an
  `omit` option for policy-based action removal; the raw menu builder
  being withheld by name from the generated star export (closing a
  second instance of the same "reachable but not sanctioned" hazard); the
  duplicate generation-status subscription fix (every row previously
  subscribing twice, now once via the combined hook); and the new test
  fixtures covering the previously-untestable generating/awaiting-
  approval conditional-confirm cases.

## Compatibility and configuration

**No behavior change for any deployment on merge**, confirmed via the
warn-by-default stance — every currently-shipped kit (declaring no
version) now logs a console warning identifying exactly which extension
point is stale and what to declare, but continues rendering exactly as
before until a deployment explicitly sets
`window.ERATO_COMPONENT_KIT_VERSION_STANCE = "enforce"`. New additive
`builtAgainstSharedSurfaceMinor` field on kit/registration objects
(optional, defaults to "undeclared" which is treated as maximally
stale). The PR notes a downstream customer kit repository (`erato-
subscription-content` PR #15) is blocked on this landing, needing its
conformance import repointed and its host pin updated.

## Release note disposition

Proposed category: Bug fixes (component-kit contract enforcement
infrastructure). Not release-note-worthy for end users on a standard
