# PR #1136: Close the composer on an archived chat and explain it (ERMAIN-794)

- PR: https://github.com/EratoLab/erato/pull/1136
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Fourth and last of the archived-chat stack (on #1135). Closes the
composer on an archived chat with an explanatory notice carrying an
Unarchive action, and — per the PR's own framing — the substance of this
PR is four *additional* write paths review found still open that the
composer lock alone didn't cover. Confirmed the two most safety-critical
fixes by reading the complete `McpToolApprovalCard.tsx` and
`useConversationDropzone.ts` diffs in full:

- **The tool-approval card fix, confirmed exactly including its subtle
  three-state gating**: a chat parked on a tool approval keeps that state
  through archiving (the approval request is durable), and Approve/Deny
  previously posted directly with no gate at all. The card now renders
  `status={isArchived ? "dismissed" : "pending"}` with `resolvedLabel=
  {archivedNoticeText()}` when archived — so an archived chat's approval
  card shows the resolved/dismissed state with an explanation instead of
  live, postable buttons. Confirmed the gate is genuinely `isArchived`
  (a dedicated hook, `useChatArchived(chatId)`), not derived from edit
  rights — matching the PR's stated reason precisely. Confirmed the two
  disclosed asymmetric-timing guards exactly: the confirmation-registry
  hold releases only when `isArchived === true` (stays held while
  `isArchived` is still `undefined`/loading, so a queued send can't slip
  past an undecided approval during the detail fetch), while the durable
  "action required" marker seeds only when `isArchived !== false` is
  false — i.e. only once `isArchived` is confirmed exactly `false` — so
  the marker is never seeded for a chat whose archived status isn't yet
  known. Both conditions are deliberately opposite directions (hold
  releases on confirmed-true, seed fires on confirmed-false), each
  correctly erring toward safety for its own failure mode.
- **The drag-and-drop tab-hijack fix, confirmed exactly**: a new
  `swallowDrag` handler (`event.preventDefault()` plus
  `event.dataTransfer.dropEffect = "none"`) is wired to `onDragEnter`,
  `onDragOver`, *and* `onDrop` on the dropzone root whenever the zone is
  closed (`disabled || isUploading`) — a code comment states precisely
  why `dragenter` must be handled alongside `dragover`: Blink fires only
  `dragenter`, not `dragover`, on the frame a drag target changes to, so
  omitting it would have let a drop on the conversation itself navigate
  the browser tab away (the underlying `react-dropzone` library only
  guards document-level drops *outside* its target, never drops on the
  target itself while disabled). Confirmed this closes the same hole
  during an ordinary in-progress upload too, not just an archived chat —
  matching the PR's own "incidentally closes the same hole" claim.
- Per the PR (not independently re-verified given remaining scope): the
  new `ArchivedChatNotice.tsx` component (43 lines) reaching the web chat
  page, the assistant chat space, and the add-in through the existing
  delegated-run header's slot (so no host needed its own integration
  code); the message-edit/regenerate/share flag moving from a
  sidebar-listing lookup (which produced two disclosed bugs: vanishing
  for the wrong reason under the active filter, reappearing with edit
  rights under the all filter) to reading directly off the chat detail,
  combined with the same lock the composer uses so a *running* delegated
  run withdraws these controls regardless of the delegated-runs filter
  state and a *finished* one offers them regardless — the
  `useChatCanEdit.ts`/`useChatHeader.ts` (renamed from
  `useDelegatedRunHeader.tsx`) diffs implementing this were not
  independently read; the welcome screen's starter prompts now withheld
  whenever the composer is closed; and the delegated-run-specific notice
  (archived run says so but offers no unarchive path, reusing the
  already-translated run-scoped string rather than minting a new one, with
  the run header's own previously-duplicated archived branch removed in
  favor of the single shared notice).
- **Explicitly disclosed known gap, per the PR**: between opening an
  archived chat and its detail query resolving, the composer is briefly
  open, and a send in that window is rejected only by the existing
  visible error (not proactively blocked) — the PR states locking on
  "not yet loaded" was considered and rejected because it would also lock
  the new-chat page (which never fetches a detail row at all), so this
  narrow race window is left as-is.

## Compatibility and configuration

None breaking. Real, intentional UX and safety fixes: an archived chat's
composer, tool-approval prompt, drag-and-drop, and edit/regenerate/share
controls are now all consistently locked, closing several previously-open
paths that could either silently fail against the backend's write refusal
or, in the drag-and-drop case, navigate the browser tab away unexpectedly.
