# PR #1088: Derive dropdown row radius from a panel radius token and four-sided inset

- PR: https://github.com/EratoLab/erato/pull/1088
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a visual bug where every dropdown row highlight touched the panel's
side borders while floating vertically off the top/bottom, with corners
rounder than the panel itself — caused by three independently-landed
changes (a vertical-only inset token, a rounded row highlight, and the
row radius moving to the unrelated control token) that together
decoupled the row's geometry from the panel's. Confirmed by reading the
complete `globals.css` and the relevant `theme.ts`/`DropdownMenu.tsx`
diffs:

- **Two-token contract with a derived row radius, confirmed exactly**: a
  new `--theme-radius-dropdown` token (default `0.5rem`) replaces
  `--theme-radius-base` as what `.anchored-popover-skin` reads for the
  panel's own corner radius — confirmed deliberately distinct from the
  existing control-radius token, matching the PR's stated reasoning that
  customer themes scope the control token to button pill shapes. The
  existing `--theme-spacing-dropdown-chrome-padding-y` becomes
  `--theme-spacing-dropdown-chrome-padding` and now applies to all four
  sides (`.dropdown-panel-chrome-geometry` switches from `padding-block`
  to plain `padding`), closing exactly the asymmetric-inset degree of
  freedom the PR identifies as the root cause.
- **Row radius formula, confirmed exactly**: `.dropdown-item-geometry`
  and `.btn-geometry-list-item` (now merged into one CSS rule, previously
  the latter had its own independent static `border-radius:
  var(--theme-radius-control)`) both get `border-radius: max(0px,
  var(--theme-radius-dropdown) - var(--theme-spacing-dropdown-chrome-padding))`
  — exactly the "panel radius − inset" derivation the PR describes, with
  the `max(0px, ...)` guard preventing a negative radius if a theme sets
  an inset larger than its own panel radius.
- **Utility-class removal confirmed on the sampled call site**: `Dropdown
  Menu.tsx`'s row button drops `rounded-[var(--theme-radius-control)]`
  from its class string entirely, leaving `.dropdown-item-geometry`'s
  layered CSS rule as the sole source of the row's radius — confirmed
  necessary since a Tailwind utility class would otherwise outrank the
  layered `@layer` rule and the new derivation would never take visible
  effect. Per the PR (not independently re-verified), the same utility
  removal applies across four other copies of the row class string
  (`ChatInputAddMenu.tsx`, `ChatHistoryFilterMenu.tsx`, and the two
  add-in row injector components).
- **Legacy compatibility back-fill and docs, confirmed by the diff
  stat**: `themeUtils.ts` gains a one-line addition (presumably the
  `borderRadius` legacy-compatibility mapper filling the new
  `radius.dropdown` key, matching the #1068/#1069 pattern of this
  session's earlier reviews — not independently re-read here) and
  `theming.mdx` documents both new tokens.
- **Disclosed known gaps, per the PR**: `AssistantMentionPopover` and
  `DelegationRunModePopover` share the panel class and pick up the new
  inset/radius automatically but were not rendered/verified, so their row
  content (not using the `.dropdown-item-geometry`/`.btn-geometry-
  list-item` classes) carries no themed row rounding; the Office add-in's
  two string-literal edits were not linted/typechecked in this PR's own
  verification; and a companion change to the separate
  `erato-subscription-content` repository's `open-webui-like` theme is
  required to ship alongside this PR, since that theme currently hand-
  patches the old geometry and would otherwise double-inset.

## Compatibility and configuration

**Visual change for every dropdown/menu surface** using the affected
classes: panel radius increases from the previous 6px (`--theme-radius-
base`) to 8px (`--theme-radius-dropdown`, same default numeric value
`0.5rem`... note: 0.5rem = 8px, and the PR's own before/after table shows
"Before: Panel 6px" which implies `--theme-radius-base` was previously
`0.375rem` or similar — not independently cross-checked against the prior
value of `--theme-radius-base`), and row radius drops to a value derived
from panel-radius-minus-inset (4px per the PR's measured table) rather
than a flat 8px. A customer theme setting `--theme-radius-dropdown`
directly now controls both the panel and, via the derivation, the row
radius together — closing the exact mismatch bug this PR fixes. A theme
setting only the old `--theme-spacing-dropdown-chrome-padding-y` key
would need to migrate to the new four-sided key name.
