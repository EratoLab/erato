# PR #841: E2E: streaming composer + message queue (ERMAIN-466/470)

## Summary

**The PR title and description describe this as purely adding
end-to-end test coverage** for #837/#840 (composer-stays-usable-while-
streaming + message-queue-on-send-during-generation), but the diff
contains a real, previously-undisclosed production bug fix, confirmed by
reading the code:

- New `composeSessionStore.ts` (100 lines, read in full) moves the compose
  session-id-per-chat and per-session-draft maps out of `useComposeSession`'s
  React refs into a module-level Zustand store. The store's own doc
  comment states the reason precisely: `ChatInput` is torn down and
  rebuilt underneath the user in two situations — the "New Chat" button
  bumps a mount-key counter in `ChatProvider`, and the empty-state →
  messages layout switch remounts the component by position — and holding
  the session/draft maps in a `ref` meant such a remount minted a **fresh**
  session id for the same chat, silently **orphaning that chat's saved
  draft and any queued (not-yet-sent) message**.
- Confirmed the actual fix in `ChatInput.tsx`: a new mount-time
  `useLayoutEffect` re-seeds the composer text/attachments from the
  session's stored draft (so a remount doesn't present an empty composer
  for a chat that had text pending), and a new unmount cleanup effect
  folds any still-queued message back into that session's draft before
  teardown (via `mergeComposeDrafts`) — otherwise a queued message would
  strand in the queue store waiting for a turn the now-unmounted chat is
  no longer displaying, and could unexpectedly auto-send when the user
  later returned to it.
- This is a genuine correctness fix for the #840 message-queue feature
  (which had only just landed), not merely refactoring for testability —
  without it, clicking "New Chat" (or the layout transitioning from
  empty-state to messages) while a message was queued or a draft was
  pending could lose that content or cause a surprise background send.

Alongside this fix, the PR adds the actual E2E coverage its title
describes: one new Playwright spec,
`queue-and-streaming-composer.many-models.spec.ts` (473 lines, not read in
detail), covering 10 scenarios against the real mock-LLM streaming path —
composer-stays-editable, Enter/Queue-button queuing and auto-send-on-
completion, overwrite-confirmation, cancel/edit of a queued chip, Stop
returning a queued draft to the composer, navigating away dropping a
queued message to a draft rather than background-sending, and a queued
message's attachment surviving to the auto-sent turn. The PR explicitly
notes deliberate coverage gaps as follow-ups: the error-path restore
branch (no reliable slow-then-error mock exists yet), facet/tool selection
surviving mid-stream (needs a scenario change), and mid-stream dictation
start (left to unit tests).
