# PR #1163: Report why a delegated run ended and frame the child's answer (ERMAIN-767)

- PR: https://github.com/EratoLab/erato/pull/1163
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Stack 2, PR 2/5, on top of #1162. **Explicitly disclosed as an ungated
wire change** affecting the already-shipped @-mention delegation route
with no feature flag — deliberately stacked after #1162 so the frontend
can render the new status/reason vocabulary before the backend starts
emitting it (otherwise every delegation step would render as an error,
since the pre-#1162 frontend treats any non-`completed` status as one).
Splits the overloaded `failed` status into `cancelled`/`completed` with a
`reason`, and wraps a delegated child's answer in an untrusted-data frame
against prompt injection. Confirmed by reading the complete
`frame_delegation_result` function and its surrounding module in
`delegation.rs` in full:

- **One shared framing function used at both model-facing seams,
  confirmed exactly — the central correctness property of this PR**: a
  doc comment on `frame_delegation_result` states directly "This is the
  single funnel BOTH model-facing seams pass through: the live tool
  response (`DelegationResultEnvelope::model_response_text`) and the
  replay of the stored part on every later turn (`strip_ui_only_tool_output`
  in `prompt_composition`)" — with the stated reasoning that framing only
  the live seam would contain an injected answer for exactly one turn and
  hand it over raw from turn N+1 onward, which is precisely the turn an
  injected instruction would be waiting for. Confirmed the module also
  states a test pins that both seams produce identical framed content
  (acknowledging the raw JSON bytes can differ in key order after a
  `jsonb` round-trip, but the framed text content cannot diverge).
- **Escape, not strip — and line structure preserved, confirmed exactly,
  consistent with this session's earlier-confirmed offer-side pattern**:
  `framed_untrusted_block` replaces `<`/`>` with `&lt;`/`&gt;` (not
  stripping or collapsing), with a doc comment explicitly distinguishing
  this from the existing `bounded_untrusted` helper (used for the tool
  *offer*, which collapses to one line) — because this is a sub-task's
  answer a *person* may also read, so its line structure must survive.
  Confirmed via the diff's own extensive test coverage that a child
  answer containing a literal `</untrusted-data>` string is correctly
  escaped to `&lt;/untrusted-data&gt;`, and the rendered output still
  contains exactly one genuine `</untrusted-data>` closing tag (the
  framer's own) — directly proving the escaping defeats an adversarial
  attempt to forge a frame boundary from inside the child's own answer.
- **`status`/`reason`/ids kept outside the untrusted frame, confirmed
  exactly**: `frame_delegation_result` only wraps the `result` field's
  string value; `status`, the new `reason`, `child_run_id`, and
  `parent_tool_call_id` are read and re-attached as plain object keys
  outside the frame — matching the PR's stated design that the response
  must stay machine-readable even while the answer text itself is
  distrusted.
- **The unforgeable-guidance placement, confirmed exactly**: the new
  `RESULT_UNTRUSTED_GUIDANCE` sentence is inserted as a sibling `note`
  key, never inside the untrusted block itself — a doc comment states
  this is deliberate specifically so it stays unforgeable: if it were
  placed inside the frame, a malicious child answer containing the exact
  same guidance sentence would land inside the region the model is told
  to distrust, rather than being indistinguishable from the genuine
  system-authored guidance.
- **The status-vocabulary split, confirmed exactly matching the stated
  before/after table**: `DelegationRunStatus`'s doc comment states
  `failed` is now infrastructure-only, with `timeout` removed in favor of
  `cancelled` + `reason: timeout` (legacy `timeout`-status parts
  persisted before this change keep their stored spelling and remain
  renderable, consistent with #1162's frontend-side legacy-tolerance
  confirmed in this session's earlier review) — a dedicated test asserts
  `parsed["reason"] == "timeout"` for the new path.
- Per the PR (not independently re-verified given remaining scope): the
  `completed` + `reason: no_answer` reclassification for an empty
  delegate response (previously misreported as `failed`, inviting the
  origin model to retry a call that would produce the same empty answer
  again); the `approval_unavailable` reason added to the existing parked-
  approval-during-archival failure case; `expected_output`/`constraints`
  also framed on the way into the child's system context (via the same
  escape-preserving mechanism, per the diff's test assertions showing
  `Expected output:\n<untrusted-data>\nA list.\n</untrusted-data>`), while
  the task brief itself is deliberately left unframed since it is the
  child's own user message, read directly by a person; and the
  `is_delegation_tool_name` helper confirming both delegation tool names
  (`delegate_to_assistant`, `delegate_task`) receive identical treatment
  wherever a stored part is read back.

## Compatibility and configuration

**Explicitly ungated, live wire change**, per the PR's own warning: this
alters values the already-shipped @-mention delegation route emits today,
with no feature flag, and must deploy after (never before) the frontend
change in #1162 — the PR states `CHANGELOG.md` itself carries this
deploy-order note. No migration; purely a change to what values the
backend emits/persists for delegation tool parts.

## Release note disposition

Proposed category: Bug fixes (with a security dimension — prompt-
injection hardening for delegated-run results). Worth a mention: a
delegated run's outcome now distinguishes an infrastructure failure from
a run that simply had nothing to add or was stopped, and a delegate's
