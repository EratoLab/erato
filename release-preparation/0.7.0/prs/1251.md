# PR #1251: Show add-in UI in the host application's display language

- PR: https://github.com/EratoLab/erato/pull/1251
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a language mismatch inside Office/Teams task panes: `navigator.language`
reflects the OS or browser, not the host application's own display
language setting, so the add-in could show a different language than
the surrounding Outlook/Word/Teams chrome. Confirmed every claim
precisely:

- **`getSupportedLocale` resolves to `null` rather than forcing the
  default, confirmed exactly — the key correctness change**: the
  existing `getValidLocale` function is split into a new
  `getSupportedLocale(locale)` (exact match, then BCP-47-prefix partial
  match, else `null`) plus a thin `getValidLocale = getSupportedLocale(locale)
  ?? defaultLocale` wrapper preserving the old always-something
  behavior for existing callers. `activateHostLocale` uses the new
  function and returns early without calling `dynamicActivate` when it's
  `null` — leaving whatever locale `I18nProvider` already activated from
  the browser in place. This directly confirms "The library exports
  `getSupportedLocale` so an unsupported host language leaves the
  browser locale in place instead of forcing the default" — the critical
  distinction being that an unsupported *host* language no longer
  overrides an already-correct browser-detected one with English.
- **Resolution order — host, then browser, then English — confirmed
  exactly, by construction**: `I18nProvider` activates the browser
  locale first (unchanged, pre-existing behavior, confirmed by the new
  code never touching that path), and `activateHostLocale` runs
  afterward, only ever overriding when the host locale resolves to a
  genuinely supported value — so the three-tier fallback (host →
  already-active browser locale → `defaultLocale`, which is English per
  `getValidLocale`'s fallback) is exactly the chain the code implements.
- **Activated before children render, in both hosts, confirmed exactly,
  including the explicit comment stating the intent**: `OfficeProvider`
  calls `await activateHostLocale(displayLanguage)` inside its
  `Office.onReady().then(async (info) => {...})` callback, before any of
  the subsequent provider state is computed; `TeamsProvider` calls
  `await activateHostLocale(teamsContext.app.locale)` immediately after
  `app.getContext()` resolves, before its own `cancelled` check and
  subsequent state updates. Both call sites carry the identical comment
  "Children render in the host's language from their first paint" —
  matching "Once the host is ready... activates... before rendering
  their children" exactly.
- **Correct host API per surface, confirmed exactly**: `OfficeProvider`
  (shared by Outlook and Word per the PR's parenthetical) reads
  `Office.context.displayLanguage`; `TeamsProvider` reads
  `teamsContext.app.locale` — matching "OfficeProvider (Outlook, Word)
  now activates `Office.context.displayLanguage` and TeamsProvider
  activates the Teams `app.locale`" precisely.
- **Failures never block startup, confirmed exactly**: `OfficeProvider`
  wraps the `Office.context.displayLanguage` read itself in a try/catch
  (logging a warning on failure and proceeding with `null`), and
  `activateHostLocale` separately wraps its own `dynamicActivate` call in
  try/catch — two independent layers of failure-swallowing, consistent
  with the function's own doc comment "failures are swallowed: the
  language must never block the host from finishing its startup."
- Per the PR (not independently re-verified given remaining scope): the
  44-line new `activateHostLocale.test.ts` and 16-line `i18n.test.ts`
  additions (not read, though the functions they presumably test were
  read directly and match the described behavior).

## Compatibility and configuration

None. Pure frontend/add-in UX fix; `getValidLocale`'s existing callers
are unaffected by the refactor (confirmed it's now a thin wrapper
producing byte-identical results to the old implementation for every
input, since `getSupportedLocale(locale) ?? defaultLocale` reduces to
the same three branches the old function had, just restructured). No
backend, config, or wire changes.
