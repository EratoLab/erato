# PR #1157: Release the MCP consent card when the decision is accepted and stream the continuation

- PR: https://github.com/EratoLab/erato/pull/1157
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a real, reported UX bug: approving or denying an MCP tool call
left the consent card stuck on screen (buttons greyed out) until the
*entire* continuation finished generating, and the answer then appeared
all at once instead of streaming — because `McpToolApprovalCard`
previously `await`ed the full SSE response body rather than resolving as
soon as the server accepted the decision. This PR is unusually
extensively self-documented, including a full disclosed review round
that found and fixed eight further gaps in the first commit's optimistic
UI path. Given the very large, almost entirely frontend-state-machine
scope, review directly confirmed the one backend change:

- **The backend terminal-update fix, confirmed exactly**: before
  `run_continue_message_task` contacts the model, it now sends one
  `ToolCallUpdate` event for the gated call itself, with `status:
  if succeeded { ToolCallStatus::Success } else { ToolCallStatus::Error
  }` derived from `tool_use.status` — confirming both halves of the PR's
  claim: (1) this event is emitted *before* the model is contacted,
  mirroring the terminal update the main tool-execution loop already
  emits after every tool it runs (a code comment states this explicitly:
  "Mirrors the terminal update the main loop emits after every tool it
  runs"), and (2) a refused/failed gated call genuinely reports `Error`
  status (not a false `Success`), so a client seeding a "running"
  placeholder for this call correctly settles it to the error glyph
  rather than a green checkmark when the server actually refused the
  call.
- Per the PR (not independently re-verified given the very large
  frontend scope — a 307-line `useChatMessaging.ts` diff implementing an
  entire new optimistic-streaming/seeding/rollback state machine, plus
  eight additional disclosed fixes from a review round): the new
  `continueToolApproval` action opening the continuation through the
  normal SSE connection path and resolving on `onOpen` (server-accepted)
  rather than stream-close; the seeding mechanism reconstructing the
  continuation's buffer from the parked message's persisted parts plus
  the two parts the backend appends (decision, then the gated tool-use)
  so the card's visibility derives from the seeded decision part rather
  than local component state (stated as robust to a virtualization
  unmount); the wire-contract test
  (`test_continuestream_numbers_deltas_after_the_decision_and_call_parts`)
  pinning "first delta lands at persisted length + 2" for both approve
  and deny; the sidebar-status handling (`seedRunningLocal` replacing a
  tombstone on the streamed path, with `markApprovalDecided` kept only as
  the fallback-path mechanism); and the disclosed review-round fixes
  covering: a card hiding prematurely over a still-parked row when the
  worker later refuses an optimistically-accepted decision; a decision
  race during the park's own completion refetch; a stale "generating"
  sidebar status surviving a refused decision; the answer visually
  blinking at completion due to a stale-persisted-copy preference window
  (`getRenderableMessages` now keeping the buffer while `isFinalizing`);
  duplicated text after a dropped connection (the buffer rewound to its
  seed before a `resumestream` handoff); a decision left pending forever
  after an aborted connection (`onClose` before acceptance now rejects
  and rolls back); an `approve_always` roster cache-staleness issue; and
  a missing-local-copy-of-the-parked-message guard refusing the decision
  rather than seeding a broken buffer.
- **Explicitly disclosed follow-up, not done here**: `continueToolApproval`
  is optional on `ChatContextValue` with the pre-PR buffered behavior
  kept as a fallback for any host that doesn't wire it — both in-repo
  hosts (`ChatProvider`, `AddinChatProviderCore`) are confirmed wired
  (per the diff stat showing both files touched), making that fallback
  path (and `markApprovalDecided`, which only it still calls) dead code
  in this repository, with removing both flagged as a small separate
  cleanup not attempted in this PR.

## Compatibility and configuration

None breaking. Real, disclosed UX fix: approving/denying an MCP tool
call now releases the consent card immediately and streams the
continuation's answer token-by-token, instead of freezing the UI until
the entire response completed. No API contract change beyond the new
terminal `tool_call_update` event, additive to the existing SSE stream
shape.
