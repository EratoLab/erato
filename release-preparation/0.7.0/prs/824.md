# PR #824: Add hash suffix to react runtime module

- PR: https://github.com/EratoLab/erato/pull/824
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Customer themes and component kits

## Summary

Fixes a cache-invalidation gap for the component-kit React runtime script.
Previously `frontend/vite.config.ts` emitted this runtime at a fixed,
unhashed path, `public/common/assets/component-kit-react-runtime.js`; all
other build outputs use a content-hashed filename
(`[name]-[hash].js`). Because the runtime is imported by other generated
files, an unhashed runtime file could go stale across deployments — a
browser or CDN could keep serving an old cached `component-kit-react-runtime.js`
that no longer matches the hashed app bundle importing it, since only the
importing files' hashes would change, not the runtime's own URL.

`vite.config.ts` now emits the runtime with a content hash too
(`component-kit-react-runtime-[hash].js`). Since the backend's HTML
post-processing (`inject_environment_script_tag` in
`backend/erato/src/frontend_environment.rs`) previously hardcoded the old
static filename when injecting the `<script>` tag for component kits, it
now instead detects the runtime's actual hashed path from the
`<link rel="modulepreload" href="...">` tag Vite emits for it (since the
main app itself also imports the runtime), and falls back to the old
static path only if no such hashed link is found (`LEGACY_COMPONENT_KIT_REACT_RUNTIME_SCRIPT_PATH`,
preserved for backward compatibility with frontend bundles built before
this change).

## Compatibility and configuration

No configuration keys or migrations. This is a frontend build-output and
backend HTML-injection fix; not independently observable by operators
beyond the runtime script's filename changing on each build. Because the
backend detects the hashed runtime path dynamically from the served HTML
rather than hardcoding it, the frontend and backend should generally be
deployed as matching versions as usual for this and other frontend/backend
paired changes this release; the fallback path exists specifically so an
older (pre-fix) frontend bundle still works if served by this backend
version.
