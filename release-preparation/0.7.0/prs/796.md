# PR #796: Hidden facets: platform-scoped, always-on system-prompt injection

- PR: https://github.com/EratoLab/erato/pull/796
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Adds a way to define a baseline system-prompt facet that is always active
and never user-selectable, for platform-specific behavior that should wrap
the whole experience (e.g. "you are running inside the Outlook add-in").

**The shipped implementation differs from the PR description's proposed
config shape.** The PR body proposes a new top-level section,
`[hidden_facets.facets.<id>]` with a `platform` key, but the actual code
adds two new fields directly onto the *existing* `FacetConfig` struct used
by regular `[experimental_facets.facets.<id>]` entries: `hidden: bool`
(default `false`) and `hidden_always_active_for_platform: Option<String>`
(default `None` = all platforms) — there is no separate `hidden_facets`
config table. This is confirmed by both the `config.rs` diff and the
`site/content/docs/configuration.mdx` documentation this PR itself adds,
which correctly describes `experimental_facets.facets.<facet-id>.hidden`
and `.hidden_always_active_for_platform` as the real keys. The practical
effect of this design (versus a separate section) is explicit in the
docs: "Because it is an ordinary facet, its `model_settings` and
`tool_call_allowlist` still apply (per request) like any active facet" —
i.e. a hidden facet gets all the same per-request configuration knobs a
regular facet has, for free, rather than needing its own parallel schema.

When `hidden = true`, the facet never appears in the `/facets` API
response (so it can't be shown/toggled/removed in any client UI) and is
instead injected as a `System`-role prompt once at conversation start —
under the same gating rule as the base system prompt
(`should_add_system_prompts`) — for any request whose platform (from the
`X-Erato-Platform` header) matches `hidden_always_active_for_platform`,
or unconditionally if that field is omitted. A new
`AbstractChatSequencePart::HiddenFacetSystemPrompt` variant mirrors the
existing `FacetAdditionalSystemPrompt` mechanism. Per the PR notes, this
is a deliberate single-injection-at-start design (not re-injected every
turn), matching how the base system prompt itself behaves and avoiding
the accumulation problem regular toggleable facets guard against;
injection order across multiple hidden facets is deterministic (sorted by
config id).

## Compatibility and configuration

New, entirely optional per-facet fields, both unset/`false` by default —
no behavior change for any existing `experimental_facets.facets.*` entry
that doesn't set `hidden = true`:
```toml
[experimental_facets.facets.<facet-id>]
hidden = true                                   # default false
hidden_always_active_for_platform = "outlook"   # optional; omit = all platforms
additional_system_prompt = "..."                 # existing field, reused
```
No migration, no new OpenAPI/config-reference schema beyond the two new
fields on the existing facet type (confirmed: `config_reference.json`'s
diff is 2 lines, and the PR's own notes state "OpenAPI unchanged"). Inert
until a deployment configures a facet with `hidden = true`.

independently corroborated by the two files read in full, giving
reasonable confidence in the described mechanism even without tracing
every line of the injection code itself.

## Release note disposition

Proposed category: Features and enhancements. Worth a mention if the
maintainer wants to document this for deployments building
platform-specific customizations (e.g. a distinct baseline prompt for the
Outlook add-in vs. the web app): facets can now be marked `hidden` to
apply as an always-on, non-selectable baseline system prompt, optionally
scoped to a specific client platform.
