# PR #786: Client-executed tool round-trip for action facets (client_tools)

- PR: https://github.com/EratoLab/erato/pull/786
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: Outlook scheduling and shared mailboxes

## Summary

Backend foundation for `client_tools`: tools the model calls mid-turn that
execute on the client (add-in/web app) rather than the backend or an MCP
server, with the result fed back into the same agentic loop — conceptually
"an MCP tool, but client-side," distinct from the pre-existing
`propose_client_action` mechanism (client-executed but terminal/one-way,
requiring user confirmation, per `CLIENT_ACTION_TOOL_NAME` referenced from
#894). Motivating use case (per the PR body): an Outlook facet fetching
the user's calendar availability — only reachable client-side via
MSAL/EWS — mid-reasoning, before proposing meeting times.

Confirmed against the code: tools are declared top-level under
`[client_tools.tools.<id>]` (`ClientToolsConfig`/`ClientToolConfig` in
`backend/erato/src/config.rs`), keyed by a config id distinct from the
model-facing `name` (so tools remain overrideable/composable across config
files, matching how `chat_providers` works). Each tool has `name`
(model-facing, validated non-empty/trimmed/not the reserved
`propose_client_action` name), an optional `namespace` (default
`"client"`, used only for `tool_call_allowlist` selection, e.g.
`outlook/*`), `description`, `parameters` (a JSON Schema string, parsed
and validated as a JSON object at config load), and an optional
`timeout_ms` (defaults to **60 seconds**,
`DEFAULT_CLIENT_TOOL_PARK_TIMEOUT_MS = 60_000`, confirmed in
`message_streaming.rs`). The `namespace/name` pair must be globally
unique across all client tools (enforced at config-load time via a
`HashSet`, panicking on a duplicate). `ActionFacetConfig` gains a new
`tool_call_allowlist` field using the existing `namespace/*` /
`server/tool` pattern syntax; per the code comment, this allowlist "also
selects MCP tools" — i.e. it's a shared, additive selection mechanism
across both client tools and MCP tools, not a client-tools-only concept.

Mechanically: the backend offers allowed client tools to the model
alongside MCP tools; when the model calls one, the generation loop parks
(`select! { result, abort, timeout }` on a per-call channel attached to
`StreamingTask`) and emits a `client_tool_call` event instead of executing
anything itself. The client executes the tool and calls the new
`POST /me/messages/clienttoolresult` endpoint (`client_tool_result`
handler, confirmed wired into the router in
`backend/erato/src/server/api/v1beta/mod.rs`) to deliver the result, which
resumes the parked turn. If the per-tool timeout elapses first, the loop
injects an error tool response and continues rather than hanging
indefinitely. Per the config type's own doc comment: "Returning client
tools MUST be read-only/idempotent: a backend restart drops the parked
turn, so a client may re-execute on recovery" — i.e. this mechanism is
explicitly not meant for stateful/mutating operations (those remain the
job of the terminal `propose_client_action` path).

This PR is explicitly inert by design until a consumer opts in: no
existing action facet sets `tool_call_allowlist`, so no behavior changes
for any existing deployment purely from this PR merging — it's foundation
for the Outlook scheduling feature work later in this same cluster (#795,
#799-#804, #818-#819).

## Compatibility and configuration

New, entirely optional top-level config section, empty/absent by default:
```toml
[client_tools.tools.<id>]
name = "fetch_availability"
namespace = "outlook"           # optional, defaults to "client"
description = "..."
parameters = '{ "type": "object", "properties": { ... } }'
timeout_ms = 120000              # optional, defaults to 60000
```
And a new field on existing action-facet configuration:
```toml
[experimental_facets.facets.<id>]
tool_call_allowlist = ["outlook/*"]   # selects client tools AND MCP tools; empty by default
```
No migration. No breaking change: with no client tools configured and no
facet's `tool_call_allowlist` populated (the default for every
pre-existing facet), this PR has zero observable effect. A misconfigured
client tool (duplicate `namespace/name`, empty/whitespace name, reserved
name, or non-object `parameters`) fails backend startup with a clear
panic message, rather than being silently accepted.
