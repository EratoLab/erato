## Summary

Per the PR's title and its brief body ("~covers 80% of memory usage";
"Related Linear issue: ERMAIN-808"). Adds two new internal crates,
`erato_memory` and `erato_memory_derive` (a `HeapSize` derive macro
applied — confirmed via diff — across dozens of existing config, policy,
and MCP-related structs throughout `erato_config/src/config.rs`), plus a
new `backend/erato/src/metrics/{memory,owned,components,process,exporter}.rs`
module set (~1,750 new lines combined) and a 244-line addition to
`site/content/docs/integrations/prometheus.mdx`, satisfying this repo's
own convention (per `AGENTS.md`) of updating that doc alongside metric
changes.

- **New always-on gauges, confirmed exactly via the docs diff**:
  `erato_owned_memory_bytes` (labels `owner`, `kind` ∈
  {`capacity`,`estimated`}), `erato_owned_memory_unmeasured_objects`,
  `erato_owned_memory_tracked_objects`, `erato_owned_memory_sample_stale`
  — these require only the existing Prometheus integration, "no profiling
  feature, special allocator, Linux requirement, or
  `ERATO_MEMORY_COMPONENTS` setting" (quoted directly from the new docs).
  They report ~20 named owner paths (app state caches, shared
  distribution/registry/policy/guardrails state, per-request working
  buffers, MCP stateless caches, upload buffers) using periodic
  nonblocking-lock snapshots targeting a 5-second cadence.
- **A separate, deeper opt-in tier, confirmed exactly via the docs**: a
  Linux `profiling` build with `ERATO_MEMORY_COMPONENTS=1` plus the
  Prometheus integration additionally exposes
  `erato_allocator_memory_bytes` (Linux `profiling` builds only) for
  per-component allocator attribution — this is a separate, more invasive
  opt-in, not the default behavior.
- Per the PR (not independently re-verified, given the size of this
  change): the actual sampling/weak-reference/deduplication implementation
  in the new `metrics/` modules and `erato_memory` crate, the ~1,750 lines
  of new Rust across those files, and the new
  `backend/erato/tests/component_memory.rs` (137 lines) integration test.

## Compatibility and configuration

None breaking. The baseline owned-memory gauges are always-on once the
existing Prometheus integration (`[integrations.prometheus].enabled`,
pre-existing) is configured — no new config key gates them, per the docs.
The deeper per-component attribution requires an explicit
`ERATO_MEMORY_COMPONENTS=1` environment variable on a Linux `profiling`
build specifically, so it cannot accidentally activate on a standard
deployment.
