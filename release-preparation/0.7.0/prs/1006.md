# PR #1006: Bound delegated runs: in-task deadline, reaper backstop, background concurrency cap (ERMAIN-636)

- PR: https://github.com/EratoLab/erato/pull/1006
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: Delegation

## Summary

Restores the two safety bounds that #1005's detached background dispatch
removed: previously, an *awaited* delegated run was bounded by the
dispatch loop's own timeout race and by the fact that only one child could
exist per waiting user turn; detaching a background run removed both.
This layer, gated behind the still-default-off `allow_background` flag,
adds three independent mechanisms — confirmed by direct reading of all
three.

- **The run deadline moved inside the child task itself, confirmed
  precisely**: `run_delegated_child` now races its own generation future
  against `sleep(run_timeout_seconds)` via `tokio::select!`, and on
  timeout, requests a cooperative abort and then **awaits the same run
  future to completion** — so the abort's wind-down (persisting whatever
  partial answer exists) happens in the child's own task, in its own
  failure domain, regardless of whether anything is still awaiting it.
  The pre-existing dispatch-side timeout race is kept, but confirmed
  re-purposed (via a new code comment) as classification-only: it exists
  solely so an *awaited* run's result can be labeled `timeout` for the
  parent's tool response, while the actual enforcement now lives
  exclusively in the child task's own timer.
- **A maintenance-loop backstop for a wedged (not dead) replica, confirmed
  via the full SQL**: a new periodic query
  (`enqueue_overdue_delegated_run_aborts`) atomically inserts an `abort`
  command for every `running` generation whose provenance is `delegation`,
  **not adopted** (`provenance.adopted_at IS NULL` — matching the stated
  rule that an adopted run is the user's own conversation now, with no
  deadline, same as any ordinary chat), started more than `run_timeout +
  2×heartbeat_interval` ago, and with no already-pending unconsumed abort
  command (avoiding redundant stacking). Confirmed this reuses the
  existing 100ms cross-replica command-listener infrastructure with zero
  new plumbing. Confirmed the gating is on `assistants.delegation.enabled`
  specifically — **not** `allow_background` — via the `state.rs` wiring
  (`config.assistants.delegation.enabled.then_some(run_timeout_seconds)`),
  matching the stated rationale that an *awaited* run stuck on a wedged
  replica benefits from this backstop equally, independent of whether
  background mode is even enabled.
- **Background concurrency cap, confirmed precisely**: a new
  `assistants.delegation.max_concurrent_background_runs` (default 5, `0`
  disables) is enforced only for `Background` mode, before the child chat
  is even created, via two soft (racy-by-design, non-atomic) checks: an
  in-memory per-turn atomic counter checked *first* (since a launch made
  moments earlier within the same turn wouldn't yet be visible as a
  database row), incremented only *after* a successful launch (confirmed
  via `fetch_add` placed immediately before returning the `Dispatched`
  outcome, so a failed launch never consumes a slot); then an owner-wide
  database count of currently-running background delegated runs
  (`count_running_background_delegated_runs`, riding the existing
  `idx_chats_delegated_runs` index from #979). Confirmed both refusal
  paths return distinct, deliberately different wording exactly matching
  the PR's stated reasoning: the per-turn refusal says "delegate the
  remaining work in a later message" (since more mentions can still be
  sent), while the owner-wide refusal says "wait for one to finish"
  (appropriate since that's a genuinely different constraint) — and the
  PR notes "wait" would be actively wrong advice for the per-turn case,
  since a background result never re-enters the turn regardless of how
  long the user waits.

## Compatibility and configuration

New, optional config field:
```toml
[assistants.delegation]
max_concurrent_background_runs = 5  # default; 0 disables (unlimited)
```
No behavior change for any deployment without `allow_background` enabled
(background mode stays gated off per #1004/#1005). The maintenance-loop
backstop is new infrastructure that activates whenever
`assistants.delegation.enabled` is true, regardless of `allow_background`
— an existing deployment with plain (awaited) delegation already enabled
gets this additional wedged-replica safety net automatically on upgrade.
