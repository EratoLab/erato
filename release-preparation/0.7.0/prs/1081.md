# PR #1081: Per-setting resolution orders + stable audience ids on the wire (dual-written, invisible at one setting)

- PR: https://github.com/EratoLab/erato/pull/1081
- Status: pending (diff reviewed)
- Category: Features and enhancements
- Theme: None

## Summary

Groundwork follow-up to the starting-assistant stack (#1071–#1077),
laying the schema for a future second policy-driven setting while keeping
current behavior byte-identical and mixed-version-deployment safe.
Confirmed by reading the complete `experience_policy.rs` diff and the
relevant `starting_assistant.rs` change:

- **Wire additions, confirmed exactly**: `ExperienceAudience` gains
  `#[serde(default)] pub id: Option<String>` (opaque, no semantic
  interpretation beyond uniqueness), and `ExperiencePolicyDocument` gains
  `#[serde(default)] pub setting_orders: HashMap<String, Vec<String>>` —
  a per-setting, first-match-wins order expressed as a flat list of
  audience ids. `audiences` stays name-keyed (not re-keyed by id).
- **Parse-time validation, confirmed exactly**: a blank id, a duplicate
  id across audiences, and a `setting_orders` entry naming an unknown id
  or repeating an id within one list all reject the whole document.
- **The agreement invariant, confirmed exactly and matching the PR's own
  description precisely**: whenever `setting_orders` carries the
  `starting_assistant` key (checked via `document.setting_orders.get(...)`
  — key *presence*, including an empty list), the document is rejected
  unless that order and `priority_order` have equal length **and**, at
  every position, the audience id at position *i* in `setting_orders`
  actually belongs to the audience named at position *i* in
  `priority_order`. Confirmed this specifically means an empty
  `setting_orders["starting_assistant"]` beside a non-empty
  `priority_order` is rejected (unequal lengths), precisely the
  "deliberately strengthened beyond presence-only" case the PR calls out
  — a document cannot carry a new-key-only or empty-new-key-beside-full-
  legacy-list shape that would resolve differently on old vs. new
  readers.
- **Single home for resolution precedence, confirmed exactly via
  `resolution_order_for`**: builds an id→`(name, audience)` index from
  `policy.audiences` (with deterministic tie-breaking — the
  lexicographically smallest name wins a duplicate id, confirmed matching
  the doc comment's stated robustness for documents the parser itself
  would already reject), then yields entries from `setting_orders[setting]`
  when that key is present, falling back to `priority_order` *only* when
  the key is absent *and* `setting == STARTING_ASSISTANT_SETTING` — so no
  other future setting silently inherits the legacy list. Unknown ids/names
  in either path are skipped via `filter_map`, keeping resolution total
  even over an already-parsed (and thus already-validated) document.
- **`starting_assistant.rs`'s `match_winning_audience`, confirmed
  rewritten** to call `resolution_order_for(policy,
  STARTING_ASSISTANT_SETTING).find(...)` in place of the previous direct
  `policy.priority_order.iter().find_map(...)` — the matching predicate
  itself (`is_active_at(now) && subjects.any(matches)`) is unchanged, so
  behavior is identical whenever `setting_orders["starting_assistant"]`
  is absent (today's only possible state, since nothing writes this field
  yet). Confirmed the response shape carries no new `audience_id` field —
  the PR's stated "smallest wire change" claim.
- Per the PR (not independently re-verified): the three alternative
  designs considered and rejected (re-keying `audiences` by id — would
  strand every already-deployed pre-change erato at no-match, i.e.
  org-wide silent welcome-screens; pairwise winner entries — cannot
  guarantee a total acyclic order without a second resolver; per-audience
  rank numbers — renumbering churn); the disclosed "legacy-drop condition"
  design note (recorded so the dual-write isn't accidentally permanent,
  gated on a future reader-floor migration, not merely the second
  setting's arrival); and the new
  `experience_policy_resolution_contract.json` fixture (166 lines, not
  read) presumably shared with the admin panel's own test suite across
  repos.

## Compatibility and configuration

None. Purely additive schema (both new fields `#[serde(default)]`,
absent in every document written before this PR and by every writer
until the cross-repo admin panel increment ships). No migration, no API
wire-contract change. Behaviorally invisible at the currently-live single
setting, confirmed by the unchanged resolution predicate and the
fallback-only-when-absent logic in `resolution_order_for`.
