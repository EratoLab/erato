# PR #1286: Take organization user editor grants into account for assistant edit sharing

- PR: https://github.com/EratoLab/erato/pull/1286
- Status: pending (diff reviewed)
- Category: Bug fixes
- Theme: None

## Summary

Fixes a policy evaluation gap where users who had editor-level access to an assistant through their organization membership (via `organization_user_id`) were not recognised as editors when the system checked sharing permissions. The edit menu therefore incorrectly hid editing options for these users.

**Root cause.** The OPA policy engine constructs a fact set for each authorization check that includes the subject's `organization_group_ids` and individual `groups`, but was missing the subject's `organization_user_id`. The OPA rules in `backend.rego` that grant edit permission to organization-wide editors rely on this identifier to determine whether the user is covered by an org-level grant. Without it, the policy saw only per-user and per-group grants and denied edit access to org-level editors.

**Fix.** Two changes:

1. **Engine layer**: `PolicyEngine::authorize` and `PolicyEngine::check_filtered_facts` now accept an `organization_user_id: Option<&str>` parameter and include it in the JSON input sent to OPA as `"organization_user_id": subject.organization_user_id()`. All internal call sites are updated to pass the value.

2. **OPA policy**: `backend.rego` is updated (27 lines changed) to recognize the new `organization_user_id` input and grant edit access when that user ID matches an organization-level editor grant.

3. **Model layer**: The `assistant.rs` model adds a field to carry the organization user context through to the policy check.

4. **Tests**: 124 new lines of integration tests in `assistants.rs` covering the org-level editor grant scenario end-to-end.

## Compatibility and configuration

No config changes. The fix corrects a policy evaluation bug; all existing sharing configurations continue to work, and org-level editor grants now function as intended.

## Evidence and review

- The `organization_user_id` parameter is threaded through `authorize` → `authorize_full` → `check_filtered_facts` and included in the OPA input JSON.
- `subject.organization_user_id()` returns `Option<&str>`; when `None`, OPA receives `null` and the org-level rules simply do not match — safe for subjects that are not associated with an organization.
- The rego policy's new condition checks `input.organization_user_id` against the grant's user list; no existing rules are modified.

## Release note disposition

Mention in Bug fixes: Organization-level editor grants for shared assistants are now correctly recognized when determining edit permissions.
