## Summary

Per the PR's detailed body (native-gate tested, treated as reliable given
the specific gate-report citation convention used throughout this Word
add-in cluster, not independently re-verified line-by-line): fixes
in-place Apply/Revert falsely refusing or misreporting success when Word
itself silently rewrites housekeeping metadata that isn't a real content
change (list fingerprint IDs, table `tblLook` defaults, theme-font
language regions on web; re-detected `w:lang` after an import on
PC/Mac). A new `WORD_HOUSEKEEPING` registry
(`frontend/src/lib/wordReview/wordHousekeeping.ts`, 264 new lines) names
each such known-harmless signature so the fingerprint/write-verification/
staleness checks can ignore exactly those fields while still catching a
genuine language change the user makes themselves.

- **Confirmed via `config.rs` (6-line diff)**: Word for the web's default
  `whole_document_import` policy changes from `Confirm` to `Off` — the
  code comment explains why: "Word for the web rewrites styles, settings
  and comment metadata on every import," making the whole-document
  import path itself unable to be verified as faithful, so it's disabled
  by default on that host rather than offered with a confirmation prompt.
  PC/Mac defaults (`in_place: false`, `whole_document_import: Allowed`)
  are unchanged by this specific PR (changed next, in #1380).
- 267 new lines of dedicated `wordHousekeeping.test.ts` coverage, per the
  PR, proves a real change still shows through for each registered rule.

## Compatibility and configuration

**Default behavior change, not a breaking config removal**: Word for the
web deployments relying on the previous `whole_document_import = Confirm`
default (prompting the user before a full-document rewrite) will now see
that path refused outright by default. An explicit
`integrations.ms_office.addin.default_settings.word_apply.whole_document_import
= "confirm"` override (if such an explicit per-host override key exists —
not confirmed in this diff; the change here is only to the hardcoded
`WEB_DEFAULTS` constant) would be needed to restore the old prompt-based
behavior. No database migration.
